> Machine-readable architecture, commands, conventions, and constraints for AI coding agents.

## Project Overview

Docuvia is a universal VCS knowledge graph engine. It ingests Git commit history and spec documents, auto-generates L1/L2/L3 structured knowledge nodes via OpenAI, and exposes them through a human review workflow and MCP tool endpoints. Stack: TypeScript monorepo (pnpm workspaces, Node.js 24), Express 5 API server, React + Vite frontend, PostgreSQL + Drizzle ORM, Zod validation, OpenAI via Replit AI Integrations. All API types generated from a single OpenAPI spec via Orval.

## Commands

### Install

```bash
pnpm install
```

### Dev

```bash
pnpm --filter @workspace/api-server run dev   # API server on port 8080
pnpm --filter @workspace/kg-engine run dev    # Frontend on port 18774
```

### Build (typecheck + compile all packages)

```bash
pnpm run build
```

### Typecheck only

```bash
pnpm run typecheck
```

### Codegen — regenerate React Query hooks and Zod validators from OpenAPI spec

```bash
pnpm --filter @workspace/api-spec run codegen
```

Run this after **every** change to `lib/api-spec/openapi.yaml`.

### DB push — apply schema to dev DB

```bash
pnpm --filter @workspace/db run push
# Force (destructive) push:
pnpm --filter @workspace/db run push-force
```

### Format

```bash
pnpm prettier --write .
```

### Test

```bash
# One test file exists (Vitest + supertest):
pnpm --filter @workspace/api-server exec vitest run
```

> **Note**: Only `artifacts/api-server/test/extensions_vscode.test.ts` exists. No test runner is configured at the workspace root. No tests exist for routes, schemas, or pipeline logic outside this file.

### Knowledge Graph Structure

- **L1 Tags** — global classification pool, shared across all projects, human-anchored
- **L2 Nodes** — Package / Module / Component, scoped per project
- **L3 Nodes** — Implementation rules, decisions, rationale, scoped per L2 node
- Every L2/L3 node carries `aiGenerated`, `confidence`, and `needsReview` flags
- `node_links` table stores directed module dependency edges for impact analysis
- `activity_log` is append-only (denormalized) — the dashboard reads from this table

### Commit Signal Scoring

Commits are scored 0.0–1.0 at ingestion time:

- Noise patterns (merge / chore / ci / wip) → score ≤ 0.1
- Signal patterns (feat / fix / decision) → boosted score
- Valid (high-signal) threshold: ≥ 0.4

### MCP Tool Endpoints

All GET endpoints available at `/api/mcp/<tool>`. Agentic RAG at `POST /api/mcp/query`.

| Tool                  | Route                          |
| --------------------- | ------------------------------ |
| `list_projects`       | `GET /api/mcp/list_projects`   |
| `search_knowledge`    | `GET /api/mcp/search_knowledge`|
| `get_dependencies`    | `GET /api/mcp/get_dependencies`|
| `impact_analysis`     | `GET /api/mcp/impact_analysis` |
| `get_decision_record` | `GET /api/mcp/get_decision_record` |
| Agentic RAG query     | `POST /api/mcp/query`          |

### AI Generation Pipeline

`POST /api/generate` triggers: L1 Tagger → L2 Extractor → L3 Generator (in sequence). L3 is the most LLM-intensive step — recommend a stronger model for production use.

## Conventions

- **Contract-first API**: All API changes must start in `lib/api-spec/openapi.yaml`. Never write types by hand that Orval can generate.
- **Zod version split**: Use `zod` (not `zod/v4`) in `artifacts/api-server/` routes — esbuild cannot resolve the `zod/v4` subpath export. Use `zod/v4` freely in `lib/` packages.
- **TypeScript config**: Strict mode — `noImplicitAny`, `strictNullChecks`, `alwaysStrict`, `useUnknownInCatchVariables`. Module resolution: `bundler`. Target: `es2022`.
- **OpenAPI body schema names**: Use entity-shaped names (e.g., `ProjectInput`, not `CreateProjectBody`) to avoid Orval TS2308 name collisions.
- **Build system**: API server uses esbuild (CJS bundle, `build.mjs`). Frontend uses Vite. Root `pnpm run build` runs `typecheck` first, then builds all packages via `-r`.
- **Package manager**: pnpm only. The `preinstall` script rejects npm and yarn.

## Important Constraints

### Do not edit — generated files

- `lib/api-client-react/src/generated/` — regenerated every time you run codegen
- `lib/api-zod/src/generated/` — regenerated every time you run codegen
- `pnpm-lock.yaml` — managed exclusively by pnpm

### Supply-chain protection

`pnpm-workspace.yaml` enforces `minimumReleaseAge: 1440` (1 day) for all packages. Do not disable this. Use `minimumReleaseAgeExclude` sparingly (only for packages from trusted organizations with an established security posture) and remove the exclusion once the 1-day window has passed.

### integrations-openai-ai-server

The tsconfig for this package has `"types": []` to avoid TS2688 node type conflicts. Do not add `@types/node` to this package.

## Common Gotchas

- **Run codegen after every spec change**: Skipping `pnpm --filter @workspace/api-spec run codegen` after editing `openapi.yaml` leaves React Query hooks and Zod validators out of sync with the API.
- **DB push required after schema changes**: `pnpm --filter @workspace/db run push` must run before the server will reflect schema changes in dev.
- **Tailwind v4 `dark` class**: Cannot use `dark` as a `@apply` utility in Tailwind CSS v4. Use the `dark:` prefix variant directly in JSX/TSX instead.
- **`AbortError` import**: In `lib/integrations-openai-ai-server`, import `AbortError` as a named export from `p-retry` — `pRetry.AbortError` does not work.
- **Default LLM model**: The active implementation defaults to `gpt-5.2`. The roadmap documentation references `gemma3:12b` via Ollama — these differ. Use `gpt-5.2` unless per-project `llm_configs` overrides it.
- **`PORT` env var is mandatory**: The API server (`artifacts/api-server/src/index.ts`) throws immediately on startup if `PORT` is not set.
- **Monorepo filter flags**: Use `pnpm --filter @workspace/<name>` to target individual packages. Use `pnpm -r` to run across all packages.
- **`pnpm -w`**: Use `-w` (workspace root) flag when running scripts defined in the root `package.json`.

## Agentic Workflow

This repository uses a closed-loop multi-agent orchestration system:

1. **Requirement Analyzer** — Parses user requests, produces AI implementation documents
2. **Specialist Developer** (Backend / Frontend / DB / API Architect) — Implements changes
3. **Task Verifier** — Validates the implementation against requirements; re-dispatches on failure

Agents are defined in `.github/agents/`. The orchestrator instructions live in `.github/copilot-instructions.md` and `.github/instructions/orchestrator.instructions.md`.

When implementing a feature, prefer dispatching to the appropriate specialist agent rather than implementing directly. Always verify with Task Verifier after implementation.
