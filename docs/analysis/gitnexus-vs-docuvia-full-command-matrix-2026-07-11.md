# GitNexus vs Docuvia — Full Command-Surface Matrix (2026-07-11)

> **Status**: Findings-only comparison, follow-up to [`docuvia-cli-vs-gitnexus-2026-07-10.md`](docuvia-cli-vs-gitnexus-2026-07-10.md). That audit covered the commands both tools share in depth (crash bugs, stubs, coverage gaps); this document's purpose is different — enumerate **every** GitNexus command, map it to its Docuvia equivalent (blank if none exists), and give each row its own function/performance/issues/recommendation assessment, so nothing in GitNexus's surface is silently left uncompared.

## Methodology

- **GitNexus surface**: `gitnexus@1.6.9` (globally installed), enumerated directly via `gitnexus --help` on 2026-07-11 — 23 commands + `help`. Matches the prior audit's version exactly, no drift.
- **Docuvia surface**: `artifacts/cli/src/constants/cli-commands.ts`'s `CLI_COMMANDS`/`CLI_COMMAND_DESCRIPTIONS` — 10 commands (`init`, `analyze`, `query`, `review`, `snapshot`, `sync`, `status`, `clean`, `export --topology`, `mcp`), read directly from source, current as of this session (post the 2026-07-11 fixes to `init`/`snapshot`/logging — see [`implement_init_gating_snapshot_perf_and_command_logging.md`](../ai_plans/implement_init_gating_snapshot_perf_and_command_logging.md)).
- **Performance figures** are cited from whichever prior measurement is freshest and labeled with its date/fixture; figures not re-measured this session are marked "not re-measured" rather than guessed.
- **"—" in the Docuvia column** means no equivalent command or flag exists at all, not "exists but broken."

**This session's `snapshot` performance fix** (see [`implement_init_gating_snapshot_perf_and_command_logging.md`](../ai_plans/implement_init_gating_snapshot_perf_and_command_logging.md), Part 2): root-caused the slowness to (a) a guaranteed-to-fail `fs.readFile` pre-check on every symbol's markdown file (tempDir is always freshly created empty, so the check can never succeed) and (b) fully sequential, unbatched filesystem I/O across tens of thousands of small files in both the markdown-write and orphan-branch-packing passes. Fixed by removing the dead read and parallelizing both loops with bounded concurrency. Measured on a synthetic 3,000-file/18,000-node fixture: the persist+pack phase this fix touches went **29.8s → 11.4s (2.6×)**; end-to-end `snapshot` wall-clock went 124.0s → 103.4s, diluted by a separate, out-of-scope bottleneck newly discovered during this fix — `FileDiscoveryService`'s git-native path spawns one `git cat-file` subprocess per file, sequentially, which dominates wall-clock on fixtures with many low-symbol-density files. **Not yet re-measured against the real `hermes-agent` checkout** at current (broader) extraction settings — the synthetic-fixture numbers demonstrate the fix works but aren't a direct like-for-like replacement for the original 6-min/134s comparison.

## Summary

Of GitNexus's 23 commands (+`help`):

- **4 map cleanly**: `mcp`, `status`, `clean`, `help`.
- **5 map partially** (real but narrower functionality): `setup` (bundled into `init`), `query`/`context` (name-lookup + edges, no concept-search/execution-flow layer), `detect-changes` (file-level not hunk-level), `augment` (exists only inside a generated hook, not user-invokable).
- **1 is a near-zero-cost gap**: `impact` — the backend logic (`QueryService.getImpact()`) already exists and is already used internally by `review`; it just isn't exposed as its own command. Highest-value/lowest-effort item on this matrix.
- **1 is a real, actionable gap with no backend work started**: `uninstall` — increasingly important now that `init` writes more files than ever (8 repo-scoped paths + 1 gated global path after this session's fixes).
- **2 are meaningful but larger features**: `doctor`, `wiki`.
- **1 is a genuinely new capability**: `trace` (graph pathfinding).
- **6 depend on a multi-repo registry Docuvia's architecture doesn't have**: `list`, `remove`, `index`, `group`, and (partially) `serve`/`publish` — a design difference, not a bug, but worth documenting explicitly so users don't search for commands that will never exist under the current local-first model.
- **1 is architecturally inapplicable**: `cypher` (no graph-query engine to expose).
- **1 is internal tooling, not a real gap**: `eval-server`.
- **1 is under-specified relative to GitNexus's flags**: `clean` (missing `--force`/`--all`, cosmetic).

Docuvia additionally has 2 commands (`snapshot`, `sync`) with no GitNexus equivalent at all — its git-native, server-less distribution model is a genuine differentiator, not a gap.

**If picking a single next action from this matrix**: wire `docuvia impact <target>` — it reuses fully-built, already-tested logic (`QueryService.getImpact()` + `review`'s existing risk thresholds) for close to zero new backend work, the same pattern that made this session's `query`→`getContext()` wiring cheap and low-risk.
