## 3. Observations & Findings (C#-specific)

> General findings about Docuvia2/GitNexus/Graphify/CRG that surfaced during this pass but aren't specific to C# (e.g. query-engine bugs, uninstall cleanup, GitNexus's registry model, Graphify's CLI scope) have moved to [`README.md` §4](./README.md#4-cross-tool-findings-from-language-benchmark-passes) so this report stays scoped to the C# results.

- **Benchmark data comparison (PowerShell & Orleans)**
  - PowerShell: Docuvia2 **26,451** nodes / **39,419** edges; GitNexus **40,211** / **124,114**; Graphify (AST-only) **22,318** / **44,334**; CRG **22,370** / **122,020**.
  - Orleans: Docuvia2 **47,703** / **55,287**; GitNexus **61,604** / **132,184**; Graphify (AST-only) **41,425** / **65,938**; CRG **38,815** / **158,252**.
  - Two clusters emerge: GitNexus and CRG converge on similarly dense graphs (~122K–158K edges) despite different node-counting granularity, while Docuvia2 and Graphify's AST-only pass sit in a lighter ~39K–66K-edge band — expected for Graphify (missing the semantic/cross-file layer the full product would add), but notable that Docuvia2's default view lands in the same ballpark despite being a fully deterministic, LLM-independent product.
  - Blast radius: Docuvia2 **and** GitNexus both return surprisingly shallow/zero "upstream" impact for foundational base symbols (`PSCmdlet`: Docuvia2 1 file, GitNexus 0 impacted; `IGrain`: Docuvia2 1 file, GitNexus 5 direct implementors once disambiguated), where CRG's `impact` surfaces hundreds-to-thousands of transitively-impacted files for the same symbols. Either CRG's traversal is fundamentally broader/more inclusive by default, or Docuvia2/GitNexus's "upstream" direction means something narrower (direct inheritance only) than CRG's fuller transitive closure — worth a deeper follow-up if a genuine apples-to-apples impact comparison is wanted.
  - CRG remains the only tool with out-of-the-box wiki + real visual-export artifacts in this no-LLM comparison; GitNexus's wiki needs an LLM and Docuvia2 has no wiki command at all.

- **Root cause of Docuvia2's edge-count gap (Tier A vs. Tier B / LSP)** — traced by reading the analyze pipeline rather than re-running the benchmark:
  - Docuvia2 splits graph-building into **Tier A** (default `docuvia analyze` — tree-sitter AST, same-file edges plus heuristic cross-file `calls` that stay unresolved/`INFERRED`) and **Tier B** (`docuvia analyze --escalate-to-lsp` — a real language-server call for LSP-precision cross-file resolution; see [`analyze-workflow.ts`](../../lib/ui-core/src/workflows/analyze/analyze-workflow.ts)'s `execute()` dispatch and [`analyze.ts`](../../artifacts/cli/src/commands/analyze.ts)).
  - **This benchmark never passed `--escalate-to-lsp` for any tool/language**, so only Tier A ever ran for Docuvia2 — by design this is opt-in, not automatic (`--escalate-to-lsp` is described as "the core quality engine" in `docs/gitbook/adr/impact/IMPT-002-lsp-for-absolute-quality.md`). That fully accounts for the banding above: Docuvia2's Tier-A-only counts sit with Graphify's admittedly-AST-only pass, not with GitNexus/CRG. This is **not evidence of a broken/unwired C# LSP** — Tier B was simply never invoked this session, for any of the eleven supported languages, not just C#.
  - **5 blockers found chasing C# Tier B (2026-07-24 → 2026-07-29), all fixed**:
    1. ~~`csharp-ls` not on `PATH`~~ — fixed 2026-07-28 (NuGet/tool-manifest state on this machine, not a code bug).
    2. ~~`dotnet tool install` failure~~ — same fix as (1), was transient.
    3. ~~Orleans fails the `.slnx` marker-file check~~ — fixed 2026-07-24, commit `f816706` (`csharp-lsp-preflight.ts` now recognizes `.slnx`, not just `.sln`/`.csproj`).
    4. ~~Tier B queue empty for any freshly-built repo~~ — fixed 2026-07-29, commit `f5293b04` (full ingestion + `ADDED`-status files now queue for every Tier-B language, not just C#).
    5. ~~Per-request LSP timeout hardcoded at 30s, no override~~ — fixed 2026-07-29, commit `29034173`: `requestTimeoutMs` now shares the configurable batch-cap value, new `docuvia analyze --lsp-timeout=<ms>` flag, `0` = never time out.
  - **Real re-test against Orleans (3 files seeded into `tierBQueue`), all 5 fixes in place**: 5-minute run (`--lsp-timeout=300000`) → 0 edges. Full 30-minute run (`--lsp-timeout=1800000`, 1,800,141ms actually elapsed) → still 0 edges. Both runs first hit an unrelated blocker — Orleans' `global.json` pins .NET SDK `10.0.302`, this machine only has `9.0.316` — worked around by temporarily renaming `global.json` (restored after each test). Once past that, `initialize` succeeded (a first for C# here) but no file ever completed within 30 minutes.
  - **Root cause, corrected twice**: not "`csharp-ls` is slow" (Visual Studio indexes both repos in under 3 minutes) and not "spawn-per-batch cold start" (the whole queue is already one spawn, not one per file). The real cost is the *query shape* — `textDocument/references` per method forces a whole-solution search, and Tier B queries backwards (callee → find callers) instead of forwards (call site → resolve callee). Deeper still: C#'s Tier A produces **~0 cross-file `calls` edges** to begin with — `ScopeResolver.resolveCall` only matches same-file locals/explicit imports, and `persist-ast-graph.ts` deliberately disables the name-fallback for calls (documented in its own comments, to avoid false-matching common short method names). So Tier B wasn't correcting existing edges, it was trying to create them from nothing via the most expensive mechanism available.
  - **Also found**: a live node_key-collision bug in the *shipped* TypeScript Tier B provider — `lsp-edge-provider-base.ts` builds the callee key with no line-number disambiguation, so overloaded/duplicate-named symbols can get an edge attached to the wrong target or dropped.
  - **Recommendation**: drop full-LSP for C# Tier B; build a Docuvia-native, in-process resolver instead (two-phase: build a read-only project-symbol registry once from existing L2 nodes, then per-file forward resolution) — the same shape both GitNexus and CRG independently converged on for their own C# handling. Keep `csharp-ls`/`--escalate-to-lsp` reachable behind the existing flag, don't delete it. Do first, regardless of direction: fix `runWithTimeout()`'s `Promise.race` silently discarding whatever a timed-out batch actually finished, and fix the node_key disambiguation bug above. Cross-language version of this finding (why no off-the-shelf system was adopted instead) is in [README §4.5](./README.md#45-cross-language-symbol-resolution-is-a-full-lsp-or-any-off-the-shelf-system-the-right-approach-2026-07-29).
  - Both of Docuvia2's existing safety nets — `docuvia doctor`'s `runLspBinaryDiagnostic` and `--escalate-to-lsp`'s `confirmTierBGateOrAbort` gate — correctly surfaced every blocker above as it was hit.

- Both target repos were verified clean (`git status --porcelain` → only the pre-existing `.gitignore` baseline diff) after every tool's artifacts (`.docuvia/`, `.gitnexus/`, `graphify-out/`, `.claude/skills/gitnexus/`, generated `AGENTS.md`/`CLAUDE.md`, the `docuvia-knowledge` branch) were removed — including restoring Orleans' real, upstream-tracked `AGENTS.md` via `git checkout --` rather than deleting it, since GitNexus had appended a generated section into it in place.

- **Docuvia2 Tier B / `--escalate-to-lsp`**: all 5 blockers are fixed (§3). - **GitNexus `wiki`**: needs `GITNEXUS_API_KEY`/`OPENAI_API_KEY` for a cloud backend, or `--provider claude` to shell out to the already-installed `claude` CLI with no separate key.

- **Remote Sync & Git Integration category**: still N/A for all four tools — no credentials configured for any hosted/remote backend in this environment (Docuvia2's `DOCUVIA_API_URL`/`MCP_PAT`, GitNexus's `AZURE_DEVOPS_URL`/`AZURE_DEVOPS_PAT`, CRG's registry/daemon features, etc.).
- **Minor follow-up**: GitNexus's Orleans `impact`/`context` on bare `"IGrain"` resolved ambiguously (2 candidates); only `impact` was disambiguated (via `-f <path>`) this session. Re-running `context` with the same disambiguation would complete that data point if a cleaner single-target reading is wanted.
