## 3. Observations & Findings

- **Docuvia2 Performance**: Zero crashes, exit code 0 on every command across both repos. Correction to the 2026-07-23 note: the gating env var for L3 decision extraction is **not** `ANTHROPIC_API_KEY` — the actual code path (`resolveAnalyzeLlmConfig` in [`artifacts/cli/src/commands/analyze.ts`](../../artifacts/cli/src/commands/analyze.ts)) reads `AI_DOCUVIA_INTEGRATIONS_OPENAI_BASE_URL` + `AI_DOCUVIA_MODEL`/`AI_DOCUVIA_FAST_MODEL` (+ optionally `AI_DOCUVIA_INTEGRATIONS_OPENAI_API_KEY`), an OpenAI-compatible-shaped config that can point at any backend. None of these were set this session either (LLM parts skipped by explicit user choice), so L3 Decisions again stayed at 0 with no errors — graceful degradation confirmed a second time. The "incremental" delta check in `analyze` is keyed to `HEAD === lastIngestedSourceSha` (see `lib/ui-core/src/workflows/analyze/analyze-workflow.ts`), so **uncommitted working-tree edits are completely invisible to it** — unchanged from before. Edge counts were captured this session by querying the `node_links` SQLite table directly (`sqlite3` CLI isn't installed in this environment; used `python -c "import sqlite3; ..."` instead) right after `analyze` and before `clean`: **39,419** (PowerShell) and **55,287** (Orleans) — both consistent with the `--collapse=symbol` topology-export figure from the 07-23 run. `docuvia uninstall` still does not fully clean up on its own — it empties git hook files (this time actually removed them, per its own log) but still leaves the `.docuvia/` folder shell and, again, the hidden `docuvia-knowledge` branch — manual `git branch -D` was required both times. **Fixed (2026-07-24, same-day follow-up):** `uninstall` now force-deletes the `docuvia-knowledge` branch and removes the rest of `.docuvia/` too, both gated by the existing `--keep-db` flag. The `query` command's shallow single-edge output noted in both repos' Query Engine rows below is also fixed the same day: `getIncomingEdges`/`getOutgoingEdges` never surfaced the actual relationship type (`calls`/`implements`/`extends`) — only the neighbor's node kind, always `"module"` — and never excluded `contains` edges, so a symbol's own containing file (e.g. `IGrain.cs`) was showing up disguised as its one "incoming caller". `query`'s structural context now excludes `contains` and labels each edge by its real relationship; the `<l2_module>` tag also now carries `type`/`file` attributes instead of being an empty shell when there are no LLM-derived L3 decisions.

- **Retest confirmation (2026-07-24, post-fix pass on `PowerShell/PowerShell`)**: All three fixes from commit `e1a07c3` verified live against the same C# repo used for the original benchmark. **`query "PSCmdlet" --format=prompt`**: `<l2_module name="PSCmdlet" type="module" file="src/System.Management.Automation/engine/CommandBase.cs">` now carries the previously-missing `type`/`file` attributes, and `<incoming>` returned **128 real `extends` relationships** (e.g. `NewWinEventCommand.cs`, `GetCounterCommand.cs`, `Select-Object.cs`, …) instead of the old single fake "containing file" edge — `contains` is no longer conflated with an actual caller. **`export-topology`** (default `--collapse=auto`): now reports `1275 nodes, 797 links, 22 groups, collapsed — 847 more relationship(s) folded within files at this granularity; pass --collapse=symbol for the full symbol-level view`, replacing the old silent "0 links" undercount with an honest folded-count disclosure. **`uninstall`**: default run logged `Deleted hidden knowledge branch` + `Removed .docuvia/ directory`, and `git branch --list 'docuvia*'` / `ls .docuvia` both confirmed empty afterward — the branch and folder no longer survive uninstall. Also re-verified `--keep-db` still gates correctly: re-ran `init`, then `uninstall --keep-db` skipped both the branch deletion and the `.docuvia/` removal (only git hooks were removed), confirmed via the same two checks before a final unqualified `uninstall` fully cleaned up. Three corrections/findings worth flagging: (1) **it is not only `--skills` that writes into the target repo** — plain `gitnexus analyze` already installs standard skill files under `.claude/skills/gitnexus/*` and appends a generated section to `AGENTS.md`/`CLAUDE.md` **by default**; avoiding all of that needs `--index-only` (or `--skip-skills` + `--skip-agents-md` together). (2) On `D:\GitHub\orleans`, `AGENTS.md` turned out to be a **real file already tracked by the upstream dotnet/orleans repo** (confirmed via `git ls-files`) — GitNexus's default run appended a 45-line section into it rather than creating a new file, so cleanup required `git checkout -- AGENTS.md` to restore the original content, not a delete. Anyone running GitNexus against a repo that ships its own AGENTS.md should be aware its content will be mutated by default. (3) GitNexus maintains a **global** cross-repo registry (`~/.gitnexus/registry.json`) rather than Docuvia2/CRG's per-repo-only model — this machine already had 8 repos registered from prior use, so bare `query`/`impact`/`context` fail with "Multiple repositories indexed" unless `-r <name>` is passed. On correctness: the incremental check (mtime/hash-based) **correctly detected** the same 1-line uncommitted edits that Docuvia2's git-HEAD-based check missed on both repos — a genuine capability edge over Docuvia2 — but it did **not** translate into a latency win here: the incremental re-run took 71.8s/73.8s vs. 63.2s/68.2s for the full build (PowerShell/Orleans respectively), essentially full-build cost again, unlike CRG's clearly-faster `update` (1.94s/6.7s vs. 25.2s/36.3s). `impact`/`context` on a bare ambiguous name (`"IGrain"` on Orleans, which resolves to both the real interface and a generated public-API-surface stub file) returned an explicit `"ambiguous"` status with disambiguation candidates — the same class of behavior CRG's `query` shows for bare names. Once disambiguated, `impact` returned a genuinely informative result: an `"epistemic": "lower-bound"` field plus a `boundaries` array stating in plain language what isn't traced (interface/DI dispatch) — a transparency feature neither Docuvia2 nor CRG expose. No CLI-level visual-export command exists at all (confirmed against the full `--help` command list) — visual output is only reachable via `gitnexus serve`'s web UI, out of scope for a static-artifact comparison. `wiki` generation needs an LLM (`GITNEXUS_API_KEY`/`OPENAI_API_KEY`, or `--provider claude` to shell out to an already-installed `claude` CLI with no separate key) — skipped this session per the no-LLM scope.

The one piece that's genuinely deterministic, LLM-free, and has its own real CLI entry point is the structural layer: `python -m graphify.extract <path>` (see its `if __name__ == "__main__":` block in [`extract.py`](../../../graphify/graphify/extract.py)) — tree-sitter AST parsing with a same-file call-graph pass, used for both repos' numbers above. Side effect confirmed: even this bare structural pass writes a per-file SHA256 cache under `<repo>/graphify-out/cache/*.json` directly into the target repo — cleaned up manually alongside the other tools' artifacts.

- **Comparison & Regressions (updated with full-repo node/edge data)**: **PowerShell** — Docuvia2 26,451 nodes/**39,419** edges; GitNexus 40,211/**124,114**; Graphify (AST-only) 22,318/**44,334**; CRG 22,370/**122,020**. **Orleans** — Docuvia2 47,703/**55,287**; GitNexus 61,604/**132,184**; Graphify (AST-only) 41,425/**65,938**; CRG 38,815/**158,252**. Two clusters emerge: GitNexus and CRG converge on similarly dense graphs (~122K–158K edges) despite different node-counting granularity, while Docuvia2 and Graphify's AST-only pass sit in a lighter ~39K–66K-edge band — expected for Graphify, since it's missing the semantic/cross-file layer the full (LLM-driven) product would add, but notable that Docuvia2's default view is in the same ballpark despite being a fully deterministic, LLM-independent product. On blast-radius behavior specifically: Docuvia2 **and** GitNexus both returned surprisingly shallow/zero "upstream" impact for foundational base symbols (`PSCmdlet`: Docuvia2 1 file, GitNexus 0 impacted; `IGrain`: Docuvia2 1 file, GitNexus 5 direct implementors once disambiguated) where CRG's `impact` surfaced hundreds-to-thousands of transitively-impacted files for the same symbols — CRG's blast-radius traversal is fundamentally broader/more inclusive by default, or Docuvia2/GitNexus's "upstream" direction means something narrower (direct inheritance only) than CRG's fuller transitive closure. That's the standout finding worth a deeper follow-up if a genuine apples-to-apples impact comparison is ever wanted. CRG remains the only tool with out-of-the-box wiki + real visual-export artifacts in this no-LLM comparison; GitNexus's wiki needs an LLM and Docuvia2 has no wiki command at all.

- **Root cause of Docuvia2's edge-count gap (2026-07-24 diagnostic follow-up)**: traced by reading the analyze pipeline rather than re-running the benchmark. Docuvia2 splits graph-building into **Tier A** (default `docuvia analyze` — tree-sitter AST, same-file edges plus heuristic cross-file `calls` that stay unresolved/`INFERRED`) and **Tier B** (`docuvia analyze --escalate-to-lsp` — a real language-server call for LSP-precision cross-file resolution; see [`analyze-workflow.ts`](../../lib/ui-core/src/workflows/analyze/analyze-workflow.ts)'s `execute()` dispatch and [`analyze.ts`](../../artifacts/cli/src/commands/analyze.ts)). **This benchmark never passed `--escalate-to-lsp` for any tool/language**, so only Tier A ever ran for Docuvia2 — by design this is opt-in, not automatic (`--escalate-to-lsp` is described as "the core quality engine" in `docs/gitbook/adr/impact/IMPT-002-lsp-for-absolute-quality.md`). That fully accounts for the banding above: Docuvia2's Tier-A-only counts sit with Graphify's admittedly-AST-only pass, not with GitNexus/CRG, which apparently do their equivalent deeper resolution by default. This is **not evidence of a broken/unwired C# LSP** — Tier B was simply never invoked this session, for any of the eleven supported languages, not just C#.
  - A C#-specific follow-up check found three additional blockers that would need clearing before a Tier-B re-run could produce real numbers for these two repos:
    1. **`csharp-ls` isn't on `PATH` in this environment** (`where csharp-ls` → not found). Unlike the TS/Python providers, which check a project-local `node_modules/.bin` and then an already-cached `npx --no-install` before giving up, C#'s provider is PATH-native only (`resolvePathNativeBinary` in [`lsp-binary-resolver-strategies.ts`](../../lib/core/src/lsp/lsp-binary-resolver-strategies.ts)) with no local/cache fallback of its own — and note even the npm/npx path is `--no-install`, i.e. it never fetches over the network either; every provider's design comment states "Never falls back to a bundled copy -- there isn't one," so there's no tool in this codebase today that silently downloads an LSP server.
    2. **The standard install path itself failed live**: `dotnet tool install --global csharp-ls` on this machine returned "工具之 NuGet 套件中的設定檔案無效: 無法在套件中找到設定檔 'DotnetToolSettings.xml'" (invalid tool manifest — `DotnetToolSettings.xml` missing from the package) — an environment/NuGet-feed-level failure external to Docuvia2, but it means "just install csharp-ls" isn't a one-line fix here without first debugging the local NuGet configuration.
    3. **Orleans would fail Tier B's marker-file check regardless of (1)/(2)**: `checkMarkerFileResolvable` in [`csharp-lsp-preflight.ts`](../../lib/core/src/lsp/csharp-lsp-preflight.ts) only recognizes `*.sln`/`*.csproj` at the workspace root. `D:\GitHub\PowerShell` has `PowerShell.sln` (passes); `D:\GitHub\orleans`'s root only has `Orleans.slnx` — the newer XML solution format — which this check doesn't recognize, so it would report `"no solution (.sln) or project file (*.csproj) found at the workspace root"` even with `csharp-ls` installed and the flag passed. This is a genuine, fixable gap (the extension list needs `.slnx` added), independent of the two environment issues above.
  - Both of Docuvia2's existing safety nets for this — `docuvia doctor`'s per-language `runLspBinaryDiagnostic` (reports `csharp-ls is not resolvable...` as an informational PASS line) and `analyze --escalate-to-lsp`'s interactive `confirmTierBGateOrAbort` gate (warns and asks to proceed when unavailable) — already exist in the codebase and would have surfaced items (1)/(3) above immediately. Neither `doctor` nor `--escalate-to-lsp` was run this session, so neither warning path was exercised; this wasn't a case of the warnings failing to fire.
