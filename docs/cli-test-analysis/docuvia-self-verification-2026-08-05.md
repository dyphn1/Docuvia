# Docuvia2 Self-Verification via Docuvia (2026-08-05)

This session tested whether `docuvia query` can substitute for Read/Grep/Glob during ordinary code exploration — per CLAUDE.md's instruction to run `npx --no-install docuvia query "<concept_or_file>" --format=prompt` and query the local knowledge graph before exploring with Read/Grep/Glob. Real `docuvia query` commands were run against Docuvia2's own repo (`docuvia status` at test time: 5136 L2 nodes, 1 project, 0 L3 decisions) and the results compared directly against what Glob/Grep/Read found for the same target.

> **Revision note**: this pass initially ran against a local checkout 6 commits behind `origin/main` — missing `efea870d` (a same-day Tier B LSP fix, scoped to the `vscode` external benchmark target, not this repo) and `ec19931d`/`0c5e57f6` (a same-day CLAUDE.md/AGENTS.md update that already documents a Grep/Glob/Read fallback policy — see Finding 1 below). Findings were re-verified after pulling `origin/main` and rebuilding (`pnpm run build`); numbers below are post-pull.

## Finding 1 — `docuvia query`'s keyword search cannot substitute for Read/Grep/Glob during exploratory work

It only reliably works when the caller already knows the exact symbol name in the graph's stored casing/form (case 1). Concept phrases (case 2), free text embedded in comments (case 3), directory-style enumeration (case 4), and even a same-module lookup under a different naming convention (case 5) all fail — either returning nothing or an unrelated single hit, with no fuzzy/"did you mean" fallback and no signal distinguishing "this doesn't exist" from "the matching algorithm missed it."

**Impact**: AGENTS.md's "Docuvia-First Development Workflow (Mandatory)" section (around lines 94-120) already documents three fallback-to-Grep/Glob/Read triggers: (a) `query`/`impact` returns empty or is flagged `tier_b_status="unprocessed"`; (b) exact source text, formatting, or a diff is needed; (c) a dependency `impact` can't detect (dynamic import, computed specifier, spawned process). Cases 1, 3, and 5 above are already correctly handled by this policy — case 1 succeeded outright, and cases 3 and 5's failure mode is an empty result, which correctly trips trigger (a). The surviving, narrower gap is cases 2 and 4: both return a non-empty result that isn't flagged `tier_b_status="unprocessed"`, yet is nonetheless wrong (case 2: a confident but unrelated single match) or incomplete (case 4: 1 file instead of an enumeration) — neither condition trips any of the three documented triggers, so an agent following the current policy to the letter would trust a wrong or incomplete answer as final rather than falling back. The fallback policy has no trigger for "confidently wrong" or "confidently incomplete" non-empty results — only for empty/flagged/text-need/dynamic-dependency cases.

## Finding 2 — No first-class visibility into Tier B (LSP) coverage breadth; `doctor` gives false confidence

Querying almost any symbol in this repo (e.g. `docuvia query "docuvia-api" --format=prompt`, `docuvia query "LLM" --format=prompt`) surfaces this note buried inside the `<incoming>` tag: `No callers found, but 410 of 484 tracked file(s) have never been Tier B-processed -- this may be incomplete, not confirmed zero. Run \`docuvia analyze --escalate-to-lsp --full\` to resync.` — i.e. 84.7% of this repo's own tracked files have never been through Tier B (LSP) processing. Reproduced identically across two separate unrelated queries (`"docuvia-api"`and`"LLM"`), confirming it's a stable, repo-wide figure, not query-specific noise. This figure was live-verified to move — 422/484 at initial test time, down to 410/484 after pulling `origin/main`, rebuilding, and running one real `docuvia analyze --escalate-to-lsp` pass (which processed the 16 newly-queued files from the pulled commits) — confirming the mechanism is a genuine incremental backlog gated by the commit-cap budget, not stuck or broken, just still 84.7% unprocessed on this repo.

Meanwhile `docuvia doctor` reports `10/10 checks passed`, including a `tier_b_commit_cap` check showing `✓ PASS — Tier B commit-cap not yet reached`. `runTierBCommitCapDiagnostic` ([`doctor-workflow.ts:474-513`](../../lib/ui-core/src/workflows/doctor/doctor-workflow.ts)) has its own doc comment confirming this check's `status` is _hardcoded_ to `DiagnosticStatus.PASS` regardless of whether the cap is exceeded — deliberate design per decision 1c/1d, already documented as [`roadmap-and-open-items.md`](../gitbook/analysis/roadmap-and-open-items.md) item 15, because "neither 'not yet exceeded' nor 'exceeded' is itself a defect." That existing design decision is correct on its own terms, but it means the commit-cap check was never meant to answer, and doesn't answer, a different question: what fraction of the repo has _ever_ been Tier-B processed. That number currently exists nowhere as a first-class `status`/`doctor` metric — it's only discoverable as an incidental note buried inside individual `query` responses, and only surfaces when that particular query happens to have zero incoming edges.

**Impact**: neither an agent nor a human has any reliable way to know, before trusting a `query` result's empty call graph as ground truth, whether "no callers" means "genuinely no callers" or "this file was simply never processed" — and `doctor`'s all-green summary actively reinforces the wrong read.

## Finding 3 — Tier C (LLM decision extraction) has produced zero L3 decisions despite a reachable, configured endpoint

`docuvia status` still reports `L3 Decisions: 0` for this repo, but the reason is now known — confirmed via `.docuvia/logs/analyze.log`, not speculation. The Tier C queue is not empty or unconfigured: it currently holds **673 queued candidates** (via `analyze.log`'s `analyze.tierC.start` events, growing from 662 the previous day to 673 after this session's delta). Every `analyze --escalate-to-lsp` run attempts the queue in a fixed order up to an item cap and wall-clock budget ([`GitConstants.DEFAULT_TIER_C_ITEM_CAP`/`DEFAULT_TIER_C_WALL_CLOCK_MS`](../../lib/core/src/git/git-constants.ts) — 20 items / 12s, `git-constants.ts:259-261`), and the same two items are always first:

1. `commitMessage` target `a489345b87c15611bfbe8062d0f74d35b6dc6753` → fails with `no-anchor` (its changed files have no matching L2 node in the graph).
2. `commitMessage` target `240f96ee1648e2b81033951f149b77920faaf5ce` → fails with `bridge-unreachable`.

Both failures are logged identically across two separate `analyze` runs 18 hours apart (2026-08-04T18:30:53Z and 2026-08-05T12:31:36Z) — deterministic, not a transient outage.

The `bridge-unreachable` classification is the mechanism that fully blocks the queue: [`handleTierCItemOutcome`](../../lib/ui-core/src/workflows/analyze/run-tier-c-drain.ts) (around line 380-417) treats a `bridge-unreachable` failure as a whole-loop-stop signal (`return outcome.reason === TierCFailReasons.BRIDGE_UNREACHABLE`), and separately, `removeTierCQueueEntries` (dequeue) is only ever called on the `outcome.success` branch — a failed item is never removed from the queue. The combination is a permanent head-of-line block: item 2 fails, the drain loop stops immediately (2 items attempted out of an item cap of 20), and because item 2 is never dequeued, it stays first-in-line and re-fails identically on every future `analyze` run — the other 671+ queued candidates behind it can never be reached, regardless of how long the queue grows or how many times `analyze` runs.

This fully explains 0 L3 decisions despite a reachable, correctly-configured endpoint: `doctor`'s `llm_reachability` check calls the lighter-weight `checkAvailability()`, explicitly documented ([`doctor-workflow.ts:320-321`](../../lib/ui-core/src/workflows/doctor/doctor-workflow.ts)) as "reachability, not correctness" — a different, weaker guarantee than a real `chatCompletion()` call succeeding for every queued item.

**Not yet investigated**: why item 2 specifically triggers `bridge-unreachable` (could be prompt size, encoding, content-filter, or something else about that specific commit) — but the structural bug (one permanently-failing item can permanently starve the entire Tier C queue, with no skip-ahead/eviction/alerting) stands regardless of that item's specific root cause.

These three findings are also tracked as items 22-24 in [`roadmap-and-open-items.md`](../gitbook/analysis/roadmap-and-open-items.md). Two of the three — Finding 1's fallback-trigger gap and Finding 3's Tier C head-of-line-blocking queue bug — are precisely root-caused with log/code evidence; Finding 2's Tier B backlog is confirmed real and moving (not stuck) but has no fix proposed here, just a visibility gap flagged. Finding 1 (case 1) also confirms `docuvia query` genuinely outperforms grep for the one case it's built for (exact-symbol call-graph lookup) — this is not a "`docuvia query` is broken" report, it's a "`docuvia query`'s usable surface is much narrower than agents currently assume" report.

## Fixed (2026-08-05, same-day follow-up)

All three findings above have since shipped fixes, each code-reviewed and independently `task-verifier`-approved with live re-verification against this repo's real `.docuvia/local.db` — full detail in [`roadmap-and-open-items.md`](../gitbook/analysis/roadmap-and-open-items.md) items 22-24. Findings 1 and 2 got the fixes their diagnoses called for: a `match_type` confidence field closing the fallback-policy gap (Finding 1), and a first-class `tier_b_coverage` metric in `status`/`doctor` (Finding 2). Finding 3 is the more interesting case: the originally-diagnosed fix (evict a permanently-failing queue item after repeated failures) was implemented and, in the course of live-verifying it, surfaced a second, far more consequential bug underneath — a doubled `/v1` segment in the Tier C completions URL had caused **100% of Tier C LLM calls to fail** since this repo's inception (not just the 2 originally-diagnosed poison items), misclassified as `bridge-unreachable` the whole time. Both are now fixed; `docuvia status`'s `L3 Decisions` moved off 0 for the first time in this repo's history. Worth keeping visible as a concrete example of why live re-verification after a fix matters, not just unit tests — the eviction fix alone would have "worked" (stopped blocking) while never actually producing a single decision.

**Deliberately not fixed, tracked as follow-up** (`roadmap-and-open-items.md` item 25): Finding 1's `match_type` field only signals when a match is low-confidence — it does not make `query`'s underlying FTS/keyword matching itself better. `docuvia query "query command"` still resolves to the wrong file today, now correctly labeled `match_type="keyword"` rather than looking as confident as an exact hit, but still wrong. Improving the actual ranking (synonym/token expansion, a fallback strategy when the top FTS hit scores far below what an exact match would) is a separate, larger piece of work, parked until a measured pain trigger shows up rather than spec'd speculatively now.
