### 1.1 Docuvia2: same git-knowledge-branch pack-step crash as the vscode pass, plus a new `maxBuffer` scale bug

**FIXED 2026-08-04, verified by re-running the exact crashing operation against this session's own leftover `moby` `local.db`.** See the addendum below for the confirmed root cause and fix.

- **Pack-step crash reproduced on a second large repo.** `typescript-cli-benchmark.md` §4 first saw `docuvia init` crash (exit 1) at the git-knowledge-branch pack step against `vscode` (288,726 nodes, root cause not isolated that pass, flagged as follow-up work item 1). This session hit the **same symptom** against `moby` — `Error: write EOF` on a `Socket` instance right after `"Packing initial knowledge graph onto the knowledge branch..."` logs, Tier A ingestion (AST parse + `local.db` persist) already complete and intact at crash time. Two large-repo reproductions now point at the same step; still not root-caused to file:line in either pass — worth prioritizing given it's now 2-for-2 on every repo above ~130K nodes tested across both Go and TypeScript passes.

**Addendum (2026-08-04): root-caused and fixed.** Reproduced directly against this pass's own leftover `moby` `.docuvia/local.db` (Tier A's 136,329/157,139 rows were still intact post-crash) by re-running `docuvia snapshot` against it. Two independent bugs, one masking the other:

1. **The real failure**: `git fast-import` itself rejected the commit outright — `fatal: invalid path 'knowledge/client/pkg/progress/progress/Aux.md'`. moby's real `pkg/progress.Aux` symbol (Docker's `JSONMessage.Aux` field) rendered to a git tree path whose final segment, `Aux`, is a Windows/DOS-reserved device name — git's own cross-platform path guard (`core.protectNTFS`, on by default on every platform, not just Windows) refuses to create such a path so the branch stays checkoutable everywhere. [`SnapshotRendererService`](../../lib/core/src/git/snapshot-renderer.service.ts)'s `sanitizeSegment` stripped illegal characters but never checked for reserved names.
2. **Why it was an unhandled crash instead of a clean error**: [`runFastImport`](../../lib/git-local/src/fast-import.ts) streams the whole commit to `git fast-import`'s stdin via one `child.stdin.end(fastImportData, "utf8")` call, with an `"error"` listener registered on `child` but never on `child.stdin` (a distinct `EventEmitter`/`Socket`). When git aborted mid-stream on the invalid path above, the still-in-flight stdin write failed (`write EOF` on Windows, `EPIPE`-equivalent), and with no listener for that `"error"` event, Node.js threw it as an uncaught exception — crashing the whole `docuvia` process before the `"close"` handler ever got to report git's real exit code/stderr message. This is why the crash looked like a raw pipe/size issue with no visible root cause across two separate benchmark passes (`vscode` and `moby`): the actual git error was always there in `stderr`, just never reached because the process died first.

- **Fix**: (1) `sanitizeSegment` (both the copy in `snapshot-renderer.service.ts` and its mirrored copy in `l3-card-renderer.ts`, which must stay in lockstep for L3DIST-007) now mangles a segment matching a reserved name (`con`, `prn`, `aux`, `nul`, `com0`-`com9`, `lpt0`-`lpt9`, case-insensitive, checked before the first `.`) by appending `_`, e.g. `Aux.md` → `Aux_.md`. (2) `runFastImport` now also listens for `"error"` on `child.stdin` (swallowed — the `"close"` handler's exit-code/stderr rejection is still the one callers see), so _any_ future fast-import rejection (this one or a different one) surfaces as a normal, catchable `DocuviaError` instead of crashing the process.
- **Verified**: re-ran `docuvia snapshot` against the same leftover `moby` database post-fix — **136,329 nodes / 157,139 edges / 136,329 markdown files packed successfully**, no crash; confirmed via `git ls-tree` that the real node landed as `knowledge/client/pkg/progress/progress/Aux_.md` on the `docuvia-knowledge` branch.
- **New finding this pass**: `git ls-files -s` failed with `"stdout maxBuffer length exceeded"` during workspace discovery, before AST parsing even started. Traced to [`git-local-provider.ts:490`](../../lib/git-local/src/git-local-provider.ts) — a hardcoded `maxBuffer: 10 * 1024 * 1024` (10MB) on the staged-files listing call, too small for `moby`'s 13,121-tracked-file `git ls-files -s` output. Docuvia2 caught this gracefully and fell back to manual filesystem globbing (`"Git operations failed during discovery, falling back to manual globbing"`) — not a crash, but worth noting the cap is 6.4x smaller than the two other `maxBuffer` call sites in the same file (`515`/`579`: `64 * 1024 * 1024`), which looks like an oversight rather than a deliberate choice.
- **Oversized-file skip worked as designed**: 7 vendored generated files (600KB-955KB `.pb.go`/protobuf/enum files) were correctly skipped with a clear per-file log line rather than silently truncated or crashing the parse.

### 1.2 Graphify: bare-label resolution is not just wrong, but _inconsistently_ wrong across its own commands

On `gin` (§3.3), `affected` alone failed on a bare label that `query`/`explain` handled fine. On `moby` — a codebase large enough to have real name collisions — the picture is worse: **`query "Container"` and `explain "Container"` each resolved to a different wrong node**, neither the real struct:

- `explain "Container"` → `.Container()`, a 2-degree method on `IpcMode` in `api/types/container/hostconfig.go:127`.
- `query "Container"` → the vendored `containerd` package's own `Container` struct (`vendor/github.com/containerd/containerd/v2/core/containers/containers.go:30`).
- The real target (`daemon/container/container.go:70`, degree 64, clearly the most-connected candidate) was reachable only by first grepping `graphify-out/graph.json` for its generated node ID (`daemon_container_container_go_container_container`) and passing that explicitly.

Two different commands against the identical graph, given the identical bare input, silently returned two different _wrong_ answers rather than either resolving correctly or surfacing the ambiguity (compare CRG's explicit `"status": "ambiguous"` response to the same kind of input, §1.4). This is a correctness gap, not just a UX rough edge: a user asking "what does `Container` connect to" gets a confidently-wrong, plausible-looking answer with no signal that it's wrong.

### 1.3 CRG appears to exclude `vendor/` by default — a real, unannounced scope difference from the other three tools

CRG's `build --repo .` log reported `"2340/2340 files parsed"` against a repo `git ls-files` puts at 10,546 `.go` files (2,206 first-party + 8,340 vendored). Docuvia2 (136,329 nodes), GitNexus (32,736 nodes off a `.go`-file-scale comparable to the full count), and Graphify (10,717 code files scanned, explicitly including `vendor/…` paths in its own log output) all clearly processed vendor code; CRG's count lines up almost exactly with `moby`'s first-party-only file count. Not confirmed against CRG's source this pass (would need to check its file-discovery/ignore-rule code for an explicit `vendor/` exclusion vs. some other filter that happens to net out to a similar number) — flagged as a real cross-tool comparability caveat: CRG's smaller graph and faster build partly reflect indexing 4.5x less code, not purely a speed advantage.

### 1.4 CRG: disambiguation candidate list is capped and (apparently) alphabetical — the real match can fall off the list entirely

`query callers_of Container` (bare) returned `"'Container' matches 20 node(s)"` — but all 20 shown were from `api/types/container/*.go` (alphabetically first among matches), and the real, most-referenced `daemon/container/container.go::Container` was **not among them** despite being a real match (confirmed separately via `search Container`, whose FTS ranking correctly surfaced it as the top hit). A user relying on `query`'s own disambiguation list to find the right qualified name for a common symbol name would not find it there on a codebase this size, and would need to already know to try `search` instead. Same underlying gap `typescript-cli-benchmark.md` §5.4 already flagged for `findNodeByName`'s unordered `LIMIT 1` (there: silently wrong; here: silently incomplete) — worth the same fix recommendation (rank by connectivity/non-test-path, don't just cap alphabetically).

### 1.5 Docuvia2: `export-topology`'s default collapse mode degenerates to `Links: 1` on `moby`

Default `--collapse=auto` produced `"Nodes: 10562, Links: 1"` for a graph with 157,139 real edges — not the "0 links" bug already fixed in the 2026-07-24 C# pass (`stats.foldedLinkCount` now correctly reports 31,371 folded links, so the fix from that pass still holds), but a new, much larger-repo-specific degenerate case: collapsing to file-level granularity across `moby`'s 97 groups apparently leaves only **one** visible cross-group edge. `gin` (§2, `Nodes: 1609, Links: 2246`) didn't trigger auto-collapse at all — small enough that "auto" stayed at full granularity. `--collapse=symbol` immediately produces the correct full **136,329/157,139** counts, so this is purely a default-heuristic edge case on a repo this large, not a data-loss bug — but the default view is close to useless at this scale without knowing to pass `--collapse=symbol`. Not root-caused to the folding algorithm's file:line this pass — flagged as a follow-up.

## 3. Observations & Findings (gin pass, 2026-08-03)

### 3.1 Docuvia2 Tier B (LSP escalation) is effectively non-functional for Go — new finding, distinct from GRPH-006

**FIXED 2026-08-04, verified against a re-run of this exact `gin` batch.** See the addendum at the end of this section for the confirmed root cause and fix.

`docuvia analyze --escalate-to-lsp` against `gin` (after `doctor` confirmed `lsp_binary_go: PASS — gopls resolved`) processed the 98-file queue and failed on 95 of them:

- **2 files timed out** (`auth.go`, `auth_test.go`) at the per-request 30,000ms cap with `"LSP request \"textDocument/documentSymbol\" timed out"` — consistent with gopls still doing its initial workspace/module load right after `initialize`.
- **The remaining ~93 failures** were near-instant (sub-50ms apart in the log) `"no identifier found"` — gopls's own error text, not a Docuvia2-authored message (grepped the full `lib/` tree; the string appears nowhere in Docuvia2 source). A handful of others report `"no package metadata for file …"` (e.g. `context_appengine.go`, `codec/json/sonic.go` — files gated behind Go build tags gopls's default build won't include).
- **Root cause, traced to file:line**: [`lsp-edge-provider-base.ts:663-669`](../../lib/core/src/lsp/lsp-edge-provider-base.ts) issues `textDocument/references` at `symbol.selectionRange.start`, where `symbol` comes from `textDocument/documentSymbol`'s response. The pattern (near-universal, near-instant, same error text across almost every symbol in almost every file) points at a systemic position/response-shape mismatch between what gopls's Go `documentSymbol` returns and what this code assumes — not occasional bad luck on a handful of edge-case symbols. **Not fully root-caused this pass** (would need to log gopls's raw `documentSymbol` response for one `gin` file and diff it against what `containsPosition`/`symbol.selectionRange` expects) — flagged as a concrete, high-value follow-up rather than guessed at further.
- **Distinct from the pre-existing GRPH-006 note** in this doc (§ header, `supportsQualifiedContainment: false` — about containment/nesting shape for receiver methods). This finding is about `references` resolution failing outright, upstream of containment ever mattering. Both are `go-lsp-edge-provider.ts`-adjacent but independent gaps.
- **Practical impact**: on `gin`, Tier B ran for ~128s and produced 0 corrected edges — strictly worse than not running it (same result as skipping `--escalate-to-lsp` entirely, minus ~128s). Go should probably be flagged as "Tier B not yet viable" until this is root-caused, rather than silently returning a 0-edge success.

**Addendum (2026-08-04): root-caused and fixed.** [`initializeSession`](../../lib/core/src/lsp/lsp-edge-provider-base.ts) sent `capabilities: {}` — completely empty — on every language's `initialize` request. Confirmed live by spawning gopls v0.23.0 directly against a two-symbol fixture and diffing its `documentSymbol` response with and without `textDocument.documentSymbol.hierarchicalDocumentSymbolSupport: true` declared: with empty capabilities, gopls (correctly, per the LSP spec's own negotiation rules) falls back to the flat, pre-3.10 `SymbolInformation[]` shape instead of hierarchical `DocumentSymbol[]`. `normalizeDocumentSymbols` then aliases `selectionRange` to `location.range`, whose `start` is the _declaration's_ start (e.g. `{line: 8, character: 0}`, the `f` of `func`) rather than the identifier's own start (`{line: 8, character: 18}`, the `G` of `Greet`) — `textDocument/references` at the wrong position fails outright with gopls's own `"no identifier found"`. A `type X struct` declaration's flat-mode range happens to start exactly on the name (no keyword before it), which is why struct/type symbols "worked" (3/98) while every function/method failed (95/98). Fix: declare `hierarchicalDocumentSymbolSupport: true` in `initializeSession`'s capabilities — a one-line, base-class-level change affecting every language, though only gopls's stricter spec adherence ever made the gap observable. **Verified**: re-ran the identical `docuvia analyze --escalate-to-lsp` batch against `gin` post-fix — **92/98 files processed, 804 corrected edges applied** (was 3/98, 0 edges). The remaining 6 failures are unrelated, already-documented pre-existing gaps (1 `auth.go` timeout from gopls's initial workspace load, 5 build-tag-gated files gopls's default build doesn't include) — not the position bug this fix targets.
