## 3. Observations & Findings (nest pass, 2026-07-28/29)

- **Docuvia2 Performance**: `init`'s AST parse (~283s for 1,675 `.ts` files) was markedly slower per-file than the 2026-07-24 C# session's PowerShell/Orleans passes (~22-59s for similar-or-larger file counts) — consistent with the session-wide slowdown noted at the top of this doc, not a TypeScript-specific regression. All read-path commands (`query`/`impact`/`export-topology`/`clean`/`uninstall`) stayed fast (1-5s) regardless, suggesting the slowdown is concentrated in the AST-parse/worker-pool step rather than general CLI overhead.
- **Docuvia2's AST stage measured 1.8-2.9x slower than GitNexus/Graphify** (307.3s vs. 173.6s vs. 104.5s). Attributed to WASM (`web-tree-sitter`, [ADR-022](../gitbook/adr/legacy/ADR-022-wasm-ast-blast-radius.md)) vs. native `tree-sitter` bindings — parallelization itself is correct ([`ast-processing.service.ts:29`](../../lib/core/src/ast/ast-processing.service.ts)). **⚠️ Superseded by §3.7**: a same-day Docuvia2-only re-test measured the identical stage at ~15.1s (~19x faster, no code change). The WASM-vs-native gap is still real architecturally, but this specific multiplier isn't trustworthy without re-timing GitNexus/Graphify the same day.
- **Comparison & Regressions**: two concrete UX fixes from the 2026-07-24 C# session were re-verified as holding on a fresh TypeScript repo: (1) the dirty-worktree fast-path now explicitly says uncommitted changes were skipped instead of staying silent, and (2) `export-topology`'s collapsed view reports its folded-link count instead of an unexplained "0 links."

### 3.1 Docuvia2's `hasUncommittedChanges` check is a blanket `git status --porcelain`, and `init` never gitignores its own artifacts

- `docuvia init` never writes `.docuvia/` (or `.claude/hooks/hooks.json`) into the target repo's `.gitignore` — confirmed by grepping `lib/ui-core/src/workflows/init/` for any `gitignore` handling (none found).
- `hasUncommittedChanges()` ([`git-local-provider.ts:663`](../../lib/git-local/src/git-local-provider.ts)) is a bare `git status --porcelain` with no path scoping and no `--untracked-files=no` — so `.docuvia/`'s own untracked presence alone makes it return `true`.
- **Reproduced directly**: with `.docuvia/`/`.claude/hooks/` left ungitignored, `docuvia analyze` after a real new commit printed the _dirty_ fast-path message ("uncommitted changes... won't be reflected"); after gitignoring those paths (fully clean `git status --porcelain`), the identical commit sequence instead printed the _clean_ message ("Already up to date with HEAD.") and the SHA watermark advanced correctly. Isolated by rebuilding `.gitignore` as (pristine original + 2 new lines) to rule out the pre-existing unrelated `.gitignore` diff as a confound.
- **Practically**: this doesn't block real commits from being ingested (see §3.2 — the post-commit hook picks them up regardless, since the fast-path's dirty/clean distinction only changes the _log message_, never the noop-vs-ingest decision — see `analyze-workflow.ts:216-233`). But a human running `docuvia analyze` interactively right after `init`, before manually gitignoring `.docuvia/`, will see a misleading "uncommitted changes" warning on every single run even with a perfectly clean source tree — worth a follow-up: either `init` should append `.docuvia/` to `.gitignore` itself, or `hasUncommittedChanges` should scope its check away from paths docuvia itself generates.

### 3.2 The post-commit hook works correctly (positive finding)

- `docuvia init` installs a fire-and-forget post-commit hook (`.git/hooks/post-commit`: `npx --no-install docuvia analyze > /dev/null 2>&1 &`) that silently re-runs Tier A's delta ingestion after every commit.
- Verified this actually fires and correctly advances `lastIngestedSourceSha` to the new HEAD without any manual `docuvia analyze` call — confirmed via `.docuvia/local.db`'s `docuvia_meta` table and the JSONL `analyze.log`.

### 3.3 Docuvia2 Tier B queue never populated — bugs #1 and #2, fixed 2026-07-29

- LSP binary resolution itself worked once `typescript-language-server` was made resolvable (unlike C#'s `csharp-ls`, which never resolved at all) — see [`lsp-binary-resolver-strategies.ts`](../../lib/core/src/lsp/lsp-binary-resolver-strategies.ts).
- **Bug #1**: `runFullIngestion` ([`run-full-ingestion.ts`](../../lib/ui-core/src/workflows/analyze/run-full-ingestion.ts)) never wrote to `tierBQueue` at all — no reference to it anywhere in the file.
- **Bug #2**: `classifyChangedFile` ([`run-delta-ingestion.ts:270`](../../lib/ui-core/src/workflows/analyze/run-delta-ingestion.ts)) permanently excluded `ADDED`-status files (`if (entry.status !== MODIFIED) return { contractChanged: false }`), so a new file's exports could never reach the semantic-diff comparison.
- **Fixed 2026-07-29**: `runFullIngestion` now queues every parsed file when a `headSha` exists (treats "no prior commit" as CONTRACT_CHANGED, same logic `resolvePruningLevel` already uses); `classifyChangedFile` now also classifies `ADDED` files by diffing against empty `oldContent`.
- **Correction (§3.7)**: bug #1's fix lives in `analyze`'s own empty-graph branch, not `docuvia init` — `init-workflow.ts` never calls `runFullIngestion` at all. Mostly harmless in practice since `init` stamps a source trailer that routes the next `analyze` through the (delta) path instead.

### 3.4 GitNexus: incremental update is ~10x slower than a full rebuild for a widely-imported file

- A 1-line uncommitted edit to `bind.decorator.ts` (imported, transitively, by 872 files per GitNexus's own BFS) triggered: `Incremental: changed=1, added=0, deleted=0 (skipping wipe + 2039 unchanged file rows preserved)` followed by `Incremental: +872 importer(s) added to writable set (BFS depth ≤ 4)` — i.e. the incremental path re-processes every transitive importer up to depth 4, not just the changed file.
- Measured: **1785.8s (≈29.8 min)** for this single-file incremental update, vs. **173.6s** for the full rebuild of the entire repo — an incremental update costing ~10x a full rebuild is a significant, reproducible finding (not an artifact of environment slowness alone, since it's 10x slower than GitNexus's _own_ full-build number measured minutes earlier on the same machine).

## 5. Dogfooding follow-up (2026-07-29/30, later session): root-causing the "usable but thin" query finding

A separate same-day session (`b8a575bf`, evening of 2026-07-29) used Docuvia2's own CLI (`query`/`status`) to navigate **Docuvia2's own repo** while fixing two Tier B bugs found via an isolated nest worktree. That session's own summary called the query experience "usable but thin" (Traditional Chinese original: 「結果堪用但偏薄」) — an `<l2_module>` result with no `<incoming>`/`<outgoing>` edges. This section root-causes that finding precisely and re-tests it live against current `main`.

### 5.1 It is not a `query` formatting bug

`getContext()` ([`query.service.ts:80-94`](../../lib/core/src/query/query.service.ts)) and the CLI's `<incoming>`/`<outgoing>` XML rendering ([`query.ts:68-108`](../../artifacts/cli/src/commands/query.ts)) are both already fully wired — confirmed by direct code read. "Thin" output means the underlying edge rows are genuinely absent for that node, not that `query` is failing to display edges that exist.

### 5.2 Root cause A (fixed): five Tier B execution bugs found and fixed across 2026-07-29

The `b8a575bf` session itself found and fixed two of these; three more were found and fixed later the same evening. Any one of the five would independently produce a populated node count with sparse/wrong edges:

1. Tier B runtime degradation never flipped `process.exitCode` — fixed same session (`c507a270`).
2. JSONL logs never wrote a `level` field, so `doctor`'s log-scan safety net could never fire — fixed same session (part of `c507a270`'s changes).
3. Windows `npx` preflight probed with no shell wrapper, false-negatively hard-failing the whole Tier B gate on any project relying on the npx fallback — fixed (`18640d71`).
4. `runWithTimeout()` raced the _whole batch_ against a timer and discarded all completed progress (edges, `filesProcessed`) on timeout, even at 999/1000 files done — fixed via a cooperative per-file deadline (`edc60238`).
5. `node_key` for LSP-derived edges had no disambiguation at all (`file#symbolName` collided for any two same-named symbols in one file — overloads, same-named methods on different classes) — fixed by sharing Tier A's `buildUniqueNodeKey` disambiguation logic and pre-assigning keys by line position so Tier B's ordering converges onto Tier A's (`2e4176d1`, `c04f0770`). A fuller, order-independent fix (structurally-qualified keys, e.g. `file#ClassName.methodName`) is proposed but **not implemented** — [`GRPH-006-qualified-symbol-table-node-key.md`](../gitbook/adr/graph/GRPH-006-qualified-symbol-table-node-key.md) (`5cb889e4`).

**Live re-verification (2026-07-30, this session):** rebuilt from current `main` (`pnpm run build`), ran `docuvia analyze --escalate-to-lsp` against Docuvia2's own repo — `doctor` reported 11/11 checks passing first. Result: **151 files processed, 451 corrected edges applied, exit 0**, no degradation. `query "buildUniqueNodeKey" --format=prompt` — a symbol touched by today's fix commits, so its callers were part of this batch — now returns **5 real `<incoming>` edges** (`persist-ast-graph.ts`, `GraphPersisterService`, `lsp-edge-provider-base.ts`, `BaseLspEdgeProvider`, `node-key.unit.test.ts`). Confirms the five fixes above are real and effective for symbols whose callers get reprocessed.

### 5.3 Root cause B (not fixed, more fundamental than any single bug): Tier B is strictly commit/delta-scoped, with no full-resync path

Querying two other real, heavily-called symbols in the same repo, same session, **immediately after** the clean 451-edge Tier B batch above:

```
$ docuvia query "QueryService" --format=prompt
<docuvia_context>
  <l2_module name="QueryService" type="module" file="lib/core/src/query/query.service.ts">
  </l2_module>
</docuvia_context>

$ docuvia query "findNodeByName" --format=prompt
<docuvia_context>
  <l2_module name="findNodeByName" type="module" file="lib/schema/src/sqlite/repos/graph-repo.ts">
  </l2_module>
</docuvia_context>
```

Both come back with **zero edges**, despite `findNodeByName` having real, greppable callers (`query.service.ts:81,143`, `impact.service.ts:48`, `persist-ast-graph.ts:361`) and `QueryService` being instantiated/used across the CLI. This is the exact "thin" symptom from the `b8a575bf` session — reproduced live, _after_ every bug in §5.2 was fixed.

**Root cause, confirmed by direct inspection:** `git log -1 -- lib/core/src/query/query.service.ts lib/schema/src/sqlite/repos/graph-repo.ts` shows both files last changed **2026-07-24** (`e1a07c3b`) — six days before this batch, and before every fix in §5.2 existed. Tier B only (re)computes a symbol's incoming "calls" edges when one of its _caller_ files is itself part of a processed Tier B batch (`tierBQueue`, populated by full-ingestion-time queueing or per-commit `CONTRACT_CHANGED` delta detection — [`run-delta-ingestion.ts:51`](../../lib/ui-core/src/workflows/analyze/run-delta-ingestion.ts)). Neither `query.service.ts` nor any of `findNodeByName`'s callers has been touched by a commit since 2026-07-24, so none of them has ever been queued into `tierBQueue` under _any_ version of the code — the edges were never computed, correctly or incorrectly; there is nothing to have been dropped by the §5.2 bugs.

This means: **Docuvia2's own knowledge graph — built up continuously over weeks of real commits, long before today's fixes existed — has a large backlog of files that Tier B has never reprocessed under the current, fixed code**, and will not until each one happens to be touched by a future commit. Two compounding structural gaps make this worse, both confirmed by direct code/CLI inspection:

- `docuvia init` only started queueing a **fresh** workspace's full initial parse into `tierBQueue` as of `4232439f` (2026-07-29, "queue init's initial parse for Tier B, matching analyze's full ingestion") — Docuvia2's own graph predates that fix, so was never queued in full even once, on any version of the code.
- There is **no user-facing way to force a full Tier B resync of an existing graph**. `docuvia analyze --help` exposes only `--escalate-to-lsp`/`--fallback-ast`/`--lsp-timeout`/`--interactive`/`--force`; `--force` is scoped entirely to Tier C decision extraction ([`run-tier-c-drain.ts:152`](../../lib/ui-core/src/workflows/analyze/run-tier-c-drain.ts)), not Tier B's queue. The only way to force a full resweep today is `clean` (wipe `local.db`) + re-`init` — untested this session against a graph this size for side effects on already-persisted L3 decisions.

**Practical implication:** `docuvia query`/`impact` cannot currently distinguish "this symbol genuinely has no callers" from "this symbol's callers were never processed by Tier B" — both render as an identical empty `<incoming>`/`<outgoing>` block. On a codebase with real dogfooding history (not a fresh `init`), most queries will hit the second case for a long time, which is what actually produced the "usable but thin" impression — a structural gap, not a leftover bug from §5.2's list.

### 6.3 New bug found via `git reset --soft`: delta ingestion reads git-blob content at `headSha`, not the working tree — a backward-moving `HEAD` silently reverts real, on-disk code out of the graph

The session owner specifically asked for a `git reset --soft HEAD~3` test (moving `HEAD` back 3 real commits, leaving the working tree/index untouched at the newer state) to probe `impact`/blast-radius correctness. This surfaced a genuine, independently-reproduced-on-two-repos bug, more severe than any gap §3-§5 already cover.

**nest** (tested first): reset to 3 commits before `dfaa3761` (69 real files changed, including a rewritten `InterceptorsConsumer.transformDeferred` and a new-parameter signature change to `LegacyRouteConverter.printWarning`). `docuvia analyze` handled the rewound-`HEAD`-with-staged-changes state without crashing: `"Re-parsed 13 file(s), dropped 2 deleted file(s), queued 9 file(s) for Tier B"`, `L2 Nodes` dropping 16,159 → 16,066. At the time this read as plausible delta behavior. Restored to `dfaa3761` via `git reset --soft` back to the original sha (working tree was never touched by the soft reset, so no re-ingestion was needed to restore consistency) and confirmed clean.

**vscode** (tested second, with a more targeted symbol): reset to 3 commits before `1b6a1881` (18 files changed). Picked `isRelatedNeighboringFileType` — a brand-new free function added by exactly those 3 commits (`extensions/copilot/.../similarFiles/neighborFiles.ts`), with one real intra-file `calls` edge, confirmed present via a baseline `query` **before** the reset:

```
$ docuvia query "isRelatedNeighboringFileType" --format=prompt   # before reset
<l2_module name="isRelatedNeighboringFileType" ... />
<incoming><caller name=".../neighborFiles.ts" relation="calls" /></incoming>
```

After `git reset --soft HEAD~3` + `docuvia analyze` (`"Re-parsed 18 file(s), dropped 0 deleted file(s), queued 11 file(s) for Tier B"` — no crash):

```
$ docuvia query "isRelatedNeighboringFileType" --format=prompt   # after reset+analyze
<docuvia_context></docuvia_context>

$ docuvia impact "isRelatedNeighboringFileType"
⚠ No matching node found for "isRelatedNeighboringFileType"
```

The function **vanished from the graph entirely** — not "thin," genuinely absent — despite being unchanged, real, present code in the actual file on disk (a soft reset never touches the working tree).

**Root cause, confirmed by direct code read and a reproducing git command:**

- `headSha` is resolved as a bare `git rev-parse HEAD` ([`analyze-workflow.ts:202`](../../lib/ui-core/src/workflows/analyze/analyze-workflow.ts)) — no comparison against the actual working-tree/index state.
- `collectFilesToParse()` then reads each changed file's content via `git.readFileAtRef(workspaceRoot, headSha, entry.file)` ([`run-delta-ingestion.ts:222`](../../lib/ui-core/src/workflows/analyze/run-delta-ingestion.ts)) — a git blob lookup at that exact ref, **never the actual file on disk**.
- Verified the diff direction directly: `git diff --stat <fromSha=1b6a1881, newer/last-ingested> <headSha=f9a0f54c, older/rewound>` on the affected file reports **"3 insertions(+), 23 deletions(-)"** — i.e. the function's _addition_ renders as a _deletion_ in this direction, because `fromSha` (already ingested) is newer than the now-rewound `headSha`. Delta ingestion re-parses using `headSha`'s git-historical (older, function-less) content, not the real current file, so the function is correctly-per-its-own-logic-but-wrongly-in-reality dropped as if deleted.
- **Independently reproduced on nest**: the "dropped 2 deleted file(s)" from the nest test above was confirmed (via `git diff --name-status <3-commits-back> <original HEAD>`) to be exactly the two files genuinely **added** by those 3 commits (`packages/common/test/utils/http-error-by-code.util.spec.ts`, `packages/core/test/router/legacy-route-converter.spec.ts`) — still present, unchanged, on disk. Same root cause, same wrong-direction consequence, on a second, independent repo, found without deliberately targeting it.

**Practical implication**: any git operation that moves `HEAD` backward while the working tree/index stays at (or ahead of) the newer state — `git reset --soft`/`--mixed`, an undone `commit --amend`, a rebase later aborted after `analyze` already ran mid-rebase, reflog-based recovery — causes Docuvia2's delta ingestion to **silently remove real, currently-existing symbols and files from the knowledge graph**, with `analyze` reporting success (`"Delta ingestion complete"`) and no error surfaced. This directly corrupts `impact`/`query`/blast-radius results for affected symbols, and is worse than §5.3's already-documented "thin" gap: §5.3 is _missing_ data (never-yet-processed callers); this is _wrong_ data (actively-reverted, stale content masquerading as current). Not covered by any of §3.3/§3.7's three fixed bugs, §4's environment gate, or §5.3's commit/delta-scoped-resync gap — a sixth, distinct delta-ingestion architecture gap: **delta ingestion trusts git commit-graph ordering (`fromSha → headSha`) as ground truth for "current state," instead of comparing actual file content against what was already ingested.**

**Recommendation**: `collectFilesToParse()` should read from the actual working-tree/index content (or Docuvia should at minimum detect when `headSha` is not a descendant of `fromSha` in the commit graph and fall back to a full re-ingestion / surfaced warning, rather than silently trusting a same-direction diff that is actually backward).

## 7. Performance deep-dive (2026-08-04, same session): why vscode's AST-parse phase scales far worse than file-count alone predicts

This section was requested to explain a gap sitting unexamined in §4 and §6.2: Docuvia2's `init`/`analyze` AST-parse phase against `vscode` measured ~1047.6s (§4) and ~1057.8s (§6.2) — a consistent ~1050s across two independent runs, both already downstream of the `better-sqlite3` environment fix landed in §3.7. A naive linear projection from nest's post-environment-fix AST-parse number (15.1s, §3.7) by file count alone predicts far less: nest has 1,675 `.ts` files, vscode has ~6.9x more (12,338 files requested per §6.2's `filesRequested: 12338`), so linear scaling predicts ~104-111s — the actual ~1050s is roughly **10x** that projection, not a rounding-error gap. A dedicated, read-only code investigation was run this session to explain it. **This investigation substantially revises this document's own prior assumptions**: §3's framing that "Docuvia2's AST stage measured 1.8-2.9x slower than GitNexus/Graphify... Attributed to WASM (`web-tree-sitter`, ADR-022) vs. native `tree-sitter` bindings," and §3.7's attribution of the nest 283.1s→15.1s swing to the `better-sqlite3` ABI fix, both turn out to be incomplete or unsupported once the file-size distribution is actually measured and the WASM grammar-loading code path is actually traced. The rest of this section explains why — with the caveat, stated plainly and matching this doc's own epistemic norms elsewhere, that some of what follows is a code-reading-derived hypothesis, not a live re-measurement; §7.4 lists exactly what would need to be measured to fully confirm it.

### 7.1 File-size distribution, not just file count, is the dominant factor (confirmed by direct measurement)

Measured directly this session via `git ls-files '*.ts' | xargs stat` against the real local clones (`D:\GitHub\nest`, `D:\GitHub\vscode`, both present in this environment) — this is a real measurement, not a hypothesis:

|                                             | nest (1,675 `.ts`) | vscode (11,636 `.ts`) | ratio                                                    |
| ------------------------------------------- | ------------------ | --------------------- | -------------------------------------------------------- |
| mean bytes                                  | 2,076              | 12,191                | 5.87x                                                    |
| median (p50)                                | 647                | 5,092                 | 7.87x                                                    |
| p90                                         | 5,178              | 26,020                | 5.03x                                                    |
| p99                                         | 21,458             | 94,007                | 4.38x                                                    |
| max                                         | 41,037             | 8,535,324             | —                                                        |
| total bytes                                 | 3,476,735          | 141,850,200           | **40.80x**                                               |
| files >512,000B (the enforced oversize cap) | 0                  | 5                     | matches §6.2's logged `filesSkippedOversized: 5` exactly |

Re-projecting from nest's 15.1s using **total bytes** instead of file count gives `15.1s × 40.80 ≈ 616s` — vs. the naive file-count-only projection of ~104-111s. The actual measured ~1050s is only about **1.7x** above this byte-weighted projection, not ~10x. So file-size skew (vscode's `.ts` files are ~5.9x bigger on average, and the gap holds across the whole distribution, not just a few outliers — the median gap is actually _larger_ than the mean gap at 7.87x) explains most of the originally-puzzling 10x gap on its own. This is the strongest, most directly-verified finding in this section.

### 7.2 The residual ~1.7x: `Language.load()` is called fresh per file, never cached, never disposed (code-confirmed mechanism, not yet live-measured)

- [`ast-worker.ts:640-693`](../../lib/core/src/ast/ast-worker.ts) (`buildParseResponse`): `Parser.init()` and the provider `registry` are memoized at worker-lifetime scope (`parserInitialized`/`registryPromise`, [`ast-worker.ts:110-116`](../../lib/core/src/ast/ast-worker.ts)), but the grammar itself is not — `const langInstance = await Language.load(wasmPath);` at [`ast-worker.ts:687`](../../lib/core/src/ast/ast-worker.ts) runs once per file, forever, with no cache anywhere in `ast-worker.ts`, `ast-worker-pool.ts`, or the registry types ([`language-provider.ts`](../../lib/ast-core/src/language-provider.ts)'s `LanguageProvider` only carries a `wasm_file` filename, never a loaded `Language` instance).
- This is a real cost, not a cheap wrapper call: `Language.load()` (in `web-tree-sitter`'s own source, `tree-sitter.js:2028-2059`) reads the `.wasm` bytes from disk and calls Emscripten's `loadWebAssemblyModule` (`tree-sitter.js:2902-3141`) — a dynamic-library loader doing real `WebAssembly.instantiate` plus relocation into the shared runtime's Table/Memory.
- `web-tree-sitter`'s `Language` class has no `delete()`/dispose method (unlike `Tree`/`Parser`, which [`ast-worker.ts:629-630`](../../lib/core/src/ast/ast-worker.ts) _does_ correctly free) — so every `Language.load()` call permanently grows the worker's shared WASM dynamic-linking state (Table entries, static data) for the life of the worker process, with no way to release it.
- Worker count is identical between the two runs: `workerCount = Math.max(1, os.cpus().length - 1)` ([`ast-processing.service.ts:29`](../../lib/core/src/ast/ast-processing.service.ts)) → 13 workers on this machine either way. But per-worker cumulative load differs 7.4x: ~949 files/worker on vscode vs. ~129 files/worker on nest (12,338/13 vs. 1,675/13) — far more room for any cumulative WASM-heap/Table-growth cost to compound within a single worker's lifetime.
- **Corroborating evidence already elsewhere in this same document**: §6.2 (line ~278) already logged `filesFailed: 4` with `RuntimeError: table index is out of bounds` in web-tree-sitter's WASM parser during the vscode run. State plainly: this is not proof of the leak mechanism, but it's a real, already-observed failure signature consistent with a WASM dynamic-linking Table that's been repeatedly grown/relinked without ever being unloaded — worth flagging as corroborating, not conclusive.
- Secondary, non-independent amplifier: [`ast-processing.service.ts:40-105`](../../lib/core/src/ast/ast-processing.service.ts) processes files in fixed batches of 50 with a hard `Promise.all` barrier per batch (behavior unchanged by commit `05a8dc10`'s ordering fix, per direct `git show 05a8dc10`). vscode runs ~247 such batches vs. nest's ~34 — if later files in a long worker lifetime get progressively costlier under the Language.load leak, one straggler per batch stalls the whole batch even while other workers idle, so the pool never stays continuously fed across the full run the way a flat queue would.

### 7.3 A previously-stated causal claim in this document does not hold up: the §3.7 `better-sqlite3` attribution

Report plainly, since this is a genuine correction to the document's own prior claim (matching §3's own self-correction style, "⚠️ Superseded by §3.7"): `AstProcessingService`/`AstWorkerPool`/`ast-worker.ts` — the whole AST-parse code path — never import or touch `better-sqlite3` anywhere in that call chain (confirmed by direct code trace this session). So §3.7's framing ("Speed: ~307.3s → ~24s, same source, no code change... Confirms the environment was the dominant factor") has no actual code-level causal path for the _specific_ 283.1s→15.1s AST-parse-phase swing it's attached to, even though the `better-sqlite3` ABI mismatch was real and did legitimately block DB commands.

The alternate, more mundane and independently testable explanation: the 15.1s re-run was a second, back-to-back run over an _unchanged_ file set — nest's entire working set (1,675 files × ~2KB average + a handful of reused `.wasm` grammars, all comfortably within available RAM) would already be resident in the OS page cache on that second run, a classic warm-vs-cold-cache swing of exactly this magnitude, independent of sqlite entirely. Flagged explicitly: **if this alternate explanation is right, 15.1s is not a trustworthy "steady state" baseline to linearly project from in the first place — it may be the outlier run, not vscode's ~1050s.** This is stated as a hypothesis requiring the re-test in §7.4 below to confirm, not as settled.

### 7.4 What would need to be _measured_, not just read, to fully confirm this (per this doc's own verify-before-claim norm)

1. Instrument `Language.load()` ([`ast-worker.ts:687`](../../lib/core/src/ast/ast-worker.ts)) with per-call wall-clock timing plus a per-worker running file counter during a real vscode run, to check whether load time trends upward with that worker's cumulative files processed — the single most decisive missing measurement for §7.2's leak-growth hypothesis.
2. Add a `Map<wasmPath, Promise<Language>>` cache in `ast-worker.ts` and re-time the vscode pass — if the ~1.7x residual from §7.1 mostly disappears, that's a clean confirmation of §7.2 _and_ a real, shippable fix, not just a diagnosis.
3. Re-run nest's AST-parse phase a third consecutive time (same day, same machine, zero code changes) — if it stays ~15s, the warm-page-cache hypothesis in §7.3 weakens (something else made the first run slow); if a _first_ run after a fresh reboot reproduces ~283s again, that's strong evidence for page-cache over the sqlite-coincidence explanation.
4. A controlled parse-time-vs-file-size regression — isolate a stratified sample of small/medium/large `.ts` files and time `parser.parse()` alone — to determine whether tree-sitter's per-file parse cost is linear or worse-than-linear in bytes for large files, which would separate "§7.2's WASM Language-leak" from a completely different explanation ("large files are just structurally more expensive to parse — deeper ASTs, more query matches") that code-reading alone cannot distinguish.
