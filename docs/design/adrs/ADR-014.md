# ADR-014: Microkernel AST Architecture & Plugin Ecosystem

## Context
To allow AI to accurately understand project structures, static scanning using an Abstract Syntax Tree (AST) parser (e.g., Tree-sitter) is required. However, supporting a multitude of languages (e.g., 30+ languages) in a monolithic architecture would lead to a massive binary/dependency size, performance drag, and difficult maintenance. Every time a language releases a new syntax feature, the core project would require updates.

## Decision
We will transition the core system into a lightweight "Microkernel Architecture" and separate the AST parsing logic for each language into independent "Plugins".

- **Docuvia Core (Microkernel)**: The core (`@workspace/api-server`) will handle lifecycle management, task scheduling, database writes (PostgreSQL/Drizzle), and Agentic RAG routing. It will not contain any language-specific logic. It receives standard JSON/Object interfaces (`GraphNode`, `GraphEdge`, `CallFlow`) to write into the database.
- **Docuvia Language Plugins**: Each language parser will be encapsulated in an independent package (e.g., `@workspace/plugin-ast-typescript`).
- **Plugin Manager (Dynamic Loader)**: During the project initialization phase, an Extension Probe will determine the language composition of the project. The Plugin Manager will then dynamically load only the required language plugins at runtime based on the detected file extensions.

## Consequences
- **Positive**: The core package size is minimized, enabling extremely fast startup times.
- **Positive**: Enhanced extensibility. The community can create new language plugins matching the Docuvia interface without modifying the core source code.
- **Positive**: Fault tolerance via sandboxed isolation. If a specific language parser crashes or hangs, it won't crash the Docuvia API server; the microkernel can catch the error and flag the node parsing as failed.
