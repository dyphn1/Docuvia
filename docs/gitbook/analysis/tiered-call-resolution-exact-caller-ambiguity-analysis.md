# Exact caller review: ambiguous target matches

This is a read-only investigation of the nine FP labels in the current 60-item review artifact: eight in `other` and one in `class-ownership`. No resolver behavior changed as part of this analysis.

## Evidence limits

The committed review artifact stores target/caller symbols, source snippets, and call-site snippets. It does **not** store the audit's per-edge `CallResolutionSummary` or `CallSiteResolutionRecord`. The parity runner also replaces `ImpactService.buildEntry` to avoid L3 reads and emits no per-site provenance. Therefore the exact `resolutionClass`, `confidence`, Q1/Q2/Q3 proof signature, or hypothesis record cannot be recovered for a static `calls` row from this artifact alone. The table names the producing path supported by the source and current resolver implementation, and marks unavailable per-site fields instead of guessing. A persisted static `calls` entry has no `edgeSource`; a call without a resolution record is surfaced as `resolutionClass: unknown` with no confidence. The three file-node rows are identifiable as the ImpactService same-name fallback and carry `edgeSource: lsp-fallback`; that label is a heuristic same-name call-site fallback, not evidence that an LSP server resolved the call.

For the six function/class rows, the source snippets show same-file member/bare-name cases that `ScopeResolver.resolveMemberCall` can resolve through its local-name fallback. Its result contains only a target file and symbol, with no confidence. Strict proof projection can replace a target when Q1/Q2/Q3 proof exists, but this review artifact does not say whether it did so for these particular call sites. Thus `ScopeResolver` is the supported producer inference; the strict-proof record is unverified.

The v1/v2 audit compares impact membership, not every incoming edge. Each listed caller is v2-only by node key, so v1 did not return that exact caller for the target. Target resolution is shared by the caller policies; the cached reports do not preserve the alternative v1 caller node, so a specific replacement caller cannot be named reliably.

## Existing syntactic signals and hook points

System One already captures call kind, receiver text/hint, receiver type-known status, generic arguments, imports, and a bounded source window in `system1-syntax.ts` and `system1-types.ts`. Its ambiguity classifiers detect unresolved receivers, overloads, DI lookups, and several import/call-shape conditions. `receiverTypeHint` recognizes annotations, `new` initializers, assertions, and `this.field` declarations. These are useful inputs, but System One does not currently classify cross-language name collisions, built-in method receivers, a `this`/`self` owner mismatch, or duplicate test-registry declarations as dedicated ambiguity classes.

The hypothesis index carries `callSiteShapeFacts` and `declaredTypeFacts`, exposes `getReceiverTypeFact` and `candidateMatchesReceiver`, and the hypothesis service has an `explicitReceiverType` filter stage plus a syntax-bound-class path. This is enough structure to feed some receiver evidence into the candidate ranking, but it is not evidence that the nine historical rows were filtered: the audit omitted their per-site records. `candidatesForSyntaxBoundClass` is for a simple `ClassName.member()` receiver; the unresolved `this.field`, Python `self`, DOM and builtin cases need a receiver-owner compatibility rule. No explicit cross-language fallback guard or registry-stub duplicate detector was found in these paths.

Minimal future hooks, without changing this PR's resolver:

- In `ImpactService.resolveCallSiteFallback`, compare source and target file languages before creating a file-level fallback. Cross-language same-name matches should be hard exclusions.
- Near `GraphPersisterService.resolveCallTarget` / the ScopeResolver member fallback, use existing call-shape and declared-type facts to prevent known incompatible receiver owners and builtin receivers from becoming confirmed `calls` edges. Keep the bounded candidate targets with a candidate certainty label.
- In the System One feature builder/classifiers, add explicit receiver-owner-mismatch, builtin-receiver, cross-language-name, and duplicate-registry signals. Its later decision stage can narrow or reject these candidates using the candidate list; it should not retroactively turn heuristic name equality into proof.
- Leave locally bound receivers whose types cannot be read syntactically to LSP. If LSP is unavailable, expose a candidate set with unknown confidence rather than a confirmed edge.

## Retrospective score sensitivity

The original labels are 51 TP, 9 FP, 0 unsure (60 items): 85.0% stratified stress score and 97.8% population-weighted point estimate, with a 78.8% lower bound and a failed gate. Applying only the visible cues to these nine rows would hard-exclude the cross-language `reset` and builtin `Set.add` matches, and demote the other seven FP rows to candidates.

The confirmed-only reviewed precision is 51/51 (100.0%); all 51 reviewed TP callers remain on the caller list, so sample caller-list recall is 51/51 (100.0%). The last line is a sample-only weighted sensitivity calculation: it subtracts all nine observed FP items from their existing `other`/`class-ownership` eligible counts and treats all remaining reviewed items as confirmed. It is not a new population estimate because the corpus-wide frequency of these syntactic cues has not been measured. Even under that optimistic sensitivity, the weighted lower bound stays below the 90% acceptance threshold, so the 60-item re-score does **not** change the gate decision. A production proposal needs a corpus-wide reclassification and a fresh seeded sample before making a precision claim.
