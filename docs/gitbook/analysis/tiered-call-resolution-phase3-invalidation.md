# GRPH-008 Phase 3: Dependency invalidation

This closes the source-change invalidation gap for the current Q1/Q2 proof slices and supports the explicit Q3 receiver dependencies documented in [Phase 3 Q3 receiver proofs](tiered-call-resolution-phase3-q3-receiver-proof.md). It does not change ScopeResolver, proof selection policy, Tier B eligibility, calibration, or test/temporal labels.

## Workflow wiring

- Delta ingestion hashes every changed path at `headSha`, including configuration files; deleted paths and the old side of renames are sent with a null hash. Generated Docuvia hooks are excluded. Immediately after hashing and before semantic classification, the repository invalidates proofs whose stored dependency fingerprint changed and rebuilds each affected caller's collapsed `calls` projection inside the same SQLite transaction.
- The delta workflow reparses affected callers that were not already changed or retired. A delta reuses the persisted complete source index when its commit and file facts are current; otherwise it conservatively keeps ScopeResolver's edge and leaves strict reproof to a later complete ingestion. A stale proven target is never retained.
- Full ingestion and successful hydration invalidate all current proof rows and rebuild their projections before replacing graph state. Full ingestion can prove again from its complete source index; hydration treats imported aggregate links as unproven graph state.
- Repeat `init` does not reparse a populated graph: `InitWorkflow.execute()` returns through its already-initialized guard before discovery or persistence. First-time init has no prior proof state to invalidate.
- Tier B results for stale rows continue to be rejected. Projection rebuilding retains a collapsed caller-to-target edge while any other current call site in that caller still selects the target.

## Complete delta reproof

### Design

`project_files.source_index_json` stores one versioned v3 source-index record per parsed file. It contains the exact parser-input SHA-256 and the facts consumed by the hypothesis index: imports, exports, re-exports, call-site shapes, and declared-type facts. It also stores each function's graph node key, name/container, source span, and declaration target keys, plus the local function, class, and variable names registered with `ScopeResolver`. The graph references let a delta map a strict proof's selected target to an unchanged function node without parsing that target file again. The resolver names let it rebuild the same whole-workspace resolver used by full ingestion. Full ingestion clears and replaces these records as part of graph persistence. Delta persistence updates records for changed and re-parsed caller files; deleted and renamed-old files lose their records with their `project_files` rows.

After a complete full ingestion, `callResolutionSourceIndexSha` records the source `HEAD` represented by the facts. The marker is written only when discovery parsed every candidate, every project-file row has a valid source record, and Git reports a clean working tree. It is a diagnostic stamp, not an authorization token: a blank marker after an earlier fallback must not block recovery forever. Before a delta reuses unchanged facts, Git must report a clean working tree and the workflow validates the persisted inventory against the tracked blob hashes at current `HEAD`. For every unchanged discoverable source path, its project-file row must exist, its versioned source facts and graph/resolver references must validate, and `project_files.content_hash` must equal that path's HEAD blob SHA. The clean-worktree check makes the staged index blob map identical to `HEAD`; `project_files.content_hash` remains the Git blob SHA used by file discovery.

Changed paths are parsed from `headSha` as usual. An unchanged tracked source with missing, malformed, or hash-mismatched persisted facts is added to the repair parse set and read from `headSha`; a persisted source path no longer present in the tracked tree is retired. These repairs run before the persister claims completeness, so a source row written from dirty working-tree content cannot validate merely because its JSON is well-formed. Affected callers reparsed from committed `HEAD` are stored with their tracked Git blob SHA, matching file discovery, rather than a parser-input SHA-256; otherwise an unchanged caller would be treated as stale on every later delta. Dirty/untracked paths cause the current run to retain the ScopeResolver fallback. Once the tree is clean, a later delta can recover by validating all unchanged rows and reparsing any dirty-content rows from committed `HEAD`, even if the prior fallback cleared `callResolutionSourceIndexSha`. The Git diff remains the complete path transition from `fromSha` to `headSha`; renames are applied as removal of the old path plus addition of the new path.

When a delta falls back after it has changed or reparsed callers, `callResolutionReproofPendingPaths` stores those changed and invalidated caller paths. The next clean delta merges that queue with hash-mismatch repairs, reparses the queued paths from `headSha`, and derives their proofs even when the new commit did not change those callers. The queue is cleared only after the merged source index and strict-proof pass complete. A full ingestion on a clean tree clears it as well. This is required because a complete source index alone does not prove that a previous fallback's caller rows were re-derived.

The persister constructs the same workspace index from that combined record set and applies strict proofs only to the changed and invalidated caller files. For projection, it combines the persisted function-node references for unchanged files with freshly rebuilt references for parsed files; reparsed entries override their old references. It also rebuilds `ScopeResolver` from every validated persisted file's imports and local names, then overlays the fresh facts for parsed files. Thus both strict proof collection and the legacy resolver fallback see the same complete source inventory as a full parse. `sourceManifestFingerprint` sorts the same `(filePath, sourceContentHash)` manifest used by full ingestion, so record order does not affect the index identity.

### Equivalence argument

The argument is inductive. At commit A, a full parse of every discoverable candidate on a clean tree stores every parser fact, resolver local-name inventory, graph function reference, and clean tracked Git blob SHA. Assume those records equal a fresh full parse and graph-reference map at A. For A→B, every added or changed source path is parsed from B and replaces its A facts/references; every deleted or rename-old path is removed; and each unchanged row is accepted only if its stored blob SHA still equals the clean tracked `HEAD` blob and its source/index/reference schema validates. A missing or mismatched unchanged row is rebuilt from B before the pass can claim completeness. Any paths whose callers were processed during an incomplete fallback remain queued and are reparsed from B on the next complete delta. Therefore, after successful repairs and pending reproof, the combined path/hash/fact/reference set and proven caller rows equal a fresh full parse at B. The same hypothesis-index builder receives the same semantic inputs; the rebuilt resolver receives the same imports and local names; and projection sees the same target node keys. Each re-parsed caller therefore receives the same strict proven rows and the same `calls` edges as full init. Proof dependencies are still invalidated before persistence; changed targets or barrels cannot retain stale proofs. Calls outside strict-proof rules continue through the existing ScopeResolver logic, now with its complete source inventory.

### Fail-closed cases

Reproof falls back to the current parsed-batch ScopeResolver behavior and writes a reason into the `analyze.delta.summary` JSONL record if Git status cannot be read, the worktree is dirty, the source-fact repository or HEAD blob inventory is unavailable, the pending-reproof path list is malformed (`pending-reproof-paths-invalid`), changed content cannot be read, an affected caller cannot be read, a repair/change is oversized, or parsing has any failure. Missing, malformed, unsupported, or blob-mismatched rows are not accepted: current tracked source paths are reparsed from `HEAD`, while obsolete paths are retired. Parse/read/size failures leave the index incomplete and retain the precise fallback reason. `callResolutionSourceIndexSha` may be blank after fallback, but the next clean delta recomputes completeness from the rows and pending caller paths and can self-heal without a full init. This avoids both trusting dirty facts and a sticky fallback state.

### Repository benchmark

On Node 24.14.1, four non-frozen workflow TypeScript files received comment-only edits at B; both the pre-change and current delta runs reparsed seven files. The pre-change delta took **0.89 s**. The current delta took **14.15 s**, while a fresh full init at B took **83.95 s**. The current delta therefore pays to validate and index the persisted workspace facts, but remains below the full-init reference. The pre-change full init at A took 81.42 s.

The delta and full-init B snapshots contained the same 4,710 strict-proof rows, including counts of 3,462 Q1 named-import, 47 Q2 re-export, 1,040 Q3 new-receiver, 10 Q3 super-call, and 151 Q3 typed-receiver proofs. All 763 raw `calls` rows sourced by the seven reparsed files matched. A whole-graph probe found three additional source-target pairs in full init, all from unchanged AST fixture callers outside the reparsed set; the fixture integration test separately asserts exact full-graph `calls` row equality for its changed and re-parsed fixture callers.

This mechanism does not change Q1 rule inputs, Q1 certification configuration, proof signatures, dependency fingerprints, or the order of dependency invalidation. Hydrated/legacy databases without these records remain safe: they fail the baseline check and require a full ingestion before delta reproof can be enabled.

## Exit-gate coverage

The workflow tests cover a changed target, a Q2 barrel edit, a configured `tsconfig` path edit, an unrelated one-file edit, and invalidation errors before persistence. SQLite integration tests cover hash changes and deletion, unrelated-path no-churn, shared collapsed edges after an LSP contradiction, stale Tier B responses, bounded batches, and rollback when projection rebuilding fails. Full-ingestion and hydration tests assert invalidation occurs before source replacement. The focused run passed 102 tests across five files.

Q1 and Q2 are implemented for their current strict proof slices, as are the bounded explicit Q3 receiver rules. Broader proof shapes and the remaining Phase 3 exit and certification gates stay open in the [Phase 3 gap table](tiered-call-resolution-phase3-q1-named-import-proof.md#phase-3-gap-audit). Delta invalidation deliberately chooses safe over-invalidation over treating an incomplete index as complete.
