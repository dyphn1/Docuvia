## Round 1 — Architecture & Design Review

### Design ↔ Implementation Alignment

**✅ Correctly implemented:**

1. CLI `sync` subcommand with post-commit hook stdin support (RESOLVED since 0626)
2. `POST /projects/:id/sync` has `requireApiKey` auth (RESOLVED since 0626)
3. Server-side sync performs real git clone + commit delta ingestion (RESOLVED since 0626)
4. ADR-021 shared core API implemented; local SQLite migration complete (RESOLVED c3de191)
5. **`docuvia.sync` command registered in VS Code extension** (RESOLVED since 130d37d) — Command registered at `extension.ts:447` using `SyncService` from `@workspace/core`
6. **`docuvia.sync` registered in `package.json`** — Command appears in contributes.commands (line 141)
7. **New `SyncService` calls authenticated endpoint** — `SyncService.sync()` at `lib/core/src/services/SyncService.ts` calls `POST /projects/:id/sync` with Bearer token auth, NOT the legacy `/sync/push`

### Gaps / Deviations

1. **❌ `POST /sync/push` has no `requireApiKey`** — The legacy CQRS outbox receiver remains unauthenticated. Any client can send arbitrary L3 node creation events to the server without API key. This is a 🔴 security risk.

2. **⚠️ Hardcoded `projectId = "1"` in `docuvia.sync` command** — The new VS Code sync command hardcodes `projectId = "1"` (extension.ts:462). This means the command always syncs to project ID 1 regardless of which workspace project the user intends. This is a 🟡 functional gap — multi-project workspaces would sync the wrong project.

3. **⚠️ `CentralServerClient.sync()` is still dead code** — The new `docuvia.sync` command uses `SyncService` (from @workspace/core) instead of `CentralServerClient.sync()`. The `CentralServerClient.sync()` method remains implemented but never called from any extension code path. It also calls the legacy `/sync/push` endpoint (unauthenticated), which is a secondary concern.

## Round 2 — Code Quality & Security Review

### Strengths

1. `POST /projects/:id/sync` correctly uses `requireApiKey` middleware
2. `SyncService.sync()` sends Bearer token auth — the new sync command is properly authenticated
3. Advisory lock (`pg_try_advisory_xact_lock`) prevents concurrent sync conflicts
4. Transaction wrapping ensures atomic L3 node creation
5. Input validation via `SyncPushBody.safeParse()` Zod schema on the legacy endpoint
6. **`docuvia.sync` command requires getToken() — fails early with error message if no token set**

### Issues Found

1. **🔴 `POST /sync/push` unauthenticated** — No `requireApiKey` middleware. The endpoint accepts CQRS outbox events and writes directly to the database without any authentication. This is exploitable for unauthorized data injection.
   - **File:** `artifacts/api-server/src/routes/sync.ts` line 14
   - **Fix:** Add `requireApiKey` middleware or remove the endpoint if `/projects/:id/sync` fully supersedes it.

2. **🟡 Hardcoded projectId** — The `docuvia.sync` command uses `const projectId = "1"` (extension.ts:462). This should be derived from the workspace's `.docuvia/config.json` or similar project mapping.
   - **Fix:** Read projectId from the workspace's local configuration instead of hardcoding.

3. **🟡 Inconsistent auth patterns** — Three different auth mechanisms across sync surfaces: MCP_PAT Bearer token (SyncService → `/projects/:id/sync`), x-docuvia-token header (CentralServerClient → `/sync/push`), and no auth on the `/sync/push` route itself. The new command correctly uses Bearer auth, but the dead CentralServerClient still uses the legacy header pattern.

## Overall Verdict

**⚠️ WARN**

Two source files changed since the previous verification (2026-06-28). The most significant change is the **addition of `docuvia.sync` command** in `extension.ts` (commit 130d37d), which resolves the prior VS Code integration gap. However, the new command introduces a minor finding (hardcoded `projectId = "1"`).

The remaining open findings are:

1. **🔴 `POST /sync/push` unauthenticated** — The legacy CQRS outbox receiver at `artifacts/api-server/src/routes/sync.ts:14` has no `requireApiKey` middleware. This allows unauthenticated L3 node creation. **Recommendation:** Add `requireApiKey` to the router or remove the endpoint if `POST /projects/:id/sync` fully supersedes it.
2. **🟡 Dead `CentralServerClient.sync()`** — Now clearly superseded by `SyncService` from `@workspace/core`. The SDK method calls the unauthenticated `/sync/push` endpoint and is never invoked. **Recommendation:** Remove `CentralServerClient.sync()` or rewiring it to call the authenticated `/projects/:id/sync` endpoint.
3. **🟡 Hardcoded `projectId = "1"`** — The `docuvia.sync` VS Code command always targets project ID 1. **Recommendation:** Read the project ID from the workspace's local `.docuvia/` configuration file.
4. **🟡 Inconsistent auth patterns** — SyncService uses Bearer token, CentralServerClient uses x-docuvia-token header, `/sync/push` has no auth.

The sync CLI feature is now functionally complete for both terminal and IDE users. The remaining gaps are one security hardening issue, one dead code cleanup, and one configuration gap.

**Recommendation:** Priority order for the Developer Agent:
1. Add `requireApiKey` to `sync.ts` or remove it if `/projects/:id/sync` fully supersedes it (resolves 🔴)
2. Replace hardcoded `projectId = "1"` with workspace config lookup (resolves 🟡)
3. Either remove `CentralServerClient.sync()` or rewiring it to the authenticated endpoint (resolves 🟡)
