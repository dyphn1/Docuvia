2. **`l2_node_l1_tags`** (defined in `l2_nodes.ts`) — association table for l2_nodes and l1_tags.

- **ADR-009 (Token Management):** `l3_nodes` table has `occurrenceCount`, `sourceCommits`, `validityStatus` fields ✅; `llm_configs` has `similarityThreshold` (default 0.85) and `condensationThreshold` (default 30) ✅
- **ADR-010 (L2 Bootstrap):** `commit_l2_links` junction table is defined ✅; `l2_nodes` has `pathPatterns` (JSONB) and `isBootstrapConfirmed` ✅
- **ADR-011 (Two-Phase Validity):** Both `commits` and `l3_nodes` have `validityStatus` fields ✅; `commits` has `branchName` ✅
- **ADR-012 (Document Misc Pool):** `documents.projectId` is nullable ✅; has `contentHash`, `affiliatedAt`, `status` fields ✅

### Design Document and Implementation Consistency

Design documents and implementation are highly consistent. All 16 table field designs match the architecture document descriptions. `commits.l2NodeId` and `l3_nodes.commitHash` are both correctly marked `@deprecated`, showing the team has a clear migration strategy.

## Round 2: Code Quality and Security Review

### Code Structure

- **High consistency:** All 16 schema files follow a unified pattern — using `pgTable` definitions, `createInsertSchema` to generate Zod validation schemas, and exporting TypeScript types.
- **Foreign Key Integrity:** All foreign key references use `{ onDelete: "cascade" }` or `{ onDelete: "set null" }`, ensuring data integrity.
- **Naming Conventions:** Table names use snake_case (Drizzle convention), TypeScript variables use camelCase, consistent and clear.
- **Zod Validation:** 14 tables have `createInsertSchema` (except `activity_log` and `l2_node_l1_tags`). `activity_log` is an internal audit table that doesn't need external input validation — reasonable.

### Security

- **SQL Injection Protection:** Uses Drizzle ORM parameterized queries, no raw SQL concatenation risk.
- **Input Validation:** Zod schemas auto-generated via `drizzle-zod`, all insert operations have type validation.
- **Foreign Key Constraints:** Database-level foreign key constraints prevent orphaned records.

### Potential Issues

1. **`llm_configs.model` default value is `gpt-5.2`** (line 11 of `llm_configs.ts`): This is a very new model name. If OpenAI hasn't released this model yet, it could cause LLM call failures. Recommend confirming the model name is available, or changing the default to a confirmed existing model (e.g., `gpt-4o`).

2. **`l2_node_l1_tags` not exported from `index.ts`:** Although `l2NodeL1TagsTable` is defined in `l2_nodes.ts`, `index.ts` does not have an `export *` statement to export it. This means external modules cannot access this table via `import { l2NodeL1TagsTable } from '@workspace/db/schema'`. If this table is being used, the export should be added; if not yet used, it can remain but should be annotated with a comment.

3. **`activity_log` missing Zod schema:** While acceptable as an internal audit table, if future API endpoints need to manually write to activity_log, insert validation should be considered.

4. **`commits.valid` field** (line 15 of `commits.ts`): Type is `boolean`, but `validityStatus` is `text`. There is semantic overlap — `valid` is a boolean while `validityStatus` is a string status. Recommend documenting the relationship between the two, or unifying them in a future version.

## Round 3: Integration and Completeness Review

### Integration with API Server

- `lib/db/src/index.ts` provides a `db` proxy object (using `AsyncLocalStorage`), supporting transaction context propagation.
- The `runInRollbackTransaction` function provides a `withRollback()` mode for integration tests, consistent with the test infrastructure in `artifacts/api-server/test/support/db.ts`.
- `package.json` `exports` provides both `./` (full DB client) and `./schema` (schema only), allowing the API server to import just the schema without connection logic.

### Drizzle Kit Migration Configuration

- `drizzle.config.cjs` correctly points to `./src/schema/index.ts` as the schema source.
- `package.json` has `push` and `push-force` scripts, corresponding to checklist item 1.1.2.
- Migration SQL files exist in `lib/db/src/migrations/`, but are in suggested SQL format (marked "Suggested SQL DDL") and have not been converted to formal Drizzle migrations. This is acceptable in early development.

### Test Infrastructure

- `artifacts/api-server/test/support/factories.ts` and `db.ts` exist, supporting DB state creation and rollback testing.
- The correspondence between schema definitions and test factories needs subsequent verification (falls under item 1.1.4 scope).

### End-to-End Usability

- All 16 table schema definitions are complete, including necessary fields, constraints, defaults, and indexes.
- Foreign key relationships form a complete data model: projects → commits → l2_nodes → l3_nodes, plus cross-table node_links and subscriptions.
- Enum types (project_status, vcs_type, document_type, review_task_type, etc.) provide additional type safety at the database level.

### Missing Items

- No formal Drizzle migration folder (`drizzle/` directory), only hand-written SQL suggestion files. Acceptable during v1 development, but production should use `drizzle-kit generate` to produce formal migrations.
- `l2_node_l1_tags` table is not exported, which may affect L1-L2 association feature development.
