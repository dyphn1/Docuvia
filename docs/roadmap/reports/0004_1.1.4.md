### Factory Pattern Consistency

The existing 3 factories follow a unified pattern:
1. `build(overrides)` — pure data object generation, no DB interaction
2. `create(overrides, client)` — inserts into DB and returns the created record
3. Optional `client` parameter (defaults to `db`) supports rollback context
4. `overrides` uses spread operator to allow partial overrides

This pattern is consistent with AGENTS.md's description of "accept overrides and remain friendly to randomized/fuzz inputs."

### Contradictions Between Design Documents

No contradictions. However, the design document description is too general and does not explicitly require factories for all tables.

## Round 2: Code Quality and Security Review

### Factory Structure Quality

```typescript
// Factory pattern example (ProjectFactory)
export const ProjectFactory = {
  build(overrides: Partial<InsertProject> = {}): InsertProject {
    const id = nextSequence();
    return {
      name: `Project ${id}`,
      repoUrl: `https://github.com/example/project-${id}`,
      description: `Generated project ${id}`,
      status: "active",
      vcsType: "git",
      ...overrides,
    };
  },
  async create(overrides: Partial<InsertProject> = {}, client: DbLike = db) {
    const [project] = await client
      .insert(projectsTable)
      .values(ProjectFactory.build(overrides))
      .returning();
    return project;
  },
};
```

**Strengths:**
- Uses `Partial<InsertProject>` type to ensure type-safe overrides
- `build()` and `create()` are separated, supporting both pure data tests and DB integration tests
- `client` parameter supports rollback context injection
- Spread operator allows flexible overrides

**Issues:**

1. **Sequence counter not reset** (`factories.ts` lines 6-11):
   ```typescript
   let sequence = 0;
   function nextSequence() {
     sequence += 1;
     return sequence;
   }
   ```
   The module-level `sequence` variable increments continuously during test runs and is never reset. Although `withRollback()` rolls back DB data, the sequence counter is not reset. This means:
   - Different test cases will have different sequence values (test order dependency)
   - If a test assertion depends on a specific name (e.g., `"Project 1"`), it may fail depending on execution order
   - Recommendation: Reset the sequence in `setup.ts`'s `beforeEach`, or use random strings instead of incrementing numbers

2. **Missing `resetSequence()` function:** No public function to reset the sequence, preventing tests from controlling the starting value.

3. **L2NodeFactory `projectId` parameter design:**
   ```typescript
   build(projectId: number, overrides: Partial<InsertL2Node> = {}): InsertL2Node
   ```
   `projectId` is a required parameter, meaning tests must create a Project before creating an L2 Node. This is logically correct (foreign key constraint), but the factory does not provide a convenience method for "auto-creating dependencies." Similarly, `L3NodeFactory` also requires `l2NodeId`.

4. **L3NodeFactory missing ADR-009 fields:**
   - `occurrenceCount` (default 1) — needed for L3 dedup tests
   - `sourceCommits` (JSONB) — source commit tracking
   - `validityStatus` (default "pending") — ADR-011 two-phase validity
   - `source` (default "commit") — knowledge source classification

5. **activity_log table has no Insert type** (`activity_log.ts`):
   ```typescript
   // activity_log.ts only defines the table, no createInsertSchema
   export const activityLogTable = pgTable("activity_log", { ... });
   ```
   The other 15 tables all have `Insert*` type exports, but `activity_log` does not. This makes it impossible to create a type-safe factory for `activity_log`.

### Security

- No SQL injection risk: Uses Drizzle ORM parameterized queries
- Factories are only used in test environments, not affecting production code
- `client` parameter ensures factories are safely used in rollback context

### Integration with withRollback

The integration of factories with `withRollback()` is well-designed:
- The `create()` `client` parameter defaults to the global `db` object
- Within a `withRollback()` callback, the `db` Proxy automatically routes to the transaction connection
- Therefore, `ProjectFactory.create()` works in `withRollback` without explicitly passing a client

```typescript
// Usage in mcp-list-projects.test.ts
await withRollback(async () => {
  const project = await ProjectFactory.create({ name: "Test" });
  // db Proxy automatically uses the transaction connection
});
```

## Findings Summary

### ✅ Passed Items

1. `factories.ts` exists at the specified path, containing 3 factories (ProjectFactory, L2NodeFactory, L3NodeFactory)
2. Factory pattern design is correct: `build()` for pure data, `create()` for DB insert, `overrides` support, `client` parameter for rollback
3. Type-safe: uses `Partial<Insert*>` to ensure type checking on overrides
4. Well integrated with `withRollback()`, factories automatically use transaction connection in rollback context
5. At least one test (`mcp-list-projects.test.ts`) correctly uses factories
6. 15 out of 16 schema files have `Insert*` type exports (activity_log is the exception)

### ⚠️ Warnings

1. **Extremely low factory coverage:** Only 3/17 tables have factories (17.6%); 14 tables lack corresponding factories
2. **Sequence counter not reset:** Module-level `sequence` variable increments continuously during test runs with no reset mechanism, potentially causing test order dependency
3. **L3NodeFactory missing ADR key fields:** Missing `occurrenceCount`, `sourceCommits`, `validityStatus`, `source`, affecting ADR-009 and ADR-011 related tests
4. **L2NodeFactory missing embedding field:** May affect vector search related tests
5. **activity_log has no Insert type:** Schema does not use `createInsertSchema`, making it impossible to create a type-safe factory

### ❌ Failed Items

None. The factory infrastructure itself is correctly designed; the issue is insufficient coverage rather than implementation errors.

## Recommendations

### High Priority

1. **Create factories for all missing tables:** At minimum, create `CommitFactory`, `DocumentFactory`, `L1TagFactory`, `ReviewTaskFactory`, `CorrectionExampleFactory`, `PullRequestFactory`, `LlmConfigFactory`, `PromptTemplateFactory`

2. **Create Insert type for activity_log:** Add `createInsertSchema` to `activity_log.ts` and export the `InsertActivityLog` type

3. **Fix sequence counter issue:**
   ```typescript
   // Recommended addition to factories.ts
   export function resetSequence() {
     sequence = 0;
   }
   ```
   And call `resetSequence()` in `setup.ts`'s `afterEach`

4. **Add ADR fields to L3NodeFactory:** Add default values for `occurrenceCount`, `sourceCommits`, `validityStatus`, `source`

### Medium Priority

5. **Create junction table factories:** `CommitL2LinkFactory`, `NodeLinkFactory`

6. **Add convenience methods to factories:** e.g., `ProjectFactory.createWithL2Nodes(count)` to auto-create projects with child nodes

7. **Consider using a faker library:** Replace predictable names from `nextSequence()` with random data to avoid implicit dependencies between tests

### Low Priority

8. **Write unit tests for factories themselves:** Verify that `build()` output conforms to schema constraints

9. **Create factory documentation:** Add usage instructions and examples at the top of `factories.ts`

## Overall Verdict

**⚠️ WARN**

The test factory infrastructure is correctly established, and the existing 3 factories have a well-designed pattern with correct `withRollback()` integration. However, factory coverage is only 17.6% (3/17 tables), 14 tables lack corresponding factories, and the existing L3NodeFactory is missing ADR-009/011 key fields. The sequence counter not being reset may cause test order dependency. The factory infrastructure itself has no defects, but the coverage is severely insufficient to support comprehensive integration test development.
