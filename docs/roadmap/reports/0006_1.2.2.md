## Round 1: Architecture and Design Review

### Design and Implementation Consistency

The design documents explicitly require calling `svn log --xml` and `svn diff` via `child_process.execFile`, storing SVN revisions in the `commits` table, and using the `vcsType` field to distinguish between Git and SVN. The implementation fully conforms to this design:

- `svn-client.ts` uses `execFileAsync("svn", [...])` which correctly prevents shell injection
- `commits` table has `revision` (integer) and `vcsType` (text) fields
- `projects` table has `svnUrl`, `lastSvnRevision`, `vcsType` fields
- Route handler uses `hash: "svn:R${rev.revision}"` to ensure uniqueness
- OpenAPI spec defines complete `SvnIngestInput` and `SvnIngestResult` schemas

### Issues Found

**Issue 1: `endRevision` type inconsistency (HIGH)**

The Zod validator (`IngestSvnBody`, `api.ts` lines 295–298) defines `endRevision` as:
```typescript
endRevision: zod.number().optional().describe("...defaults to HEAD")
```

But `getSvnLog()` function signature (`svn-client.ts` line 54) accepts `number | "HEAD"`:
```typescript
endRevision: number | "HEAD",
```

And the route handler (`ingest.ts` line 224) uses:
```typescript
const endRevision = body.endRevision ?? "HEAD";
```

This means:
1. If client sends `endRevision: "HEAD"` (string), Zod will reject the request (400 Bad Request)
2. If client omits `endRevision`, the route handler correctly uses `"HEAD"` as default
3. OpenAPI spec also defines `endRevision` as `integer` type

**Conclusion:** The design intent is to allow the `"HEAD"` string value, but the API contract (Zod + OpenAPI) does not allow it. This is a spec-vs-implementation inconsistency.

**Issue 2: Missing URL validation (MEDIUM)**

The AI implementation plan (`implement_svn-integration.md` line 271) explicitly states:
> "The `repoUrl` is validated against an allowlist regex in the route handler before reaching this function."

But the actual route handler (`ingest.ts` lines 209–322) has **no URL format validation**. `svnUrl` is taken directly from `body.svnUrl` and passed to `getSvnLog()` / `getSvnDiff()`. While `execFile` itself prevents shell injection, the lack of URL validation means invalid or malicious URLs are passed to the SVN CLI, potentially causing unexpected network requests or error message leakage.

**Issue 3: Missing `--` option separator (LOW)**

The AI implementation plan (lines 187, 230) recommends adding a `--` separator before the URL to prevent it from being interpreted as a CLI flag:
```typescript
"--",   // end of options — prevents URL from being interpreted as a flag
repoUrl,
```

But the actual implementation (`svn-client.ts` lines 63–69, 98–103) does **not** include this separator. While this won't cause issues in most cases, if `svnUrl` starts with `-`, it could be misinterpreted as a command-line option.

## Round 2: Code Quality and Security Review

### Security

| Item | Status | Notes |
|------|--------|-------|
| Uses `execFile` instead of `exec` | ✅ Correct | Prevents shell injection attacks |
| `--no-auth-cache` flag | ✅ Correct | Prevents credentials from being cached to `.subversion/auth` |
| `--non-interactive` flag | ✅ Correct | Prevents process from waiting for interactive password input |
| URL validation | ❌ Missing | No format validation on `svnUrl` |
| Password transmission | ⚠️ Caution | Password passed via command-line arguments, may be visible via `/proc` or `ps` |
| Error message leakage | ⚠️ Caution | Full SVN CLI error messages returned to client, may leak internal path info |

### Code Quality

**Strengths:**
- `svn-client.ts` has clear structure with single-responsibility functions
- `SvnRevisionInfo` interface provides good type safety
- XML parsing uses regex (lightweight, no external dependencies)
- Error handling distinguishes between "SVN not installed" and "SVN command failed"
- Route handler correctly implements incremental ingestion (`lastSvnRevision` cursor)
- Uses `scoreCommit()` for signal/noise filtering, consistent with Git ingestion

**Weaknesses:**
- XML parsing uses regex instead of a formal XML parser; complex SVN message content (e.g., containing `<` or `>` characters in commit messages) may fail to parse
- Regex in `parseSvnLogXml` uses `[\s\S]*?` non-greedy matching, which may be incorrect for nested XML or special characters
- Route handler collects `getSvnDiff` failures into an `errors` array but **still stores the revision in the database** (with empty `diff`), potentially causing incomplete data to be ingested
- `ingest.ts` line 221 redundantly parses `req.body` again (`SvnModeSchema.parse(req.body)`) since `IngestSvnBody` already includes the `mode` field

### Code Smell

```typescript
// ingest.ts line 221 — redundant body parsing
const { mode: svnMode } = SvnModeSchema.parse(req.body);
// Should use body.mode directly, since IngestSvnBody already includes mode
```

### End-to-End Usability

The feature is theoretically complete:
1. Client sends `POST /projects/:id/ingest/svn` request
2. Server calls `svn log --xml` to get revision list
3. Calls `svn diff` for each new revision
4. Stores results in `commits` table
5. Updates `projects.lastSvnRevision`
6. Returns ingestion statistics

But the following issues affect actual usability:
- `endRevision: "HEAD"` cannot be sent via API (Zod type restriction)
- No URL validation, error messages may not be user-friendly
- No tests to ensure graceful degradation when SVN CLI is unavailable

## Recommendations

1. **Fix `endRevision` type**: Change Zod schema and OpenAPI spec to `zod.union([zod.number(), zod.literal("HEAD")])` or similar, allowing clients to explicitly send `"HEAD"`
2. **Add URL validation**: Add `svnUrl` format validation in route handler (e.g., `/^(svn(\+ssh)?|https?):\/\/.+/i`)
3. **Add `--` separator**: Add `"--"` separator to `execFile` arguments in `svn-client.ts`
4. **Handle diff failure**: Consider skipping the revision when diff fetch fails, or mark it for retry
5. **Add unit tests**: Add unit tests for XML parsing functions in `svn-client.ts`
6. **Add integration tests**: Add integration tests for SVN ingestion route (can use MSW or mock `child_process`)
7. **Remove redundant parsing**: Use `body.mode` directly instead of re-parsing `req.body`

## Overall Verdict

# ⚠️ WARN

**Rationale:** The core SVN ingestion functionality is fully implemented, including the `svn-client.ts` CLI wrapper, route handler, OpenAPI spec, Zod validators, and database schema. However, there is a high-priority type inconsistency (`endRevision` cannot accept `"HEAD"` string), missing URL validation, and zero test coverage. These issues need to be addressed in the next development cycle.
