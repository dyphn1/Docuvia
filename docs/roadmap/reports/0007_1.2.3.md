### Gaps Found

**Gap 1: OpenAPI Response Status Code Inconsistency**
- OpenAPI spec (line 369) defines success response as `"200"`
- Implementation (`ingest.ts` line 384) returns `res.status(201)`
- Design document (line 303) also specifies `"201"`
- **Impact:** OpenAPI spec is the single source of truth, but is inconsistent with implementation. Orval-generated hooks may expect a different status code than actual.

**Gap 2: Missing contentHash Calculation**
- DB schema (`documents.ts` line 22) defines `contentHash` field
- Design document (ADR-012 / 4.4.2) requires SHA-256 hash calculation on upload
- Implementation does not calculate or store `contentHash` at all
- **Impact:** Cannot perform document deduplication or integrity verification

**Gap 3: Missing activity_log Recording**
- Git and SVN ingestion paths both write to `activityLogTable`
- Document upload path (lines 343-386) **does not write to activity log**
- **Impact:** Audit trail is incomplete; document upload events won't appear in activity log

**Gap 4: Missing `commitSha` Association Handling**
- OpenAPI spec's `DocumentUploadInput` (lines 2011-2013) defines optional `commitSha` field
- Route handler does not process this field at all
- **Impact:** Cannot associate documents with specific commits on upload

**Gap 5: `projectId` is nullable in DB schema but upload route requires project to exist**
- DB schema (`documents.ts` line 17): `projectId` has no `.notNull()`
- Upload route (lines 348-349): returns 404 if project doesn't exist
- This means DB allows null projectId, but API doesn't allow uploading to non-existent project
- **Impact:** Design document ADR-012 mentions "Misc Pool" concept (documents can exist independently of projects), but upload endpoint enforces valid project requirement — contradiction

### Conclusion

Core functionality is fully implemented, design documents and source code are largely aligned. Main gaps: (1) OpenAPI status code inconsistency, (2) missing contentHash, (3) missing activity_log, (4) unhandled commitSha, (5) incomplete Misc Pool support.

## Round 2: Code Quality and Security Review

### Code Structure

**Strengths:**
- `document-parser.ts` uses lazy loading (`require()`) to avoid pdf-parse's DOMMatrix startup issue (lines 26-27) — reasonable engineering decision
- `upload.ts` middleware is cleanly designed with MIME type + extension dual validation
- Error handling follows defensive design: multer errors have dedicated handler (lines 428-446)
- Parse failure returns 422 (unprocessable entity) — semantically correct
- Empty content check (lines 368-372) prevents storing meaningless documents

**Issues:**

**Issue 1: `require()` mixing ESM and CJS**
- `document-parser.ts` uses `require()` to import pdf-parse, mammoth, officeparser
- Project is `"type": "module"` (`package.json` line 6)
- Although `eslint-disable` comment is added, this is an anti-pattern
- Should use dynamic `import()` or ensure ESM compatibility
- **Risk:** Future package versions may no longer support CJS require, causing runtime errors

**Issue 2: `parsePptx` Promise wrapping is unsafe**
```typescript
// document-parser.ts lines 42-57
return new Promise((resolve, reject) => {
  const { OfficeParser } = require("officeparser") as { ... };
  OfficeParser.parseOffice(buffer, (err, data) => {
    if (err) reject(err);
    else resolve(data ?? "");
  });
});
```
- If `OfficeParser.parseOffice` throws synchronously (instead of via callback), the Promise won't catch it
- Should move `require()` outside the Promise or wrap with try-catch

**Issue 3: Missing file name length limit**
- `originalname` stored directly in DB with no length limit
- Extreme cases could cause DB field overflow or XSS (if frontend doesn't properly escape)

**Issue 4: Missing virus/malicious content scanning for uploaded files**
- Uploaded PDF/DOCX may contain malicious content
- Currently only MIME type checking, no deep content validation
- **Risk:** Low (internal tool), but worth noting

**Issue 5: `detectDocType` extension mapping includes `log` but design doc doesn't mention it**
- `document-parser.ts` line 19: `log: "build_artifact"`
- Design document (line 141) only lists `map`, `fv`, `fd`
- This may have been added later without updating the design doc

### Security Assessment

| Item | Status | Notes |
|------|--------|-------|
| File size limit | ✅ | 10 MB hard cap |
| MIME type allowlist | ✅ | Dual validation (MIME + extension) |
| Memory storage (no disk write) | ✅ | `multer.memoryStorage()` |
| Path traversal protection | ✅ | No filesystem operations |
| Binary data not stored in DB | ✅ | Only extracted text stored |
| Project existence validation | ✅ | 404 if project doesn't exist |
| Input length validation | ⚠️ | File name has no length limit |
| Deep content type validation | ⚠️ | Only checks MIME, doesn't validate file content structure |

## Round 3: Integration and Completeness Review

### End-to-End Flow

**Document Upload → Knowledge Graph Flow:**
1. Client uploads file → `POST /projects/:id/ingest/document/upload`
2. Multer validates file type and size
3. `detectDocType()` determines type from file extension
4. `extractText()` calls appropriate parser
5. Extracted text stored in `documentsTable.content`
6. Returns 201 with document record
7. (Expected) Client then calls `POST /projects/:id/generate` for L1→L2→L3 knowledge extraction

**Integration Issues:**

**Issue 1: Missing activity_log recording affects audit trail**
- Git/SVN ingestion both have activity_log, but document upload doesn't
- This causes `/projects/:id/activity` endpoint to be unable to fully track all ingestion events

**Issue 2: Zero test coverage**
- Searching the entire project, there are **no** `document-parser.test.ts` or `ingest.test.ts` files
- Design document §8 lists explicit test scenarios (PDF/DOCX/PPTX upload curl tests)
- But automated tests are completely absent
- **Risk:** Parser behavior changes may break silently

**Issue 3: Package versions differ from design document**
- Design doc specifies: `pdf-parse ^1.1.1`, `mammoth ^1.8.0`, `officeparser ^4.1.2`, `multer ^1.4.5-lts.2`
- Actually installed: `pdf-parse ^2.4.5`, `mammoth ^1.12.0`, `officeparser ^6.1.1`, `multer ^2.1.1`
- Version differences are significant (officeparser 4.x → 6.x, multer 1.x → 2.x)
- **Risk:** Major version upgrades may have breaking changes, but no tests to verify

**Issue 4: OpenAPI spec missing 422 response**
- Implementation returns 422 (parse failure, empty content)
- OpenAPI spec only defines 200, 400, 413
- Missing 422 response definition

**Issue 5: Frontend integration status unknown**
- Design document mentions frontend uses Orval-generated hooks
- Generated `DocumentUploadInput` schema includes `commitSha` and `docType` fields
- But route handler doesn't process these fields; even if frontend sends them, they're ignored

### Performance Considerations

- Synchronous parsing of large files may block the event loop
- No queue mechanism: large PDF parsing will occupy the Event Loop
- No progress reporting: must wait for complete parsing after upload before getting response
- For 10 MB files, this may be acceptable in practice, but should be monitored

### Conclusion

The feature core is implemented and architecturally sound, but lacks automated tests, activity_log integration, contentHash calculation, and has OpenAPI spec inconsistencies. These issues don't block basic functionality but affect system completeness, maintainability, and audit capability.

## Recommendations

1. **Fix OpenAPI status code**: Change spec line 369 from `"200"` to `"201"`, aligning with implementation and design document
2. **Implement contentHash**: Calculate `crypto.createHash('sha256').update(content).digest('hex')` in upload route and store in DB
3. **Add activity_log**: Insert activity log record after successful document upload
4. **Handle commitSha**: Read `commitSha` from `req.body` and store in DB or create association
5. **Add unit tests**: Create tests for `document-parser.ts` and upload route, covering all file types and error scenarios
6. **Update design document**: Update package versions to match actually installed versions
7. **Consider ESM-compatible imports**: Change `require()` to dynamic `import()`

## Overall Verdict

**Rationale:** The core functionality (PDF/DOCX/PPTX/MD/TXT upload and text extraction) is fully implemented.
