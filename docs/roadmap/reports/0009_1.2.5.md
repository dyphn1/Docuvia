## Round 1 — Architecture & Design Review

### Design Spec Coverage

The design specification adequately describes the intent of `scoreCommit()`:
- **04-solution-strategy.md** places it in the Input Layer alongside Git/SVN adapters, GitHub webhook listener, and document upload.
- **06-runtime-scenarios.md** shows it as a filtering step in the Git ingestion sequence.
- **12-glossary.md** defines it precisely: "signal/noise scoring function applied during ingestion to filter out low-value commits."

### Gaps Between Design and Implementation

1. **Not a shared library module.** The design places `scoreCommit()` in the Input Layer as a standalone filter component. In practice, it is a local function `function scoreCommit(message: string): number { ... }` duplicated across two route files (`ingest.ts` and `github_webhooks.ts`). There is no file like `artifacts/api-server/src/lib/commit-scorer.ts` or similar.

2. **Scope limited to commit message only.** The function scores only the commit message text. It does not examine the diff size, number of files changed, file paths, or other metadata that could improve signal/noise discrimination (e.g., a commit that touches one file with a vague message like "update" might be noise, but a commit that touches 50 files with a 2-line message might be significant).

3. **Threshold is hardcoded.** The commit-validity threshold (`score >= 0.4`) is hardcoded in three places (ingest.ts line 156, ingest.ts line 277, github_webhooks.ts line 96). There is no configuration option to tune this per-project or globally.

4. **No `valid`/score info in API response.** The commit's score is reduced to a boolean (`valid: score >= 0.4`). The actual numeric score is discarded, making it impossible for downstream consumers (e.g., review UI) to rank commits by signal quality.

### Contradictions Between Design Documents

- The **archive design** (`11-commit-filter.md`) references file paths (`generateInput.ts`, `gitIngestInputMode.ts`) that do not exist in the current codebase — these are from the v1 design and were replaced by the current route-based architecture. This is acceptable as historical documentation but could confuse new contributors.

### Completeness Per Design Spec

The core 10 noise patterns and 10 signal patterns are implemented:
- **Noise (return 0.1):** `^merge (pull request|branch)`, `^bump version`, `^chore:`, `^auto-generated`, `^ci:`, `^wip:`, `^revert `, `^initial commit`, `^update changelog`, `^\[skip ci\]`
- **Signal (+0.15 each):** `fix(ed|es|ing)?`, `feat(ure)?`, `add(ed|s|ing)?`, `refactor`, `implements?`, `resolves?`, `breaking change`, `decision`, `architecture`, `performance`
- **Bonus (+0.1):** message length > 50 characters
- **Base score:** 0.3

## Round 2 — Code Quality & Security Review

### Code Structure

**FINDING — CRITICAL DUPLICATION [D-01 / R-05]:** The `scoreCommit()` function is copy-pasted across two files with 34-line identical logic:

| Location | Lines | Local variable name |
|----------|-------|-------------------|
| `ingest.ts` | 43–78 | `const msg = message.toLowerCase()` |
| `github_webhooks.ts` | 32–66 | Uses `message` directly (no `toLowerCase()`) |

**Subtle behavioral difference:** In `ingest.ts` (line 44), the message is lowercased before testing: `const msg = message.toLowerCase()`. The noise/signal regex patterns are all case-insensitive (`/i` flag), so the `toLowerCase()` is redundant. In `github_webhooks.ts`, there is no `toLowerCase()` call — the message is passed directly to the regex tests. The `/i` flag means both produce the same result, but the inconsistency indicates copy-paste drift and differing author styles.

**Violation of POP (Protocol-Oriented Programming) standard:** The project's coding standards specify POP for services. A shared scoring utility should be a protocol (interface) with a concrete implementation in `artifacts/api-server/src/lib/commit-scorer.ts`, imported by both route files.

### Security

- **Low risk.** `scoreCommit()` operates purely on commit message strings with regex matching. No injection vectors, no I/O, no auth bypass risks.
- **Input validation:** Commit messages come from trusted sources (Git CLI output, GitHub API). No user-supplied data flows through `scoreCommit()` without prior ingestion into the database.

### Code Smells

1. **Magic numbers:** 0.3 (base score), 0.15 (signal bonus), 0.4 (validity threshold), 50 (min message length) are all hardcoded with no named constants or configuration.
2. **No exported function:** The function is file-scoped (`function scoreCommit`), making it impossible to unit test without exporting or refactoring.
3. **No error handling:** If `message` is `null` or `undefined`, calling `.toLowerCase()` (in `ingest.ts`) or accessing `.length` (in both) will throw a runtime error. In practice, GitHub/Git commit messages are always strings, but defensive coding would add a guard.

### Test Coverage

**No unit tests exist for `scoreCommit()`.** This was flagged in the 1.2.1 verification report (0005_1.2.1.md) and remains unresolved. The function is pure (no side effects, no DB calls) and trivially testable:

```typescript
// Ideal test cases that should exist:
// - "fix: resolve auth bug" → score ≥ 0.45
// - "Merge pull request #123" → 0.1 (noise)
// - "chore: bump version to 1.2.3" → 0.1 (noise)
// - "" (empty) → 0.3 (base)
// - "wip: initial commit" → 0.1 (noise, matches both patterns but noise is checked first)
// - "Add new feature: implement OAuth2 flow with PKCE" → ≥ 0.6
```

## Round 3 — Integration & Completeness Review

### System Integration

1. **Generate pipeline integration (correct):** `generate.ts` line 407 correctly filters `commits.valid = true` when fetching commits for L1/L2/L3 generation. This ensures low-signal commits are excluded from knowledge construction.

2. **Ingestion integration (correct):** Both Git and SVN ingestion routes in `ingest.ts` use `scoreCommit()` to set `commits.valid`. GitHub webhook PR ingestion in `github_webhooks.ts` also uses it.

3. **Downstream consumers see only boolean:** The `commits.valid` boolean is set at ingestion time. The numeric score is discarded. If the threshold needs tuning, all previously ingested commits would need re-scoring.

### Performance

- **Negligible.** `scoreCommit()` runs 11 regex tests maximum per commit. Even with 10,000 commits, this is ~110,000 regex operations — trivial for a single Node.js thread.
- The function is called synchronously in the ingestion loop, which is already I/O-bound (DB inserts, Git CLI calls). No async concerns.

### End-to-End Usability

- The feature works end-to-end: low-signal commits (merges, bumps, auto-generated) get `valid = false` and are excluded from the generate pipeline.
- **Usability gap:** There is no UI or API to view/adjust the signal threshold or to re-score commits after tuning.

## Recommendations

1. **Extract `scoreCommit()` to `artifacts/api-server/src/lib/commit-scorer.ts`** as a shared utility. Export the function so it can be imported by `ingest.ts`, `github_webhooks.ts`, and any future ingestion sources. This directly addresses **D-01** and **R-05** in the project's debt register.
2. **Add unit tests** in `commit-scorer.unit.test.ts` covering: each noise pattern, each signal pattern, compound-signal commits, empty string, boundary scores (0.3, 0.4), and max score capping (1.0).
3. **Replace magic numbers** with named constants: `const BASE_SCORE = 0.3`, `const SIGNAL_BONUS = 0.15`, `const VALID_THRESHOLD = 0.4`, `const DETAIL_BONUS_LENGTH = 50`.
4. **Consider storing the numeric score** in a `commits.score` column (or similar) instead of discarding it after the boolean conversion. This enables threshold tuning without re-ingestion.
5. **Add input guard** at the top of `scoreCommit()`: `if (!message) return 0.1;`

---

## Overall Verdict

### ⚠️ WARN

The `scoreCommit()` signal/noise filter is **functionally correct** and properly integrated into all three ingestion paths (Git, SVN, GitHub webhooks). The noise/signal pattern sets are reasonably comprehensive for a v1 filter, and the generate pipeline correctly consumes the `valid` boolean.

However, the **code duplication between `ingest.ts` and `github_webhooks.ts`** is a documented risk (D-01/R-05) that has not been addressed. The lack of unit tests, hardcoded magic numbers, and loss of numeric score granularity further reduce confidence. These are not blockers for functionality, but they are concrete code quality issues that should be resolved.
