## Round 1 — Architecture & Design Review

### Does the design document correctly describe the feature?

**Yes.** ADR-007 in `docs/design/09-architectural-decisions.md` (line 153) clearly states:

> The `projects` table has `lastGitIngestedAt` (timestamp) and `lastSvnRevision` (string) cursor columns. The `commits` table has a `processedAt` column. Incremental ingestion reads only commits newer than the cursor; the `mode: "incremental" | "full"` parameter is respected in all ingest routes.

This accurately describes the implementation. The design specifies three cursor columns across two tables, and the implementation matches:
- `projects.lastGitIngestedAt` — line 22 of `projects.ts` schema: `timestamp("last_git_ingested_at")`
- `projects.lastSvnRevision` — line 23 of `projects.ts` schema: `integer("last_svn_revision")`
- `commits.processedAt` — line 20 of `commits.ts` schema: `timestamp("processed_at")`

### Are there gaps between the design spec and the actual implementation?

**No major gaps.** All three cursor columns exist in the schema and are wired into the ingest/generate routes. However, there is one subtle design-implementation mismatch:

1. **ADR says `lastSvnRevision` is "string" but schema defines it as `integer`.** The ADR document describes `lastSvnRevision` as "(string)" but the actual Drizzle schema defines it as `integer("last_svn_revision")`. The implementation correctly uses `integer` since SVN revisions are numeric. The ADR description is imprecise but the code is correct.

2. **`processedAt` cursor is used in `generate.ts` not `ingest.ts`.** The `commits.processedAt` column is set in `generate.ts` (line 860-867) when `mode === "incremental"`, not in `ingest.ts`. This is architecturally correct — `ingest.ts` stores raw commits, and `generate.ts` marks them as processed after knowledge extraction. The ADR groups them together correctly.

### Are there contradictions between different design documents?

**No contradictions found.** The ADR-007 decision is consistently reflected in the schema definitions and route implementations.

### Is the feature complete per the design spec?

**Yes.** The feature is complete:
- Git incremental ingestion uses `lastGitIngestedAt` as a `since` parameter to the GitHub API
- SVN incremental ingestion uses `lastSvnRevision` to set `startRevision`
- Generate incremental mode uses `processedAt IS NULL` to find unprocessed commits
- All three cursor columns are exposed via the `/ingest/status` endpoint
- The `mode: "full" | "incremental"` parameter is respected in both Git and SVN ingest routes

## Round 2 — Code Quality & Security Review

### Is the implementation code well-structured and following the project's coding rules?

**Mostly yes.** The code follows MVC patterns (routes → DB via Drizzle ORM), uses defensive design (early returns for 404s, input validation via Zod), and follows the project's coding conventions.

### Are there security vulnerabilities?

**Several concerns identified:**

1. **`githubToken` accepted in request body (ingest.ts line 107).** The Git ingest endpoint accepts a `githubToken` in the POST body, which is then used as a Bearer token for GitHub API calls. While this allows per-request token override, it means:
   - The token will be logged in HTTP access logs
   - The token could be leaked in error responses
   - No validation is performed on the token format before use
   - **Recommendation:** Use `Authorization` header or environment variable only; avoid accepting secrets in request bodies.

2. **SVN credentials in request body (ingest.ts lines 222-236).** The SVN ingest endpoint accepts `username` and `password` in the request body via the `IngestSvnBody` Zod schema. These are passed as command-line arguments to `svn`. While `execFile` prevents shell injection, the credentials:
   - May appear in process listings (`ps aux`)
   - Will be logged in HTTP access logs
   - Are not encrypted at rest
   - **Recommendation:** Use environment variables or a credential store for SVN auth.

3. **No authentication on ingest endpoints.** None of the ingest routes (`POST /projects/:id/ingest/git`, `POST /projects/:id/ingest/svn`, `POST /projects/:id/ingest/document`) have authentication middleware. Any client can trigger ingestion for any project.
   - **Recommendation:** Add authentication middleware to protect these endpoints.

4. **Zod parsing error exposes details (ingest.ts line 218).** The SVN ingest route catches Zod errors and returns the full error object: `return res.status(400).json({ error: "Invalid request body", details: err })`. This could leak internal schema details to clients.
   - **Recommendation:** Sanitize Zod errors before returning them.

### Are there code smells, duplication, or anti-patterns?

**Several minor issues:**

1. **Duplicate notification/subscription logic.** The Git ingest (lines 176-191) and SVN ingest (lines 296-311) routes contain nearly identical notification/subscription code. This is duplicated across both routes.
   - **Recommendation:** Extract into a reusable helper function.

2. **Number coercion without validation (ingest.ts line 81, 210).** `Number(req.params.id)` can return `NaN` for non-numeric IDs. While the DB query would return no results, it's better to validate earlier.
   - **Recommendation:** Use Zod params parsing consistently (as done in `projects.ts`).

3. **`getAll` pattern for commits (generate.ts line 402-409).** In incremental mode, `generate.ts` fetches all unprocessed valid commits into memory at once (with a `maxCommits` default of 50). For projects with many unprocessed commits, this could be memory-intensive.
   - **Recommendation:** Consider batching or streaming for large commit sets.

### Are error handling and edge cases properly addressed?

**Good overall:**

1. **GitHub API errors** — Handled with try/catch, returns 400 with error message (lines 121-126)
2. **SVN CLI errors** — Handled with try/catch, returns 520 for SVN failures (lines 231-236)
3. **Empty commit lists** — Handled in generate route (lines 413-427)
4. **Multer upload errors** — Handled with dedicated error middleware (lines 428-446)
5. **Not handled:** If `lastGitIngestedAt` is set but the GitHub API returns no new commits, the cursor is still updated to `new Date()` (line 195). This is correct behavior (prevents re-fetching), but the `new Date()` fallback when `newestCommitDate` is null means the cursor advances even when no commits are found, which is fine.

**Edge case concern:**
- **Git ingest cursor drift (ingest.ts line 195).** When `mode === "incremental"` but `newestCommitDate` is null (all commits were duplicates/skipped), the cursor is set to `new Date()`. This is correct because the GitHub API `since` parameter would not return those commits again (their dates are in the past). However, if the GitHub API pagination returns commits in non-chronological order, the `newestCommitDate` tracking could miss a newer commit that appears on a later page. The GitHub API returns commits in reverse-chronological order by default, so this is unlikely but worth noting.

## Round 3 — Integration & Completeness Review

### Does the feature integrate correctly with other parts of the system?

**Yes.** The cursor columns integrate properly:

1. **`projects` table → `ingest.ts`:** Both Git and SVN ingest routes read the cursor before ingestion and write it after successful ingestion.
2. **`commits` table → `generate.ts`:** The generate route reads `processedAt IS NULL` to find unprocessed commits in incremental mode, and writes `processedAt` after processing.
3. **`/ingest/status` endpoint (lines 324-341):** Exposes all three cursor values, including `pendingCommits` count based on `processedAt IS NULL`.

### Are there missing tests for this feature?

**Yes, this is a gap.** While the existing reports (0005_1.2.1 through 0009_1.2.5) have tested individual ingestion components, there are no specific integration tests for:
- Git incremental ingestion with `lastGitIngestedAt` cursor updates
- SVN incremental ingestion with `lastSvnRevision` cursor updates
- Generate incremental mode with `processedAt` filtering and updates
- The `/ingest/status` endpoint cursor reporting

### Are there performance concerns?

**Minor concerns:**

1. **Git pagination without rate-limit handling.** The Git ingest endpoint (lines 114-130) paginates through GitHub API results but doesn't handle GitHub rate limiting (403/429 responses). For repos with many commits, this could fail silently.
   - **Recommendation:** Add rate-limit detection and retry logic.

2. **SVN sequential diff fetching.** The SVN ingest route fetches diffs one revision at a time (line 262). For large revision ranges, this is slow.
   - **Recommendation:** Consider batching or parallelizing SVN diff fetches.

### Is the feature actually usable end-to-end?

**Yes.** The complete flow is:
1. `POST /projects/:id/ingest/git` with `mode: "incremental"` → fetches only new commits, updates `lastGitIngestedAt`
2. `POST /projects/:id/ingest/svn` with `mode: "incremental"` → fetches only new revisions, updates `lastSvnRevision`
3. `POST /projects/:id/generate` with `mode: "incremental"` → processes only `processedAt IS NULL` commits, sets `processedAt` after processing
4. `GET /projects/:id/ingest/status` → reports cursor positions and pending commit count

The `mode: "full"` default is respected in both Git and SVN ingest routes, and `mode: "incremental"` is correctly optional.

## Findings

### ✅ Strengths
1. All three cursor columns (`lastGitIngestedAt`, `lastSvnRevision`, `processedAt`) are correctly defined in the Drizzle schema
2. The `mode: "full" | "incremental"` parameter is consistently implemented across Git, SVN, and Generate routes
3. Cursor updates happen after successful ingestion (no premature advancement)
4. The `/ingest/status` endpoint provides visibility into cursor state and pending commits
5. The `generate.ts` route correctly uses `processedAt IS NULL` for incremental mode and sets `processedAt` after processing
6. Duplicate commit detection via `existingHashes` Set prevents re-insertion regardless of mode

### ⚠️ Warnings
1. **ADR-007 description mismatch:** ADR describes `lastSvnRevision` as "string" but it's implemented as `integer`. The code is correct; the ADR should be updated.
2. **Credentials in request body:** GitHub tokens and SVN credentials are accepted in request bodies, which is a security concern.
3. **No auth on ingest endpoints:** All ingest routes lack authentication middleware.
4. **Zod error leak:** SVN ingest route returns raw Zod error objects to clients.
5. **Duplicate notification code:** Git and SVN ingest routes have nearly identical notification logic.
6. **No tests for incremental mode:** No integration tests verify cursor-based incremental ingestion.

### 🔴 Risks
1. **Cursor update atomicity (ADR-007 identified risk):** The cursor is updated *after* commit inserts but not in a single transaction. If the process crashes between commit inserts and cursor update, the next incremental run could miss commits. The `existingHashes` Set mitigates this (duplicates are skipped), but it's a data integrity concern.
2. **GitHub rate limiting:** No rate-limit handling for paginated GitHub API calls.

### Recommendations
1. Update ADR-007 to correctly describe `lastSvnRevision` as `integer`
2. Add authentication middleware to ingest routes
3. Move credential handling from request bodies to environment variables or headers
4. Extract shared notification logic into a helper function
5. Add integration tests for incremental ingestion with cursor verification
6. Add rate-limit handling for GitHub API pagination
7. Consider wrapping commit inserts + cursor updates in a DB transaction for atomicity

---

## Overall Verdict

**⚠️ WARN**

The feature is functionally complete and correctly implemented per the design spec. All three cursor columns exist in the schema and are properly wired into the ingest/generate routes. The incremental mode works end-to-end. However, there are security concerns (credentials in request bodies, no auth on ingest endpoints), a schema description mismatch in the ADR, and missing tests for incremental mode. The cursor atomicity risk identified in ADR-007 is not mitigated by transactions.
