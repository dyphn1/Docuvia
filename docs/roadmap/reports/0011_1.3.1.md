## Round 1 — Architecture & Design Review

### What the Design Specifies (ADR-007)

ADR-007 describes a routing funnel with O(1) arbitration:

1. **Direct RAG** — O(1) lookup when query contains `#attach` or file extensions (`.ts`, `src/`)
2. **Graph RAG** — when query hits L1/L2 names in the database
3. **Hybrid / Vector LLM Arbitration** — fallback to LLM classification for vector_search, graph_traversal, direct_lookup, or hybrid

The 4 strategies are: Direct RAG, Graph RAG, Vector RAG, and Hybrid RAG.

### Implementation Assessment

The `intent-router.ts` file (634 lines) implements all 4 strategies:

- **`classifyIntent(query)`** (line 106): LLM-based classification using `gpt-4o-mini` with JSON mode. Returns strategy, entities (moduleName, commitHash, searchQuery), confidence, and reasoning. Includes a fallback to `vector_search` on any failure.
- **`vectorSearchHandler(query, projectId, limit, includePending)`** (line 165): Generates embedding, searches L2 and L3 nodes by cosine similarity, applies temporal decay. Falls back to SQL LIKE if embedding generation fails.
- **`graphTraversalHandler(moduleName, projectId)`** (line 327): Finds L2 node by name, traverses outbound and inbound `node_links`.
- **`directLookupHandler(commitHash, includePending)`** (line 424): Looks up commit by hash prefix, then finds associated L3 nodes.
- **`hybridSearch(query, classification, ...)`** (line 488): Runs vector search, extracts top-3 L2 names, runs graph traversal for each, merges and deduplicates.
- **`routeQuery(query, ...)`** (line 533): Top-level orchestrator implementing the 3-tier arbitration pipeline.

### Findings

1. **Design-implementation alignment is strong.** All 4 routing strategies from ADR-007 are implemented. The O(1) fast-path arbitration (direct filter → graph filter → LLM fallback) matches the design spec.

2. **Naming discrepancy:** ADR-007 mentions `target_refs` for Direct RAG, but the implementation uses `commitHash` lookup on `commitsTable` and `l3NodesTable`. This is functionally equivalent for the use case (finding knowledge by commit reference) but the terminology differs.

3. **Parallel search path exists but is not a design violation.** The `search.ts` route provides a separate `/search` endpoint with its own vector/Like search logic. This is a legacy/alternative path and doesn't contradict the design — the intent-router is positioned as the MCP/query path.

4. **Schema supports the feature.** `l3_nodes` has `validityStatus` (with `"pending"` default), `lastVerifiedAt`, and `embedding` columns. `l2_nodes` has `lastVerifiedAt` and `embedding`. These are required for the intent router's filtering and decay logic.

## Round 2 — Code Quality & Security Review

### Strengths

- **Input sanitization** (line 99-104): `sanitizeQuery` truncates to 2000 chars and strips control characters (`\x00-\x1F`, `\x7F`). This mitigates prompt injection.
- **LLM response validation** (line 129-153): Strategy is validated against a whitelist (`VALID_STRATEGIES` set). Confidence is clamped to [0, 1]. Entity types are checked.
- **Graceful degradation**: If LLM classification fails, falls back to `vector_search`. If embedding generation fails, falls back to SQL LIKE search.
- **Structured logging**: Classification results and query completion are logged via `logger.info`.
- **Defensive design**: Early returns for empty results, null checks throughout.

### Issues Found

1. **No unit tests for intent-router.ts.** There are zero test files for the intent router or embedding modules. The only test files in the project are `artifacts/vscode-client/src/tests/phase1.test.ts` and `artifacts/api-server/test/integration/mcp-list-projects.test.ts`. The intent classification logic, cosine similarity, temporal decay math, and hybrid merge/dedup logic are all untested. This is a significant gap for a core routing component.

2. **Code duplication between `intent-router.ts` and `search.ts`.** The vector search logic is implemented twice:
   - `intent-router.ts` `vectorSearchHandler()` (lines 165-321): Includes temporal decay, `includePending` filter, project filtering.
   - `search.ts` inline (lines 66-140): No temporal decay, no `includePending` filter, different result shape.
   
   This duplication means bug fixes or improvements to vector search need to be applied in two places. The `search.ts` route should ideally delegate to `intent-router.ts` or share a common search utility.

3. **Potential SQL LIKE wildcard injection in `graphTraversalHandler`.** Line 336: `like(l2NodesTable.name, \`%${moduleName}%\`)`. The `moduleName` comes from LLM-extracted entities. While Drizzle ORM uses parameterized queries (preventing SQL injection), a malicious `moduleName` containing SQL wildcards (`%`, `_`) could cause unexpectedly broad matches. For example, if the LLM extracts `moduleName = "%"`, it would match all L2 nodes. This is low-severity since the input comes from LLM output (not direct user input), but it's worth noting.

4. **No commit hash format validation in `directLookupHandler`.** Line 437: `like(commitsTable.hash, \`${commitHash}%\`)`. The `commitHash` is used directly without validating it looks like a hex string. The LLM prompt asks for "hex string 4-40 chars" but there's no programmatic validation. A malformed `commitHash` could match unintended rows.

5. **Hybrid search only uses top-3 L2 results for graph context** (line 501-504). If the vector search returns fewer than 3 L2 nodes, or if the top L2 results are not the most relevant for graph traversal, the hybrid search may miss important structural context. This is a design trade-off (performance vs. completeness) but could produce suboptimal results for complex queries.

6. **`hybridSearch` is not exported** (line 488: `async function hybridSearch` without `export`). It's only called internally from `routeQuery`. This is fine for encapsulation but means it can't be tested or reused independently.

## Round 3 — Integration & Completeness Review

### Integration Points

1. **`POST /mcp/query`** (mcp.ts line 326): The primary entry point for the intent router. Accepts `{ q, project_id, limit }` via Zod-validated body. Calls `routeQuery()` and returns the full `RouteQueryResult`. This is correctly implemented.

2. **`GET /mcp/search_knowledge`** (mcp.ts line 47): Does **NOT** use the intent router. Has its own inline vector/Like search logic with a different result shape (no `source` field, no temporal decay). This means the MCP search endpoint bypasses intent classification entirely.

3. **`POST /search`** (search.ts line 32): Does **NOT** use the intent router. Separate implementation with L1/L2/L3 search, no temporal decay, no intent classification.

4. **Frontend `query.tsx`** (line 65): Calls `/api/search` (not `/api/mcp/query`). The main UI query page does not use the intent router.

5. **Frontend `mcp.tsx`**: Provides a playground for MCP endpoints but does not include the `POST /mcp/query` endpoint — only the GET endpoints are listed.

6. **`POST /search/feedback`** (search.ts line 217): Correctly updates `lastVerifiedAt` for L2 and L3 nodes, supporting the temporal decay "refresh" mechanism described in ADR-007.

### Findings

1. **The intent router is underutilized.** It is only called by `POST /mcp/query`, which is not used by the frontend. The main search UI (`query.tsx`) and the MCP search endpoint (`GET /mcp/search_knowledge`) both use separate, non-intent-routed code paths. This means the 4-way classification is implemented but not integrated into the primary user-facing search flow.

2. **Temporal decay inconsistency.** Temporal decay is applied in `intent-router.ts` `vectorSearchHandler` (lines 188-199, 233-237) but NOT in `search.ts`. Users searching via the main UI will see different (non-decayed) scores than users querying via `POST /mcp/query`.

3. **`includePending` not supported in search.ts.** The intent router supports `includePending` for queries that want to include pending-validity nodes. The `search.ts` route has no such parameter, meaning the main UI can only ever see `valid` L3 nodes.

4. **No `POST /mcp/query` in the MCP playground UI.** The `mcp.tsx` page lists 5 GET endpoints but doesn't include the `POST /mcp/query` endpoint, which is the most sophisticated endpoint (the one that uses the intent router).

5. **No OpenAPI spec entry for `POST /mcp/query`.** The `openapi-3-0.yaml` only has a tag reference for `mcp` but no path definition for `POST /mcp/query`. This means the endpoint won't appear in generated API docs or client code.

6. **Feature completeness per design spec:**
   - ✅ 4-way classification (vector | graph | direct | hybrid)
   - ✅ LLM-based intent classification with JSON mode
   - ✅ O(1) fast-path for `#attach`/file extensions → direct_lookup
   - ✅ O(1) fast-path for L1/L2 name matches → graph_traversal
   - ✅ Fallback to LLM classification
   - ✅ Temporal decay in vector search
   - ✅ Feedback endpoint for refreshing `lastVerifiedAt`
   - ⚠️ Intent router not wired to primary UI search path
   - ⚠️ No OpenAPI spec for `POST /mcp/query`
   - ❌ No unit tests for intent classification or search logic

---

## Overall Verdict

**⚠️ WARN**

The 4-way LLM-based intent classification is **fully implemented** in `intent-router.ts` with all 4 strategies (vector, graph, direct, hybrid), O(1) fast-path arbitration, temporal decay, and graceful fallback. The code is well-structured, properly sanitized, and follows defensive design patterns.

However, there are significant concerns:

1. **The intent router is not integrated into the primary search paths.** The main UI (`query.tsx`) and the MCP search endpoint (`GET /mcp/search_knowledge`) bypass the intent router entirely, using duplicated inline search logic. The 4-way classification is only accessible via `POST /mcp/query`, which has no frontend integration.

2. **No unit tests** for the core routing logic — a critical gap for a component that arbitrates all query traffic.

3. **Code duplication** between `intent-router.ts` and `search.ts` for vector search logic, with inconsistent behavior (temporal decay in one but not the other).

4. **Missing OpenAPI spec** for the `POST /mcp/query` endpoint.

### Recommendations

1. Wire the frontend `query.tsx` page to use `POST /mcp/query` instead of `POST /search`, or refactor `search.ts` to delegate to the intent router.
2. Add unit tests for `classifyIntent`, `vectorSearchHandler`, `cosineSimilarity`, temporal decay math, and hybrid merge/dedup logic.
3. Add `POST /mcp/query` to the OpenAPI spec and the MCP playground UI.
4. Consolidate the duplicated vector search logic between `intent-router.ts` and `search.ts` into a shared utility.
5. Add input validation for `commitHash` (hex format, 4-40 chars) in `directLookupHandler`.
6. Consider escaping SQL LIKE wildcards in `moduleName` and `commitHash` before using them in `like()` clauses.
