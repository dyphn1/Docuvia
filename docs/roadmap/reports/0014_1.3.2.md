## Round 1 — Architecture & Design Review

### Design Spec (ADR-007)
ADR-007 describes "Vector RAG" as "Standard embedding similarity via PGVector (`embedding.ts`)" — one of the 4 routing strategies. The intent router should classify queries as `vector_search` and execute cosine similarity over stored embeddings. The design also specifies temporal decay (`Math.exp(-LAMBDA * daysSinceVerified)`) and validity status filtering.

### Implementation Status

**What exists:**
1. **`embedding.ts`** — Clean, well-structured module with three functions:
   - `generateEmbedding(text)` — Calls OpenAI `text-embedding-3-small` (1536 dims), returns `null` on failure.
   - `cosineSimilarity(a, b)` — Standard cosine similarity, handles zero-length and mismatched vectors.
   - `parseEmbedding(raw)` — Parses JSON-stored embedding strings back to `number[]`.

2. **`intent-router.ts` → `vectorSearchHandler()`** (lines 165–321):
   - Generates query embedding via `generateEmbedding()`.
   - If embedding succeeds: fetches all L2 nodes with non-null embeddings, computes cosine similarity, applies temporal decay, sorts, and slices. Does the same for L3 nodes.
   - If embedding fails (OpenAI unavailable): graceful fallback to SQL LIKE search on L2/L3 text fields.
   - Supports `projectId` filtering for L2 (but not L3 — see Finding 1).
   - Supports `includePending` parameter for L3 validity status filtering.

3. **`search.ts` → `POST /search`** (lines 32–215):
   - Standalone search route that also performs vector search.
   - L1 tags always use SQL LIKE (no embedding column — correct per schema).
   - L2 and L3 semantic search with cosine similarity when embedding is available.
   - Fallback to SQL LIKE when embedding generation fails.

4. **`mcp.ts` → `GET /mcp/search_knowledge`** (lines 47–198):
   - MCP search endpoint with its own vector search implementation.
   - Supports `include_pending` query parameter for L3 validity filtering.
   - Does NOT apply temporal decay (see Finding 8).

5. **`generate.ts`** — The generate pipeline calls `generateEmbedding()` for L2/L3 nodes during creation. The `detectCrossProjectLinks()` function (line 231) generates embeddings for new L2 nodes and checks cross-project similarity. The `runSieveModel()` function (line 383) uses embeddings for L2 node classification.

6. **Schema** — Both `l2_nodes.embedding` and `l3_nodes.embedding` are defined as `text("embedding")` — stored as JSON text.

### Findings

**F1. Schema mismatch: `text` vs `JSONB` for embedding column.**
- ADR-007 says "cosine similarity over JSONB embeddings."
- Both `l2_nodes.ts` (line 19) and `l3_nodes.ts` (line 31) define embedding as `text("embedding")`, not `jsonb("embedding")`.
- The `parseEmbedding()` function treats the stored value as a JSON string (calls `JSON.parse()`), which works for both `text` and `jsonb` PostgreSQL types.
- **Impact:** Low. The code works correctly with `text` type. However, using `jsonb` would enable PostgreSQL-native JSON operations and indexing. The design doc says JSONB but the implementation uses text.

**F2. `search.ts` L3 semantic search does NOT filter by `validityStatus`.**
- In `search.ts` line 108: `db.select().from(l3NodesTable).where(isNotNull(l3NodesTable.embedding))` — no validity status filter.
- In `intent-router.ts` lines 224–227: The vector search handler correctly applies `l3ValidityCondition` (valid-only or valid+pending).
- In `mcp.ts` lines 109–112: The MCP search correctly applies `l3ValidityCondition`.
- **Impact:** Medium. The standalone `/search` endpoint will return orphaned or pending L3 nodes in semantic search results, which contradicts the design intent (ADR-011: MCP query default filter is `status = valid` only).

**F3. `search.ts` L3 semantic search does NOT support `projectId` filtering.**
- The `search.ts` route fetches ALL L3 nodes with embeddings across all projects, then only filters by project during the L2 lookup phase (lines 120–122).
- **Impact:** Low-Medium. Cross-project semantic search may be intentional, but it's inconsistent with the intent-router's `vectorSearchHandler` which doesn't filter L3 by projectId either.

**F4. No database-level vector indexing.**
- Embeddings are stored as `text` and loaded entirely into memory for in-process cosine similarity computation.
- There is no PostgreSQL `pgvector` extension usage, no vector column type, and no ANN (Approximate Nearest Neighbor) index.
- **Impact:** Low for small datasets, but will not scale. All embeddings must be loaded into memory and compared one-by-one (O(n) per query). This is acceptable for the current stage but will need pgvector for production scale.

**F5. `vectorSearchHandler` in intent-router does not filter L3 by `projectId`.**
- Line 224–227 fetches all L3 nodes with embeddings regardless of project.
- **Impact:** Low. The `projectId` parameter is accepted but only applied to L2 queries.

**F6. Three separate vector search implementations with inconsistent behavior.**
- `intent-router.ts` → `vectorSearchHandler()` — has temporal decay, validity filtering, no project filter on L3.
- `search.ts` → `POST /search` — no temporal decay, no validity filtering, no project filter on L3.
- `mcp.ts` → `GET /mcp/search_knowledge` — no temporal decay, has validity filtering, no project filter on L3.
- **Impact:** High. Three separate implementations of the same feature with different behavior. Any fix (e.g., adding validity filter) must be applied in three places.

## Round 2 — Code Quality & Security Review

### Code Quality

**Strengths:**
- `embedding.ts` is clean, well-documented, and follows defensive design (null checks, try/catch, graceful degradation).
- `cosineSimilarity()` correctly handles edge cases (zero vectors, mismatched lengths).
- `parseEmbedding()` safely handles null/invalid input.
- The fallback to SQL LIKE when OpenAI is unavailable is a good graceful degradation pattern.
- Temporal decay is correctly applied in `vectorSearchHandler` using exponential decay: `Math.exp(-LAMBDA * daysSinceVerified)`.
- The `generateEmbedding` function truncates input at 8192 chars to stay within OpenAI limits.

**Issues:**

**F7. N+1 query pattern in all three search implementations.**
- In `intent-router.ts` `vectorSearchHandler()`: For each L2 node in the result set, a separate `SELECT` query is made to fetch the project name (lines 206–209). This is an N+1 query.
- In `search.ts` (lines 88–93, 120–121): Each L2/L3 node triggers separate project/L2 lookups.
- In `mcp.ts` (lines 91–95, 120): Same N+1 pattern for project lookups.
- **Impact:** Medium. For a result set of 10 nodes, this means 10 additional round-trips to the database. Should be batched or joined.

**F8. No input sanitization on the search route.**
- `search.ts` line 33: `SearchSchema.parse(req.body)` validates the query is a string with min length 1, but the query is then used directly in SQL LIKE patterns (`%${query}%`) at line 41.
- While Drizzle's parameterized queries prevent SQL injection, the LIKE pattern could match unintended results if users include `%` or `_` characters.
- **Impact:** Low. Not a security vulnerability (Drizzle parameterizes), but could cause unexpected search behavior.

**F9. No unit tests for `embedding.ts` or any vector search function.**
- There are zero `*.unit.test.ts` files in the entire repository (`find` confirmed none exist).
- The `cosineSimilarity()` and `parseEmbedding()` functions are pure and easily testable.
- **Impact:** Medium-High. The cosine similarity function is a critical mathematical operation that should have unit tests with known vector pairs. Lack of tests increases regression risk.

**F10. `generateEmbedding` truncates at 8192 chars but doesn't warn.**
- `embedding.ts` line 16: `input: text.slice(0, 8192)` — silently truncates long texts.
- **Impact:** Low. Acceptable for the current stage, but should log a warning when truncation occurs.

**F11. `mcp.ts` `search_knowledge` duplicates vector search logic instead of calling `vectorSearchHandler()`.**
- The MCP endpoint at lines 70–195 reimplements the entire vector search flow (embedding generation, cosine similarity, sorting, fallback) that already exists in `intent-router.ts`.
- **Impact:** Medium. Code duplication means fixes and improvements must be applied in multiple places.

### Security

**F12. No authentication on the `/search` endpoint.**
- `search.ts` has no auth middleware. The intent-router is called internally, but the standalone `/search` POST endpoint appears to be unauthenticated (depends on global middleware in `index.ts`).
- **Impact:** Needs verification at the app middleware level. If no global auth is applied, this is a security gap.

**F13. `mcp/search_knowledge` uses GET with query parameters for search.**
- Line 47–50: The search query is passed as a URL query parameter (`req.query.query`), which may be logged in server access logs.
- **Impact:** Low. Search queries could contain sensitive information. POST with body would be more appropriate.

## Round 3 — Integration & Completeness Review

### Integration

**F14. `generateEmbedding` is called during node creation in `generate.ts`.**
- The generate pipeline creates embeddings for L2/L3 nodes. This is confirmed by the `detectCrossProjectLinks()` function (line 231) which generates embeddings for new L2 nodes.
- The `runSieveModel()` function (line 383) also generates embeddings for L3 node classification.
- **Impact:** Low. The integration exists and works correctly.

**F15. Temporal decay is applied in `intent-router.ts` but NOT in `search.ts` or `mcp.ts`.**
- `intent-router.ts` lines 188–200: Applies exponential decay based on `lastVerifiedAt`.
- `search.ts` lines 78–85: Raw cosine similarity score, no decay applied.
- `mcp.ts` lines 82–85: Raw cosine similarity score, no decay applied.
- **Impact:** Medium. The standalone search and MCP search endpoints don't implement temporal decay, which is a core feature per ADR-007.

**F16. Cross-project link detection uses vector similarity correctly.**
- `generate.ts` `detectCrossProjectLinks()` (lines 231–303): Generates embedding for new L2 node, compares against all L2 nodes from other projects using `cosineSimilarity()`, and creates review tasks when similarity ≥ 0.85.
- This is a good use of vector search for knowledge graph maintenance.
- **Impact:** Positive finding. Well-implemented feature.

### Completeness

**F17. Feature is functionally complete for the design spec.**
The core vector search feature is implemented:
- ✅ Embedding generation via OpenAI `text-embedding-3-small`
- ✅ Cosine similarity computation
- ✅ JSON text parsing of stored embeddings
- ✅ Graceful fallback to SQL LIKE when OpenAI is unavailable
- ✅ Temporal decay in intent-router
- ✅ L2 and L3 semantic search
- ✅ Project filtering (L2 only)
- ✅ Validity status filtering (intent-router and MCP, but not search.ts)
- ✅ Cross-project link detection via vector similarity
- ✅ Sieve model uses embeddings for L2 classification

**Missing:**
- ❌ No database-level vector indexing (pgvector)
- ❌ No unit tests for `embedding.ts` or vector search functions
- ❌ No validity status filtering in standalone search route
- ❌ No temporal decay in standalone search route or MCP search
- ❌ No batch project name lookup (N+1 queries in 3 places)
- ❌ Three duplicated vector search implementations

## Recommendations

1. **Consolidate the three vector search implementations** — Extract the vector search logic into a single shared function in `embedding.ts` or a new `vector-search.ts` module. Have `search.ts`, `mcp.ts`, and `intent-router.ts` all call this shared function. This is the highest-priority fix.

2. **Add `validityStatus` filter to `search.ts`** — Apply the same `l3ValidityCondition` pattern from the intent-router and MCP routes.

3. **Add temporal decay to `search.ts` and `mcp.ts`** — Apply exponential decay consistently across all search paths.

4. **Add unit tests for `embedding.ts`** — Test `cosineSimilarity` with known vectors (orthogonal, identical, opposite), `parseEmbedding` with edge cases (null, invalid JSON, empty array), and `generateEmbedding` with mocked OpenAI responses.

5. **Fix N+1 queries** — Batch project name lookups using `IN` clauses or SQL JOINs instead of per-row queries.

6. **Consider adding `pgvector`** — For production scale, migrate the `text` column to `vector(1536)` and add an IVFFlat or HNSW index.

7. **Sanitize LIKE wildcards** — Escape `%` and `_` in user queries before building LIKE patterns.

8. **Add unit tests for the entire codebase** — The repository has zero `*.unit.test.ts` files. This is a significant gap.

## Overall Verdict

**⚠️ WARN**

The vector search feature is functionally implemented and works correctly for the core use case. The `embedding.ts` module is clean and well-structured. The intent-router's `vectorSearchHandler` is the most complete implementation (with temporal decay and validity filtering). The cross-project link detection is a well-designed use of vector similarity.

However, there are three separate implementations of vector search (`intent-router.ts`, `search.ts`, `mcp.ts`) with inconsistent behavior — the standalone `search.ts` route lacks both validity status filtering and temporal decay, and the MCP route lacks temporal decay. There are no unit tests anywhere in the repository, the N+1 query pattern will cause performance issues at scale, and the embedding column uses `text` instead of `jsonb` as specified in the design. These issues should be addressed to improve consistency, testability, and maintainability.
