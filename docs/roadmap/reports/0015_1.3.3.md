## Round 1 — Architecture & Design Review

### What the Design Specifies

ADR-007 describes Graph RAG as: "Traverses `node_links` to find structural dependencies (Neighbor Infection)." The routing funnel shows that queries hitting L1/L2 names in the database should be routed to Graph RAG. The design also specifies:

1. **One-hop traversal** via `node_links` (confirmed by 03-context-and-scope.md: "One-hop impact analysis via `node_links`")
2. **Bidirectional traversal** — both outbound (dependencies) and inbound (dependents)
3. **O(1) fast-path** — queries matching known architectural terms skip LLM classification
4. **Hybrid merge** — graph results combined with vector results for hybrid queries

### What the Implementation Provides

The `graphTraversalHandler()` function (`intent-router.ts:327-418`) implements:
1. L2 node lookup by name pattern (line 333-336)
2. Returns the matched node itself with score 1.0 (lines 347-357)
3. Outbound traversal: `node_links WHERE sourceNodeId = node.id` → returns targets as dependencies (lines 360-386)
4. Inbound traversal: `node_links WHERE targetNodeId = node.id` → returns sources as dependents (lines 389-415)

The `routeQuery()` orchestrator (`intent-router.ts:533-634`) correctly:
- Fast-path intercepts queries containing L1/L2 names (lines 554-576)
- Dispatches to `graphTraversalHandler` for `graph_traversal` strategy (lines 595-598)
- Hybrid search combines vector top-3 L2 results with graph traversal (lines 488-527)

### Gaps Identified

**Gap 1: `/projects/:id/graph` endpoint missing edges**
The OpenAPI spec defines `GET /projects/:id/graph` as "Get full L1/L2/L3 graph for a project." The implementation (`projects.ts:163-188`) returns L2 and L3 nodes but does **not** include `node_links` edges. A graph without edges is incomplete for visualization or dependency analysis.

**Gap 2: ER diagram vs. schema contradiction for L3 links**
The ER diagram in `08-crosscutting-concepts.md:71` shows `l3_nodes ||--o{ node_links : "source/target"`, suggesting L3 nodes can be link endpoints. However, the `node_links` schema (`node_links.ts:8-13`) only has FK references to `l2NodesTable.id`. The glossary (12-glossary.md) contradicts the ER diagram: "Node Links model module-level structural dependencies; L3 decisions are scoped within their parent L2 node and **are not directly linked**." The ER diagram is outdated/incorrect.

**Gap 3: Multi-hop traversal not implemented (known risk R-02)**
The current implementation only traverses one hop. For deep dependency chains (A→B→C), querying A will not reveal C. This is documented as a known risk in `11-risks-and-debt.md`.

**Gap 4: Cross-project link activation not wired (known risk R-03)**
Review resolution does not insert `node_links` rows for cross-project connections. The review_tasks route doesn't create node_links entries upon approval.

## Round 2 — Code Quality & Security Review

### Strengths

- **SQL injection safe**: All queries use Drizzle ORM parameterized queries. The `like()` calls use bound parameters, not string concatenation. ✅
- **Clean separation of concerns**: `graphTraversalHandler`, `vectorSearchHandler`, `directLookupHandler`, and `hybridSearch` are separate functions with clear responsibilities. ✅
- **Consistent result shape**: All handlers return `AgenticSearchResult[]` with uniform fields. ✅
- **Defensive null checks**: Both inbound and outbound traversal check for missing target/source nodes before accessing properties. ✅

### Issues

**Issue 1: SQL LIKE wildcard injection in `graphTraversalHandler` (Medium)**
`intent-router.ts:336`: `like(l2NodesTable.name, \`%${moduleName}%\`)` — If `moduleName` contains SQL LIKE wildcards (`%` or `_`), the query will match unintended nodes. For example, a moduleName of `%` would match all L2 nodes. The `sanitizeQuery()` function (line 99-104) exists for LLM queries but is **not applied** to graph traversal inputs. Similarly, `mcp.ts:210` and `mcp.ts:258` have the same issue in `/mcp/get_dependencies` and `/mcp/impact_analysis`.

**Issue 2: N+1 query pattern in graph traversal (Medium)**
`intent-router.ts:365-386` (outbound) and `intent-links.ts:394-415` (inbound): For each link, a separate SELECT query fetches the target/source node. A node with 50 links executes 100+ queries. This should be batched: fetch all target/source IDs, then SELECT WHERE id IN (...).

**Issue 3: Significant code duplication between `mcp.ts` and `intent-router.ts` (Medium)**
- `mcp.ts:47-198` (`/mcp/search_knowledge`) duplicates the vector search logic from `vectorSearchHandler()` (~150 lines)
- `mcp.ts:201-247` (`/mcp/get_dependencies`) duplicates the graph traversal logic from `graphTraversalHandler()`
- `mcp.ts:249-290` (`/mcp/impact_analysis`) duplicates the inbound traversal logic
- Changes to search/traversal logic must be synchronized across multiple files, creating maintenance risk.

**Issue 4: No input validation on `moduleName` parameter (Low-Medium)**
The `graphTraversalHandler` accepts `moduleName: string` with no length limit, character validation, or sanitization. The MCP endpoints (`mcp.ts:202`, `mcp.ts:250`) use `String(req.query.module ?? "")` with no validation beyond checking for empty string.

**Issue 5: `mcp.ts` `/mcp/search_knowledge` does not apply validity filter (Low)**
`mcp.ts:108-112`: The L3 semantic search in the MCP endpoint does not filter by `validityStatus`, returning all L3 nodes including `pending` and `orphaned`. Compare with `intent-router.ts:224-227` which correctly applies the `l3ValidityCondition` filter.

## Round 3 — Integration & Completeness Review

### Integration Points

1. **`routeQuery` → `graphTraversalHandler`**: ✅ Correctly integrated. The orchestrator dispatches to graph traversal when strategy is `graph_traversal`.
2. **O(1) fast-path → graph**: ✅ The fast-path in `routeQuery` (lines 554-576) correctly identifies queries containing L1/L2 names and routes to graph traversal without LLM overhead.
3. **Hybrid search → graph**: ✅ `hybridSearch()` (lines 488-527) extracts top-3 L2 names from vector results and calls `graphTraversalHandler` for each, then merges and deduplicates.
4. **MCP `/mcp/query` → `routeQuery`**: ✅ The POST endpoint delegates to `routeQuery`, so it benefits from the full routing pipeline.
5. **MCP `/mcp/get_dependencies` and `/mcp/impact_analysis`**: ⚠️ These are standalone endpoints that duplicate logic instead of reusing `graphTraversalHandler`. They work correctly but create a maintenance burden.

### Test Coverage

**No dedicated tests exist for graph traversal.** The only MCP test file is `mcp-list-projects.test.ts`. There are no unit or integration tests for:
- `graphTraversalHandler()` directly
- The O(1) graph fast-path in `routeQuery()`
- The `/mcp/get_dependencies` endpoint
- The `/mcp/impact_analysis` endpoint
- The `/projects/:id/graph` endpoint
- The `/l2-nodes/:id/links` CRUD endpoints

### Performance Concerns

1. **N+1 queries** (detailed in Round 2, Issue 2): Each link traversal issues individual SELECT queries.
2. **No pagination**: `graphTraversalHandler` returns all linked nodes with no limit parameter. A highly-connected L2 node could return hundreds of results.
3. **Fast-path loads all L1/L2 names**: `routeQuery` lines 555-561 loads ALL l1_tags and ALL l2_nodes into memory on every query that doesn't match the `#attach` fast-path. This is O(N) in the number of tags/nodes, not O(1) as the design claims.

### End-to-End Usability

The graph traversal feature is **partially usable**:
- ✅ Via `POST /mcp/query` with a query matching an L2 module name
- ✅ Via `GET /mcp/get_dependencies?module=<name>`
- ✅ Via `GET /mcp/impact_analysis?module=<name>`
- ✅ Via `POST /l2-nodes/:id/links` (create links) and `GET /l2-nodes/:id/links` (read links)
- ❌ Via `GET /projects/:id/graph` — returns nodes but no edges, making it unsuitable for graph visualization
- ❌ Multi-hop analysis (A→B→C transitive dependencies) — not implemented
- ❌ Cross-project link creation — not wired to review resolution

## Recommendations

1. **Sanitize LIKE inputs**: Add a `sanitizeLikeInput()` function that escapes `%` and `_` wildcards, and apply it to all user-supplied values in `like()` clauses.
2. **Batch link queries**: Replace N+1 queries with `WHERE id IN (...)` batch queries in `graphTraversalHandler`.
3. **Deduplicate MCP logic**: Refactor `mcp.ts` to reuse `graphTraversalHandler` and `vectorSearchHandler` instead of duplicating logic.
4. **Fix `/projects/:id/graph`**: Include `node_links` edges in the response to match the OpenAPI spec.
5. **Add tests**: Write unit tests for `graphTraversalHandler` and integration tests for the MCP dependency/impact endpoints.
6. **Add pagination**: Add a `limit` parameter to `graphTraversalHandler` to prevent unbounded result sets.
7. **Fix L3 validity filter**: Apply `validityStatus` filter in `mcp.ts:/mcp/search_knowledge` for L3 nodes.

---

## Overall Verdict

**⚠️ WARN** — The core graph traversal via `node_links` is implemented and functional. The `graphTraversalHandler` correctly performs bidirectional one-hop traversal, and the intent router correctly dispatches graph queries. However, there are meaningful gaps: SQL LIKE wildcard injection risk, N+1 query performance issues, significant code duplication, missing edges in the project graph endpoint, no test coverage, and two known limitations (multi-hop and cross-project links) that reduce the feature's completeness. The feature works for basic use cases but needs hardening before production use.
