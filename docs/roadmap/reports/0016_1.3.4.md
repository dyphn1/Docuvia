## Round 1 — Architecture & Design Review

### What the Design Specifies

The design spec (`06-runtime-scenarios.md`, Section 6.3 "Agentic RAG Query") defines the direct branch of the intent router as:

```
else direct
    API->>DB: Full-text search on l3_nodes.content
    DB-->>API: Direct match results
```

The intent classification system prompt (`intent-router.ts:68`) defines `direct_lookup` as: "The user is looking for a specific commit hash or decision record by exact identifier."

The `RoutingStrategy` enum in the OpenAPI spec (`openapi.yaml:2394`) includes `direct_lookup` as one of four valid strategies.

The design presents `direct_lookup` as an O(1) fast-path strategy, distinct from vector search (semantic similarity) and graph traversal (structural relationships).

### What the Implementation Provides

**`directLookupHandler()` (intent-router.ts:424-482):**
This function takes a `commitHash` string and:
1. Queries `commitsTable` with `LIKE commitHash%` to find a commit by hash prefix (line 434-437)
2. Queries `l3NodesTable` with `LIKE commitHash%` on the `commitHash` column to find L3 nodes linked to that commit (line 457-465)
3. Returns results with hardcoded score 1.0

**Full-text search on `l3_nodes.content` DOES exist, but NOT in the direct_lookup handler:**
- `search.ts:176-208` implements SQL LIKE search on `l3_nodes.title` and `l3_nodes.content` (in the embedding fallback branch)
- `mcp.ts:169-194` duplicates the same SQL LIKE search on `l3_nodes.title` and `l3_nodes.content`

**Fast-path arbitration (intent-router.ts:543-551):**
The `routeQuery()` fast-path triggers `direct_lookup` strategy when the query contains `#attach` or matches `/src\/|\.ts|\.md/i`. In this case, the raw query string (which is a natural language query or file path) is passed as the `commitHash` to `directLookupHandler()`.

### Gaps Identified

**Gap 1 (Critical): `directLookupHandler` does not perform full-text search on `l3_nodes.content`**
The design spec explicitly says the direct strategy should do "Full-text search on l3_nodes.content." The implementation searches by `commitHash` only. These are fundamentally different operations:
- **Design**: Full-text content search — any natural language query matches against L3 node text
- **Implementation**: Commit hash prefix lookup — only works with hex hash strings

When the LLM classifies a query as `direct_lookup` and the user asks something like "how does authentication work?", the `classifyIntent()` function would need to produce a valid `commitHash` entity for `directLookupHandler` to work. But the prompt (line 73) defines `commitHash` as "hex string 4-40 chars" — a natural language query won't match.

**Gap 2 (Critical): Fast-path `direct_lookup` passes raw query as commitHash**
At `intent-router.ts:600-602`, when the fast-path triggers `direct_lookup`, the code does:
```
const commitHash = classification.entities.commitHash ?? query;
results = await directLookupHandler(commitHash, includePending);
```
The fast-path (line 544-551) creates a classification with `entities: { searchQuery: query }` — no `commitHash` entity. So `classification.entities.commitHash` is always `undefined`, and the raw query string (e.g., `"src/auth.ts"` or a natural language query) is passed as `commitHash`. This will silently return zero results since no commit hash matches `"src/auth.ts"`.

**Gap 3 (Moderate): Intent classification prompt does not align with handler capability**
The `direct_lookup` prompt description says "looking for a specific commit hash or decision record by exact identifier." But the handler only searches by commit hash — it has no ability to search by "decision record" identifier (e.g., L3 node ID or title). If the LLM extracts a moduleName or searchQuery instead of a commitHash, the handler ignores them entirely.

**Gap 4 (Moderate): The actual full-text search is disconnected from the intent router**
The SQL LIKE-based full-text search on `l3_nodes.content` exists in `search.ts` (line 176-208) and `mcp.ts` (line 169-194), but these are in the embedding fallback branch and are never invoked when the intent router classifies a query as `direct_lookup`. The intent router's `directLookupHandler` does not call or reuse this full-text search logic.

## Round 2 — Code Quality & Security Review

### Strengths

- **Clean handler separation**: `directLookupHandler` is a standalone, exported function with clear input/output types. ✅
- **SQL injection safe (commit hash)**: The commit hash is passed through Drizzle ORM's parameterized `like()` query, preventing SQL injection. ✅
- **`includePending` support**: `directLookupHandler` correctly applies the `validityStatus` filter (lines 430-432), consistent with `vectorSearchHandler`. ✅

### Issues

**Issue 1: SQL LIKE wildcard injection in commit hash (Medium)**
`intent-router.ts:437`: `like(commitsTable.hash, \`${commitHash}%\`)` — If `commitHash` contains SQL LIKE wildcards (`%` or `_`), the prefix search will match unintended commits. For example, a commitHash of `%` would match all commits. Similarly, `intent-router.ts:462`: `like(l3NodesTable.commitHash, \`${commitHash}%]\`)` has the same vulnerability. Since the fast-path can pass arbitrary user queries as `commitHash`, this is exploitable.

**Issue 2: No input validation on commitHash (Medium)**
`directLookupHandler` accepts `commitHash: string` with no length limits, character validation, or sanitization. An empty string would match all commits with `LIKE '%'`. The function does not validate that the input looks like a commit hash (hex characters, 4-40 chars).

**Issue 3: Results always get score 1.0 regardless of relevance (Low)**
All results from `directLookupHandler` get a hardcoded `score: 1.0` (lines 452, 476). This means a partial commit hash match that returns 50 unrelated L3 nodes all get the same score as an exact match. When merged into hybrid results, this biases the ranking.

**Issue 4: L3 node projectId is always set to null (Low)**
`intent-router.ts:474`: Direct lookup L3 results set `projectId: null` and `projectName: null`. This is inconsistent with `vectorSearchHandler` (line 249) and `search.ts` (line 203) which resolve the project via the L2 parent node. Direct lookup L3 nodes do have an `l2NodeId` FK, so the project could be resolved.

**Issue 5: Significant code duplication with `mcp.ts` and `search.ts` (Low-Medium)**
The `mcp.ts:292-314` `get_decision_record` endpoint duplicates the commit hash lookup and L3 node retrieval logic from `directLookupHandler`. As noted in the 1.3.3 report, this creates a maintenance burden.

## Round 3 — Integration & Completeness Review

### Integration Points

1. **`routeQuery` → `directLookupHandler`**: ⚠️ Integrated but functionally broken for natural language queries. The handler only works with commit hash strings, but the router may pass arbitrary text when the fast-path triggers.
2. **LLM classification → `direct_lookup`**: ⚠️ The LLM can classify queries as `direct_lookup` and may or may not provide a `commitHash` entity. If the user asks "show me the decision about JWT tokens", the LLM may return `searchQuery: "JWT tokens"` with `commitHash: null`, causing the handler to silently search for a commit named "JWT tokens" and return nothing.
3. **Full-text content search**: ❌ Exists in `search.ts` and `mcp.ts`, but is not wired to the intent router's `direct_lookup` strategy at all.
4. **`POST /mcp/query` → `routeQuery`**: ✅ Correctly delegates to the full routing pipeline, including `direct_lookup`.

### Test Coverage

**No tests exist for direct lookup.** The only MCP test file is `mcp-list-projects.test.ts`. There are no unit or integration tests for:
- `directLookupHandler()` directly
- The `direct_lookup` strategy in `routeQuery()`
- The `#attach` fast-path → `direct_lookup` dispatch
- The `GET /mcp/get_decision_record` endpoint
- Edge cases: empty commitHash, non-hex inputs, non-existent hashes, wildcard characters

### Performance Concerns

1. **LIKE with leading wildcard on commitsTable**: `LIKE '${commitHash}%'` can use a B-tree index on the hash column (trailing wildcard), so this is acceptable for commit lookup.
2. **No index on l3_nodes.commitHash assumed**: `LIKE '${commitHash}%'` on `commitHash` is also index-friendly if an index exists, but this is a text column that may not have an index.

### End-to-End Usability

The direct search feature is **not usable** as designed:
- ❌ As a full-text content search: **Not implemented**. A query like "find decisions about error handling" classified as `direct_lookup` will fail to return results.
- ❌ Via `POST /mcp/query` with a commit hash: **Works only if the LLM correctly extracts a commit hash**. For a raw commit hash like `abc1234`, the LLM should classify it as `direct_lookup` with `commitHash: "abc1234"`, and this path works. But this is a narrow, fragile success case.
- ❌ Via the `#attach` fast-path: **Broken**. The fast-path passes the raw query as `commitHash`, which will match nothing in the commits table.
- ✅ The full-text LIKE search on `l3_nodes.content` **does work** via `POST /search` and `GET /mcp/search_knowledge`, but these are not routed through the intent router and don't use the `direct_lookup` strategy.

## Recommendations

1. **Implement full-text search in `directLookupHandler`**: Add SQL LIKE search on `l3_nodes.content` and `l3_nodes.title` (matching what `search.ts` already does in its fallback branch). Accept a generic search string, not just a commit hash. This aligns the implementation with the design spec.
2. **Fix the fast-path `direct_lookup` dispatch**: When the `#attach` fast-path triggers `direct_lookup`, it should pass `searchQuery` (not the raw query) as the search term, and only fall back to the raw query if no `searchQuery` entity was extracted. Better yet, the fast-path should set a proper `commitHash` entity only when the query actually contains a hex string matching the commit hash pattern.
3. **Sanitize LIKE inputs**: Add a `sanitizeLikeInput()` function that escapes `%` and `_` wildcards, and apply it to all user-supplied values in `like()` clauses. Reuse it across `directLookupHandler`, `graphTraversalHandler`, `search.ts`, and `mcp.ts`.
4. **Validate commitHash**: When the handler receives a `commitHash`, validate it matches `[0-9a-fA-F]{4,40}` before querying. Return empty results for invalid input rather than silently querying with garbage.
5. **Wire full-text search to the intent router**: Extract the SQL LIKE search logic from `search.ts` into a reusable function (e.g., `fullTextSearchHandler()`) and call it from both the `directLookupHandler` and the standby `/search` route.
6. **Reconsider the `direct_lookup` strategy definition**: Either rename it to `commit_hash_lookup` to be accurate, or expand it to include full-text content search per the design spec. Update the intent classification prompt accordingly.
7. **Add tests**: Write unit tests for `directLookupHandler` covering: valid commit hash, invalid input, empty string, wildcard characters, and full-text content search (once implemented).
8. **Resolve projectId for L3 results**: In `directLookupHandler`, resolve `projectId` via the L2 parent node, consistent with other handlers.

---

## Overall Verdict

**⚠️ WARN** — The `direct_lookup` strategy is partially implemented but does not match the design specification. The design calls for "full-text search on l3_nodes.content" as the direct search strategy. The implementation only performs commit hash prefix lookup, which is a fundamentally different operation. The full-text content search on `l3_nodes.content` does exist in the codebase (`search.ts` fallback branch and `mcp.ts`) but is entirely disconnected from the intent router's `direct_lookup` strategy. The fast-path arbitration that dispatches to `direct_lookup` is also broken — it passes raw query text as a commit hash. As a result, any query classified as `direct_lookup` (either by the LLM or the fast-path) will silently return zero results for natural language inputs. The feature needs a proper reimplementation of `directLookupHandler` (or a rename to `commitHashHandler` plus a new `fullTextSearchHandler`) to align with the design spec and deliver meaningful functionality.
