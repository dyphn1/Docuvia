## Round 1 — Architecture & Design Review

### Design Document Analysis

ADR-007 describes the hybrid strategy as: *"Intersection of graph constraints and vector similarities."* The arc42 runtime scenario (§6.3) says: *"Run vector + graph; merge and re-rank results."*

### Implementation Analysis

The `hybridSearch()` function (intent-router.ts, lines 488–527) implements a **pipeline approach** rather than a true intersection:

1. **Step 1 (line 498):** Runs `vectorSearchHandler()` to get vector results.
2. **Step 2 (lines 501–504):** Extracts the top-3 L2 node names from vector results.
3. **Step 3 (lines 507–509):** Runs `graphTraversalHandler()` for each of those L2 names in parallel.
4. **Step 4 (lines 512–522):** Merges vector + graph results, deduplicating by `(nodeLayer, id)`.
5. **Step 5 (lines 524–526):** Re-ranks by existing `score` field and returns top `limit`.

### Findings

1. **Design-implementation mismatch — "intersection" vs. "union":** ADR-007 describes hybrid as an "intersection of graph constraints and vector similarities." The implementation is actually a **union with deduplication** — it takes all vector results and all graph results, removes duplicates, and re-ranks. A true intersection would only return nodes that appear in BOTH result sets. The current approach is more accurately described as a "cascade" or "enriched vector search" — vector results seed graph traversals, and the combined pool is returned.

2. **Top-3 L2 seed limitation (line 503):** The hybrid search only extracts the top-3 L2 node names from vector results to seed graph traversal. If the vector search returns fewer than 3 L2 nodes (e.g., mostly L3 results), the graph traversal phase will be underutilized. This is a reasonable heuristic but is not documented in the design spec.

3. **No score boosting for nodes appearing in both sources:** A true hybrid re-rank would boost nodes that appear in BOTH vector and graph results (since they are validated by two independent signals). The current implementation simply deduplicates and uses the original score from whichever result was seen first. This means a node found by both vector and graph search gets no advantage over a node found by only one.

4. **Frontend does NOT expose hybrid search:** The kg-engine Query page (`query.tsx`, line 65) calls `POST /api/search`, which is the standalone search route (`search.ts`). This route does NOT perform intent classification or hybrid routing — it does a flat semantic/Like search across L1/L2/L3. The hybrid strategy is only accessible via `POST /mcp/query` (the MCP endpoint). This means the hybrid search feature is not usable from the web UI.

5. **No OpenAPI spec coverage:** The `openapi-3-0.yaml` file has empty `paths: {}` and `components: {}`. The main `openapi.yaml` was not found to contain `/mcp/query` or hybrid-specific documentation. The API contract for hybrid search is not formally specified.

## Round 2 — Code Quality & Security Review

### Code Structure

The `hybridSearch()` function is well-structured and follows the project's conventions:
- Async/await pattern used consistently
- Clear step-by-step pipeline with comments
- Deduplication via `Set<string>` with composite key `${nodeLayer}:${id}`
- Defensive: no input validation issues (inputs are already sanitized by `classifyIntent()` upstream)

### Issues Found

1. **No deduplication score merging (line 516–521):** When a node appears in both vector and graph results, only the first occurrence is kept. The graph results are appended after vector results, so if a node appears in both, the vector result (with its computed cosine similarity score) is kept, and the graph result (with its hardcoded score of 0.7 or 1.0) is discarded. This is fine for vector-priority but means graph-only nodes with score 0.7 could outrank vector nodes with score 0.65, which may not be the intended behavior.

2. **Hardcoded magic number `3` (line 503):** `.slice(0, 3)` for top L2 names is not configurable. Should be a named constant or parameter.

3. **No limit on graph traversal fan-out (lines 507–509):** Each of the up to 3 L2 names triggers a full graph traversal that can return the matched node + all its inbound + all outbound links. In a densely connected graph, this could return many results. The final `slice(0, limit)` caps the output, but the intermediate result set could be large.

4. **No error isolation (lines 507–509):** If `graphTraversalHandler()` throws for one of the 3 L2 names, the entire `Promise.all()` will reject, and the hybrid search fails entirely. There's no `Promise.allSettled()` or try/catch to allow partial graph results.

5. **No input validation on `query` parameter in `hybridSearch()`:** The function accepts `query: string` directly without sanitization. While `routeQuery()` calls `classifyIntent()` which sanitizes, the `hybridSearch()` function itself (exported) could be called directly with unsanitized input. However, since it's only called internally from `routeQuery()`, this is a low risk.

6. **No tests:** There are zero unit or integration tests for `hybridSearch()`, `vectorSearchHandler()`, `graphTraversalHandler()`, or `routeQuery()`. The hybrid search path is completely untested.

## Round 3 — Integration & Completeness Review

### Integration Points

1. **MCP endpoint (`POST /mcp/query`):** Correctly calls `routeQuery()` which dispatches to `hybridSearch()` when the LLM classifies intent as `"hybrid"`. This is the only way to trigger hybrid search.

2. **VS Code extension (`extensions-service.ts`, line 8–10):** `vscodeQuery()` delegates to `routeQuery()`, so the VS Code extension CAN use hybrid search through the MCP/query path.

3. **Frontend Query page (`query.tsx`):** Calls `POST /api/search` directly, bypassing the intent router entirely. The hybrid strategy is NOT available from the web UI.

4. **Search route (`search.ts`):** This is a completely independent implementation that duplicates vector search logic (semantic + LIKE fallback) without intent classification. It does not call `routeQuery()` or `hybridSearch()`.

### Findings

1. **Feature not usable from web UI:** The hybrid search is only accessible via the MCP endpoint. The kg-engine Query page uses a separate `/api/search` route that does not perform intent classification or hybrid routing. Users searching from the web UI will never get hybrid results.

2. **Duplicated search logic:** The `/api/search` route in `search.ts` contains its own vector search implementation (lines 66–140) that duplicates logic in `vectorSearchHandler()` in `intent-router.ts`. This creates a maintenance burden and risk of divergence.

3. **No temporal decay in hybrid re-rank:** The vector search results include temporal decay scoring (lines 192–199 of `intent-router.ts`), but the graph traversal results use hardcoded scores (1.0 for matched node, 0.7 for neighbors). When merged, these score scales are inconsistent — a graph neighbor with score 0.7 could outrank a vector result with decayed score 0.5, even if the vector result is more semantically relevant.

4. **No performance concerns for small datasets:** For the target scale (≤100K nodes), the in-memory cosine similarity approach is acceptable per the solution strategy. However, the hybrid search makes 1 embedding call + 2 DB queries (L2 + L3) for vector + up to 3 graph traversals (each with multiple DB queries). This could be slow for large graphs.

5. **No `includePending` propagation to graph traversal:** The `hybridSearch()` function passes `includePending` to `vectorSearchHandler()` but NOT to `graphTraversalHandler()` (line 508). The graph traversal handler doesn't accept an `includePending` parameter, so graph results are always unfiltered by validity status.

## Recommendations

1. **Fix the web UI integration:** Update `query.tsx` to call `POST /mcp/query` instead of `POST /api/search`, or add hybrid support to the search route.
2. **Add tests:** Write unit tests for `hybridSearch()` covering: basic merge, deduplication, score ordering, empty vector results, empty graph results, and error handling.
3. **Consider score boosting:** When a node appears in both vector and graph results, boost its score (e.g., `max(vectorScore, graphScore) + 0.1`) to reflect dual-signal validation.
4. **Use `Promise.allSettled`:** Wrap graph traversals to allow partial results if one traversal fails.
5. **Document the actual behavior:** Update ADR-007 to accurately describe the implementation as a "cascade" (vector seeds → graph expansion → merge → re-rank) rather than an "intersection."
6. **Extract magic number:** Make the top-N L2 seed count a named constant or configurable parameter.

---

## Verdict: ⚠️ WARN

The hybrid search is **implemented and functional** via the MCP endpoint, with a reasonable pipeline design (vector → graph seed → merge → re-rank). However, it has **no tests**, is **not accessible from the web UI**, has a **design-implementation mismatch** (union vs. intersection), and lacks **score boosting** for cross-validated results. The core logic is sound but the feature is incomplete from an integration and quality standpoint.
