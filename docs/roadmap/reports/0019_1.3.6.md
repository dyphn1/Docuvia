## Round 1 — Architecture & Design Review

### Design Spec Accuracy

ADR-007 Section 3 describes temporal decay as follows:
- Knowledge nodes contain `created_at` and `lastVerifiedAt` timestamps.
- The router applies an Exponential Temporal Decay function: `Math.exp(-LAMBDA * daysSinceVerified)`.
- When old knowledge correctly answers a query, its `lastVerifiedAt` is updated via `/api/search/feedback`.

**Assessment:** The design spec is clear, concise, and correctly describes the intended behavior.

### Schema Completeness

Both `l2_nodes.ts` (line 21) and `l3_nodes.ts` (line 33) define:
```typescript
lastVerifiedAt: timestamp("last_verified_at").defaultNow(),
```
This matches the design spec. The `defaultNow()` ensures all new nodes start with a current timestamp, which is correct for decay purposes.

### Implementation in intent-router.ts

The `vectorSearchHandler` function (lines 165–321) implements temporal decay correctly:

```typescript
const MS_PER_DAY = 1000 * 60 * 60 * 24;
const HALF_LIFE_DAYS = 30;
const LAMBDA = Math.LN2 / HALF_LIFE_DAYS;

const referenceDate = node.lastVerifiedAt ?? node.createdAt;
const daysSinceVerified = (Date.now() - referenceDate.getTime()) / MS_PER_DAY;
const decayFactor = Math.exp(-LAMBDA * Math.max(0, daysSinceVerified));
const score = rawScore * decayFactor;
```

This is applied to both L2 nodes (lines 192–200) and L3 nodes (lines 229–237). The math is correct:
- Half-life of 30 days means knowledge loses ~50% of its score after 30 days of inactivity.
- The `Math.max(0, ...)` guard prevents future-dated nodes from getting a score boost.
- The `?? node.createdAt` fallback handles nodes where `lastVerifiedAt` hasn't been explicitly set.

### Feedback Endpoint

`POST /search/feedback` (search.ts lines 217–237) correctly updates `lastVerifiedAt`:
```typescript
if (nodeLayer === "l2") {
  await db.update(l2NodesTable).set({ lastVerifiedAt: new Date() }).where(eq(l2NodesTable.id, id));
} else if (nodeLayer === "l3") {
  await db.update(l3NodesTable).set({ lastVerifiedAt: new Date() }).where(eq(l3NodesTable.id, id));
}
```
This is wired to the VS Code client via `CentralServerClient.ts` (line 190).

### Gap: Inconsistent Decay Across Search Paths

**This is the primary finding.** There are three separate search implementations in the codebase:

1. **`intent-router.ts` `vectorSearchHandler`** — ✅ Applies temporal decay
2. **`search.ts` `POST /search`** — ❌ Does NOT apply temporal decay (lines 78–85 for L2, lines 110–117 for L3)
3. **`mcp.ts` `GET /mcp/search_knowledge`** — ❌ Does NOT apply temporal decay (lines 82–89 for L2, lines 114–121 for L3)

Users searching via the main UI (`POST /search`) or the MCP search endpoint will see raw cosine similarity scores without decay, while users querying via `POST /mcp/query` (which uses the intent router) will see decayed scores. Over time, stale knowledge nodes will rank higher in the UI than in MCP queries, creating an inconsistent user experience.

## Round 2 — Code Quality & Security Review

### Decay Math Correctness

The exponential decay formula is mathematically correct:
- `LAMBDA = Math.LN2 / 30 ≈ 0.0231` (per day)
- After 30 days: `exp(-0.0231 * 30) = exp(-0.693) ≈ 0.5` (50% decay)
- After 60 days: `exp(-0.0231 * 60) = exp(-1.386) ≈ 0.25` (75% decay)
- After 90 days: `exp(-0.0231 * 90) = exp(-2.079) ≈ 0.125` (87.5% decay)

This is a standard half-life decay model and is appropriate for the use case.

### Code Structure Issues

1. **Local constants instead of module-level:** `HALF_LIFE_DAYS` and `LAMBDA` are defined inside `vectorSearchHandler` (lines 189–190). This means:
   - They are re-created on every function call (minor performance concern).
   - They cannot be easily unit-tested in isolation.
   - They cannot be configured without modifying source code.

2. **No unit tests:** There are zero test files for:
   - `intent-router.ts` (decay math, classification, hybrid merge)
   - `embedding.ts` (cosine similarity, parseEmbedding)
   - `search.ts` (search logic, feedback endpoint)

   This is a critical gap for a core routing component that arbitrates all query traffic.

3. **Code duplication:** The vector search logic is duplicated across three files (`intent-router.ts`, `search.ts`, `mcp.ts`) with different behaviors. This violates DRY and leads to the inconsistency noted above.

### Security

No security concerns specific to the temporal decay feature. The feedback endpoint uses Zod validation (`FeedbackSchema`) and properly handles errors.

## Round 3 — Integration & Completeness Review

### End-to-End Flow

The complete temporal decay lifecycle is implemented:
1. **Creation:** New L2/L3 nodes get `lastVerifiedAt = defaultNow()` from the schema.
2. **Decay application:** `intent-router.ts` applies decay during vector search.
3. **Refresh:** `POST /search/feedback` updates `lastVerifiedAt` when a user confirms a result is relevant.
4. **Client integration:** VS Code client calls the feedback endpoint via `CentralServerClient.ts`.

### Missing Pieces

1. **No decay in `search.ts`:** The standalone search endpoint used by the kg-engine UI does not apply temporal decay. This means the UI shows different rankings than the MCP endpoint.

2. **No decay in `mcp.ts` `search_knowledge`:** The MCP search knowledge endpoint also lacks temporal decay, creating a third inconsistent search path.

3. **No unit tests for RAG math:** The decay calculation, cosine similarity, and parseEmbedding functions are completely untested. These are pure functions that are easy to test and critical for correctness.

4. **No configurable half-life:** The 30-day half-life is hardcoded. While reasonable as a default, it should be configurable (e.g., via environment variable or database setting) to allow tuning without code changes.

### Performance

The decay calculation itself is O(1) per node and adds negligible overhead. However, the broader performance concern is the N+1 query pattern in `vectorSearchHandler` (lines 206–209, 242–243) where a separate project lookup query is executed for each result node. This is a pre-existing issue not specific to temporal decay.

## Recommendations

1. **Apply temporal decay consistently** across all three search paths (`intent-router.ts`, `search.ts`, `mcp.ts`). Extract the decay calculation into a shared utility function in `embedding.ts` or a new `decay.ts` module.

2. **Add unit tests** for:
   - `cosineSimilarity()` — test with identical vectors (score=1), orthogonal vectors (score=0), opposite vectors (score=-1)
   - `parseEmbedding()` — test with valid JSON, invalid JSON, null, empty string
   - Decay calculation — test with 0 days (factor=1), 30 days (factor≈0.5), 60 days (factor≈0.25), negative days (clamped to 0)

3. **Extract decay constants** to module-level or make configurable via environment variable.

4. **Consolidate search implementations** — Consider having `search.ts` and `mcp.ts` delegate to `intent-router.ts` `routeQuery()` to eliminate code duplication and ensure consistent behavior.

---

## Overall Verdict

**⚠️ WARN**

The temporal decay feature is **correctly implemented in the intent-router** with proper exponential decay math, schema support, and a feedback endpoint for refreshing node timestamps. However, the feature is **inconsistently applied** — two of three search paths (`search.ts` and `mcp.ts`) lack temporal decay entirely, creating divergent user experiences. Additionally, there are **no unit tests** for the decay calculation or related RAG math functions, and the half-life constant is not configurable. The core logic is sound, but the inconsistency and test coverage gaps warrant a WARN verdict.
