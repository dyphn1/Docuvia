## Round 1 — Architecture & Design Review

### What ADR-008 Specified

The ADR describes a DB-backed async queue pattern where:
1. Heavy operations write a `status: 'pending'` row to PostgreSQL and return immediately.
2. A **client-driven heartbeat** — the VS Code extension periodically pings `GET /api/metabolism-tick` to trigger micro-batch processing of pending tasks (e.g., 5 at a time).
3. A **dedicated admin endpoint** `GET /api/admin/metabolism-tick` for cron/nighttime execution.
4. A mutex prevents concurrent metabolism runs (Thundering Herd prevention).

### What Was Implemented

**Core Metabolism Route** (`metabolism.ts`):
- ✅ `GET /api/metabolism-tick` — exists and functional
- ✅ `GET /api/admin/metabolism-tick` — exists and functional
- ✅ In-memory mutex (`isMetabolismRunning` boolean flag) prevents overlapping runs
- ✅ Correction example distillation: queries `correction_examples` where `processedAt IS NULL`, calls OpenAI to extract guardrail rules, inserts into `promptTemplatesTable`, marks as processed
- ✅ Returns `202 Accepted` when already running, `200` on success, `500` on failure
- ✅ Both endpoints mounted in `routes/index.ts` and the Express app at `app.ts:37` (`/api`)

**VS Code Client Heartbeat** (`CentralServerClient.ts`):
- ✅ `startHeartbeat()` method with 5-minute base delay ± 1-minute jitter
- ✅ `_tickMetabolism()` calls `GET /api/metabolism-tick`
- ✅ `startHeartbeat()` called in `extension.ts:46`
- ✅ `sendFeedback()` method implemented for `POST /api/search/feedback`

**Feedback API** (`search.ts:217`):
- ✅ `POST /search/feedback` with Zod validation (`nodeLayer: enum(['l2','l3'])`, `id: number`)
- ✅ Updates `lastVerifiedAt = NOW()` on the appropriate node table

**Temporal Decay** (`intent-router.ts:188–203, 233–237`):
- ✅ Exponential decay formula: `decayFactor = exp(-λ * daysSinceVerified)`, half-life = 30 days
- ✅ Applied to both L2 and L3 vector search results
- ✅ Falls back to `createdAt` when `lastVerifiedAt` is null

**DB Schema**:
- ✅ `correction_examples.processedAt` column exists (line 14)
- ✅ `l2_nodes.lastVerifiedAt` column exists (line 21)
- ✅ `l3_nodes.lastVerifiedAt` column exists (line 33)

### Gaps and Discrepancies

1. **⚠️ No auth on admin endpoint**: The `GET /api/admin/metabolism-tick` endpoint at `metabolism.ts:96` is completely unauthenticated. Any caller can trigger metabolism processing. Unlike the GitHub webhook route which uses HMAC-SHA256, this endpoint has zero protection. For a cron-triggered endpoint, this is a significant concern — it should at minimum require a shared secret or API key.

2. **⚠️ In-memory mutex is not cluster-safe**: The mutex uses a simple `let isMetabolismRunning = false` boolean (`metabolism.ts:9`). This works for a single Node.js process, but if the server is ever scaled to multiple processes/instances (e.g., PM2 cluster mode, Docker replicas), concurrent metabolism runs will occur. The ADR itself acknowledges PostgreSQL should be the state machine — a `SELECT ... FOR UPDATE` advisory lock would be more correct.

3. **⚠️ Admin endpoint not documented in ADR's route table**: The ADR mentions `/api/admin/metabolism-tick` should exist but the gap note says "currently missing." It is now implemented, but the ADR gap note hasn't been updated to reflect this.

4. **ℹ️ Missing distributed lock pattern**: The ADR mentions "DB-backed lock" as an option but the implementation uses a plain in-memory flag. Since the spec calls for PostgreSQL-as-state-machine, this is a minor architecture deviation (acceptable for single-host deployments per ADR-007).

5. **ℹ️ No micro-batch limit on correction distillation**: The metabolism worker fetches up to 10 pending corrections (`metabolism.ts:22`, `.limit(10)`) and processes them all sequentially. Each one makes an OpenAI API call. If 10 corrections pile up, this could take 10–30 seconds and hold the mutex the entire time. The ADR suggests "5 pending tasks" as the micro-batch size.

## Round 2 — Code Quality & Security Review

### Strengths
- Clean, readable code in `metabolism.ts` with proper `try/catch/finally` ensuring mutex release even on failure.
- Proper Zod validation in the feedback endpoint (`search.ts:16–19`).
- Heartbeat uses randomized jitter (`CentralServerClient.ts:152`) to prevent thundering herd — good design.
- Error handling in `_tickMetabolism()` silently ignores network errors (`CentralServerClient.ts:173`), correct behavior for a heartbeat.
- Temporal decay math in `intent-router.ts` is clean and well-documented with named constants (`MS_PER_DAY`, `HALF_LIFE_DAYS`, `LAMBDA`).

### Issues Found

1. **❌ Security — Unauthenticated admin endpoint** (`metabolism.ts:96–112`):
   The `/admin/metabolism-tick` endpoint triggers LLM calls (cost) and database writes. It has no auth mechanism whatsoever. An attacker who discovers the URL can repeatedly trigger it, causing:
   - Unnecessary OpenAI API costs
   - Premature processing of correction examples before they're fully reviewed
   - Mutex lock contention with legitimate heartbeat calls
   
   **Recommendation**: Add at minimum a shared-secret query parameter or `X-Admin-Token` header.

2. **⚠️ No input validation on metabolism tick endpoints** (`metabolism.ts:78, 96`):
   Both endpoints accept `GET` requests with no parameters. While this is intentional, there's no rate limiting. Combined with the auth issue above, this is a concern.

3. **⚠️ Error response leaks internal details** (`metabolism.ts:88–90, 108–109`):
   ```typescript
   res.status(500).json({ error: "Metabolism tick failed" });
   ```
   This is fine (doesn't leak internals), but the logger captures the full error object. Ensure pino is configured to not serialize errors to the response in production.

4. **⚠️ Type safety issue in `metabolism.ts:27`**:
   ```typescript
   const promptsToInsert: any[] = [];
   ```
   Using `any[]` bypasses type checking. Should use the proper `InsertPromptTemplate` type from the schema.

5. **ℹ️ Search feedback endpoint returns 500 without logging** (`search.ts:234–236`):
   ```typescript
   res.status(500).json({ error: "Failed to process feedback" });
   ```
   No `logger.error()` call — failures will be silent in logs.

6. **ℹ️ Missing `return` after feedback error responses**: In `search.ts`, the error paths at lines 220 and 235 correctly use `return` before `res.json()`, but the pattern is consistent — no issue here.

## Round 3 — Integration & Completeness Review

### End-to-End Flow Assessment

**Flow 1: Human correction → Distillation → Prompt template**
1. Developer resolves a review task → correction example created with `processedAt: null`
2. VS Code heartbeat pings `/api/metabolism-tick` (every ~5 min)
3. Metabolism worker processes up to 10 pending corrections
4. OpenAI extracts guardrail rule → inserted into `promptTemplatesTable`
5. Correction marked as `processedAt = now()`

**Status: ✅ Complete and functional.** All pieces are wired together.

**Flow 2: Knowledge verification → lastVerifiedAt update → Decay recalculation**
1. User receives search results
2. Client calls `POST /api/search/feedback` with node ID and layer
3. `lastVerifiedAt` updated to `NOW()`
4. Next vector search applies temporal decay based on fresh timestamp

**Status: ✅ Complete and functional.** However, `sendFeedback()` is implemented in the client but **never called from any UI handler or chat command**. The feedback mechanism exists at the API layer but is not triggered by any user action in the extension. This means `lastVerifiedAt` is only ever set to `defaultNow()` at creation time — it will never be refreshed through actual usage.

**Flow 3: Client heartbeat lifecycle**
1. Extension activates → `startHeartbeat()` called
2. Heartbeat fires with jitter → `_tickMetabolism()`
3. On deactivation... the timeout is never cleared

**Status: ⚠️ Gap.** The `_heartbeatTimeout` is stored but never cleared on deactivation. The `deactivate()` function at `extension.ts:411` only calls `KnowledgeStore.getInstance(outputChannel).dispose()` — it doesn't stop the CentralServerClient heartbeat. This is a minor resource leak (won't cause functional issues since the extension host is shutting down, but it's untidy).

### Missing Pieces

1. **No tests for metabolism route**: No `*.unit.test.ts` or integration test found for `metabolism.ts`. The distillation logic, mutex behavior, and error paths are all untested.

2. **No tests for heartbeat**: The `startHeartbeat()`, `_tickMetabolism()`, and `sendFeedback()` methods in `CentralServerClient.ts` have no test coverage.

3. **No tests for feedback endpoint**: The `POST /search/feedback` handler has no test coverage.

4. **Feedback not triggered by any UI flow**: The `sendFeedback()` method exists but is never called from any command, CodeLens action, ChatParticipant handler, or search result interaction. The decay system will work but will only ever decay from `createdAt` since `lastVerifiedAt` is never updated through actual user feedback.

5. **No garbage collection for orphaned nodes**: The ADR mentions "garbage collection and graph recalculation" as a goal of the metabolism system, but the current implementation only handles correction distillation. There's no cleanup of orphaned L3 nodes, no recalculation of embeddings, no validity status transitions.

## Overall Verdict: ⚠️ WARN

The asynchronous metabolism mechanism from ADR-008 is **substantially implemented and functional**. The DB-backed queue pattern, in-memory mutex, correction distillation, client heartbeat with jitter, search feedback API, and temporal decay math are all in place and correctly wired together.

However, the **unauthenticated admin endpoint** is a high-severity security gap, the **feedback loop is never triggered from the UI** (making decay only directional), and there is **no test coverage** for any of the metabolism-related code. The in-memory mutex is acceptable for the documented single-host deployment but would need upgrading for any future clustering.

### Priority Recommendations

1. **Add auth to `/admin/metabolism-tick`** — at minimum a shared-secret header/query param.
2. **Wire `sendFeedback()` into the UI** — e.g., after a search result is viewed/used in chat.
3. **Add tests** for metabolism route (happy path, mutex lock, concurrent requests) and heartbeat.
4. **Replace `any[]` with proper type** in metabolism.ts.
5. **Add logger.error to the feedback endpoint** failure path.
6. **Clear heartbeat timeout on deactivate**.
