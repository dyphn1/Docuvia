## Round 1 — Architecture & Design Review

### What the Spec Requires

Item 1.4.2 requires a mutex or serialization mechanism that prevents concurrent generate requests from executing simultaneously. The concern is that the generate pipeline is a long-running, multi-step process (fetch commits → L1 tag → L2 extract → L3 generate → embed → review tasks → noise detection) that mutates shared state in PostgreSQL. Without serialization, two concurrent runs would:

1. Insert duplicate L2/L3 nodes
2. Create duplicate review tasks
3. Corrace embedding writes
4. Produce inconsistent `occurrenceCount` values on dedup updates

### What Is Implemented

**The `projects.status` field is set but not enforced as a lock.**

At `generate.ts:536–539`, the handler sets `project.status = "indexing"` before starting:
```typescript
await db
  .update(projectsTable)
  .set({ status: "indexing", updatedAt: new Date() })
  .where(eq(projectsTable.id, projectId));
```

However, there is **no gate at the top of the handler** that checks whether the project is already in `"indexing"` status. The handler proceeds directly from the status update to fetching commits without any guard.

The `project.status` enum is defined in `projects.ts:5–10`:
```typescript
export const projectStatusEnum = pgEnum("project_status", [
  "active",
  "indexing",
  "paused",
  "error",
]);
```

The status is used purely as a passive indicator — it is read by the dashboard to display pipeline state, but never used as a concurrency control.

**The metabolism mutex does NOT protect generate.**

`metabolism.ts:8–9` has an in-memory mutex:
```typescript
let isMetabolismRunning = false;
```

But this only protects `GET /api/metabolism-tick` and `GET /api/admin/metabolism-tick`. It has no relationship to the generate pipeline. This was correctly identified in the 1.4.1 report.

**The autoGenerate path in sync.ts is deferred.**

At `sync.ts:206`, the autoGenerate check explicitly logs but does NOT enqueue:
```typescript
// 4. Auto-generate check (enqueue deferred — actual queue implementation is deferred per plan)
```

This means there is no deferred queue that could have provided serialization.

**The ingest route has no mutex either.**

`ingest.ts` (lines 80–207 for git, 209–322 for svn) directly processes ingest requests with no status check or lock. Concurrent ingests for the same project could produce duplicate commits.

### Gaps and Discrepancies

1. **❌ No generate mutex exists.** This is the primary gap — the feature specified in 1.4.2 is simply not implemented. There is no mechanism (in-memory, DB-level, or otherwise) to prevent two concurrent `POST /projects/:id/generate` requests from running simultaneously.

2. **❌ No status check before generate.** While the handler sets `status = "indexing"`, it never checks `status !== "indexing"` or `status === "active"` at the start. The status field could serve as a simple advisory lock but is not used as one.

3. **❌ No ingest mutex.** Concurrent ingest requests for the same project can produce duplicate commit rows (though the `existingHashes` check at `ingest.ts:133–140` provides some dedup, it has a TOCTOU race window between the SELECT and the INSERT).

4. **ℹ️ The `paused` status enum value is never checked.** The `paused` state is defined in the schema but no handler checks for it as a guard before processing.

## Round 2 — Code Quality & Security Review

### Strengths
- The generate handler is well-structured with clear sequential steps and proper error handling that restores the project status to `"error"` on failure (`generate.ts:1026–1032`).
- The `existingHashes` set in ingest provides best-effort dedup for git ingestion, which mitigates (but does not eliminate) one race condition.
- The metabolism mutex pattern in `metabolism.ts` correctly uses try/finally to prevent permanent lockout on error.

### Issues Found

1. **❌ Critical — No serialization on generate endpoint** (`generate.ts:518–533`):
   The handler begins with a project existence check and input validation, but immediately proceeds to set `status = "indexing"` without checking current status. A second concurrent request can pass the same checks and both proceed to execute the full pipeline. This is a classic TOCTOU race.

   **Recommended fix** — Add a guard at the top of the handler:
   ```typescript
   if (project.status === "indexing") {
     return res.status(409).json({ error: "Generate already in progress for this project" });
   }
   ```
   Or better, use an atomic compare-and-swap:
   ```typescript
   const [updated] = await db.update(projectsTable)
     .set({ status: "indexing", updatedAt: new Date() })
     .where(and(eq(projectsTable.id, projectId), eq(projectsTable.status, "active")))
     .returning();
   if (!updated) return res.status(409).json({ error: "Project is not in active state" });
   ```

2. **❌ Critical — No serialization on ingest endpoint** (`ingest.ts:80–83`):
   The git ingest handler checks project existence but not status. Two concurrent ingests can both pass the `existingHashes` check and insert the same commits. The `{ allErrors: false }` option on insert (if used) or the unique constraint on `(projectId, hash)` would catch the duplicate at the DB level, but the error handling path is unclear.

3. **⚠️ Medium — Long-running handler holds no lock** (`generate.ts:518–1033`):
   The generate handler runs for potentially minutes (multiple sequential LLM calls, embedding generation, DB writes). During this entire time, there is no lock held. Even if a status check is added, the window between the status check and the status update is atomic (single UPDATE), but the check-then-update pattern is not atomic without `SELECT ... FOR UPDATE` or a conditional UPDATE.

4. **⚠️ Medium — In-memory mutex pattern is fragile** (`metabolism.ts:8–9`):
   The `isMetabolismRunning` boolean only works for a single Node.js process. This is acceptable for single-host deployment (per ADR-007), but the generate endpoint's lack of any lock means there's no analogous protection at all.

5. **ℹ️ Low — `sync.ts:206` autoGenerate is a no-op**:
   The comment says "enqueue deferred" and only logs. The log message says "enqueue generate" but nothing is actually enqueued. This is a known gap per the roadmap (3.4.3 is ❌ Todo).

## Round 3 — Integration & Completeness Review

### End-to-End Flow Assessment

**Flow: Concurrent generate requests**
1. Request A arrives → sets `status = "indexing"` → begins processing commits
2. Request B arrives → sees `status` is `"indexing"` → **should be rejected** but currently → also sets `status = "indexing"` → begins processing commits
3. Both run LLM calls → both insert L2/L3 nodes → duplicates created
4. Both update `occurrenceCount` on the same L3 nodes → **last-write-wins** race, counts may be off by one

**Status: ❌ No protection exists.**

**Flow: Ingest then generate**
1. Ingest completes → commits have `processedAt: null` (for incremental)
2. Generate starts → picks up unprocessed commits → processes them
3. Ingest runs again → adds more commits with `processedAt: null`
4. Generate finishes → marks its batch as processed
5. New commits from step 3 are orphaned until next generate

**Status: ⚠️ No corruption, but no serialization either.** This is an acceptable edge case for the current design.

### Missing Pieces

1. **No mutex on generate** — the core feature of 1.4.2 is not implemented.
2. **No tests for concurrent access** — no test verifies behavior when two generate requests arrive simultaneously.
3. **No tests for the status guard** — no test verifies that a project in "indexing" state rejects new generate requests.
4. **No integration test for generate + ingest race** — no test covers concurrent ingest and generate on the same project.
5. **No E2E test for load handling** — no test verifies behavior under concurrent API requests.

### Performance Note

The generate handler at `generate.ts:518–1033` makes multiple sequential OpenAI API calls. With `maxCommits` defaulting to 50 and a batch size of 20, this means up to 3 LLM calls just for L2 extraction, plus 1 for L1 tagging, plus embedding calls for each new node, plus potential condensation calls. Under concurrent load, this would multiply linearly, potentially hitting OpenAI rate limits and increasing costs.

## Overall Verdict: ❌ FAIL

The mutex/serialization mechanism for concurrent generate requests (item 1.4.2) is **not implemented**. While the `projects.status` field exists and is updated to `"indexing"` during generation, it is never used as a guard to reject concurrent requests. There is no in-memory lock, no DB-level advisory lock, no conditional UPDATE, and no request queue.

The only mutex in the codebase is the `isMetabolismRunning` boolean in `metabolism.ts`, which protects metabolism ticks only — this was the subject of the previous report (1.4.1) and is a separate concern.

The lack of serialization means that if two `POST /projects/:id/generate` requests arrive concurrently (e.g., from a user clicking "Generate" twice, from an automated sync hook, or from the deferred autoGenerate path), both will execute the full pipeline, producing duplicate L2/L3 nodes, duplicate review tasks, and inconsistent `occurrenceCount` values.

### Priority Recommendations

1. **Add an atomic status guard to `POST /projects/:id/generate`** — Use a conditional `UPDATE ... WHERE status = 'active'` to atomically claim the project, and return `409 Conflict` if the update affects 0 rows. This leverages the existing `projectStatusEnum` and requires minimal schema change.

2. **Add a similar guard to ingest endpoints** — At minimum, reject concurrent ingests for the same project. Alternatively, rely on the unique constraint on `(projectId, hash)` and handle duplicate key errors gracefully.

3. **Add tests** — Write integration tests that send concurrent generate requests and verify only one succeeds, and that the project status transitions correctly.

4. **Consider a proper queue for autoGenerate** — When the `autoGenerate` feature in `sync.ts` is eventually implemented, it should go through the same serialization guard.

5. **Handle the "not in active state" response** — The frontend (`kg-engine`) should handle a `409 Conflict` response from the generate endpoint gracefully (e.g., show "Pipeline already running" instead of an error).
