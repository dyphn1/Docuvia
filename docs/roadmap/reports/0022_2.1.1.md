## Round 1 — Architecture & Design Review

### Does the design document correctly describe the feature?

ADR-002 describes a "Local-First, Server-Augmented" architecture with two modes:
1. **Standalone Mode** — When `isServerConfigured()` returns false, the extension relies on local `.docuvia/` YAML files and git orphan branch reads.
2. **Server-Augmented Mode** — When a `server_url` is configured, the extension offloads heavy computation to the API server.

The implementation matches this design well. The `KnowledgeStore` class implements a clear three-tier loading strategy (lines 141-201 of `KnowledgeStore.ts`):
- **Tier 1 (Server API):** If `isServerConfigured()` is true AND `manifest.project_id` exists, it calls `pullSnapshot()` from the central server.
- **Tier 2 (Local `.docuvia/` directory):** If Tier 1 fails or returns empty, it reads `l1_tags.yaml`, `l2_modules.yaml`, `l3_router.yaml`, and `l3_decisions/*.md` directly from the workspace `.docuvia/` folder.
- **Tier 3 (Git orphan branch):** If Tier 2 also returns empty, it falls back to reading from the `docuvia-knowledge` orphan branch via `git show` and `git ls-tree`.

### Are there gaps between the design spec and the actual implementation?

**Gap 1 — `last_verified_at` decay not implemented.** ADR-002 explicitly mentions "Local garbage collection based on `last_verified_at` decay" but notes in parentheses: "(Note: `last_verified_at` is currently not implemented)." This is an acknowledged gap. The `KnowledgeStore` has no decay/garbage collection logic. The `L3Decision` type in `types.ts` does not include a `last_verified_at` field. This is consistent with the ADR's own admission.

**Gap 2 — Git orphan branch fallback requires `manifest.project_id`.** The Tier 3 git fallback (lines 189-201 of `KnowledgeStore.ts`) only activates if `manifest.project_id !== undefined`. However, the `ManifestSchema` in `types.ts` defines `project_id` as optional (`z.number().optional()`). If a user initializes a project locally without ever connecting to a server, the `project_id` will be absent, and the git fallback will never trigger. This is a minor gap — the local `.docuvia/` Tier 2 fallback will still work, but the git orphan branch recovery path is effectively unreachable for purely local projects.

**Gap 3 — `KnowledgeStore._loadFromGit` uses `exec` (child_process).** The git fallback uses `child_process.exec` via promisify, which spawns a shell. This is functional but introduces a dependency on the `git` CLI being available in the PATH. There's no check or graceful error message if git is not installed.

### Are there contradictions between different design documents?

No contradictions found. The ADR-002, the AGENTS.md, and the implementation are all aligned on the local-first principle.

### Is the feature complete per the design spec?

The core local-first feature is **complete**. The extension:
- Activates without a server (`onStartupFinished` and `workspaceContains:.docuvia` activation events in `package.json` lines 14-17).
- Loads knowledge from local `.docuvia/` YAML files when no server is configured.
- Provides full TreeView, CodeLens, Hover, Dashboard, and Chat Participant functionality using only local data.
- Gracefully degrades when server methods are called (e.g., `CentralServerClient.query()` returns `[]` when no `server_url` is configured, line 47-49).

## Round 2 — Code Quality & Security Review

### Is the implementation well-structured and following the project's coding rules?

**MVC Pattern:** The codebase follows a clean separation:
- **Model:** `KnowledgeStore` (data layer), `types.ts` (domain types with Zod schemas)
- **View:** `KnowledgeGraphTreeProvider`, `TaskQueueTreeProvider`, `DashboardPanel`, `SearchResultsPanel` (UI presentation)
- **Controller:** `extension.ts` (command handlers), `ChatParticipant.ts` (chat request routing)

**Defensive Design:** Good use of early returns and guard clauses throughout. For example:
- `KnowledgeStore.load()` guards against concurrent loading with `_loading` flag (line 94-98).
- `CentralServerClient.query()` returns `[]` early when no `server_url` (line 47-49).
- `DocuviaCodeLensProvider.provideCodeLens()` returns `[]` early when no snapshot is available (line 98).

**POP (Protocol-Oriented Programming):** The `IDocuviaClient` interface in `KnowledgeStore.ts` (lines 15-18) decouples the store from the concrete `CentralServerClient`, enabling testability and alternative implementations.

### Are there security vulnerabilities?

**1. `child_process.exec` in `_loadFromGit` (KnowledgeStore.ts line 290):** The `exec` function spawns a shell, which could be a vector if `workspaceRoot` or `projectId` were ever tainted. However, `workspaceRoot` comes from VS Code's `folder.uri.fsPath` (trusted), and `projectId` is parsed from a YAML file as a number (validated by `ManifestSchema`). The `GIT_KNOWLEDGE_BRANCH` constant is hardcoded. Risk: **LOW**.

**2. Path traversal in `DashboardPanel._handleMessage` (line 159):** The code checks `if (!msg.filePath.startsWith(workspaceRoot))` to reject paths outside the workspace. This is a good security measure.

**3. No input sanitization on YAML parsing:** The `parser.ts` functions use Zod schemas to validate parsed YAML, which provides structural validation. However, the content fields (e.g., `description`, `body`) are stored as plain strings without sanitization. Since this is a local-first VS Code extension (not a web app), the risk is minimal — the YAML files are created by the extension itself or the user.

**4. `executeSearch` in `extension.ts` (line 387-409):** The `executeSearch` function calls `centralClient.query()` which sends the query to the server. When no server is configured, `query()` returns `[]` immediately. The function does NOT fall back to local search — it only routes to the server. This means the "Open Cross-Project Search" command (`docuvia.openSearch`) silently does nothing when no server is configured (returns empty results panel). This is a UX gap, not a security issue.

### Are there code smells, duplication, or anti-patterns?

**1. `tryParse` method in `KnowledgeStore.ts` (lines 463-470) is never called.** It's defined as a private method but never used. Dead code.

**2. `KnowledgeStore.tryParse` has a broken return type.** The signature `T extends any[] ? T : never` is a conditional type that doesn't work correctly for non-array returns. Since it's unused, this is harmless but should be cleaned up.

**3. `ChatParticipant.ts` `handleQuery` performs case-insensitive search by lowercasing the query (line 281) but then compares against lowercased fields. However, `d.body.toLowerCase().includes(query)` lowercases the body at every iteration. For large decision bodies, this could be slightly inefficient. Minor.

**4. `CentralServerClient._tickMetabolism` catches all errors silently (line 172-174).** While intentional (heartbeat shouldn't crash), logging the error at debug level would aid troubleshooting.

### Are error handling and edge cases properly addressed?

**Yes, generally well-handled:**
- `KnowledgeStore.load()` uses a try-catch with `_loading` guard and `_pendingReload` for concurrent reload requests.
- `CentralServerClient.query()` throws `CentralServerAuthError` on 401, which is caught in `ChatParticipant.handleBreadthQuery` and `executeSearch`.
- `TaskRunner.runExtractionAsync` catches per-chunk errors and continues processing remaining chunks (line 285-290).
- `KnowledgeIndexer.buildTreeForFile` catches symbol provider failures gracefully (line 84-86).

**Edge case concern:** When `isServerConfigured()` is false, the `executeSearch` function (line 387-409) still calls `centralClient.query()` which returns `[]`, then shows the `SearchResultsPanel` with empty results. The user gets an empty panel with no indication that a server is needed. The `handleBreadthQuery` in `ChatParticipant.ts` does better — it shows a tip about configuring `server_url` (line 369-370).

## Round 3 — Integration & Completeness Review

### Does the feature integrate correctly with other parts of the system?

**Yes.** The local-first architecture integrates well with all subsystems:

1. **TreeView (`KnowledgeGraphTreeProvider`):** Reads directly from `KnowledgeStore.snapshots`, which are populated from local files. No server dependency.

2. **CodeLens (`DocuviaCodeLensProvider`):** Lines 104-128 show "online mode" with full decision data from local snapshot. Lines 130-146 show "offline fallback" using manifest path patterns when no L2 modules have decisions. Both paths work without a server.

3. **Hover (`DocuviaHoverProvider`):** Reads from `KnowledgeStore` snapshot and `KnowledgeIndexer`. No server dependency.

4. **Chat Participant (`ChatParticipant.ts`):** The `/query` command (lines 275-343) performs local keyword search against `store.snapshots`. The `/explore` command (lines 153-273) reads local `README.md` and `package.json` files. The `/extract` command (lines 393-497) queues local extraction tasks. Only the breadth query path (lines 357-391) requires a server, and it degrades gracefully with a helpful message.

5. **Dashboard (`DashboardPanel`):** Reads from `KnowledgeStore.getSnapshotFor()`. No server dependency.

6. **TaskRunner:** Uses `vscode.lm.selectChatModels()` for local LLM access. No server dependency.

7. **File Watcher:** `KnowledgeStore.startWatcher()` sets up `FileSystemWatcher` on `.docuvia/**` for all workspaces, enabling real-time local updates without server polling.

### Are there missing tests?

The vscode-client has unit test infrastructure (see `artifacts/vscode-client/` for test setup), but I did not find specific tests for:
- The three-tier loading strategy in `KnowledgeStore.load()`
- The `isServerConfigured()` branching logic
- The local fallback in `DocuviaCodeLensProvider`
- The `handleQuery` local search in `ChatParticipant`

This is a gap, but consistent with the project's overall test coverage pattern (E2E tests are marked as WIP across the checklist).

### Are there performance concerns?

**1. `KnowledgeStore._loadFromGit` spawns multiple sequential `git` processes.** For a project with many L2 modules and L3 decisions, this could spawn dozens of `git show` and `git ls-tree` commands sequentially. Each spawns a new process. This is acceptable for the fallback path but could be slow for large knowledge bases.

**2. `KnowledgeIndexer.buildTreeForFile` is debounced with 500ms delay (line 49-53).** This is a reasonable debounce interval.

**3. `KnowledgeStore._handleBatchedChanges` has incremental vs. full reload logic (lines 414-439).** The thresholds (50 files, 50% ratio) are configurable via VS Code settings. This is a well-designed optimization.

### Is the feature actually usable end-to-end without a server?

**Yes.** A user can:
1. Open a workspace in VS Code with the Docuvia extension.
2. Run `Docuvia: Init Project` to create `.docuvia/` with skeleton YAML files.
3. Run `Docuvia: Analyze Project Architecture` (`/explore`) to generate L1 tags from `README.md`/`package.json`.
4. Run `Docuvia: Add Decision` to create L3 decision markdown files.
5. Run `Docuvia: Run L3 Extraction on Active File` to extract decisions from code.
6. View the Knowledge Graph tree with L1/L2/L3 hierarchy.
7. See CodeLens annotations above functions/classes.
8. Hover over symbols to see L3 decision previews.
9. Use `@docuvia /query` to search the local knowledge graph.
10. Use the Dashboard panel to see project statistics.
11. Use drag-and-drop in the TreeView to categorize decisions.

**All of the above work without any server configuration.** The only features that require a server are:
- Cross-project search (`/query` with breadth patterns like "other projects")
- Server-side RAG (vector/graph search)
- Knowledge snapshot pulling from the API

## Findings

### Issues

1. **Minor — `executeSearch` shows empty results panel when no server is configured** (`extension.ts` line 397-398). Unlike `handleBreadthQuery` in `ChatParticipant.ts` which shows a helpful tip about configuring `server_url`, the `executeSearch` function silently shows an empty `SearchResultsPanel`. **Recommendation:** Add a check for `centralClient.isServerConfigured()` before calling `query()`, and show an informational message instead.

2. **Minor — `KnowledgeStore.tryParse` is dead code** (`KnowledgeStore.ts` lines 463-470). **Recommendation:** Remove the unused method.

3. **Minor — Git orphan branch fallback requires `project_id`** (`KnowledgeStore.ts` line 189). For purely local projects, `project_id` will be `undefined`, making the git fallback unreachable. **Recommendation:** Consider using a default path or workspace-based identifier for the git fallback when `project_id` is absent.

4. **Info — `last_verified_at` decay not implemented.** This is acknowledged in ADR-002 itself. No action needed for this verification cycle.

### Risks

1. **Low — Shell injection via `child_process.exec` in `_loadFromGit`.** The inputs are trusted (VS Code workspace paths and validated project IDs), but using `execFile` instead of `exec` would be more defensive.

2. **Low — No git CLI availability check.** If git is not in PATH, the Tier 3 fallback will fail with an unhandled error. The error is caught and logged, but the user may not see the message.

### Recommendations

1. Improve the `executeSearch` UX for serverless mode (show a message instead of empty panel).
2. Remove dead code (`tryParse` method).
3. Consider making the git orphan branch path work without `project_id`.
4. Add unit tests for the three-tier loading strategy.

---

## Overall Verdict: ✅ PASS

The local-first operation feature is **well-implemented and functional**. The extension provides full standalone value without a central server, with a clear three-tier loading strategy (server → local files → git orphan branch). All core features (TreeView, CodeLens, Hover, Chat Participant, Dashboard, TaskRunner, drag-and-drop) work without server configuration. The few issues found are minor UX gaps and code quality concerns, not architectural flaws or blockers.
