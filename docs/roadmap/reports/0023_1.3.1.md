## Round 1 — Architecture & Design Review

### What the Design Specifies

ADR-007 defines a routing funnel:

1. **O(1) Direct Filter** — If query contains `#attach` or file extensions (`.ts`, `src/`), route to Direct RAG
2. **O(1) Graph Filter** — If query matches L1/L2 names in the database, route to Graph RAG
3. **LLM Fallback** — Otherwise, use gpt-4o-mini to classify into one of: `vector_search`, `graph_traversal`, `direct_lookup`, `hybrid`

The four strategies are:
- **Vector RAG**: Embedding similarity via PGVector
- **Graph RAG**: Traverse `node_links` for structural dependencies
- **Direct RAG**: O(1) lookup via `target_refs` or exact identifiers
- **Hybrid RAG**: Intersection of graph constraints and vector similarities

### Implementation Assessment

The `intent-router.ts` file (634 lines) implements all 4 strategies:

- **`classifyIntent(query)`** (line 106): LLM-based classification using `gpt-4o-mini` with `response_format: { type: "json_object" }`. Sanitizes input. Returns structured `IntentClassification` with strategy, entities, confidence, reasoning. Falls back to `vector_search` on any error.
- **`vectorSearchHandler(query, projectId, limit, includePending)`** (line 165): Generates embedding, queries L2 and L3 nodes with embeddings, applies cosine similarity + temporal decay (`Math.exp(-LAMBDA * daysSinceVerified)` with half-life of 30 days), falls back to SQL LIKE if embedding fails.
- **`graphTraversalHandler(moduleName, projectId)`** (line 327): Finds matching L2 node, traverses outbound (`node_links.sourceNodeId`) and inbound (`node_links.targetNodeId`) links.
- **`directLookupHandler(commitHash, includePending)`** (line 424): Looks up commits by hash prefix, plus associated L3 nodes.
- **`hybridSearch(query, classification, projectId, limit, includePending)`** (line 488): Runs vector search, extracts top-3 L2 node names, runs graph traversal for each, merges and deduplicates by `(nodeLayer, id)`.
- **`routeQuery(query, projectId, limit, includePending)`** (line 533): Orchestrator with O(1) fast-paths (#attach/file extensions → direct, L1/L2 name match → graph), then LLM classification, then switch-based dispatch.

### Gaps and Issues

1. **Intent router is underutilized.** The 4-way intent classification is only triggered via `POST /mcp/query` (line 326 of `mcp.ts`). The main search UI (`kg-engine/src/pages/query.tsx`) calls `POST /api/search` (the `search.ts` route), which performs a flat semantic/LIKE search WITHOUT intent classification. Similarly, `GET /mcp/search_knowledge` (line 47 of `mcp.ts`) is a completely separate implementation. The intent classification feature is effectively only accessible to MCP clients, not to web UI users.

2. **"Direct RAG" strategy mismatch with ADR.** ADR-007 describes Direct RAG as O(1) lookup via `target_refs` (e.g., CodeLens references). The implementation (`directLookupHandler`, line 424) searches commits by hash and associated L3 nodes — this is not the same as the `target_refs` lookup described in the ADR. The #attach fast-path (line 544) sets `strategy: "direct_lookup"` but passes the entire query as `searchQuery` (not extracting a target ref). The `#attach` token in the fast-path doesn't actually change the search behavior meaningfully.

3. **Filter/bypass semantic inconsistency.** The fast-path arbitration (lines 543-576) sets `classification` but doesn't extract specific identifiers. For example, the graph filter (line 566) matches a term but uses the matched term as `moduleName`, which then gets passed to `graphTraversalHandler`. However, the direct fast-path (line 544) only sets `searchQuery: query` — it doesn't extract a ref or commit hash. This means the direct handler receives the entire raw query as `commitHash`.

### Round 1 Verdict

The architecture is solid and the implementation faithfully covers all 4 strategies. The O(1) fast-path funnel is a nice optimization. The main gap is that the intent router is not the primary search entry point — it's sidelined to `/mcp/query` only — and the direct lookup semantics don't fully match the ADR.

## Round 2 — Code Quality & Security Review

### Strengths

- **Input sanitization**: `sanitizeQuery()` (line 99) strips control characters (`\x00-\x1F\xx7F`) and truncates to 2000 chars before sending to LLM.
- **Strategy validation**: `VALID_STRATEGIES` set (line 88) ensures only whitelisted strategies are accepted from LLM output.
- **Confidence clamping**: `Math.max(0, Math.min(1, parsed.confidence))` on line 137 prevents out-of-range confidence values.
- **Graceful degradation**: If embedding generation fails, falls back to SQL LIKE search. If LLM classification fails, falls back to vector_search.
- **Structured logging**: Every classification, result, and error is logged with context using pino.
- **Zod validation**: `POST /mcp/query` validates request body (line 320-324).

### Issues

1. **No authentication on MCP endpoints.** None of the MCP routes (`/mcp/query`, `/mcp/list_projects`, `/mcp/search_knowledge`, `/mcp/get_dependencies`, etc.) have authentication middleware. Compare with `POST /mcp/query` which accepts a bearer token per the design (per item 6.2.3), but the implementation doesn't validate it. The `extensions_vscode.ts` route at line 29 (`VscodeQuerySchema.parse`) uses `.parse()` (throws) instead of `.safeParse()` (returns result), which would cause an unhandled 500 instead of a clean 400.

2. **`include_pending` validation inconsistency.** The `mcpQueryBodySchema` (line 320-324) validates `q`, `project_id`, and `limit` via Zod, but `include_pending` is extracted separately from query params (line 333: `req.query.include_pending === "true"`). This creates a split validation pattern — part body, part query — that's confusing and bypasses Zod for the `include_pending` field.

3. **No tests exist.** There are zero test files for any component in the intent router: no unit tests for `classifyIntent`, `cosineSimilarity`, `vectorSearchHandler`, `graphTraversalHandler`, `directLookupHandler`, `hybridSearch`, `routeQuery`, or `generateEmbedding`. These are core routing components and should have test coverage, especially for:
   - Cosine similarity edge cases (zero vectors, orthogonal vectors)
   - Temporal decay math correctness
   - Intent classification parsing (malformed JSON from LLM, missing fields)
   - Strategy routing logic (does each strategy handler get called correctly?)

4. **`projectId` filtering is inconsistent in graph traversal.** `graphTraversalHandler` (line 336-337) queries all L2 nodes matching the name pattern, then uses JavaScript `.find()` to filter by `projectId` in memory rather than adding a SQL WHERE clause. This is both less efficient and semantically different (it silently picks the first match across all projects if `projectId` is not provided).

5. **No timeout on LLM calls.** `openai.chat.completions.create()` (line 116) and `openai.embeddings.create()` (line 14 of embedding.ts) have no explicit timeout. A slow or hung LLM API would block the request indefinitely.

6. **Duplicate search implementations.** The `/mcp/search_knowledge` GET endpoint (line 47 of `mcp.ts`) contains ~150 lines of search logic that duplicates the vector search in `vectorSearchHandler`. This is a code smell — the same logic exists in two places with slight variations (e.g., no temporal decay in the GET endpoint).

### Round 2 Verdict

The code is well-structured with good defensive patterns (sanitization, validation, fallbacks). The primary concerns are: no auth on MCP routes, zero test coverage, duplicate search logic, and the `projectId` filtering anti-pattern in graph traversal.

## Round 3 — Integration & Completeness Review

### Integration Points

| Endpoint | Uses `routeQuery()`? | Notes |
|----------|---------------------|-------|
| `POST /mcp/query` | ✅ Yes (line 336 of mcp.ts) | Primary MCP query entry point |
| `POST /extensions/vscode/query` | ✅ Yes (via `vscodeQuery()` in extensions-service.ts line 8-10) | VS Code extension delegates correctly |
| `GET /mcp/search_knowledge` | ❌ No | Separate implementation with no intent classification |
| `GET /api/search` | ❌ No | kg-engine frontend calls this, not the intent router |
| `query.tsx` (kg-engine) | ❌ No | Calls `/api/search`, bypassing intent router entirely |

### Performance Concerns

1. **O(N) "O(1)" graph filter.** The fast-path graph filter (lines 554-576) loads ALL L1 tags and ALL L2 nodes from the database into memory on every query that doesn't match the `#attach` fast-path. This is O(N) in the number of tags and nodes, not O(1) as described in ADR-007. For large knowledge graphs with hundreds of nodes, this becomes a significant performance bottleneck.

2. **No caching of architectural terms.** The L1 tags and L2 node names are fetched from the database on every single query. These change infrequently and should be cached.

3. **N+1 query pattern in vector search.** After scoring nodes, the code fetches project names one-by-one (line 206-207: `await db.select(...)`) for each result node. This is an N+1 query pattern. A single JOIN would be more efficient.

4. **No rate limiting on LLM calls.** The `classifyIntent` function can be called by any unauthenticated client with arbitrary frequency, leading to potential API cost explosions.

### Missing Pieces

- **No `include_pending` query param Zod validation.** As noted above.
- **No OpenAPI spec for `GET /mcp/search_knowledge` response types.** The endpoint returns a custom inline type instead of using the generated `AgenticSearchResult` type from Orval.
- **No `/api/search/endpoint` for feedback.** ADR-007 (line 35) mentions a `/api/search/feedback` endpoint for updating `lastVerifiedAt`, which is not implemented in the examined codebase.
- **kg-engine doesn't use intent router.** The frontend query page (`query.tsx`) calls `/api/search` directly, meaning web users never get the benefit of intent classification, 4-way routing, or hybrid search.

### Round 3 Verdict

The intent router itself is fully implemented and correctly wired to its two entry points (`POST /mcp/query` and `POST /extensions/vscode/query`). However, the broader system integration is incomplete: the main search UI bypasses the intent router, the feedback endpoint is missing, and the O(1) arbitration is actually O(N) in practice.

## Overall Verdict

**⚠️ WARN**

The 4-way intent classification is fully implemented in `intent-router.ts` and correctly handles all four strategies (vector, graph, direct, hybrid) with O(1) fast-paths, temporal decay, and graceful degradation. The `routeQuery()` orchestrator is properly wired to `POST /mcp/query` and the VS Code extension query endpoint.

However, there are notable gaps: no authentication on MCP routes, zero test coverage for 634 lines of core routing logic, the main web UI bypasses the intent router entirely, the O(1) arbitration is actually O(N), and the direct lookup semantics don't match the ADR. These issues are significant enough to warrant a WARN rather than a PASS, but the core feature is functional and well-structured.
