## Round 1 — Architecture & Design Review

### Design Compliance

ADR-002 defines a three-tier knowledge loading strategy. The implementation in `KnowledgeStore._loadWorkspace()` (lines 140–201) faithfully implements all three tiers:

1. **Tier 1 — Server API** (line 141): When `this._client.isServerConfigured()` returns true and `manifest.project_id` is defined, calls `this._client.pullSnapshot()`. On failure, logs the error and falls through.
2. **Tier 2 — Local .docuvia/ YAML** (line 152): When tags and modules are still empty after the server attempt, reads `l1_tags.yaml`, `l2_modules.yaml`, `l3_router.yaml`, and the `l3_decisions/` directory directly from the workspace `.docuvia/` folder.
3. **Tier 3 — Git orphan branch** (line 189): When both previous tiers yield no data, reads from the `docuvia-knowledge` orphan branch via `git show` and `git ls-tree`.

This is a correct and complete implementation of the ADR-002 specification.

### Graceful Degradation in CentralServerClient

The `CentralServerClient` class implements graceful degradation at the method level:

- **`query()`** (line 45–75): Returns an empty array `[]` when `server_url` is not configured. This allows callers to proceed without server data.
- **`sync()`** (line 87–111): Silently returns when `server_url` is not configured. Correct for fire-and-forget operations.
- **`sendFeedback()`** (line 177–198): Silently returns when `server_url` is not configured. Correct for non-critical feedback.
- **`pullSnapshot()`** (line 117–139): Throws `Error('Server URL not configured')` when no server URL. This is appropriate because callers need the data and must handle the absence.

### ChatParticipant Routing

`ChatParticipant.handleQuery()` (line 275–343) correctly implements the local-first search pattern:
- Local keyword search against `KnowledgeStore.snapshots` works entirely offline
- "Breadth" queries (cross-project) are detected by `isBreadthQuery()` (line 347–355) and routed to `centralClient.query()`
- When the server is not configured, `query()` returns `[]` and the user sees a helpful tip about configuring `server_url`

### Interface Decoupling

The `IDocuviaClient` interface (KnowledgeStore.ts, lines 14–18) decouples `KnowledgeStore` from the concrete `CentralServerClient` class. This is good design — it allows for test doubles and alternative implementations.

### Gaps

- **No `last_verified_at` decay in standalone mode**: ADR-002 (line 36) mentions "Local garbage collection based on `last_verified_at` decay" but notes it is "currently not implemented." This is consistent with the checklist marking 1.3.6 as WIP.
- **`checkAuthorizationScope()` stub** (line 78–81): Returns `true` for all scopes. Acceptable for v1 but should be flagged for enterprise deployments.

## Round 2 — Code Quality & Security Review

### Code Quality

- **Defensive design**: All methods in `CentralServerClient` check for `server_url` before making network calls. Early returns are used consistently.
- **Error handling**: `CentralServerAuthError` is properly thrown on 401 responses and caught in `handleBreadthQuery()` (ChatParticipant.ts, lines 380–389) with a user-friendly message directing them to set the server token.
- **Token safety**: The `x-docuvia-token` header is only set when a token exists (line 55–57). No risk of sending `"undefined"` or `"null"` strings.
- **Consistent patterns**: All HTTP methods follow the same pattern: check URL → get token → build headers → fetch → check status → return/throw.

### Security Findings

1. **No HTTPS enforcement** (Medium risk): `server_url` can be set to an `http://` URL. The `x-docuvia-token` header will be sent in cleartext. The `GlobalConfigSchema` uses `z.string().url()` which accepts both `http://` and `https://`. No `.startsWith('https://')` guard exists in the schema or in the client methods.
   - **File**: `CentralServerClient.ts`, lines 46, 60, 88, 99, 118, 129, 162, 171, 178, 190
   - **Recommendation**: Add an HTTPS enforcement check in `isServerConfigured()` or in the config schema.

2. **No request timeout** (Low risk): `fetch()` calls in `CentralServerClient` have no timeout configured. A hung server could cause the extension to hang indefinitely.
   - **File**: `CentralServerClient.ts`, lines 60, 99, 129, 171, 190
   - **Recommendation**: Use `AbortController` with a reasonable timeout (e.g., 30 seconds).

3. **No response size limit** (Low risk): `response.json()` is called without checking `Content-Type` or response size. A malicious server could return a very large response.
   - **File**: `CentralServerClient.ts`, lines 74, 138

### Code Smells

- **Duplicated HTTP boilerplate**: The pattern of building headers, making a fetch call, and checking response status is repeated 5 times in `CentralServerClient`. Consider extracting a private `_request()` helper method.
- **Silent error swallowing**: `_tickMetabolism()` (line 172) and `sendFeedback()` (line 195) silently catch all errors. While acceptable for non-critical operations, logging at debug level would aid troubleshooting.

## Round 3 — Integration & Completeness Review

### Integration Points

The graceful degradation logic integrates correctly with all major extension subsystems:

| Subsystem | Server Dependency | Degradation Behavior |
|-----------|-------------------|---------------------|
| KnowledgeGraphTreeProvider | Via KnowledgeStore | Shows local/git data when server unavailable |
| DocuviaCodeLensProvider | None (local only) | Works entirely from KnowledgeStore snapshots |
| DocuviaHoverProvider | None (local only) | Works entirely from KnowledgeStore + KnowledgeIndexer |
| ChatParticipant `/query` | Optional | Local search always works; breadth search degrades gracefully |
| ChatParticipant `/explore` | None | Uses local VS Code LM API |
| ChatParticipant `/extract` | None | Uses local VS Code LM API via TaskRunner |
| SearchResultsPanel | Via CentralServerClient | Only shown when server returns results |
| TaskRunner | None | Uses local VS Code LM API |
| KnowledgeIndexer | None | Indexes from local KnowledgeStore |

### Missing Tests

- No unit tests for `CentralServerClient.isServerConfigured()` returning false
- No unit tests for `CentralServerClient.query()` returning `[]` when no server URL
- No integration tests for the three-tier fallback chain in `KnowledgeStore._loadWorkspace()`
- No tests for `ChatParticipant.handleBreadthQuery()` when server is not configured

### Performance

- The three-tier fallback in `_loadWorkspace()` is sequential and blocking. If the server is configured but unreachable, the `pullSnapshot()` call will wait for the TCP timeout before falling back to local files. This could cause a noticeable delay (5–30 seconds depending on OS TCP timeout settings).
- **Recommendation**: Add a short timeout (e.g., 5 seconds) to the server API call, or attempt local fallback concurrently.

### Resource Leak

- The heartbeat timeout (`_heartbeatTimeout`) is started in `extension.ts` (line 46) but never cleared on deactivation. This was also noted in the 1.4.1 verification report. While not critical (the extension host is shutting down), it's untidy.

## Overall Verdict

**✅ PASS**

The graceful degradation fallback logic is correctly implemented and aligns with the ADR-002 design specification. The three-tier fallback chain (Server API → Local YAML → Git orphan branch) in `KnowledgeStore._loadWorkspace()` is complete and well-structured. The `CentralServerClient` methods correctly handle the absence of a server configuration. The `ChatParticipant` properly routes queries between local and server paths.

The findings are minor (no HTTPS enforcement, no request timeout, no tests) and do not block the feature from functioning as designed. The architecture is sound and the degradation behavior is correct.
