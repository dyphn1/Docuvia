## Round 1 — Architecture & Design Review

### Does the design document correctly describe the feature?

The design spec in `init-project.md` describes a 4-step flow: **Workspace Resolution → Project Naming → Scaffolding → Post-Initialization**. The implementation follows this flow closely:

1. ✅ **Workspace Resolution** (lines 418–446 of `extension.ts`): Correctly handles single-root, multi-root (QuickPick of uninitialized folders), and TreeView inline action (node.workspaceRoot) paths.
2. ✅ **Project Naming** (lines 463–472): Uses `showInputBox` with prefill from `path.basename(targetRoot)` and validation against empty names (BUG G-1 fix).
3. ✅ **Scaffolding** (lines 474–499): Creates `.docuvia/` and `.docuvia/l3_decisions/` directories, writes `l1_tags.yaml`, `l2_modules.yaml`, and `l3_router.yaml` skeleton files.
4. ✅ **Post-Initialization** (lines 501–506): Calls `store.load()` and shows success information message.

### Gaps between design spec and implementation

1. **Force-Overwrite Prompt — IMPLEMENTED (spec was outdated)**: The design spec at `init-project.md` line 51 still states "⚠️ CONFLICT – Force-Overwrite Prompt Not Implemented". However, the current implementation **does** include the force-overwrite prompt (lines 451–460). When `isAlreadyInitialized` is true, it shows a `showWarningMessage` with 'Overwrite'/'Cancel' buttons, and uses unconditional `writeFile` instead of `writeIfAbsent`. The spec's conflict note is **stale** and should be updated.

2. **`projectName` written to `l1_tags.yaml`**: The design spec for `init-project.md` states the skeleton includes `project_name` key. The implementation at line 488 correctly writes `project_name: "${projectName}"` in the YAML. However, ADR-001 mentions generating a `_project_profile.yaml` (Cognitive Snapshot) — this file is **never created** by `initProject`. Missing feature.

3. **Deterministic Recon / Feature Sniffing**: ADR-001 describes steps 2–3: "Deterministic Recon (Read .gitignore, package.json)" and "Unknown Framework Defense". The `initProject` command does **none of this** — it only creates skeleton files. The AI-driven architecture analysis is delegated to the `/explore` chat command (`docuvia.startExplore`), which is a separate flow. This means the "Zero to One in 1 minute" experience described in ADR-001 actually requires the user to run **two commands**: `initProject` first, then `/explore`. The ADR implies it should be a single flow.

4. **`manifest.yaml` not created**: The `KnowledgeStore._loadWorkspace()` reads `manifest.yaml` at line 131-132, but `initProject` does **not** create a `manifest.yaml` skeleton. After `initProject`, `KnowledgeStore` will fail to find `manifest.yaml`, fall back to `parseManifest('', ...)`, and get `ManifestSchema.parse({})` which defaults to `{ project_id: undefined, modules: [] }`. This works but means `project_id` is never set locally, preventing server sync until the user manually creates `manifest.yaml`.

5. **`.snapshot-ref` file missing**: Item 2.2.3 in the roadmap mentions `.docuvia/ directory creation with manifest.yaml, config.yaml, .snapshot-ref`. The `initProject` function does not create `config.yaml` or `.snapshot-ref`. These appear to be planned but not yet implemented.

### Contradictions between design documents

- The `init-project.md` spec says "⚠️ CONFLICT – Force-Overwrite Prompt Not Implemented", but the code now **does** implement it (lines 451–460). The spec is stale.
- ADR-001's mermaid diagram shows `@docuvia /init` triggering the full Zero-to-One flow including LLM analysis. The actual `initProject` command is a pure scaffold creator with no AI component. The AI analysis is in `startExplore`/`/explore` — a completely separate command.

## Round 2 — Code Quality & Security Review

### Code Structure

1. ✅ **Guard Clauses / Early Returns**: The `initProject` function uses defensive design — early return for no workspace folders (line 419), cancellation (line 444), missing targetRoot (line 448), user cancel on overwrite (line 459), user cancel on name input (line 470). Good practice.

2. ✅ **Multi-Root Support**: Properly filters uninitialized folders for QuickPick (line 433). Already-initialized single-root workspaces trigger the overwrite prompt.

3. ✅ **Empty Name Validation**: BUG G-1 fix is implemented — `validateInput` on `showInputBox` and post-check on line 470.

4. ⚠️ **`writeIfAbsent` and `writeFile` branching logic** (lines 482–484): The `writeFile` variable is assigned as either `writeIfAbsent` or an anonymous overwrite function based on `isAlreadyInitialized`. This is clever but has a subtle issue: if the user chose "Overwrite" for a multi-root workspace, but `.docuvia/` already existed with some files and not others (partial initialization), the overwrite path would rewrite ALL skeleton files even for ones that may have been user-edited. The spec says "This action cannot be undone" so this is arguably correct, but there's no backup mechanism.

5. ⚠️ **No `_context` parameter usage**: The `initProject` function takes `_context: vscode.ExtensionContext` but never uses it. The underscore prefix indicates this is intentional, but it could be needed for future features (e.g., storing initialization state in `context.globalState`).

### Security

1. ⚠️ **YAML injection via `projectName`**: At line 488, the `projectName` is interpolated directly into YAML: `project_name: "${projectName}"`. If a user enters a name containing YAML special characters (e.g., `"test": [1,2,3]` or multi-line strings), it could break the YAML structure or cause unintended parsing. The double-quote wrapping provides some protection, but a truly malicious input like `foo"\ntags:\n  - id: evil` would break out of the string. **Recommendation**: Use a YAML library (`yaml` package is already imported in the project) to properly serialize the `project_name` value.

2. ✅ **No remote data exposure**: The command only writes to the local filesystem within the workspace root.

3. ✅ **`vscode.workspace.fs` API**: Uses VS Code's file system API rather than raw `fs`, which respects workspace permissions and virtual file systems.

### Code Smells

1. ⚠️ **`node` parameter typed as `any`** (line 417): The `node` parameter in `initProject` is typed as `any`. Should be typed as `KGNode | undefined` for type safety.

2. ✅ **Consistent use of `void` prefix**: Fire-and-forget `showInformationMessage` calls correctly use `void` prefix (line 504).

3. ⚠️ **Hard-coded skeleton templates**: The YAML skeleton strings (lines 487–498) are hard-coded as template literals. If skeleton format changes, these strings must be updated in multiple places. Consider extracting to a shared `skeletons.ts` module.

### Error Handling

1. ⚠️ **No error handling around `createDirectory` / `writeFile`**: The `vscode.workspace.fs.createDirectory()` and `writeFile()` calls (lines 478–499) have no try-catch. If the filesystem is read-only or there's a permissions issue, the error will propagate as an unhandled promise rejection. VS Code will show a generic error, but the user may not understand what happened. **Recommendation**: Wrap the scaffolding block in a try-catch and show a descriptive error message.

2. ✅ **`store.load()` failure is graceful**: The `store.load()` call at line 502 returns a boolean; if it fails, the success message still shows but the store won't be populated.

## Round 3 — Integration & Completeness Review

### Integration with other system components

1. ✅ **KnowledgeStore reload**: `store.load()` is called after scaffolding (line 502), which triggers `onDidLoad` event → `KnowledgeGraphTreeProvider.refresh()`. The UI updates correctly.

2. ✅ **`docuvia:isInitialized` context**: `store.load()` calls `setContext('docuvia:isInitialized', anyLoaded)` (KnowledgeStore.ts line 108), which hides the Welcome View after initialization. This integrates correctly with the `viewsWelcome` contribution in `package.json` (line 121: `when: "!docuvia:isInitialized"`).

3. ✅ **FileSystemWatcher**: The watcher is already started (extension.ts line 51), so any file changes from `initProject` will also trigger a debounced reload. However, since `store.load()` is called explicitly at line 502, the watcher's reload would be redundant but harmless (debounced at 300ms).

4. ⚠️ **`parseTags` compatibility**: The `parser.ts::parseTags` function (lines 18–34) correctly handles the object format `{ project_name, tags }` generated by `initProject`. This was previously a critical bug (noted in the spec), but the current implementation at lines 20–25 checks `Array.isArray(raw)` and falls back to `(raw as any)?.tags`. ✅ **This bug is FIXED.**

5. ⚠️ **`addDecision` after `initProject`**: If a user runs `initProject` and immediately tries `addDecision`, the `snapshot.modules` will be empty (skeleton `l2_modules.yaml` has no entries). The `addDecision` command handles this by including a "Create new module later..." option (line 572). This is acceptable UX but not ideal — the user has no modules to assign decisions to.

6. ❌ **`manifest.yaml` not scaffolded**: As noted in Round 1, `initProject` does not create `manifest.yaml`. The `KnowledgeStore._loadWorkspace()` always reads this file (line 131). While it gracefully handles its absence (`parseManifest` defaults), this means `project_id` is never set locally, preventing the server-augmented path from ever being used unless the user manually creates the file.

### Missing Tests

1. ⚠️ **Phase 1 test is incomplete**: `phase1.test.ts` has a basic test that executes `docuvia.initProject` (line 36), but:
   - It will **hang** because `showInputBox` and `showQuickPick` require user interaction that cannot be provided in automated tests without mocking.
   - It only checks for `.docuvia` and `l1_tags.yaml` existence — doesn't verify `l2_modules.yaml`, `l3_router.yaml`, or `l3_decisions/` directory.
   - The test comment acknowledges this: "the command palette flow requires user interaction."
   
2. ❌ **No unit tests for `initProject` logic**: The function cannot be unit-tested in isolation because it's a private function in `extension.ts` and depends heavily on `vscode.window` APIs. There are no extraction tests for the branching logic (overwrite vs. new, multi-root filtering, etc.).

3. ❌ **No integration test for the full onboarding flow**: There's no test that covers `initProject` → `store.load()` → TreeView refresh → Welcome View hidden.

### Performance

1. ✅ **No performance concerns**: The operation is purely file I/O — creating 2 directories and writing 3 small YAML files. Performance is not an issue.

### End-to-End Usability

1. ⚠️ **Two-step onboarding**: As noted in Round 1, the ADR-001 describes a single "Zero to One" experience, but in practice the user must run `initProject` manually and then `/explore` separately. The `viewsWelcome` in `package.json` (line 120) only shows a button for `docuvia.startExplore` ("Analyze Project Architecture"), **not** `docuvia.initProject`. This means new users hitting the Knowledge Graph view will trigger `/explore`, which calls `acceptL1Tags` (which creates `.docuvia/` via a different code path at lines 296–324). There are **two competing initialization paths**: `initProject` (manual) and `acceptL1Tags` (via `/explore`). This could cause confusion.

2. ⚠️ **Competing init paths divergence**: The `acceptL1Tags` command (lines 286–324) creates `.docuvia/` differently from `initProject`:
   - `acceptL1Tags` writes `l1_tags.yaml` from LLM-provided content, but uses `writeIfAbsent` for `l2_modules.yaml` and `l3_router.yaml` (always).
   - `initProject` writes `l1_tags.yaml` from a skeleton template, and uses `writeIfAbsent` or overwrite depending on `isAlreadyInitialized`.
   - Neither creates `manifest.yaml`.

## Overall Verdict

### ⚠️ WARN

The `docuvia.initProject` command is **functional and correctly implements the core scaffolding flow** (workspace resolution, project naming, `.docuvia/` creation, skeleton files, post-init reload). Several previously identified bugs have been fixed (BUG G-1 empty name validation, force-overwrite prompt, `parseTags` object format bug).

However, there are significant gaps that prevent this from being a complete "Zero-to-One" onboarding experience:

1. **Missing `manifest.yaml`** creation blocks the server-augmented path.
2. **YAML injection risk** from unsanitized `projectName` interpolation.
3. **Competing initialization paths** (`initProject` vs `acceptL1Tags` via `/explore`) may confuse users.
4. **Design spec is stale** — documents bugs/features that have been fixed.
5. **E2E tests are incomplete** — the phase 1 test will hang in CI.

The feature works for the happy path (new workspace, single root, normal project name) but needs hardening for edge cases and consistency with the broader onboarding design intent from ADR-001.
