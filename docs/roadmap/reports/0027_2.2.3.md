## Round 1 — Architecture & Design Review

### What the checklist item requires

Item 2.2.3 states: `.docuvia/ directory creation with manifest.yaml, config.yaml, .snapshot-ref`. This breaks down into four sub-requirements:

1. **`.docuvia/` directory creation** — Creating the root Docuvia directory inside the workspace.
2. **`manifest.yaml`** — A manifest file inside `.docuvia/` that describes the project's modules and server-side project ID.
3. **`config.yaml`** — A configuration file. Note: the design uses `config.yaml` at the **global** level (`~/.docuvia/config.yaml`), not per-project inside `.docuvia/`. This may be a naming ambiguity in the checklist.
4. **`.snapshot-ref`** — A file that presumably stores a reference/snapshot pointer for the knowledge graph, possibly related to the orphan branch or the cognitive snapshot (`_project_profile.yaml` mentioned in ADR-001).

### Analysis of implementation vs. design

#### `.docuvia/` directory creation — ✅ Implemented

The `initProject()` function in `extension.ts` (lines 474-479) creates the `.docuvia/` directory and its `l3_decisions` subdirectory:

```ts
const docuviaUri = vscode.Uri.file(path.join(targetRoot, '.docuvia'));
const decisionsUri = vscode.Uri.file(path.join(targetRoot, '.docuvia', 'l3_decisions'));
await vscode.workspace.fs.createDirectory(docuviaUri);
await vscode.workspace.fs.createDirectory(decisionsUri);
```

The `acceptL1Tags` command handler (line 300-301) also creates `.docuvia/` when writing L1 tags from the ChatParticipant.

#### `manifest.yaml` — ❌ NOT created by initProject

This is a **critical gap**. The `KnowledgeStore.ts` **reads** `manifest.yaml` on every `load()` call (line 131):

```ts
const manifestContent = await this.readUriSafe(vscode.Uri.joinPath(docuviaDir, MANIFEST_FILE));
const manifest = parseManifest(manifestContent, `${DOCUVIA_DIR}/${MANIFEST_FILE}`);
```

The `ManifestSchema` in `types.ts` is well-defined with `project_id` and `modules` fields. However, **no code path in `initProject()` or `acceptL1Tags` creates `manifest.yaml`**. The `initProject()` function only creates:

- `l1_tags.yaml`
- `l2_modules.yaml`
- `l3_router.yaml`
- `l3_decisions/` (empty directory)

Since `readUriSafe()` returns an empty string on file-not-found, and `parseManifest()` returns `{ project_id: undefined, modules: [] }` for empty input, the system degrades gracefully but the manifest is never initialized. This means:

- `manifest.project_id` is always `undefined` → the server-augmented and git-fallback code paths in `KnowledgeStore._loadWorkspace()` (lines 141 and 189) are **never reached** for projects initialized via `initProject`.
- `manifestModules` is always empty → offline CodeLens matching has no path patterns.
- For these features to work, users must **manually create** `manifest.yaml`, which is not documented or prompted.

#### `config.yaml` — ⚠️ Ambiguous / Partially Implemented

There are **two** different `config.yaml` concepts in the codebase:

1. **Global config** at `~/.docuvia/config.yaml` (read in `extension.ts` line 29): This is implemented. `GlobalConfigSchema` defines `server_url`, `chunking_strategy`, and `telemetry`. However, **no code creates this file** — it must be manually created by the user. If absent, the system continues with defaults.

2. **Per-workspace config** inside `.docuvia/config.yaml`: This is **not implemented** anywhere. No code reads or writes this file. The design docs (ADR-001) mention writing to `.docuvia/l1_tags.yaml` and `.docuvia/manifest.yaml`, but do not explicitly define a per-project `config.yaml`.

If the checklist item refers to the global `~/.docuvia/config.yaml`, it is read but never auto-created. If it refers to a per-project config, it is entirely unimplemented.

#### `.snapshot-ref` — ❌ NOT Implemented

No code in the entire `vscode-client` source references `.snapshot-ref`. The ADR-001 mentions `_project_profile.yaml` as a "cognitive snapshot" capturing topology information, but this file is also **never created** by any code path. The `KnowledgeStore` does not read or write any `.snapshot-ref` file.

### Design gaps

- The `init-project.md` design doc (line 21) lists only `l1_tags.yaml`, `l2_modules.yaml`, `l3_router.yaml` as scaffold files. It makes no mention of `manifest.yaml` or `.snapshot-ref`.
- ADR-001 mentions `_project_profile.yaml` but this is not implemented and does not match the `.snapshot-ref` naming.
- There is a disconnect between the `ManifestSchema` + `KnowledgeStore` reading logic (which expects `manifest.yaml`) and the `initProject` write logic (which never creates it).

## Round 2 — Code Quality & Security Review

### Code structure

- The `initProject()` function is well-structured with proper workspace resolution, multi-root handling, and input validation (BUG G-1 fix: validates non-empty project name).
- The overwrite logic (lines 450-460) properly handles re-initialization with a destructive warning prompt.
- The `writeIfAbsent` helper (line 694) follows defensive design by checking file existence before writing.

### Security concerns

- **Project name injection**: The `projectName` is interpolated into YAML content via template literal (line 488). If a user enters a project name containing YAML special characters (e.g., `"`, `:`, `#`, multiline), the generated `l1_tags.yaml` could be malformed or have unintended semantics. The input is validated for emptiness but **not sanitized for YAML safety**.
- No path traversal risk: `targetRoot` always comes from `vscode.workspace.workspaceFolders`, not user input.

### Code smells

- The `initProject()` function has clearly evolved through bug fixes (BUG G-1, comments referencing Round 2 changes), but the code is still readable and not excessively long.
- The manifest being read but never written is a conceptual code smell — the `KnowledgeStore` has sophisticated logic for server fallback and git fallback based on `manifest.project_id`, but this logic is effectively dead code for any user who only uses `initProject`.

### Error handling

- `writeIfAbsent` silently skips existing files — no logging to indicate this happened.
- The `acceptL1Tags` command creates `.docuvia/` and `l3_decisions/` but does not create `manifest.yaml`, `l3_router.yaml` skeleton (it does via `writeIfAbsent` for some files), which could lead to an inconsistent state.

## Round 3 — Integration & Completeness Review

### Integration issues

1. **Broken server-augmented path**: Because `manifest.yaml` is never created, `manifest.project_id` is always `undefined`, so the server-augmented loading path (`KnowledgeStore._loadWorkspace()` line 141) and the git-fallback path (line 189) are **never activated** for projects initialized via the standard flow. This means the `CentralServerClient.pullSnapshot()` and the `_loadFromGit()` method are effectively dead code in the standard onboarding flow.

2. **Offline CodeLens**: `DocuviaCodeLensProvider.ts` uses `snapshot.manifestModules` for offline matching (line 134). Since `manifest.yaml` is never created, `manifestModules` is always empty, making offline CodeLens matching non-functional.

3. **`acceptL1Tags` creates a different set of files than `initProject`**: The `acceptL1Tags` handler (line 286-325) creates `.docuvia/`, `l3_decisions/`, `l1_tags.yaml`, `l2_modules.yaml`, and `l3_router.yaml` — but `initProject` creates the same set. Both lack `manifest.yaml`. The two code paths for `.docuvia/` creation are duplicated logic.

### Missing tests

- The `initProject` command has a basic test reference (`phase1.test.ts` line 36: `vscode.commands.executeCommand('docuvia.initProject')`), but no test verifies what files are actually created, or that `manifest.yaml` and `.snapshot-ref` are missing.
- No integration test validates the full end-to-end onboarding flow.

### Performance concerns

- None significant for this item. Directory/file creation is I/O-bound and straightforward.

### End-to-end usability

- A user running `docuvia.initProject` gets a partially initialized project. The `.docuvia/` directory contains YAML skeleton files but is missing the manifest that `KnowledgeStore` expects. The system silently degrades to local-only mode with no warning.
- If the user connects to a server and creates a project, there is no automated flow to write `project_id` into `manifest.yaml` — this would require manual intervention.
- The success message ("Populate the YAML files to build your knowledge graph.") does not mention `manifest.yaml` or `.snapshot-ref` as files the user should create.

## Findings

| # | Severity | Finding | Recommendation |
|---|----------|---------|----------------|
| 1 | **Critical** | `manifest.yaml` is never created by `initProject()` or `acceptL1Tags`, yet `KnowledgeStore.load()` reads it and uses `project_id` for server/git fallback paths. | Add `manifest.yaml` creation to `initProject()` with a default skeleton: `project_id: ~\nmodules: []`. Also add it to `acceptL1Tags`. |
| 2 | **Critical** | `.snapshot-ref` does not exist in the codebase at all. No code reads or writes it. | Implement `.snapshot-ref` (or `_project_profile.yaml` per ADR-001) creation during `initProject()`, storing a topology fingerprint for future O(1) lookups. |
| 3 | **High** | Server-augmented and git-fallback loading paths are dead code for projects initialized via `initProject` because `manifest.project_id` is always `undefined`. | Once `manifest.yaml` is created, implement a flow that writes `project_id` to manifest when a server project is created (e.g., after first ingest). |
| 4 | **Medium** | `config.yaml` at the global level (`~/.docuvia/config.yaml`) is never auto-created. Users must manually create it to configure `server_url`. | Auto-create `~/.docuvia/config.yaml` with default values during first extension activation, or provide a "Configure Server" command that writes it. |
| 5 | **Medium** | YAML injection risk: `projectName` is interpolated into YAML template without sanitization. | Use a YAML library (`yaml.stringify()`) to generate the file or sanitize the project name for YAML-safe characters. |
| 6 | **Medium** | Duplicated `.docuvia/` file creation logic in both `initProject()` and `acceptL1Tags` handler. | Extract a shared `scaffoldDocuviaDir(workspaceRoot, projectName)` function. |
| 7 | **Low** | Offline CodeLens matching is non-functional because `manifestModules` is always empty (no `manifest.yaml` with modules). | Document this limitation or add a UI hint prompting users to add modules to `manifest.yaml`. |
| 8 | **Low** | No test coverage for verifying which files `initProject` creates. | Add integration test that asserts the expected file set after `initProject` runs. |

## Overall Verdict

⚠️ **WARN**

The `.docuvia/` directory is successfully created by `initProject()` with skeleton YAML files (`l1_tags.yaml`, `l2_modules.yaml`, `l3_router.yaml`, and the `l3_decisions/` directory). However, two of the three named files in the checklist item are **not implemented at all**:

- **`manifest.yaml`** — Not created by any initialization code path, despite being read by `KnowledgeStore` and being critical for server-augmented and git-fallback load paths. This is a functional gap that silently breaks key features.
- **`.snapshot-ref`** — Does not exist anywhere in the codebase. No code reads or writes this file.

The `config.yaml` aspect is ambiguous (global vs. per-project) but at minimum the global config is never auto-created.

The core directory creation works, but the item is incomplete per its specification. Marking as ⚠️ WARN rather than ❌ FAIL because the basic `.docuvia/` directory creation is functional and the system degrades gracefully (no crashes), but the missing `manifest.yaml` and `.snapshot-ref` are significant functional gaps.
