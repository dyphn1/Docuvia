## Round 1 — Architecture & Design Review

### Design Intent

Item 2.3.1 requires that `TaskRunner` correctly operates within the context of the appropriate workspace root in a multi-root workspace setup. The VS Code extension should scope all file I/O, knowledge graph updates, and task operations to the correct workspace folder when multiple folders are open.

### Findings

**✅ Multi-root architecture is correctly implemented:**

1. **KnowledgeStore multi-root map** (`KnowledgeStore.ts:42`): The `_snapshots: Map<string, KnowledgeGraphSnapshot>` is keyed by workspace root path. The `load()` method (line 93) iterates over all `vscode.workspace.workspaceFolders` and loads each independently.

2. **TaskRunner workspace resolution** (`TaskRunner.ts:294`): In `runExtractionAsync`, the workspace root is resolved dynamically via:
   ```typescript
   const workspaceRoot = vscode.workspace.getWorkspaceFolder(vscode.Uri.file(params.sourceFilePath))?.uri.fsPath;
   ```
   This correctly maps any file path to its containing workspace folder, even in multi-root setups.

3. **Auto-categorization scoping** (`TaskRunner.ts:59-76`): `queueAutoCategorization` accepts an explicit `workspaceRoot` parameter, which is passed from the caller in `extension.ts:136`:
   ```typescript
   await taskRunner.queueAutoCategorization(node.workspaceRoot, unassignedNodes);
   ```
   The `node.workspaceRoot` comes from the `KGNode` which is always scoped to a specific workspace.

4. **KnowledgeGraphTreeProvider scoping** (`KnowledgeGraphTreeProvider.ts:154-178`): The root level creates one project node per workspace folder, each with `workspaceRoot` set. All child nodes (l1tag, l2module, l3entry, unassigned-group) carry the `workspaceRoot` property, ensuring per-workspace isolation.

5. **FileSystemWatcher per workspace** (`KnowledgeStore.ts:351-391`): `startWatcher` creates a separate `FileSystemWatcher` for `.docuvia/**` in each workspace folder, with `vscode.workspace.onDidChangeWorkspaceFolders` handling dynamic folder addition/removal.

6. **Snapshot lookup by URI** (`KnowledgeStore.ts:68-76`): `getSnapshotFor(uri)` correctly resolves any file URI to its parent workspace folder and returns the appropriate snapshot.

**✅ No design gaps found.** The architecture correctly supports multi-root workspace scoping throughout the TaskRunner and related components.

## Round 2 — Code Quality & Security Review

### Findings

**⚠ Minor issues identified:**

1. **Redundant null check** (`TaskRunner.ts:349`): In `writeExtractionResults`, there is a redundant `if (!workspaceRoot) return;` check at line 349, even though `workspaceRoot` is already used unconditionally at line 343 (`path.join(workspaceRoot, ...)`). If `workspaceRoot` were undefined, the code would have already thrown at line 343. This is a minor code smell — the guard should be at the top of the function, or removed entirely since the caller already resolves it.

2. **Error message quality** (`TaskRunner.ts:164, 286, 306`): Error messages use `String(err)` which loses stack trace information. For debugging purposes in the output channel, it would be better to use `err instanceof Error ? err.message : String(err)` and optionally log `err.stack` at debug level.

3. **No content size validation in TaskRunner** (`TaskRunner.ts:39`): The `queueExtraction` method does not validate the `content` parameter size. While the caller in `extension.ts:224-232` checks file size before calling, other callers (e.g., `ChatParticipant.ts:484`) do not perform the same check. A defensive size limit within `TaskRunner` itself would be prudent.

4. **Prompt injection protection** (`TaskRunner.ts:318-328`): The `processChunk` method correctly wraps user code in `<code_chunk>` tags and instructs the LM to ignore instructions within them. This is a good security practice.

5. **Cancellation token lifecycle** (`TaskRunner.ts:236-308`): The `runExtractionAsync` method correctly checks `params.token.isCancellationRequested` at the start of each chunk iteration (line 263), allowing cooperative cancellation. However, the `CancellationToken` is created in `extension.ts:235` and disposed via `.finally()` at line 241, which means the token could be disposed before the async extraction completes. This is acceptable since a disposed token simply reports `isCancellationRequested` as true, but it's worth noting.

**✅ Positive observations:**
- Clean separation of concerns: TaskRunner handles orchestration, KnowledgeStore handles data, TreeProvider handles UI
- Consistent use of `void` for fire-and-forget async calls (lines 54, 73)
- Good error isolation: chunk processing errors don't abort the entire extraction (line 289)

## Round 3 — Integration & Completeness Review

### Findings

**✅ Integration is correct:**

1. **Extension → TaskRunner → KnowledgeStore flow**: The `docuvia.runExtraction` command in `extension.ts:185-246` correctly resolves the workspace folder, reads the file, and passes the file path to `TaskRunner.queueExtraction`. TaskRunner then resolves the workspace root from the file path and writes results to the correct `.docuvia/` directory.

2. **ChatParticipant → TaskRunner flow**: `ChatParticipant.ts:393-497` (`handleExtract`) resolves the workspace root via `vscode.workspace.getWorkspaceFolder()` at line 427 and passes file paths to TaskRunner. For directory extraction, it correctly computes `relativePath` using the workspace root for pattern matching.

3. **Auto-categorization flow**: The `docuvia.autoCategorizeDecisions` command in `extension.ts:132-143` passes `node.workspaceRoot` from the tree node to `taskRunner.queueAutoCategorization`, ensuring the correct snapshot is used.

4. **Store reload after writes**: Both `writeExtractionResults` (TaskRunner.ts:299) and `applyAutoCategorization` (TaskRunner.ts:232) call `await this.store.load()` after writing files, ensuring the in-memory state is synchronized. Note: this triggers a full reload rather than an incremental update, which is consistent with the known design debt documented in `store.md`.

5. **Multi-root isolation**: Each workspace's `.docuvia/` directory is independent. The `l3_decisions/`, `l1_tags.yaml`, `l2_modules.yaml`, and `l3_router.yaml` files are all written within the correct workspace root.

**✅ No missing pieces for 2.3.1.** The dynamic root scoping is fully implemented and functional.

## Overall Verdict

**✅ PASS**

The TaskRunner dynamic root scoping (item 2.3.1) is correctly and completely implemented. The TaskRunner resolves workspace roots dynamically from file paths using `vscode.workspace.getWorkspaceFolder()`, and all file I/O is scoped to the correct workspace folder. The multi-root architecture is consistently applied across KnowledgeStore, KnowledgeGraphTreeProvider, ChatParticipant, and extension.ts. Minor code quality issues (redundant null check, error message formatting, missing defensive size check) are low severity and do not affect correctness.
