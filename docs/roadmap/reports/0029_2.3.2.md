## Round 1 — Architecture & Design Review

### 1.1 Design spec alignment

The design documents clearly specify per-workspace `.docuvia/` isolation:

- **`store.md`** defines a `Map<string, KnowledgeGraphSnapshot>` keyed by `workspaceRoot` paths — **implemented exactly as specified** (line 42: `private _snapshots: Map<string, KnowledgeGraphSnapshot> = new Map()`).
- **`nodes.md`** specifies that all tree nodes carry a `workspaceRoot` property — **confirmed in implementation**: `KGNode.workspaceRoot` (line 15 of `KnowledgeGraphTreeProvider.ts`) is propagated from project nodes through L1, L2, and L3 children.
- **`nodes.md`** specifies per-workspace `FileSystemWatcher` — **implemented** at `KnowledgeStore.ts:351-391`, with a watcher created per workspace folder and `onDidChangeWorkspaceFolders` handling dynamic folder addition/removal.
- **`12-glossary.md`** defines `.docuvia/` as a per-workspace directory — all file operations (`initProject`, `addDecision`, `acceptL1Tags`, `writeExtractionResults`) construct paths as `path.join(workspaceRoot, '.docuvia', ...)` which is correct.

### 1.2 Gaps between design and implementation

- **Design doc conflict in `store.md` line 23**: The design doc states "_CONFLICT – Debounce and Incremental Update Not Implemented: The current `KnowledgeStore.startWatcher()` implementation calls `void this.load()` **immediately** on every event_". **This conflict is now RESOLVED** — the current implementation (lines 367-388) includes proper debounce (300ms), batch collection (`pendingChanges` Set), and threshold-based incremental/full reload logic in `_handleBatchedChanges()`. The design doc is stale and should be updated.
- **Design doc conflict in `nodes.md` line 55**: States the `unassigned-group` node is "absent from `KnowledgeGraphTreeProvider.ts`". **This conflict is now RESOLVED** — lines 203-214 in the current implementation create an `unassigned-group` node when unassigned decisions exist, and lines 231-245 render them as L3 entries. The design doc is stale.

### 1.3 Contradictions between design documents

No contradictions found. The arc42 sections (05, 12), the design docs (store.md, nodes.md), and ADR-001 are consistent in their description of per-workspace isolation. The only issues are stale conflict notes in the design docs (see above).

## Round 2 — Code Quality & Security Review

### 2.1 Code structure & patterns

**Overall**: Well-structured code following the project's MVC/POP patterns. KnowledgeStore acts as the Model, providers as View, and commands/TaskRunner as Controller.

**Positives**:
- Clean separation: `KnowledgeStore` is the single source of truth with a proper singleton pattern (lines 40-62).
- Defensive design: `getSnapshotFor` returns `undefined` on failure (line 75), all consumers check for `undefined`.
- POP pattern: `IDocuviaClient` interface (lines 15-18) decouples KnowledgeStore from CentralServerClient implementation.
- Proper disposal: `dispose()` cleans up watchers and resets singleton (lines 441-448).
- Loading guard: `_loading`/`_pendingReload` prevents concurrent loads (lines 94-117).

### 2.2 Security considerations

- **No injection risk**: `.docuvia/` paths are always constructed via `path.join(workspaceRoot, '.docuvia', ...)` where `workspaceRoot` comes from `vscode.workspace.workspaceFolders` — trusted VS Code API.
- **No arbitrary path traversal**: The ChatParticipant's `/extract` command resolves workspace via `vscode.workspace.getWorkspaceFolder`, not from user input.
- **Git command safety**: `_loadFromGit` uses template literals with `GIT_KNOWLEDGE_BRANCH` and numeric `projectId` — no user-controlled injection point for git commands.

### 2.3 Code smells & concerns

1. **Minor: `load()` clears all snapshots** (line 100): `this._snapshots.clear()` is called at the start of every `load()`. For a multi-root workspace where only one workspace changed, this causes a full re-read of **all** workspaces. The incremental path (`_loadWorkspace`) is only triggered via the watcher, not from command-triggered reloads like `initProject` → `store.load()` (line 502) or `addDecision` → `store.load()` (line 628). This is a performance smell but not a correctness bug — functionally, isolation is maintained.

2. **Minor: `handleDrop` cross-workspace guard**: Line 53 checks `n.workspaceRoot === target.workspaceRoot`, which correctly prevents cross-workspace drag-and-drop. Good.

3. **Minor: `showDecisionsForLens` aggregates across workspaces** (lines 645-649 in extension.ts): This function iterates `store.snapshots.values()` and merges all decisions into a single map. Since `decisionId` is a UUID, there's no collision risk, but this is slightly inconsistent with the "per-workspace isolation" principle. Since it's a display-only read path for CodeLens clicks, this is acceptable.

4. **Minor: `_handleBatchedChanges` incremental reload only updates one workspace** (line 429: `void this._loadWorkspace(workspaceRoot)`), but the full reload path (line 437: `void this.load()`) reloads ALL workspaces. The threshold logic could be improved to do a full reload of just the affected workspace instead of all.

### 2.4 Error handling

- File-not-found conditions are handled with try/catch returning `false` or empty (e.g., `_loadWorkspace` line 124, `readUriSafe` line 458).
- `_loadWorkspace` has a three-tier fallback: server API → local `.docuvia/` files → git orphan branch. Each tier catches errors and falls through gracefully.
- Parser failures are caught by `tryParse` (line 463) which logs and returns `[]`.

## Findings

### Issues

(None — the feature is fully implemented and working correctly.)

### Gaps

1. **No multi-root isolation regression test**: There is no automated test verifying that data in one workspace's `.docuvia/` doesn't leak into another. **Recommendation**: Add a test case in `phase1.test.ts` or `phase2.spec.ts` that sets up a multi-root workspace with two folders, initializes both, and verifies `store.getSnapshotFor(folderAUri).decisions` doesn't contain decisions from folder B.

2. **Stale conflict notes in design docs**: `store.md` line 23 and `nodes.md` line 55 contain conflict warnings about debounce and unassigned-group being unimplemented. Both are now implemented. **Recommendation**: Update these design docs to remove the stale conflict markers.

### Risks

1. **Full reload on command-triggered loads**: `initProject` → `store.load()` and `addDecision` → `store.load()` call `load()` which clears ALL snapshots and re-reads everything. In a workspace with 10+ folders and large knowledge graphs, this could cause a noticeable pause. The risk is low for typical usage (≤3 workspace folders) but could impact power users. **Mitigation**: Future optimization could add a `loadWorkspace(workspaceRoot)` overload that only reloads one workspace.

2. **`showDecisionsForLens` cross-workspace aggregation**: While functionally harmless (UUIDs prevent collisions), it slightly violates the isolation principle by merging decisions from all workspaces into a single lookup. This is acceptable for display but should be documented.

### Recommendations

1. Add a regression test for multi-root workspace isolation.
2. Update `store.md` to remove the stale debounce/incremental conflict warning.
3. Update `nodes.md` to remove the stale unassigned-group conflict warning.
4. (Low priority) Consider adding a single-workspace reload method to avoid full reload after command-triggered writes.

## Overall Verdict

✅ **PASS**

The per-workspace `.docuvia/` isolation is fully implemented and matches the design specification. The `KnowledgeStore` maintains a `Map<string, KnowledgeGraphSnapshot>` keyed by workspace root, all tree nodes carry `workspaceRoot` properties, `FileSystemWatcher` is created per workspace, and all commands/features correctly resolve and scope their operations to a single workspace. The only findings are minor performance considerations about full-reload triggers and stale documentation, neither of which affect the correctness or usability of the isolation feature.
