### Unassigned Group Implementation Details

The unassigned group is implemented at `KnowledgeGraphTreeProvider.ts` lines 202–214:

```typescript
const validModuleIds = new Set(snap.modules.map(m => m.id));
const hasUnassigned = [...snap.decisions.values()].some(
  d => d.l2_module_id === 'unassigned' || !validModuleIds.has(d.l2_module_id)
);
if (hasUnassigned) {
  tagChildren.push({
    kind: 'unassigned-group',
    id: '__unassigned__',
    label: 'Unassigned Decisions',
    workspaceRoot: node.workspaceRoot,
  });
}
```

This correctly:
1. Builds a set of valid L2 module IDs from the snapshot
2. Checks if any decision has `l2_module_id === 'unassigned'` (sentinel value) or references a non-existent module
3. Appends the unassigned group node **after** L1 tags, matching the design spec's "Virtual Level 1" placement

The unassigned group's children are resolved at lines 231–245, returning L3 entry nodes for all unassigned decisions.

The `getTreeItem()` method (lines 89–94) renders the unassigned group with:
- `vscode.ThemeIcon('question')` — matches the spec's `$(question)` icon
- `contextValue: 'unassigned-group'` — matches the spec exactly
- `TreeItemCollapsibleState.Collapsed` — correct default state

### Command Integration

The `docuvia.autoCategorizeDecisions` command (extension.ts lines 132–143) is registered and functional:
```typescript
vscode.commands.registerCommand('docuvia.autoCategorizeDecisions', async (node?: KGNode) => {
  if (node && node.workspaceRoot) {
    const unassignedNodes = kgProvider.getChildren(node);
    if (unassignedNodes.length > 0) {
      await taskRunner.queueAutoCategorization(node.workspaceRoot, unassignedNodes);
      vscode.commands.executeCommand('docuvia.taskQueue.focus');
    } else {
      vscode.window.showInformationMessage('No unassigned decisions to categorize.');
    }
  }
});
```

This correctly calls `kgProvider.getChildren(node)` on the unassigned-group node to get the list of unassigned L3 entries, then passes them to `TaskRunner.queueAutoCategorization()`.

## Round 2 — Code Quality & Security Review

### Code Quality

- **Defensive design**: The `hasUnassigned` check uses `Set.has()` for O(1) module ID lookups. The spread `[...snap.decisions.values()]` is safe.
- **Switch/case pattern**: `getTreeItem()` uses a clean switch on `node.kind` with exhaustive handling of all 6 kinds. TypeScript's exhaustiveness checking would catch any missing kind.
- **Drag-and-drop**: The `handleDrop` method (lines 44–81) correctly filters for `l3entry` nodes and updates `l3_router.yaml` with the new `l2_module_id`. Error handling is present (try/catch with console.error).
- **Separation of concerns**: The TreeProvider only handles tree rendering; data loading is delegated to KnowledgeStore.

### Security

No security concerns specific to this TreeView component. All data comes from local `.docuvia/` YAML files parsed by the KnowledgeStore. No network calls or user-controlled code execution.

### Code Smells

1. **Hardcoded sentinel value `'unassigned'`**: The string `'unassigned'` is used as a sentinel for unassigned decisions in both `KnowledgeGraphTreeProvider` (line 205) and `TaskRunner` (line 107 in `unassignedNodes` filtering). This is not defined as a constant. If changed in one place, it could be missed in another.
   - **File**: `KnowledgeGraphTreeProvider.ts`, line 205
   - **Recommendation**: Define a shared constant like `UNASSIGNED_MODULE_ID = 'unassigned'` in a shared constants file or in `types.ts`.

2. **Hardcoded node ID `'__unassigned__'`**: The unassigned group node uses a hardcoded ID. This is acceptable for a singleton virtual node but could collide if the ID format is ever used for real data.
   - **File**: `KnowledgeGraphTreeProvider.ts`, line 210
   - **Risk**: Low — the double-underscore prefix is a clear sentinel pattern.

3. **No null check on `snap.decisions`**: The code assumes `snap.decisions` is always a `Map`. If the snapshot is somehow corrupted, `[...snap.decisions.values()]` would throw. In practice, the KnowledgeStore always initializes this as a Map.
   - **Risk**: Very low — defensive but not critical.

### Performance

- The `hasUnassigned` check iterates all decisions in the snapshot. For large knowledge graphs (thousands of decisions), this is O(n) per tree refresh. Acceptable for typical project sizes.
- The `validModuleIds` Set construction is O(m) where m = module count. Efficient.
- No performance concerns for typical use cases.

### End-to-End Usability

The feature works end-to-end:
1. User initializes a project → skeleton YAML files created
2. User extracts decisions → decisions get `l2_module_id: "sys-uncategorized"` (from TaskRunner line 367)
3. TreeView shows "Unassigned Decisions" group under the project node
4. User can drag L3 entries from unassigned group onto L2 modules
5. User can right-click the unassigned group and run "Auto-categorize Decisions"
6. After categorization, decisions move under their assigned L2 modules

**Note**: Extracted decisions get `l2_module_id: "sys-uncategorized"` (TaskRunner line 367), not `"unassigned"`. The `hasUnassigned` check catches this because `"sys-uncategorized"` won't be in `validModuleIds` (assuming no L2 module has that ID), so `!validModuleIds.has(d.l2_module_id)` returns true. This means extracted decisions correctly appear in the unassigned group.
