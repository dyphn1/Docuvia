## Round 1 — Architecture & Design Review

### What the Design Spec Describes

The design spec (`settings.md`) defines `docuvia.extraction.maxFileSizeKBWarning` as a user-configurable numeric setting (default: 50 KB) that acts as a second layer of token-consumption protection alongside the line-count limit (`maxLinesWarning`). The `run-extraction.md` design doc describes a two-threshold size protection system:

1. **Line count check**: If `editor.document.lineCount > maxLinesWarning` (default: 1000), warn the user.
2. **Byte size check**: If `fileSizeKB > maxFileSizeKBWarning` (default: 50 KB), warn the user.

Both checks are independent — a file can trigger either or both warnings. The user can abort extraction after either warning.

### What is Actually Implemented

The implementation in `extension.ts` (lines 198–232) provides:

1. **Line count check** (lines 214–221): ✅ Implemented. Reads `docuvia.extraction.maxLinesWarning` (default 1000), compares `editor.document.lineCount`, shows warning with line count.

2. **Byte size check** (lines 223–232): ✅ Implemented. Reads `docuvia.extraction.maxFileSizeKBWarning` (default 50), computes `Buffer.byteLength(editor.document.getText(), 'utf-8') / 1024`, shows warning with file size in KB.

3. **Settings registration in package.json** (lines 245–249): ✅ Implemented. `docuvia.extraction.maxFileSizeKBWarning` is registered with type `number`, default `50`, and a clear description.

4. **Both checks are independent**: ✅ The line count check and KB size check are sequential and independent. A file can trigger zero, one, or both warnings.

### Gaps Between Design and Implementation

| Gap | Severity | Detail |
|-----|----------|--------|
| **None identified** | — | The implementation matches the design spec exactly. Both size-protection thresholds are implemented, independently checked, and properly registered in `package.json`. |

### Design Doc Conflict Note

The `settings.md` file previously contained a ⚠️ CONFLICT note (line 44) stating that `maxFileSizeKBWarning` was absent from `package.json`. This conflict has been resolved — the setting IS present in `package.json` at lines 245–249. The CONFLICT note in `settings.md` is now stale and should be updated.

## Round 2 — Code Quality & Security Review

### Code Structure

The `docuvia.runExtraction` command handler (extension.ts lines 185–245) follows a clear sequential validation pattern:

1. Context validation (active editor check)
2. File type filtering (`includePatterns` with `minimatch`)
3. Line count warning
4. KB size warning
5. Task dispatching

Each validation step is independent and returns early if the user cancels. This is clean defensive design.

### Security

| Issue | Severity | Detail |
|-------|----------|--------|
| **No size limit on `editor.document.getText()`** | Low | The full file text is read into memory at line 234 (`editor.document.getText()`) AFTER the size checks pass. For files just under the 50 KB threshold, this is fine. But the `maxFileSizeKBWarning` is a soft limit (user can proceed), so a user could proceed with a very large file. However, VS Code itself limits document sizes, and the subsequent chunking in `TaskRunner` mitigates token explosion. |
| **No path traversal risk** | None | All file paths come from `vscode.window.activeTextEditor.document.uri.fsPath` — no user-controlled path input. |

### Code Smells & Anti-Patterns

| Issue | Severity | Detail |
|-------|----------|--------|
| **Double text read** | Low | `editor.document.getText()` is called twice: once at line 225 for byte length calculation, and again at line 234 for the actual extraction content. For large files, this reads the text twice. Could be optimized by computing byte length from the already-read text. |
| **Hardcoded `utf-8` encoding** | None | `Buffer.byteLength(..., 'utf-8')` is correct for VS Code documents which are always UTF-8. No issue. |

### Error Handling

- ✅ No try/catch needed for the size checks — they're synchronous reads on in-memory document state.
- ✅ User cancellation at any warning step cleanly returns without side effects.
- ✅ The `config.get()` calls use default values, so missing settings don't cause errors.

### Performance Concerns

No significant performance issues. The size checks are O(n) in file size (for `Buffer.byteLength` and `lineCount`), but these are in-memory operations on VS Code's document model. The double `getText()` call (lines 225 and 234) is a minor inefficiency — for a 50 KB file, negligible.

### End-to-End Usability

The feature works end-to-end:
1. User runs `docuvia.runExtraction` on a file > 50 KB.
2. User sees: "This file is large (X KB). Extraction might be slow. Proceed anyway?" with Proceed/Cancel.
3. If Proceed → extraction runs with chunked content (4000 chars per chunk).
4. If Cancel → no extraction, no side effects.

The two-layer protection (line count + KB size) provides defense-in-depth against token exhaustion.

## Findings

### Critical/High

None. The feature is implemented correctly per the design spec.

### Medium

1. **Stale CONFLICT note in `settings.md`** — The settings design doc (line 44) contains a ⚠️ CONFLICT note claiming `maxFileSizeKBWarning` is absent from `package.json`. This is no longer true — the setting IS registered. **Recommendation**: Remove or update the CONFLICT note in `settings.md`.

2. **Double `getText()` call** — `editor.document.getText()` is called twice: once for byte length calculation (line 225) and once for extraction content (line 234). **Recommendation**: Read text once, compute byte length from the result: `const text = editor.document.getText(); const fileSizeKB = Buffer.byteLength(text, 'utf-8') / 1024;`

### Low

3. **No unit tests for size-limit logic** — The size-warning thresholds are untested at the unit level. The E2E tests don't cover this path. **Recommendation**: Add unit tests or extend E2E tests to verify warning behavior for files at/above/below thresholds.

4. **No unit tests for `chunkContent()`** — The chunking logic in `TaskRunner.ts` has no test coverage. Edge cases (empty content, single line > CHUNK_SIZE, exact boundary) are untested. **Recommendation**: Add unit tests for `chunkContent()`.
