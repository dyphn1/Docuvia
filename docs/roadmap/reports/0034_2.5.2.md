## Round 1 — Architecture & Design Review

### What the Design Spec Describes

ADR-009 establishes the token management philosophy for Docuvia, emphasizing:
1. **Local Deterministic Constraints** — solidify known boundaries to prevent token waste
2. **Batching & Chunking** — massive tasks are sliced into chunks to prevent context overflow
3. Configurations like chunking strategy must be exposed to control how content is split

The `run-extraction.md` design doc describes the post-dispatch pipeline in `TaskRunner`:
- **Step 2: Content Chunking** — `TaskRunner.chunkContent()` splits file content into chunks
- Strategy is determined by `globalConfig.chunking_strategy`:
  - `'line'` (default): Accumulates lines until the chunk would exceed **4,000 characters** (`CHUNK_SIZE = 4000`), then starts a new chunk
  - `'ast'`: AST-based chunking (noted as future work)

The `settings.md` design doc defines the `GlobalConfigSchema`:
- `chunking_strategy`: `'line' | 'ast'`, default `'line'`
- Read from `~/.docuvia/config.yaml` at extension activation
- Stored in `KnowledgeStore.globalConfig` and passed to `TaskRunner`

### What is Actually Implemented

The implementation provides:

1. **`CHUNK_SIZE = 4000` constant** (TaskRunner.ts line 20): ✅ Defines the 4000-character threshold per chunk.

2. **`chunkContent()` method** (TaskRunner.ts lines 405–431): ✅ Implements line-based chunking. Reads `this.globalConfig?.chunking_strategy ?? 'line'`. If strategy is `'ast'`, logs a fallback warning and falls through to line chunking. The line-based algorithm accumulates lines into `currentChunk`, flushing to the chunks array when adding the next line would exceed `CHUNK_SIZE`.

3. **`GlobalConfigSchema` with `chunking_strategy`** (types.ts line 65): ✅ Zod-validated enum `'line' | 'ast'`, defaulting to `'line'`.

4. **`parseGlobalConfig()`** (parser.ts lines 76–88): ✅ Validates the global config YAML including the chunking strategy field. Falls back to defaults on parse failure.

5. **Global config loading** (extension.ts lines 28–41): ✅ Reads `~/.docuvia/config.yaml` at activation, parses it, stores it in `KnowledgeStore.setGlobalConfig()`.

6. **Config propagation to TaskRunner** (extension.ts line 70): ✅ `new TaskRunner(tqProvider, outputChannel, store, store.globalConfig ?? undefined)` — passes the global config to TaskRunner.

7. **TaskRunner constructor** (TaskRunner.ts line 31): ✅ Accepts `globalConfig?: { chunking_strategy?: 'line' | 'ast' }`.

### Gaps Between Design and Implementation

| Gap | Severity | Detail |
|-----|----------|--------|
| **AST chunking not implemented** | Medium | The `'ast'` strategy falls back to line chunking with a log message (TaskRunner.ts lines 408–411). The design spec describes AST chunking as a future capability, and the code has a TODO. This is a known gap, not a bug. |
| **Chunking strategy not exposed in VS Code Settings UI** | Low | The `chunking_strategy` is only configurable via `~/.docuvia/config.yaml` (global config file). Unlike `maxFileSizeKBWarning` and `maxLinesWarning`, it is NOT registered in `package.json`'s `contributes.configuration`. Users must manually edit the YAML file. This is by design (it's a global user-level setting, not a workspace setting), but could be confusing. |
| **No per-chunk size overlap / context preservation** | Low | The line-based chunking splits strictly at the 4000-character boundary with no overlap between chunks. This means an architectural decision that spans the boundary could be split across two chunks, potentially losing context. The design spec does not specify overlap, so this is an observation rather than a gap. |

### Design Doc Staleness Note

The `run-extraction.md` design doc (line 49) contains a ⚠️ CONFLICT note stating that the KB size check is not implemented and `maxFileSizeKBWarning` is absent from `package.json`. This conflict has been resolved (verified in report 0033_2.5.1). The chunking-related portions of the design doc are accurate and up-to-date.

## Round 2 — Code Quality & Security Review

### Code Structure

The `chunkContent()` method (TaskRunner.ts lines 405–431) is well-structured:
- Clear strategy selection with fallback
- Simple, readable line-accumulation loop
- Proper handling of the final chunk (lines 426–428)
- The `CHUNK_SIZE` constant is module-level for easy adjustment

### Security

| Issue | Severity | Detail |
|-------|----------|--------|
| **No security concerns** | None | The `chunkContent()` method operates on in-memory strings from VS Code's document model. No user-controlled paths, no external input, no injection surface. |

### Code Smells & Anti-Patterns

| Issue | Severity | Detail |
|-------|----------|--------|
| **Type narrowing redundancy** | Low | `globalConfig` is typed as `{ chunking_strategy?: 'line' | 'ast' }` but the Zod schema in `types.ts` already validates this. The optional chaining (`this.globalConfig?.chunking_strategy ?? 'line'`) is correct defensive code, but the type could be more precisely typed as `GlobalConfig['chunking_strategy']`. |
| **AST chunking fallback logs but doesn't warn the user** | Low | When `chunking_strategy: 'ast'` is configured, the fallback only logs to the output channel (`this.outputChannel.appendLine(...)`). The user who configured AST chunking may not realize it's not active. A VS Code warning notification would be more visible. |
| **CHUNK_SIZE is a hardcoded constant** | Low | `CHUNK_SIZE = 4000` is not configurable. If users want to adjust chunk size for their specific LLM context limits, they would need to modify source code. This is reasonable for v1 but could be a future enhancement. |

### Error Handling

- ✅ The `chunkContent()` method has no failure modes — it operates on a string and returns a string array.
- ✅ The `globalConfig` parameter is optional with a `?? 'line'` default, so missing config doesn't cause errors.
- ✅ The `parseGlobalConfig()` function catches all errors and returns defaults (parser.ts lines 85–87).

### Performance Concerns

No significant performance issues. The `chunkContent()` method is O(n) in content length with a single pass through the lines. For a typical source file (< 100 KB), this is negligible. The 4000-character chunk size is a reasonable default for LLM context windows.

### End-to-End Usability

The chunking feature works end-to-end:
1. User configures `chunking_strategy` in `~/.docuvia/config.yaml` (or uses default `'line'`).
2. User runs `docuvia.runExtraction` on a file.
3. `TaskRunner` reads the global config's `chunking_strategy`.
4. Content is split into 4000-character chunks (line-based).
5. Each chunk is sent to the LLM independently.
6. Results are aggregated and written to `.docuvia/l3_decisions/`.

The feature is functional and complete for the `'line'` strategy. The `'ast'` strategy is documented as future work with a graceful fallback.

## Findings

### Critical/High

None. The chunking configs feature is implemented correctly per the design spec.

### Medium

1. **AST chunking not implemented** — The `'ast'` chunking strategy falls back to line chunking with only an output channel log message (TaskRunner.ts lines 408–411). Users who configure `chunking_strategy: ast` in their global config will silently get line chunking instead. **Recommendation**: Add a VS Code warning notification when AST chunking is requested but not available, so users are aware of the fallback. Consider implementing AST chunking using tree-sitter or a language-appropriate parser.

2. **No unit tests for `chunkContent()`** — The core chunking function has zero test coverage. Edge cases (empty content, single line exceeding CHUNK_SIZE, content exactly at boundary, multi-byte characters) are untested. **Recommendation**: Add unit tests covering all edge cases and both strategy paths.

### Low

3. **`CHUNK_SIZE` is hardcoded** — The 4000-character chunk size is a module-level constant that users cannot configure. Different LLM models have different context window sizes. **Recommendation**: Consider exposing `chunk_size` as a configurable field in `~/.docuvia/config.yaml` (e.g., `chunk_size: 4000`) to allow users to tune for their specific LLM.

4. **No chunk boundary overlap** — Chunks are split strictly at the 4000-character boundary with no overlap. Architectural decisions that span a chunk boundary may be split across two LLM calls, potentially losing context. **Recommendation**: Consider adding a small overlap (e.g., 200 characters) between chunks to preserve context at boundaries.

5. **Stale CONFLICT note in `run-extraction.md`** — The design doc (line 49) contains a ⚠️ CONFLICT note about `maxFileSizeKBWarning` being absent from `package.json`. This was resolved in a prior round. **Recommendation**: Remove the stale CONFLICT note.

## Overall Verdict

✅ **PASS**

**Rationale**: The chunking configs feature is fully implemented and functional. The `chunking_strategy` configuration flows correctly from `~/.docuvia/config.yaml` through `GlobalConfigSchema` validation, `KnowledgeStore`, and into `TaskRunner.chunkContent()`. The default `'line'` strategy works correctly with a 4000-character chunk size. The `'ast'` strategy gracefully falls back to line chunking (documented as future work in the design spec). The only issues are: (1) AST chunking is not yet implemented (known gap per design spec), (2) no unit tests for `chunkContent()`, and (3) `CHUNK_SIZE` is not user-configurable. None of these constitute a failure — the feature is complete and usable as designed.
