## Round 1 — Architecture & Design Review

### What the checklist item requires

Item 2.2.3 states: `.docuvia/ directory creation with manifest.yaml, config.yaml, .snapshot-ref`. This breaks down into four sub-requirements:

1. **`.docuvia/` directory creation** — Creating the root Docuvia directory inside the workspace.
2. **`manifest.yaml`** — A manifest file inside `.docuvia/` that describes the project's modules and server-side project ID.
3. **`config.yaml`** — A configuration file. Per ADR-008 (line 198), `.docuvia/` should contain `config.yaml` as part of the lightweight manifest.
4. **`.snapshot-ref`** — A file that stores a reference/snapshot pointer for the knowledge graph, pointing to the orphan branch HEAD.

### Analysis of implementation vs. design

#### `.docuvia/` directory creation — ✅ Implemented

The `initProject()` function in `extension.ts` (lines 474-479) creates the `.docuvia/` directory and its `l3_decisions` subdirectory:

```ts
const docuviaUri = vscode.Uri.file(path.join(targetRoot, '.docuvia'));
const decisionsUri = vscode.Uri.file(path.join(targetRoot, '.docuvia', 'l3_decisions'));
await vscode.workspace.fs.createDirectory(docuviaUri);
await vscode.workspace.fs.createDirectory(decisionsUri);
```

The `acceptL1Tags` command handler (line 300-301) also creates `.docuvia/` when writing L1 tags from the ChatParticipant.

#### `manifest.yaml` — ❌ NOT created by initProject

This is a **critical gap**. The `KnowledgeStore.ts` **reads** `manifest.yaml` on every `load()` call (line 131):

```ts
const manifestContent = await this.readUriSafe(vscode.Uri.joinPath(docuviaDir, MANIFEST_FILE));
const manifest = parseManifest(manifestContent, `${DOCUVIA_DIR}/${MANIFEST_FILE}`);
```

The `ManifestSchema` in `types.ts` is well-defined with `project_id` and `modules` fields. However, **no code path in `initProject()` or `acceptL1Tags` creates `manifest.yaml`**. The `initProject()` function only creates:

- `l1_tags.yaml`
- `l2_modules.yaml`
- `l3_router.yaml`
- `l3_decisions/` (empty directory)

Since `readUriSafe()` returns an empty string on file-not-found, and `parseManifest()` returns `{ project_id: undefined, modules: [] }` for empty input, the system degrades gracefully but the manifest is never initialized. This means:

- `manifest.project_id` is always `undefined` → the server-augmented and git-fallback code paths in `KnowledgeStore._loadWorkspace()` (lines 141 and 189) are **never reached** for projects initialized via `initProject`.
- `manifestModules` is always empty → offline CodeLens matching has no path patterns.
- For these features to work, users must **manually create** `manifest.yaml`, which is not documented or prompted.

#### `config.yaml` — ❌ NOT created inside `.docuvia/`

Per ADR-008 (line 198), the `.docuvia/` working tree should contain `config.yaml` as part of the lightweight manifest. However:

- The **global** config at `~/.docuvia/config.yaml` is read (line 29 of `extension.ts`) but **never auto-created**. Users must manually create it.
- A **per-project** `.docuvia/config.yaml` is **not implemented** anywhere — no code reads or writes this file.

The checklist item explicitly names `config.yaml` alongside `manifest.yaml` and `.snapshot-ref` as files that should be inside `.docuvia/`, and this is consistent with ADR-008. Neither variant is auto-created during initialization.

#### `.snapshot-ref` — ❌ NOT Implemented

No code in the entire `vscode-client` source references `.snapshot-ref`. A grep for `snapshot-ref`, `snapshotRef`, and `snapshot_ref` across the entire repository returned zero results. The ADR-001 mentions `_project_profile.yaml` as a "cognitive snapshot" capturing topology information, but this file is also **never created** by any code path.

### Design gaps

- The `init-project.md` design doc (line 21) lists only `l1_tags.yaml`, `l2_modules.yaml`, `l3_router.yaml` as scaffold files. It makes no mention of `manifest.yaml`, `config.yaml`, or `.snapshot-ref`.
- ADR-001 mentions `_project_profile.yaml` but this is not implemented and does not match the `.snapshot-ref` naming from ADR-008.
- There is a disconnect between the `ManifestSchema` + `KnowledgeStore` reading logic (which expects `manifest.yaml`) and the `initProject` write logic (which never creates it).
- ADR-008 clearly specifies the `.docuvia/` working tree should contain `manifest.yaml`, `config.yaml`, `.snapshot-ref`, but the implementation only creates three YAML files that are not part of that specification.

## Round 2 — Code Quality & Security Review

### Code structure

- The `initProject()` function is well-structured with proper workspace resolution, multi-root handling, and input validation (BUG G-1 fix: validates non-empty project name).
- The overwrite logic (lines 450-460) properly handles re-initialization with a destructive warning prompt.
- The `writeIfAbsent` helper (line 694) follows defensive design by checking file existence before writing.

### Security concerns

- **Project name injection**: The `projectName` is interpolated into YAML content via template literal (line 488):
  ```ts
  project_name: "${projectName}"
  ```
  If a user enters a project name containing YAML special characters (e.g., `"`, `:`, `#`, backslash, multiline), the generated `l1_tags.yaml` could be malformed or have unintended YAML semantics. The input is validated for emptiness but **not sanitized for YAML safety**. A name like `my"project` would produce broken YAML.
- No path traversal risk: `targetRoot` always comes from `vscode.workspace.workspaceFolders`, not user input.

### Code smells

- The manifest being read but never written is a conceptual code smell — the `KnowledgeStore` has sophisticated logic for server fallback and git fallback based on `manifest.project_id`, but this logic is effectively dead code for any user who only uses `initProject`.
- The `acceptL1Tags` command handler (line 286-325) duplicates the `.docuvia/` scaffolding logic from `initProject()` — both create the same set of YAML skeleton files. This is duplicated maintenance.

### Error handling

- `writeIfAbsent` silently skips existing files — no logging to indicate this happened.
- The `acceptL1Tags` command creates `.docuvia/` and `l3_decisions/` but does not create `manifest.yaml`, which could lead to an inconsistent state where some but not all expected files exist.

## Round 3 — Integration & Completeness Review

### Integration issues

1. **Broken server-augmented path**: Because `manifest.yaml` is never created, `manifest.project_id` is always `undefined`, so the server-augmented loading path (`KnowledgeStore._loadWorkspace()` line 141) and the git-fallback path (line 189) are **never activated** for projects initialized via the standard flow. This means the `CentralServerClient.pullSnapshot()` and the `_loadFromGit()` method are effectively dead code in the standard onboarding flow.

2. **Offline CodeLens**: `DocuviaCodeLensProvider.ts` uses `snapshot.manifestModules` for offline matching. Since `manifest.yaml` is never created, `manifestModules` is always empty, making offline CodeLens matching non-functional.

3. **`acceptL1Tags` creates a different set of files than `initProject`**: The `acceptL1Tags` handler (line 286-325) creates `.docuvia/`, `l3_decisions/`, `l1_tags.yaml`, `l2_modules.yaml`, and `l3_router.yaml` — but `initProject` creates the same set. Both lack `manifest.yaml`. The two code paths for `.docuvia/` creation are duplicated logic.

4. **No flow to populate `project_id`**: Even if a user connects to a server and creates a project, there is no automated flow to write `project_id` into `manifest.yaml`. The `CentralServerClient` has no method to update the local manifest after server project creation.

### Missing tests

- The `initProject` command has a basic test reference (`phase1.test.ts` line 36: `vscode.commands.executeCommand('docuvia.initProject')`), but the test is incomplete — it only checks for `.docuvia/` directory and `l1_tags.yaml`, and does not verify the presence or absence of `manifest.yaml`, `config.yaml`, or `.snapshot-ref`.
- No integration test validates the full end-to-end onboarding flow.
- No test verifies that the server/git fallback paths work after initialization.

### Performance concerns

- None significant for this item. Directory/file creation is I/O-bound and straightforward.

### End-to-end usability

- A user running `docuvia.initProject` gets a partially initialized project. The `.docuvia/` directory contains YAML skeleton files but is missing the manifest that `KnowledgeStore` expects. The system silently degrades to local-only mode with no warning.
- The success message ("Populate the YAML files to build your knowledge graph.") does not mention `manifest.yaml`, `config.yaml`, or `.snapshot-ref` as files the user should create.
- The `~/.docuvia/config.yaml` global config is never auto-created, so users who want to connect to a server must manually create this file with the correct `server_url` — this is not documented in any in-app flow.

## Overall Verdict

⚠️ **WARN**

The `.docuvia/` directory is successfully created by `initProject()` with skeleton YAML files (`l1_tags.yaml`, `l2_modules.yaml`, `l3_router.yaml`, and the `l3_decisions/` directory). However, three of the four named requirements in the checklist item are **not implemented**:

- **`manifest.yaml`** — Not created by any initialization code path, despite being read by `KnowledgeStore` and being critical for server-augmented and git-fallback load paths. This is a functional gap that silently breaks key features.
- **`config.yaml`** — Not created inside `.docuvia/` per ADR-008. The global variant at `~/.docuvia/config.yaml` is also never auto-created.
- **`.snapshot-ref`** — Does not exist anywhere in the codebase. No code reads or writes this file.

The core directory creation works, but the item is incomplete per its specification. Marking as ⚠️ WARN rather than ❌ FAIL because the basic `.docuvia/` directory creation is functional and the system degrades gracefully (no crashes), but the missing `manifest.yaml`, `config.yaml`, and `.snapshot-ref` are significant functional gaps that break the ADR-008 three-layer architecture.
