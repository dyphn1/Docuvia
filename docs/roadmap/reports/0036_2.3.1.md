## Round 1 — Architecture & Design Review

### What 2.3.1 Requires

TaskRunner must scope its file reads/writes to the correct workspace root in a multi-root VS Code workspace. When a user triggers extraction, the results must land in the `.docuvia/` of the workspace folder that contains the source file — not in an arbitrary folder or the first workspace.

### How It's Implemented

The codebase uses three distinct strategies for workspace root resolution:

**1. Extraction (`runExtractionAsync`, TaskRunner.ts line 294):**
```typescript
const workspaceRoot = vscode.workspace.getWorkspaceFolder(vscode.Uri.file(params.sourceFilePath))?.uri.fsPath;
if (workspaceRoot) {
  await this.writeExtractionResults(workspaceRoot, params.sourceFilePath, allDecisions);
}
```
Uses `vscode.workspace.getWorkspaceFolder(uri)` — the canonical VS Code API that maps a URI to its workspace folder. This is correct and reliable. The extracted L3 decisions are written to `<workspaceRoot>/.docuvia/l3_decisions/`.

**2. Auto-categorization (`queueAutoCategorization`, TaskRunner.ts line 59):**
```typescript
async queueAutoCategorization(workspaceRoot: string, unassignedNodes: KGNode[]): Promise<string> {
```
Takes `workspaceRoot` as an explicit parameter. The extension.ts command handler (`extension.ts` line 132-142) extracts it from the tree node's `workspaceRoot` property. This is correct — the tree node always carries its originating workspace root.

**3. KnowledgeStore (multi-root aware):**
The store maintains a `Map<string, KnowledgeGraphSnapshot>` keyed by workspace root path (line 42). The `load()` method iterates all `workspaceFolders` (line 102-106). Watchers are created per folder (lines 358-391). `getSnapshotFor(uri)` uses `getWorkspaceFolder()` for lookup (lines 68-76). All properly scoped.

**4. `docuvia.runExtraction` command (`extension.ts` line 185-244):**
Uses `vscode.workspace.getWorkspaceFolder(editor.document.uri)` (line 194) to determine the workspace folder for include-pattern matching. The `sourceFilePath` is then passed to `taskRunner.queueExtraction()`, which internally resolves the workspace root. Consistent.

### Design Compliance

The design spec (06-runtime-scenarios.md, line 161) shows `TaskRunner.runExtraction(workspaceUri)`, implying workspace-aware execution. The implementation goes further — it doesn't need a workspace URI parameter because it resolves one internally from the source file path.

### Gaps in Design Spec

The design spec doesn't explicitly describe the auto-categorization flow's workspace scoping, but the tree-node-driven approach (via `docuvia.autoCategorizeDecisions` on an "Unassigned Decisions" group) is a natural extension of the same pattern.

### Round 1 Verdict: The architecture is sound. Dynamic root scoping is correctly implemented at every level.

## Round 2 — Code Quality & Security Review

### Code Quality Observations

**1. Consistent use of `vscode.workspace.getWorkspaceFolder()`:**
Every workspace resolution in the codebase uses this API — no hardcoded paths or `workspaceFolders?.[0]` fallbacks in TaskRunner. This is exemplary.

**2. Null-safety on workspace root resolution (TaskRunner.ts line 294):**
```typescript
const workspaceRoot = vscode.workspace.getWorkspaceFolder(vscode.Uri.file(params.sourceFilePath))?.uri.fsPath;
```
The optional chaining (`?.`) correctly handles the case where a file might not belong to any workspace folder. The subsequent `if (workspaceRoot)` guard on line 295 prevents writing to an undefined path.

**3. Auto-categorization scoped to workspace snapshot (TaskRunner.ts line 95):**
```typescript
const snap = this.store.snapshots.get(workspaceRoot);
if (!snap) {
  this.tqProvider.updateTaskStatus(taskId, 'failed', 'Knowledge graph not loaded');
  return;
}
```
Properly validates that the workspace is loaded before proceeding. Good defensive design.

**4. `writeExtractionResults` parameter redundancy (TaskRunner.ts line 342-349):**
```typescript
private async writeExtractionResults(
    workspaceRoot: string,
    sourceFile: string,
    decisions: string[]
  ): Promise<void> {
    if (decisions.length === 0) return;
    if (!workspaceRoot) return;
```
The `!workspaceRoot` check on line 349 is defensive but redundant — the caller already guards against this (line 295). Not harmful, but slightly redundant.

**5. `writeExtractionResults` frontmatter bug (TaskRunner.ts line 367):**
```typescript
l2_module_id: "sys-uncategorized",
```
Extracted decisions are hardcoded to `"sys-uncategorized"` rather than being assigned to a real L2 module. This is a documented known issue (R-09 in 11-risks-and-dead, BUG B-1 in user-journeys.md). While not strictly a "dynamic root scoping" issue, it means extracted decisions end up in the unassigned group — confirming why the auto-categorization feature exists.

**6. No input validation on `workspaceRoot` in `queueAutoCategorization`:**
The `workspaceRoot` parameter is typed as `string` but never validated. If called with an empty string or invalid path, the store lookup would fail silently and the task would fail with "Knowledge graph not loaded". This is acceptable — the only caller is the tree view command handler which always passes a valid root.

### Security Observations

No security concerns specific to the dynamic root scoping feature. Path traversal is not a risk since `workspaceRoot` is always an absolute path from VS Code's `workspaceFolders`, not user-controlled input.

### Round 2 Verdict: Code quality is high. Defensive patterns are used consistently. The `l2_module_id: "sys-uncategorization"` hardcoding is a known tracked issue but does not affect root scoping correctness.

## Round 3 — Integration & Completeness Review

### Integration Points

**1. TaskRunner ↔ KnowledgeStore integration:**
After writing extraction results, `runExtractionAsync` calls `this.store.load()` (TaskRunner.ts line 299), which triggers a full reload of all workspace snapshots and fires `onDidLoad`, which triggers `KnowledgeGraphTreeProvider.refresh()`. This ensures the TreeView updates to show newly extracted decisions. Correct.

After auto-categorization writes, `applyAutoCategorization` calls `this.store.load()` (line 232). Correct.

**2. TaskRunner ↔ TaskQueueTreeProvider integration:**
Task status updates flow correctly through `tqProvider.updateTaskStatus()` at every stage (pending → in_progress → done/failed). The task queue is global (not per-workspace), which is appropriate since it's a single panel.

**3. KnowledgeGraphTreeProvider multi-root display:**
The TreeView shows one project node per workspace folder (line 168-177). Each node carries its `workspaceRoot`. Children (L1 tags, L2 modules, L3 entries) are scoped to that workspace's snapshot. Drag-and-drop operations check `workspaceRoot` matching (line 53). This is fully multi-root aware.

**4. KnowledgeStore watcher per workspace:**
FileSystemWatchers are created per workspace folder (lines 358-391). The `_handleBatchedChanges` method receives the workspace root and performs incremental or full reload scoped to that workspace. Correct.

**5. `docuvia.initProject` multi-root support (extension.ts line 417-446):**
When multiple workspace folders are open, the user is prompted to pick one. The `store.snapshots` map is checked to filter out already-initialized folders. Correct.

**6. `docuvia.openDashboard` multi-root support (extension.ts line 165-182):**
When multiple workspace folders are open, the user is prompted via `showWorkspaceFolderPick`. Correct.

### Edge Cases

**1. File outside any workspace folder:**
If a user opens a file that doesn't belong to any workspace folder, `getWorkspaceFolder()` returns `undefined`. The extraction command would still queue the task, but `writeExtractionResults` would be skipped (line 295 guard). The task would show as "done" with 0 decisions. This is acceptable behavior — the user gets a message but no data corruption occurs.

**2. Workspace folder added/removed at runtime:**
`onDidChangeWorkspaceFolders` handler (extension.ts line 396-400) calls `store.load()` and `startWatcher()`, which clears old watchers and creates new ones. Correct.

**3. Auto-categorization on a workspace that was just initialized:**
The `store.snapshots.get(workspaceRoot)` check (TaskRunner.ts line 95-98) handles this — if the snapshot isn't loaded yet, the task fails gracefully with a clear message.

### Missing Tests

There are no unit or integration tests specifically for the dynamic root scoping behavior. The existing test infrastructure (factories.ts, withRollback) is DB-focused. Testing multi-root workspace behavior would require mocking `vscode.workspace.workspaceFolders` and `vscode.workspace.getWorkspaceFolder()`, which is possible but not currently done.

### Round 3 Verdict: Integration is complete and correct. All components work together properly in multi-root scenarios. The only gap is the absence of automated tests for this specific behavior.

## Overall Verdict

**✅ PASS**

The TaskRunner dynamic root scoping is correctly and comprehensively implemented. Every code path that reads or writes workspace-scoped data properly resolves the workspace root using `vscode.workspace.getWorkspaceFolder()`. The KnowledgeStore, KnowledgeGraphTreeProvider, and all command handlers are fully multi-root aware. The implementation is defensive, handles edge cases gracefully, and integrates correctly across all components.

The only recommendations are cosmetic (redundant null check) and test-coverage related (no automated tests for multi-root scenarios), neither of which affects correctness.
