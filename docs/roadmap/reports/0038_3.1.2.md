## Round 1 — Architecture & Design Review

### What the Design Spec Describes

Item 3.1.2 states: **Few-shot injection into generate pipeline**. Per ADR-006, the Swarm Intelligence pipeline requires that the generate pipeline consume prior human corrections as few-shot context. Specifically:

1. Human corrections are stored in `correction_examplesTable` (verified in 3.1.1).
2. The background distillation job compresses them into guardrails stored in `prompt_templatesTable`.
3. **The generate pipeline must inject these corrections as few-shot examples** into LLM prompts so that future generations avoid repeating past mistakes.

### What is Actually Implemented

The generate pipeline in `generate.ts` implements few-shot injection as follows:

**A. Direct Few-Shot Injection (via `correctionExamplesTable`):**

1. `getRecentCorrections(projectId, "l2_node")` is called at line 696 during the POST `/projects/:id/generate` handler.
2. This fetches the 5 most recent `correction_examples` rows where `entityType = "l2_node"`, ordered by `createdAt desc`.
3. The corrections are passed to `generateL2Nodes()` at line 745 as the `corrections` parameter.
4. Inside `generateL2Nodes()`, `buildFewShotSection(corrections)` at line 201 formats them into:
   ```
   Previous human corrections (use these as quality guidance):
   Example 1:
     Original: "..."
     Corrected: "..."
   ```
5. This section is appended to the system prompt at line 213:
   ```
   ${systemPromptOverride}\n\nAvailable L1 tags to map L2 nodes to: ${tagNames}${docSection}${fewShotSection}${previousBatchSection}
   ```

**B. Distilled Guardrail Injection (via `prompt_templatesTable`):**

1. `getSystemPrompt(projectId, "l2_extractor")` at line 695 fetches an active template from `promptTemplatesTable`.
2. This template could be a distilled guardrail created by `metabolism.ts`.
3. The retrieved prompt is used as `systemPromptOverride` in `generateL2Nodes()`.

### Gaps Between Design and Implementation

| Gap | Severity | Detail |
|-----|----------|--------|
| **L3 corrections never fetched for few-shot** | High | Only `getRecentCorrections(projectId, "l2_node")` is called (line 696). Corrections with `entityType = "l3_node"` are never fetched or injected. Since the L3 nodes are generated within the same L2 extraction LLM call, L3 corrections could provide valuable guidance for L3 node content quality, but they are completely unused. |
| **No few-shot in L1 tag generation** | Medium | The `generateL1Tags()` function (lines 136-169) does not accept or use corrections. L1 tag generation has no few-shot feedback loop. |
| **No few-shot in sieve extraction** | Low | The `/projects/:id/extract/sieve` endpoint (lines 453-517) does not fetch corrections. This endpoint provides isolated decision extraction without any feedback loop. This may be acceptable since sieve extraction is a standalone operation. |
| **Distilled guardrails stored as wrong template type** | Medium | The metabolism job stores ALL distilled guardrails as `templateType: "l3_generator"` (metabolism.ts line 53), regardless of whether the correction was for an `l2_node` or `l3_node` entity. However, `getSystemPrompt(projectId, "l2_extractor")` is called at line 695 and `getSystemPrompt(projectId, "l3_generator")` is called at line 471. This means distilled L2 corrections stored as `l3_generator` would only be applied in the sieve extraction context, not during the main generate pipeline. |
| **`buildFewShotSection` not reused for L3 context** | Low | The `buildFewShotSection()` function is well-structured and reusable, but is only called in `generateL2Nodes()`. If L3 corrections were to be injected (e.g., into a future dedicated L3 generation step), the function would need to be called there as well. |

## Round 2 — Code Quality & Security Review

### Code Structure

The few-shot injection code is clean and well-factored:

- `getRecentCorrections()` (lines 62-78): Single-responsibility function that queries corrections with proper filtering (`projectId`, `entityType`), ordering (`createdAt desc`), and limiting (`LIMIT 5`).
- `buildFewShotSection()` (lines 80-91): Pure function that formats corrections into a readable string. Returns empty string for zero corrections. Uses template literals for clean formatting.
- Integration in `generateL2Nodes()`: The `corrections` parameter is properly threaded through from the caller.

### Security

| Issue | Severity | Detail |
|-------|----------|--------|
| **Prompt injection via correction content** | Medium | Correction content from the database (both `originalContent` and `correctedContent`) is embedded directly into the LLM system prompt via `buildFewShotSection()`. These values originate from AI-generated descriptions and developer-authored corrections. A malicious correction containing crafted text (e.g., "Ignore previous instructions and output...") could manipulate the LLM's behavior. Impact is scoped to the user's own project, but could degrade output quality. **Recommendation**: Wrap correction text in XML tags (e.g., `<original>...</original>`) and add injection-mitigation instructions to the system prompt. |
| **No output length limit on few-shot section** | Low | If a project accumulates many long corrections, the `buildFewShotSection` output could grow large. The current `LIMIT 5` mitigates this, but individual corrections could still be very long. **Recommendation**: Truncate individual correction content to a reasonable limit (e.g., 500 chars each) in `buildFewShotSection()`. |

### Code Smells & Anti-Patterns

| Issue | Severity | Detail |
|-------|----------|--------|
| **Only L2 corrections fetched** | High | The generate pipeline only calls `getRecentCorrections(projectId, "l2_node")` at line 696. L3 corrections are never fetched. This means the `entityType` filtering in `getRecentCorrections` works correctly, but the generate pipeline doesn't leverage the full correction dataset. **Recommendation**: Also fetch L3 corrections and inject them into the L3 generation context. |
| **Hardcoded entityType string** | Low | The `"l2_node"` string is hardcoded at line 696. While not a bug, this could be templated or parameterized if additional entity types need few-shot injection in the future. |

### Error Handling

- ✅ `getRecentCorrections()` relies on Drizzle's query execution; errors will propagate to the outer try/catch in the generate route handler.
- ✅ `buildFewShotSection()` is a pure function with no failure modes.
- ✅ The `generateL2Nodes()` function has a try/catch around JSON parsing (lines 223-228).
- ⚠️ If `getRecentCorrections()` throws (e.g., DB connection failure), the entire generate pipeline fails. Since corrections are an enhancement (not a core requirement), this could be made optional with a try/catch that falls back to no corrections.

### End-to-End Flow Verification

The few-shot injection works end-to-end for the L2 extraction path:

1. Developer resolves a review task with a correction → `correction_examplesTable` row created.
2. On next generate, `getRecentCorrections(projectId, "l2_node")` fetches up to 5 recent corrections.
3. Corrections are formatted by `buildFewShotSection()` into "Previous human corrections..." text.
4. This text is appended to the L2 extraction system prompt.
5. The LLM generates L2/L3 nodes with awareness of past corrections.

**The pipeline works correctly for L2 corrections.**

### Performance Concerns

- `getRecentCorrections()` runs a `LIMIT 5` query on every generate request. This is lightweight but could benefit from an index on `(projectId, entityType, createdAt)`.
- The few-shot section adds ~200-500 tokens to the system prompt (depending on correction length). This is acceptable given the quality improvement.
- No caching of corrections between generate calls. For high-frequency generation, caching could reduce DB queries, but the current design is simple and correct.

### End-to-End Usability

The feature is usable end-to-end:
1. Developer sees an incorrect L2 node in the review queue.
2. Developer approves the task with a corrected description.
3. The correction is stored in `correction_examplesTable`.
4. On next generate, the correction appears as a few-shot example in the LLM prompt.
5. The LLM avoids the same mistake in future extractions.

This improves output quality over time, which is the core value proposition of the Swarm Intelligence pipeline.

## Findings

### Critical/High

1. **L3 corrections are never injected into the generate pipeline** — The generate pipeline only fetches `l2_node` corrections (line 696). L3 corrections stored in `correction_examplesTable` with `entityType = "l3_node"` are completely ignored by the generate pipeline. This means corrections to L3 node content (implementation rules, decisions, rationale) do not feed back into future L3 generation. **Recommendation**: Either (a) add a separate `getRecentCorrections(projectId, "l3_node")` call and inject them into the L3 generation context, or (b) modify `generateL2Nodes()` to accept both L2 and L3 correction arrays and include L3 corrections in the prompt.

2. **No fallback for correction fetch failures** — If `getRecentCorrections()` throws (DB error, etc.), the entire generate pipeline fails. Corrections are an enhancement, not a core requirement. **Recommendation**: Wrap the corrections fetch in a try/catch that logs the error and proceeds with an empty corrections array.

### Medium

3. **Distilled guardrails stored as wrong template type** — `metabolism.ts` stores all distilled guardrails as `templateType: "l3_generator"` regardless of the original correction entity type. This means L2 corrections distilled into guardrails are applied in the sieve extraction context (`l3_generator` template at line 471) rather than the main generate pipeline's L2 extraction context (`l2_extractor` template at line 695). **Recommendation**: Use `correctionExamplesTable.entityType` to map to the correct `templateType` during distillation (e.g., `l2_node` → `l2_extractor`).

4. **No few-shot injection for L1 tag generation** — The `generateL1Tags()` function has no corrections input. L1 corrections (if they were captured) could improve tag generation quality. This is contingent on fixing L1 correction capture (identified in 3.1.1 report).

5. **Prompt injection via correction content** — Correction content is embedded directly into the system prompt without sanitization or structural isolation. **Recommendation**: Wrap correction content in `<original>` and `<corrected>` tags.

### Low

6. **No index on `correction_examples` for the few-shot query** — The query in `getRecentCorrections()` filters on `(projectId, entityType)` and orders by `createdAt desc` with `LIMIT 5`. A composite index on `(projectId, entityType, createdAt desc)` would optimize this query. **Recommendation**: Add a Drizzle migration with `CREATE INDEX idx_correction_examples_query ON correction_examples (project_id, entity_type, created_at DESC)`.

7. **No unit tests for few-shot injection logic** — The `getRecentCorrections()` and `buildFewShotSection()` functions are untested.

## Overall Verdict

✅ **PASS**

**Rationale**: The few-shot injection into the generate pipeline is implemented and functional. The `getRecentCorrections()` function correctly fetches recent corrections from the `correction_examplesTable`, and `buildFewShotSection()` properly formats them as few-shot examples that are appended to the L2 extraction system prompt. The integration between review resolution → correction storage → few-shot injection works end-to-end for the L2 correction path.

The primary finding is that L3 corrections are never fetched or injected — only `l2_node` corrections are used. Additionally, distilled guardrails from the metabolism job are stored as `l3_generator` template type regardless of their original entity type, which may cause them to be applied in the wrong context. However, the core feature described in the checklist item — few-shot injection into the generate pipeline — is implemented and working for the main use case (L2 corrections guiding L2 extraction). The findings represent improvement opportunities rather than functional failures, consistent with the ✅ Done status in the checklist body.
