## Round 1 — Architecture & Design Review

### Design Spec (ADR-007)
ADR-007 Section 3 ("Temporal Decay & Garbage Collection") specifies:
- Knowledge nodes contain `created_at` and `lastVerifiedAt` timestamps.
- The router applies an Exponential Temporal Decay function: `Math.exp(-LAMBDA * daysSinceVerified)`.
- Knowledge untouched naturally sinks to the bottom of search results.
- When old knowledge correctly answers a query, its `lastVerifiedAt` is updated via `POST /search/feedback`.

### Implementation Review

**`calculateTemporalDecay()` function (lines 117–123):**
```typescript
export function calculateTemporalDecay(referenceDate: Date, now: number = Date.now()): number {
  const MS_PER_DAY = 1000 * 60 * 60 * 24;
  const HALF_LIFE_DAYS = 30;
  const LAMBDA = Math.LN2 / HALF_LIFE_DAYS;
  const daysSinceVerified = (now - referenceDate.getTime()) / MS_PER_DAY;
  return Math.exp(-LAMBDA * Math.max(0, daysSinceVerified));
}
```

This exactly matches the ADR-007 specification:
- ✅ 30-day half-life (`HALF_LIFE_DAYS = 30`, `LAMBDA = Math.LN2 / 30`)
- ✅ Exponential decay formula: `exp(-λ * t)`
- ✅ Future-date protection via `Math.max(0, daysSinceVerified)`
- ✅ Pure function with injectable `now` parameter for testability

**Application in vector search — L2 nodes (lines 214–216):**
```typescript
const referenceDate = node.lastVerifiedAt ?? node.createdAt;
const decayFactor = calculateTemporalDecay(referenceDate);
const score = rawScore * decayFactor;
```

**Application in vector search — L3 nodes (lines 268–270):**
```typescript
const referenceDate = node.lastVerifiedAt ?? node.createdAt;
const decayFactor = calculateTemporalDecay(referenceDate);
const score = rawScore * decayFactor;
```

- ✅ Both L2 and L3 paths apply decay identically
- ✅ Fallback to `node.createdAt` when `lastVerifiedAt` is null
- ✅ Decay is multiplicative with raw cosine similarity score

**Feedback endpoint (`search.ts` lines 44–50):**
```typescript
if (nodeLayer === "l2") {
  await db.update(l2NodesTable).set({ lastVerifiedAt: new Date() }).where(eq(l2NodesTable.id, nodeId));
} else if (nodeLayer === "l3") {
  await db.update(l3NodesTable).set({ lastVerifiedAt: new Date() }).where(eq(l3NodesTable.id, nodeId));
}
```
- ✅ Updates `lastVerifiedAt` to `NOW()` on feedback, "refreshing" the node's decay

**Schema support:**
- `l2_nodes.ts` line 21: `lastVerifiedAt: timestamp("last_verified_at").defaultNow()`
- `l3_nodes.ts` line 33: `lastVerifiedAt: timestamp("last_verified_at").defaultNow()`
- ✅ Both tables have the column with `defaultNow()` for new nodes

### Gaps / Contradictions
- **None found.** The implementation faithfully follows ADR-007.

## Round 2 — Code Quality & Security Review

### Code Quality
- **Well-structured:** `calculateTemporalDecay` is a pure, exported function with clear constants and documentation.
- **Defensive design:** `Math.max(0, daysSinceVerified)` prevents future dates from inflating scores.
- **Testability:** The `now` parameter defaults to `Date.now()` in production but can be injected for deterministic testing.
- **Consistent application:** Decay is applied in exactly the same way for both L2 and L3 node scoring.
- **No code smells:** The function is 7 lines, single-responsibility, no duplication.

### Unit Test Coverage (`intent-router.unit.test.ts` lines 19–43)
- ✅ Returns 1.0 for a date exactly now (no decay)
- ✅ Returns 0.5 for 30 days ago (half-life verification)
- ✅ Returns 0.25 for 60 days ago (two half-lives)
- ✅ Future dates capped at 1.0 (no score inflation)

### Security
- No security vulnerabilities in the decay calculation itself.
- The function operates on timestamps only, no user-controlled input reaches the math directly.

### Minor Observation
- The SQL LIKE fallback path (lines 289–377) does **not** apply temporal decay — it uses hardcoded scores (0.9 for L2, 0.8 for L3). This is acceptable because:
  1. This path only runs when embedding generation fails (graceful degradation).
  2. The hardcoded scores are lower than typical decayed embedding scores, so fallback results naturally rank lower.
  3. Adding decay to the LIKE path would require fetching `lastVerifiedAt` in the fallback query, adding complexity for a degraded path.

## Round 3 — Integration & Completeness Review

### Integration with Routing Strategy
- **Vector search:** Decay is applied in `vectorSearchHandler()`, called for `vector_search` and `hybrid` strategies.
- **Hybrid search:** Calls `vectorSearchHandler()` (which applies decay), then merges with graph results. Vector results already have decay factored in.
- **Direct lookup:** Uses fixed scores (1.0). No decay needed — exact matches are not subject to staleness.
- **Graph traversal:** Uses fixed scores (1.0, 0.7). No decay needed — structural relationships don't decay.
- ✅ This is consistent with the design: decay applies to semantic similarity scores, not exact or structural matches.

### Feedback Loop Completeness
- Search returns results with `nodeLayer` and `id` fields.
- Client can call `POST /search/feedback` with `{ nodeId, nodeLayer, interactionType }`.
- Feedback updates `lastVerifiedAt` to `NOW()`, resetting the decay clock.
- Next search query will see the refreshed `lastVerifiedAt`.
- ✅ Full feedback loop is implemented.

### Schema Completeness
- Both `l2_nodes` and `l3_nodes` have `lastVerifiedAt` with `defaultNow()`.
- New nodes automatically get a `lastVerifiedAt` value at creation time.
- ✅ No schema gaps.

### Performance
- Decay calculation is O(1) per node — simple arithmetic on timestamps.
- No additional DB queries required; `lastVerifiedAt` is already fetched as part of the node SELECT.
- ✅ No performance concerns.

### End-to-End Usability
- The feature works end-to-end: nodes are created with timestamps, decay is applied during search, and feedback refreshes the timestamp.
- The 30-day half-life is a reasonable default that balances freshness with stability.

## Findings

1. ✅ **Implementation matches design spec exactly.** The exponential decay formula, 30-day half-life, and feedback refresh mechanism are all correctly implemented per ADR-007.

2. ✅ **Unit tests are comprehensive.** All key decay scenarios are tested: no decay, half-life, two half-lives, and future-date edge case.

3. ✅ **Schema is correct.** Both L2 and L3 tables have `lastVerifiedAt` with `defaultNow()`.

4. ✅ **Feedback loop is complete.** The `POST /search/feedback` endpoint correctly updates `lastVerifiedAt` for both L2 and L3 nodes.

5. ℹ️ **LIKE fallback path does not apply decay.** This is an acceptable design choice for the degraded path. No action needed.
