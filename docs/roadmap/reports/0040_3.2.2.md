## Round 1 — Architecture & Design Review

### Design Spec (ADR-007)

ADR-007 Section 3 ("Temporal Decay & Garbage Collection") specifies:
- Knowledge nodes contain `created_at` and `lastVerifiedAt` timestamps.
- The router applies an Exponential Temporal Decay function to search scores: `Math.exp(-LAMBDA * daysSinceVerified)`.
- Knowledge untouched naturally sinks to the bottom of search results.
- When old knowledge correctly answers a query, its `lastVerifiedAt` is updated via `POST /search/feedback`, "refreshing" its lifespan.

Item 3.2.2 specifically verifies that decay is **applied to the final query results** — not just that the math function exists (that was 3.2.1), but that the decay-adjusted scores actually flow through to the API response and are visible to consumers.

### Implementation Trace

**`vectorSearchHandler()` — L2 nodes (lines 210–218):**
```typescript
const l2Scored = l2Rows
  .map((node) => {
    const emb = parseEmbedding(node.embedding);
    const rawScore = emb ? cosineSimilarity(queryEmbedding, emb) : 0;
    const referenceDate = node.lastVerifiedAt ?? node.createdAt;
    const decayFactor = calculateTemporalDecay(referenceDate);
    const score = rawScore * decayFactor;
    return { node, score };
  })
  .sort((a, b) => b.score - a.score)
  .slice(0, limit);
```
✅ Decay is applied to L2 scores before sorting. Results are ranked by decay-adjusted score.

**`vectorSearchHandler()` — L3 nodes (lines 264–274):**

### Gaps / Contradictions

1. **Frontend `query.tsx` uses a local `SearchResultItem` interface** (lines 17–26) that does NOT include the `source` field from the backend's `AgenticSearchResult`. The local interface is:
   ```typescript
   interface SearchResultItem {
     nodeLayer: "l1" | "l2" | "l3";
     id: number;
     title: string;
     content: string | null;
     projectId: number | null;
     projectName: string | null;
     score: number;
     createdAt: string;
   }
   ```
   The backend's `AgenticSearchResult` has `source`, `nodeLayer` (including `"commit"`), and `id` as `number | string`. The frontend interface is missing `source` and doesn't support `commit` layer or string IDs. This means the frontend cannot display the source of the result (vector/graph/direct), which is relevant context for understanding why a result has its particular score.

2. **No decay metadata exposed to the frontend.** The score displayed to users (`item.score.toFixed(2)` at line 187) is the decay-adjusted score, but there is no indication of:
   - Whether decay was applied
   - The node's `lastVerifiedAt` date
   - The raw (pre-decay) score vs. the decayed score
   - A "staleness" indicator

   This is a usability gap — users see scores but don't know why a highly-relevant node might rank lower than expected.

3. **SQL LIKE fallback path does not apply decay** (lines 289–377). Hardcoded scores of 0.9 (L2) and 0.8 (L3) are used. This is acceptable for a degraded path but means fallback results don't benefit from temporal ranking.

## Round 2 — Code Quality & Security Review

### Code Quality

- **Correct application:** Decay is applied consistently in both L2 and L3 scoring paths using the same pattern: `rawScore * decayFactor`.
- **Correct ordering:** Results are sorted by decay-adjusted score, so staleness directly impacts ranking.
- **No double-application:** Decay is applied once per node during scoring, not again during merging or response construction.
- **Hybrid merge correctness:** In `hybridSearch()`, when a node appears in both vector and graph results, the score is boosted (`existing.score += r.score + 0.5`). The vector score already includes decay, so the boost is applied to the decay-adjusted value. This is correct — nodes found by both semantic similarity AND structural relationships get a relevance boost on top of their decayed score.

### Unit Test Coverage

The unit tests in `intent-router.unit.test.ts` (lines 19–43) test the `calculateTemporalDecay` function directly:
- ✅ Returns 1.0 for current date (no decay)
- ✅ Returns 0.5 for 30 days ago (half-life)
- ✅ Returns 0.25 for 60 days ago (two half-lives)
- ✅ Future dates capped at 1.0

However, there are **no integration tests** verifying that:
- Decay-adjusted scores actually appear in the `/search` response
- The ranking order changes when `lastVerifiedAt` differs between nodes
- The feedback endpoint correctly resets decay

### Security

- No security vulnerabilities in the decay application pipeline.
- The `score` field in the response is computed server-side from DB timestamps and cosine similarity — no user input can manipulate it.
- The `includePending` flag is properly validated through Zod schemas.

### Code Smell

- The frontend `query.tsx` defines a **duplicate** `SearchResultItem` interface instead of importing the generated type from `@workspace/api-client-react`. This creates a maintenance risk — if the backend response shape changes, the frontend interface will silently diverge. The project already has a generated `SearchResultItem` type in `lib/api-client-react/src/generated/api.schemas.ts` that includes `source`, `nodeLayer`, and all other fields.

## Round 3 — Integration & Completeness Review

### End-to-End Flow

1. **User submits query** → `POST /search` or `POST /mcp/query`
2. **`routeQuery()` classifies intent** → selects strategy (vector/graph/hybrid/direct)
3. **Vector/hybrid path** → `vectorSearchHandler()` computes `rawScore * decayFactor` for each node
4. **Results sorted by decayed score** → stale nodes sink lower
5. **Response returned** → decay-adjusted scores in `results[].score`
6. **Frontend displays** → `item.score.toFixed(2)` shows the decayed score

✅ The end-to-end flow is complete and functional.

### Feedback Loop

1. **User finds a result useful** → calls `POST /search/feedback` with `{ nodeId, nodeLayer, interactionType }`
2. **Feedback handler updates** `lastVerifiedAt` to `NOW()` for L2 or L3 nodes
3. **Next query** → the refreshed `lastVerifiedAt` results in a higher decay factor (closer to 1.0)
4. **Node rises in rankings** → positive reinforcement loop

✅ The feedback loop is complete.

### Cross-Strategy Consistency

| Strategy | Decay Applied? | Rationale |
|----------|---------------|-----------|
| `vector_search` | ✅ Yes | Semantic similarity scores are multiplied by decay factor |
| `hybrid` | ✅ Yes | Inherits decay from vector search; graph results use fixed scores |
| `graph_traversal` | ❌ No | Structural relationships don't decay; fixed scores (1.0, 0.7) |
| `direct_lookup` | ❌ No | Exact matches are not subject to staleness; fixed score (1.0) |

✅ This is consistent with the design: decay applies to semantic similarity, not exact or structural matches.

### Performance

- Decay calculation is O(1) per node — simple arithmetic on timestamps already fetched from DB.
- No additional DB queries required.
- Sorting by decayed score uses the same `Array.sort()` as raw scores — no performance impact.
- ✅ No performance concerns.

### Missing Tests

- **No integration test** for the full search pipeline with decay. The unit tests only cover the `calculateTemporalDecay` function in isolation.
- **No test** verifying that the `/search` response contains decay-adjusted scores.
- **No test** verifying that the feedback endpoint's `lastVerifiedAt` update actually affects subsequent query results.

## Findings

1. ✅ **Decay is correctly applied to knowledge query results.** The `vectorSearchHandler()` applies `calculateTemporalDecay()` to both L2 and L3 node scores before sorting. The `hybridSearch()` inherits this behavior. The `routeQuery()` orchestrator passes decay-adjusted results through to the API response without modification.

2. ✅ **All three search endpoints return decay-adjusted scores.** `POST /search`, `POST /mcp/query`, and `GET /mcp/search_knowledge` all call `routeQuery()` and return results with decay-adjusted scores.

3. ✅ **Feedback loop is complete.** The `POST /search/feedback` endpoint updates `lastVerifiedAt` to `NOW()`, which resets the decay clock for subsequent queries.

4. ⚠️ **Frontend uses a duplicate `SearchResultItem` interface.** `query.tsx` lines 17–26 define a local interface that is missing the `source` field and doesn't support `commit` layer or string IDs. It should import the generated type from `@workspace/api-client-react` to stay in sync with the backend.

5. ⚠️ **No decay metadata exposed to users.** The frontend displays `item.score.toFixed(2)` but provides no context about whether decay was applied, the node's verification date, or a staleness indicator. Users cannot tell why a relevant node ranks lower than expected.

6. ⚠️ **No integration tests for decay in search results.** Only the `calculateTemporalDecay` function is unit-tested. There are no tests verifying the full pipeline: query → decay application → response → feedback → re-query with refreshed decay.

7. ℹ️ **SQL LIKE fallback path does not apply decay.** This is acceptable for the degraded path (noted in 3.2.1).

---

## Overall Verdict

**✅ PASS**

Temporal decay is correctly applied to knowledge query results across all relevant search strategies (vector_search and hybrid). The decay-adjusted scores flow through the `routeQuery()` orchestrator to all three search endpoints (`POST /search`, `POST /mcp/query`, `GET /mcp/search_knowledge`). The feedback loop correctly resets the decay clock via `lastVerifiedAt` updates. The implementation faithfully follows ADR-007.

**Recommendations (non-blocking):**
1. Replace the local `SearchResultItem` interface in `query.tsx` with the generated type from `@workspace/api-client-react` to prevent divergence.
2. Add a staleness indicator or "last verified" date to the query result cards in the frontend.
3. Add integration tests verifying decay-adjusted scores in the full search pipeline, including the feedback refresh loop.
