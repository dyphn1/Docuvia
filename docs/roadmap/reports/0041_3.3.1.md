## Round 1 — Architecture & Design Review

### Design-to-Implementation Mapping

The design spec (ADR-007) defines a routing funnel with two O(1) pre-filters before falling back to LLM classification:

1. **Direct RAG filter** (line 669 of `intent-router.ts`):
   ```typescript
   if (query.includes("#attach") || /src\/|\.ts|\.md/i.test(query))
   ```
   This matches the design: queries containing `#attach` or file extensions (`.ts`, `.md`, or path `src/`) are routed directly to `direct_lookup` without LLM. ✅ Matches design.

2. **Graph RAG filter** (lines 679–701):
   ```typescript
   const tags = await db.select({ name: l1TagsTable.name }).from(l1TagsTable);
   // ... fetch all L2 node names ...
   for (const term of allArchitecturalTerms) {
     if (term && query.toLowerCase().includes(term.toLowerCase())) {
       classification = { strategy: "graph_traversal", ... };
       break;
     }
   }
   ```
   This matches the design: queries matching L1/L2 names are routed to `graph_traversal` without LLM. ✅ Matches design.

3. **LLM fallback** (lines 703–706):
   ```typescript
   if (!classification) {
     classification = await classifyIntent(query);
   }
   ```
   ✅ Matches design.

### Gaps Identified

- **Guardrail pre-injection (ADR-006 §3):** The design specifies that "guardrails and common query structures are identified by the router without LLM latency" and that the router should "pre-inject the guardrail natively." The current implementation has **no guardrail pre-injection mechanism**. The fast-path only sets the routing strategy but does not inject any guardrail content into the query or results. This is a **design gap** — the guardrail concept from ADR-006 is not implemented in the fast-path.

### Verdict on Architecture

The core O(1) fast-path filters are implemented as designed in ADR-007. The routing funnel correctly short-circuits LLM calls for `#attach`/extension queries and L1/L2 name matches. However, the guardrail pre-injection described in ADR-006 is missing.

## Round 2 — Code Quality & Security Review

### Issue 1: Overly Broad Regex Pattern (Medium Risk)

**File:** `intent-router.ts`, line 669
```typescript
if (query.includes("#attach") || /src\/|\.ts|\.md/i.test(query))
```

The regex `/src\/|\.ts|\.md/i` is not anchored and will match these strings **anywhere** in the query text:
- A query like `"describe the authentication flow"` matches because `"describe"` contains `"src"` as a substring (`de**scr**ibe` — actually this doesn't match `src/`, but `"discuss src patterns"` would).
- More importantly, `.ts` will match any occurrence of `ts` preceded by any character, e.g., `"what is the best approach?"` — the `t` in "best" followed by a space won't match, but `"update ts config"` would correctly match. However, `"posts about testing"` contains `ts` in `posts` which preceded by `.` would match if there's a dot.
- The `.md` pattern similarly matches any two characters followed by `md`.

**Recommendation:** Anchor the regex to match actual file extensions or paths:
```typescript
if (query.includes("#attach") || /(?:^|\s)(?:src\/.*|\.ts\b|\.md\b)/i.test(query))
```

### Issue 2: Substring Matching for L1/L2 Names (Medium Risk)

**File:** `intent-router.ts`, lines 690–699
```typescript
for (const term of allArchitecturalTerms) {
  if (term && query.toLowerCase().includes(term.toLowerCase())) {
```

This uses `String.includes()` which is a **substring match**, not a word-boundary match. A query containing `"auth"` would match an L2 node named `"Authentication"`, but a query containing `"authority"` would also match. More problematically, short L1/L2 names (e.g., `"API"`, `"UI"`, `"DB"`) would trigger false positives on many common English words.

**Recommendation:** Use word-boundary regex matching:
```typescript
const pattern = new RegExp(`\\b${escapeRegex(term)}\\b`, 'i');
if (pattern.test(query)) { ... }
```

### Issue 3: Not Actually O(1) — Database Query on Every Non-Direct Request (Low-Medium Risk)

**File:** `intent-router.ts`, lines 680–686
```typescript
const tags = await db.select({ name: l1TagsTable.name }).from(l1TagsTable);
let l2Query = db.select({ name: l2NodesTable.name }).from(l2NodesTable).$dynamic();
```

The design claims O(1) fast-path filters, but the L1/L2 name matching requires **two database queries** on every request that doesn't match the `#attach`/extension filter. This is O(n) in the number of architectural terms (for the in-memory loop), not O(1). For large knowledge graphs with hundreds of L2 nodes, this loop could become a bottleneck.

**Recommendation:** Cache L1/L2 names in memory with a TTL or use a Set-based lookup. Alternatively, use a single SQL query with `ILIKE` for all terms.

### Issue 4: No Unit Tests for Fast-Path Logic (Medium Risk)

**File:** `intent-router.unit.test.ts`

The unit test file only tests `escapeLike`, `calculateTemporalDecay`, and `sanitizeQuery`. There are **zero tests** for:
- The `#attach` regex pre-filter
- The L1/L2 name matching pre-filter
- The overall `routeQuery()` routing decision logic
- The interaction between fast-path and LLM fallback

**Recommendation:** Add tests for the fast-path logic, including edge cases (false positives, empty queries, queries matching both filters).

### Issue 5: Error Handling in Route Handlers (Low Risk)

**File:** `search.ts`, lines 29–31
```typescript
} catch (error) {
  res.status(500).json({ error: "Search failed" });
}
```

The error is not logged. Compare with `mcp.ts` (line 58) which does log the error. Inconsistent error handling.

**Recommendation:** Add error logging in `search.ts` catch block.

### Positive Observations

- The `sanitizeQuery()` function (lines 106–111) properly truncates to 2000 chars and strips control characters — good prompt injection mitigation.
- The `escapeLike()` function (lines 98–100) properly escapes SQL LIKE wildcards.
- The `directLookupHandler` uses a proper hex regex (`/^[0-9a-fA-F]{4,40}$/`) for commit hash detection.
- The `classifyIntent()` function has proper fallback handling with validated strategy names.

## Round 3 — Integration & Completeness Review

### Integration Points

The `routeQuery()` function is correctly integrated into:
1. **`POST /search`** (`search.ts`, line 27) — calls `routeQuery(query, projectId, limit)` without `includePending`
2. **`POST /mcp/query`** (`mcp.ts`, line 198) — calls `routeQuery(q, project_id, limit, includePending)` with `includePending`
3. **`GET /mcp/search_knowledge`** (`mcp.ts`, line 55) — calls `routeQuery(query, projectId, limit, includePending)` with `includePending`

All three entry points correctly invoke the fast-path logic before any LLM call.

### Missing Tests

- No unit tests for the fast-path regex or L1/L2 name matching
- No integration tests verifying that fast-path queries actually skip the LLM (e.g., by mocking `openai.chat.completions.create` and asserting it was NOT called)
- No tests for the `routeQuery()` function itself — only helper functions are tested

### Performance Concerns

- The L1/L2 name matching fetches **all** L1 tags and L2 nodes from the database on every non-direct request. For large projects, this could return hundreds of rows.
- The in-memory loop comparing each term against the query is O(n) where n = number of architectural terms.
- No caching layer exists for architectural terms.

### End-to-End Usability

The feature is functionally usable end-to-end:
- A query like `"#attach src/auth.ts"` will bypass LLM and go directly to `direct_lookup`
- A query like `"Authentication module dependencies"` will match the L2 node "Authentication" and route to `graph_traversal`
- A generic query like `"how does logging work"` will fall through to LLM classification

However, the false positive rate for both filters is likely high in practice due to the substring matching issues identified above.

## Overall Verdict

**⚠️ WARN**

The O(1) fast-path filters are implemented and functional — the `#attach`/extension regex and L1/L2 name matching both correctly bypass LLM classification as designed in ADR-007. The feature is integrated into all three query entry points (`/search`, `/mcp/query`, `/mcp/search_knowledge`).

However, there are significant quality concerns: the regex and substring matching are overly broad (likely causing false positives), the L1/L2 matching is not truly O(1) as the design claims, there are no tests for the fast-path logic, and the guardrail pre-injection from ADR-006 is missing. These issues warrant a WARN verdict.
