- **ADR-003 (Server-Side Zero-to-One):** Defines the `docuvia-knowledge` orphan branch as the canonical knowledge store, with `git fetch origin docuvia-knowledge` for developer consumption.
- **ADR-005 (Knowledge Abstraction Strategy):** Top-Down Archaeology strategy feeds into the knowledge that is serialized to the orphan branch.
- **architectural-decisions.md (Section: Orphan Branch):** "Knowledge is stored in three layers: PostgreSQL (full index), `docuvia-knowledge` orphan branch (human-readable YAML/Markdown), `.docuvia/` (lightweight manifest pointing to orphan branch HEAD)."
- **Glossary:** Defines the orphan knowledge branch as "a git orphan branch (e.g., `docuvia-knowledge`) that stores the canonical YAML/Markdown knowledge files independently of the source code tree."

## Round 1 — Architecture & Design Review

### Design Completeness

The design spec (ADR-004, architectural-decisions.md) defines the orphan branch writer as the mechanism to serialize knowledge from PostgreSQL into the `docuvia-knowledge` orphan git branch. The implementation at `orphan-branch-writer.ts` covers this:

1. **Data Query:** Queries all L2 nodes for a given `projectId` from `l2NodesTable`, then queries L3 nodes for each L2 node from `l3NodesTable`.
2. **YAML Serialization:** Builds L1 tags YAML (`buildL1TagsYaml`), L2 module YAML per node (`buildL2ModuleYaml`), and L3 decision Markdown per node (`buildL3DecisionMd`).
3. **Git fast-import:** Uses `git fast-import` protocol to write files directly to the `docuvia-knowledge` branch without a working tree checkout. This is the correct technical approach for writing to an orphan branch programmatically.

### Gaps Between Design and Implementation

1. **L1 Tag Names Not Populated:** The `buildL1TagsYaml` function at line 94 is called with an empty array `[]`:
   ```typescript
   const l1TagsYaml = buildL1TagsYaml([]);
   ```
   This means the `l1_tags.yaml` file will always contain `tags: []` regardless of actual L1 tags in the database. The comment at line 93 says "Collect L1 tag names from L2 nodes (through join — simplified: use distinct names from DB)" but this simplification drops all L1 tag data. This is a meaningful gap — the orphan branch will never contain L1 tag information.

2. **No L1 Tag Query:** The function never queries `l1TagsTable` or `l2NodeL1TagsTable` to resolve L1 tag names. The design spec says L1 tags are global categorizations and should be serialized.

3. **No Error Propagation:** The `writeKnowledgeToOrphanBranch` function catches all errors and only logs them (line 146). The caller in `sync.ts` (line 233) also handles errors non-fatally. This is intentional (fire-and-forget) but means silent failures are possible — if `git fast-import` fails (e.g., the orphan branch doesn't exist yet, or git is not in the PATH), the knowledge won't be written with no indication to the caller.

4. **No Handling of Pre-existing Branch:** The design implies writing to the orphan branch, but if the branch doesn't exist yet, the first `git fast-import` call will create it. However, if the branch already exists, the `deleteall` command in the fast-import data (line 164) will replace ALL files in the branch. This is correct for a full snapshot rewrite, but it means incremental delta writing is not supported — every call rewrites the entire project's knowledge.

5. **No Integration with Generate Pipeline:** The generate route (`generate.ts`) does NOT call `writeKnowledgeToOrphanBranch` after generating knowledge. Only the sync route (`sync.ts`) triggers it. This means knowledge generated via the generate API endpoint will NOT be reflected in the orphan branch until a separate sync call is made. This is a significant architectural gap — the server-side metabolism path does not update the orphan branch.

6. **unused `git show` call:** Line 121 calls `git show ${branch}:${filePath} 2>/dev/null || true` inside the file loop but discards the result. This appears to be dead code from an earlier approach and is never used.

## Round 2 — Code Quality & Security Review

### Code Structure

The code is well-structured as a single exported function with helper functions for serialization. The three builder functions (`buildL1TagsYaml`, `buildL2ModuleYaml`, `buildL3DecisionMd`) follow a clean separation of concerns.

### Security Considerations

1. **Command Injection via `execAsync`:** The function uses `child_process.exec` (via `promisify`) to run git commands. Most commands use hardcoded strings or data from the database (not user input), which is safe. However:
   - Line 125: `printf '%s' ${JSON.stringify(content)} | git hash-object -w --stdin` — this is actually not used effectively (the blob hash is logged but not used for the actual write). The real write happens via `git fast-import` with inline data.
   - Line 139: `printf '%s' ${JSON.stringify(fastImportData)} | git fast-import --quiet` — the `fastImportData` contains file contents from the database. If file contents contain null bytes or other special characters, `printf '%s'` could truncate data. This is a minor risk since the content comes from AI-generated knowledge, not direct user input.

2. **Path Traversal:** Internal file paths are constructed as `${projectId}/l2_modules/${l2Slug}.yaml` where `projectId` is a number and `l2Slug` is derived from the L2 node name via `slugify()`. The `slugify` function strips all non-alphanumeric characters, preventing path traversal. Safe.

3. **Git Availability Check:** Lines 84-89 check for git CLI availability and gracefully skip if unavailable. Good defensive design.

### Code Smells

1. **Dead Code (lines 119-132):** The loop iterates over files and calls `git hash-object` to stage blobs, but the resulting blob hashes are only logged and never used. The actual write uses `git fast-import` with inline data. This is approximately 15 lines of dead code that should be removed.

2. **No Tests:** There are no unit tests or integration tests for `orphan-branch-writer.ts`. This is a critical component of the Git-isomorphic graph architecture and should have tests covering: serialization correctness, fast-import data format, error handling, and the L1 tags gap.

3. **Missing Return:** The unused code on line 121 calls a git show but the timeout/minutes don't matter since the result is discarded with `|| true`.

## Round 3 — Integration & Completeness Review

### Integration with Sync Route

The integration with `sync.ts` (line 232-235) is correct — after syncing commits and updating the database, it fires off a fire-and-forget write to the orphan branch:

```typescript
writeKnowledgeToOrphanBranch(projectId).catch((err) => {
  logger.warn({ err, projectId }, "[sync] orphan branch write failed (non-fatal)");
});
```

This ensures the orphan branch stays consistent with the database after every sync.

### Integration with KnowledgeStore (Consumer)

The VS Code extension's `KnowledgeStore.ts` (lines 286-346) correctly implements the consumer side — reading from the `docuvia-knowledge` orphan branch via `git show` and `git ls-tree` as an offline fallback (Tier 3). This is properly implemented and tested in previous verification rounds.

### Integration Gaps

1. **Generate Pipeline Not Connected:** As noted above, after the generate pipeline creates L2/L3 nodes, the orphan branch is not updated. This means:
   - Users who generate knowledge via the API and then trigger a `git fetch origin docuvia-knowledge` will NOT see the newly generated knowledge.
   - The orphan branch will be stale until a sync event occurs.

2. **Git Hook Not Self-Contained:** The `githook-template.sh` calls `docuvia sync --branch ... --commits ...`, but no such CLI exists (item 3.4.3 is marked ❌ Todo). The hook template references a non-functional command. Even if the hook were installed, it would fail because the `docuvia sync` CLI doesn't exist.

3. **No Delta/Incremental Write:** The current implementation rewrites ALL files for the project on every call (`deleteall` in fast-import). For large projects with hundreds of L3 nodes, this could be slow. An incremental approach (only writing changed files) would be more efficient but is a minor concern.

### End-to-End Usability

The feature is **partially usable** end-to-end:
- Server-side write: Functional (called from sync route)
- Client-side read: Functional (KnowledgeStore reads from orphan branch)
- Trigger mechanism: Broken (no `docuvia sync` CLI to trigger from git hook)
- Generate pipeline integration: Missing (orphan branch not updated after generation)

## Findings

### Issues

1. **[HIGH] L1 Tags Always Empty in Orphan Branch:** `buildL1TagsYaml([])` always produces `tags: []`. The L1 tags query and `l2_node_l1_tags` join are never performed. This means the orphan branch knowledge files will never contain L1 tag information.

2. **[HIGH] Generate Pipeline Does Not Update Orphan Branch:** After `POST /projects/:id/generate` creates new L2/L3 nodes, the orphan branch is not updated. Knowledge generated via the API is invisible to the git-based sync mechanism.

3. **[MEDIUM] Dead Code:** Lines 119-132 in `orphan-branch-writer.ts` contain a loop that computes blob hashes via `git hash-object` but never uses them. This should be removed.

4. **[MEDIUM] No Tests:** Zero test coverage for the orphan branch writer. Given its role as the bridge between PostgreSQL and Git-isomorphic storage, tests are critical.

5. **[LOW] printf '%s' Truncation Risk:** Using `printf '%s'` to pipe data to `git fast-import` could truncate content at null bytes. For AI-generated Markdown/YAML this is unlikely but technically possible.

### Risks

- The orphan branch could become permanently stale if the sync pipeline is not the primary mechanism for knowledge updates. Since the generate pipeline doesn't trigger an orphan branch write, any operation that modifies knowledge through the generate endpoint will not be reflected in the orphan branch.
- Without the `docuvia sync` CLI (item 3.4.3), the entire git hook mechanism is dead on installation. The githook template exists but references a non-existent command.

### Recommendations

1. **Fix L1 tags:** Query `l1TagsTable` joined with `l2NodeL1TagsTable` to collect L1 tag names and include them in the orphan branch YAML.
2. **Connect generate pipeline:** Call `writeKnowledgeToOrphanBranch(projectId)` after the generate pipeline completes successfully, similar to how `sync.ts` does it.
3. **Remove dead code:** Delete lines 119-132 in `orphan-branch-writer.ts`.
4. **Add tests:** Write unit tests for the serialization functions and an integration test that verifies the fast-import output.
5. **Consider incremental writes:** For large projects, consider tracking which files changed and only writing those, rather than `deleteall` + full rewrite.

---

## Overall Verdict

## ⚠️ WARN

The orphan branch writer is **implemented and functional** — the checklist marking of ❌ Todo is outdated. The core `git fast-import` approach is correct and the integration with the sync route and KnowledgeStore consumer works. However, there are meaningful gaps: L1 tags are always empty, the generate pipeline doesn't trigger orphan branch updates, and there is dead code and no test coverage. These issues prevent the feature from being fully usable end-to-end.
