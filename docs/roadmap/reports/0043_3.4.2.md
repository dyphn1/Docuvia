# Verification Report: 3.4.2 — Bidirectional Sync Between Client and Server

**Date:** 2026-06-09
**Item ID:** 3.4.2
**Description:** Bidirectional sync between Client and Server — the VS Code client pushes local knowledge changes to the server (client→server), and the server pushes updated knowledge back to the client via the orphan branch and/or API (server→client).

---

## Design Spec References

- **ADR-003 (Server-Side Zero-to-One):** Defines the orphan branch protocol. The `docuvia-knowledge` orphan branch is the canonical knowledge store. Developers fetch this branch to get the latest knowledge snapshot. The git hook (`post-push`) triggers `docuvia sync`, which uploads local changes to the server. The server writes back to the orphan branch.
- **ADR-008 (Orphan Branch as Knowledge Store):** Three-layer storage: PostgreSQL (full index), `docuvia-knowledge` orphan branch (human-readable YAML/Markdown), `.docuvia/` (lightweight manifest). The git hook triggers `docuvia sync` which uploads local changes to the server, which in turn updates the orphan branch.
- **Glossary:** Defines `docuvia sync` as "The CLI command (not yet implemented) triggered by the `post-push` git hook. Uploads the local `.docuvia/` manifest and any newly local-reviewed knowledge to the Docuvia server, which in turn updates the orphan knowledge branch and PostgreSQL."
- **architectural-decisions.md (Section 9.3):** Lists the orphan branch protocol as the sync mechanism between client and server.

## Round 1 — Architecture & Design Review

### Design Completeness

The design spec defines bidirectional sync as a two-way protocol:

1. **Client → Server (push):** When a developer pushes commits, the `post-push` git hook triggers `docuvia sync`, which sends the branch name, commit hashes, and configYaml to `POST /sync`. The server processes these, updates the database, and triggers an orphan branch write.
2. **Server → Client (pull):** The server writes updated knowledge to the `docuvia-knowledge` orphan branch. The client can then fetch this branch (`git fetch origin docuvia-knowledge`) or pull the full graph via `GET /projects/{id}/graph`.

### Gaps Between Design and Implementation

1. **[CRITICAL] `docuvia sync` CLI Does Not Exist:** The entire client→server sync path depends on a `docuvia sync` CLI command (item 3.4.3, marked ❌ Todo). The git hook template at `githook-template.sh` calls `docuvia sync --branch "$BRANCH" --commits "$COMMITS"`, but this CLI has never been implemented. Without it, the git hook is dead on installation — it will fail with "command not found."

2. **[CRITICAL] No Automatic Sync Trigger in VS Code Extension:** The VS Code extension's `extension.ts` activation code does NOT register any automatic sync trigger. There is no `git.push` event listener, no post-commit hook registration, and no background sync timer. The `CentralServerClient.sync()` method exists but is never called automatically — it would need to be invoked manually by a command or external trigger.

3. **[HIGH] KnowledgeStore Reads from `.docuvia/` Working Tree, Not Orphan Branch as Primary:** The `KnowledgeStore._loadWorkspace()` method (lines 141-201) has a three-tier loading strategy:
   - Primary: Server API (`pullSnapshot`) — only when server is configured
   - Fallback 1: Local `.docuvia/` files from the working tree filesystem
   - Fallback 2: Git orphan branch via `git show`
   
   The problem is that Fallback 1 reads from the `.docuvia/` working tree, which per ADR-008 should only contain a lightweight manifest — NOT the full knowledge content. The current implementation reads `l1_tags.yaml`, `l2_modules.yaml`, `l3_router.yaml`, and `l3_decisions/` from `.docuvia/`, treating it as the full knowledge store. This contradicts the ADR-008 design where `.docuvia/` is just a manifest pointing to the orphan branch HEAD.

4. **[HIGH] Server Response Mismatch:** The OpenAPI spec defines `SyncResponse` with a `message` field (required), but the actual `sync.ts` implementation returns `{ ok, projectId, pushedBranch, commitsProcessed, mainBranchPromotion }` — a completely different shape. This means any client code generated from the OpenAPI spec would receive unexpected fields.

5. **[MEDIUM] No Conflict Resolution:** ADR-003 describes conflict resolution: "When Developers A and B push overlapping L2 definitions, the Server LLM performs a horizontal comparison and resolves the collision automatically." The `POST /sync` route has no conflict detection or resolution logic. It simply updates `llm_configs`, sets `branchName` on commits, promotes validity on main branch pushes, and triggers an orphan branch write. There is no LLM-based conflict resolution.

6. **[MEDIUM] No Bidirectional Sync Test Coverage:** There are no tests for the sync route (`sync.ts`), the `CentralServerClient.sync()` method, or the end-to-end sync flow.

## Round 2 — Code Quality & Security Review

### Code Structure

- `sync.ts` (246 lines): Well-structured with Zod validation, defensive checks (project existence, empty arrays), and clear step-by-step processing. Uses fire-and-forget pattern for orphan branch writes.
- `CentralServerClient.sync()` (lines 87-111): Clean implementation with proper error handling (401 detection, generic error). Uses `x-docuvia-token` header for auth.
- `githook-template.sh` (6 lines): Simple shell script, but references a non-existent CLI.

### Security Considerations

1. **Auth Token in `x-docuvia-token` Header:** The `CentralServerClient.sync()` uses a custom `x-docuvia-token` header rather than standard `Authorization: Bearer <token>`. This is consistent with the rest of the client but deviates from standard HTTP auth practices. The MCP endpoints use Bearer token auth — there's an inconsistency.

2. **No Input Sanitization on `configYaml`:** The `configYaml` field in the sync body is parsed by `parseSimpleYaml()` which only handles top-level keys. However, the parsed values are used directly in DB updates without further validation. A malicious `configYaml` with unexpected keys would be silently ignored, but a `configYaml` with a very large `model` string could be inserted into the DB.

3. **No Rate Limiting on Sync Endpoint:** The `POST /sync` endpoint has no rate limiting. A client could flood the server with sync requests, each triggering database writes and orphan branch operations.

### Code Smells

1. **Dead Code in `orphan-branch-writer.ts`:** Lines 119-132 compute blob hashes via `git hash-object` but never use them (the actual write uses `git fast-import` with inline data). This was noted in the 3.4.1 verification report.

2. **Inconsistent Response Shape:** The sync route returns `{ ok, projectId, pushedBranch, commitsProcessed, mainBranchPromotion }` but the OpenAPI spec defines `SyncResponse` with only `{ message }`. This is a spec-implementation drift.

## Round 3 — Integration & Completeness Review

### Integration Points

1. **Server Sync Route → Orphan Branch Writer:** ✅ Connected. `sync.ts` calls `writeKnowledgeToOrphanBranch(projectId)` after processing.

2. **Client CentralServerClient → Server Sync Route:** ⚠️ Method exists but is never called automatically. No command, no hook, no timer triggers it.

3. **Git Hook → `docuvia sync` CLI:** ❌ Broken. The hook template references a non-existent CLI.

4. **Server → Client (Orphan Branch):** ⚠️ Partially functional. The server writes to the orphan branch, and `KnowledgeStore._loadFromGit()` can read from it. But this is only used as a fallback when both the server API and local `.docuvia/` files are unavailable.

5. **Server → Client (API Pull):** ✅ Functional. `CentralServerClient.pullSnapshot()` calls `GET /projects/{id}/graph` and `KnowledgeStore._mapApiSnapshot()` maps the response. This works when the server is configured.

### End-to-End Usability

The bidirectional sync is **NOT usable end-to-end**:

- **Client → Server path:** Broken. No `docuvia sync` CLI exists, no automatic trigger in the VS Code extension. A developer would need to manually call `POST /sync` with the correct payload — there is no supported workflow to do this.
- **Server → Client path:** Partially functional. The server writes to the orphan branch, and the client can read from it as a fallback. However, the client's primary loading path (local `.docuvia/` files) does not match the ADR-008 design where `.docuvia/` is a lightweight manifest.

### Missing Components

1. **`docuvia sync` CLI** (item 3.4.3): The most critical missing piece. Without it, the entire client→server sync path is non-functional.
2. **Automatic sync trigger in VS Code extension:** No `git.push` event listener or background sync mechanism.
3. **Conflict resolution logic:** ADR-003 describes LLM-based conflict resolution for overlapping L2 definitions, but this is not implemented.
4. **Sync route tests:** No unit or integration tests for the sync endpoint.
5. **OpenAPI spec alignment:** The `SyncResponse` schema doesn't match the actual implementation.

## Findings

### Issues

1. **[CRITICAL] `docuvia sync` CLI Does Not Exist:** The entire client→server sync path depends on this CLI (item 3.4.3, marked ❌ Todo). The git hook template references it but it has never been built. The bidirectional sync cannot function without it.

2. **[CRITICAL] No Automatic Sync Trigger in VS Code Extension:** The `CentralServerClient.sync()` method exists but is never invoked automatically. There is no git push listener, no background timer, and no command that triggers sync. The extension relies entirely on manual user action.

3. **[HIGH] OpenAPI Spec/Implementation Mismatch:** `SyncResponse` in the spec has `{ message }` but the implementation returns `{ ok, projectId, pushedBranch, commitsProcessed, mainBranchPromotion }`. Generated clients would receive unexpected data.

4. **[HIGH] KnowledgeStore Loading Strategy Contradicts ADR-008:** The `.docuvia/` working tree is treated as a full knowledge store (reading `l1_tags.yaml`, `l2_modules.yaml`, `l3_decisions/`), but ADR-008 says `.docuvia/` should only contain a lightweight manifest pointing to the orphan branch HEAD.

5. **[MEDIUM] No Conflict Resolution:** ADR-003 describes LLM-based conflict resolution for overlapping L2 definitions, but `sync.ts` has no conflict detection or resolution logic.

6. **[MEDIUM] No Tests:** Zero test coverage for the sync route, the client sync method, or the end-to-end sync flow.

7. **[LOW] Inconsistent Auth Header:** `CentralServerClient` uses `x-docuvia-token` header while MCP endpoints use standard `Authorization: Bearer <token>`.

### Risks

- The bidirectional sync architecture is fundamentally incomplete. Without the `docuvia sync` CLI, the system relies entirely on the server-side generate pipeline to populate knowledge, and clients can only pull (not push) knowledge changes.
- The KnowledgeStore's reliance on `.docuvia/` as a full knowledge store means that if a developer checks out a different branch, the `.docuvia/` files (which are committed to the repo) may contain stale knowledge from a different branch — contradicting ADR-008's design goal of "branch-agnostic — checking out any feature branch does not change the knowledge view."

### Recommendations

1. **Implement `docuvia sync` CLI (item 3.4.3):** This is the highest priority. The CLI should accept `--branch` and `--commits` arguments, read the `.docuvia/` manifest for the project ID, and call `POST /sync`.
2. **Add automatic sync trigger in VS Code extension:** Register a `git.push` event listener or install a git hook programmatically during `docuvia.initProject` that calls `CentralServerClient.sync()`.
3. **Fix OpenAPI spec:** Update `SyncResponse` to match the actual implementation shape, or update the implementation to match the spec.
4. **Align KnowledgeStore with ADR-008:** Make the orphan branch the primary loading path (not a fallback), and treat `.docuvia/` as a lightweight manifest only.
5. **Add conflict resolution:** Implement LLM-based conflict detection and resolution in the sync route for overlapping L2 definitions.
6. **Add tests:** Write integration tests for the sync route and unit tests for the client sync method.

---

## Overall Verdict

## ❌ FAIL

The bidirectional sync between Client and Server is **not implemented**. While individual components exist (server `POST /sync` route, `CentralServerClient.sync()` method, orphan branch writer, KnowledgeStore git fallback), the critical glue that makes them work together — the `docuvia sync` CLI and automatic sync triggers — is entirely missing. The system has no working mechanism for the client to push local changes to the server, which is half of the "bidirectional" contract. The server-to-client direction is partially functional (orphan branch writes + API pull) but the KnowledgeStore's loading strategy contradicts the ADR-008 design. The feature cannot be used end-to-end by any developer.
