## Round 1 — Architecture & Design Review

### Design Completeness

The `docuvia sync` CLI is a critical component in the bidirectional sync architecture:

1. **Trigger:** The `post-push` git hook (`githook-template.sh`) fires after `git push`, running: `docuvia sync --branch "$BRANCH" --commits "$COMMITS"`.
2. **CLI Responsibility:** Per the design plan, the CLI should:
   - Read `.docuvia/config.yaml` for the project ID and server URL.
   - Read `.docuvia/.snapshot-ref` for the current orphan branch snapshot.
   - Call `POST /sync` with `{ projectId, pushedBranch, pushedCommits, configYaml }`.
   - After the server responds, run `git fetch origin docuvia-knowledge` to update the local snapshot ref.
3. **Server Processing:** The `POST /sync` endpoint (already implemented in `sync.ts`) handles the server-side logic: upserting llm_configs, updating commit branch names, promoting validity on main branch, and writing to the orphan branch.

### Gap Analysis

**The `docuvia sync` CLI does not exist.** This is confirmed by:

1. **No CLI binary/package:** There is no `bin` entry in any `package.json` in the repository. A search for `"bin"` across all `package.json` files returned zero results. There is no `cli/` directory, no `docuvia-sync` executable, and no script registered as a CLI entry point.
2. **No npm workspace for a CLI:** The workspace packages are `kg-engine`, `api-server`, `db`, `api-spec`, `vscode-client`, and `scripts`. None of them define a CLI binary.
3. **Git hook references non-existent command:** The `githook-template.sh` (line 6) calls `docuvia sync --branch "$BRANCH" --commits "$COMMITS"`, but there is no `docuvia` command available on the system PATH.
4. **No command in VS Code extension commands:** The VS Code extension registers commands (`docuvia.initProject`, `docuvia.refreshKnowledgeGraph`, etc.) but does not register a `docuvia.sync` CLI-like command that could serve as a substitute.

**Design Plan vs. Implementation:**

The `implement_v2-core-architecture.md` plan describes the CLI as a "new binary or VS Code code" (Section 3.3). Neither option has been implemented:
- No standalone binary (`docuvia-sync`, `docuvia`, etc.) exists.
- No npm package with a `bin` field exists.
- The VS Code extension has no sync-triggering command registered.

### Contradictions

No contradictions between design documents. All design documents consistently describe the CLI as not yet implemented.

## Round 2 — Code Quality & Security Review

### Code That Would Be Needed

Since the CLI doesn't exist, the review covers the components that would interact with it:

1. **`githook-template.sh` (6 lines):** Simple shell script, well-structured. However, it has a subtle issue: the `COMMITS` variable builds a comma-separated list with a trailing comma (e.g., `abc123,def456,`). The server-side `sync.ts` expects `pushedCommits` as `z.array(z.string())`, and each element would need to be a valid commit hash. The trailing comma would create an empty string element `""` which would fail validation. This is a latent bug in the hook template that would surface once the CLI exists.

2. **`sync.ts` — `POST /sync` endpoint (246 lines):** Well-structured with Zod validation, defensive checks, and clear step-by-step processing. The endpoint is properly registered in `routes/index.ts` (line 46: `router.use(syncRouter)`). No issues with the server-side code.

3. **`CentralServerClient.sync()` (lines 87-111):** Clean implementation with proper error handling. Uses `x-docuvia-token` header for auth. This method exists in the VS Code client but is never called automatically — it would be the model for the CLI's HTTP call.

### Security Considerations (for when the CLI is implemented)

1. **Token Storage:** The CLI would need to read an auth token. The VS Code client uses `CredentialManager` backed by VS Code's `SecretStorage`. A standalone CLI would need a secure token storage mechanism (e.g., system keychain via `keytar` or a local config file with restricted permissions).
2. **Server URL in Config:** The `.docuvia/config.yaml` is a committed, plaintext file. The server URL would be visible to anyone with repo access. This is acceptable for most setups but should be documented.
3. **Input Validation:** The CLI would receive `--branch` and `--commits` as command-line arguments. These should be validated before being passed to the server (the server does validate via Zod, but pre-validation is good practice).

## Round 3 — Integration & Completeness Review

### Integration Points

```
Developer pushes commits
        ↓
post-push git hook fires
        ↓
[docuvia sync --branch X --commits Y]  ← MISSING: does not exist
        ↓
POST /sync  ← EXISTS: sync.ts route ready
        ↓
Server updates DB + writes orphan branch
        ↓
git fetch origin docuvia-knowledge  ← Would update local snapshot
```

The integration chain is broken at the first link. The server-side (`POST /sync`) and the orphan branch writer are both implemented and functional. The missing piece is entirely on the client side — the CLI that bridges the git hook to the server.

### End-to-End Usability

The feature is **completely unusable** in its current state. There is no mechanism for a developer to trigger a sync from their local machine after pushing commits. The git hook template exists but references a non-existent command, so even if installed, the hook would fail silently (shell scripts in git hooks typically swallow errors).

### What Is Needed to Complete This Feature

A minimal implementation requires:

1. **CLI Binary:** Create a new npm package (e.g., `@workspace/cli` or extend `scripts/`) with a `bin` entry point that exports a `docuvia` command with a `sync` subcommand.
2. **Argument Parsing:** Accept `--branch`, `--commits`, and `--project-root` (optional) flags.
3. **Config Reading:** Read `.docuvia/manifest.yaml` or `.docuvia/config.yaml` to get the `projectId` and `serverUrl`.
4. **HTTP Call:** Call `POST /sync` with the project ID, branch, commits, and config YAML content.
5. **Post-Sync Fetch:** After a successful response, run `git fetch origin docuvia-knowledge` and update `.docuvia/.snapshot-ref`.
6. **Auth:** Read the API token from a credential store (system keychain or `.docuvia/` config).
7. **Package Distribution:** Either bundle the CLI with the VS Code extension (via `postinstall` or extension activation) or publish as a standalone npm package.
8. **Fix Hook Template:** Fix the trailing comma bug in `githook-template.sh` where `COMMITS` ends with a trailing comma.

### Missing Tests

- No tests exist for `sync.ts` (the server endpoint).
- No tests exist for `CentralServerClient.sync()` (the VS Code client method).
- No tests would exist for the CLI (since it doesn't exist).

## Findings

### Issues

1. **[CRITICAL] `docuvia sync` CLI Does Not Exist:** There is no CLI binary, no npm `bin` entry, and no command in any package that implements the `docuvia sync` functionality. The entire client→server sync path is non-functional. This is the single most critical missing piece for the bidirectional sync feature (item 3.4.2).

2. **[HIGH] Git Hook Template References Non-Existent Command:** The `githook-template.sh` calls `docuvia sync` which will fail with "command not found" if the hook is installed. This means the git hook mechanism is dead on installation.

3. **[MEDIUM] Trailing Comma Bug in Git Hook Template:** In `githook-template.sh` line 5: `git log @{u}..HEAD --format=%H | tr '\n' ','` produces output like `abc123,def456,` (trailing comma). When the CLI splits this on commas, the last element will be an empty string `""`, which would pass the `z.string()` validation in the `pushedCommits` array but would never match any commit hash in the database.

4. **[LOW] No Defined CLI Package:** There is no designated workspace package or directory where the CLI binary would live. The project has no precedent for a standalone CLI — all existing code is organized into workspace packages (`api-server`, `vscode-client`, `kg-engine`, etc.). A decision needs to made about where the CLI belongs.

### Risks

- **Complete Sync Path Failure:** Without the CLI, the entire client→server sync direction is non-functional. The bidirectional sync (item 3.4.2) cannot work until this is resolved.
- **Cascading Dependency:** Items 3.4.2 (bidirectional sync) and 3.4.4 (KnowledgeStore rewrite) both depend on `docuvia sync` existing. Until the CLI is built, these items cannot be completed.

### Recommendations

1. **Create the `docuvia sync` CLI as the highest priority.** This is the critical path blocker for the entire bidirectional sync milestone (Milestone 3.4).
2. **Choose a packaging strategy:** Either (a) create a new `@workspace/cli` package with a `bin: { "docuvia": "./dist/cli.js" }` entry, or (b) extend the existing `@workspace/scripts` package to include a sync command.
3. **Fix the trailing comma bug in `githook-template.sh`.** Use `tr '\n' ',' | sed 's/,$//'` or equivalent to strip the trailing comma.
4. **Add token storage for the CLI:** Use `keytar` (system keychain) or a local config file with restricted permissions for storing the API token outside of VS Code.
5. **Add tests for the sync endpoint** in `sync.ts` (integration test with `withRollback`) and for the CLI unit logic.

---

## Overall Verdict

## ❌ FAIL

The `docuvia sync` CLI is **not implemented**. There is no CLI binary, no npm package with a `bin` entry, and no code that performs the sync operation from the command line. The git hook template (`githook-template.sh`) references a non-existent `docuvia sync` command. While the server-side `POST /sync` endpoint and the `CentralServerClient.sync()` method both exist and are functional, the standalone CLI that bridges the git hook to the server is entirely missing. This is the critical missing link that prevents the entire bidirectional sync flow (item 3.4.2) from working.
