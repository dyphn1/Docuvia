## Round 1 — Architecture & Design Review

**Does the design document correctly describe the feature?**

The design document (`init-project.md`) accurately describes the `docuvia.initProject` command flow. The implementation in `extension.ts` (lines 417–507) follows the documented flow:

1. **Workspace Resolution** — Correctly handles three paths: explicit node from TreeView, single-root workspace, and multi-root QuickPick selection. The multi-root filter correctly excludes already-initialized folders.
2. **Project Naming** — Uses `showInputBox` with the directory basename as placeholder and default value, including `validateInput` to prevent empty names (BUG G-1 fix confirmed).
3. **Scaffolding** — Creates `.docuvia/` and `.docuvia/l3_decisions/` directories, then writes three YAML skeleton files: `l1_tags.yaml`, `l2_modules.yaml`, `l3_router.yaml`.
4. **Post-Initialization** — Calls `store.load()` and shows a success toast.

**Are there gaps between the design spec and the actual implementation?**

Several gaps and deviations identified:

1. **`project_name` key duplicated in `l1_tags.yaml` skeleton** (line 488 of `extension.ts`): The template writes both a commented-out example line (`# project_name: ${projectName}`) and an actual key (`project_name: "${projectName}"`). The `KnowledgeStore._loadWorkspace()` parser (line 157) only extracts `project_name` via the object format path, so this is functionally correct, but the commented example line is misleading.

2. **Force-overwrite dialog not fully implemented per design spec** — The design spec shows a flow where the user picks an already-initialized folder, then sees an overwrite prompt. The actual implementation adds an overwrite prompt (lines 451–460) that does `store.snapshots.has(targetRoot)` check, but then the multi-root QuickPick at line 433 filters out already-initialized folders via `!store.snapshots.has(f.uri.fsPath)`. So in multi-root mode, the user can never pick an already-initialized folder, and the overwrite dialog is unreachable in that path. Only the single-root path (line 429) can trigger it. The design spec explicitly notes this as a "CONFLICT — Force-Overwrite Prompt Not Implemented" and it remains partially resolved.

3. **`manifest.yaml` is never created by `initProject`** — The `KnowledgeStore._loadWorkspace()` reads `manifest.yaml` first (line 131) for `project_id` and `manifest.modules`. It falls back to local YAML files when the manifest is absent, so the system still functions, but the `ManifestSchema` with `project_id` and `modules` is never populated by `initProject`. The server-augmented and git-fallback code paths requiring `manifest.project_id` are unreachable for projects initialized solely via `initProject`.

4. **Activation event creates chicken-and-egg problem** — The `workspaceContains:.docuvia` activation event means the extension only activates when `.docuvia/` already exists. The `initProject` command requires activation, so it cannot be invoked in a fresh workspace without `.docuvia/`. The `onStartupFinished` activation event partially mitigates this, but the `docuvia.initProject` command still cannot appear in the Command Palette before activation.

5. **`viewsWelcome` is partially implemented** — The `package.json` includes a `viewsWelcome` entry (lines 117–123) that shows a welcome message with an "Analyze Project Architecture" button when `!docuvia:isInitialized`. However, it does NOT include a button for "Init Project" as noted in audit docs (`audit_vscode_extension_phase1_5.md`, P2-3).

**Are there contradictions between design documents?**

- The `init-project.md` design doc's mermaid flowchart shows a clean overwrite path, but the implementation note (line 51) acknowledges this as deferred. The actual code has a partial overwrite mechanism that makes the flowchart inaccurate.

## Round 2 — Code Quality & Security Review

**Is the implementation code well-structured?**

The `initProject()` function (lines 417–507) is well-structured with clear sections:
- Workspace resolution (lines 418–446)
- Already-initialized check with overwrite prompt (lines 450–460)
- Project name input with validation (lines 462–472)
- Directory creation (lines 474–479)
- File writing with conditional overwrite/skip logic (lines 481–499)
- Post-init reload and notification (lines 501–506)

The function is ~90 lines, which is reasonable for its complexity. The `writeFile` conditional at line 482 (`isAlreadyInitialized ? ... : writeIfAbsent`) is a clean approach to differentiate new init from re-init.

**Are there code smells or anti-patterns?**

1. **Duplicate condition check** — When `projectName` is empty, line 470 checks `projectName === undefined || projectName.trim().length === 0`. But `validateInput` at line 467 already prevents empty strings from being accepted (returning an error message). The `trim().length === 0` check at line 470 is redundant given that `validateInput` prevents submission of empty strings.

2. **Silent error swallowing in `writeIfAbsent`** (line 694–701) — If `vscode.workspace.fs.stat()` throws for reasons other than "file not found" (e.g., permission error), the function silently proceeds to write. This could mask permission issues.

3. **No input sanitization on `projectName`** — The project name from `showInputBox` is directly interpolated into the YAML content (line 488: `project_name: "${projectName}"`). If the user enters a name containing YAML-significant characters (e.g., quotes, colons, `#`), the resulting YAML could be malformed. For example, a project name of `My "Project"` would produce `project_name: "My "Project""` which is invalid YAML.

**Security considerations:**

- No XSS or injection risks in the VS Code extension context.
- The `projectName` is only written to local files, not transmitted to any server.
- No credential or sensitive data handling in this function.

## Round 3 — Integration & Completeness Review

**Does the feature integrate correctly with other parts of the system?**

1. **KnowledgeStore reload** — The `store.load()` call at line 502 correctly triggers a full reload of the knowledge graph. The reload clears existing snapshots and re-reads from disk. The `onDidLoad` event fires, which the `KnowledgeGraphTreeProvider` listens to for UI updates.

2. **FileSystemWatcher integration** — The newly created `.docuvia/` files trigger the `FileSystemWatcher` (set up in `KnowledgeStore.startWatcher()`), which also schedules a reload. This means the reload may happen twice (once from `store.load()` at line 502 and once from the watcher's debounce). The `_loading` guard in `load()` (line 94) prevents concurrent reloads, so this is safe but slightly wasteful.

3. **VS Code context update** — The `load()` method calls `setContext('docuvia:isInitialized', anyLoaded)` (line 108), which controls the visibility of the welcome view and inline actions. This correctly hides the welcome view after initialization.

4. **Missing integration with `manifest.yaml`** — As noted in Round 1, `initProject` never creates `manifest.yaml`. The `KnowledgeStore` expects it for `project_id` and `manifest.modules`. While the local YAML fallback works, projects initialized via the local VS Code client are permanently limited to offline-only mode (no server sync, no git fallback).

**Are there missing tests?**

- No dedicated unit or integration test for `initProject()` exists in the codebase. The extension test file (`artifacts/vscode-client/src/tests/phase1.test.ts`, line 36) calls the command via `executeCommand('docuvia.initProject')` but this is a high-level functional test, not a focused test for the init flow.
- No tests verify the multi-root QuickPick flow, overwrite dialog behavior, or YAML content correctness.

**Is the feature usable end-to-end?**

The feature is usable end-to-end for the basic case (initialize a single-root workspace). The flow works:
1. User opens Command Palette → "Docuvia: Init Project"
2. Enters project name
3. `.docuvia/` directory and skeleton files are created
4. KnowledgeStore reloads → tree view updates

However, several edge cases reduce usability:
- In multi-root workspaces, re-initializing a project shows the overwrite prompt but only for single-root scenarios (the multi-root QuickPick filters out initialized folders, making the overwrite path unreachable there).
- The chicken-and-egg activation event issue means `initProject` may not be available in a fresh workspace without any `.docuvia/` directory.
- No `manifest.yaml` is created, limiting server-augmented features.

## Findings

### Issues

1. **⚠️ Medium** — `manifest.yaml` never created by `initProject`. The `KnowledgeStore._loadWorkspace()` reads `manifest.yaml` first and uses it for server/git fallback. Projects initialized via `initProject` are permanently limited to local-only mode because `manifest.project_id` is always `undefined`. The `_loadWorkspace()` server path (line 141) and git path (line 189) both require `manifest.project_id !== undefined`.

2. **⚠️ Medium** — Project name not sanitized for YAML. User input with special YAML characters (quotes, colons, `#`) can produce invalid YAML in `l1_tags.yaml`. This would cause `parseTags()` to either fail or return unexpected results.

3. **⚠️ Low** — Force-overwrite dialog unreachable in multi-root mode. The multi-root QuickPick (line 433) filters out already-initialized folders, so the overwrite prompt at lines 451–460 is only reachable when there is exactly one workspace folder. The design spec's mermaid diagram implies overwrite is always available.

4. **⚠️ Low** — Chicken-and-egg activation event problem. The `workspaceContains:.docuvia` activation event means the extension won't activate until `.docuvia/` exists. While `onStartupFinished` partially mitigates this, users who haven't run `initProject` yet may not see the command in the Command Palette.

5. **⚠️ Low** — `viewsWelcome` missing "Init Project" button. The welcome view (line 117–123) only shows "Analyze Project Architecture" button. An "Init Project" button would provide a clearer onboarding path.

6. **ℹ️ Info** — Duplicate `project_name` line in skeleton `l1_tags.yaml`. Line 488 generates both a commented-out interpolations and a real `project_name:` key. The commented line is confusing.

### Recommendations

1. **Create `manifest.yaml` in `initProject`** — Add a `writeFile` call for `manifest.yaml` with at minimum a placeholder structure so that `manifest.project_id` can be populated later (e.g., when connecting to a server).

2. **Sanitize `projectName` for YAML** — Escape or wrap the project name in quotes properly. Consider using `yaml.stringify()` instead of string interpolation to produce valid YAML.

3. **Add `"Init Project"` button to `viewsWelcome`** — Add a second welcome entry or modify the existing one to include an "Initialize Project" command button when `!docuvia:isInitialized`.

4. **Fix multi-root overwrite flow** — Either include already-initialized folders in the QuickPick (marking them as "already initialized") or provide a separate code path for re-initialization.

---

## Overall Verdict

**⚠️ WARN**

The `docuvia.initProject` command is implemented and functional for the basic single-root case. The workspace resolution, project naming with validation, directory creation, file scaffolding, and post-init reload are all working correctly. The force-overwrite dialog is partially implemented.

However, the missing `manifest.yaml` creation is a significant architectural gap that permanently limits projects initialized via this command to local-only mode. The lack of YAML sanitization for user input is a latent defect. The overwrite dialog is unreachable in multi-root workspaces due to the filtering logic. These issues collectively warrant a **⚠️ WARN** rating.
