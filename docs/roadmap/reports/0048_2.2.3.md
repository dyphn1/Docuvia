## Round 1 — Architecture & Design Review

### What the checklist item requires

Item 2.2.3 states: `.docuvia/ directory creation with manifest.yaml, config.yaml, .snapshot-ref`. This breaks down into four sub-requirements:

1. **`.docuvia/` directory creation** — Creating the root Docuvia directory inside the workspace.
2. **`manifest.yaml`** — A manifest file inside `.docuvia/` that describes the project's modules and server-side project ID.
3. **`config.yaml`** — A configuration file (per ADR-008, part of the `.docuvia/` working tree alongside `manifest.yaml`).
4. **`.snapshot-ref`** — A file that stores a reference/snapshot pointer for the knowledge graph, pointing to the orphan branch HEAD.

### Analysis of implementation vs. design

#### `.docuvia/` directory creation — ✅ Implemented

The `initProject()` function in `extension.ts` (lines 474-479) creates the `.docuvia/` directory and its `l3_decisions` subdirectory:

```ts
const docuviaUri = vscode.Uri.file(path.join(targetRoot, '.docuvia'));
const decisionsUri = vscode.Uri.file(path.join(targetRoot, '.docuvia', 'l3_decisions'));
await vscode.workspace.fs.createDirectory(docuviaUri);
await vscode.workspace.fs.createDirectory(decisionsUri);
```

The `acceptL1Tags` command handler (line 296-301) also creates `.docuvia/` and `l3_decisions/` when writing L1 tags from the ChatParticipant.

#### `manifest.yaml` — ❌ NOT created by initProject

This is a **critical gap**. The `KnowledgeStore.ts` **reads** `manifest.yaml` on every `load()` call (line 131):

```ts
const manifestContent = await this.readUriSafe(vscode.Uri.joinPath(docuviaDir, MANIFEST_FILE));
const manifest = parseManifest(manifestContent, `${DOCUVIA_DIR}/${MANIFEST_FILE}`);
```

The `ManifestSchema` in `types.ts` is well-defined with `project_id` and `modules` fields. However, **no code path in `initProject()` or `acceptL1Tags` creates `manifest.yaml`**. The `initProject()` function only creates:
- `l1_tags.yaml`
- `l2_modules.yaml`
- `l3_router.yaml`
- `l3_decisions/` (empty directory)

Since `readUriSafe()` returns an empty string on file-not-found, and `parseManifest()` returns `{ project_id: undefined, modules: [] }` for empty input, the system degrades gracefully but the manifest is never initialized. This means:

- `manifest.project_id` is always `undefined` → the server-augmented and git-fallback code paths in `KnowledgeStore._loadWorkspace()` (lines 141 and 189) are **never reached** for projects initialized via `initProject`.
- `manifestModules` is always empty → offline CodeLens matching has no path patterns.
- For these features to work, users must **manually create** `manifest.yaml`, which is not documented or prompted.

#### `config.yaml` (per-workspace) — ❌ NOT Implemented

There are **two** different `config.yaml` concepts in the codebase:

1. **Global config** at `~/.docuvia/config.yaml` (read in `extension.ts` line 29): This is implemented. `GlobalConfigSchema` defines `server_url`, `chunking_strategy`, and `telemetry`. However, **no code creates this file** — it must be manually created by the user. If absent, the system continues with defaults.

2. **Per-workspace config** inside `.docuvia/config.yaml`: ADR-008 explicitly lists this as part of the `.docuvia/` working tree. This is **not implemented** anywhere. No code reads or writes this file.

#### `.snapshot-ref` — ❌ NOT Implemented

No code in the entire repository references `.snapshot-ref` as a file (only design docs and prior reports mention it). ADR-008 (section 09, line 198) explicitly defines `.docuvia/.snapshot-ref` as a pointer to the orphan branch HEAD. The `KnowledgeStore` does not read or write any `.snapshot-ref` file.

### Design gaps

- ADR-008 explicitly defines the `.docuvia/` working tree as a lightweight manifest containing `manifest.yaml`, `config.yaml`, `.snapshot-ref` — but the implementation writes full knowledge content files (`l1_tags.yaml`, `l2_modules.yaml`, `l3_router.yaml`) instead.
- The `init-project.md` design doc (line 21) lists only `l1_tags.yaml`, `l2_modules.yaml`, `l3_router.yaml` as scaffold files. It makes no mention of `manifest.yaml`, `config.yaml`, or `.snapshot-ref`.
- ADR-001 mentions `_project_profile.yaml` but this is not implemented and does not match the `.snapshot-ref` naming from ADR-008.
- There is a fundamental disconnect: the implementation writes full knowledge content to `.docuvia/` (legacy architecture), while ADR-008 specifies `.docuvia/` as a lightweight manifest pointing to the orphan branch.

## Round 2 — Code Quality & Security Review

### Code structure

- The `initProject()` function is well-structured with proper workspace resolution, multi-root handling, and input validation (validates non-empty project name).
- The overwrite logic (lines 450-460) properly handles re-initialization with a destructive warning prompt.
- The `writeIfAbsent` helper (line 694) follows defensive design by checking file existence before writing.

### Security concerns

- **YAML injection risk**: The `projectName` is interpolated into YAML content via template literal (line 488: `project_name: "${projectName}"`). If a user enters a project name containing YAML special characters (e.g., `"`, `:`, `#`, multiline), the generated `l1_tags.yaml` could be malformed or have unintended semantics. The input is validated for emptiness but **not sanitized for YAML safety**.
- No path traversal risk: `targetRoot` always comes from `vscode.workspace.workspaceFolders`, not user input.

### Code smells

- The `initProject()` function has clearly evolved through multiple bug fixes, but the code is still readable and not excessively long.
- The manifest being read but never written is a conceptual code smell — the `KnowledgeStore` has sophisticated logic for server fallback and git fallback based on `manifest.project_id`, but this logic is effectively dead code for any user who only uses `initProject`.

### Error handling

- `writeIfAbsent` silently skips existing files — no logging to indicate this happened.
- The `acceptL1Tags` command creates `.docuvia/` and `l3_decisions/` but uses `writeIfAbsent` for `l2_modules.yaml` and `l3_router.yaml`, which could lead to an inconsistent state if the init is interrupted between creating `l1_tags.yaml` and the other files.

## Round 3 — Integration & Completeness Review

### Integration issues

1. **Broken server-augmented path**: Because `manifest.yaml` is never created, `manifest.project_id` is always `undefined`, so the server-augmented loading path (`KnowledgeStore._loadWorkspace()` line 141) and the git-fallback path (line 189) are **never activated** for projects initialized via the standard flow. This means the `CentralServerClient.pullSnapshot()` and the `_loadFromGit()` method are effectively dead code in the standard onboarding flow.

2. **Offline CodeLens**: `DocuviaCodeLensProvider.ts` uses `snapshot.manifestModules` for offline matching (line 134). Since `manifest.yaml` is never created, `manifestModules` is always empty, making offline CodeLens matching non-functional.

3. **`acceptL1Tags` creates a different set of files than `initProject`**: Both code paths create `.docuvia/`, `l3_decisions/`, `l1_tags.yaml`, and use `writeIfAbsent` for `l2_modules.yaml` and `l3_router.yaml`. Neither creates `manifest.yaml`, `config.yaml`, or `.snapshot-ref`. The two code paths for `.docuvia/` creation are duplicated logic.

4. **Architecture mismatch with ADR-008**: The three-layer knowledge store architecture specifies:
   - Layer 1: `.docuvia/` (working tree) — lightweight manifest
   - Layer 2: Orphan branch — full knowledge content
   - Layer 3: Server API — dynamic query
   
   The current implementation puts full knowledge content directly in `.docuvia/` (Layer 1), while the orphan branch and server API fallback paths are dead code in the standard flow.

### Missing tests

- The `initProject` command has a basic test reference (extension test: `vscode.commands.executeCommand('docuvia.initProject')`), but no test verifies what files are actually created, or that `manifest.yaml`, `config.yaml`, and `.snapshot-ref` are missing.
- No integration test validates the full end-to-end onboarding flow.

### Performance concerns

- None significant for this item. Directory/file creation is I/O-bound and straightforward.

### End-to-end usability

- A user running `docuvia.initProject` gets a partially initialized project. The `.docuvia/` directory contains legacy YAML skeleton files but is missing the manifest that `KnowledgeStore` expects. The system silently degrades to local-only mode with no warning.
- If the user connects to a server and creates a project, there is no automated flow to write `project_id` into `manifest.yaml` — this would require manual intervention.
- The success message ("Populate the YAML files to build your knowledge graph.") does not mention `manifest.yaml`, `config.yaml`, or `.snapshot-ref` as files the user should create.

## Overall Verdict

⚠️ **WARN**

The `.docuvia/` directory is successfully created by `initProject()` with skeleton YAML files (`l1_tags.yaml`, `l2_modules.yaml`, `l3_router.yaml`, and the `l3_decisions/` directory). However, all three files named in the checklist item are **not implemented**:

- **`manifest.yaml`** — Not created by any initialization code path, despite being read by `KnowledgeStore` and critical for server-augmented and git-fallback load paths. This is the most impactful gap.
- **`config.yaml`** (per-workspace) — Not created or referenced by any code. ADR-008 explicitly requires it.
- **`.snapshot-ref`** — Does not exist anywhere in the codebase. No code reads or writes this file. ADR-008 explicitly requires it.

The core directory creation works, but the item is incomplete per its specification. Marking as ⚠️ WARN rather than ❌ FAIL because the basic `.docuvia/` directory creation is functional and the system degrades gracefully (no crashes), but the missing `manifest.yaml`, `config.yaml`, and `.snapshot-ref` are significant functional gaps that break the ADR-008 three-layer knowledge store architecture.
