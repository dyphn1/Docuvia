## Round 1 — Architecture & Design Review

### What 3.5.1 Requires

Per ADR-004, item 3.5.1 implements the "Baseline Inheritance" feature of the Git-Isomorphic Graph:

1. When checking out an unknown branch, the system resolves the common ancestor with `git merge-base HEAD <base-branch>`.
2. The client queries the server for the knowledge snapshot of that ancestor commit.
3. This instantly inherits historical guardrails without rescanning the entire history.

### Current State

**❌ NOT IMPLEMENTED.** There is no source code implementing this feature. The feature exists only as a design specification in ADR-004.

### Design Spec Analysis

The ADR-004 describes the feature at a conceptual level:
- "When checking out an unknown branch, the system executes `git merge-base HEAD origin/main`"
- "The client queries the server for the knowledge snapshot of this ancestor commit"
- This is Section 1 of ADR-004 ("The Baseline Inheritance (Nearest Ancestor)")

The design spec itself is ambiguous about which component executes the merge-base:
- The **VS Code client** could execute it locally (since it has the git repo)
- The **API server** could execute it (if it has a clone of the repo)
- A **CLI command** could trigger it

The spec does not define the API contract (endpoint, request/response shape) for querying the server by commit hash for a knowledge snapshot.

### Gaps Between Design and Implementation

| Gap | Type | Description |
|-----|------|-------------|
| No implementation | Critical | Zero source code exists for merge-base lookup |
| API contract undefined | Design | No endpoint defined for querying knowledge snapshots by commit hash |
| Component responsibility unclear | Design | Spec does not specify whether client or server executes the merge-base |
| No integration point | Design | No specification for how the inherited baseline merges with existing knowledge |

### Round 1 Verdict: Feature is NOT implemented. The design spec exists but is high-level and lacks implementation detail.

## Round 2 — Code Quality & Security Review

Since there is no implementation code, this round reviews the **design spec** for implementation readiness.

### Design Readiness for Implementation

1. **ADR-004 pseudocode pattern** (line 21-29): Provides a mermaid diagram and a one-line description of `git merge-base HEAD origin/main`. This is sufficient as a starting point but needs elaboration.

2. **Dependencies on adjacent features:**
   - Item 3.4.1 (orphan-branch-writer) — ✅ Implemented
   - Item 3.4.2 (bidirectional sync) — ❌ Not implemented
   - Item 3.4.3 (docuvia sync CLI) — ❌ Not implemented
   - Item 3.4.4 (KnowledgeStore rewrite to read from orphan branch) — ❌ Not implemented

   **3.5.1 depends on 3.4.4** since the KnowledgeStore needs to read from the orphan branch before it can use the merge-base result to find the right snapshot. Without 3.4.4, there's no orphan-branch-based snapshot to inherit.

3. **Security considerations for future implementation:**
   - `merge-base` result must be validated server-side to prevent git history manipulation
   - The knowledge snapshot of the ancestor commit should be immutable once committed to the orphan branch
   - If the client executes merge-base, the result must be verified against the server's git state

### Round 2 Verdict: The design spec is implementable but requires additional detail before implementation. The most critical prerequisite (3.4.4 KnowledgeStore rewrite) is still incomplete.

### Orphan Branch Writer — Adjacent Implementation Review

The existing `orphan-branch-writer.ts` (item 3.4.1) writes knowledge snapshots to the `docuvia-knowledge` orphan branch using `git fast-import`. However:
- It writes but does **not read** specific snapshots by commit hash
- It flattens the orphan branch to a single commit per project (no commit history per snapshot)
- To support merge-base-based inheritance, the writer needs to either:
  (a) Tag commits by the source commit hash, or
  (b) Maintain an index mapping commit hashes → orphan branch commit hashes

### What Would Be Needed to Implement 3.5.1

1. **New module: `merge-base-resolver.ts`** (in api-server)
   - Accepts a commit hash and branch name
   - Executes `git merge-base <commit> <baseBranch>` using `child_process.execFile`
   - Returns the ancestor commit hash

2. **New API endpoint: `GET /commits/:commitHash/knowledge-snapshot`**
   - Returns the knowledge snapshot for a specific commit from the orphan branch
   - Depends on orphan branch reader being able to extract files at a specific commit

3. **Orphan branch reader enhancement**
   - The current writer does not support reading by commit hash
   - Needs ability to `git show <commit>:<path>` or maintain a commit-hash → tree index

4. **VS Code client integration**
   - After extraction on an unresolved branch, client calls merge-base endpoint
   - Inherits the baseline knowledge from the ancestor
   - Only extracts deltas (new files/modified files between ancestor and HEAD)

5. **Delta computation**
   - `git diff --name-only <ancestor>..HEAD` to get changed files
   - Only run extraction on changed files

### Missing Tests

No tests exist for this feature (feature does not exist). Tests that would be needed:
- Unit test for `git merge-base` resolution
- Integration test: orphan branch read by commit hash
- Integration test: knowledge snapshot inheritance for ancestor commit
- E2E test: extraction on un-indexed branch triggers merge-base flow

### Round 3 Verdict: Feature is completely unimplemented. The prerequisite chain (3.4.4 → 3.5.1) is not yet satisfied. Implementation requires significant new code across multiple components.

## Overall Verdict

**❌ FAIL**

Item 3.5.1 — git merge-base lookup for un-indexed commits — is **not implemented**. There is no source code, no API endpoint, no tests, and no integration. The feature remains at the design-spec level only (ADR-004).

The primary blocker is the incomplete prerequisite chain: items 3.4.2 (bidirectional sync), 3.4.3 (docuvia sync CLI), and 3.4.4 (KnowledgeStore rewrite) must all be implemented before 3.5.1 is feasible. Additionally, the existing orphan branch writer (3.4.1) only writes — it cannot read snapshots by commit hash, which is required for the merge-base inheritance pattern.

**Recommendation:** Keep as ❌ Todo. The prerequisite 3.4.x features should be completed first. Once 3.4.4 is done, 3.5.1 can be planned as a new feature with a dedicated API contract definition.
