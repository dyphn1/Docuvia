## Round 1 — Architecture & Design Review

### Design Spec (ADR-007, Section 3)

ADR-007 specifies:
1. Knowledge nodes contain `created_at` and `lastVerifiedAt` timestamps.
2. The router applies an **Exponential Temporal Decay** function to **search scores**: `Math.exp(-LAMBDA * daysSinceVerified)`.
3. Knowledge untouched naturally sinks to the bottom of search results.
4. When old knowledge correctly answers a query, its `lastVerifiedAt` is updated via `POST /search/feedback`.

### Implementation Analysis

This item (3.2.2) is the **complement** of item 3.2.1 (which verified the `calculateTemporalDecay` math function itself — ✅ PASS). Item 3.2.2 verifies that decay is actually **applied** to knowledge query results across all relevant paths.

#### Where decay IS applied:

**1. Vector search — embedding path (L2 nodes, lines 210–220):**
```typescript
const l2Scored = l2Rows
  .map((node) => {
    const emb = parseEmbedding(node.embedding);
    const rawScore = emb ? cosineSimilarity(queryEmbedding, emb) : 0;
    const referenceDate = node.lastVerifiedAt ?? node.createdAt;
    const decayFactor = calculateTemporalDecay(referenceDate);
    const score = rawScore * decayFactor;
    return { node, score };
  })
```
✅ Decay is applied. `lastVerifiedAt` is preferred, falling back to `createdAt`.

**2. Vector search — embedding path (L3 nodes, lines 264–274):**
```typescript
const l3Scored = l3Rows
  .map(({ node, projectId, projectName }) => {
    const emb = parseEmbedding(node.embedding);
    const rawScore = emb ? cosineSimilarity(queryEmbedding, emb) : 0;
    const referenceDate = node.lastVerifiedAt ?? node.createdAt;
    const decayFactor = calculateTemporalDecay(referenceDate);
    const score = rawScore * decayFactor;
    return { node, projectId, projectName, score };
  })
```
✅ Same pattern as L2. Correct.

#### Where decay is NOT applied:

❌ No decay applied. Hardcoded score of 0.9.

**4. Vector search — SQL LIKE fallback path (L3, lines 364–376):**

```typescript
  score: 0.8,  // hardcoded, no decay

```
❌ No decay applied. Hardcoded score of 0.8.

**5. Graph traversal handler (lines 408–475):**
All results use fixed scores (1.0 for matched node, 0.7 for neighbors).
❌ No decay applied.

**6. Direct lookup handler (lines 502–597):**

❌ No decay applied.

**7. Hybrid search (lines 604–652):**
Calls `vectorSearchHandler()` (which applies decay for embedding path) and `graphTraversalHandler()` (no decay), then merges. Graph results from the merge have fixed scores with no decay.
❌ Partial — graph results within hybrid are not decayed.

### Architectural Assessment

The ADR-007 language says "the router applies an Exponential Temporal Decay function to search scores." The key question is the **scope** of "search scores":

- **Narrow interpretation:** Decay only applies to semantic similarity scores (vector search). This is what's implemented. Exact matches (direct lookup) and structural relationships (graph) don't "decay" because they're deterministic.
- **Broad interpretation:** All knowledge query results should be decayed regardless of retrieval strategy. Under this interpretation, the graph traversal, direct lookup, and LIKE fallback paths all have gaps.

The narrow interpretation is **defensible and reasonable** because:
1. Graph traversal results represent structural dependencies that don't become "stale" — if A depends on B, that's true regardless of time.
2. Direct lookups by commit hash are exact matches — the user asked for a specific thing and got it.
3. The LIKE fallback is a degraded mode when embeddings are unavailable, and the hardcoded scores (0.9, 0.8) are lower than typical decayed embedding scores.

However, the ADR also says "Knowledge untouched naturally sinks to the bottom of search results" — this is a **system-wide** statement. In the current implementation, a graph traversal result for a never-verified node will score 0.7, while a highly-relevant vector result for a very stale node might score 0.4 (0.8 similarity × 0.5 decay). This means **stale but semantically relevant knowledge can sink below fresh but structurally related knowledge**, which is the intended behavior. But it also means graph results for stale nodes will rank higher than their actual relevance warrants.

**Contradiction between design documents:** The ADR says knowledge "naturally sinks" but the graph/direct paths bypass sinking entirely. This is a minor design-implementation gap, not a critical flaw.

### Schema Support

- `l2_nodes.lastVerifiedAt` ✅ (line 21, `defaultNow()`)
- `l3_nodes.lastVerifiedAt` ✅ (line 33, `defaultNow()`)
- `commits.lastVerifiedAt` ❌ **Missing.** The `commits` table has `validityStatus` and `branchName` but no `lastVerifiedAt` column. This means commit results from direct lookup cannot be decayed even if the design intended it.

### Gaps / Contradictions

1. **SQL LIKE fallback path does not apply decay** — acceptable for degraded mode but undocumented.
2. **Graph traversal does not apply decay** — defensible but inconsistent with the broad ADR language.
3. **Direct lookup does not apply decay** — defensible (exact matches).
4. **`commits` table lacks `lastVerifiedAt`** — if decay were to be applied to commit results, the schema doesn't support it.
5. **`AgenticSearchResult` interface lacks `lastVerifiedAt`** — even if a post-hoc decay pass were added to `routeQuery()`, the timestamp isn't available in the result object for graph/direct results.

## Round 2 — Code Quality & Security Review

### Code Quality

- **Decay application is clean and consistent** where it is applied (lines 214–216, 268–270). The pattern `node.lastVerifiedAt ?? node.createdAt` is correct and defensive.
- **No duplication** — the decay logic is in a single function `calculateTemporalDecay()` and called from two places.
- **The LIKE fallback path** (lines 289–377) is a separate code path that doesn't share the scoring logic with the embedding path. This is a structural issue — the fallback could theoretically fetch `lastVerifiedAt` and apply decay too, but it would add complexity.

### Unit Test Coverage

The unit tests in `intent-router.unit.test.ts` (lines 19–43) cover the `calculateTemporalDecay` function itself:
- ✅ Returns 1.0 for current date
- ✅ Returns 0.5 at 30-day half-life
- ✅ Returns 0.25 at 60 days
- ✅ Future dates capped at 1.0

**Missing test coverage:**
- ❌ No integration tests verifying decay is actually applied to query results end-to-end
- ❌ No tests for the SQL LIKE fallback scoring behavior
- ❌ No tests for graph traversal or direct lookup scoring

### Security

- No security vulnerabilities in the decay application logic.
- The `lastVerifiedAt` timestamp comes from the database, not user input.

### Code Smell

- The `AgenticSearchResult` interface (lines 36–46) includes `createdAt` but not `lastVerifiedAt`. This means the frontend receives the creation date but cannot display staleness or allow users to see when a node was last verified. This is a **usability gap** — users have no visibility into why certain results rank lower.

## Round 3 — Integration & Completeness Review

### End-to-End Flow

1. **Node creation:** L2/L3 nodes get `lastVerifiedAt` via `defaultNow()` ✅
2. **Vector search:** Decay is applied to embedding-based results ✅
3. **Feedback loop:** `POST /search/feedback` updates `lastVerifiedAt` to `NOW()` ✅
4. **Next search:** Refreshed `lastVerifiedAt` is read and decay is recalculated ✅

The feedback loop is complete for the vector search path.

### Integration with Routing Strategy

| Strategy | Handler | Decay Applied? | Notes |
|----------|---------|----------------|-------|
| `vector_search` | `vectorSearchHandler()` | ✅ Yes (embedding path) / ❌ No (LIKE fallback) | Partial |
| `hybrid` | `hybridSearch()` | ✅ Partial | Vector portion decayed, graph portion not |
| `graph_traversal` | `graphTraversalHandler()` | ❌ No | Fixed scores |
| `direct_lookup` | `directLookupHandler()` | ❌ No | Fixed scores |

### Frontend Integration

The `query.tsx` page (kg-engine) displays `score` but has no concept of decay or staleness. The `SearchResultItem` interface includes `createdAt` but the UI doesn't render it. Users see scores but don't know if a low score is due to low relevance or high staleness.

The VS Code `SearchResultsPanel.ts` uses `CentralSearchResult` which has an optional `score` field but no staleness indicator.

### Performance

- Decay calculation is O(1) per node — no performance concern.
- No additional DB queries needed for the embedding path (timestamp is part of the SELECT).
- The LIKE fallback would need to select `lastVerifiedAt` to apply decay — minor overhead.

### Missing Tests for 3.2.2 Specifically

- No integration test that verifies a stale node ranks lower than a fresh node with the same embedding.
- No test verifying the feedback endpoint resets decay.
- No test verifying decay is applied in the hybrid search merge.

## Findings

1. ✅ **Decay is correctly applied in the primary vector search path** (embedding-based). Both L2 and L3 nodes have their cosine similarity scores multiplied by the decay factor. The `lastVerifiedAt ?? createdAt` fallback is correct.

2. ✅ **The feedback loop is complete.** `POST /search/feedback` updates `lastVerifiedAt` for L2 and L3 nodes, which resets the decay clock on the next search.

3. ⚠️ **Decay is NOT applied in 3 of 4 search paths.** Graph traversal, direct lookup, and the SQL LIKE fallback all use fixed scores without decay. This is defensible for direct lookup (exact match) and graph (structural), but the LIKE fallback path should arguably apply decay for consistency.

4. ⚠️ **`commits` table lacks `lastVerifiedAt`.** The `commits` table has `validityStatus` and `branchName` but no `lastVerifiedAt` column. If the design intends for commit results to decay, the schema is incomplete.

5. ⚠️ **`AgenticSearchResult` lacks `lastVerifiedAt`.** The result interface doesn't carry the verification timestamp, preventing post-hoc decay and frontend staleness display.

6. ⚠️ **No integration tests for decay-in-query.** Unit tests cover the math function but there are no integration tests verifying that decay actually affects query result ordering end-to-end.

7. ℹ️ **Frontend doesn't expose staleness.** Neither `query.tsx` nor `SearchResultsPanel.ts` shows `lastVerifiedAt` or any staleness indicator to the user.

---

## Overall Verdict

**⚠️ WARN**

The decay function itself is mathematically correct and well-tested (per 3.2.1 ✅ PASS), and it is correctly applied in the primary vector search path. The feedback loop for refreshing `lastVerifiedAt` is complete. However, decay is not applied to 3 of 4 search paths (graph traversal, direct lookup, SQL LIKE fallback), the `commits` table lacks `lastVerifiedAt`, the `AgenticSearchResult` interface doesn't carry the verification timestamp, and there are no integration tests for decay's effect on query results. The feature works for the happy path (vector semantic search) but is incomplete for the full query surface.

### Recommendations

1. **Add `lastVerifiedAt` to the `commits` schema** if commit results should also decay.
2. **Add `lastVerifiedAt` to the `AgenticSearchResult` interface** to enable post-hoc decay and frontend staleness display.
3. **Consider applying decay to the LIKE fallback path** for consistency — fetch `lastVerifiedAt` in the query and multiply the hardcoded scores.
4. **Add integration tests** that verify: (a) a stale node ranks lower than a fresh node with identical embeddings, (b) the feedback endpoint resets decay, (c) hybrid search results reflect decay.
5. **Frontend enhancement:** Display `lastVerifiedAt` or a staleness indicator in the query results UI.
