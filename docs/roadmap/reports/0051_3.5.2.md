## Round 1 — Architecture & Design Review

### What 3.5.2 Requires

Per ADR-004, Section 2 "Local-Side Incremental Analysis (Knowledge Patch)":

1. The system identifies the ancestor commit (via `git merge-base`, item 3.5.1).
2. It computes the file-level diff between the ancestor and HEAD: `git diff --name-only <ancestor>..HEAD`.
3. It extracts **only new L3 decisions** from the files in that delta.
4. New L3 nodes are anchored to the new commit hashes via the `sourceCommits` JSONB array.
5. The system avoids re-scanning unchanged files, preserving tokens and preventing duplicate L3 nodes for unmodified code.

### Current State

**❌ NOT IMPLEMENTED.** There is no source code implementing temporal delta projection. The feature exists only as a design specification in ADR-004.

### Design Spec Analysis

The ADR-004 describes the feature at a conceptual level with a mermaid diagram showing:
```
C4 --> |Extract Delta| NewL3[New L3: hotfix_rule]
```

The spec states: "The developer only extracts new L3 decisions for the files modified in the delta between the ancestor and HEAD." However, the spec does not detail:

- **Which component computes the diff** — the client could run `git diff` locally, or the server could run it if it has a repo clone
- **How the delta file list is communicated** to the extraction pipeline
- **How existing L3 nodes from unchanged files are preserved** during incremental generation
- **The API contract** — no endpoint or request/shape is defined for delta-scoped extraction
- **Conflict handling** — what happens when the same file produces different L3s in the delta vs. what already exists

### Incremental Mode in generate.ts — Partial Overlap

The `generate.ts` route at line 33 defines a `mode` parameter accepting `"full"` or `"incremental"`:

```typescript
mode: z.enum(["full", "incremental"]).optional().default("full"),
```

When `mode === "incremental"` (lines 565-567), the query filters for commits where `processedAt IS NULL`:

```typescript
mode === "incremental"
  ? and(eq(commitsTable.projectId, projectId), eq(commitsTable.valid, true), isNull(commitsTable.processedAt))
  : and(eq(commitsTable.projectId, projectId), eq(commitsTable.valid, true))
```

This is **not** temporal delta projection. It is cursor-based incremental processing — it picks up commits that haven't been processed yet, but still runs the full extraction pipeline on each commit. It does not:

- Compute file-level diffs between an ancestor and HEAD
- Scope L3 extraction to only changed files
- Prevent re-extraction of L3s from unchanged files

### Gaps Between Design and Implementation

| Gap | Type | Description |
|-----|------|-------------|
| No implementation | Critical | Zero source code exists for temporal delta projection |
| API contract undefined | Design | No endpoint or request shape for delta-scoped extraction |
| Component responsibility unclear | Design | Not specified whether client or server computes the delta |
| No conflict resolution | Design | No specification for handling L3 conflicts between delta and existing data |
| Existing "incremental" mode misaligned | Design | Current `incremental` mode in generate.ts is cursor-based, not diff-based |

### Round 1 Verdict

Feature is **NOT implemented**. The design spec exists at a high level but lacks the detail needed for implementation. The existing `incremental` mode in `generate.ts` provides a foundation (it has the concept of partial processing) but does not implement temporal delta projection as described in ADR-004.

## Round 2 — Code Quality & Security Review

Since there is no implementation of temporal delta projection, this round reviews the **closest existing code** for quality and the **design spec** for implementation readiness.

### Review of Existing Incremental Mode in generate.ts

The current `incremental` mode in `generate.ts` (lines 565-567):

```typescript
mode === "incremental"
  ? and(eq(commitsTable.projectId, projectId), eq(commitsTable.valid, true), isNull(commitsTable.processedAt))
  : and(eq(commitsTable.projectId, projectId), eq(commitsTable.valid, true))
```

**Issues identified:**

1. **No file-level scoping** — The incremental mode filters commits but does not filter files within commits. A commit with 50 changed files where only 5 are new will still re-extract L3s for all 50 files.
2. **No ancestor awareness** — The mode doesn't accept or use an ancestor commit hash. It purely uses the `processedAt` cursor.
3. **Semantic mismatch with ADR-004** — ADR-004's delta projection is fundamentally different from cursor-based incremental processing. The naming collision ("incremental") could cause confusion during implementation.
4. **Test coverage** — No tests specifically validate the `incremental` mode's behavior. The existing tests in `generate.unit.test.ts` do not cover the `mode: "incremental"` code path.

### Design Readiness for Implementation

1. **ADR-004 description is sufficient as a starting point** for the high-level algorithm, but needs a detailed implementation spec covering:
   - API request/response format
   - Error handling (what if the ancestor is not in the DB?)
   - Idempotency (what if extraction is run twice on the same delta?)

2. **Dependencies on adjacent features:**
   - Item 3.5.1 (git merge-base lookup) — ❌ Not implemented (required to find the ancestor)
   - Item 3.5.1 itself depends on 3.4.4 (KnowledgeStore rewrite) — ❌ Not implemented
   - Item 3.4.x chain (orphan branch sync) — ❌ Not implemented

3. **Security considerations for future implementation:**
   - The ancestor commit hash must be validated to prevent path traversal via crafted hashes
   - `git diff --name-only` output must be sanitized before being used in file path operations
   - L3 extraction from only changed files must not accidentally delete or overwrite existing L3s from unchanged files

### Round 2 Verdict

The design spec is implementable but requires additional detail. The existing `incremental` mode in `generate.ts` is a naming collision — it implements cursor-based incremental processing, not the ancestor-based temporal delta projection described in ADR-004. Implementation should either extend the existing incremental mode or add a separate endpoint.

### Prerequisite Chain

```
3.4.2 (bidirectional sync) ──❌──▶ 3.4.3 (sync CLI) ──❌──▶ 3.4.4 (KnowledgeStore rewrite)
                                                                       │
                                                                       ▼
                                                            3.5.1 (merge-base lookup) ──❌──▶ 3.5.2 (this item)
```

The entire prerequisite chain is incomplete. 3.5.2 cannot be implemented until 3.5.1 and 3.4.4 are done.

### What Would Be Needed to Implement 3.5.2

1. **New function: `computeTemporalDelta(ancestorHash: string, headHash: string): string[]`**
   - Executes `git diff --name-only <ancestorHash> <headHash>` using `child_process.execFile`
   - Returns the list of changed file paths
   - Should be placed in a new module: `api-server/src/lib/temporal-delta.ts`

2. **Enhanced incremental mode in `generate.ts` or new endpoint**
   - Accept `ancestorHash` parameter
   - Filter extraction to only changed files from the delta
   - Preserve existing L3 nodes for unchanged files
   - Could extend the existing `POST /projects/:id/generate` with optional `ancestorHash` field, or add a new `POST /projects/:id/generate/delta` endpoint

3. **L3 extraction scoping**
   - The extraction pipeline must accept a file filter
   - Only extract decisions from files in the delta list
   - Respect existing L3s by using semantic dedup (already implemented in `generate.ts` lines 840-930)

4. **API contract definition**
   ```yaml
   POST /projects/:id/generate/delta
   Request:
     ancestorHash: string  # commit hash from merge-base
     headHash: string      # defaults to HEAD
     model?: string
   Response:
     l3NodesCreated: number
     filesScanned: number
     ancestorHash: string
   ```

5. **Orphan branch integration**
   - After delta extraction, push new L3s to the orphan branch (depends on 3.4.1 orphan-branch-writer)
   - Orphan branch should tag the commit with the source commit hash for future ancestor lookups

### Missing Tests

No tests exist for this feature. Tests that would be needed:
- Unit test: `computeTemporalDelta()` returns correct file list for a given ancestor/head pair
- Unit test: extraction pipeline correctly filters to changed files only
- Integration test: delta extraction does not overwrite L3s from unchanged files
- E2E test: checkout unknown branch → resolve ancestor → delta extraction → verify L3s

### Performance Considerations

The primary performance benefit of temporal delta projection is token efficiency. By scoping extraction to only changed files:
- **Before (full scan):** 50 commits × 200 files = 10,000 file tokens
- **After (delta projection):** 5 changed files = 50 file tokens  
- This is a ~200x reduction for the extraction step

However, this assumes the ancestor resolution (3.5.1) is already cached. The first run on a new branch always requires a full scan.

### Round 3 Verdict

Feature is completely unimplemented. The prerequisite chain (3.4.x → 3.5.1 → 3.5.2) is not satisfied. Implementation requires new modules, API endpoints, and significant changes to the extraction pipeline. The existing cursor-based incremental mode in `generate.ts` provides a partial foundation but does not implement the ADR-004 temporal delta projection pattern.

## Overall Verdict

**❌ FAIL**

Item 3.5.2 — Temporal delta projection — is **not implemented**. There is no source code, no API endpoint, no tests, and no integration. The feature remains at the design-spec level only (ADR-004, Section 2).

The primary blockers are the incomplete prerequisite chain: items 3.4.2 (bidirectional sync), 3.4.3 (docuvia sync CLI), 3.4.4 (KnowledgeStore rewrite), and 3.5.1 (git merge-base lookup) must all be implemented before 3.5.2 is feasible.

Additionally, the existing `incremental` mode in `generate.ts` uses cursor-based filtering (`processedAt IS NULL`) rather than ancestor-based diff projection. While this provides a partial foundation for incremental processing, it does not implement the ADR-004 temporal delta projection pattern. Care should be taken during implementation to avoid conflating these two distinct concepts.

**Recommendation:** Keep as ❌ Todo. The 3.4.x and 3.5.1 prerequisites should be completed first. Once 3.5.1 is done, 3.5.2 should be planned as a dedicated feature with a formal API contract addition to `openapi.yaml` and corresponding Orval codegen.
