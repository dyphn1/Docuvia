## Round 1 — Architecture & Design Review

### Design Intent

ADR-008 establishes a three-layer knowledge storage architecture:

1. **PostgreSQL** — full company-wide knowledge index
2. **`docuvia-knowledge` orphan branch** — canonical, human-readable YAML/Markdown knowledge files
3. **`.docuvia/` (working tree)** — lightweight manifest (`manifest.yaml`, `config.yaml`, `.snapshot-ref`) that points to the orphan branch HEAD

The ADR explicitly states that the KnowledgeStore "must be rewritten" because the "current implementation reads `.docuvia/` files directly from the working tree filesystem; it must instead read from the orphan branch ref."

### Current Implementation Analysis

The current `KnowledgeStore._loadWorkspace()` (lines 120–223) implements a **three-tier fallback**:

1. **Tier 1 — Server API** (line 141): When server is configured and `manifest.project_id` exists, calls `this._client.pullSnapshot()`.
2. **Tier 2 — Local `.docuvia/` YAML files** (line 152): When Tier 1 yields no data, reads `l1_tags.yaml`, `l2_modules.yaml`, `l3_router.yaml`, and `l3_decisions/` directory directly from the workspace `.docuvia/` folder using `vscode.workspace.fs`.
3. **Tier 3 — Git orphan branch** (line 189): When both previous tiers yield no data, reads from the `docuvia-knowledge` orphan branch via `git show` and `git ls-tree` using `child_process.exec`.

### Gap Between Design and Implementation

The current implementation **does** read from the orphan branch ref (Tier 3), but the design intent is that the orphan branch should be the **primary** knowledge source, not a last-resort fallback. The key gaps are:

1. **Tier 2 reads full knowledge from `.docuvia/` working tree** — The design says `.docuvia/` should contain only a lightweight manifest. But the current Tier 2 reads `l1_tags.yaml`, `l2_modules.yaml`, `l3_router.yaml`, and all `l3_decisions/*.md` files directly from the working tree. This means the `.docuvia/` directory contains the full knowledge content, not just a manifest.

2. **Orphan branch is only used as a last resort** — The `_loadFromGit()` method (Tier 3) is only reached when both Tier 1 (server) and Tier 2 (local YAML) return empty results. In practice, if a developer has a `.docuvia/` directory with YAML files, the orphan branch is never consulted. The design intent is the opposite: the orphan branch should be the canonical source, and `.docuvia/` should just be a pointer.

3. **No `.snapshot-ref` mechanism** — The design describes `.docuvia/.snapshot-ref` as a file that points to the orphan branch HEAD. This file is never read or written by the current KnowledgeStore. The `initProject` function (extension.ts, line 417) creates `manifest.yaml`, `l1_tags.yaml`, `l2_modules.yaml`, and `l3_router.yaml` as skeleton files in `.docuvia/`, but never creates `.snapshot-ref`.

4. **FileSystemWatcher monitors `.docuvia/` not the orphan branch** — `startWatcher()` (line 351) creates a `FileSystemWatcher` on `.docuvia/**`. When files change in the working tree, the watcher triggers a reload. But if the orphan branch is updated (e.g., via `git fetch origin docuvia-knowledge`), the watcher won't detect it because the orphan branch files are not in the working tree.

5. **`initProject` writes full knowledge skeletons, not a manifest** — The `initProject` function (extension.ts, lines 417–507) writes `l1_tags.yaml`, `l2_modules.yaml`, and `l3_router.yaml` as skeleton files with example content. Per ADR-008, these should be minimal or non-existent — the actual knowledge should come from the orphan branch.

### New in Commit `eba22d4`: KnowledgeIndexer

The new `KnowledgeIndexer` class (`artifacts/vscode-client/src/indexer/KnowledgeIndexer.ts`) is a well-designed background indexer that:
- Builds interval trees for O(log N) line-based decision lookup
- Listens to `onDidChangeTextDocument` and `onDidSaveTextDocument` for incremental updates
- Uses `vscode.executeDocumentSymbolProvider` to anchor L3 decisions to code symbols

However, the `KnowledgeIndexer.indexSnapshot()` method (line 29) reads from `snapshot.routerIndex` and `snapshot.decisions` — which are populated by whatever tier succeeds in `_loadWorkspace()`. Since Tier 2 (local `.docuvia/` files) is the one that actually loads knowledge in practice, the KnowledgeIndexer inherits the same architectural issue: it indexes knowledge from the working tree, not from the orphan branch.

### Contradictions Between Design Documents

- **knowledge-graph/store.md** (line 13) says: *"`load()`: ...parses `l1_tags.yaml`, `l2_modules.yaml`, `l3_router.yaml`, and the markdown files in `l3_decisions/`."* This describes the current (pre-rewrite) behavior, not the ADR-008 target state. The design doc has not been updated to reflect the ADR-008 decision.
- **05-building-blocks.md** (line 116) says: *"`KnowledgeStore.ts` — Model layer: manages `.docuvia/` YAML snapshot; syncs to disk."* Again describes the old model.

## Round 2 — Code Quality & Security Review

### Code Quality

The current `_loadFromGit()` implementation (lines 286–346) is well-structured:
- Uses `git show` to read individual files from the orphan branch
- Uses `git ls-tree -r` to list L3 decision files recursively
- Properly handles errors at each step (`.catch(() => '')`)
- Parses the same YAML/Markdown formats as Tier 2, ensuring consistency

The new `KnowledgeIndexer` (commit `eba22d4`) is well-designed:
- Uses `IntervalTree` for efficient O(log N) range queries
- Debounces file indexing with a 500ms delay and deduplication via `_indexingQueue`
- Handles document symbol resolution with a scoring-based matching algorithm
- Properly shifts ranges on text changes to maintain index accuracy

### Security Considerations

1. **Command Injection via `child_process.exec`** — The `_loadFromGit()` method uses `exec()` with template literals:
   ```typescript
   `git show "${GIT_KNOWLEDGE_BRANCH}:${projectId}/l1_tags.yaml"`
   ```
   The `projectId` comes from `manifest.project_id` which is parsed from YAML. The `_loadFromGit` signature declares `projectId: number`, and the Zod validation in `parseManifest()` enforces this type. When coerced to a string in the template literal, a number is safe from injection. **Low risk.**

2. **No validation of orphan branch content** — Files read from the orphan branch are parsed with the same parsers as local files. If the orphan branch contains malformed YAML, the parsers will throw, caught by `tryParse` which returns empty arrays. This is acceptable defensive behavior.

### Code Smells

1. **Duplicate parsing logic** — The same YAML/Markdown parsing is done in both Tier 2 (local files) and Tier 3 (orphan branch). The parsers are called with different source labels but produce identical output. This represents maintenance risk if parsing logic changes.

2. **Silent failure chain** — All three tiers can fail silently (Tier 1 logs to output channel, Tier 2 catches and logs, Tier 3 catches and logs). If all three tiers fail, the user sees an empty knowledge graph with no prominent indication of what went wrong.

3. **No caching of orphan branch HEAD** — Every call to `_loadFromGit()` re-reads the orphan branch from scratch. There's no caching of the orphan branch HEAD ref or the knowledge content.

4. **`KnowledgeIndexer` indexes from working tree data** — The `indexSnapshot()` method reads `snapshot.routerIndex` which contains `file_path` entries pointing to `.docuvia/l3_decisions/*.md` in the working tree. This means the indexer is indexing working tree files, not orphan branch content, which is consistent with the current (incorrect) Tier 2 behavior.

## Round 3 — Integration & Completeness Review

### Integration with Orphan Branch Writer (3.4.1)

The server-side orphan branch writer (`orphan-branch-writer.ts`) writes knowledge to the `docuvia-knowledge` branch. The KnowledgeStore's `_loadFromGit()` reads from the same branch. This integration is architecturally sound — the writer produces what the reader consumes.

However, the integration is only usable when:
1. The server has written knowledge to the orphan branch (via sync route)
2. The developer has fetched the orphan branch (`git fetch origin docuvia-knowledge`)
3. The developer has no `.docuvia/` YAML files (so Tier 3 is reached)

In practice, condition #3 is unlikely because `initProject` creates `.docuvia/` YAML files, which means Tier 2 will always succeed (even if the files are empty skeletons), and Tier 3 will never be reached.

### Integration with docuvia sync CLI (3.4.3)

The `docuvia sync` CLI (item 3.4.3) does not exist (verified as ❌ WARN in report 0044). This CLI is supposed to:
1. Read `.docuvia/config.yaml` and `.docuvia/.snapshot-ref`
2. Call `POST /sync`
3. Run `git fetch origin docuvia-knowledge` to update the local snapshot

Without this CLI, there's no automated way to update the local orphan branch snapshot after the server writes new knowledge.

### Integration with Bidirectional Sync (3.4.2)

The bidirectional sync (item 3.4.2) depends on the orphan branch as the sync medium. The KnowledgeStore reading from the orphan branch is the consumer side of this sync. Without the KnowledgeStore properly reading from the orphan branch as the primary source, the bidirectional sync cannot function as designed.

### Integration with KnowledgeIndexer (new)

The new `KnowledgeIndexer` is activated in `extension.ts` (line 90) and subscribes to `store.onDidLoad` to re-index when the store reloads. It also listens to `onDidChangeTextDocument` and `onDidSaveTextDocument` for incremental updates. This is well-integrated with the existing KnowledgeStore lifecycle.

However, the `KnowledgeIndexer` reads `entry.file_path` from `snapshot.routerIndex`, which points to `.docuvia/l3_decisions/*.md` in the working tree. If the KnowledgeStore were rewritten to read from the orphan branch, the `KnowledgeIndexer` would also need to be updated to read decision content from the orphan branch (or from a local cache populated by the orphan branch fetch).

### End-to-End Usability

The feature is **partially implemented** but **not usable as designed**:

| Component | Status |
|-----------|--------|
| Orphan branch writer (server) | ✅ Implemented (item 3.4.1) |
| KnowledgeStore reads orphan branch | ✅ Implemented (Tier 3 fallback) |
| KnowledgeStore reads orphan branch as PRIMARY source | ❌ Not implemented |
| `.docuvia/` contains only manifest | ❌ Not implemented (contains full knowledge) |
| `.snapshot-ref` mechanism | ❌ Not implemented |
| FileSystemWatcher monitors orphan branch | ❌ Not implemented |
| `docuvia sync` CLI triggers fetch | ❌ Not implemented (item 3.4.3) |
| KnowledgeIndexer uses orphan branch data | ❌ Not implemented (uses working tree data) |

### Missing Tests

- No unit tests for `_loadFromGit()`
- No integration tests for the three-tier fallback chain
- No tests verifying orphan branch content is correctly parsed
- No tests for the `.snapshot-ref` mechanism (doesn't exist)
- No tests for `KnowledgeIndexer` with orphan branch data

### Performance

The `_loadFromGit()` method executes multiple sequential `git` commands via `child_process.exec`. For a project with N L3 decisions, it runs:
- 1 `git show` for `l1_tags.yaml`
- 1 `git ls-tree` for `l2_modules/`
- N `git show` for each L2 module YAML
- 1 `git ls-tree -r` for `l3_decisions/`
- M `git show` for each L3 decision Markdown file

This could be slow for large projects (50+ L3 decisions = 50+ sequential process spawns). A more efficient approach would be to use `git archive` or `git cat-file --batch` to read multiple files in a single command.

The `KnowledgeIndexer` is well-optimized with O(log N) interval tree lookups and debounced indexing.

## Findings

### Issues

1. **[HIGH] KnowledgeStore reads full knowledge from `.docuvia/` working tree, not orphan branch** — The current Tier 2 reads `l1_tags.yaml`, `l2_modules.yaml`, `l3_router.yaml`, and `l3_decisions/*.md` from the working tree. Per ADR-008, `.docuvia/` should contain only a lightweight manifest. The orphan branch should be the primary knowledge source.

2. **[HIGH] Orphan branch is only used as last-resort fallback** — `_loadFromGit()` (Tier 3) is only reached when both Tier 1 and Tier 2 return empty results. In practice, `initProject` creates `.docuvia/` YAML files, so Tier 2 always succeeds and Tier 3 is never reached.

3. **[MEDIUM] No `.snapshot-ref` mechanism** — The design describes `.docuvia/.snapshot-ref` as a pointer to the orphan branch HEAD. This file is never created, read, or used. Without it, the KnowledgeStore has no way to know which orphan branch commit to read.

4. **[MEDIUM] FileSystemWatcher doesn't detect orphan branch updates** — The watcher monitors `.docuvia/**` in the working tree. When the orphan branch is updated (via `git fetch`), the watcher doesn't fire.

5. **[MEDIUM] `initProject` writes full knowledge skeletons** — The `initProject` function writes `l1_tags.yaml`, `l2_modules.yaml`, and `l3_router.yaml` as skeleton files with example content. Per ADR-008, these should be minimal or the knowledge should come from the orphan branch.

6. **[MEDIUM] KnowledgeIndexer indexes working tree data, not orphan branch data** — The new `KnowledgeIndexer` (commit `eba22d4`) reads `snapshot.routerIndex` entries that point to `.docuvia/l3_decisions/*.md` in the working tree. If the KnowledgeStore were rewritten to read from the orphan branch, the indexer would need corresponding updates.

7. **[LOW] Duplicate parsing logic in Tier 2 and Tier 3** — The same YAML/Markdown parsing is performed for both local files and orphan branch content, with no shared caching.

8. **[LOW] Sequential git commands for orphan branch reading** — Each file in the orphan branch is read via a separate `git show` command, which is inefficient for large projects.

### Risks

- **Knowledge staleness**: Without the `.snapshot-ref` mechanism and orphan branch monitoring, the KnowledgeStore will continue reading stale `.docuvia/` files even after the orphan branch has been updated with new knowledge.
- **Cascading dependency**: This item (3.4.4) is a prerequisite for the bidirectional sync (3.4.2) to work as designed. Until the KnowledgeStore reads from the orphan branch as the primary source, the sync architecture is incomplete.
- **Developer confusion**: Developers who follow the ADR-008 design and expect `git fetch origin docuvia-knowledge` to update their knowledge view will be confused when the KnowledgeStore continues reading from `.docuvia/` working tree files.
- **KnowledgeIndexer orphan branch gap**: The new KnowledgeIndexer (commit `eba22d4`) will need to be updated when the KnowledgeStore is rewritten, otherwise it will continue indexing working tree data while the KnowledgeStore reads from the orphan branch.

### Recommendations

1. **Rewrite `_loadWorkspace()` to prioritize the orphan branch** — Change the loading order to: (1) Server API, (2) Orphan branch ref, (3) Local `.docuvia/` manifest only. Remove the reading of full knowledge from `.docuvia/` working tree files.

2. **Implement `.snapshot-ref` mechanism** — Create `.docuvia/.snapshot-ref` that stores the orphan branch HEAD commit hash. Read this file to determine which commit to read from the orphan branch.

3. **Update `initProject` to write only a manifest** — Instead of writing full knowledge skeletons, write only `manifest.yaml` (with `project_id` and `server_url`) and `.snapshot-ref` (pointing to the orphan branch HEAD).

4. **Add orphan branch change detection** — Either poll the orphan branch periodically or provide a command to refresh from the orphan branch. The FileSystemWatcher on `.docuvia/**` should also watch for changes to `.snapshot-ref`.

5. **Update `KnowledgeIndexer` to work with orphan branch data** — When the KnowledgeStore is rewritten, ensure the `KnowledgeIndexer` can index decisions from orphan branch content (or from a local cache populated by the orphan branch fetch).

6. **Optimize orphan branch reading** — Use `git cat-file --batch` or `git archive` to read multiple files from the orphan branch in a single command, reducing process spawn overhead.

7. **Update design docs** — Update `knowledge-graph/store.md` and `05-building-blocks.md` to reflect the ADR-008 target architecture.

## Overall Verdict

## ❌ FAIL

The VS Code KnowledgeStore has **not been rewritten** to read from the orphan branch ref as its primary knowledge source. While the `_loadFromGit()` method exists and correctly reads from the `docuvia-knowledge` orphan branch via `git show` and `git ls-tree`, it is only used as a **last-resort fallback** (Tier 3) when both the server API and local `.docuvia/` files yield no data. In practice, Tier 3 is never reached because `initProject` creates `.docuvia/` YAML files that Tier 2 reads.

The ADR-008 design requires the KnowledgeStore to read knowledge content from the orphan branch ref, with `.docuvia/` containing only a lightweight manifest. The current implementation inverts this: `.docuvia/` contains full knowledge content, and the orphan branch is an unused fallback. The `.snapshot-ref` mechanism, orphan branch change detection, and manifest-only `.docuvia/` structure are all missing.

The new `KnowledgeIndexer` (introduced in commit `eba22d4`) is well-designed for O(log N) AST anchoring but indexes working tree data, not orphan branch content, and will need corresponding updates when the KnowledgeStore is rewritten.

This item is a critical blocker for the bidirectional sync (item 3.4.2) and depends on the `docuvia sync` CLI (item 3.4.3) being implemented to provide the `git fetch origin docuvia-knowledge` trigger.
