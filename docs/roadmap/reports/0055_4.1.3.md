## Round 1 — Architecture & Design Review

### Design Intent

ADR-009 specifies that when a candidate L3 node matches an existing node (cosine similarity ≥ 0.85), the system should:
1. NOT insert a new node.
2. Increment the existing node's `occurrenceCount`.
3. Append the source commit hash to the existing node's `sourceCommits` JSONB array.

When a new L3 node is inserted (no match), it should be initialized with `sourceCommits = [commitHash]`.

### Implementation Analysis

**Schema (`l3_nodes.ts` line 35):**
```typescript
sourceCommits: jsonb("source_commits"),
```
The `sourceCommits` column is defined as `jsonb("source_commits")` — nullable, no default. This matches the design spec.

**Append on dedup match (`generate.ts` lines 856–869):**
```typescript
if (maxL3Sim >= similarityThreshold && bestL3Match) {
  const currentSources = Array.isArray(bestL3Match.sourceCommits)
    ? (bestL3Match.sourceCommits as string[])
    : [];
  const updatedSources = l3data.commitHash
    ? [...currentSources, l3data.commitHash]
    : currentSources;
  const newOccurrenceCount = bestL3Match.occurrenceCount + 1;

  await db
    .update(l3NodesTable)
    .set({ occurrenceCount: newOccurrenceCount, sourceCommits: updatedSources })
    .where(eq(l3NodesTable.id, bestL3Match.id));
```
This correctly reads the existing array, appends the new commit hash, and writes the updated array back. ✅

**Init on new insert (`generate.ts` lines 893–907):**
```typescript
sourceCommits: l3data.commitHash ? [l3data.commitHash] : [],
```
New L3 nodes are initialized with the first commit hash in `sourceCommits`. ✅

**Condensation reads sourceCommits (`generate.ts` lines 96–134):**
```typescript

  model: string

  if (!commits.length) return null;

```
The condensation function correctly reads `sourceCommits` and uses it as input for AI re-synthesis. ✅

**Sync route reads sourceCommits (`sync.ts` lines 163–178):**
```typescript

  .select({ id: l3NodesTable.id, sourceCommits: l3NodesTable.sourceCommits })

  })
```

The sync route uses `sourceCommits` to determine which L3 nodes should be promoted to "valid" status based on pushed commits. ✅

### Gaps

1. **No dedup within the `sourceCommits` array.** If the same commit hash is processed multiple times (e.g., re-running the generate pipeline on the same commit), the commit hash will be appended to `sourceCommits` each time, creating duplicate entries. The code at line 861–863 does `[...currentSources, l3data.commitHash]` without checking if `l3data.commitHash` already exists in `currentSources`.

2. **Nullable column with no DB-level default.** The `sourceCommits` column is `jsonb("source_commits")` with no `.default()` and no `.notNull()`. This means it defaults to `NULL` at the DB level. The code handles this defensively (`Array.isArray(...)` check), but a DB-level default of `'[]'::jsonb` would be safer.

3. **No DB index on `sourceCommits`.** The design spec mentions a reverse index (`commit_hash → l3_node_ids`). There is no GIN index on `source_commits` in the schema. Querying "which L3 nodes did this commit contribute to?" would require a full table scan.

## Round 2 — Code Quality & Security Review

### Code Quality

**Defensive handling:** The code consistently uses `Array.isArray(bestL3Match.sourceCommits)` before accessing the array. This is good defensive programming against NULL or malformed JSONB values. ✅

**Immutability:** The spread operator `[...currentSources, l3data.commitHash]` creates a new array rather than mutating the existing one. ✅

**Separation of concerns:** The append logic is inline within the generate pipeline's dedup branch. This is acceptable for the current scope but could be extracted into a helper function if the pattern is reused elsewhere.

**Type safety:** The `sourceCommits` column is typed as `jsonb("source_commits")` which maps to `unknown` in the Drizzle schema. The code casts it to `string[]` after the `Array.isArray` check. This is a reasonable approach, but a more precise Drizzle type (e.g., `jsonb("source_commits").$type<string[]>()`) would improve type safety.

### Security

**No injection risk:** The commit hash is appended to a JSONB array via Drizzle's parameterized queries. No SQL injection risk. ✅

**No authorization check on append:** The `sourceCommits` append happens within the generate pipeline, which is an internal server process. No direct user input triggers this path. ✅

**Input validation:** The `l3data.commitHash` is checked for truthiness before appending (`l3data.commitHash ? [...currentSources, l3data.commitHash] : currentSources`). However, there is no validation that the commit hash is a valid SHA-1/SHA-256 format. An empty string or malformed hash would be filtered by the truthiness check, but a non-empty invalid string would be appended.

### Code Smells

1. **Duplicate logic in `test-output.ts`:** The `test-output.ts` file contains nearly identical dedup logic to `generate.ts` (lines 837–847 and 883). This is a maintenance risk — fixes to the dedup logic need to be applied in both places.

2. **Magic number in condensation:** `commits.slice(0, 50)` limits condensation to 50 commits. This is not configurable and not documented in the design spec.

## Round 3 — Integration & Completeness Review

### Integration

**Generate pipeline → Condensation:** The `sourceCommits` array is correctly passed to `condenseL3Node()` which uses it to fetch commit data and re-synthesize content. The integration is sound. ✅

**Generate pipeline → Sync route:** The sync route reads `sourceCommits` to promote L3 nodes to "valid" status when their commits are pushed. This creates a clean pipeline: generate appends → sync validates. ✅

**Schema → API layer:** The `l3_nodes.ts` route handler does not explicitly handle `sourceCommits` in its CRUD endpoints (it relies on the default Drizzle insert/update behavior). This is acceptable since `sourceCommits` is managed internally by the generate pipeline.

### Completeness

**What works:**
- ✅ Schema column exists (`sourceCommits jsonb`)
- ✅ Append on dedup match (generate.ts lines 856–869)
- ✅ Init on new insert (generate.ts line 904)
- ✅ Condensation reads sourceCommits (generate.ts lines 96–134)
- ✅ Sync route reads sourceCommits for validity promotion (sync.ts lines 163–178)
- ✅ Defensive null/type checking throughout

**What's missing:**
- ⚠️ No dedup check within the `sourceCommits` array before appending (duplicate entries possible)
- ⚠️ No GIN index on `source_commits` for reverse lookup performance
- ⚠️ No DB-level default (`'[]'::jsonb`) — relies on application-level handling of NULL
- ⚠️ No tests specifically for the `sourceCommits` append behavior (unit or integration)
- ⚠️ `test-output.ts` duplicates the dedup logic, creating a maintenance risk

### Performance

The `sourceCommits` append is a single-row UPDATE via primary key (`WHERE id = ?`), which is O(1). No performance concern for the append operation itself. However, the lack of a GIN index means reverse lookups (commit hash → L3 nodes) will be O(n) table scans.

## Findings

| # | Severity | Finding |
|---|----------|---------|
| 1 | Low | No dedup check within `sourceCommits` array before appending — re-processing the same commit will create duplicate entries. The condensation function uses SQL `IN` which handles duplicates gracefully, so impact is minimal. |
| 2 | Low | `sourceCommits` column has no DB-level default (`'[]'::jsonb`). NULL is handled defensively in application code, but a DB default would be safer. |
| 3 | Medium | No GIN index on `source_commits` column. Reverse lookups (commit → L3 nodes) will require full table scans. The design spec explicitly mentions this reverse index as a benefit. |
| 4 | Medium | No unit or integration tests for the `sourceCommits` append behavior. The logic is only exercised through the full generate pipeline. |
| 5 | Low | `test-output.ts` duplicates the dedup/append logic from `generate.ts`, creating a maintenance risk. |
| 6 | Low | The `l3data.commitHash` is not validated for proper SHA format before appending to `sourceCommits`. |

---

## Recommendations

1. **Add dedup check before append:** Before `[...currentSources, l3data.commitHash]`, check `!currentSources.includes(l3data.commitHash)` to prevent duplicate entries.
2. **Add GIN index:** Consider adding `CREATE INDEX idx_l3_nodes_source_commits ON l3_nodes USING gin (source_commits);` in a migration for reverse lookup performance.
3. **Add DB-level default:** Change the column definition to `jsonb("source_commits").default(sql`'[]'::jsonb`)` to ensure NULL is never stored.
4. **Add tests:** Write unit tests for the dedup logic that verify `sourceCommits` append behavior, including edge cases (null, empty array, duplicate hash).
5. **Consolidate duplicate logic:** Refactor `test-output.ts` to share the dedup logic with `generate.ts` or remove the duplication.

---

## Overall Verdict

**⚠️ WARN**

The `sourceCommits` JSONB array append is correctly implemented per ADR-009. The append-on-match logic in `generate.ts` works as designed, the init-on-insert is correct, and the downstream consumers (condensation, sync) properly read the array. However, there are minor issues: no dedup within the array, no GIN index for reverse lookups, no DB-level default, and no tests. These are not blockers but should be addressed for robustness.
