## Round 1 — Architecture & Design Review

**Question:** Does the design document correctly describe the feature? Are there gaps between the design spec and the actual implementation?

**Analysis:**

The ADR-009 describes the condensation behavior clearly:
1. Check cosine similarity ≥ 0.85 before L3 insert
2. If match found, increment `occurrenceCount` and append to `sourceCommits`
3. When `occurrenceCount` reaches `condensation_threshold` (default: 30), run AI condensation
4. Condensation re-synthesizes `content` using all `sourceCommits` as input
5. Condensation review task creation is configurable via `condensation_review_required`

**What is implemented:**
- The `condenseL3Node()` function exists at `generate.ts:96-134` and correctly implements re-synthesis: it fetches commit data from the DB for each hash in `sourceCommits`, builds a summary, and calls the LLM with a system prompt to produce updated content.
- The threshold check exists at `generate.ts:872`: `if (newOccurrenceCount >= condensationThreshold)`.
- The `condensationThreshold` column exists in `llm_configs.ts:15` with `.notNull().default(30)`.
- The `condensationReviewRequired` column exists in `llm_configs.ts:16` with `.notNull().default(false)`.
- `sync.ts:86-94` correctly reads these values from `configYaml` and upserts them into `llm_configs`.

**Verdict:** The design document correctly describes the feature, and the implementation covers the core architecture as specified. The only gap is a data flow bug (detailed in Round 2), not an architectural gap.

## Round 2 — Code Quality & Security Review

**Question:** Is the implementation well-structured and following project coding rules? Are there security issues, code smells, bugs?

**Findings:**

### 🐛 BUG-01: Stale Data Passed to Condensation Function (Severity: Medium)

**File:** `artifacts/api-server/src/routes/generate.ts`, lines 866–873

```typescript
// Lines 866-869: DB is updated with new occurrenceCount and updated sourceCommits
await db
  .update(l3NodesTable)
  .set({ occurrenceCount: newOccurrenceCount, sourceCommits: updatedSources })
  .where(eq(l3NodesTable.id, bestL3Match.id));

// Lines 872-873: OLD stale bestL3Match object is passed to condensation
if (newOccurrenceCount >= condensationThreshold) {
  const condensed = await condenseL3Node(bestL3Match, model);
```

The `bestL3Match` object was fetched from the database *before* the DB update on line 866. It contains the old `sourceCommits` array (without the latest commit hash appended on line 861–863). When `condenseL3Node` receives this stale object, it will synthesize content **without the latest commit context**. The fix should either:
- Pass `{ ...bestL3Match, sourceCommits: updatedSources }` to `condenseL3Node`, or
- Re-fetch the node after the update

### 🔍 OBSERVATION-01: Occurrence Count Threshold Edge Case (Severity: Low)

When condensation runs and synthesizes new content, the `occurrenceCount` is NOT reset. This means:
- If threshold is 30, condensation runs at 30, 31, 32, ... on every subsequent duplicate match
- This could result in repeated LLM calls for the same node every time a new duplicate is found, which may be intentional (progressively richer synthesis) or wasteful depending on interpretation.

The ADR does not specify whether `occurrenceCount` should be reset after condensation. The current implementation does not reset it. This is a design ambiguity rather than a bug, but it could lead to unexpected LLM costs at scale.

### 🔍 OBSERVATION-02: No Unit Tests for Condensation Logic (Severity: Medium)

There are no unit tests anywhere that cover the `condenseL3Node()` function or the condensation threshold trigger path. The test directory `artifacts/api-server/test/` contains no `generate.*.test.ts` files. This means:
- The condensation function's LLM error handling is untested
- The threshold trigger logic is untested
- The stale data bug (BUG-01) would not be caught by automated tests

### ✅ Code Quality: Good

- The `condenseL3Node` function follows defensive design: checks `Array.isEmpty`, try/catch around LLM call, returns `null` on failure
- The condensation trigger correctly reads config from DB with defaults
- The review task creation follows the same pattern as other review tasks in the codebase
- Nesting is manageable; the function remains readable

## Round 3 — Integration & Completeness Review

**Question:** Does the feature integrate correctly with other parts of the system? Are there missing tests, performance concerns, usability gaps?

**Findings:**

### Integration Assessment

1. **Schema → Generate → Sync integration:** The `llm_configs` table stores `condensationThreshold` and `condensationReviewRequired`. The `generate` route reads them via `getModel()` (line 528–534). The `sync` route can update them from `.docuvia/config.yaml` (lines 86–94 in sync.ts). This three-way integration is correct and complete.

2. **Dedup → Condensation pipeline:** Condensation only fires within the dedup path (when `maxL3Sim >= similarityThreshold`). The flow is:
   - Candidate L3 embedding computed → compared against existing L3s → if match found → increment count → check threshold → condense
   
   This is correct per ADR-009. New L3 nodes (no dedup match) start at `occurrenceCount: 1` and won't trigger condensation until 29 more similar commits are processed.

3. **Content update after condensation:** The condensed content updates `l3_nodes.content` DB row (line 877). No cache invalidation occurs, but since the system reads from DB on next query, this is fine.

4. **Review task integration:** When `condensationReviewRequired` is true, a `validate` review task is created (line 881–888). This follows the same pattern as other review tasks in the codebase.

### Performance Concerns

- **O(n) per-node LLM calls:** Each condensation trigger calls the LLM synchronously during the generate run. If multiple nodes hit the threshold in the same run (likely in batch processing), this could significantly increase the generate run's latency. No batching or queuing mechanism exists for condensation tasks.

- **No async/deferred condensation:** ADR-009 does not specify whether condensation should be synchronous or deferred. The current implementation is synchronous, which means a generate run's response time includes all condensation LLM calls. For high-frequency dedup matches, this could make the API endpoint slow.

## Findings Summary

### Issues

| ID | Severity | Finding | Location |
|----|----------|---------|----------|
| BUG-01 | Medium | Stale `bestL3Match` object (with old `sourceCommits`) is passed to `condenseL3Node()` after the DB has been updated with the latest commit hash. The condensation AI synthesizes content without the latest commit's context. | `generate.ts:873` |
| OBS-01 | Low | `occurrenceCount` is never reset after condensation. The AI condensation will re-run on every subsequent duplicate match (at 30, 31, 32, ...) which may cause repeated LLM costs. ADR does not specify reset behavior. | `generate.ts:872-889` |
| OBS-02 | Medium | Zero unit tests exist for the condensation logic. No test file for the generate route handler condensation path. | `artifacts/api-server/test/` |
| OBS-03 | Low | Synchronous condensation during generate runs may cause latency spikes when multiple nodes hit the threshold in the same batch. No async/deferred mechanism. | `generate.ts:872-878` |

### Recommendations

1. **Fix BUG-01:** Change line 873 from `condenseL3Match(bestL3Match, model)` to `condenseL3Node({ ...bestL3Match, sourceCommits: updatedSources }, model)` so the condensation function receives the complete source commits including the latest one.

2. **Address OBS-01:** Decide whether `occurrenceCount` should be reset after condensation. If yes, add `.set({ occurrenceCount: 0 })` or similar after condensation completes. If no, document this behavior in the ADR.

3. **Address OBS-02:** Add unit tests for `condenseL3Node()` covering: empty sourceCommits, LLM failure, successful synthesis. Add integration tests for the condensation trigger path.

4. **Address OBS-03:** Consider making condensation asynchronous (fire-and-forget or queued) so generate run latency is not impacted by multiple condensation LLM calls.

## Overall Verdict

**⚠️ WARN**

The AI condensation feature at occurrence threshold is **fully implemented** per the ADR-009 design spec. The core logic exists and functions correctly end-to-end: threshold configuration, condensation trigger, LLM-based content re-synthesis, and optional review task creation are all present.

However, there is a **data freshness bug** (BUG-01) where the condensation function receives stale commit data, potentially producing incomplete synthesized content. Combined with the complete absence of tests for this feature, a **⚠️ WARN** verdict is warranted. The bug is straightforward to fix and does not require architectural changes.
