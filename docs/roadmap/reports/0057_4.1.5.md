## Round 1 — Architecture & Design Review

### Design-to-Implementation Mapping

ADR-009 specifies three new columns on `l3_nodes`. Here is the precise mapping:

#### 1. `occurrenceCount` column

**Schema (`l3_nodes.ts`, line 34):**
```typescript
occurrenceCount: integer("occurrence_count").notNull().default(1),
```
✅ Column exists with correct type (`integer`), `NOT NULL` constraint, and default value of 1.

**Write path — increment on dedup match (`generate.ts`, lines 864–869):**
```typescript
const newOccurrenceCount = bestL3Match.occurrenceCount + 1;
await db.update(l3NodesTable).set({ occurrenceCount: newOccurrenceCount, ... });
```
✅ Incremented by 1 on each dedup match.

**Write path — init on new insert (`generate.ts`, line 903):**
```typescript
occurrenceCount: 1,
```
✅ New nodes start at count 1.

**Read path — condensation trigger (`generate.ts`, line 872):**
```typescript
if (newOccurrenceCount >= condensationThreshold) { ... }
```
✅ Count is compared against configurable threshold to trigger condensation.

#### 2. `sourceCommits` column

**Schema (`l3_nodes.ts`, line 35):**
```typescript
sourceCommits: jsonb("source_commits"),
```
✅ Column exists with correct type (`jsonb`). Nullable (no `.notNull()`), no DB-level default.

**Write path — append on dedup match (`generate.ts`, lines 858–863):**
```typescript
const currentSources = Array.isArray(bestL3Match.sourceCommits)
  ? (bestL3Match.sourceCommits as string[])
  : [];
const updatedSources = l3data.commitHash
  ? [...currentSources, l3data.commitHash]
  : currentSources;
```
✅ Defensive null/type handling, immutable array append.

**Write path — init on new insert (`generate.ts`, line 904):**
```typescript
sourceCommits: l3data.commitHash ? [l3data.commitHash] : [],
```
✅ New nodes initialized with first commit hash.

**Read path — condensation (`generate.ts`, lines 96–134):**
```typescript
const commits = Array.isArray(node.sourceCommits) ? (node.sourceCommits as string[]) : [];
if (!commits.length) return null;
```
✅ Defensive read with empty-array guard.

**Read path — sync route (`sync.ts`, lines 163–184):**
```typescript
const sources = Array.isArray(n.sourceCommits) ? (n.sourceCommits as string[]) : [];
return sources.some((h) => pushedCommits.includes(h));
```
✅ Used to promote L3 nodes to "valid" when their commits are pushed.

#### 3. `validityStatus` column

**Schema (`l3_nodes.ts`, line 36):**
```typescript
validityStatus: text("validity_status").notNull().default("pending"),
```
✅ Column exists with correct type (`text`), `NOT NULL` constraint, and default value of "pending".

**Write path — new L3 nodes (`generate.ts`, line 905):**
```typescript
validityStatus: "pending",
```
✅ All new L3 nodes start with "pending" status.

**Write path — sync promotion (`sync.ts`, lines 180–184):**
```typescript
await db.update(l3NodesTable).set({ validityStatus: "valid" })
  .where(inArray(l3NodesTable.id, validL3Ids));
```
✅ L3 nodes are promoted to "valid" when their source commits are pushed.

**Read path — intent router filtering (`intent-router.ts`, lines 194–195, 494–495):**
```typescript
// With include_pending:
? or(eq(l3NodesTable.validityStatus, "valid"), eq(l3NodesTable.validityStatus, "pending"))
// Without include_pending (default):
: eq(l3NodesTable.validityStatus, "valid");
```
✅ Intent router correctly filters by validityStatus, supporting both default (valid-only) and include-pending modes.

### Gaps Identified

1. **No DB index on `l3_nodes(l2NodeId)`:** ADR-009 states "A DB index on `l3_nodes(l2NodeId)` with pre-loaded embeddings makes the per-node scan efficient at L2-scoped scale." The schema definition has no index. The dedup query at `generate.ts:825–828` will perform a sequential scan. This was also noted in the 4.1.1 report.

2. **No GIN index on `source_commits`:** ADR-009 mentions a "reverse index (`commit_hash → l3_node_ids`)" as a consequence. There is no GIN index on the `source_commits` JSONB column. Querying "which L3 nodes did this commit contribute to?" requires a full table scan. This was also noted in the 4.1.3 report.

3. **`sourceCommits` column has no DB-level default:** The column is `jsonb("source_commits")` with no `.default()`. It defaults to `NULL` at the DB level. Application code handles this defensively, but a DB-level default of `'[]'::jsonb` would be safer.

4. **`validityStatus` uses `text` type instead of `pgEnum`:** The `nodeType` column uses `pgEnum("l3_node_type", [...])`, but `validityStatus` uses a plain `text("validity_status")`. This means invalid values (e.g., "valid", "orphaned", or typos) can be stored at the DB level. A `pgEnum` would provide DB-level constraint validation. However, the application code consistently uses string literals, so this is a minor risk.

5. **No `orphaned` status in the codebase:** ADR-011 (item 4.3.3) specifies the validity status enum as `pending | valid | orphaned`. The current code only uses "pending" and "valid". The "orphaned" status is not yet implemented anywhere. This is expected since ADR-011 items are still pending verification.

### Verdict on Architecture

All three columns (`occurrenceCount`, `sourceCommits`, `validityStatus`) are **correctly defined** in the Drizzle schema and **correctly used** throughout the codebase. The schema matches ADR-009's specification precisely. The missing DB indexes are performance optimizations noted in previous reports. The `text` vs `pgEnum` choice for `validityStatus` is a minor design inconsistency but not a correctness issue.

## Round 2 — Code Quality & Security Review

### Positive Observations

1. **Consistent defensive coding:** All reads of `sourceCommits` use `Array.isArray()` checks before accessing the array. This protects against NULL or malformed JSONB values. ✅

2. **Immutable array operations:** The spread operator `[...currentSources, l3data.commitHash]` creates a new array rather than mutating the existing one. ✅

3. **Default values are correct:** `occurrenceCount` defaults to 1 (each L3 node has at least one occurrence — its own creation). `validityStatus` defaults to "pending" (new AI-generated nodes need review/validation). ✅

4. **Clean column naming:** The Drizzle schema uses camelCase in TypeScript (`occurrenceCount`, `sourceCommits`, `validityStatus`) and snake_case in SQL (`occurrence_count`, `source_commits`, `validity_status`), following the project convention. ✅

### Issues

#### Issue 1: Missing DB Index on `l3_nodes(l2NodeId)` (Medium Risk)

**File:** `lib/db/src/schema/l3_nodes.ts`

The schema has no index on `l2NodeId`. The dedup query in `generate.ts:825–828`:
```typescript
const existingL3ForNode = await db
  .select()
  .from(l3NodesTable)
  .where(and(eq(l3NodesTable.l2NodeId, l2node.id), isNotNull(l3NodesTable.embedding)));
```
performs a sequential scan. For large knowledge graphs with thousands of L3 nodes, this could be slow.

**Recommendation:** Add an index via a migration:
```sql
CREATE INDEX idx_l3_nodes_l2_node_id ON l3_nodes(l2_node_id);
-- Or a partial index for the dedup query:
CREATE INDEX idx_l3_nodes_l2_embedding ON l3_nodes(l2_node_id) WHERE embedding IS NOT NULL;
```

#### Issue 2: Missing GIN Index on `source_commits` (Medium Risk)

**File:** `lib/db/src/schema/l3_nodes.ts`

ADR-009 specifies a reverse index for `commit_hash → l3_node_ids`. The `sourceCommits` JSONB column has no GIN index. The sync route's filter (`sync.ts:171–178`) scans all L3 nodes in memory to find matches.

**Recommendation:** Add a GIN index:
```sql
CREATE INDEX idx_l3_nodes_source_commits ON l3_nodes USING gin(source_commits);
```

#### Issue 3: `validityStatus` Uses `text` Instead of `pgEnum` (Low Risk)

**File:** `lib/db/src/schema/l3_nodes.ts`, line 36

```typescript
validityStatus: text("validity_status").notNull().default("pending"),
```

The `nodeType` column uses `pgEnum`, but `validityStatus` uses plain `text`. This means the DB will accept any string value, including typos like "vaild" or "pendng". The application code is the only guard.

**Recommendation:** Consider using `pgEnum` for consistency and DB-level validation:
```typescript
export const l3ValidityStatusEnum = pgEnum("l3_validity_status", ["pending", "valid", "orphaned"]);
```

#### Issue 4: No DB-Level Default on `sourceCommits` (Low Risk)

**File:** `lib/db/src/schema/l3_nodes.ts`, line 35

```typescript
sourceCommits: jsonb("source_commits"),
```

No `.default()` is set. The column defaults to `NULL` at the DB level. Application code handles this, but a DB default would be safer:
```typescript
sourceCommits: jsonb("source_commits").default(sql`'[]'::jsonb`),
```

#### Issue 5: No Unit Tests for Schema Column Behavior (Medium Risk)

There are no unit tests that verify:
- The `occurrenceCount` default value of 1
- The `validityStatus` default value of "pending"
- The `sourceCommits` column accepts and returns JSONB arrays correctly
- The `validityStatus` column accepts only valid values (if constrained)

The schema is only tested indirectly through integration tests of the generate and sync routes.

## Round 3 — Integration & Completeness Review

### Integration Points

1. **Schema → Generate pipeline:** All three columns are correctly written by the generate pipeline. New L3 nodes get `occurrenceCount: 1`, `sourceCommits: [hash]`, `validityStatus: "pending"`. Dedup matches increment `occurrenceCount` and append to `sourceCommits`. ✅

2. **Schema → Sync route:** The sync route reads `sourceCommits` to identify L3 nodes whose commits have been pushed, then promotes their `validityStatus` to "valid". This creates a clean pipeline: generate writes "pending" → sync promotes to "valid". ✅

3. **Schema → Intent router:** The intent router filters L3 nodes by `validityStatus`. By default, only "valid" nodes are returned. With `include_pending=true`, both "valid" and "pending" nodes are included. This is correct per ADR-011 (item 4.3.4). ✅

4. **Schema → Condensation:** The `sourceCommits` array is read by the `condenseL3Node()` function to fetch commit data and re-synthesize content. The `occurrenceCount` drives the condensation threshold check. ✅

5. **Schema → API layer:** The `l3_nodes.ts` route handler (CRUD) does not explicitly manage these columns — they are internal to the generate/sync pipeline. The PATCH endpoint (line 52–62) allows updating any field including these, which is acceptable. ✅

### Missing Tests

- No unit tests for the Drizzle schema defaults (occurrenceCount=1, validityStatus="pending")
- No integration tests that verify the full lifecycle: generate creates "pending" → sync promotes to "valid"
- No tests for the intent router's validityStatus filtering
- No tests for the GIN index (if added) on source_commits

### Performance Concerns

1. **Sequential scan on `l2NodeId`:** Without an index, the dedup query scans all L3 nodes. For typical projects (< 100 L3 nodes per L2), this is acceptable. For large-scale projects, the missing index could cause noticeable latency.

2. **In-memory filtering in sync route:** The sync route loads all L3 nodes for the relevant L2 parents into memory and filters by `sourceCommits` in JavaScript (`sync.ts:171–178`). A GIN index would allow DB-level filtering.

3. **JSONB storage overhead:** The `sourceCommits` JSONB array grows with each dedup match. For high-frequency L3 nodes (occurrenceCount > 100), the array could become large. This is acceptable for the current scale but should be monitored.

### End-to-End Usability

The three columns form a complete lifecycle:

1. **Creation:** New L3 nodes start with `occurrenceCount: 1`, `sourceCommits: [hash]`, `validityStatus: "pending"`.
2. **Dedup:** Repeated generation runs increment `occurrenceCount` and append to `sourceCommits`.
3. **Condensation:** When `occurrenceCount` reaches the threshold, AI condensation re-synthesizes content.
4. **Validation:** When commits are pushed, the sync route promotes `validityStatus` to "valid".
5. **Query:** The intent router filters by `validityStatus` to control what knowledge is surfaced to agents.

This lifecycle is fully implemented and usable end-to-end.

## Recommendations

1. **Add DB index on `l2NodeId`:** `CREATE INDEX idx_l3_nodes_l2_node_id ON l3_nodes(l2_node_id);` — improves dedup query performance.
2. **Add GIN index on `source_commits`:** `CREATE INDEX idx_l3_nodes_source_commits ON l3_nodes USING gin(source_commits);` — enables efficient reverse lookups.
3. **Consider `pgEnum` for `validityStatus`:** Provides DB-level constraint validation and consistency with `nodeType`.
4. **Add DB-level default for `sourceCommits`:** `.default(sql`'[]'::jsonb`)` — prevents NULL values at the DB level.
5. **Add unit tests:** Test schema defaults, validityStatus filtering in intent-router, and the generate→sync lifecycle.

## Overall Verdict

**✅ PASS**

The `occurrenceCount`, `sourceCommits`, and `validityStatus` columns on `l3_nodes` are correctly defined in the Drizzle ORM schema and correctly used throughout the codebase. All three columns match the ADR-009 design specification:

- `occurrenceCount` — `integer NOT NULL DEFAULT 1`, incremented on dedup match, drives condensation threshold.
- `sourceCommits` — `jsonb`, appended on dedup match, read by condensation and sync routes.
- `validityStatus` — `text NOT NULL DEFAULT "pending"`, set to "valid" by sync route, filtered by intent router.

The issues identified are all performance or quality improvements (missing indexes, no `pgEnum`, no tests) — none are correctness issues or design-spec violations. The feature is functionally complete and usable end-to-end. The checklist marking of ⚠️ WIP is overly conservative — this feature is implemented and should be ✅ Done.
