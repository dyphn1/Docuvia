## Round 1 — Architecture & Design Review

### Design Spec Summary (ADR-010)

ADR-010 describes a "progressive batch mode" for the first generate run on a new project:

1. **Batch processing:** Commits are processed in groups of 20
2. **AI self-correction:** Each batch's LLM prompt includes the L2 module list from previous batches, enabling the AI to self-correct module names/boundaries across batches
3. **No human review for cross-batch merges:** Self-correction is automatic
4. **Human confirmation after all batches:** The discovered L2 module map is presented to the project manager for confirmation
5. **Path rule storage:** Upon confirmation, L2 module boundaries are written as glob path patterns to `.docuvia/config.yaml`
6. **Deterministic assignment:** All future commits are assigned to L2 modules via path matching (no LLM)
7. **Retroactive correction:** Historical `commit_l2_links` rows are flagged with `reindexRequired: true` and corrected on next generate run

### Implementation Analysis

**✅ Progressive batch mode exists (generate.ts:733-755):**

The generate route implements batch processing:
```typescript
// Bootstrap mode: batch 20 commits per LLM call, pass previous L2 list for self-correction
const BATCH_SIZE = 20;
const previousL2Names: string[] = [];

for (let batchStart = 0; batchStart < commitData.length; batchStart += BATCH_SIZE) {
    const batchCommits = commitData.slice(batchStart, batchStart + BATCH_SIZE);
    const batchResult = await generateL2Nodes(
        batchCommits, allL1Tags, documentContext, model,
        l2SystemPrompt, corrections, previousL2Names
    );
    for (const node of batchResult) {
        if (!previousL2Names.includes(node.name)) {
            previousL2Names.push(node.name);
        }
    }
    l2Input = [...l2Input, ...batchResult];
}
```

This correctly implements the batch-of-20 logic and passes `previousL2Names` for AI self-correction.

**✅ `generateL2Nodes()` function accepts `previousL2Names` parameter (generate.ts:187-229):**

The function builds a `previousBatchSection` into the LLM prompt when `previousL2Names` is provided:
```typescript
const previousBatchSection =
    previousL2Names && previousL2Names.length > 0
        ? `\n\nL2 modules discovered in previous batches (maintain consistency with these names): ${previousL2Names.join(", ")}`
        : "";
```

This enables the AI to self-correction module names across batches, per the design spec.

**✅ `generateL2Nodes()` also receives `corrections` for few-shot injection (generate.ts:193,201):**

The `buildFewShotSection()` function formats correction examples into the prompt. This supports the self-correction mechanism.

**✅ Schema supports bootstrap state tracking:**
- `l2_nodes.pathPatterns` (jsonb) — stores glob patterns
- `l2_nodes.reindexRequired` (boolean) — flags for retroactive correction
- `l2_nodes.isBootstrapConfirmed` (boolean) — tracks human confirmation

**✅ Bootstrap detection logic (generate.ts:722-731):**
```typescript
const allBootstrapConfirmed =
    existingL2.length > 0 && existingL2.every((n) => n.isBootstrapConfirmed);

if (allBootstrapConfirmed) {
    logger.info(..., "[generate] All L2 nodes bootstrap-confirmed — path-rule mode; L2 assignment deferred to sync pipeline");
} else {
    // Bootstrap mode: batch 20 commits per LLM call...
}
```

### Gaps Identified

1. **No bootstrap confirmation API endpoint:** ADR-010 requires the system to "present the discovered L2 module map to the project manager for confirmation." There is no `POST /projects/:id/l2-nodes/confirm-bootstrap` or similar endpoint. The `isBootstrapConfirmed` column exists in the schema but there is no API to set it to `true`. The `l2_nodes.ts` routes only have CRUD endpoints (POST, PATCH, DELETE, GET links) — none of them handle bootstrap confirmation.

2. **No path pattern storage endpoint:** ADR-010 says "L2 module boundaries are written as glob path patterns to `.docuvia/config.yaml` under `modules:`." There is no endpoint that writes path patterns to the config. The PATCH `/l2-nodes/:id` endpoint doesn't explicitly handle `pathPatterns` as a confirmed set.

3. **No reindex trigger on confirmation:** ADR-010 says "Historical `commit_l2_links` rows are flagged with `reindexRequired: true` and retroactively corrected on the next generate run." The `reindexRequired` column exists but no code sets it to `true` during bootstrap confirmation or triggers a reindex.

4. **No deterministic commit-to-module assignment in sync pipeline:** ADR-010 says "All future commits are assigned to L2 modules deterministically by path matching — LLM is no longer used for L2 assignment." The sync endpoint (`sync.ts`) logs "L2 assignment deferred to sync pipeline" but the actual path-matching logic is **not implemented** in sync.ts. The sync endpoint only handles branch name updates, validity promotion, config upsert, and orphan branch writing.

5. **Sieve model has partial path-pattern matching (generate.ts:426-431):** The `runSieveModel()` function does check `node.pathPatterns` for git-history score (W1) and directory-structure score (W3) with `sourceFile.startsWith(p)`. However, this uses `startsWith` rather than full glob matching, and the Sieve model is only called in the `/extract/sieve` endpoint context — not in the main sync pipeline.

## Round 2 — Code Quality & Security Review

### Code Quality

**✅ Well-structured batch loop:** The batch processing loop (generate.ts:737-754) is clean, uses `const BATCH_SIZE = 20` as a named variable, and correctly accumulates results.

**✅ Self-correction mechanism is sound:** Passing `previousL2Names` into the LLM prompt is a reasonable approach to cross-batch consistency. The names are accumulated incrementally: `if (!previousL2Names.includes(node.name))` prevents duplicates.

**✅ Schema design is clean:** `commit_l2_links.ts` properly defines a junction table with unique constraint and indexes on both `commitId` and `l2NodeId`. The `commits.ts` table properly deprecates `l2NodeId` with a comment.

**⚠️ `startsWith` vs. glob matching inconsistency:** In `generate.ts:428`, path pattern matching uses `sourceFile.startsWith(p)`, which is a prefix match rather than glob matching. The VS Code client (`DocuviaCodeLensProvider.ts:65`) correctly uses `minimatch(relPath, pattern, { matchBase: true })`. These two implementations are inconsistent — the server-side Sieve model won't match patterns like `src/auth/**` correctly with `startsWith`.

**⚠️ Orphan branch writer writes path_patterns but doesn't confirm bootstrap:** `orphan-branch-writer.ts:32-36` reads `node.pathPatterns` and writes it to YAML, and line 42 writes `bootstrap_confirmed: ${node.isBootstrapConfirmed}`. However, since no code ever sets `isBootstrapConfirmed = true`, the orphan branch will always show `bootstrap_confirmed: false` and `path_patterns: []`.

**⚠️ `writeKnowledgeToOrphanBranch` L1 tag names collection is a no-op:** At `orphan-branch-writer.ts:94`, `buildL1TagsYaml([])` is always called with an empty array, so L1 tags are never written to the orphan branch. This is a minor code quality issue.

**⚠️ Sync endpoint's autoGenerate check doesn't actually enqueue:** At `sync.ts:212-229`, when `autoGenerate` is enabled and cooldown has passed, the code only logs a message — it doesn't actually call the generate endpoint or enqueue a job. The comment says "enqueue deferred — actual queue implementation is deferred per plan."

### Security

**✅ No security vulnerabilities identified in the batch processing code.** The generate endpoint validates the project exists, uses Zod input validation (`GenerateInputSchema`), and processes commits within a try/catch that properly resets the project status to "error" on failure.

**⚠️ No authorization checks on the generate endpoint itself.** The endpoint validates the project exists but doesn't verify the caller has access to that project. This is consistent with the rest of the API (no auth middleware observed), so it's a systemic issue rather than a 4.2.1-specific one.

## Round 3 — Integration & Completeness Review

### Integration Points

**✅ Generate pipeline integration:** The batch mode is correctly integrated into the main `/projects/:id/generate` POST endpoint. It runs after L1 tag generation and before L3 node processing, which is the correct order.

**✅ VS Code client integration:** `DocuviaCodeLensProvider.ts:65` uses `minimatch` for path-pattern matching in the offline CodeLens fallback, which aligns with the path-rule concept from ADR-010.

**✅ Orphan branch writer integration:** The `orphan-branch-writer.ts` reads `pathPatterns` and `isBootstrapConfirmed` from the DB and writes them to YAML files in the orphan branch. The integration path exists even though the values are never set.

### Missing Integration Pieces

1. **Bootstrap confirmation UI (4.2.3):** The design spec calls for presenting the L2 module map for human confirmation. Neither the kg-engine frontend (`projects/[id].tsx`) nor the API server has a confirmation UI or endpoint. The `L2Directory` component in `[id].tsx` shows L2 nodes but has no "Confirm Bootstrap" button or path pattern editing capability.

2. **Path-rule assignment in sync pipeline (4.2.5):** When `allBootstrapConfirmed` is true, the generate pipeline skips L2 assignment with the message "deferred to sync pipeline." However, the sync pipeline has no path-matching logic to assign commits to L2 modules based on `pathPatterns`. This means the system can never actually transition from bootstrap mode to path-rule mode.

3. **Retroactive reindex (4.2.1 ADR requirement):** No code sets `reindexRequired = true` on historical `commit_l2_links` rows after bootstrap confirmation, and no reindex logic exists in the generate pipeline to handle them.

### Performance Considerations

**✅ Batch size of 20 is reasonable:** Processing commits in batches of 20 keeps LLM prompt sizes manageable while minimizing the number of API calls.

**⚠️ Embedding generation per L2 node is sequential:** At `generate.ts:795-805`, embeddings for L2 nodes are generated one at a time in a `for` loop. For projects with many L2 nodes, this could be slow. Batching or parallelizing embedding calls would improve performance.

**⚠️ Similarity scan per L3 candidate:** At `generate.ts:844-853`, cosine similarity is computed against all existing L3 nodes for each candidate. This is O(n*m) where n = candidates and m = existing nodes per L2. For large knowledge graphs, this will be slow (as noted in ADR-009 consequences).

### Test Coverage

**❌ No tests found for the bootstrap batch mode.** There are no unit tests verifying:
- The batch loop correctly processes commits in groups of 20
- `previousL2Names` is correctly accumulated across batches
- The bootstrap-to-path-rule transition
- The `isBootstrapConfirmed` check logic

The test files in the repository focus on other areas (RAG math, DB transactions, VS Code extension) but don't cover ADR-010 bootstrap logic.

## Overall Verdict

## ⚠️ WARN

### Rationale

The **core batch processing logic** (progressive batches of 20, AI self-correction via `previousL2Names`) is **correctly implemented** in `generate.ts`. The schema has all required columns. The architectural scaffolding for the full ADR-010 lifecycle exists.

However, the **bootstrap confirmation → path-rule activation pipeline is incomplete**. Three critical pieces are missing:
1. **No API endpoint** for confirming the L2 module map (setting `isBootstrapConfirmed`, storing path patterns)
2. **No path-rule matching logic** in the sync pipeline to deterministically assign commits to L2 modules
3. **No reindex mechanism** for retroactive `commit_l2_links` correction

Without these, the system can **discover** L2 modules via AI but can never **confirm** them or transition to deterministic path-rule mode. The batch mode works as a discovery mechanism, but the full ADR-010 lifecycle (discover → confirm → path rules) is incomplete.

### Recommendations (Priority Order)

1. **Add a `POST /projects/:id/l2-nodes/confirm-bootstrap`** endpoint that accepts the confirmed module map with path patterns, sets `isBootstrapConfirmed = true` on all L2 nodes, stores `pathPatterns`, sets `reindexRequired = true` on existing `commit_l2_links`, and writes to `.docuvia/config.yaml`
2. **Implement path-rule matching in the sync pipeline** — when `allBootstrapConfirmed` is true, match each pushed commit's diff paths against `l2_nodes.pathPatterns` (using `minimatch`, not `startsWith`) and create `commit_l2_links` entries
3. **Add a reindex step** in the generate pipeline that processes commits with `reindexRequired = true` and reassigns them via path matching
4. **Fix `startsWith` → `minimatch`** in `runSieveModel()` (generate.ts:428) for consistency with VS Code client
5. **Add unit tests** for the batch loop and bootstrap confirmation flow
6. **Parallelize L2 embedding generation** using `Promise.all` for better performance
7. **Add L1 tags to orphan branch writer** by passing actual tag names instead of empty array
