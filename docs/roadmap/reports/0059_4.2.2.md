## Round 1 — Architecture & Design Review

### Design Spec Summary (ADR-010 — AI Self-Correction)

ADR-010 Section 9.2 describes the self-correction mechanism:

> "Each batch's LLM prompt includes the L2 module list produced by previous batches, enabling the AI to self-correct module names and boundaries across batches (automatic, no human review needed for cross-batch merges)."

The self-correction mechanism has two components:
1. **Cross-batch name consistency:** Previous batch L2 module names are injected into subsequent batch prompts
2. **Few-shot correction injection:** Human corrections from `correction_examples` table are injected as quality guidance

### Implementation Analysis

**✅ Cross-batch self-correction (`generateL2Nodes()` at generate.ts:187-229):**

The function accepts `previousL2Names?: string[]` parameter and builds a `previousBatchSection` into the LLM prompt:

```typescript
// generate.ts:202-205
const previousBatchSection =
    previousL2Names && previousL2Names.length > 0
        ? `\n\nL2 modules discovered in previous batches (maintain consistency with these names): ${previousL2Names.join(", ")}`
        : "";
```

This section is appended to the system prompt at line 213:
```typescript
content: `${systemPromptOverride}\n\nAvailable L1 tags to map L2 nodes to: ${tagNames}${docSection}${fewShotSection}${previousBatchSection}`,
```

**✅ Batch loop accumulates previousL2Names (generate.ts:734-754):**

```typescript
const BATCH_SIZE = 20;
const previousL2Names: string[] = [];

for (let batchStart = 0; batchStart < commitData.length; batchStart += BATCH_SIZE) {
    const batchCommits = commitData.slice(batchStart, batchStart + BATCH_SIZE);
    const batchResult = await generateL2Nodes(
        batchCommits, allL1Tags, documentContext, model,
        l2SystemPrompt, corrections, previousL2Names
    );
    for (const node of batchResult) {
        if (!previousL2Names.includes(node.name)) {
            previousL2Names.push(node.name);
        }
    }
    l2Input = [...l2Input, ...batchResult];
}
```

The accumulation logic correctly:
- Passes `previousL2Names` to each batch call
- Adds new unique names after each batch (with `includes()` dedup check)
- Accumulates across all batches (not just the immediately preceding one)

**✅ Few-shot correction injection (generate.ts:62-78, 80-91, 696):**

```typescript
// generate.ts:694-696
const l2SystemPrompt = await getSystemPrompt(projectId, "l2_extractor");
const corrections = await getRecentCorrections(projectId, "l2_node");
```

The `getRecentCorrections()` function fetches the 5 most recent `correction_examples` for `entityType = "l2_node"`, ordered by `createdAt desc`. These are formatted by `buildFewShotSection()`:

```typescript
// generate.ts:80-91
function buildFewShotSection(
  corrections: Array<{ original: string; corrected: string }>
): string {
  if (corrections.length === 0) return "";
  const corrections = corrections
    .map(
      (c, i) =>
        `Example ${i + 1}:\n  Original: "${c.original}"\n  Corrected: "${c.corrected}"`
    )
    .join("\n");
  return `\n\nPrevious human corrections (use these as quality guidance):\n${examples}`;
}
```

**✅ Correction creation on review approval (review_tasks.ts:124-138):**

When a review task is resolved with `status: "approved"` and a `correctedValue`, the system creates a `correction_examples` entry:

```typescript
// review_tasks.ts:124-138
if (body.correctedValue && task.status === "approved") {
    if (task.entityType === "l2_node") {
      const [node] = await db.select().from(l2NodesTable).where(eq(l2NodesTable.id, task.entityId));
      if (node && node.description) {
        await db.insert(correctionExamplesTable).values({
          projectId: node.projectId,
          entityType: "l2_node",
          entityId: task.entityId,
          originalContent: node.description,
          correctedContent: body.correctedValue,
        });
      }
    }
```

This creates the feedback loop: corrections → few-shot examples → better L2 extraction.

### Gaps Identified

1. **No explicit self-correction instruction in the default `l2_extractor` prompt:** The default prompt in `templates.ts:16-40` describes the L2/L3 extraction task but does NOT include instructions about maintaining consistency with previously discovered modules or how to handle the "previous batch" section. The self-correction behavior relies entirely on the `previousBatchSection` string being appended to the prompt, which says "maintain consistency with these names" but doesn't provide guidance on WHEN to reuse vs. create new names, or how to handle near-duplicate names (e.g., "Auth" vs "Authentication").

2. **No normalization of L2 names for deduplication:** The `previousL2Names.includes(node.name)` check at generate.ts:749 is case-sensitive and exact-match. If batch 1 produces "Auth Module" and batch 2 produces "auth module" or "Authentication Module", both will be added to the list and both will be passed to subsequent batches, defeating the self-correction purpose. There is no fuzzy matching or name normalization.

3. **Corrections are fetched once, not per-batch:** At generate.ts:696, `getRecentCorrections()` is called once before the batch loop. If a human corrects an L2 node during a long generate run (e.g., via a concurrent review), the correction won't be picked up by subsequent batches in the same run.

4. **No `correctedValue` on `l2_node` review for name corrections:** The review_tasks.ts writeback at line 124-146 only stores `correctedValue` as the `description` field of the L2 node. The `name` field is never updated from corrections. Since the self-correction mechanism primarily concerns module NAMES (not descriptions), the correction_examples will contain description corrections, not name corrections. The few-shot examples won't help the AI correct module names across batches.

5. **No tests for the self-correction mechanism:** There are no unit tests verifying:
   - `previousL2Names` accumulation logic
   - `buildFewShotSection()` formatting
   - `getRecentCorrections()` query behavior
   - End-to-end self-correction across mock batches

## Round 2 — Code Quality & Security Review

### Code Quality

**✅ Clean separation of concerns:** The self-correction logic is well-separated into distinct functions:
- `getRecentCorrections()` — data access
- `buildFewShotSection()` — prompt formatting
- `generateL2Nodes()` — LLM call with prompt assembly
- Batch loop in the route handler — orchestration

**✅ Defensive coding:** The `previousBatchSection` is conditionally built only when `previousL2Names` has entries (line 202-205), avoiding empty noise in the first batch's prompt. The `buildFewShotSection()` returns empty string for empty corrections (line 83).

**✅ The `buildFewShotSection()` function name is misleading:** It builds a "previous human corrections" section, not a "few-shot" section in the traditional ML sense. The name `buildFewShotSection` is technically accurate (it does provide few-shot examples), but the section header says "use these as quality guidance" rather than "follow this correction pattern." This is a minor naming/documentation issue.

**⚠️ Case-sensitive name deduplication (generate.ts:749):**

```typescript
if (!previousL2Names.includes(node.name)) {
    previousL2Names.push(node.name);
}
```

This is case-sensitive exact match. "Auth" and "auth" would both be added. The `existingL2Map` at line 716 uses `node.name.toLowerCase()` for dedup, but `previousL2Names` does not. This inconsistency means the self-correction prompt could contain near-duplicate names, confusing the LLM.

**⚠️ Corrections only capture description, not name (review_tasks.ts:130-136):**

```typescript
if (node && node.description) {
    await db.insert(correctionExamplesTable).values({
        ...
        originalContent: node.description,
        correctedContent: body.correctedValue,
    });
}
```

The correction captures `description` changes. But the self-correction mechanism is primarily about module NAMES. If a human renames "Auth" to "Authentication," that correction is never captured in `correction_examples` because the `name` field is not tracked.

**⚠️ `correctedValue` is a single free-text field:** The `ResolveReviewTaskBody` schema (from `@workspace/api-zod`) provides a single `correctedValue` string. There's no structured way to correct just the name, just the description, or both. This limits the quality of correction examples.

**⚠️ No prompt instruction for self-correction behavior:** The `l2_extractor` default prompt (templates.ts:16-40) says nothing about:
- What to do when a discovered module name matches a previously-seen one
- How to handle near-duplicate module names
- When to merge vs. split modules
- The meaning of the "previous batches" section

The only instruction is the dynamically-appended string: "maintain consistency with these names." This is a minimal instruction that may not be sufficient for reliable self-correction.

### Security

**✅ No security vulnerabilities identified.** The self-correction mechanism operates entirely within the generate pipeline's existing security context. The correction examples are project-scoped (filtered by `projectId`), and the review task resolution requires the task to exist.

**⚠️ Prompt injection risk via correction examples:** If a malicious user enters crafted text as a `correctedValue` in a review task, that text will be injected into the LLM prompt as a "correction example." The `buildFewShotSection()` function does not sanitize or escape the text. However, this is a low-severity risk since the system has no authentication/authorization (a systemic issue, not specific to 4.2.2).

## Round 3 — Integration & Completeness Review

### Integration Points

**✅ Generate pipeline integration:** The self-correction mechanism is correctly integrated into the main `/projects/:id/generate` POST endpoint. It runs after L1 tag generation (which provides `allL1Tags`) and before L3 node processing.

**✅ Review task → correction_examples → generate pipeline feedback loop:** The full cycle exists:
1. AI generates L2 nodes → creates review tasks
2. Human reviews → approves with correction → `correction_examples` entry created
3. Next generate run → `getRecentCorrections()` fetches corrections → `buildFewShotSection()` formats them → injected into L2 extraction prompt

**✅ Orphan branch writer integration:** The `orphan-branch-writer.ts` reads `pathPatterns` and `isBootstrapConfirmed` from the DB. While not directly related to self-correction, the bootstrap confirmation flow (4.2.3) is the gate that transitions from AI-discovery mode (with self-correction) to path-rule mode.

### Missing Integration Pieces

1. **No bootstrap confirmation endpoint (4.2.3):** The self-correction mechanism is part of the bootstrap phase. Without a bootstrap confirmation endpoint, the system can never transition out of bootstrap mode, meaning self-correction will run on every generate run — even when it's no longer needed. This is a design gap in the overall ADR-010 lifecycle, not specifically in the self-correction code.

2. **No reindex mechanism (4.2.1 finding):** After bootstrap confirmation, historical `commit_l2_links` should be flagged with `reindexRequired: true`. The self-correction mechanism doesn't handle reindexing — it only operates on new batches during bootstrap.

3. **Correction examples for L2 names not captured:** As noted in Round 2, the review task writeback only captures description corrections. The self-correction mechanism is primarily about name consistency, but name corrections are never stored.

### Performance Considerations

**✅ Batch-level self-correction is efficient:** Passing `previousL2Names` as a simple string array in the prompt adds negligible token overhead. For a typical project with 5-15 L2 modules, this adds ~50-100 tokens per batch.

**✅ Corrections limit of 5 is reasonable:** `getRecentCorrections()` limits to 5 examples, keeping the few-shot section manageable.

**⚠️ Sequential batch processing:** Batches are processed sequentially (not in parallel), which is correct for self-correction (each batch depends on previous results) but means large repositories will take proportionally longer. A 1000-commit project = 50 batches = 50 sequential LLM calls.

### Test Coverage

**❌ No tests exist for the self-correction mechanism.** The repository has only 4 test files:
- `artifacts/api-server/test/integration/mcp-list-projects.test.ts`
- `artifacts/api-server/src/lib/intent-router.unit.test.ts`
- `artifacts/api-server/src/lib/embedding.unit.test.ts`
- `artifacts/vscode-client/src/tests/phase1.test.ts`

None of these cover:
- `generateL2Nodes()` function behavior
- `previousL2Names` accumulation across batches
- `buildFewShotSection()` formatting
- `getRecentCorrections()` query
- The batch loop in the generate route
- The review task → correction_examples → generate feedback loop

### What Works Well

- The **cross-batch name passing** mechanism (`previousL2Names` array accumulated and injected into prompts) is a sound implementation of ADR-010's self-correction requirement
- The **few-shot correction injection** pipeline (review_tasks → correction_examples → generate) creates a proper human-in-the-loop feedback cycle
- The **prompt assembly** in `generateL2Nodes()` cleanly combines system prompt, L1 tags, document context, few-shot corrections, and previous batch names into a single coherent prompt
- The **batch loop** correctly passes `previousL2Names` to each batch and accumulates results
- The **correction_examples schema** properly stores `originalContent` and `correctedContent` with `entityType` and `entityId` for targeted few-shot retrieval
- The **review task resolution** correctly creates correction examples on approval with `correctedValue`

## Overall Verdict

## ⚠️ WARN

### Rationale

The **AI self-correction across batches** mechanism is **architecturally implemented and functionally present**. The core loop — accumulating `previousL2Names` and injecting them into subsequent batch prompts — works as designed. The few-shot correction injection from `correction_examples` is also properly wired.

However, there are **three medium-severity issues** that reduce the effectiveness of self-correction:

1. **Case-sensitive name deduplication** means the self-correction prompt could contain near-duplicate names (e.g., "Auth" and "auth"), undermining the LLM's ability to maintain consistency
2. **Correction examples capture descriptions, not names**, so the few-shot feedback loop doesn't actually help the AI correct the thing it needs to correct most — module names
3. **No self-correction guidance in the default prompt** means the LLM receives a list of previous names but no instructions on how to use them

The mechanism works at a basic level but needs refinement to be reliable across diverse projects. The lack of test coverage is also a concern for future regression prevention.

### Recommendations (Priority Order)

1. **Normalize `previousL2Names` for deduplication** — use case-insensitive comparison (`.toLowerCase()`) and consider fuzzy matching for near-duplicates (e.g., Levenshtein distance or checking if one name contains the other)
2. **Capture L2 name corrections in `correction_examples`** — when a review task for an `l2_node` is approved with a `correctedValue`, also check if the name changed and store it as a correction example
3. **Add self-correction instructions to the `l2_extractor` default prompt** — include guidance like: "If a module you discover has a name similar to one in the 'previous batches' list, reuse that exact name instead of creating a new one. Only create a new module name if the functionality is genuinely distinct."
4. **Add unit tests** for `generateL2Nodes()`, `buildFewShotSection()`, and the batch accumulation logic
5. **Consider fetching corrections per-batch** (or at least document the limitation that corrections are fetched once at the start)
