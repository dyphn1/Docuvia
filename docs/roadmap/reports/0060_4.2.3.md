# Docuvia Design Verification Report

**Item ID:** 4.2.3  
**Description:** L2 module map confirmation UI  
**Date:** 2026-06-10  

## Design Spec References

- **ADR-010: L2 Bootstrap — AI Discovery to Path Rules** (Accepted)
  - Context: For a new project with no prior knowledge, there is no module map. The early design required a human to pre-define L2 modules before any generate run.
  - Decision: The first generate run uses a progressive batch mode: commits are processed in groups of 20. Each batch's LLM prompt includes the L2 module list produced by previous batches, enabling the AI to self-correct module names and boundaries across batches. After all batches complete, the system presents the discovered L2 module map to the project manager for confirmation.
  - Upon human confirmation:
    - L2 module boundaries are written as glob path patterns to `.docuvia/config.yaml` under `modules:`.
    - All future commits are assigned to L2 modules deterministically by path matching — LLM is no longer used for L2 assignment.
    - Historical `commit_l2_links` rows are flagged with `reindexRequired: true` and retroactively corrected on the next generate run.

## Round 1 — Architecture & Design Review

### Does the design document correctly describe the feature?
Yes, ADR-010 clearly specifies that after the bootstrap phase (AI discovery in batches of 20), the system presents the discovered L2 module map to the project manager for confirmation. Upon confirmation, the system should:
1. Write L2 module boundaries as glob path patterns to `.docuvia/config.yaml`
2. Switch to deterministic path-matching for future commit assignments
3. Flag historical `commit_l2_links` with `reindexRequired: true` for retroactive correction

### Are there gaps between the design spec and the actual implementation?
**CRITICAL GAPS IDENTIFIED:**
1. **Missing API Endpoint**: No `POST /projects/:id/l2-nodes/confirm-bootstrap` or similar endpoint exists to confirm the L2 module map
2. **Missing VS Code UI**: No interface in the VS Code extension to show discovered L2 modules and obtain human confirmation
3. **Missing Persistence**: No code sets `isBootstrapConfirmed = true` on L2 nodes or stores confirmed `pathPatterns`
4. **Missing Config Write**: No mechanism to write confirmed pathPatterns to `.docuvia/config.yaml` under `modules:`
5. **Missing Reindex Trigger**: No code sets `reindexRequired = true` on historical `commit_l2_links` rows
6. **Missing Retroactive Correction**: No logic to regenerate historical commit links using deterministic path matching

### Are there contradictions between different design documents (ADRs, arc42 sections)?
No contradictions found. ADR-010 is consistent with:
- Schema definitions in `l2_nodes.ts` (includes `pathPatterns`, `reindexRequired`, `isBootstrapConfirmed`)
- Implementation plan in `implement_v2-core-architecture.md` (Section 1.4 documents the required schema additions)
- Generate pipeline logic that checks bootstrap status to switch between AI-discovery and path-rule modes

### Is the feature complete per the design spec, or are there missing pieces?
**The feature is INCOMPLETE.** While the consuming infrastructure is ready:
- ✅ Schema includes required columns (`isBootstrapConfirmed`, `pathPatterns`, `reindexRequired`)
- ✅ Generate pipeline correctly checks bootstrap status to switch modes (lines 721-723)
- ✅ Orphan branch writer correctly reads and outputs bootstrap status (lines 30, 42)
- ❌ **MISSING**: The actual human confirmation mechanism (API endpoint + UI) to trigger the confirmed state

## Round 2 — Code Quality & Security Review

### Is the implementation code well-structured and following the project's coding rules (MVC, POP, defensive design)?
The **existing bootstrap-related code** follows good practices:
- Schema properly defined with appropriate defaults and constraints
- Generate.ts uses defensive checks: `existingL2.length > 0 && existingL2.every((n) => n.isBootstrapConfirmed)`
- Orphan branch writer safely handles potential undefined values when formatting YAML
- However, the **core feature is missing** - there is no confirmation endpoint code to review

### Are there security vulnerabilities (input validation, auth, injection, etc.)?
**N/A for missing endpoint**, but if implemented would require:
- **Authorization**: User must have permission to confirm bootstrap for the project (likely project owner/maintainer)
- **Input validation**: Validate the confirmed module map structure and path pattern safety
- **Data validation**: Ensure pathPatterns are valid glob patterns that won't cause denial-of-service
- **CSRF protection**: If web-based endpoint, implement appropriate protection

### Are there code smells, duplication, or anti-patterns?
No code smells in existing related code. The primary issue is a **missing implementation smell**: the system has all infrastructure ready (schema, consumers, writers) but lacks the trigger mechanism to activate the confirmed state.

### Are error handling and edge cases properly addressed?
**Existing code handles edge cases appropriately:**
- Generate.ts checks `existingL2.length > 0` before calling `.every()` to avoid errors on empty arrays
- Orphan branch writer safely handles undefined `isBootstrapConfirmed` values
- **BUT**: Missing endpoint means zero error handling for the confirmation flow itself

## Round 3 — Integration & Completeness Review

### Does the feature integrate correctly with other parts of the system?
**PARTIAL INTEGRATION ACHIEVED:**
- ✅ **Generate Pipeline**: Correctly switches between AI-discovery mode (batches of 20 with self-correction) and path-rule mode based on `isBootstrapConfirmed` status
- ✅ **Orphan Branch Writer**: Correctly reads `isBootstrapConfirmed` and `pathPatterns` to write to `docuvia-knowledge` branch
- ❌ **Sync Pipeline**: Writes config to `llm_configs` table but does NOT handle bootstrap confirmation → `.docuvia/config.yaml` write for pathPatterns
- ❌ **VS Code Extension**: Reads `.docuvia/config.yaml` via KnowledgeStore but never receives bootstrap-confirmed pathPatterns (remains in discovery mode)
- ❌ **Database**: No mechanism to set `reindexRequired = true` on historical `commit_l2_links` rows
- ❌ **Retroactive Correction**: No logic to regenerate historical commit links using deterministic path matching

### Are there missing tests for this feature?
**CRITICALLY MISSING TEST COVERAGE:**
- No unit tests for bootstrap confirmation endpoint
- No integration tests for the full bootstrap confirmation flow (discovery → confirmation → path-rule mode)
- No tests verifying mode switching after confirmation
- No tests verifying historical commit link reindexing functionality

### Are there performance concerns?
**No performance issues with current missing state.** If properly implemented, the confirmation endpoint should have:
- **Low frequency**: Called once per project during initial bootstrap
- **Low volume**: Transfers only the module map with path patterns (small JSON payload)
- **Non-blocking**: Orphan branch write can be fire-and-forget after DB update
- **Efficient DB operations**: Bulk updates to set flags on L2 nodes and commit_l2_links

### Is the feature actually usable end-to-end, or are there gaps?
**The feature is NOT usable end-to-end due to critical gaps:**

1. **❌ No Confirmation Mechanism**: Humans cannot confirm the discovered L2 module map
2. **❌ Permanent Bootstrap Mode**: System remains stuck in AI-discovery mode, continuously re-running LLM for L2 assignment on every generate run
3. **❌ No Path-Rule Transition**: Never switches to deterministic path-matching for commit assignments
4. **❌ Uncorrected History**: Historical `commit_l2_links` never get flagged for retroactive correction
5. **❌ Stale Knowledge Store**: Orphan branch perpetually shows `bootstrap_confirmed: false` and empty `pathPatterns: []`
6. **❌ Confused VS Code UI**: Extension never receives stabilized module boundaries, showing perpetual discovery state

## Findings (issues, gaps, risks, recommendations)

### Issues/Gaps Identified:
1. **Missing Bootstrap Confirmation Endpoint**: No API to:
   - Set `isBootstrapConfirmed = true` on all L2 nodes for a project
   - Store confirmed `pathPatterns` in the database
   - Set `reindexRequired = true` on existing `commit_l2_links` rows
   - Write pathPatterns to `.docuvia/config.yaml` under `modules:`

2. **Missing VS Code Confirmation UI**: No interface to:
   - Fetch discovered L2 nodes during/bootstrap phase
   - Present them for review/confirmation
   - Allow user to modify/approve module boundaries and path patterns
   - Submit confirmed map to the API

3. **Missing Config Write Mechanism**: No code to write confirmed pathPatterns to `.docuvia/config.yaml`

4. **Missing Reindex Trigger**: No logic to set `reindexRequired = true` on historical `commit_l2_links`

5. **Missing Retroactive Correction**: No generate pipeline logic to reprocess historical links using path matching

6. **Missing Tests**: Zero test coverage for bootstrap confirmation functionality

### Risks:
- **Resource Waste**: Projects continuously consume LLM tokens for redundant bootstrap L2 assignment
- **Inconsistent Assignments**: LLM-generated L2 assignments vary vs. deterministic path matching
- **Knowledge Stagnation**: Orphan branch never reflects stabilized, confirmed state
- **Developer Confusion**: Users observe Docuvia "rediscovering" the same modules repeatedly
- **Delayed Value**: System never reaches efficient path-rule mode performance benefits

### Recommendations:
1. **Implement POST /projects/:id/l2-nodes/confirm-bootstrap Endpoint**:
   ```typescript
   // Accepts: { projectId: number, confirmedModules: { id: number, pathPatterns: string[] }[] }
   // Sets isBootstrapConfirmed = true, stores pathPatterns, sets reindexRequired = true on commit_l2_links
   // Writes modules: to .docuvia/config.yaml (via direct write or sync integration)
   ```

2. **Add VS Code Confirmation UI**:
   - Command: `docuvia.confirmBootstrapModules`
   - Fetches project's L2 nodes during/bootstrap phase
   - Shows review dialog with module names and auto-detected path patterns
   - Allows user to edit/approve before submission
   - Calls new API endpoint on confirmation

3. **Implement Retroactive Correction Logic**:
   - In generate pipeline: process commits where `reindexRequired = true`
   - Regenerate `commit_l2_links` using deterministic path matching against confirmed `pathPatterns`
   - Clear `reindexRequired` flag after successful processing

4. **Add Comprehensive Test Suite**:
   - Unit tests: endpoint validation, error cases, bulk updates
   - Integration tests: full flow from discovery → confirmation → path-rule mode
   - E2E tests: config file generation, orphan branch output, mode switching

## Overall Verdict: ❌ FAIL

**Reason**: While the schema, consuming infrastructure (generate pipeline, orphan branch writer), and mode-switching logic are correctly implemented, the **critical human confirmation mechanism is completely missing**. Without an API endpoint and UI to confirm the discovered L2 module map, the system cannot transition from AI-discovery mode to deterministic path-rule mode as specified in ADR-010. The feature remains unusable in its current state, trapping all projects in perpetual bootstrap mode with associated performance and consistency drawbacks.

**Required Action**: Implement the missing bootstrap confirmation endpoint and associated UI to complete the ADR-010 L2 bootstrap → path-rule transition mechanism.
