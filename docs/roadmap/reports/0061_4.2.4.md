## Round 1 — Architecture & Design Review

### Design Spec Summary (ADR-010, lines 242-266)

ADR-010 describes the full L2 bootstrap lifecycle:

1. **Progressive batch mode** processes commits in groups of 20, with AI self-correction across batches
2. **Human confirmation** — after all batches, the discovered L2 module map is presented to the project manager
3. **Path pattern storage** — upon confirmation, L2 module boundaries are written as glob path patterns to `.docuvia/config.yaml` under `modules:`
4. **Deterministic assignment** — all future commits are assigned to L2 modules by path matching (no LLM)
5. **Retroactive correction** — historical `commit_l2_links` rows are flagged with `reindexRequired: true`

The design spec explicitly says path patterns go to **`.docuvia/config.yaml`** under a `modules:` key.

### What the Code Actually Does

**Schema level — ✅ column exists:**
- `l2_nodes.pathPatterns` (jsonb) exists in `l2_nodes.ts:22`
- `l2_nodes.isBootstrapConfirmed` (boolean) exists in `l2_nodes.ts:24`
- `l2_nodes.reindexRequired` (boolean) exists in `l2_nodes.ts:23`

**Orphan branch writer — ✅ writes path_patterns to YAML:**
- `orphan-branch-writer.ts:29-44` — `buildL2ModuleYaml()` reads `node.pathPatterns` and writes `path_patterns:` YAML
- This writes to individual `l2_modules/<slug>.yaml` files in the orphan branch, NOT to `.docuvia/config.yaml`

**Generate pipeline — ⚠️ gating exists but no path pattern storage:**
- `generate.ts:722-731` — correctly checks `allBootstrapConfirmed` to decide between bootstrap mode and path-rule mode
- `generate.ts:727-731` — when all bootstrap confirmed, logs "path-rule mode; L2 assignment deferred to sync pipeline"
- **No code in generate.ts writes path patterns to `l2_nodes.pathPatterns`**

**L2 CRUD routes — ⚠️ no bootstrap confirmation endpoint:**
- `l2_nodes.ts:27-68` — POST `/l2-nodes` creates a new L2 node (no path patterns)
- `l2_nodes.ts:70-104` — PATCH `/l2-nodes/:id` updates an L2 node using `UpdateL2NodeBody` (generated from Drizzle schema, may accept `pathPatterns`)
- **No dedicated `POST /projects/:id/l2-nodes/confirm-bootstrap` endpoint exists**
- **No endpoint writes path patterns to `.docuvia/config.yaml`**

**VS Code client — ❌ no config.yaml with modules:**
- `extension.ts:474-499` — `initProject()` creates `l1_tags.yaml`, `l2_modules.yaml`, and `l3_router.yaml`
- **`.docuvia/config.yaml` is NOT created by `initProject()`**
- `extension.ts:28-41` — global config is loaded from `~/.docuvia/config.yaml` (user home, NOT `.docuvia/` in workspace)
- `types.ts:61-73` — `GlobalConfigSchema` only has `server_url`, `chunking_strategy`, `telemetry` — **no `modules` or `path_patterns` field**
- `parser.ts:76-88` — `parseGlobalConfig()` only parses the 3 GlobalConfigSchema fields

**Manifest.yaml — ⚠️ similar but different:**
- `types.ts:110-113` — `ManifestModuleSchema` has `name` and `path_patterns`
- `KnowledgeStore.ts:131-132` — loads `manifest.yaml` and parses it with `parseManifest()`
- `DocuviaCodeLensProvider.ts:58-67` — uses `manifestModules[].path_patterns` with `minimatch` for offline CodeLens
- This is **functionally similar** to what ADR-010 describes but uses a **different file** (`manifest.yaml` vs `config.yaml`) and serves a **different purpose** (offline CodeLens vs bootstrap-confirmed L2 path rules)

**Sync endpoint — ⚠️ configYaml parsed but only for llm_configs:**
- `sync.ts:68-115` — parses `configYaml` using `parseSimpleYaml()` and upserts `llm_configs` fields
- **Path patterns are NOT extracted from configYaml or written to `l2_nodes.pathPatterns`**

### Gaps Identified

1. **`.docuvia/config.yaml` is never created** — The `initProject()` function creates `l1_tags.yaml`, `l2_modules.yaml`, and `l3_router.yaml` but NOT `config.yaml`. The design spec says path patterns should be stored in `.docuvia/config.yaml` under `modules:`.

2. **No bootstrap confirmation flow** — There is no API endpoint or VS Code command that triggers "write path patterns to config.yaml". The `isBootstrapConfirmed` column exists but no code ever sets it to `true`.

3. **`GlobalConfigSchema` doesn't include modules/path_patterns** — The `~/.docuvia/config.yaml` global config schema only has `server_url`, `chunking_strategy`, and `telemetry`. Even if `.docuvia/config.yaml` existed, the parser wouldn't handle a `modules:` section.

4. **Orphan branch writer writes to `l2_modules/<slug>.yaml`, not `config.yaml`** — The `buildL2ModuleYaml()` function writes individual L2 module files with `path_patterns:` to the orphan branch. This is a different storage location than what ADR-010 specifies.

5. **No path-rule assignment in sync pipeline** — The generate pipeline defers L2 assignment to the sync pipeline when bootstrap is confirmed, but the sync pipeline has no logic to match commit diff paths against `l2_nodes.pathPatterns`.

## Round 2 — Code Quality & Security Review

### Code Quality

**✅ Schema design is sound:** The `l2_nodes` table has all required columns (`pathPatterns`, `reindexRequired`, `isBootstrapConfirmed`) with appropriate types.

**✅ Orphan branch writer YAML generation is clean:** `buildL2ModuleYaml()` (orphan-branch-writer.ts:29-44) properly handles empty patterns and formats YAML correctly.

**✅ Manifest module path_patterns matching works correctly:** `DocuviaCodeLensProvider.ts:64-66` uses `minimatch(relPath, pattern, { matchBase: true })` for proper glob matching.

**⚠️ Inconsistent path matching approaches:**
- `DocuviaCodeLensProvider.ts:65` uses `minimatch` (correct glob matching)
- `generate.ts:428` (Sieve model) uses `sourceFile.startsWith(p)` (prefix matching only)
- `KnowledgeStore.ts:248` maps API L2 nodes with `source_paths: []` (always empty)

**⚠️ `parseSimpleYaml` is fragile:** `sync.ts:29-41` uses a regex-based YAML parser (`/^(\w+):\s*(.+?)\s*$/`) that only handles flat key-value pairs. It would fail for nested structures like `modules:` with a list of objects containing `path_patterns`.

**⚠️ `initProject` doesn't create config.yaml:** The `extension.ts:474-499` function creates 3 YAML files but not `config.yaml`. This is a missing piece of the initialization flow.

### Security

**✅ No security vulnerabilities identified in the path pattern storage area.** Path patterns are used for file matching, not execution. The `minimatch` library is a safe pattern matching utility.

**⚠️ No authorization on L2 node PATCH:** The `PATCH /l2-nodes/:id` endpoint (`l2_nodes.ts:70-104`) doesn't verify the caller has access to the project. This is a systemic issue, not specific to 4.2.4.

## Round 3 — Integration & Completeness Review

### Integration Points

**✅ Orphan branch writer integration exists:** The `orphan-branch-writer.ts` already reads `pathPatterns` from the DB and writes it to YAML. The integration path from DB → orphan branch works.

**✅ Manifest module integration works:** `KnowledgeStore.ts:131-132` loads `manifest.yaml` and stores `manifestModules`. `DocuviaCodeLensProvider.ts:130-146` uses them for offline CodeLens fallback.

**❌ No integration between bootstrap confirmation and config.yaml:**
- No endpoint sets `isBootstrapConfirmed = true`
- No endpoint writes path patterns to `.docuvia/config.yaml`
- No endpoint reads path patterns from `.docuvia/config.yaml` for L2 assignment

**❌ No integration between sync pipeline and path-rule matching:**
- `sync.ts` receives `configYaml` but only uses it for `llm_configs` upsert
- No code matches commit diff paths against `l2_nodes.pathPatterns`
- No code creates `commit_l2_links` entries based on path matching

### Missing Pieces (End-to-End Flow)

The ADR-010 design spec describes this flow:
```
AI discovers L2 modules → Human confirms → Path patterns written to .docuvia/config.yaml
                                              → Future commits matched by path
```

What's actually implemented:
```
AI discovers L2 modules → [HUMAN CONFIRMATION MISSING] → [PATH PATTERN STORAGE MISSING]
                                                                → [PATH-RULE ASSIGNMENT MISSING]
```

The system can **discover** L2 modules via AI (batch mode in generate.ts works), but the confirmation → storage → activation pipeline is incomplete.

### Test Coverage

**❌ No tests found for path pattern storage.** There are no unit or integration tests verifying:
- Path patterns are written to `l2_nodes.pathPatterns` after bootstrap confirmation
- Path patterns are written to `.docuvia/config.yaml`
- Path patterns are read from `.docuvia/config.yaml` and used for L2 assignment
- The `parseGlobalConfig` function handles a `modules:` section (it doesn't)

## Overall Verdict

## ❌ FAIL

### Rationale

ADR-010 explicitly states: *"L2 module boundaries are written as glob path patterns to `.docuvia/config.yaml` under `modules:`."*

**`.docuvia/config.yaml` does not exist anywhere in the codebase.** It is not created by `initProject()`, not written by any API endpoint, not parsed by any reader, and not referenced by any path-pattern matching logic. The `GlobalConfigSchema` doesn't include a `modules` field.

While the **schema column** (`l2_nodes.pathPatterns`) and the **orphan branch writer scaffolding** exist, the actual storage of path patterns to `.docuvia/config.yaml` is completely unimplemented. The system has no way to:

1. **Write** path patterns to `.docuvia/config.yaml` (no endpoint, no init code)
2. **Read** path patterns from `.docuvia/config.yaml` (no parser support)
3. **Activate** path-rule mode (no bootstrap confirmation flow)

The manifest.yaml system provides a proof-of-concept for path pattern storage and matching, but it serves a different purpose (offline CodeLens) and uses a different file. The ADR-010 requirement for `.docuvia/config.yaml` with `modules:` containing path patterns is not met.

### Recommendations (Priority Order)

1. **Add `.docuvia/config.yaml` creation to `initProject()`** — Create a skeleton `config.yaml` with an empty `modules:` list when initializing a project
2. **Extend `GlobalConfigSchema`** (or create a new `ProjectConfigSchema`) to include `modules: [{ name, path_patterns: [] }]` 
3. **Add a `POST /projects/:id/l2-nodes/confirm-bootstrap`** endpoint that accepts the confirmed module map with path patterns, sets `isBootstrapConfirmed = true`, stores `pathPatterns` on each L2 node, and writes the config to `.docuvia/config.yaml`
4. **Add a `parseProjectConfig()` function** that can parse the `modules:` section from `.docuvia/config.yaml`
5. **Implement path-rule matching in the sync pipeline** — when bootstrap is confirmed, match commit diff paths against `l2_nodes.pathPatterns` using `minimatch` and create `commit_l2_links` entries
6. **Fix `parseSimpleYaml` → use proper YAML parser** for the sync endpoint's configYaml parsing (use the `yaml` package like the VS Code client does)
7. **Add tests** for the config.yaml path pattern storage and matching flow
