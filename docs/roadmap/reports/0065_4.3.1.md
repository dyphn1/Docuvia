## Round 1 — Architecture & Design Review

### Design Compliance

ADR-011 Phase 1 specifies that the existing `review_tasks` mechanism serves as the quality gate. The design requires:

1. **AI-generated nodes enter review** — ✅ The generate pipeline (`generate.ts`) creates review tasks for:
   - Every new L1 tag (task type: `anchor`) — line 669
   - Every new L2 node with `needsReview: true` (task type: `validate`) — line 968
   - Every new L3 node with confidence < 0.8 (task type: `validate`) — line 921
   - L3 nodes reaching condensation threshold (task type: `validate`, if configured) — line 881
   - Noise-detected L1 tags (task types: `anchor`, `merge`) — lines 327, 361

2. **Human reviews and resolves** — ✅ The `PATCH /review-tasks/:id` endpoint supports `approved`, `rejected`, and `deferred` statuses.

3. **Correction examples feed back** — ✅ On approval with a corrected value, the resolver writes to `correction_examples` table (lines 131, 158) and updates the actual node content (lines 139, 167, 174).

4. **Activity logging** — ✅ Every resolution creates an activity log entry (line 191).

5. **Web UI for review** — ✅ The kg-engine Review page (`review.tsx`) provides a full-featured UI with task filtering, content viewing, inline editing, and approve/reject/defer actions.

6. **Dashboard integration** — ✅ The dashboard endpoint exposes `pendingReviews` count (line 54 of `dashboard.ts`).

### Gaps / Observations

- The ADR text says "Passing Phase 1 sets status to `pending`" (line 280 of the ADR). This is slightly misleading wording — what it means is that L3 nodes have `validityStatus: "pending"` set at creation time (line 905 of `generate.ts`), which is correct. The review task itself starts as `pending` and transitions to `approved` on human approval. The two concepts (review task status vs node validity status) are properly separated.

- The `review_tasks` table does not have a `projectId` column. Tasks are linked to entities (l1_tag, l2_node, l3_node) but not directly to projects. Project name is resolved via the `enrichTask` helper at query time. This works but means there's no direct FK from review_tasks to projects.

## Round 2 — Code Quality & Security Review

### Strengths

- **Zod validation** on both params and body for the resolve endpoint (lines 110–111 of `review_tasks.ts`).
- **Defensive null checks** throughout — e.g., `tag?.name ?? null`, `node?.content ?? null`.
- **Correction writeback** properly handles all three entity types (l1_tag, l2_node, l3_node) with appropriate field updates.
- **Idempotency guards** in the generate pipeline — checks for existing pending review tasks before creating duplicates (e.g., lines 315–326, 349–360, 958–964).
- **Activity audit trail** — every resolution is logged with a descriptive message including the task ID, status, and whether a correction was applied.
- **UI/UX quality** — the review page has expand/collapse, inline editing, status filtering, stats sidebar, and clear action buttons.

### Issues Found

1. **Minor: `l3_nodes` lacks `needsReview` column** — The `l2_nodes` table has a `needsReview` boolean column that is set to `true` on AI generation and cleared to `false` on review resolution. The `l3_nodes` table has no such column. Instead, L3 review tracking relies entirely on the existence of review tasks. This is an asymmetry but not a functional bug — it works because the generate pipeline creates review tasks for low-confidence L3 nodes, and the post-generation L2 review task creation loop (lines 954–977) only covers L2 nodes. L3 nodes with confidence ≥ 0.8 never get review tasks created, which is intentional (they're considered high-confidence auto-approved).

2. **Minor: `l3_node` `needsReview` never cleared** — Since `l3_nodes` doesn't have a `needsReview` column, there's no way to mark an L3 node as "reviewed" at the node level. The review task status is the only indicator. This is acceptable given the current design but could be confusing if a future feature wants to filter "unreviewed L3 nodes" directly.

3. **Informational: No `projectId` on `review_tasks`** — Filtering review tasks by project requires joining through the entity tables. This is handled by the `enrichTask` helper but could become a performance concern at scale.

## Round 3 — Integration & Completeness Review

### End-to-End Flow

The Phase 1 Local Review quality gate is fully implemented end-to-end:

1. **Generation** → `POST /projects/:id/generate` creates review tasks for AI-generated entities
2. **Listing** → `GET /review-tasks` returns enriched tasks with entity names, project names, and content
3. **Stats** → `GET /review-tasks/stats` provides counts by status
4. **Resolution** → `PATCH /review-tasks/:id` resolves tasks with writeback and correction capture
5. **UI** → The kg-engine Review page provides a complete human interface
6. **Feedback loop** → Correction examples are stored and injected as few-shot prompts in subsequent generate runs (via `getRecentCorrections` in `generate.ts`)

### Integration Points

- **Dashboard**: Shows pending review count ✅
- **Generate pipeline**: Creates review tasks at multiple stages ✅
- **Correction examples**: Written on approval, read on next generate ✅
- **Activity log**: Records all review resolutions ✅
- **Notifications**: The generate pipeline sends notifications for new L3 nodes (line 988) but does NOT send notifications for new review tasks. This is a minor gap — reviewers must poll or refresh the UI to see new tasks.

### Test Coverage

No dedicated test files were found for the review_tasks route. The generate route also lacks tests for review task creation logic. This is a testing gap but not a design/implementation defect.

## Overall Verdict

**✅ PASS** — The Phase 1 Local Review quality gate is fully implemented per ADR-011. The `review_tasks` mechanism covers all AI-generated entity types (L1, L2, L3), supports the full review lifecycle (list → inspect → approve/reject/defer → correct), writes back corrections to nodes, captures correction examples for the feedback loop, and provides a complete Web UI. The minor issues identified (L3 `needsReview` asymmetry, no project FK, no review-task notifications) are cosmetic or scalability considerations, not functional defects.
