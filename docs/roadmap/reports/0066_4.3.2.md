## Design Spec Summary

ADR-011 defines a two-phase knowledge validity system:

- **Phase 1 — Local Review (Quality Gate):** Developer reviews AI-generated content. Passing sets status to `pending`. (Implemented via `review_tasks` — item 4.3.1.)
- **Phase 2 — Merge Gate (Validity Gate):** When `docuvia sync` fires on `git push`, the server checks whether source commits have been merged into the main/default branch:
  - **Merged:** Commits and associated L3 nodes → `valid`
  - **Abandoned (branch deleted without merge):** Commits and associated L3 nodes → `orphaned` (archived, not shown in standard queries)

The ADR explicitly states: *"Server must track branch merge status — requires either GitHub webhook integration or periodic polling."*

## Round 1 — Architecture & Design Review

### What ADR-011 Requires

The Merge Gate (Phase 2) must handle **two transitions**:

1. **→ `valid`:** When commits are confirmed merged into the main/default branch, their associated L3 nodes should be promoted to `valid`.
2. **→ `orphaned`:** When a branch is deleted/closed without merging, the L3 nodes from commits on that branch should be set to `orphaned` (archived, excluded from default queries).

The ADR specifies two mechanisms for tracking merge status:
- GitHub webhook integration (preferred)
- Periodic polling (fallback)

### What Is Actually Implemented

#### Partial Implementation: Direct Push to Main (`sync.ts:130-204`)

The sync route at `POST /sync` handles the `→ valid` transition for **direct pushes to main/master/trunk**:

```typescript
// sync.ts:130-204
if (isMainBranch(pushedBranch)) {
  // Promote commits to valid
  await db.update(commitsTable).set({ validityStatus: "valid" })...;
  // Cascade: find L3 nodes linked via commit_l2_links or commitHash
  // Promote matching L3 nodes to valid
  await db.update(l3NodesTable).set({ validityStatus: "valid" })...;
}
```

This is a **correct but incomplete** implementation. It only works when:
- Someone pushes directly to main/master/trunk
- The `POST /sync` endpoint is actually called (requires the `docuvia sync` CLI, which does not exist — item 3.4.3)

#### Missing: PR Merge via GitHub Webhook (`github_webhooks.ts:253-316`)

The GitHub webhook handler detects PR merges:

```typescript
// github_webhooks.ts:253
} else if (action === "closed" && isMerged) {
  // Updates PR record state to "merged"
  await db.update(pullRequestsTable).set({ state: "merged", ... })...;
  // Generates AI summary, posts comment to GitHub
  // Notifies subscribers
}
```

**Critical gap:** When a PR is merged, the webhook updates the `pull_requests` record but does **NOT**:
- Set `commits.validityStatus = 'valid'` for the PR's commits
- Set `l3_nodes.validityStatus = 'valid'` for L3 nodes associated with those commits

This means L3 nodes generated from PR commits will remain `pending` forever, even after the PR is merged into main.

#### Missing: Orphaned Transition (No Implementation)

There is **no code anywhere** in the codebase that sets `validityStatus` to `"orphaned"`. Specifically:

- The GitHub webhook's `action === "closed"` handler (without merge) at `github_webhooks.ts:317-328` only updates the PR record:
  ```typescript
  } else if (action === "closed") {
    // Closed but not merged
    await db.update(pullRequestsTable).set({ state: "closed", ... })...;
  }
  ```
  It does **not** cascade to L3 nodes or commits.

- There is no branch deletion webhook handler.
- There is no polling mechanism to detect abandoned branches (item 4.3.8 covers this separately).

#### Missing: `docuvia sync` CLI

The sync endpoint exists but is unreachable from git hooks because the `docuvia sync` CLI does not exist (item 3.4.3 is ❌ FAIL). The git hook template described in the implementation plan (`docs/ai_plans/implement_v2-core-architecture.md:173-180`) has not been implemented.

## Round 2 — Code Quality & Security Review

### Code Quality Issues

1. **Hardcoded branch names in `sync.ts:43`:**
   ```typescript
   const DEFAULT_BRANCHES = new Set(["main", "master", "trunk"]);
   ```
   This is not configurable. Some projects use `develop`, `release`, or custom default branch names. This should be configurable per-project (e.g., in `llm_configs` or `projects` table).

2. **No `orphaned` status in codebase:**
   The validity status enum is defined as `pending | valid | orphaned` in ADR-011 and the glossary, but the string `"orphaned"` never appears in any source code. The codebase only uses `"pending"` and `"valid"`.

3. **Inconsistent merge detection:**
   - Direct push to main → `sync.ts` promotes to `valid` ✅
   - PR merge via GitHub → `github_webhooks.ts` does NOT promote to `valid` ❌
   
   This creates a situation where the same commit can have different validity status depending on how it was merged (direct push vs. PR).

4. **No DB-level enum constraint for `validityStatus`:**
   Both `commits.ts:23` and `l3_nodes.ts:36` use `text("validity_status")` instead of `pgEnum`. This means invalid values can be stored at the DB level. (Noted in previous report 0057_4.1.5.)

### Security Review

No specific security vulnerabilities in the merge gate logic itself. The GitHub webhook already has HMAC-SHA256 signature validation (`github_webhooks.ts:22-31`). The sync endpoint does not have authentication — it relies on the `docuvia sync` CLI being the only caller, but since the CLI doesn't exist, this is currently a non-issue.

## Round 3 — Integration & Completeness Review

### Integration Analysis

The merge gate is supposed to integrate with:

1. **Generate pipeline** → Creates L3 nodes with `validityStatus: "pending"` ✅
2. **Sync endpoint** → Promotes to `valid` on main branch push ⚠️ (works but unreachable)
3. **GitHub webhook** → Should promote to `valid` on PR merge ❌ (not implemented)
4. **MCP query filter** → Filters by `validityStatus` ✅ (implemented in `intent-router.ts`)

The MCP query filter (item 4.3.4) correctly defaults to `status = valid` only. This means that L3 nodes stuck in `pending` status (due to incomplete merge gate) are **invisible** to MCP queries by default. This creates a silent failure mode: users query the knowledge graph and get no results for PR-merged commits, with no indication that nodes exist but are pending.

### End-to-End Flow Analysis

**Scenario A: Direct push to main**
1. Developer pushes to `main`
2. `docuvia sync` CLI should call `POST /sync` → **FAILS** (CLI doesn't exist)
3. Even if called, sync route would promote to `valid` ✅
4. **Result:** ❌ Broken end-to-end (missing CLI)

**Scenario B: PR merge via GitHub**
1. Developer merges PR on GitHub
2. GitHub webhook fires → `github_webhooks.ts` handles `action === "closed" && isMerged`
3. PR record updated to `merged` ✅
4. AI summary generated and posted ✅
5. **But:** Commits and L3 nodes NOT promoted to `valid` ❌
6. **Result:** ❌ Broken end-to-end (missing cascade)

**Scenario C: Branch abandoned (closed without merge)**
1. Developer closes PR without merging / deletes branch
2. GitHub webhook fires → `github_webhooks.ts` handles `action === "closed"` (not merged)
3. PR record updated to `closed` ✅
4. **But:** Commits and L3 nodes NOT set to `orphaned` ❌
5. **Result:** ❌ Broken end-to-end (missing orphaned transition)

### Missing Tests

There are no tests for:
- Sync route's validity promotion logic
- GitHub webhook's merge handling cascade
- Orphaned status transitions
- End-to-end flow from git push → sync → validity promotion

## Findings

### Critical Issues

1. **GitHub webhook does not cascade PR merge to L3 node validity** — When a PR is merged, the webhook handler updates the `pull_requests` record but does not promote associated `commits.validityStatus` or `l3_nodes.validityStatus` to `"valid"`. This is the primary gap in the merge gate implementation.

2. **No `orphaned` transition exists** — There is no code that sets `validityStatus` to `"orphaned"` for commits/L3 nodes on abandoned branches. The GitHub webhook's close-without-merge handler only updates the PR record.

3. **`docuvia sync` CLI does not exist** — The sync endpoint (`POST /sync`) is the mechanism for promoting validity on direct pushes, but the CLI that should call it is not implemented (item 3.4.3 ❌ FAIL). This makes the sync route unreachable from git hooks.

### Warnings

4. **Hardcoded default branch names** — `sync.ts:43` hardcodes `["main", "master", "trunk"]`. Projects with non-standard default branches (e.g., `develop`, `release`) will not trigger validity promotion.

5. **Inconsistent merge detection** — Direct pushes to main are handled by `sync.ts`, PR merges are handled by `github_webhooks.ts`. These two paths have different behavior: one promotes validity, the other doesn't.

6. **Silent failure mode** — The MCP query filter defaults to `status = valid` only. L3 nodes stuck in `pending` due to incomplete merge gate are silently invisible to users.

### Recommendations

1. **Add validity cascade to GitHub webhook PR merge handler** — In `github_webhooks.ts:253-316`, after updating the PR record to `merged`, add logic to:
   - Fetch the PR's commits (via `fetchPrCommits`)
   - Set `commits.validityStatus = 'valid'` for those commits
   - Find associated L3 nodes (via `sourceCommits` or `commitHash`) and set `l3_nodes.validityStatus = 'valid'`

2. **Add orphaned transition to GitHub webhook close handler** — In `github_webhooks.ts:317-328`, after updating the PR record to `closed`, add logic to:
   - Fetch the PR's commits
   - Set `commits.validityStatus = 'orphaned'` for those commits
   - Find associated L3 nodes and set `l3_nodes.validityStatus = 'orphaned'`

3. **Implement `docuvia sync` CLI** (blocked by item 3.4.3) — The CLI should read `.docuvia/config.yaml` and `.docuvia/.snapshot-ref`, then call `POST /sync` with the pushed branch and commit list.

4. **Make default branch configurable** — Add a `defaultBranch` column to the `projects` table or `llm_configs` table, and use it in `sync.ts:isMainBranch()` instead of the hardcoded set.

5. **Add tests** — Write integration tests for:
   - Sync route validity promotion (direct push to main)
   - GitHub webhook PR merge cascade to L3 nodes
   - GitHub webhook PR close without merge → orphaned transition

---

## Overall Verdict

## ❌ FAIL

The Phase 2 Merge Gate is **not functionally implemented**. While the database schema supports validity status and the sync route has partial promotion logic for direct main branch pushes, the critical path — PR merge via GitHub webhook — does not cascade to promote L3 nodes to `valid`. The `orphaned` transition for abandoned branches is completely absent. The `docuvia sync` CLI that should trigger the sync endpoint does not exist. The merge gate cannot operate end-to-end in any scenario.
