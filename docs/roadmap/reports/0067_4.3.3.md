## Design Spec Summary

ADR-011 defines a two-phase knowledge validity system:

- **Phase 1 (Local Review / Quality Gate):** AI-generated L3 nodes enter the review queue. Human review confirms accuracy. Passing Phase 1 sets status to `pending`.
- **Phase 2 (Merge Gate / Validity Gate):** When `docuvia sync` fires on `git push`, the server checks if source commits have been merged into the main branch. Merged commits → L3 nodes become `valid`. Abandoned branches → L3 nodes become `orphaned`.
- **Validity status enum:** `pending | valid | orphaned`
- **MCP query default:** Only `status = valid` is returned. `include_pending=true` parameter enables pending knowledge.

---

## Round 1 — Architecture & Design Review

### What the design requires

1. `l3_nodes` table must have a `validityStatus` column with enum values `pending | valid | orphaned`
2. `commits` table must have a `validityStatus` column
3. `commits` table must have a `branchName` column
4. Default value for `validityStatus` on both tables should be `"pending"`
5. The generate pipeline must create L3 nodes with `validityStatus: "pending"`
6. The sync endpoint must promote L3 nodes to `valid` when commits are pushed to the main branch
7. The sync endpoint must handle orphaned status for abandoned branches
8. MCP queries must filter by `valid` by default, with `include_pending=true` to include pending

### What the implementation provides

**Schema level — ✅ Fully implemented:**
- `l3_nodes.ts` line 36: `validityStatus: text("validity_status").notNull().default("pending")` — correct column, correct default
- `commits.ts` line 23: `validityStatus: text("validity_status").notNull().default("pending")` — correct column, correct default
- `commits.ts` line 22: `branchName: text("branch_name")` — correct column

**Generate pipeline — ✅ Correct:**
- `generate.ts` line 905: New L3 nodes are inserted with `validityStatus: "pending"` — matches ADR-011 Phase 1 behavior

**Sync endpoint — ✅ Partially implemented:**
- `sync.ts` lines 130-203: When `pushedBranch` is a main branch (`main`, `master`, `trunk`):
  - Commits are promoted to `validityStatus: "valid"` (line 133)
  - L3 nodes linked via `commit_l2_links` with matching `sourceCommits` are promoted to `valid` (lines 164-185)
  - L3 nodes linked via legacy `commitHash` field are promoted to `valid` (lines 189-197)
- This correctly implements Phase 2 (Merge Gate) for the main branch case

**Intent router / MCP query filtering — ✅ Correct:**
- `intent-router.ts` lines 193-195: `vectorSearchHandler` builds `l3ValidityCondition` that filters by `valid` only by default, or `valid | pending` when `includePending=true`
- `intent-router.ts` lines 493-495: `directLookupHandler` applies the same validity filter
- `intent-router.ts` lines 604-614: `hybridSearch` passes `includePending` through to `vectorSearchHandler`
- `mcp.ts` line 50: `GET /mcp/search_knowledge` reads `include_pending` query param
- `mcp.ts` line 195: `POST /mcp/query` reads `include_pending` query param

### Gaps identified

1. **No `orphaned` status transition logic exists.** The sync endpoint (`sync.ts`) only handles promotion to `valid` on main branch pushes. There is no mechanism to detect abandoned/deleted branches and set L3 nodes to `orphaned`. The `orphaned` value is defined in the enum but never written by any code path. This is a partial implementation of ADR-011 Phase 2 — the "orphaned" branch of the logic is missing.

2. **No native PostgreSQL `pgEnum` for validity status.** The schema uses `text("validity_status")` rather than a proper `pgEnum`. This means the database does not enforce the enum constraint at the DB level — any string value could be inserted. Compare with `review_tasks.ts` which properly uses `pgEnum` for `review_status` and `review_task_type`. This is a data integrity risk.

3. **`include_pending` not in OpenAPI spec.** The `GET /mcp/search_knowledge` endpoint in `openapi.yaml` (lines 929-955) does not define an `include_pending` query parameter. The `POST /mcp/query` endpoint (lines 1022-1051) also lacks it. The `McpQueryInput` schema only has `q`, `project_id`, and `limit`. This means the parameter is not part of the API contract and won't be available to generated clients.

4. **`GET /mcp/get_dependencies` and `GET /mcp/impact_analysis` do not filter by validity status.** These endpoints query L2 nodes without any validity filter (which is correct for L2 since they don't have validity status), but `GET /mcp/get_decision_record` (lines 154-176) queries L3 nodes by `commitHash` without filtering by `validityStatus`. This means orphaned or pending L3 nodes are returned by this endpoint, which contradicts the ADR-011 principle that default queries should only return `valid` nodes.

## Round 2 — Code Quality & Security Review

### Code Quality

1. **Schema design inconsistency.** The `validityStatus` column is defined as `text` without a `pgEnum`, while other status columns in the project (`review_tasks.status`, `review_tasks.taskType`, `review_tasks.entityType`) all use `pgEnum`. This is inconsistent and reduces type safety at the database level.

2. **Sync endpoint orphaned detection is missing.** The `sync.ts` endpoint handles the main branch promotion well, but the orphaned detection would require either:
   - GitHub webhook integration for branch delete events (item 4.3.8, marked ❌ Todo)
   - Periodic polling of branch status
   Without this, the `orphaned` status is unreachable dead code.

3. **`include_pending` validation bypasses Zod.** In `mcp.ts`, `include_pending` is read from `req.query` directly (line 50, 195) rather than being part of the Zod-validated schema. This is a minor inconsistency — the parameter is not validated or type-checked. Other query parameters (`query`, `project_id`, `limit`) are properly validated.

4. **No input validation on `validityStatus` values.** Since the column is `text` rather than `pgEnum`, there's no database-level constraint preventing invalid values like `"approved"` or `"rejected"` from being inserted. Application-level code always sets the correct values, but this is fragile.

### Security

No security vulnerabilities specific to this feature. The `validityStatus` column is not user-writable via any API endpoint — it's only set internally by the generate pipeline and sync endpoint.

## Round 3 — Integration & Completeness Review

### Integration Points

1. **Generate → Sync → Query pipeline:** The flow from generate (creates L3 with `pending`) → sync (promotes to `valid` on main branch) → intent-router (filters by `valid` by default) is correctly wired end-to-end for the happy path.

2. **Orphan branch writer:** `orphan-branch-writer.ts` (line 52) reads `validityStatus` from L3 nodes and includes it in the YAML frontmatter of generated markdown files. This is correct — the orphan branch reflects the current validity status.

3. **Review tasks integration:** The review task system (Phase 1) is independent of the validity status. Review tasks use their own `status` column (`pending | approved | rejected | deferred`). The two systems operate correctly in parallel — review approval doesn't change `validityStatus`, and merge promotion doesn't affect review task status.

### Missing Pieces

1. **Orphaned branch detection (blocked by 4.3.8):** The `orphaned` status cannot be set without branch merge status tracking (item 4.3.8, marked ❌ Todo). This is a known dependency — ADR-011 explicitly states "Server must track branch merge status — requires either GitHub webhook integration or periodic polling."

2. **No tests for validity status transitions.** There are no unit or integration tests verifying:
   - L3 nodes are created with `validityStatus: "pending"` after generate
   - Sync promotes L3 nodes to `valid` on main branch push
   - MCP queries filter by `valid` by default
   - `include_pending=true` includes pending nodes

3. **OpenAPI spec out of sync.** The `include_pending` parameter is missing from both MCP endpoints in the OpenAPI spec, which means generated clients (via Orval) won't have this parameter available.

## Findings

### Issues

| # | Severity | Finding |
|---|----------|---------|
| 1 | **Medium** | `orphaned` status is defined but never set by any code path. No branch-delete detection exists (blocked by item 4.3.8). |
| 2 | **Medium** | `validityStatus` uses `text` column instead of `pgEnum`, unlike other status columns in the project. No DB-level enum constraint. |
| 3 | **Medium** | `GET /mcp/get_decision_record` does not filter L3 nodes by `validityStatus`, returning orphaned/pending nodes contrary to ADR-011. |
| 4 | **Low** | `include_pending` parameter is missing from OpenAPI spec for both `GET /mcp/search_knowledge` and `POST /mcp/query`. |
| 5 | **Low** | `include_pending` is read from raw `req.query` bypassing Zod validation. |
| 6 | **Low** | No tests for validity status transitions or MCP filtering behavior. |

### Recommendations

1. **Create a `pgEnum` for validity status.** Add `validityStatusEnum = pgEnum("validity_status", ["pending", "valid", "orphaned"])` and use it in both `l3_nodes.ts` and `commits.ts` schemas. This ensures DB-level constraint and consistency with other enums in the project.

2. **Add `include_pending` to OpenAPI spec.** Add the parameter to both `GET /mcp/search_knowledge` and `POST /mcp/query` endpoints, then regenerate types with Orval.

3. **Filter by validity in `GET /mcp/get_decision_record`.** Add a `validityStatus` filter to the L3 query in this endpoint, defaulting to `valid` only.

4. **Plan orphaned detection.** Even though full branch-delete detection is blocked by 4.3.8, consider a simple heuristic: during sync, check if the branch still exists via `git branch -r` and mark L3 nodes as `orphaned` if the branch is gone.

5. **Add integration tests.** Test the full flow: generate → sync (main branch) → query with/without `include_pending`.

---

## Verdict

**⚠️ WARN**

The core schema and the happy-path flow (generate → sync main branch → query with default filter) are correctly implemented. L3 nodes are created with `pending`, promoted to `valid` on main branch push, and filtered correctly in MCP queries. However, the `orphaned` status is unreachable (no branch-delete detection), the column lacks a proper `pgEnum` constraint, `get_decision_record` doesn't filter by validity, and the OpenAPI spec is missing the `include_pending` parameter. These gaps warrant a WARN verdict.
