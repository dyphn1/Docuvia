## Design Spec Summary

ADR-011 (Two-Phase Knowledge Validity) states:

> **MCP query behavior:** Default filter is `status = valid` only. Query parameter `include_pending=true` enables pending knowledge (e.g., for querying a specific feature branch's design decisions).

This requirement has two parts:
1. **Default filter:** All MCP knowledge queries must only return L3 nodes with `validityStatus = "valid"` by default.
2. **`include_pending` parameter:** When `include_pending=true` is provided, queries should also return L3 nodes with `validityStatus = "pending"`.

---

## Round 1 — Architecture & Design Review

### What the design requires

1. All MCP query endpoints that return L3 nodes must filter by `validityStatus = "valid"` by default.
2. An `include_pending=true` parameter must expand the filter to include `"pending"` nodes.
3. This applies to the MCP query endpoints: `GET /mcp/search_knowledge`, `POST /mcp/query`, and any other MCP endpoint returning L3 data.

### What the implementation provides

**`GET /mcp/search_knowledge` (mcp.ts lines 46–61):**
- Line 50: `const includePending = req.query.include_pending === "true";`
- Line 55: `const result = await routeQuery(query, projectId, limit, includePending);`
- ✅ Correctly reads the `include_pending` query parameter and passes it to the intent router.

**`POST /mcp/query` (mcp.ts lines 188–204):**
- Line 195: `const includePending = req.query.include_pending === "true";`
- Line 198: `const result = await routeQuery(q, project_id, limit, includePending);`
- ✅ Correctly reads the `include_pending` query parameter and passes it to the intent router.

**`vectorSearchHandler` (intent-router.ts lines 184–381):**
- Lines 193–195: Builds `l3ValidityCondition` — `valid` only by default, or `valid | pending` when `includePending=true`.
- Lines 241–260: Applies `l3ValidityCondition` to L3 semantic search queries.
- Lines 337–360: Applies `l3ValidityCondition` to L3 fallback LIKE queries.
- ✅ Correctly filters L3 nodes by validity status in both embedding-based and fallback search.

**`directLookupHandler` (intent-router.ts lines 485–598):**
- Lines 493–495: Builds `l3ValidityCondition` — same logic as vector search.
- Lines 531–546: Applies `l3ValidityCondition` to commit-hash-based L3 queries.

**`hybridSearch` (intent-router.ts lines 604–652):**

### Gaps identified

1. **`GET /mcp/get_decision_record` does NOT filter by validity status.** (mcp.ts lines 154–176)
   - Line 163–166: Queries L3 nodes by `commitHash` without any `validityStatus` filter.
   - This means orphaned and pending L3 nodes are returned, violating the ADR-011 principle that default queries should only return `valid` nodes.
   - This endpoint has no `include_pending` parameter at all.

2. **`include_pending` parameter is missing from the OpenAPI spec.** (`openapi.yaml`)
   - `GET /mcp/search_knowledge` (lines 929–955): Parameters are `query`, `project_id`, `limit` — no `include_pending`.
   - `POST /mcp/query` (lines 1022–1051): The `McpQueryInput` schema (lines 2484–2498) only has `q`, `project_id`, `limit` — no `include_pending`.
   - Since the project follows API-first with Orval codegen, this means generated clients won't have access to the `include_pending` parameter.

3. **`GET /mcp/search_knowledge` and `POST /mcp/query` read `include_pending` from `req.query` (GET query params for POST endpoint).** (mcp.ts line 195)
   - For `POST /mcp/query`, `include_pending` is read from `req.query` (URL query string), not from the JSON request body. This is an intentional design choice (query param on a POST), but it's inconsistent with the rest of the request body being JSON. The OpenAPI spec doesn't document this parameter at all.

4. **No tests for the `include_pending` filtering behavior.** The only MCP test file (`mcp-list-projects.test.ts`) tests `GET /mcp/list_projects` which doesn't return L3 nodes. There are no tests verifying:
   - Default queries only return `valid` L3 nodes.
   - `include_pending=true` also returns `pending` L3 nodes.
   - `GET /mcp/get_decision_record` filters by validity status.

## Round 2 — Code Quality & Security Review

### Code Quality

1. **Consistent validity filter pattern.** The `l3ValidityCondition` is constructed identically in three places (`vectorSearchHandler` line 193, `directLookupHandler` line 493). This is a minor DRY concern — the condition could be extracted into a shared helper function like `buildValidityCondition(includePending)`. However, the duplication is small and the code is readable.

2. **`include_pending` bypasses Zod validation.** In both `GET /mcp/search_knowledge` (line 50) and `POST /mcp/query` (line 195), the parameter is read directly from `req.query` rather than being part of a Zod-validated schema. This is a minor inconsistency — other parameters like `query`, `project_id`, and `limit` are properly validated. For `GET /mcp/search_knowledge`, there's no Zod schema at all (raw `req.query` access). For `POST /mcp/query`, the body is validated with Zod but the query param is not.

3. **No `pgEnum` for validity status.** (Noted in 4.3.3 report as well.) The `validityStatus` column uses `text("validity_status")` rather than a proper `pgEnum`, so the database does not enforce the enum constraint. This is a data integrity risk, though not specific to the MCP query filter behavior.

### Security

No security vulnerabilities specific to this feature. The `include_pending` parameter is a simple boolean toggle that doesn't expose additional data beyond what the user could already access through other means. The `validityStatus` column is not user-writable via any API endpoint.

## Round 3 — Integration & Completeness Review

### Integration Points

1. **Intent router → MCP route integration:** The `include_pending` parameter flows correctly from the MCP route handlers through `routeQuery` to all search handlers (`vectorSearchHandler`, `directLookupHandler`, `hybridSearch`). The wiring is correct end-to-end for the two main query endpoints.

2. **Schema → query integration:** The `l3_nodes.validityStatus` column (with default `"pending"`) is correctly referenced by the intent router's filter conditions. The generate pipeline creates L3 nodes with `validityStatus: "pending"`, and the sync endpoint promotes them to `"valid"` on main branch push. The MCP query filter operates on this column correctly.

3. **Orphan branch writer integration:** The orphan branch writer reads `validityStatus` from L3 nodes and includes it in generated markdown files. This is unaffected by the MCP query filter behavior.

### Missing Pieces

1. **`GET /mcp/get_decision_record` is unprotected.** This endpoint returns L3 nodes without any validity filter, which is a gap in the ADR-011 contract. Any MCP client can retrieve orphaned or pending knowledge through this endpoint.

2. **OpenAPI spec out of sync.** The `include_pending` parameter is missing from both MCP query endpoints in the OpenAPI spec. This means:
   - Generated TypeScript types (via Orval) won't include this parameter.
   - API documentation won't mention it.
   - The parameter exists in the code but is invisible to API consumers.

3. **No test coverage.** There are no tests for the MCP query filter behavior. The only MCP test covers `list_projects` which doesn't interact with L3 validity filtering.

4. **No `orphaned` detection.** (Blocked by item 4.3.8.) The `orphaned` status is defined in the schema but never set by any code path. This means the default filter (`valid` only) will correctly exclude orphaned nodes, but there will never be any orphaned nodes in practice until branch-delete detection is implemented.

## Findings

| # | Severity | Finding |
|---|----------|---------|
| 1 | **Medium** | `GET /mcp/get_decision_record` does not filter L3 nodes by `validityStatus`, returning orphaned/pending nodes contrary to ADR-011's default-filter requirement. |
| 2 | **Medium** | `include_pending` parameter is missing from OpenAPI spec for both `GET /mcp/search_knowledge` and `POST /mcp/query`. Generated clients won't have access to it. |
| 3 | **Low** | `include_pending` is read from raw `req.query` bypassing Zod validation on `POST /mcp/query`. |
| 4 | **Low** | No tests for MCP query validity filtering behavior (default filter or `include_pending`). |
| 5 | **Info** | `l3ValidityCondition` logic is duplicated in `vectorSearchHandler` and `directLookupHandler` — could be extracted to a shared helper. |

### Recommendations

1. **Add validity filter to `GET /mcp/get_decision_record`.** Add a `validityStatus` filter to the L3 query in this endpoint (mcp.ts line 163), defaulting to `valid` only. Optionally add an `include_pending` parameter.

2. **Add `include_pending` to OpenAPI spec.** Add the parameter to both `GET /mcp/search_knowledge` and `POST /mcp/query` endpoints in `openapi.yaml`, then regenerate types with Orval. For `POST /mcp/query`, decide whether `include_pending` should be in the request body (`McpQueryInput` schema) or documented as a query parameter.

3. **Add integration tests.** Test the full flow: create L3 nodes with `pending` status → query without `include_pending` (should exclude pending) → query with `include_pending=true` (should include pending) → promote to `valid` via sync → query without `include_pending` (should now include them).

4. **Extract shared validity filter helper.** Create a `buildValidityCondition(includePending: boolean)` helper to eliminate the duplicated condition construction.

---

## Verdict

**⚠️ WARN**

The core MCP query filter implementation is **correctly implemented** for the two main query endpoints (`GET /mcp/search_knowledge` and `POST /mcp/query`). The `include_pending` parameter is properly read, propagated through `routeQuery` to all search handlers, and the `l3ValidityCondition` correctly filters by `valid` only by default and expands to `valid | pending` when `include_pending=true`. The intent router's `vectorSearchHandler`, `directLookupHandler`, and `hybridSearch` all apply the filter consistently.

However, there are notable gaps:
- `GET /mcp/get_decision_record` does not filter by validity status at all, violating the ADR-011 default-filter contract.
- The `include_pending` parameter is missing from the OpenAPI spec, making it invisible to generated clients.
- There are no tests for the filtering behavior.

These gaps are actionable and should be addressed to fully satisfy ADR-011.
