## Design Spec Summary

ADR-011 (Two-Phase Knowledge Validity) states:

> **MCP query behavior:** Default filter is `status = valid` only. Query parameter `include_pending=true` enables pending knowledge (e.g., for querying a specific feature branch's design decisions).

Item 4.3.5 specifically covers the `include_pending=true` query parameter — its presence in the API, its propagation through the intent router, and its effect on L3 node filtering.

---

## Round 1 — Architecture & Design Review

### What the design requires

1. MCP query endpoints must accept an `include_pending=true` query parameter.
2. When the parameter is present, queries must also return L3 nodes with `validityStatus = "pending"`.
3. The parameter should be documented in the API contract (OpenAPI spec) so generated clients can use it.

### Gaps identified

1. **`GET /mcp/get_decision_record` does NOT support `include_pending` and does NOT filter by validity status.** (mcp.ts lines 154–176)
   - Line 163–166: Queries L3 nodes by `commitHash` without any `validityStatus` filter.
   - This endpoint always returns all L3 nodes regardless of validity status (pending, valid, or orphaned).
   - No `include_pending` parameter exists — but more critically, there's no filter at all.

2. **`include_pending` parameter is missing from the OpenAPI spec.** (`openapi.yaml`)
   - `GET /mcp/search_knowledge` (lines 929–955): Parameters are `query`, `project_id`, `limit` — no `include_pending`.
   - `POST /mcp/query` (lines 1022–1051): The `McpQueryInput` schema (lines 2484–2498) only has `q`, `project_id`, `limit` — no `include_pending`.
   - Since the project follows API-first with Orval codegen, generated TypeScript clients (`lib/api-client-react/`, `lib/api-zod/`) do not include this parameter. Confirmed: zero matches for `include_pending` in generated code directories.

3. **`POST /search` (non-MCP general search) also lacks `include_pending` support.** (search.ts line 27)
   - Calls `routeQuery(query, projectId, limit)` without the `includePending` parameter, always defaulting to `false`.
   - This is a minor gap — the general search endpoint has no way to include pending knowledge.

## Round 2 — Code Quality & Security Review

### Code Quality

1. **`include_pending` bypasses Zod validation.** In `GET /mcp/search_knowledge` (line 50) and `POST /mcp/query` (line 195), the parameter is read directly from `req.query` rather than being part of a Zod-validated schema. This is inconsistent with how other parameters (`query`, `project_id`, `limit`) are validated. For `GET /mcp/search_knowledge`, there is no Zod schema at all — all parameters come from raw `req.query`. For `POST /mcp/query`, the body is validated with Zod (`mcpQueryBodySchema`) but the query parameter is extracted separately.

2. **DRY concern: `l3ValidityCondition` logic is duplicated.** The identical condition construction appears in `vectorSearchHandler` (line 193) and `directLookupHandler` (line 493). This could be extracted into a shared helper function like `buildValidityCondition(includePending: boolean)`. The duplication is small and currently readable, but it's a maintenance risk.

3. **Inconsistent parameter location for `POST /mcp/query`.** The `include_pending` parameter is read from `req.query` (URL query string) on a POST endpoint, while the rest of the request data comes from the JSON body. This split pattern (body + query param) is unconventional and could confuse API consumers. The OpenAPI spec doesn't document this parameter at all, compounding the confusion.

### Security

No security vulnerabilities specific to this feature. The `include_pending` parameter is a simple boolean toggle that expands the result set to include `pending` L3 nodes. It does not expose data that the user couldn't already access through other means (e.g., `GET /mcp/get_decision_record` returns everything without filtering). The `validityStatus` column is not user-writable via any API endpoint.

## Round 3 — Integration & Completeness Review

### Integration Points

1. **MCP route → Intent router integration:** The `include_pending` parameter flows correctly from both MCP query endpoints (`GET /mcp/search_knowledge` and `POST /mcp/query`) through `routeQuery` to all search handlers. The wiring is correct end-to-end. ✅

2. **Schema → Query integration:** The `l3_nodes.validityStatus` column (default `"pending"`) is correctly referenced by the intent router's filter conditions. The generate pipeline creates L3 nodes with `validityStatus: "pending"`, and the sync endpoint promotes them to `"valid"` on main branch push. ✅

3. **OpenAPI → Generated client integration:** **Broken.** The `include_pending` parameter is not in the OpenAPI spec, so Orval-generated clients don't include it. This means frontend applications (`kg-engine/`) and other API consumers cannot use this parameter through the standard generated hooks. ❌

### Missing Pieces

1. **No test coverage for `include_pending`.** There are no tests verifying:
   - Default queries exclude `pending` L3 nodes.
   - `include_pending=true` includes `pending` L3 nodes.
   - `GET /mcp/get_decision_record` filters by validity status.
   - The `POST /search` endpoint's behavior with pending nodes.

2. **Generated clients lack the parameter.** Since `include_pending` is not in the OpenAPI spec, the Orval codegen pipeline won't produce types or hooks for it. Frontend developers would need to manually construct requests to use this parameter, violating the project's API-first principle.

3. **`GET /mcp/get_decision_record` is a gap in the validity filter contract.** This endpoint returns L3 nodes without any validity filter, which is inconsistent with ADR-011's requirement that default queries should only return `valid` nodes.

4. **`POST /search` has no `include_pending` support.** The general search endpoint always filters to `valid` only with no way to include pending nodes.

## Findings

| # | Severity | Finding |
|---|----------|---------|
| 1 | **Medium** | `include_pending` parameter is missing from OpenAPI spec for both `GET /mcp/search_knowledge` and `POST /mcp/query`. Generated clients (Orval) don't have access to it, violating the API-first principle. |
| 2 | **Medium** | `GET /mcp/get_decision_record` does not filter L3 nodes by `validityStatus` and has no `include_pending` parameter, returning all nodes regardless of status. |
| 3 | **Low** | `include_pending` is read from raw `req.query` bypassing Zod validation on both MCP endpoints. |
| 4 | **Low** | `POST /search` (non-MCP) also lacks `include_pending` support — always defaults to `valid` only. |
| 5 | **Low** | No tests for `include_pending` filtering behavior (default filter or parameter-enabled expansion). |
| 6 | **Info** | `l3ValidityCondition` logic is duplicated in `vectorSearchHandler` and `directLookupHandler` — could be extracted to a shared helper. |
| 7 | **Info** | `include_pending` on `POST /mcp/query` is read from URL query string instead of JSON body, creating an inconsistent parameter location pattern. |

### Recommendations

1. **Add `include_pending` to the OpenAPI spec.** Add the parameter to both `GET /mcp/search_knowledge` and `POST /mcp/query` endpoints in `openapi.yaml`, then regenerate types with Orval. For `POST /mcp/query`, decide whether `include_pending` should be in the request body (`McpQueryInput` schema) or documented as a query parameter. Adding it to the body schema would be more consistent with REST conventions and Zod validation.

2. **Add validity filter to `GET /mcp/get_decision_record`.** Add a `validityStatus` filter to the L3 query in this endpoint (mcp.ts line 163), defaulting to `valid` only. Optionally add an `include_pending` parameter for consistency with other MCP endpoints.

3. **Add integration tests.** Test the full flow: create L3 nodes with `pending` status → query without `include_pending` (should exclude pending) → query with `include_pending=true` (should include pending) → promote to `valid` via sync → query without `include_pending` (should now include them).

4. **Consider adding `include_pending` to `POST /search`.** For consistency, the general search endpoint should also support the parameter.

5. **Extract shared validity filter helper.** Create a `buildValidityCondition(includePending: boolean)` helper to eliminate the duplicated condition construction.

## Verdict

**⚠️ WARN**

The core `include_pending=true` query parameter implementation is **correctly wired** for the two main MCP query endpoints (`GET /mcp/search_knowledge` and `POST /mcp/query`). The parameter is properly read from the request, propagated through `routeQuery` to all search handlers (`vectorSearchHandler`, `directLookupHandler`, `hybridSearch`), and the `l3ValidityCondition` correctly expands from `valid`-only to `valid | pending` when the parameter is `true`.

However, there are notable gaps that prevent a PASS:

- The `include_pending` parameter is **missing from the OpenAPI spec**, making it invisible to generated clients and violating the project's API-first principle. This is the most significant gap — the parameter exists in code but is not part of the API contract.
- `GET /mcp/get_decision_record` has **no validity filter at all**, returning orphaned and pending nodes indiscriminately.
- There are **no tests** for the `include_pending` filtering behavior.
- The parameter **bypasses Zod validation** by being read from raw `req.query`.

These gaps are actionable and should be addressed to fully satisfy ADR-011's `include_pending=true` query parameter requirement.
