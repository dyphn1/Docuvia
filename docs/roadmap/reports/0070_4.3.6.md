## Design Spec Summary

ADR-011 (Two-Phase Knowledge Validity) defines a knowledge validity system with two phases:

- **Phase 1 (Local Review / Quality Gate):** AI-generated L3 nodes are created with `validityStatus: "pending"`. Human review confirms accuracy via the existing `review_tasks` mechanism.
- **Phase 2 (Merge Gate / Validity Gate):** When `docuvia sync` fires on `git push`, the server checks if source commits have been merged into the main branch. Merged → `valid`. Abandoned → `orphaned`.

The schema requirements stated in ADR-011:
> ⚠️ `l3_nodes` and `commits` tables require `validityStatus` column
> ⚠️ `commits` table requires `branchName text` column

The validity status enum is: `pending | valid | orphaned`

---

## Round 1 — Architecture & Design Review

### What the design requires

1. `l3_nodes` table must have a `validityStatus` column with values `pending | valid | orphaned`
2. `commits` table must have a `validityStatus` column with the same enum values
3. Default value for `validityStatus` on both tables should be `"pending"`
4. The generate pipeline must create L3 nodes with `validityStatus: "pending"`
5. The sync endpoint must promote L3 nodes to `valid` when commits are pushed to the main branch
6. The intent router / MCP must filter by `valid` by default, with `include_pending` to include pending

### Gaps identified

1. **No `pgEnum` for validity status.** Both schemas use `text("validity_status")` rather than a proper `pgEnum`. This is inconsistent with `review_tasks.ts` which uses `pgEnum` for `review_status`, `review_task_type`, and `review_entity_type`. Without a `pgEnum`, the database does not enforce the enum constraint — any string value could be inserted (e.g., `"approved"`, `"rejected"`, or typos like `"pendng"`).

2. **No migration SQL for adding `validityStatus` to existing databases.** The existing migration files (`001_add_l3_node_source_refs.sql`, `002_add_project_integrations.sql`) do not include DDL for adding `validity_status` to `l3_nodes` or `commits`. If a database was set up before these columns were added to the Drizzle schema, running `pnpm --filter @workspace/db run push` would apply them via Drizzle's schema diff, but there is no explicit migration for production environments that require controlled migration scripts.

3. **`insertCommitSchema` includes `validityStatus` in the insert schema.** The `insertCommitSchema` omits only `id` and `createdAt`, meaning `validityStatus` is a valid field in the insert schema. While not a bug (the DB default handles inserts that omit it), it means API consumers could theoretically set `validityStatus` to any value during insert, bypassing the intended state machine. The `insertL3NodeSchema` has the same characteristic.

## Round 2 — Code Quality & Security Review

### Code Quality

1. **Schema design inconsistency (Medium severity).** The `validityStatus` column is defined as `text` without a `pgEnum`, while other status columns in the project (`review_tasks.status`, `review_tasks.taskType`, `review_tasks.entityType`) all use `pgEnum`. This reduces type safety at the database level and is inconsistent with project conventions.

2. **Insert schema exposes `validityStatus` (Low severity).** Both `insertCommitSchema` and `insertL3NodeSchema` include `validityStatus` as an optional field. Since `validityStatus` is an internal state machine value (set by the generate pipeline and sync endpoint), it should not be user-settable. It should be omitted from the insert schema:
   ```typescript
   export const insertCommitSchema = createInsertSchema(commitsTable).omit({
     id: true,
     createdAt: true,
     validityStatus: true,  // Internal field — not user-settable
   });
   ```

3. **No orphaned detection (Info — blocked by 4.3.8).** The `orphaned` value in the enum is never written by any code path. Branch-delete detection (item 4.3.8) is marked ❌ Todo. This is a known dependency, not a schema defect.

### Security

No security vulnerabilities specific to this feature. The `validityStatus` column is set internally by the generate pipeline and sync endpoint. No API endpoint allows users to directly set this column (though the insert schema technically allows it — see issue #2 above).

## Round 3 — Integration & Completeness Review

### Integration Points

1. **Generate → Sync → Query pipeline:** The flow from generate (creates L3 with `pending`) → sync (promotes to `valid` on main branch) → intent-router (filters by `valid` by default) is correctly wired end-to-end. The schema columns support this flow.

2. **Orphan branch writer:** `orphan-branch-writer.ts` reads `validityStatus` from L3 nodes and includes it in the YAML frontmatter of generated markdown files. This works correctly with the current schema.

3. **Review tasks integration:** The review task system (Phase 1) uses its own `status` column (`pending | approved | rejected | deferred`). The `validityStatus` column on `l3_nodes` is independent and parallel. No conflicts.

4. **MCP query filtering:** The intent router correctly uses `l3NodesTable.validityStatus` in WHERE clauses. The column is properly indexed by the database (Drizzle creates indexes based on query patterns).

### Missing Pieces

1. **No `pgEnum` constraint.** The database will not reject invalid values like `"foo"` or `"approved"`. This is a data integrity risk.

2. **No migration DDL.** No SQL migration file exists for adding `validity_status` to `l3_nodes` and `commits`. While Drizzle's `push` command handles this for dev environments, production deployments typically require explicit migration scripts.

3. **No tests for schema constraints.** There are no tests verifying that:
   - The default value is `"pending"` on insert
   - The column rejects NULL values
   - Invalid values are rejected (only possible with `pgEnum`)

## Findings

| # | Severity | Finding |
|---|----------|---------|
| 1 | **Medium** | `validityStatus` uses `text` column instead of `pgEnum`, unlike other status columns in the project. No DB-level enum constraint. |
| 2 | **Low** | `insertCommitSchema` and `insertL3NodeSchema` expose `validityStatus` as a user-settable field. Should be omitted since it's an internal state machine value. |
| 3 | **Low** | No migration SQL for adding `validity_status` to `l3_nodes` and `commits` tables. |
| 4 | **Info** | `orphaned` status value is defined but never set by any code path (blocked by item 4.3.8 — branch merge status tracking). |
| 5 | **Info** | No tests for schema constraints (default value, NOT NULL, enum values). |

### Recommendations

1. **Create a `pgEnum` for validity status.** Add:
   ```typescript
   export const validityStatusEnum = pgEnum("validity_status", ["pending", "valid", "orphaned"]);
   ```
   And use it in both `l3_nodes.ts` and `commits.ts`:
   ```typescript
   validityStatus: validityStatusEnum("validity_status").notNull().default("pending"),
   ```
   This ensures DB-level constraint and consistency with other enums in the project.

2. **Omit `validityStatus` from insert schemas.** Update both `insertCommitSchema` and `insertL3NodeSchema` to omit `validityStatus: true`, preventing API consumers from setting this internal field.

3. **Add migration DDL.** Create a migration file (e.g., `003_add_validity_status.sql`) that adds the `validity_status` column (as a proper `TYPE` enum) to both `l3_nodes` and `commits` tables.

4. **Add schema constraint tests.** Write tests verifying the default value, NOT NULL constraint, and (once `pgEnum` is added) enum value rejection.

---

## Verdict

**⚠️ WARN**

The `validityStatus` column is correctly defined on both `l3_nodes` and `commits` tables with the right name, NOT NULL constraint, and `"pending"` default value. The generate pipeline, sync endpoint, and intent router all correctly use this column. The schema requirement from ADR-011 is functionally met.

However, the column uses `text` instead of a proper `pgEnum` (inconsistent with project conventions for status columns), the insert schemas expose an internal field, and no migration DDL exists. These issues warrant a WARN verdict.
