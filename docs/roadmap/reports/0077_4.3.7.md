## Design Spec Summary

ADR-011 (Two-Phase Knowledge Validity) requires the `commits` table to track which branch each commit belongs to, so that the sync endpoint can determine whether commits have been merged into the main branch. The specific schema requirement stated in ADR-011:

> ⚠️ `commits` table requires `branchName text` column

The `branchName` column is used by the sync pipeline (`POST /sync`) to:
1. Record the pushed branch name on each commit (line 117-127 of `sync.ts`)
2. Determine whether to promote commits and their L3 nodes to `valid` status (when the pushed branch is `main`, `master`, or `trunk`)

---

## Round 1 — Architecture & Design Review

### What the design requires

1. `commits` table must have a `branchName text` column
2. The sync endpoint must set `branchName` on pushed commits
3. The sync endpoint must use `branchName` (via `isMainBranch()`) to trigger Phase 2 validity promotion
4. The column should be nullable (pre-existing commits may lack branch info)

### What the implementation provides

**Schema — ✅ Column exists:**
```typescript
// lib/db/src/schema/commits.ts line 22
branchName: text("branch_name"),
```
- Column name: `branch_name` ✅
- Type: `text` ✅
- Nullable: yes (no `.notNull()`) ✅ — correct for pre-existing commits

**Sync endpoint — ✅ Sets branchName on push:**
```typescript
// sync.ts lines 117-127
// 2. Update commits.branchName for pushed commits
if (pushedCommits.length > 0) {
  await db
    .update(commitsTable)
    .set({ branchName: pushedBranch })
    .where(
      and(
        eq(commitsTable.projectId, projectId),
        inArray(commitsTable.hash, pushedCommits)
      )
    );
```
This correctly updates `branchName` for all pushed commits.

**Sync endpoint — ✅ Uses branchName for validity promotion:**
```typescript
// sync.ts lines 129-204
if (isMainBranch(pushedBranch)) {
  // Promote commits and L3 nodes to 'valid'
}
```
The `isMainBranch()` function checks against `main`, `master`, `trunk` — correct.

### Gaps identified

1. **Ingestion pipeline does NOT set `branchName` on initial commit insert.** The `ingest.ts` route extracts the `branch` parameter from the request (line 41: `const branch = body.branch ?? "main"`) but never passes it to `processIngestion()` or includes it in the commit insert. The `GitCommitItem` interface (ingestion-pipeline.ts lines 23-29) has no `branch` field. This means commits ingested via `POST /projects/:id/ingest/git` will have `branchName = NULL` until a subsequent sync push updates them. This is a data completeness gap — the branch information is available at ingest time but is not captured.

2. **`branchName` is missing from the OpenAPI `Commit` schema.** The `Commit` response schema (openapi.yaml lines 1948-1969) does not include a `branchName` property. This means generated API clients (via Orval) will not have access to this field, and the API contract does not document it.

3. **`insertCommitSchema` exposes `branchName` as a user-settable field.** The `insertCommitSchema` (commits.ts lines 26-29) omits only `id` and `createdAt`, meaning `branchName` is a valid field in the insert schema. Since `branchName` is an internal field set by the sync endpoint, it should not be user-settable via the API.

## Round 2 — Code Quality & Security Review

### Code Quality

1. **Nullable column design is correct.** The `branchName` column is intentionally nullable, which is appropriate because:
   - Pre-existing commits (ingested before the column was added) won't have branch info
   - The sync endpoint populates it retroactively when pushes occur
   - This avoids a migration requiring a default value for existing rows

2. **No database-level constraint on branchName values.** This is acceptable — `branchName` is a free-form text field (branch names can contain slashes, hyphens, etc.). A `pgEnum` would be inappropriate here.

3. **`insertCommitSchema` exposes internal field (Low severity).** The `branchName` field should be omitted from the insert schema to prevent API consumers from setting it:
   ```typescript
   export const insertCommitSchema = createInsertSchema(commitsTable).omit({
     id: true,
     createdAt: true,
     branchName: true,  // Internal field — set by sync endpoint only
   });
   ```

4. **OpenAPI spec out of sync (Low severity).** The `Commit` schema in `openapi.yaml` is missing `branchName`. It should include:
   ```yaml
   branchName:
     type: ["string", "null"]
     description: Branch name this commit was pushed to (null if not yet synced)
   ```

### Security

No security vulnerabilities specific to this feature. The `branchName` column is set internally by the sync endpoint and is not security-sensitive data.

## Round 3 — Integration & Completeness Review

### Integration Points

1. **Sync → Validity Promotion pipeline:** The flow from sync (sets `branchName`) → `isMainBranch()` check → promote to `valid` is correctly wired. The `branchName` column is used as intended by ADR-011 Phase 2.

2. **Ingest → Sync gap:** The ingestion pipeline creates commits without `branchName`. The sync endpoint later updates `branchName` when pushes occur. This means:
   - For the common flow (ingest first, then sync on push), `branchName` will be populated correctly by the sync endpoint
   - For commits that are ingested but never pushed (e.g., historical ingestion of already-merged commits), `branchName` will remain NULL, and the Phase 2 validity promotion won't trigger for them
   - This is a partial gap — the system works for the happy path but not for backfill scenarios

3. **Orphan branch writer:** The `orphan-branch-writer.ts` reads commit data for export. Since `branchName` may be NULL for ingested-but-not-synced commits, the orphan branch YAML may lack branch information for some commits.

### Missing Pieces

1. **No `branch` field in `GitCommitItem` interface.** The ingestion pipeline's `GitCommitItem` interface (lines 23-29) has `sha`, `message`, `author`, `date`, and `diff` — but no `branch`. The `branch` parameter is available in the ingest route but is not threaded through to the pipeline.

2. **No tests for `branchName` behavior.** There are no tests verifying:
   - `branchName` is set by the sync endpoint
   - `branchName` is NULL after initial ingestion
   - `isMainBranch()` correctly identifies main branches
   - Validity promotion only occurs for main branch pushes

3. **Backfill scenario not addressed.** Historical commits ingested before the sync endpoint is called will have `branchName = NULL`. There is no mechanism to backfill branch names for already-ingested commits (e.g., by parsing git reflog or using the GitHub API).

## Findings

| # | Severity | Finding |
|---|----------|---------|
| 1 | **Medium** | Ingestion pipeline does not set `branchName` on initial commit insert. The `branch` parameter is available in `ingest.ts` but not passed through to `processIngestion()` or the commit insert. Commits will have `branchName = NULL` until a sync push occurs. |
| 2 | **Low** | `branchName` is missing from the OpenAPI `Commit` response schema. Generated API clients won't have access to this field. |
| 3 | **Low** | `insertCommitSchema` exposes `branchName` as a user-settable field. Should be omitted since it's an internal field set by the sync endpoint. |
| 4 | **Info** | No tests for `branchName` behavior (set by sync, NULL after ingest, validity promotion logic). |
| 5 | **Info** | No backfill mechanism for `branchName` on historical commits ingested before sync. |

### Recommendations

1. **Thread `branch` through the ingestion pipeline.** Add a `branch` field to `GitCommitItem` and pass it from `ingest.ts` to `processIngestion()`, then include it in the commit insert:
   ```typescript
   // In ingest.ts, pass branch to processIngestion
   const { ingested, skipped, errors } = await processIngestion({
     type: "git",
     projectId,
     projectName: project.name,
     items: gitItems,
     branch,  // NEW
   });
   
   // In ingestion-pipeline.ts, add to GitCommitItem and include in insert
   await db.insert(commitsTable).values({
     projectId,
     hash: c.sha,
     message: c.message.slice(0, 4000),
     author: c.author ?? "Unknown",
     valid: score >= 0.4,
     vcsType: "git",
     branchName: c.branch ?? null,  // NEW
   });
   ```

2. **Add `branchName` to OpenAPI `Commit` schema.** Update the `Commit` schema in `openapi.yaml` to include the `branchName` property, then regenerate types with Orval.

3. **Omit `branchName` from `insertCommitSchema`.** Prevent API consumers from setting this internal field:
   ```typescript
   export const insertCommitSchema = createInsertSchema(commitsTable).omit({
     id: true,
     createdAt: true,
     branchName: true,
   });
   ```

4. **Add tests.** Write integration tests verifying:
   - `branchName` is NULL after initial git ingestion (until recommendation #1 is implemented)
   - `branchName` is set after sync push
   - Validity promotion only occurs for main branch pushes

---

## Verdict

**⚠️ WARN**

The `branchName` column is correctly defined on the `commits` table as a nullable `text` column, and the sync endpoint correctly updates it on pushed commits and uses it for Phase 2 validity promotion. The core schema requirement from ADR-011 is met.

However, the ingestion pipeline does not set `branchName` at insert time (even though the branch information is available), the OpenAPI spec is missing the field from the `Commit` response schema, and the insert schema inappropriately exposes this internal field. These gaps warrant a WARN verdict.
