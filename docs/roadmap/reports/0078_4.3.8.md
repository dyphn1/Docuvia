# Verification Report: Item 4.3.8 — Branch Merge Status Tracking (GitHub Webhook or Polling)

**Date:** 2026-06-12
**Item ID:** 4.3.8
**Description:** Branch merge status tracking (GitHub webhook or polling)
**Design Spec:** ADR-011 (Two-Phase Knowledge Validity) — `docs/design/09-architectural-decisions.md` lines 269–299
**Status in Checklist:** ❌ Todo

---

## Design Spec Summary

ADR-011 defines a two-phase knowledge validity system. Phase 2 (Merge Gate) requires the server to track whether source commits have been merged into the main/default branch:

- **Merged:** Commits and associated L3 nodes → `valid`
- **Abandoned (branch deleted without merge):** Commits and associated L3 nodes → `orphaned`

The ADR explicitly states (line 296):
> ⚠️ Server must track branch merge status — requires either GitHub webhook integration or periodic polling

This tracking is a prerequisite for the `orphaned` validity transition. Without it, L3 nodes from abandoned branches can never be marked as `orphaned`, and the two-phase validity system is incomplete.

## Round 1 — Architecture & Design Review

### What ADR-011 Requires

The branch merge status tracking system must:

1. **Detect PR merges** — When a PR is merged on GitHub, the server should know that the PR's commits have been merged into the main branch.
2. **Detect abandoned branches** — When a branch is deleted or a PR is closed without merging, the server should know that the branch's commits were NOT merged.
3. **Cascade to validity status** — Merge detection should promote commits and L3 nodes to `valid`. Abandon detection should set them to `orphaned`.

The ADR specifies two acceptable mechanisms:
- **GitHub webhook integration** (preferred) — React to `pull_request` (closed/merged) and `delete` (branch) events in real time.
- **Periodic polling** (fallback) — Regularly check branch/PR status via the GitHub API.

### What Is Actually Implemented

#### GitHub Webhook Handler (`github_webhooks.ts`)

The webhook handler at `POST /webhooks/github/:projectId` processes `pull_request` events with three action handlers:

1. **`action === "opened" || action === "synchronize"`** (lines 198–252): Upserts PR record, ingests PR commits, notifies subscribers. ✅ Works correctly.

2. **`action === "closed" && isMerged`** (lines 253–316): Updates PR record to `merged`, generates AI summary, posts GitHub comment, notifies subscribers. ✅ PR record is updated correctly. ❌ **Does NOT cascade to `commits.validityStatus` or `l3_nodes.validityStatus`.**

3. **`action === "closed"` (not merged)** (lines 317–328): Updates PR record to `closed`. ✅ PR record is updated. ❌ **Does NOT set `commits.validityStatus` or `l3_nodes.validityStatus` to `orphaned`.**

#### Critical Gap: No `delete` Event Handler

The webhook handler only processes `pull_request` events (line 156: `if (eventType !== "pull_request")`). It does **not** handle:
- `delete` events (branch or tag deletion)
- `push` events (which could indicate force-pushes or branch deletions)

GitHub sends a `delete` event when a branch is deleted. Without handling this event, the server cannot detect abandoned branches in real time.

#### Critical Gap: No Polling Mechanism

There is **no periodic polling mechanism** anywhere in the codebase:
- No `setInterval` or cron-based polling of GitHub API for branch/PR status
- No background job that checks if branches still exist
- No fallback mechanism when webhooks are not configured

#### Critical Gap: No Validity Cascade on PR Merge

When a PR is merged (`action === "closed" && isMerged`), the webhook handler:
- ✅ Updates `pull_requests.state` to `"merged"`
- ✅ Generates AI summary
- ✅ Posts comment to GitHub
- ✅ Notifies subscribers
- ❌ Does **NOT** update `commits.validityStatus` to `"valid"` for the PR's commits
- ❌ Does **NOT** update `l3_nodes.validityStatus` to `"valid"` for L3 nodes associated with those commits

#### Critical Gap: No `orphaned` Transition

When a PR is closed without merging (`action === "closed"`, not merged):
- ✅ Updates `pull_requests.state` to `"closed"`
- ❌ Does **NOT** update `commits.validityStatus` to `"orphaned"`
- ❌ Does **NOT** update `l3_nodes.validityStatus` to `"orphaned"`

There is also no code anywhere else in the codebase that sets `validityStatus` to `"orphaned"`. The string `"orphaned"` never appears in any source file.

### Architecture Gaps Summary

| Requirement | Status | Location |
|-------------|--------|----------|
| Detect PR merge via webhook | ⚠️ Partial | `github_webhooks.ts:253` — detects but doesn't cascade validity |
| Detect abandoned PR via webhook | ❌ Missing | `github_webhooks.ts:317` — updates PR record only |
| Detect branch deletion via webhook | ❌ Missing | No `delete` event handler exists |
| Periodic polling fallback | ❌ Missing | No polling mechanism anywhere |
| Cascade merge → `valid` on PR merge | ❌ Missing | No code path |
| Cascade abandon → `orphaned` on PR close | ❌ Missing | No code path |
| Cascade abandon → `orphaned` on branch delete | ❌ Missing | No code path |

## Round 2 — Code Quality & Security Review

### Code Quality Issues

1. **Webhook handler is event-type gated too narrowly** (`github_webhooks.ts:156`):
   ```typescript
   if (eventType !== "pull_request") {
     return res.status(200).json({ message: "Event ignored" });
   }
   ```
   This silently ignores `delete` events, which are essential for branch abandonment detection. The handler should either process `delete` events or log a warning when receiving unhandled event types.

2. **No `orphaned` string literal in codebase**: The validity status enum is defined as `pending | valid | orphaned` in ADR-011, but the string `"orphaned"` never appears in any source file. The codebase only uses `"pending"` and `"valid"`. This means the `orphaned` status is dead code — defined in the schema but unreachable.

3. **Inconsistent merge detection paths**: The system has two paths for detecting merges:
   - `sync.ts` — handles direct pushes to main via `POST /sync` (promotes to `valid`)
   - `github_webhooks.ts` — handles PR merges via GitHub webhook (does NOT promote to `valid`)
   
   This inconsistency means the same commit can have different validity status depending on how it was merged.

4. **No authentication on sync endpoint**: The `POST /sync` endpoint (`sync.ts:49`) has no authentication. It relies on the `docuvia sync` CLI being the only caller, but since the CLI doesn't exist (item 3.4.3 ❌ FAIL), this is currently unreachable. If it were reachable, any caller could trigger validity promotion.

### Security Review

1. **Webhook signature validation is conditional** (`github_webhooks.ts:134-143`): The HMAC-SHA256 signature check only runs when `GITHUB_WEBHOOK_SECRET` is set. If the environment variable is missing, webhooks are accepted without validation. This is a security risk in production — an attacker could forge webhook events to manipulate PR records.

2. **No rate limiting on webhook endpoint**: The webhook handler has no rate limiting. A malicious actor could flood the endpoint with fake events (if signature validation is not configured).

3. **No authentication on sync endpoint**: As noted above, `POST /sync` has no auth. This is a medium-severity issue if the endpoint becomes reachable.

## Round 3 — Integration & Completeness Review

### Integration Analysis

The branch merge status tracking is supposed to integrate with:

1. **GitHub webhook → Validity promotion**: ❌ Not implemented. The webhook detects PR merges but doesn't cascade to validity status.

2. **Branch deletion detection → Orphaned status**: ❌ Not implemented. No `delete` event handler exists.

3. **Polling fallback**: ❌ Not implemented. No polling mechanism exists.

4. **Sync endpoint → Validity promotion**: ⚠️ Partially implemented. The sync endpoint promotes to `valid` on direct main branch pushes, but the `docuvia sync` CLI that should trigger it doesn't exist (item 3.4.3 ❌ FAIL).

5. **MCP query filter**: ✅ Correctly filters by `valid` status. But since the merge gate doesn't promote PR-merged commits to `valid`, those L3 nodes remain `pending` and are invisible to default MCP queries.

### End-to-End Flow Analysis

**Scenario A: PR merged via GitHub**
1. Developer merges PR on GitHub
2. GitHub webhook fires → `github_webhooks.ts` handles `action === "closed" && isMerged`
3. PR record updated to `merged` ✅
4. AI summary generated and posted ✅
5. **But:** Commits and L3 nodes NOT promoted to `valid` ❌
6. **Result:** ❌ Broken end-to-end (missing cascade)

**Scenario B: PR closed without merge**
1. Developer closes PR on GitHub
2. GitHub webhook fires → `github_webhooks.ts` handles `action === "closed"` (not merged)
3. PR record updated to `closed` ✅
4. **But:** Commits and L3 nodes NOT set to `orphaned` ❌
5. **Result:** ❌ Broken end-to-end (missing orphaned transition)

**Scenario C: Branch deleted on GitHub**
1. Developer deletes feature branch on GitHub
2. GitHub sends `delete` event
3. Webhook handler ignores it (only processes `pull_request` events) ❌
4. **Result:** ❌ Completely unhandled

**Scenario D: Direct push to main (via sync CLI)**
1. Developer pushes to `main`
2. `docuvia sync` CLI should call `POST /sync` → **FAILS** (CLI doesn't exist)
3. Even if called, sync route would promote to `valid` ✅
4. **Result:** ❌ Broken end-to-end (missing CLI)

### Missing Tests

There are no tests for:
- Webhook PR merge cascade to L3 node validity
- Webhook PR close without merge → orphaned transition
- Webhook branch delete event handling
- Polling mechanism for branch status
- End-to-end flow from PR merge → validity promotion

### Blocker Dependencies

This item (4.3.8) is a blocker for:
- **4.3.2** (Phase 2 Merge Gate) — Cannot function without branch merge status tracking
- **4.3.3** (L3 Validity Status Enum) — `orphaned` status is unreachable without this
- **4.3.4** (MCP query default filter) — L3 nodes stuck in `pending` are silently invisible

## Findings

### Critical Issues

| # | Severity | Finding |
|---|----------|---------|
| 1 | **Critical** | GitHub webhook PR merge handler does not cascade to `commits.validityStatus` or `l3_nodes.validityStatus`. Merged PRs leave L3 nodes in `pending` status forever. |
| 2 | **Critical** | No `delete` event handler in webhook. Branch deletions are completely unhandled. No mechanism to detect abandoned branches in real time. |
| 3 | **Critical** | No polling mechanism exists as a fallback for webhook-based branch status tracking. If webhooks are not configured, branch merge status is never tracked. |
| 4 | **Critical** | No code in the entire codebase sets `validityStatus` to `"orphaned"`. The `orphaned` status is defined in the schema but is unreachable dead code. |

### Warnings

| # | Severity | Finding |
|---|----------|---------|
| 5 | **Medium** | Webhook signature validation is conditional on `GITHUB_WEBHOOK_SECRET` being set. Without it, webhooks are accepted without authentication. |
| 6 | **Medium** | `POST /sync` endpoint has no authentication. Any caller could trigger validity promotion. |
| 7 | **Medium** | Inconsistent merge detection: `sync.ts` promotes to `valid` on direct push, but `github_webhooks.ts` does not promote on PR merge. |
| 8 | **Low** | Webhook handler silently ignores non-`pull_request` events without logging a warning. |
| 9 | **Low** | No tests for branch merge status tracking, webhook cascade, or polling behavior. |

### Recommendations

1. **Add validity cascade to GitHub webhook PR merge handler** — In `github_webhooks.ts:253-316`, after updating the PR record to `merged`, add logic to:
   - Fetch the PR's commits (via `fetchPrCommits`)
   - Set `commits.validityStatus = 'valid'` for those commits
   - Find associated L3 nodes (via `sourceCommits` or `commitHash`) and set `l3_nodes.validityStatus = 'valid'`

2. **Add orphaned transition to GitHub webhook close handler** — In `github_webhooks.ts:317-328`, after updating the PR record to `closed`, add logic to:
   - Fetch the PR's commits
   - Set `commits.validityStatus = 'orphaned'` for those commits
   - Find associated L3 nodes and set `l3_nodes.validityStatus = 'orphaned'`

3. **Add `delete` event handler** — In `github_webhooks.ts`, add handling for `eventType === "delete"` to detect branch deletions:
   ```typescript
   if (eventType === "delete") {
     const refType = payload["ref_type"] as string;
     const ref = payload["ref"] as string; // branch name
     if (refType === "branch") {
       // Find commits with this branchName and set to orphaned
       // Find associated L3 nodes and set to orphaned
     }
   }
   ```

4. **Implement periodic polling fallback** — Create a background job (e.g., running every 5 minutes) that:
   - Queries all PRs with `state = 'open'` from the `pull_requests` table
   - Checks their current status via the GitHub API (`GET /repos/{owner}/{repo}/pulls/{number}`)
   - If a PR is closed/merged, applies the appropriate validity cascade
   - If a branch no longer exists, marks associated commits/L3 nodes as `orphaned`

5. **Make webhook signature validation mandatory** — Require `GITHUB_WEBHOOK_SECRET` in production. Return 500 if the secret is not configured, rather than silently accepting unverified webhooks.

6. **Add authentication to sync endpoint** — Add API key or token-based auth to `POST /sync` to prevent unauthorized validity promotion.

7. **Add integration tests** — Write tests for:
   - Webhook PR merge → validity promotion cascade
   - Webhook PR close without merge → orphaned transition
   - Webhook branch delete → orphaned transition
   - Polling fallback for PR status changes

## Overall Verdict

## ❌ FAIL

Branch merge status tracking is **not implemented**. The GitHub webhook handler detects PR merges and closes but does not cascade to validity status. There is no `delete` event handler for branch deletions. There is no polling mechanism as a fallback. The `orphaned` validity status is unreachable dead code — no code path in the entire codebase sets it.

The Phase 2 Merge Gate (item 4.3.2) is fundamentally broken without this feature. L3 nodes generated from PR commits will remain in `pending` status forever, even after the PR is merged into main. Abandoned branches are never detected, so their L3 nodes are never marked as `orphaned`.

This is a critical blocker for the two-phase knowledge validity system defined in ADR-011.
