## Round 1 — Architecture & Design Review

### Design Specification

The design spec (`04-solution-strategy.md`, section 4.4) states:

> 1. **Pipeline output → `review_tasks`**: Every AI-suggested L1 tag, L2 node, and L3 decision record creates a `review_task` row (type: `anchor`).
> 2. **Noise detection → merge/reject tasks**: The pipeline's final step scans for near-duplicate tags and low-usage L1 labels, creating `merge` and `anchor` review tasks automatically.

The glossary (`12-glossary.md`) defines: "Created by the generate pipeline for every AI-generated node."

### Implementation Analysis

The generate pipeline (`artifacts/api-server/src/routes/generate.ts`, `POST /projects/:id/generate`) creates review tasks in the following places:

1. **L1 Tags (lines 669-676)**: Each new AI-generated L1 tag gets an `anchor` review task. ✅ Matches design.

2. **L2 Nodes (lines 953-977)**: A post-processing loop queries all L2 nodes with `needsReview=true` and creates `validate` review tasks for any not already covered by a pending review task. ✅ Functionally covers all new L2 nodes, though the task type is `validate` rather than `anchor` as the design specifies.

3. **L3 Nodes (lines 920-929)**: Only L3 nodes with `confidence < 0.8` get a `validate` review task. ❌ **Gap**: High-confidence L3 nodes (confidence >= 0.8) do NOT get a review task. This contradicts the design spec which says "every AI-suggested L1 tag, L2 node, and L3 decision record creates a review_task row."

4. **Noise Detection (lines 306-375, 1009-1017)**: The `runNoiseDetection()` function creates `anchor` tasks for low-usage L1 tags (usageCount <= 1) and `merge` tasks for near-duplicate L1 tag names. ✅ Matches design.

5. **Cross-Project Links (lines 263-269)**: The `detectCrossProjectLinks()` function creates `merge` review tasks for L2 nodes with high cosine similarity (>= 0.85) to nodes in other projects. ✅ Reasonable extension beyond the design spec.

6. **Condensation (lines 880-889)**: When an L3 node's occurrence count reaches the condensation threshold, a `validate` review task is created if `condensationReviewRequired` is true (default: false). ✅ Reasonable.

### Findings

- **Gap 1 — High-confidence L3 nodes skip review**: The design says every AI-generated node should create a review task, but the code only creates review tasks for L3 nodes with confidence < 0.8. High-confidence L3 nodes are inserted directly without any review task. This is a deliberate code choice that prioritizes reducing review burden over the design spec's requirement for universal review.
- **Gap 2 — Task type naming inconsistency**: The design specifies type `anchor` for all pipeline output review tasks, but the code uses `validate` for L2 and L3 nodes. The schema does include `validate` as a valid enum value, so this is semantically acceptable but inconsistent with the design document.

## Round 2 — Code Quality & Security Review

### Schema Design (`lib/db/src/schema/review_tasks.ts`)

The schema is clean and well-structured:
- Uses PostgreSQL enums for `review_entity_type` (l1_tag, l2_node, l3_node), `review_task_type` (anchor, correct, validate, merge), and `review_status` (pending, approved, rejected, deferred).
- Includes `correctedValue` field for storing human corrections.
- Uses `drizzle-zod` for type-safe insert schema generation.
- ✅ No issues.

### Generate Route (`artifacts/api-server/src/routes/generate.ts`)

- The `reviewTasksCreated` counter is properly incremented at each creation point and returned in the JSON response (line 1038).
- The post-processing loop for L2 review tasks (lines 953-977) correctly deduplicates by checking existing pending review tasks before creating new ones.
- ✅ Well-structured with proper error handling (try/catch with project status set to "error" on failure).

### Review Tasks Route (`artifacts/api-server/src/routes/review_tasks.ts`)

- The `enrichTask()` function (lines 17-66) performs N+1 queries — one query per task to fetch entity details. With many pending tasks, this could be a performance concern. Consider batch fetching.
- The resolution handler (lines 109-197) properly:
  - Validates input with Zod schemas (`ResolveReviewTaskParams`, `ResolveReviewTaskBody`)
  - Writes back corrections to the actual node (L1/L2/L3)
  - Creates `correction_examples` entries for L2 and L3 corrections
  - Logs to `activity_log`
  - Sets `needsReview: false` on L2 nodes after resolution
- ⚠️ **Minor gap**: L3 nodes don't have a `needsReview` flag being cleared in the resolution handler. Only L2 nodes get `needsReview: false` (lines 184-189). The L3 schema doesn't appear to have a `needsReview` column, so this is acceptable if L3 nodes don't track that flag.

### Security

- Input validation via Zod on the resolve endpoint. ✅
- No SQL injection risk — uses Drizzle ORM parameterized queries. ✅
- No authentication/authorization checks visible in the route handlers (relies on middleware). ⚠️ This is a cross-cutting concern covered by item 9.1.x.

## Round 3 — Integration & Completeness Review

### OpenAPI Integration

The OpenAPI spec (`lib/api-spec/openapi.yaml`) defines three review-tasks endpoints:
- `GET /review-tasks` — List review tasks
- `GET /review-tasks/stats` — Get review task statistics
- `PATCH /review-tasks/{id}` — Resolve a review task

The generate endpoint's response schema includes `reviewTasksCreated`. ✅

### End-to-End Flow

The complete flow works as follows:
1. Generate pipeline creates AI-generated nodes and review tasks
2. Review tasks appear in the list endpoint
3. Reviewer resolves via PATCH endpoint
4. Resolution writes back corrections and creates correction_examples
5. Activity log records the resolution

✅ The flow is complete and functional.

### Missing Pieces

1. **No review task creation for the `/extract/sieve` endpoint** (lines 453-517): The sieve extraction endpoint creates L3 decisions but does NOT create review tasks for them. This is a separate endpoint from the main generate pipeline, but it still produces AI-generated content that should arguably go through review.

2. **No review task for updated L2 nodes** (lines 762-775): When an existing L2 node is updated (not newly created), the code sets `needsReview: true` and `aiGenerated: true`, but the post-processing loop only catches nodes that weren't already covered. If an existing pending review task exists for that node, no new task is created. This is actually correct behavior (no duplicate tasks), but it means updated nodes might not get reviewed if a previous review task was already resolved.

3. **No review task for L2 node L1 tag wiring**: The L1 tag wiring (lines 808-822) happens silently without review. This is likely fine since L1 tags are already reviewed separately.

## Overall Verdict

**⚠️ WARN**

The review task creation mechanism is well-implemented for the main generate pipeline. L1 tags, L2 nodes, and noise detection all correctly create review tasks. The resolution handler properly writes back corrections and maintains the correction feedback loop. However, the implementation deviates from the design spec by not creating review tasks for high-confidence L3 nodes (confidence >= 0.8), and the `/extract/sieve` endpoint bypasses review entirely. The task type naming inconsistency (`validate` vs `anchor`) is minor but should be aligned with the design documentation.
