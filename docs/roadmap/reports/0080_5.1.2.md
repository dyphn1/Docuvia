## Round 1 — Architecture & Design Review

### Design vs. Implementation Mismatch

The design documents consistently describe three review task types: **anchor**, **merge**, and **reject**. However, the actual implementation defines four task types: **anchor**, **correct**, **validate**, and **merge**.

**Schema definition** (`lib/db/src/schema/review_tasks.ts`, lines 6–11):
```typescript
export const reviewTaskTypeEnum = pgEnum("review_task_type", [
  "anchor",
  "correct",
  "validate",
  "merge",
]);
```

**OpenAPI spec** (`lib/api-spec/openapi.yaml`, line 2002):
```yaml
enum: [anchor, correct, validate, merge]
```

**Generated Zod types** (`lib/api-zod/src/generated/types/reviewTaskTaskType.ts`):
```typescript
export const ReviewTaskTaskType = {
  anchor: "anchor",
  correct: "correct",
  validate: "validate",
  merge: "merge",
} as const;
```

The value **"reject" does not exist** anywhere as a task type in the implementation. It is not in the PostgreSQL enum, the OpenAPI spec, or the generated types.

### How Task Types Are Actually Used

In the generate pipeline (`artifacts/api-server/src/routes/generate.ts`):

| Task Type | Where Created | Purpose |
|-----------|---------------|---------|
| `anchor` | Line 672 (new L1 tags), Line 330 (noise detection for low-usage tags) | Confirm a new AI-generated tag is accurate |
| `merge` | Line 266 (cross-project similarity), Line 364 (near-duplicate tags) | Consolidate two similar nodes/tags |
| `validate` | Lines 884, 924, 971 (new L2/L3 nodes) | Verify AI-generated node content |

### Resolution Statuses vs. Task Types

The design documents appear to conflate **task types** (the kind of work to do) with **resolution statuses** (the outcome of review). The implementation correctly separates these:

- **Task types** (what to do): `anchor`, `correct`, `validate`, `merge`
- **Resolution statuses** (outcome): `pending`, `approved`, `rejected`, `deferred`

The review route (`review_tasks.ts`, line 109) uses a `PATCH /review-tasks/:id` endpoint that accepts `status` values of `approved`, `rejected`, or `deferred` — these are resolution actions, not task types. The UI (`review.tsx`) provides Approve, Reject, and Defer buttons for this purpose.

### Gaps

1. **"reject" is missing as a task type** — The design spec lists it, but the implementation has no such type. Instead, "reject" exists only as a resolution status.
2. **"correct" and "validate" are not in the design spec** — The implementation has two task types (`correct`, `validate`) that the design documents never mention.
3. **Design docs are internally inconsistent** — They describe the review workflow as "anchor, merge, reject" but the actual system uses a richer type system.

## Round 2 — Code Quality & Security Review

### Code Quality

1. **Schema definition is clean and well-structured.** The `review_tasks.ts` schema file (37 lines) uses Drizzle ORM best practices with `pgEnum` for type safety and `createInsertSchema` for Zod validation.

2. **Route handler is well-organized.** The `review_tasks.ts` route file (199 lines) follows the project's defensive design pattern with early returns (line 121: `if (!task) return res.status(404)...`).

3. **Type safety is maintained end-to-end.** The enum is defined in Drizzle, propagated to PostgreSQL, exposed in OpenAPI, and consumed via generated Zod types. No hand-written type definitions for API shapes.

4. **The `any` cast on line 115** (`status: body.status as any`) is a minor code smell — it bypasses Drizzle's type checking. However, this is mitigated by the Zod validation on the request body (`ResolveReviewTaskBody`).

5. **The review route uses PATCH, not POST for resolve.** The checklist item 5.1.3 references `POST /review_tasks/:id/resolve`, but the actual implementation uses `PATCH /review-tasks/:id`. This is a separate concern (item 5.1.3) but worth noting.

### Security

1. **Zod validation is applied** to both params (`ResolveReviewTaskParams`) and body (`ResolveReviewTaskBody`) in the resolve endpoint.
2. **No SQL injection risk** — all queries use Drizzle ORM parameterized queries.
3. **No authentication/authorization** on the review endpoints — this is a pre-existing concern noted in items 9.1.4 and 9.1.5.

## Round 3 — Integration & Completeness Review

### Integration

3. **No tests** specifically verify the review task type enum values or the task creation logic in the generate pipeline. The test coverage for this area is addressed in items 9.4.x.

## Recommendations

1. **Update design documents** to reflect the actual task type enum: `anchor`, `correct`, `validate`, `merge`.
2. **Either implement `correct` task type usage** in the generate pipeline or remove it from the enum to avoid confusion.
3. **Clarify in the glossary** that "reject" is a resolution status, not a task type.

---

## Overall Verdict

# ⚠️ WARN

The review task type system is **implemented and functional** with four types (anchor, correct, validate, merge), but there is a **significant mismatch** between the design specification (which describes three types: anchor, merge, reject) and the actual implementation. The design docs conflate task types with resolution statuses. Additionally, the `correct` task type is defined but never used in the codebase.
