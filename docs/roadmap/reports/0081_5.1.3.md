## Design Spec Summary

ADR-006 defines the Human-in-the-Loop review queue. The resolution endpoint is the critical path through which AI-generated knowledge graph nodes are approved, corrected, or rejected by human reviewers. The design requires:

1. **Resolution action**: Accept `approved`, `rejected`, or `deferred` statuses
2. **Correction writeback**: When a reviewer provides a `correctedValue`, write it back to the actual node (L1 tag description, L2 node description, or L3 node content)
3. **Correction examples**: Store original + corrected content in `correction_examples` table for the feedback loop (few-shot injection in future pipeline runs)
4. **Activity logging**: Record the resolution in the `activity_log` table
5. **Node state update**: Clear `needsReview` flag on L2 nodes after resolution

The checklist references the endpoint as `POST /review_tasks/:id/resolve`.

## Round 1 — Architecture & Design Review

### What the design requires

1. A resolution endpoint supporting `approved`, `rejected`, and `deferred` statuses
2. Optional `correctedValue` for human corrections
3. Writeback of corrected values to the actual entity (L1/L2/L3)
4. Correction example storage for the feedback loop
5. Activity log entry on resolution
6. Node state cleanup (clear `needsReview`)

### What the implementation provides

**Endpoint — ✅ Implemented (with path deviation):**
```typescript
// review_tasks.ts line 109
router.patch("/review-tasks/:id", async (req, res) => {
```
The implementation uses `PATCH /review-tasks/:id` rather than `POST /review_tasks/:id/resolve`. The OpenAPI spec documents it as `PATCH /review-tasks/{id}` with operationId `resolveReviewTask`. The functional behavior is identical — it resolves a review task. The path difference is a minor deviation from the checklist text but is architecturally sound (PATCH is the correct HTTP method for partial resource updates).

**Zod validation — ✅ Params and body validated:**
```typescript

```
The `ResolveReviewTaskParams` schema validates `id` as a coerced number. The `ResolveReviewTaskBody` schema accepts:
- `status`: enum `["approved", "rejected", "deferred"]` (required)
- `correctedValue`: optional string

**Status update with resolvedAt — ✅:**

### Gaps identified

1. **Path/method deviation from checklist.** The checklist says `POST /review_tasks/:id/resolve` but the implementation uses `PATCH /review-tasks/:id`. The OpenAPI spec and frontend code are consistent with the implementation. The checklist text is outdated.

2. **No correction example storage for L1 tags.** When an L1 tag is corrected, the description is updated (line 176) but no row is inserted into `correction_examples`. L2 and L3 nodes both create correction examples. This means L1 corrections don't contribute to the feedback loop / few-shot improvement mechanism.

3. **No authorization check.** The endpoint does not verify that the caller has permission to resolve review tasks. Any authenticated (or unauthenticated) caller can resolve any task by ID.

4. **No idempotency guard.** If a task is already resolved (status != "pending"), the endpoint will overwrite the status and resolvedAt timestamp without warning. A second call with "approved" on an already "rejected" task would silently change the outcome.

## Round 2 — Code Quality & Security Review

### Code Quality

1. **`as any` cast on status (line 115).** `body.status as any` bypasses Drizzle's type checking. This is mitigated by the Zod validation on the request body, but a type-safe alternative would be preferable:
   ```typescript
   status: body.status as typeof reviewTasksTable.$inferSelect.status
   ```

2. **Single `correctedValue` field for all entity types.** For L2 nodes, this writes to `description` (not `name`). For L3 nodes, it writes to `content`. The field name `correctedValue` is generic and doesn't convey what it corrects. A structured correction object would be more precise but would require API changes.

3. **Defensive null checks are present.** The code checks `if (node && node.description)` before inserting correction examples (line 130), and `if (node)` before L3 correction example insert (line 152). The 404 check on line 121 handles missing tasks.

4. **Consistent error handling pattern.** The endpoint uses early return for 404 and Zod's `.parse()` throws on invalid input (handled by Express error middleware).

### Security

1. **No authorization middleware.** The `PATCH /review-tasks/:id` endpoint has no auth check. In a multi-tenant deployment, any user could resolve any project's review tasks. This is a **Medium** severity concern — the checklist marks this item as Done, so auth may be handled at a higher middleware layer, but no such middleware is visible in the route file or the router registration.

2. **No input length validation on `correctedValue`.** The Zod schema defines `correctedValue` as `zod.string().optional()` with no max length. A malicious caller could submit arbitrarily large values. The database `text` column has no practical limit, but application-level validation would be prudent.

3. **IDOR (Insecure Direct Object Reference).** The endpoint takes a numeric `id` path parameter and operates on it directly without checking project ownership or user permissions.

## Round 3 — Integration & Completeness Review

### Integration Points

1. **Frontend → API integration — ✅ Working.** The `review.tsx` page uses `useResolveReviewTask()` (generated by Orval from the OpenAPI spec) and calls it with `{ id, data: { status, correctedValue } }`. On success, it invalidates both the task list and stats queries. The frontend correctly maps to the `PATCH /review-tasks/{id}` endpoint.

2. **API → Database — ✅ Working.** The endpoint correctly uses Drizzle ORM for all DB operations. The `review_tasks` table has all required columns (`status`, `correctedValue`, `resolvedAt`). The `correction_examples` table stores the feedback loop data. The `activity_log` table records the audit trail.

3. **OpenAPI → Codegen → Frontend — ✅ Consistent.** The OpenAPI spec defines the `ReviewResolution` schema with `status` (required enum) and `correctedValue` (optional string). The generated Zod schemas and React Query hooks are consistent with the implementation.

4. **Route registration — ✅.** The `reviewTasksRouter` is imported and mounted in `routes/index.ts` (line 33).

### Missing Pieces

1. **No tests for the resolve endpoint.** There are no unit or integration tests verifying:
   - Successful resolution with each status (approved, rejected, deferred)
   - Correction writeback to L2 and L3 nodes
   - Correction example creation
   - Activity log entry creation
   - 404 response for non-existent task
   - Zod validation rejection of invalid statuses
   - Idempotency behavior (or lack thereof)

2. **No backfill for L1 correction examples.** As noted in Round 1, L1 tag corrections don't create `correction_examples` rows. This is a data completeness gap in the feedback loop.

3. **No notification on resolution.** The `generate.ts` pipeline dispatches notifications for new L3 nodes (line 1000-1005), but the resolve endpoint does not dispatch notifications when tasks are resolved. This means external integrations (Slack/Teams) won't be notified of review outcomes.

### Recommendations

1. **Update the checklist text** to reflect the actual endpoint: `PATCH /review-tasks/:id` instead of `POST /review_tasks/:id/resolve`.

2. **Add correction example storage for L1 tags** (Low effort, completes the feedback loop):
   ```typescript
   } else if (task.entityType === "l1_tag") {
     const [tag] = await db.select().from(l1TagsTable).where(eq(l1TagsTable.id, task.entityId));
     if (tag && tag.description) {
       await db.insert(correctionExamplesTable).values({
         projectId: null, // L1 tags are global
         entityType: "l1_tag",
         entityId: task.entityId,
         originalContent: tag.description,
         correctedContent: body.correctedValue,
       });
     }
     await db.update(l1TagsTable).set({ description: body.correctedValue }).where(eq(l1TagsTable.id, task.entityId));
   }
   ```

3. **Add idempotency guard** to prevent re-resolution of already-resolved tasks:
   ```typescript
   const [existingTask] = await db.select().from(reviewTasksTable).where(eq(reviewTasksTable.id, id));
   if (!existingTask) return res.status(404).json({ error: "Not found" });
   if (existingTask.resolvedAt) return res.status(409).json({ error: "Task already resolved" });
   ```

4. **Add authorization middleware** to the review tasks router if not handled at a higher level.

5. **Add integration tests** for the resolve endpoint covering all three statuses, correction writeback, and error cases.

## Verdict

**✅ PASS**

The review resolution endpoint is fully implemented and functional. It correctly handles all three resolution statuses (approved, rejected, deferred), writes corrected values back to L1/L2/L3 nodes, creates correction examples for L2 and L3, logs activity, and clears the `needsReview` flag. The OpenAPI spec, Zod validators, and frontend code are all consistent. The endpoint path (`PATCH /review-tasks/:id`) is architecturally sound and differs from the checklist text (`POST /review_tasks/:id/resolve`) — the checklist should be updated to match. The identified gaps (no L1 correction examples, no auth check, no idempotency guard, no tests) are improvement opportunities but do not prevent the feature from working as designed.
