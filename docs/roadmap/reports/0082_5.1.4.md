## Design Spec Summary

ADR-006 defines the Human-in-the-Loop review queue. The key feedback loop requirement (line 142):

> "Approved corrections are stored in `correction_examples` and injected as few-shot prompts in subsequent pipeline runs, creating a continuous improvement loop."

The checklist item 5.1.4 specifically requires that correction examples are created when a review task is approved.

---

## Round 1 — Architecture & Design Review

### What the design requires

1. When a reviewer approves a correction (provides a `correctedValue`), the original and corrected content must be stored in the `correction_examples` table.
2. These correction examples must be injected as few-shot prompts in subsequent generate pipeline runs.
3. The feedback loop should cover all entity types: L1 tags, L2 nodes, and L3 nodes.

### What the implementation provides

**Correction example creation is gated by two conditions** (review_tasks.ts line 124):
```typescript
if (body.correctedValue && task.status === "approved") {
```
This means correction examples are only created when:
- The reviewer provides a `correctedValue` (not null/undefined), AND
- The status is `"approved"`

**L2 nodes — ✅ Correction example created** (lines 125–146):
```typescript
if (task.entityType === "l2_node") {
  const [node] = await db.select().from(l2NodesTable).where(eq(l2NodesTable.id, task.entityId));
  if (node && node.description) {
    await db.insert(correctionExamplesTable).values({
      projectId: node.projectId,
      entityType: "l2_node",
      entityId: task.entityId,
      originalContent: node.description,
      correctedContent: body.correctedValue,
    });
  }
  // ... update node description, needsReview, aiGenerated
}
```
Stores `projectId`, `entityType`, `entityId`, `originalContent`, and `correctedContent`. The node is also updated with the corrected description.

**L3 nodes — ✅ Correction example created** (lines 147–172):
```typescript
} else if (task.entityType === "l3_node") {
  const [node] = await db.select().from(l3NodesTable).where(eq(l3NodesTable.id, task.entityId));
  if (node) {
    const [l2] = await db.select().from(l2NodesTable).where(eq(l2NodesTable.id, node.l2NodeId));
    if (node.content) {
      await db.insert(correctionExamplesTable).values({
        projectId: l2?.projectId ?? null,
        entityType: "l3_node",
        entityId: task.entityId,
        originalContent: node.content,
        correctedContent: body.correctedValue,
      });
    }
  }
  // ... update node content
}
```
Stores the correction example with the L2-derived `projectId`. The node content is updated.

**L1 tags — ❌ No correction example created** (lines 173–179):
```typescript
} else if (task.entityType === "l1_tag") {
  await db
    .update(l1TagsTable)
    .set({ description: body.correctedValue })
    .where(eq(l1TagsTable.id, task.entityId));
}
```
The L1 tag description is updated, but **no row is inserted into `correction_examples`**. This means L1 corrections are lost to the feedback loop — they don't contribute to few-shot improvement.

### Few-shot injection in generate pipeline

**L2 corrections — ✅ Injected** (generate.ts lines 696, 201):
```typescript
const corrections = await getRecentCorrections(projectId, "l2_node");
// ...
const fewShotSection = buildFewShotSection(corrections);
```
L2 correction examples are fetched (up to 5, ordered by most recent) and injected into the L2 extractor system prompt.

**L3 corrections — ❌ Not injected** (generate.ts):
The `getRecentCorrections` function accepts `"l3_node"` as a valid `entityType` parameter (line 64), but the generate route never calls it for L3. Only `getRecentCorrections(projectId, "l2_node")` is called at line 696. L3 correction examples are stored but never retrieved for few-shot injection.

### Gaps identified

1. **L1 tags: No correction example storage.** L1 corrections update the tag but don't create `correction_examples` rows.
2. **L3 corrections: Stored but not used for few-shot.** The generate pipeline only fetches L2 corrections. L3 correction examples are written to the DB but never read back.
3. **Correction examples only created for "approved" + correctedValue.** If a task is approved without a `correctedValue`, or if the status is "rejected" or "deferred", no correction example is created. This is reasonable for "rejected" (no correction to learn from) but "approved without correctedValue" could still store an implicit "original was correct" example.
4. **No `processedAt` timestamp set.** The `correction_examples` table has a `processedAt` column, but it's never set during creation. This column likely exists for the async metabolism pipeline to mark when a correction has been distilled into prompt templates, but it's left null.

## Round 2 — Code Quality & Security Review

### Code Quality

1. **Defensive null checks are present.** The code checks `if (node && node.description)` before inserting L2 correction examples (line 130), and `if (node)` before L3 correction example insert (line 152). This prevents crashes when the referenced entity has been deleted.

2. **Consistent pattern for L2 and L3.** Both L2 and L3 follow the same pattern: read current content → insert correction example → update entity. The L1 path breaks this pattern by skipping the correction example insert.

3. **`projectId` derivation for L3 is indirect.** For L3 correction examples, the `projectId` is derived from the parent L2 node (`l2?.projectId ?? null`). This could be null if the L2 node was deleted between the review task creation and resolution. A more robust approach would store `projectId` directly on the `review_tasks` table.

4. **No transaction wrapping.** The correction example insert and the entity update are not wrapped in a database transaction. If the entity update fails after the correction example is inserted, the correction example would exist without the corresponding entity update. This is a minor consistency risk.

5. **`correctedValue` guard is appropriate.** The `if (body.correctedValue)` check prevents inserting correction examples with empty/null corrected content. However, it also means that a simple "approve without changes" (no `correctedValue`) doesn't create a correction example — which is arguably correct behavior (there's nothing to learn from an unchanged approval).

### Security

1. **No authorization check.** The resolve endpoint (and by extension, correction example creation) has no auth check. Any caller can resolve tasks and create correction examples.

2. **No input length validation on `correctedValue`.** The Zod schema defines `correctedValue` as `zod.string().optional()` with no max length. The `correction_examples` table uses `text` columns which have no practical limit, but application-level validation would be prudent.

3. **No idempotency guard.** Re-resolving an already-resolved task will create duplicate correction examples if a `correctedValue` is provided again.

## Round 3 — Integration & Completeness Review

### Integration Points

1. **Review resolution → Correction example → Generate pipeline.** The core feedback loop works for L2 nodes: resolve creates correction example → generate fetches corrections → few-shot injected into LLM prompt. This is the primary feedback path and it functions correctly.

2. **Schema completeness.** The `correction_examples` table has all required columns: `projectId`, `entityType`, `entityId`, `originalContent`, `correctedContent`, `createdAt`, `processedAt`. The schema supports the full feedback loop.

3. **Frontend integration.** The review UI (`review.tsx`) sends `correctedValue` in the resolve request body, which triggers the server-side correction example creation. The frontend doesn't need to know about correction examples — it's a server-side concern.

### Missing Pieces

1. **L1 correction examples not stored.** When a reviewer corrects an L1 tag description, the correction is applied but not recorded in `correction_examples`. This means:
   - L1 corrections don't contribute to the feedback loop
   - There's no audit trail of what was changed and when
   - The async metabolism pipeline can't distill L1 corrections into prompt template improvements

2. **L3 correction examples not used for few-shot.** L3 corrections are stored but never fetched by the generate pipeline. The `getRecentCorrections` function supports `entityType: "l3_node"` but is never called with that type. This means L3 corrections are dead data — written but never read.

3. **No tests for correction example creation.** There are no unit or integration tests verifying:
   - Correction example creation on L2 approval with correctedValue
   - Correction example creation on L3 approval with correctedValue
   - Absence of correction example for L1 (or testing that it should be created)
   - Absence of correction example when status is "rejected"
   - Absence of correction example when correctedValue is not provided
   - Few-shot injection of corrections in the generate pipeline

4. **`processedAt` column never populated.** The `correction_examples.processedAt` column exists in the schema but is never set. The async metabolism pipeline (ADR-008) is supposed to distill corrections into prompt templates and mark them as processed, but this distillation logic is not implemented (item 1.4.1 is WIP).

## Findings

| # | Severity | Finding |
|---|----------|---------|
| 1 | **Medium** | L1 tag corrections don't create `correction_examples` rows. L1 corrections are applied but not recorded in the feedback loop. |
| 2 | **Medium** | L3 correction examples are stored but never fetched for few-shot injection in the generate pipeline. The `getRecentCorrections(projectId, "l3_node")` call is never made. |
| 3 | **Low** | Correction examples are only created when `status === "approved"` AND `correctedValue` is provided. Approvals without corrections and rejections don't create examples. This is mostly reasonable but could be more flexible. |
| 4 | **Low** | `correction_examples.processedAt` is never set. The async metabolism pipeline that should populate this is not yet implemented. |
| 5 | **Low** | No transaction wrapping between correction example insert and entity update. Minor consistency risk. |
| 6 | **Info** | No tests for correction example creation logic. |
| 7 | **Info** | L3 correction example `projectId` is derived from parent L2 node and could be null if L2 was deleted. |

### Recommendations

1. **Add L1 correction example storage** (completes the feedback loop for all entity types):
   ```typescript
   } else if (task.entityType === "l1_tag") {
     const [tag] = await db.select().from(l1TagsTable).where(eq(l1TagsTable.id, task.entityId));
     if (tag && tag.description) {
       await db.insert(correctionExamplesTable).values({
         projectId: null, // L1 tags are global, not project-specific
         entityType: "l1_tag",
         entityId: task.entityId,
         originalContent: tag.description,
         correctedContent: body.correctedValue,
       });
     }
     await db.update(l1TagsTable).set({ description: body.correctedValue }).where(eq(l1TagsTable.id, task.entityId));
   }
   ```

2. **Fetch and inject L3 corrections in the generate pipeline** (completes the L3 feedback loop):
   ```typescript
   // In generate.ts, alongside the L2 corrections fetch:
   const l3Corrections = await getRecentCorrections(projectId, "l3_node");
   // Inject into L3 generator prompt alongside L2 corrections
   ```

3. **Add integration tests** for correction example creation covering all entity types and edge cases.

4. **Consider wrapping correction example insert + entity update in a transaction** for consistency.

## Verdict

**⚠️ WARN**

Correction examples are created for L2 and L3 node review approvals with a `correctedValue`, and L2 corrections are successfully injected as few-shot prompts in subsequent generate runs. The core feedback loop works for the primary use case (L2 nodes).

However, there are two significant gaps:
1. **L1 tag corrections don't create correction examples** — the L1 update path (review_tasks.ts lines 173–179) only updates the tag description without storing the correction.
2. **L3 correction examples are stored but never used** — the generate pipeline only fetches L2 corrections for few-shot injection, leaving L3 corrections as dead data.

Additionally, the `processedAt` column is never populated (the async metabolism pipeline is not yet implemented), and there are no tests for the correction example creation logic.
