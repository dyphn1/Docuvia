# Verification Report: Item 4.3.7 — Schema: branchName Column on Commits

**Date:** 2026-06-12
**Item ID:** 4.3.7
**Description:** Schema: branchName column on commits
**Design Spec:** ADR-011 (Two-Phase Knowledge Validity), `docs/design/09-architectural-decisions.md` lines 269–298; ADR-004 (Git-Isomorphic Graph)
**Verdict:** ⚠️ WARN

---

## Design Spec References

- **ADR-011 (Two-Phase Knowledge Validity):** Requires `commits` table to have a `branchName text` column to support Phase 2 (Merge Gate) validity tracking. The server must know which branch each commit belongs to in order to determine whether commits have been merged into the main branch.
- **ADR-004 (Git-Isomorphic Graph):** Describes the temporal alignment architecture and the need to track which branch commits belong to for baseline inheritance and delta projection.
- **`docs/ai_plans/implement_v2-core-architecture.md`:** Explicitly lists `branchName` as a column to ADD to the `commits` table.

## Round 1 — Architecture & Design Review

### What the design requires

Per ADR-011 (lines 296–298 of `09-architectural-decisions.md`):
> ⚠️ `commits` table requires `branchName text` column

The intent is that the server tracks which branch each commit was pushed from, enabling Phase 2 (Merge Gate) logic: if the branch is merged into main, commits and their associated L3 nodes become `valid`; if the branch is deleted without merging, they become `orphaned`.

### What the implementation provides

**✅ Schema column exists** — `lib/db/src/schema/commits.ts` line 22:
```typescript
branchName: text("branch_name"),
```
The column is nullable (no `.notNull()`), which is correct for incremental rollout — pre-existing commits won't have a branch name until populated.

**✅ Column also exists in SQL migration** — `lib/db/drizzle/0000_short_ezekiel.sql` line 102:
```sql
"branch_name" text,
```

**✅ Git client supports branch name retrieval** — `git-client.ts` lines 92–103:
```typescript
async getCurrentBranchName(): Promise<string | undefined> {
  // Uses `git rev-parse --abbrev-ref HEAD`
  // Returns undefined for detached HEAD state
}
```

**✅ GitCommitData interface includes branchName** — `git-client.ts` line 17:
```typescript
export interface GitCommitData {
  sha: string;
  message: string;
  author: string;
  date: string;
  diff?: string;
  branchName?: string;
}
```

**✅ Sync route populates branchName** — `sync.ts` lines 117–127:
```typescript
await db
  .update(commitsTable)
  .set({ branchName: pushedBranch })
  .where(
    and(
      eq(commitsTable.projectId, projectId),
      inArray(commitsTable.hash, pushedCommits)
    )
  );
```
This is scoped to matching commit hashes within the project, preventing cross-project contamination.

**❌ Ingestion pipeline does NOT populate branchName** — `ingestion-pipeline.ts` lines 79–86:
```typescript
await db.insert(commitsTable).values({
  projectId,
  hash: c.sha,
  message: c.message.slice(4000),
  author: c.author ?? "Unknown",
  valid: score >= 0.4,
  vcsType: "git",
  // ← branchName is NEVER set
});
```

**❌ GitCommitItem interface lacks branchName** — `ingestion-pipeline.ts` lines 23–29:
```typescript
export interface GitCommitItem {
  sha: string;
  message: string;
  author: string;
  date?: string;
  diff?: string;
  // ← branchName is MISSING from the interface
}
```

**❌ Ingest route doesn't capture branch name** — `ingest.ts` lines 48–69: After cloning the repo and getting commits, the route never calls `client.getCurrentBranchName()` and never includes `branchName` when constructing `GitCommitItem` objects.

### Round 1 Summary

The `branchName` column is defined in the schema and the infrastructure to populate it exists (`getCurrentBranchName()`, sync route updates). However, the **primary ingestion path** (server-side git clone → `processIngestion()`) never captures or stores the branch name. The column is only populated when the VS Code client explicitly pushes commits via the `/sync` endpoint with a `pushedBranch` field. For server-side ingestion (the initial setup path), `branchName` will always be `NULL`.

## Round 2 — Code Quality & Security Review

### Code Quality

**✅ Sound schema design:** The column is nullable `text("branch_name")` with no constraints that would break existing data. This is appropriate for incremental rollout — existing rows remain `NULL` until backfilled.

**✅ Sync route is well-implemented:** The sync endpoint correctly updates `branchName` only for matching commit hashes within the project scope.

**✅ Git client handles edge cases:** `getCurrentBranchName()` properly handles detached HEAD state by returning `undefined` when `git rev-parse --abbrev-ref HEAD` returns `"HEAD"`. Try/catch wraps the call and logs warnings.

**⚠️ Inconsistent data population (Medium):** The `branchName` column has two population paths:
1. **Server-side ingestion** (`/projects/:id/ingest/git`): Never sets `branchName` → always `NULL`
2. **Client-side sync** (`/sync`): Sets `branchName` from client-provided `pushedBranch`

This means `branchName` is `NULL` for all server-side ingested commits, which is the primary ingestion path for initial project setup. Only commits pushed through the VS Code client's sync flow get their branch recorded.

**⚠️ No validation of branch name format (Low):** Neither the ingest pipeline nor the sync route validates the branch name format. This is low-risk because data comes from git itself or the VS Code client (trusted sources), and PostgreSQL `text` type has no format constraints.

**⚠️ OpenAPI spec doesn't include branchName (Low):** The `openapi.yaml` spec does not include `branchName` in the commit schema. Generated API types (via Orval) won't expose this field to API consumers.

### Security

No security vulnerabilities specific to this feature. The `branchName` column is populated from trusted sources (git client or VS Code extension) and is not user-writable via any direct API endpoint parameter for the ingestion path.

## Round 3 — Integration & Completeness Review

### Integration Points

**✅ Sync integration works end-to-end:** The `/sync` endpoint correctly receives `pushedBranch` from the client, updates the commits table, checks if it's a main branch, and cascades validity status for L3 nodes. This path is complete.

**✅ Validity status cascade:** The sync endpoint uses `branchName` (via the `pushedBranch` parameter) to determine whether to promote commits and L3 nodes to `valid`. This correctly implements ADR-011 Phase 2 for the sync path.

**⚠️ Feature is partially implemented (WIP):**
- For projects using **only server-side ingestion** (no VS Code client), `branchName` will always be `NULL`, making Phase 2 merge-gate logic inoperable for those commits.
- For projects using **VS Code client with `/sync`**, `branchName` is set for synced commits but remains `NULL` for any server-side ingested commits (e.g., historical backfill).

**⚠️ No tests for branchName population:** There are no unit or integration tests verifying:
- That `branchName` is populated during ingestion
- That `branchName` is correctly set during sync
- That `getCurrentBranchName()` returns the correct value

**⚠️ Frontend doesn't display branchName:** The `kg-engine` frontend doesn't reference `branchName` in any commit display components. The column is stored but never shown to users. This is acceptable for v1 (it's an internal tracking field) but may be needed in future UI.

**⚠️ No migration needed:** Since the column is already nullable and added to the schema, no migration is required. However, existing data will have `NULL` for `branchName` until the sync route or a backfill process populates it.

**⚠️ Orphan branch writer:** `orphan-branch-writer.ts` doesn't reference `branchName` on commits. The orphan branch stores knowledge as files keyed by L3 node, so commit branch info is not reflected in the orphan branch output.

## Findings

| # | Severity | Finding |
|---|----------|---------|
| 1 | **Medium** | Server-side ingestion pipeline does not populate `branchName`. The `GitCommitItem` interface lacks the field, and `ingest.ts` never calls `getCurrentBranchName()`. All server-side ingested commits will have `NULL` branch names. |
| 2 | **Low** | OpenAPI spec does not include `branchName` in the commit schema. Generated API types won't expose this field. |
| 3 | **Info** | No tests for `branchName` population during either ingestion or sync. |
| 4 | **Info** | Frontend doesn't display `branchName` (acceptable for v1 — internal tracking field). |
| 5 | **Info** | Nullable column means existing data has `NULL` until backfilled. No data migration concern. |

### Recommendations

1. **Fix the ingestion pipeline (Priority: Medium):**
   - Add `branchName?: string` to the `GitCommitItem` interface in `ingestion-pipeline.ts`
   - In `ingest.ts`, call `client.getCurrentBranchName()` after cloning and include it in each `GitCommitItem`
   - Pass `branchName` through in the `db.insert(commitsTable).values()` call

2. **Add branchName to OpenAPI spec (Priority: Low):**
   - Include `branchName` in the commit schema in `openapi.yaml`
   - Run Orval codegen to update the API types

3. **Add tests (Priority: Low):**
   - Unit test: verify `getCurrentBranchName()` returns correct branch and handles detached HEAD
   - Integration test: verify `branchName` is populated during server-side git ingestion
   - Integration test: verify `branchName` is set during sync endpoint call

4. **Consider backfill (Priority: Low):**
   - For existing ingested commits, a backfill script could parse `git log --all` to populate `branchName` from reflog data, though this is complex and may not be reliable.

## Overall Verdict

**⚠️ WARN** — The `branchName` column is correctly defined in the Drizzle schema (`commits.ts:22`), exists in the SQL migration (`0000_short_ezekiel.sql:102`), and the sync route (`sync.ts:119-127`) correctly populates it when the VS Code client pushes commits. The infrastructure (`getCurrentBranchName()` in `git-client.ts:92-103`, `branchName` in `GitCommitData` interface) is in place.

However, the **server-side ingestion path** — which is the primary initial setup flow — does not capture or store the branch name. The `GitCommitItem` interface (`ingestion-pipeline.ts:23-29`) lacks the `branchName` field, and `ingest.ts` never calls `getCurrentBranchName()`. This means for projects ingested via the server (the `/projects/:id/ingest/git` endpoint), `branchName` will always be `NULL`, making ADR-011 Phase 2 merge-gate logic inoperable for those commits.

The feature is partially implemented (schema ✅, sync path ✅, ingestion path ❌), which matches the checklist's ⚠️ WIP designation.
