# Verification Report: Item 4.3.7 — Schema: branchName Column on Commits

**Date:** 2026-06-12
**Item ID:** 4.3.7
**Description:** Schema: branchName column on commits
**Verdict:** ⚠️ WARN

---

## Design Spec References

- **ADR-011 (Two-Phase Knowledge Validity):** Requires `commits` table to have a `branchName text` column to support Phase 2 (Merge Gate) validity tracking. The server must know which branch each commit belongs to in order to determine whether commits have been merged into the main branch.
- **`docs/ai_plans/implement_v2-core-architecture.md`:** Explicitly lists `branchName` as a column to ADD to the `commits` table.

## Round 1 — Architecture & Design Review

### ✅ Schema column is correctly defined

The Drizzle schema at `commits.ts:22` defines:
```typescript
branchName: text("branch_name"),
```
This is a nullable `text` column with no `NOT NULL` constraint, which is appropriate for incremental rollout — existing rows remain `NULL` until backfilled. The SQL migration at `0000_short_ezekiel.sql:102` confirms:
```sql
"branch_name" text,
```
The Drizzle snapshot at `meta/0000_snapshot.json:638` also tracks the column. The schema definition is complete and correct.

### ✅ GitCommitData interface includes branchName

`git-client.ts:17`:
```typescript
export interface GitCommitData {
  sha: string;
  message: string;
  author: string;
  date: string;
  diff?: string;
  branchName?: string;
}
```

### ✅ getCurrentBranchName() infrastructure exists

`git-client.ts:92-103`: The `LocalGitClient` class has a `getCurrentBranchName()` method that calls `git rev-parse --abbrev-ref HEAD` and returns the branch name or `undefined`. This infrastructure is ready to be used.

### ✅ Sync route correctly populates branchName

`sync.ts:117-127`:
```typescript
// 2. Update commits.branchName for pushed commits
if (pushedCommits.length > 0) {
  await db
    .update(commitsTable)
    .set({ branchName: pushedBranch })
    .where(
      and(
        eq(commitsTable.projectId, projectId),
        inArray(commitsTable.hash, pushedCommits)
      )
    );
```
The sync endpoint correctly updates `branchName` for matching commit hashes within the project scope. It also correctly cascades validity promotion when `pushedBranch` is a main branch (lines 130-204).

### ❌ GitCommitItem interface lacks branchName

`ingestion-pipeline.ts:23-29`:
```typescript
export interface GitCommitItem {
  sha: string;
  message: string;
  author: string;
  date?: string;
  diff?: string;
}
```
The `branchName` field is **missing** from this interface. This is the type used by the server-side ingestion pipeline, so even though `GitCommitData` has `branchName`, it is lost when items are cast/passed as `GitCommitItem`.

### ❌ Server-side ingestion does not populate branchName

`ingest.ts:58-69`: The git ingest route spreads commit data into `GitCommitItem` objects:
```typescript
for (const c of commits) {
  const diff = await client.getDiff(c.sha);
  gitItems.push({
    ...c,   // ← c.branchName exists on GitCommitData but GitCommitItem discards it
    diff,
  });
}
```
Even though `c` (a `GitCommitData`) may have `branchName`, the `GitCommitItem` type doesn't include it, so TypeScript's structural typing will still carry the field at runtime. **However**, the `processIngestion()` function at `ingestion-pipeline.ts:79-86` never includes `branchName` in the insert:
```typescript
await db.insert(commitsTable).values({
  projectId,
  hash: c.sha,
  message: c.message.slice(0, 4000),
  author: c.author ?? "Unknown",
  valid: score >= 0.4,
  vcsType: "git",
  // ← branchName is NEVER set
});
```

### ❌ Ingest route doesn't capture branch name

`ingest.ts:48-69`: After cloning the repo and getting commits, the route never calls `client.getCurrentBranchName()` and never includes `branchName` when constructing `GitCommitItem` objects. The route does have access to `body.branch` (the branch that was cloned, defaulting to `"main"`), but this value is never passed through to the commit records.

### ❌ OpenAPI spec doesn't include branchName

`openapi.yaml:2003-2025` — The `Commit` schema does not include `branchName`:
```yaml
Commit:
  type: object
  required: [id, projectId, hash, message, author, valid, createdAt]
  properties:
    id: { type: integer }
    projectId: { type: integer }
    hash: { type: string }
    message: { type: string }
    author: { type: string }
    valid: { type: boolean }
    filterScore: { type: ["number", "null"] }
    l2NodeId: { type: ["integer", "null"] }
    createdAt: { type: string }
```
Generated API types (via Orval) won't expose this field to API consumers.

## Round 2 — Code Quality & Security Review

### ✅ Sound schema design

The column is nullable `text("branch_name")` with no constraints that would break existing data. This is appropriate for incremental rollout.

### ✅ Sync route is well-implemented

The sync endpoint correctly updates `branchName` only for matching commit hashes within the project scope. The main branch detection (`isMainBranch()`) and validity cascade logic are clean and correct.

### ⚠️ Inconsistent data population (Medium)

The `branchName` column has two population paths:
1. **Server-side ingestion** (`/projects/:id/ingest/git`): Never sets `branchName` → always `NULL`
2. **Client-side sync** (`/sync`): Sets `branchName` from client-provided `pushedBranch`

This means `branchName` is `NULL` for all server-side ingested commits, which is the primary ingestion path for initial project setup. Only commits pushed through the VS Code client's sync flow get their branch recorded.

### ⚠️ Orphan branch writer doesn't reference branchName

`orphan-branch-writer.ts` doesn't reference `branchName` on commits. The orphan branch stores knowledge as files keyed by L3 node, so commit branch info is not reflected in the orphan branch output. This is acceptable since branchName is primarily used for merge-gate logic, not knowledge storage.

### ✅ No security vulnerabilities

The `branchName` column is populated from trusted sources (git client or VS Code extension) and is not user-writable via any direct API endpoint parameter for the ingestion path. The sync route's `pushedBranch` comes from the authenticated VS Code extension.

### ⚠️ No tests for branchName population

There are zero test files referencing `branchName` or `branch_name` across the entire test suite. No unit or integration tests verify:
- That `branchName` is populated during ingestion
- That `branchName` is correctly set during sync
- That the merge-gate logic correctly uses `branchName`

## Round 3 — Integration & Completeness Review

### ✅ Validity status cascade works for sync path

The sync endpoint uses `branchName` (via the `pushedBranch` parameter) to determine whether to promote commits and L3 nodes to `valid`. This correctly implements ADR-011 Phase 2 for the sync path.

### ⚠️ Merge-gate inoperable for server-side ingestion

For projects using **only server-side ingestion** (no VS Code client), `branchName` will always be `NULL`, making Phase 2 merge-gate logic inoperable for those commits. The server cannot determine if commits have been merged without knowing which branch they belong to.

For projects using **VS Code client with `/sync`**, `branchName` is set for synced commits but remains `NULL` for any server-side ingested commits (e.g., historical backfill).

### ⚠️ Frontend doesn't display branchName

The `kg-engine` frontend doesn't reference `branchName` in any commit display components. The column is stored but never shown to users. This is acceptable for v1 (it's an internal tracking field) but may be needed in future UI.

### ⚠️ No migration needed

Since the column is already nullable and added to the schema, no migration is required. However, existing data will have `NULL` for `branchName` until the sync route or a backfill process populates it.

### ⚠️ Orphan branch writer

`orphan-branch-writer.ts` doesn't reference `branchName` on commits. The orphan branch stores knowledge as files keyed by L3 node, so commit branch info is not reflected in the orphan branch output.

## Recommendations

1. **Fix server-side ingestion to populate branchName (Priority: Medium):**
   - Add `branchName?: string` to the `GitCommitItem` interface in `ingestion-pipeline.ts`
   - In `ingest.ts`, call `client.getCurrentBranchName()` after cloning and pass it through, or use `body.branch` as a fallback
   - Pass `branchName` through in the `db.insert(commitsTable).values()` call in `processIngestion()`

2. **Add branchName to OpenAPI spec (Priority: Low):**
   - Include `branchName` in the `Commit` and `CommitInput` schemas in `openapi.yaml`
   - Run `pnpm --filter @workspace/api-spec run codegen` to regenerate types

3. **Add tests (Priority: Low):**
   - Integration test: verify `branchName` is populated during server-side git ingestion
   - Integration test: verify `branchName` is set during sync endpoint call

4. **Backfill strategy (Priority: Low):**
   - For existing ingested commits, a backfill script could parse `git log --all` to populate `branchName` from reflog data, though this is complex and may not be reliable.

## Overall Verdict

**⚠️ WARN** — The `branchName` column is correctly defined in the Drizzle schema (`commits.ts:22`), exists in the SQL migration (`0000_short_ezekiel.sql:102`), and the sync route (`sync.ts:119-127`) correctly populates it when the VS Code client pushes commits. The infrastructure (`getCurrentBranchName()` in `git-client.ts:92-103`, `branchName` in `GitCommitData` interface) is in place.

However, the **server-side ingestion path** — which is the primary initial setup flow — does not capture or store the branch name. The `GitCommitItem` interface (`ingestion-pipeline.ts:23-29`) lacks the `branchName` field, and `ingest.ts` never calls `getCurrentBranchName()` or uses the already-available `body.branch` parameter. This means for projects ingested via the server (the `/projects/:id/ingest/git` endpoint), `branchName` will always be `NULL`, making ADR-011 Phase 2 merge-gate logic inoperable for those commits.
