## Round 1 — Architecture & Design Review

### Design Specification

The design spec (`04-solution-strategy.md`, section 4.4) states:

> 1. **Pipeline output → `review_tasks`**: Every AI-suggested L1 tag, L2 node, and L3 decision record creates a `review_task` row (type: `anchor`).
> 2. **Noise detection → merge/reject tasks**: The pipeline's final step scans for near-duplicate tags and low-usage L1 labels, creating `merge` and `anchor` review tasks automatically.

The glossary (`12-glossary.md`) defines: "Created by the generate pipeline for every AI-generated node."

### Implementation Analysis

The generate pipeline (`artifacts/api-server/src/routes/generate.ts`, `POST /projects/:id/generate`) creates review tasks in the following places:

1. **L1 Tags (lines 669-677)**: Each new AI-generated L1 tag gets an `anchor` review task. ✅ Matches design.

2. **L2 Nodes (lines 1043-1067)**: A post-processing loop queries all L2 nodes with `needsReview=true` and creates `validate` review tasks for any not already covered by a pending review task. ✅ Functionally covers all new L2 nodes, though the task type is `validate` rather than `anchor` as the design specifies.

3. **L3 Nodes (lines 1009-1019)**: Only L3 nodes with `confidence < 0.8` get a `validate` review task. ❌ **Gap**: High-confidence L3 nodes (confidence >= 0.8) do NOT get a review task. This contradicts the design spec which says "every AI-suggested L1 tag, L2 node, and L3 decision record creates a review_task row."

4. **Condensation (lines 970-978)**: When an L3 node's occurrence count reaches the condensation threshold, a `validate` review task is created only if `condensationReviewRequired` is true (default: false). ✅ Reasonable extension.

5. **Noise Detection (lines 307-376)**: The `runNoiseDetection()` function creates `anchor` tasks for low-usage L1 tags (usageCount <= 1) and `merge` tasks for near-duplicate L1 tag names. ✅ Matches design.

6. **Cross-Project Links (lines 232-305)**: The `detectCrossProjectLinks()` function creates `merge` review tasks for L2 nodes with high cosine similarity (>= 0.85) to nodes in other projects. Also creates `notifications` for subscribers and fires external integration notifications. ✅ Reasonable extension beyond the design spec.

7. **Extract/Sieve endpoint (lines 454-517)**: The `POST /projects/:id/extract/sieve` endpoint creates L3 decisions but does NOT create review tasks for them. ❌ **Gap**: This is a separate endpoint from the main generate pipeline, but it still produces AI-generated content that should arguably go through review.

### Findings

- **Gap 1 — High-confidence L3 nodes skip review**: The design says every AI-generated node should create a review task, but the code only creates review tasks for L3 nodes with confidence < 0.8. High-confidence L3 nodes are inserted directly without any review task. This is a deliberate code choice that prioritizes reducing review burden over the design spec's requirement for universal review.
- **Gap 2 — Task type naming inconsistency**: The design specifies type `anchor` for all pipeline output review tasks, but the code uses `validate` for L2 and L3 nodes. The schema does include `validate` as a valid enum value, so this is semantically acceptable but inconsistent with the design document.
- **Gap 3 — Extract/Sieve bypasses review**: The `/extract/sieve` endpoint creates AI-generated decisions without any review tasks.

## Round 2 — Code Quality & Security Review

### Schema Design (`lib/db/src/schema/review_tasks.ts`)

The schema is clean and well-structured:
- Uses PostgreSQL enums for `review_entity_type` (l1_tag, l2_node, l3_node), `review_task_type` (anchor, correct, validate, merge), and `review_status` (pending, approved, rejected, deferred).
- Includes `correctedValue` field for storing human corrections.
- Uses `drizzle-zod` for type-safe insert schema generation.
- Includes timestamps `createdAt` and `resolvedAt`.
- ✅ No issues.

### Generate Route (`artifacts/api-server/src/routes/generate.ts`)

- The `reviewTasksCreated` counter is properly incremented at each creation point and returned in the JSON response (lines 1123-1133).
- The post-processing loop for L2 review tasks (lines 1043-1067) correctly deduplicates by checking existing pending review tasks before creating new ones.
- Error handling: try/catch wraps the entire pipeline; on failure, project status is set to "error" (lines 1134-1140). ✅
- Concurrency guard: Atomic optimistic lock via `UPDATE ... WHERE status IN ('active', 'error')` at lines 539-558 prevents parallel generate runs. ✅

### Review Tasks Route (`artifacts/api-server/src/routes/review_tasks.ts`)

- The `enrichTask()` function (lines 17-66) performs N+1 queries — one query per task to fetch entity details (L1 tag, L2 node, or L3 node). With many pending tasks, this is a performance concern. Consider batch fetching with `IN` clauses.
- The resolution handler (lines 109-197) properly:
  - Validates input with Zod schemas (`ResolveReviewTaskParams`, `ResolveReviewTaskBody`) ✅
  - Writes back corrections to the actual node (L1/L2/L3) ✅
  - Creates `correction_examples` entries for L2 and L3 corrections ✅
  - Logs to `activity_log` ✅
  - Sets `needsReview: false` on L2 nodes after resolution ✅
- ⚠️ **Minor gap**: L3 nodes don't have a `needsReview` flag being cleared in the resolution handler. The L3 schema doesn't appear to have a `needsReview` column, so this is acceptable if L3 nodes don't track that flag, but it means there's no way to mark an L3 node as "reviewed" at the node level.

### Security

- Input validation via Zod on the resolve endpoint. ✅
- No SQL injection risk — uses Drizzle ORM parameterized queries. ✅
- No authentication/authorization checks visible in the route handlers (relies on middleware). ⚠️ This is a cross-cutting concern covered by item 9.1.x.

## Round 3 — Integration & Completeness Review

### OpenAPI Integration

The OpenAPI spec (`lib/api-spec/openapi.yaml`) defines three review-tasks endpoints:
- `GET /review-tasks` — List review tasks
- `GET /review-tasks/stats` — Get review task statistics
- `PATCH /review-tasks/{id}` — Resolve a review task

The generate endpoint's response schema includes `reviewTasksCreated`. ✅

### End-to-End Flow

The complete flow works as follows:
1. Generate pipeline creates AI-generated nodes and review tasks
2. Review tasks appear in the list endpoint
3. Reviewer resolves via PATCH endpoint
4. Resolution writes back corrections and creates `correction_examples`
5. Activity log records the resolution

✅ The flow is complete and functional.

### Missing Pieces

1. **No review task creation for the `/extract/sieve` endpoint** (lines 453-517): The sieve extraction endpoint creates L3 decisions but does NOT create review tasks for them. This is a separate endpoint from the main generate pipeline, but it still produces AI-generated content that should arguably go through review. Furthermore, the decisions returned include a `confidence` score, which could be used to conditionally create review tasks similar to the main pipeline.

2. **No review task for high-confidence L3 nodes** (lines 1009-1019): As noted in Round 1, L3 nodes with confidence >= 0.8 skip review entirely. These nodes are inserted directly into the knowledge graph. If the confidence score is inaccurate, incorrect knowledge could propagate without human oversight.

3. **No `needsReview` flag on L3 schema**: L2 nodes clear `needsReview: false` on resolution (line 184-189), but the L3 schema lacks this column entirely. This means there's no node-level tracking of whether an L3 decision has been reviewed. This could lead to L3 nodes being re-created or duplicated on subsequent generate runs since there's no "reviewed" marker.

4. **N+1 query pattern in `enrichTask()`**: When listing review tasks, each task triggers a separate database query to fetch entity details. For a project with hundreds of pending review tasks, this could cause noticeable latency.

### Path-Rule Mode (Bootstrap-Confirmed)

When all L2 nodes are bootstrap-confirmed (entered via the ADR-010 path-rule flow), the generate pipeline skips the LLM-based L2 extraction entirely (lines 728-821). In this mode:
- Commits are assigned to L2 nodes via deterministic glob matching
- No new L2 nodes are created
- No L3 nodes are created (the L3 loop over `l2Input` at line 847 is never entered since `l2Input` stays empty)
- Consequently, **no review tasks are created** in path-rule mode

This is a design choice worth noting: once a project transitions to deterministic path-rule mode, the AI-generated content pipeline (and its review-tasks-by-default behavior) is effectively bypassed. This may be intentional — the L2 classification is now deterministic and doesn't need review — but it means the review-task creation coverage varies depending on the project's bootstrap state.

## Overall Verdict

**⚠️ WARN**

The review task creation mechanism is well-implemented for the main generate pipeline. L1 tags, L2 nodes, and noise detection all correctly create review tasks. The resolution handler properly writes back corrections and maintains the correction feedback loop. However, the implementation deviates from the design spec by not creating review tasks for high-confidence L3 nodes (confidence >= 0.8), and the `/extract/sieve` endpoint bypasses review entirely. The task type naming inconsistency (`validate` vs `anchor`) is minor but should be aligned with the design documentation. Additionally, L3 nodes lack a `needsReview` tracking column, and in path-rule mode the review task creation path is entirely skipped.

### Recommendations

1. **Create review tasks for all L3 nodes regardless of confidence** — or at minimum, add a project-level configuration (`reviewAllL3: true/false`) that defaults to `true` to match the design spec.
2. **Add review task creation to the `/extract/sieve` endpoint** — at minimum for decisions with confidence below a threshold.
3. **Align task type naming** — update the design doc to reflect `validate` as the type for L2/L3 pipeline output review tasks, or update the code to use `anchor` universally.
4. **Consider adding `needsReview` column to `l3_nodes` schema** — for parity with L2 nodes.
5. **Optimize `enrichTask()`** — batch-fetch entity details using `IN` clauses rather than N+1 queries.
