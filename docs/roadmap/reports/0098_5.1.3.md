## Round 1 — Architecture & Design Review

### Design vs. Implementation Mismatch

The design spec (`06-runtime-scenarios.md`, line 120) describes the resolution endpoint as:
```
POST /review_tasks/:id/resolve { action: "anchor" }
```

The actual implementation uses:
```
PATCH /review-tasks/:id { status: "approved", correctedValue?: string }
```

Specific mismatches:

| Aspect | Design Spec | Implementation |
|--------|-------------|----------------|
| **HTTP method** | `POST` | `PATCH` (review_tasks.ts:109) |
| **URL path** | `/review_tasks/:id/resolve` | `/review-tasks/:id` (review_tasks.ts:109) |
| **Separator** | Snake_case (`review_tasks`) | Kebab-case (`review-tasks`) |
| **Action field name** | `action` | `status` |
| **Action values** | `"anchor"` | `"approved"`, `"rejected"`, `"deferred"` |
| **DB status values** | `"resolved"` | `"pending"`, `"approved"`, `"rejected"`, `"deferred"` |

### Analysis of the Mismatch

The implementation's use of `PATCH` instead of `POST` is semantically more correct. PATCH is the appropriate HTTP method for partial resource updates (changing the status of a review task), whereas POST to a `/resolve` sub-resource is more RPC-like. The OpenAPI spec (`openapi.yaml`, line 902-926) defines `PATCH /review-tasks/{id}` under the `resolveReviewTask` operationId, which generates consistent Zod schemas and React Query hooks.

The resolution status values (`approved`, `rejected`, `deferred`) are more nuanced than the design spec's `anchor`. The design spec conflates task types (anchor, merge, reject) with resolution statuses. The implementation correctly separates these concerns:

- **Task types** (`review_task_type` enum): `anchor`, `correct`, `validate`, `merge` — what kind of work the review task asks the human to do
- **Resolution statuses** (`review_status` enum): `pending`, `approved`, `rejected`, `deferred` — the outcome of the review

The value `"anchor"` from the design spec corresponds most closely to `"approved"` in the implementation. The design spec's runtime scenario also references `{ action: "anchor" }` but the actual code at review_tasks.ts:124 checks for `task.status === "approved"`.

### Functional Completeness

The resolution handler (review_tasks.ts, lines 109-197) is **functionally complete**:

1. ✅ Validates input via Zod schemas (`ResolveReviewTaskParams`, `ResolveReviewTaskBody`)
2. ✅ Updates the review task row (status, correctedValue, resolvedAt)
3. ✅ Returns 404 if task not found
4. ✅ Writes back corrections to the actual node (L1/L2/L3) when approved with correctedValue
5. ✅ Creates `correction_examples` entries for approved corrections on L2 and L3 nodes
6. ✅ Sets `needsReview: false` on L2 nodes after approve/reject
7. ✅ Logs to `activity_log`
8. ✅ Returns enriched task object

The OpenAPI spec includes `PATCH /review-tasks/{id}` with `ReviewResolution` request body (status: approved/rejected/deferred, correctedValue?: string) and `ReviewTask` response. The generated Zod types and React Query hooks all align with the implementation.

## Round 2 — Code Quality & Security Review

### Code Quality

1. **Zod validation is properly applied** — The route validates both path params and request body using generated Zod schemas (`ResolveReviewTaskParams`, `ResolveReviewTaskBody`) at lines 110-111. ✅

2. **Early return for 404** — Line 121 uses defensive design (`if (!task) return res.status(404)...`). ✅

3. **`as any` cast on line 115** — `status: body.status as any` bypasses Drizzle's type checking. This is a minor code smell but is mitigated by the Zod validation that already constrains the status to `["approved", "rejected", "deferred"]`. ⚠️

4. **Writeback logic clarity** — The correction writeback (lines 124-181) is well-structured with clear entity type branching (l2_node, l3_node, l1_tag). Each branch handles fetching the node, writing back the correction, and creating correction_examples. ✅

5. **Missing correctedValue for non-approve statuses** — The correctedValue writeback only occurs when `body.correctedValue && task.status === "approved"` (line 124). This is correct behavior — corrections are only meaningful when approved. ✅

6. **needsReview only cleared for L2 nodes** — Line 184 clears `needsReview` only for `l2_node` entity types. L3 nodes and L1 tags don't have a `needsReview` column. This is consistent with the schema design but means L3 nodes don't track review state at the node level (same finding as in report 0096_5.1.1.md). ⚠️

### Security

1. **Zod validation prevents injection** — All user input is validated through Zod before use. ✅
2. **Drizzle ORM parameterized queries** — No SQL injection risk. ✅
3. **No authentication/authorization** — The route handler has no auth checks. This is a cross-cutting concern (addressed in items 9.1.4 and 9.1.5). ⚠️

### API Contract Consistency

The full chain from OpenAPI → Zod → React Query → UI is consistent:

- `lib/api-zod`: `ResolveReviewTaskBody` validates `status: zod.enum(["approved", "rejected", "deferred"])` + `correctedValue: zod.string().optional()`
- `lib/api-client-react`: `useResolveReviewTask` hook calls `PATCH /api/review-tasks/${id}`
- `review.tsx`: Uses `useResolveReviewTask` with correct payload shape

### OpenAPI Specification Completeness

The OpenAPI spec (`openapi.yaml`, lines 902-926) defines the review resolution endpoint with:
- Path parameter: `id` (integer, required)
- Request body: `ReviewResolution` schema (required)
  - `status`: enum `[approved, rejected, deferred]` (required)
  - `correctedValue`: string (optional)
- Response 200: `ReviewTask` schema

The `ReviewResolution` component schema (line 2076-2084) correctly defines the request body fields.

### Missing Pieces

1. **No `POST /review_tasks/:id/resolve` endpoint exists** — The design spec references this specific endpoint, but it does not exist in the implementation. Only `PATCH /review-tasks/{id}` exists. This is not a functional gap (the PATCH endpoint fulfills the same purpose more idiomatically), but it is a design spec inconsistency.

2. **No tests for the resolution endpoint** — There are no unit or integration tests specifically for the `PATCH /review-tasks/{id}` handler. The test coverage for this area is addressed in items 9.4.x.

3. **No authorization check** — Any client can resolve any review task. For a production system, this should require authentication and ideally check that the user has reviewer permissions for the project.

## Recommendations

1. **Update design documents** to reflect the actual endpoint: `PATCH /review-tasks/{id}` with `{ status: "approved" | "rejected" | "deferred", correctedValue?: string }`.
2. **Clarify the distinction** between task types (anchor/correct/validate/merge) and resolution statuses (pending/approved/rejected/deferred) in the design docs.
3. **Remove the `as any` cast** on line 115 — use proper Drizzle type narrowing instead.
4. **Add authorization middleware** to the review resolution endpoint.
5. **Add unit/integration tests** for the resolution handler, covering: approve, reject, defer, 404, correction writeback, and activity log creation.

## Overall Verdict

# ✅ PASS

The review resolution endpoint is **implemented and functional**. The `PATCH /review-tasks/{id}` handler correctly validates input via Zod, updates the review task status, writes back corrections to the underlying knowledge graph nodes (L1/L2/L3), creates `correction_examples` entries for the feedback loop, clears the `needsReview` flag on L2 nodes, logs to `activity_log`, and returns the enriched task. The OpenAPI spec, Zod schemas, React Query hooks, and UI are all consistent and correctly integrated.

The endpoint URL and field naming differences from the design spec (`POST /review_tasks/:id/resolve` with `{ action: "anchor" }` vs. actual `PATCH /review-tasks/{id}` with `{ status: "approved" }`) represent design spec inaccuracies rather than implementation bugs. The implementation is semantically superior (PATCH for partial status updates, clear separation of task types from resolution statuses). The design documents should be updated to match.

The `as any` cast and missing auth are minor issues that don't affect core functionality. No new regressions since the last verified commit.
