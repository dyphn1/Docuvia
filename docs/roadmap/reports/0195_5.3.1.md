## Round 1 — Architecture & Design Review

### Design Completeness

The `prompt_templates` table is well-defined in both the Drizzle schema and the SQL migration. The schema includes all necessary columns:

- `id` (serial PK)
- `project_id` (nullable FK → projects.id, ON DELETE CASCADE) — nullable to support global templates
- `template_type` (enum: `l1_tagger`, `l2_extractor`, `l3_generator`)
- `system_prompt` (text, NOT NULL)
- `is_active` (boolean, default true)
- `created_at` / `updated_at` (timestamps)

The design correctly supports:
1. **Per-project templates:** When `project_id` is set, the template is project-specific
2. **Global fallback templates:** When `project_id` is NULL, the template serves as a global default
3. **Three template types:** L1 tagger, L2 extractor, L3 generator — matching the knowledge hierarchy
4. **Soft toggle:** `is_active` allows disabling templates without deleting them

The API layer (templates.ts route) provides:
- `GET /projects/:id/templates` — Lists all 3 template types for a project, falling back to global defaults
- `PUT /projects/:id/templates/:type` — Upsert a project-specific template
- `DELETE /projects/:id/templates/:type` — Delete a project-specific template (resets to default)

The OpenAPI spec (lines 502–578) matches the implementation with GET/PUT/DELETE endpoints.

### Gaps and Issues

1. **No unique constraint on `(project_id, template_type)`:** The schema does not enforce uniqueness on the combination of `project_id` + `template_type`. This means a project could have multiple active templates of the same type, and the query in `getSystemPrompt` would return an arbitrary one (no `ORDER BY` or `LIMIT 1`). The `migrate.ts` seed logic checks `existing.length === 0` which only prevents seeding if *any* template exists — it doesn't handle the case where templates already exist but a specific type is missing.

2. **Inconsistent fallback logic between `getPromptTemplate` and `getSystemPrompt`:** The generate.ts file contains two separate functions for fetching templates:
   - `getPromptTemplate` (lines 30–68): Queries project-specific → global (NULL projectId) → hardcoded fallback. Uses `desc(promptTemplatesTable.createdAt)` and wraps output in `<SYSTEM_CONSTRAINT>` block.
   - `getSystemPrompt` (lines 87–101): Queries project-specific only → falls back to `DEFAULT_PROMPTS` from templates.ts. Does NOT query global templates from DB. Does NOT wrap in `<SYSTEM_CONSTRAINT>`.
   
   `getPromptTemplate` is **dead code** — it is defined but never called anywhere in the codebase. The actual generate pipeline uses `getSystemPrompt`.

3. **Schema vs. migration mismatch on `project_id`:** The Drizzle schema defines `projectId` as `integer("project_id").references(...)` — this is nullable by default in Drizzle when `.references()` is used without `.notNull()`. The SQL migration does NOT have `NOT NULL` on `project_id`. This is consistent — both allow NULL. ✅

## Round 2 — Code Quality & Security Review

### Critical Issue: Missing `desc` import in generate.ts

**File:** `artifacts/api-server/src/routes/generate.ts`
**Lines:** 41, 60

The `desc` function is used in `getPromptTemplate()` at lines 41 and 60:
```typescript
.orderBy(desc(promptTemplatesTable.createdAt))
```

However, the import at line 20 is:
```typescript
import { eq, and, sql, isNull, ne, isNotNull, inArray, or, lt } from "drizzle-orm";
```

`desc` is **not imported**. This will cause a runtime `ReferenceError: desc is not defined`. Since `getPromptTemplate` is dead code, this won't manifest in production, but it's a latent bug that would surface if the function is ever called.

### Critical Issue: Orphaned try/catch block in condenseL3Node

**File:** `artifacts/api-server/src/routes/generate.ts`
**Lines:** 187–190

```typescript
  return synthesizedContent || null;
  } catch {
    return null;
  }
}
```

After the `return` statement at line 187, there is an orphaned `} catch { return null; }` block (lines 188–190). This is a **syntax error** — the `catch` has no matching `try`. The function body appears to have been refactored (the `for` loop was likely previously wrapped in a `try/catch`), but the outer `try` was removed while the `catch` was left behind. This code will fail to compile/parse.

### Code Smell: Dual default prompt definitions

Default prompts are defined in two places:
1. `lib/db/src/schema/prompt_templates.ts` (lines 32–48) — `DEFAULT_PROMPT_TEMPLATES` array
2. `artifacts/api-server/src/routes/templates.ts` (lines 9–46) — `DEFAULT_PROMPTS` record

The content differs between the two:
- Schema version: Short, generic prompts (e.g., "You are an expert system tagger...")
- Route version: Detailed, structured prompts with JSON output format instructions

The `migrate.ts` seeds from the schema version (short prompts), while the API's `GET /projects/:id/templates` uses the route version as fallback. This means the default prompts served to users differ from what's seeded in the database.

### Input Validation

The `TemplateUpdateSchema` in `templates.ts` validates `systemPrompt` with `z.string().min(10)` — a reasonable minimum length check. The PUT route validates the template type against an allowlist (`l1_tagger`, `l2_extractor`, `l3_generator`). ✅

### Type Safety

The `templateType` parameter in the PUT route is cast as `templateType as any` when used in the Drizzle query (line 100), bypassing type safety. The `getPromptTemplate` function uses `templateType as any` similarly (lines 37, 56). This is a code smell — the typed `templateType` from the route parameter should be properly cast to the enum type.

## Round 3 — Integration & Completeness Review

### Integration with Generate Pipeline

The `generate.ts` route imports `DEFAULT_PROMPTS` from `templates.ts` and uses `getSystemPrompt()` to fetch templates during L1/L2/L3 generation. The flow is:

1. `generateL1Tags()` → calls `getSystemPrompt(projectId, "l1_tagger")`
2. `generateL2Nodes()` → calls `getSystemPrompt(projectId, "l2_extractor")`
3. L3 generation → calls `getSystemPrompt(projectId, "l3_generator")`

The `getSystemPrompt` function only queries project-specific templates and falls back to `DEFAULT_PROMPTS`. It does **not** query global templates (where `project_id IS NULL`) from the database. This means:
- If an admin seeds a global template in the DB with `project_id = NULL`, the generate pipeline will **not** use it — it will use the hardcoded `DEFAULT_PROMPTS` from `templates.ts` instead.
- The `getPromptTemplate` function (dead code) correctly implements the two-tier fallback (project → global → hardcoded), but it's never called.

### Migration Seeding Logic

The `migrate.ts` seeds default templates only when the `prompt_templates` table is completely empty (`existing.length === 0`). This means:
- If any template exists (even a single project-specific one), defaults won't be seeded.
- There's no per-type existence check — if `l1_tagger` exists but `l2_extractor` doesn't, the `l2_extractor` default will never be seeded.

### API Completeness

The API provides full CRUD for prompt templates:
- ✅ List with defaults fallback
- ✅ Upsert (create or update)
- ✅ Delete (reset to default)

However, there's no endpoint to manage global templates (where `project_id` is NULL). The DELETE endpoint deletes project-specific templates, but there's no way to create or manage global templates via the API — they can only be inserted directly into the database or via migration seeding.

### Missing Tests

There are no unit or integration tests for:
- The `templates.ts` route (GET/PUT/DELETE)
- The `getSystemPrompt` / `getPromptTemplate` functions
- The template seeding logic in `migrate.ts`

## Recommendations

1. **Fix the orphaned try/catch** in `condenseL3Node` — remove lines 188–190 or restructure the error handling
2. **Add `desc` to the drizzle-orm import** in `generate.ts` (or remove the dead `getPromptTemplate` function entirely)
3. **Consolidate `getPromptTemplate` and `getSystemPrompt`** into a single function that implements the full fallback chain (project → global DB → hardcoded defaults) with the `<SYSTEM_CONSTRAINT>` wrapper
4. **Unify default prompt definitions** — use a single source of truth for default prompts
5. **Add a unique constraint** on `(project_id, template_type)` to prevent duplicates
6. **Improve migration seeding** to check per-type existence rather than table-level emptiness
7. **Add tests** for template CRUD and template consumption in the generate pipeline

---

## Overall Verdict

**⚠️ WARN** — The `prompt_templates` table schema exists and is correctly defined. The API routes are implemented and wired up. However, there are critical code quality issues (orphaned try/catch, missing import) and architectural inconsistencies (dead code, dual fallback logic, no global template query in the active code path) that need to be addressed.
