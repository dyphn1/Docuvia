## Round 1 — Architecture & Design Review

### What the Design Specifies

The `prompt_tables` table is designed to store per-project overridable LLM prompts for the three knowledge hierarchy levels (L1 tagger, L2 extractor, L3 generator). The design calls for:

1. A `prompt_templates` table with columns: `id`, `project_id` (nullable FK), `template_type` (enum), `system_prompt`, `is_active`, `created_at`, `updated_at`
2. Nullable `project_id` to support both per-project templates and global fallback templates
3. Three template types matching the knowledge hierarchy: `l1_tagger`, `l2_extractor`, `l3_generator`
4. REST API endpoints: GET (list with defaults), PUT (upsert), DELETE (reset to default)

### What the Implementation Provides

The schema is correctly implemented in both Drizzle ORM and SQL migration:

```sql
CREATE TABLE "prompt_templates" (
  "id" serial PRIMARY KEY NOT NULL,
  "project_id" integer,
  "template_type" "prompt_template_type" NOT NULL,
  "system_prompt" text NOT NULL,
  "is_active" boolean DEFAULT true NOT NULL,
  "created_at" timestamp DEFAULT now() NOT NULL,
  "updated_at" timestamp DEFAULT now() NOT NULL
);
```

- `project_id` is nullable ✅ — supports global templates
- Foreign key constraint with ON DELETE CASCADE ✅
- Enum type `prompt_template_type` with correct values ✅
- All required columns present ✅

The route is registered at `artifacts/api-server/src/routes/index.ts:40`:
```typescript
router.use(templatesRouter);
```

### Gaps and Issues

1. **No unique constraint on `(project_id, template_type)`:** The schema does not enforce uniqueness on the combination of `project_id` + `template_type`. This means a project could have multiple active templates of the same type. The PUT route's upsert logic (`SELECT` then `INSERT` or `UPDATE`) works correctly for the normal case, but a direct INSERT (or a race condition) could create duplicates.

2. **Two competing prompt-fetching functions in generate.ts:**
   - `getPromptTemplate` (lines 30–68): Implements full 3-tier fallback (project-specific → global DB → hardcoded). Wraps prompts in `<SYSTEM_CONSTRAINT>` block. Uses `desc()` for ordering. **DEAD CODE — never called.**
   - `getSystemPrompt` (lines 87–101): Implements 2-tier fallback (project-specific only → hardcoded `DEFAULT_PROMPTS`). Does NOT query global templates from DB. Does NOT wrap in `<SYSTEM_CONSTRAINT>`. **This is the function actually used by the generate pipeline.**

   The generate pipeline calls `getSystemPrompt` at lines 528, 664, and 752 — never `getPromptTemplate`.

3. **Global templates seeded but never consumed by the active code path:** The `migrate.ts` seeds global templates (with `project_id = NULL`), and `getPromptTemplate` correctly queries them, but `getSystemPrompt` does not. This means the global template feature is architecturally incomplete — it exists in the DB but the active code path ignores it.

4. **Default prompts defined in two places with different content:**
   - `lib/db/src/schema/prompt_templates.ts` (lines 32–48): Short, generic prompts
   - `artifacts/api-server/src/routes/templates.ts` (lines 9–46): Detailed, structured prompts with JSON output format instructions

   The `migrate.ts` seeds the short schema-version prompts into the DB, while the API's GET endpoint falls back to the detailed route-version prompts. Users see different default prompts depending on whether they're viewing templates through the API or inspecting the DB directly.

## Round 2 — Code Quality & Security Review

### Critical Issue: Missing `desc` import in generate.ts

**File:** `artifacts/api-server/src/routes/generate.ts`
**Lines:** 20, 41, 60

The import at line 20:
```typescript
import { eq, and, sql, isNull, ne, isNotNull, inArray, or, lt } from "drizzle-orm";
```

`desc` is **not imported** but is used at lines 41 and 60:
```typescript
.orderBy(desc(promptTemplatesTable.createdAt))
```

This will cause a `ReferenceError: desc is not defined` at runtime. Since `getPromptTemplate` is dead code and never called, this won't manifest in production — but it's a latent bug.

### Critical Issue: Orphaned `} catch {` block in condenseL3Node

**File:** `artifacts/api-server/src/routes/generate.ts`
**Lines:** 187–190

```typescript
  return synthesizedContent || null;
  } catch {
    return null;
  }
}
```

After the `return` statement at line 187, there is an orphaned `} catch { return null; }` block. This is a **syntax error** — the `catch` has no matching `try`. The function body appears to have been refactored (the `for` loop was likely previously wrapped in a `try/catch`), but the outer `try` was removed while the `catch` was left behind.

### Security: Prompt Injection Mitigation

`getPromptTemplate` wraps user-provided prompts in a `<SYSTEM_CONSTRAINT>` block:
```typescript
return `${template.systemPrompt}\n\n<SYSTEM_CONSTRAINT>\nOUTPUT MUST BE VALID JSON ONLY. NO MARKDOWN WRAPPERS. DO NOT OUTPUT \`\`\`json\n</SYSTEM_CONSTRAINT>`;
```

However, `getSystemPrompt` (the function actually used) does NOT apply this wrapper. This means if a user stores a malicious prompt template via the PUT endpoint, the generate pipeline will use it directly without the output format constraint wrapper. This contradicts the security requirement identified in ADR-006.

### Code Smell: Dual function definitions

`getPromptTemplate` and `getSystemPrompt` have overlapping responsibilities but different fallback chains and different security postures. Having both is confusing and error-prone.

### Type Safety

`templateType as any` casts in `templates.ts:100` and `generate.ts:37,56` bypass Drizzle type safety. The `templateType` from route parameters should be properly cast to the enum type.

### Input Validation

The `TemplateUpdateSchema` validates `systemPrompt` with `z.string().min(10)` — reasonable minimum length. The PUT route validates template type against an allowlist. ✅

However, there's no maximum length check on `systemPrompt`. An extremely large prompt could cause token issues or be used for denial-of-service.

### No Tests

There are zero tests for:
- Template CRUD operations (GET/PUT/DELETE)
- `getSystemPrompt` / `getPromptTemplate` functions
- Template seeding logic in `migrate.ts`
- Template consumption in the generate pipeline

## Round 3 — Integration & Completeness Review

### Route Registration

The templates router is correctly registered in `routes/index.ts:40`. ✅

### API Completeness

The API provides full CRUD for per-project prompt templates:
- ✅ `GET /projects/:id/templates` — Lists all 3 template types for a project, falling back to hardcoded defaults
- ✅ `PUT /projects/:id/templates/:type` — Upsert a project-specific template
- ✅ `DELETE /projects/:id/templates/:type` — Delete a project-specific template (resets to default)

### Missing: Global Template Management

There is no API endpoint to create, read, or manage global templates (where `project_id` is NULL). The DELETE endpoint only deletes project-specific templates. Global templates can only be inserted directly into the database or via migration seeding.

### Integration with Generate Pipeline

The generate pipeline at lines 528, 664, and 752 calls `getSystemPrompt()`:

```typescript
const l1SystemPrompt = await getSystemPrompt(projectId, "l1_tagger");
const l2SystemPrompt = await getSystemPrompt(projectId, "l2_extractor");
const systemPrompt = await getSystemPrompt(projectId, "l3_generator");
```

`getSystemPrompt` only queries project-specific templates and falls back to hardcoded `DEFAULT_PROMPTS`. It does **not**:
1. Query global templates from the DB
2. Apply the `<SYSTEM_CONSTRAINT>` wrapper for prompt injection mitigation

### Migration Seeding Logic

The `migrate.ts` seeds default templates only when the `prompt_templates` table is completely empty (`existing.length === 0`). This means:
- If any template exists (even a single project-specific one), defaults won't be seeded
- There's no per-type existence check — if `l1_tagger` exists but `l2_extractor` doesn't, the `l2_extractor` default will never be seeded

### OpenAPI Spec Alignment

The OpenAPI spec at lines 502–578 defines the expected endpoints. The implementation matches the spec for GET, PUT, and DELETE operations. ✅

## Recommendations

1. **Fix orphaned try/catch** in `condenseL3Node` (generate.ts:188-190) — remove the dead `} catch { return null; }` block
2. **Add `desc` to the drizzle-orm import** in generate.ts:20 — or remove the dead `getPromptTemplate` function entirely
3. **Consolidate `getPromptTemplate` and `getSystemPrompt`** into a single function that implements the full fallback chain (project → global DB → hardcoded defaults) with the `<SYSTEM_CONSTRAINT>` wrapper
4. **Apply `<SYSTEM_CONSTRAINT>` wrapper in the active code path** to mitigate prompt injection
5. **Unify default prompt definitions** — use a single source of truth for default prompts (preferably the detailed versions from `templates.ts`)
6. **Add a unique constraint** on `(project_id, template_type)` to prevent duplicates
7. **Improve migration seeding** to check per-type existence rather than table-level emptiness
8. **Add tests** for template CRUD operations and template consumption in the generate pipeline
9. **Add `z.string().max()`** limit on `systemPrompt` to prevent abuse

## Overall Verdict

**⚠️ WARN** — The `prompt_templates` table schema exists and is correctly defined in both ORM and SQL. The API routes are implemented and properly registered. The OpenAPI spec matches the implementation. However, there are critical code quality issues (orphaned try/catch, missing import), a security concern (active code path bypasses prompt injection mitigation), architectural inconsistencies (dead code with better logic than the active code, global templates seeded but not consumed), and no test coverage.
