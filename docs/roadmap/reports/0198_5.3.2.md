## Round 1 — Architecture & Design Review

### Design Intent

The design spec (glossary, building blocks, crosscutting concepts) clearly states:
- Each project can override the default LLM system prompts for L1, L2, and L3 generation
- If no project-specific template exists, the system falls back to a built-in default
- Templates are stored in the `prompt_templates` table

### Implementation Status

**Schema (`prompt_templates.ts`):** ✅ Correctly implemented.
- `projectId` is nullable (nullable FK to `projects.id` with `onDelete: "cascade"`) — allows both global (null) and project-specific templates
- `templateType` enum covers all three types: `l1_tagger`, `l2_extractor`, `l3_generator`
- `isActive` boolean allows soft-disabling templates
- `DEFAULT_PROMPT_TEMPLATES` array provides hardcoded fallback defaults for all three types
- Zod schemas (`insertPromptTemplateSchema`, `updatePromptTemplateSchema`) properly validate input

**REST API (`templates.ts`):** ✅ Correctly implemented.
- `GET /projects/:id/templates` — Lists all 3 template types for a project, merging DB records with defaults. Returns `isCustom` flag to distinguish project-specific from default.
- `PUT /projects/:id/templates/:type` — Upserts a project-specific template. Validates `systemPrompt` min length (10 chars).
- `DELETE /projects/:id/templates/:type` — Deletes the project-specific template, effectively resetting to default.
- All endpoints validate project existence (404 if not found).

**Generate Pipeline (`generate.ts`):** ✅ Correctly consumes templates.
- `getSystemPrompt(projectId, templateType)` (lines 87-102) queries DB for active project-specific template, falls back to `DEFAULT_PROMPTS[templateType]` from the templates route module.
- Called at lines 528, 664, 752 for L3, L1, and L2 generation respectively.

**Frontend (`templates.tsx`):** ✅ Fully implemented.
- Project selector sidebar + template editor main area
- Shows Custom/Default badge, last updated date
- Edit mode with textarea for custom prompts
- Save (upsert) and Reset (delete) functionality
- Uses generated React Query hooks from `@workspace/api-client-react`

**OpenAPI Spec:** ✅ Complete.
- `PromptTemplate` and `PromptTemplateInput` schemas defined
- All 3 endpoints (`listProjectTemplates`, `upsertProjectTemplate`, `deleteProjectTemplate`) fully specified with correct request/response shapes

### Gaps / Issues Found

1. **Dead code function `getPromptTemplate` (lines 30-68):** This function is defined but never called anywhere in the codebase. It has a different fallback strategy than `getSystemPrompt` — it queries for global DB templates (`projectId IS NULL`) as an intermediate fallback before the hardcoded default. Since `getSystemPrompt` is the function actually used in the pipeline, `getPromptTemplate` is dead code.

2. **Missing `desc` import in `generate.ts`:** The `getPromptTemplate` function uses `desc(promptTemplatesTable.createdAt)` on lines 41 and 60, but `desc` is NOT in the import from `drizzle-orm` on line 20. The import list is `eq, and, sql, isNull, ne, isNotNull, inArray, or, lt`. This would cause a runtime `ReferenceError` if `getPromptTemplate` were ever called. Since it's dead code, the bug is latent.

3. **Design inconsistency between `getSystemPrompt` and `getPromptTemplate`:** The two functions have different fallback chains:
   - `getSystemPrompt` (used): DB project-specific → hardcoded `DEFAULT_PROMPTS` → empty string
   - `getPromptTemplate` (dead code): DB project-specific → DB global (`projectId IS NULL`) → hardcoded default → generic fallback
   
   The design spec says "Falls back to a built-in default if not set for a project" — `getSystemPrompt` matches this. But the DB-seeded global templates (via `migrate.ts`) are never actually queried by the active code path. The `migrate.ts` seeds templates with `projectId = null`, but `getSystemPrompt` only queries by specific `projectId`.

## Round 2 — Code Quality & Security Review

### Code Quality

**`templates.ts` route handler:**
- Clean structure with early returns (defensive design pattern)
- Zod validation on PUT body (`TemplateUpdateSchema` with `min(10)`)
- Proper HTTP status codes (200 for update, 201 for create, 204 for delete, 400 for invalid type, 404 for missing project)
- ✅ Follows project coding conventions

**`generate.ts` — `getSystemPrompt`:**
- Simple, clean function with early return pattern
- Uses `??` nullish coalescing for fallback chain
- ✅ Follows defensive design

**`generate.ts` — `getPromptTemplate` (dead code):**
- ❌ Missing `desc` import — would crash at runtime
- More complex than necessary (3-level fallback)
- Not used anywhere — should be removed

**`templates.tsx` frontend:**
- Well-structured React component with proper separation of concerns
- Uses generated API hooks (correct per project conventions)
- Good UX with edit/save/reset/cancel flow
- Loading states and error handling via toast notifications
- ✅ Follows MVC pattern (View = TSX, Controller = event handlers + mutations, Model = React Query hooks)

### Security

- **Input validation:** PUT endpoint validates `systemPrompt` with Zod (`min(10)`). No max length check — a very large prompt could be stored, but this is bounded by PostgreSQL's `text` type and LLM context limits.
- **No injection risk:** Prompts are stored as `text` and passed to LLM as system prompts — no SQL injection risk (parameterized queries via Drizzle ORM).
- **No auth check on template endpoints:** The templates route does NOT verify that the authenticated user owns the project. This is consistent with other routes in the project (auth is not implemented at the route level), but worth noting as a gap.
- **No XSS risk:** The frontend renders prompts in `<pre>` tags (escaped by React) and `<textarea>` (safe).

## Round 3 — Integration & Completeness Review

### Integration Points

1. **Schema → Migration:** ✅ `migrate.ts` seeds default templates with `projectId = null` on first run. Uses existence check to avoid re-seeding.

2. **Schema → API Routes:** ✅ `templates.ts` correctly imports and uses `promptTemplatesTable` from `@workspace/db`.

3. **API Routes → Generate Pipeline:** ✅ `generate.ts` imports `DEFAULT_PROMPTS` from `./templates.js` and `promptTemplatesTable` from `@workspace/db`. The `getSystemPrompt` function is called during L1, L2, and L3 generation.

4. **OpenAPI → Frontend:** ✅ `templates.tsx` uses generated hooks (`useListProjectTemplates`, `useUpsertProjectTemplate`, `useDeleteProjectTemplate`) from `@workspace/api-client-react`.

5. **Route Registration:** ✅ `templatesRouter` is imported and mounted in `routes/index.ts` (line 15/40).

### Missing Tests

- ❌ No unit tests for `templates.ts` route handler
- ❌ No unit tests for `getSystemPrompt` function in `generate.ts`
- ❌ No integration tests for the templates API endpoints
- ❌ No frontend component tests for `templates.tsx`

### Performance

- `getSystemPrompt` queries the DB on every generation call with no caching. For a generation run that processes L1, L2, and L3, this means 3 separate DB queries for prompts. This is acceptable for the current scale but could be optimized with a short-lived cache or by fetching all 3 templates in a single query.

### End-to-End Usability

The feature is fully usable end-to-end:
1. Admin seeds default templates via migration
2. User navigates to Templates page in kg-engine
3. User selects a project from the sidebar
4. User sees all 3 template types (L1, L2, L3) with Custom/Default badges
5. User clicks Edit, modifies the prompt, clicks Save → template is stored in DB
6. On next generation run, the custom prompt is used instead of the default
7. User can Reset to delete the project-specific template and revert to default
