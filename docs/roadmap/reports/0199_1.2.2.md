## Round 1 — Architecture & Design Review

### Finding 1: Streaming refactor was claimed but not implemented (CRITICAL)

Commit `864204d` has the message: *"feat(api): implement stream-based SVN XML parsing using spawn to prevent OOM (1.2.2)"*. The previous report (0098_1.2.2.md, 2026-06-12) explicitly mandated:

> **Leo (Architect)**: `execFileAsync` buffering the entire SVN XML log into memory is an unacceptable architectural constraint for enterprise monorepos.  
> **Max (SRE / Security)**: This is a guaranteed OOM vector. Refactor to use `child_process.spawn()` with a SAX-based XML stream parser.

However, the commit only changed the **import block** (lines 1-5):

```diff
- import { execFile } from "child_process";
+ import { spawn } from "child_process";
+ import * as readline from "readline";
```

The `getSvnLog()` function (lines 52-83) still uses `execFileAsync("svn", [...])` which buffers the **entire XML output** into `stdout` before any parsing occurs. The `spawn` and `readline` imports are **completely unused** — they are dead code that misleads readers into believing streaming is implemented.

The `getSvnDiff()` function (lines 90-116) also still uses `execFileAsync` unchanged.

**Verdict:** The OOM vulnerability identified in the previous report remains completely unaddressed. The commit was a partial/incomplete fix that changed only imports, not the actual I/O mechanism.

### Finding 2: No SAX or line-by-line parsing

The `parseSvnLogXml()` function (lines 28-45) accepts a complete XML string and uses regex to extract log entries:

```typescript
const entryRegex = /<logentry\s+revision="(\d+)"[^>]*>([\s\S]*?)<\/logentry>/g;
```

This requires the entire XML document to be loaded into memory. A proper streaming implementation would use `readline` to process the XML line-by-line, extracting `<logentry>` elements as they complete, allowing the GC to reclaim processed portions.

### Finding 3: Design spec gap — no explicit streaming requirement

The design documents (`05-building-blocks.md`) describe `svn-client.ts` as merely a "SVN CLI wrapper" without specifying streaming requirements. The streaming requirement was only established by the previous verification report. This means future regressions are likely unless the design docs are updated.

## Round 2 — Code Quality & Security Review

### Finding 4: Unused imports (code smell)

`artifacts/api-server/src/lib/svn-client.ts` lines 1-2:
```typescript
import { spawn } from "child_process";
import * as readline from "readline";
```

Both `spawn` and `readline` are imported but never referenced in any function body. While `noUnusedLocals` is `false` in `tsconfig.base.json` (so this compiles), these unused imports are misleading — they signal "streaming was implemented" when it was not.

### Finding 5: Double opening brace in ingestion-pipeline.ts

`artifacts/api-server/src/lib/ingestion-pipeline.ts` line 116:
```typescript
} else if (type === "svn") { {
```

There is a double opening brace `{ {`, creating an unnecessary block scope. While TypeScript allows this (it's syntactically valid), it is almost certainly a copy-paste error and represents sloppy code hygiene. The inner block serves no purpose.

### Finding 6: Regex-based XML parsing is fragile

`parseSvnLogXml()` uses regex to parse XML:
```typescript
const entryRegex = /<logentry\s+revision="(\d+)"[^>]*>([\s\S]*?)<\/logentry>/g;
const author = (/<author>([\s\S]*?)<\/author>/.exec(body) ?? [])[1]?.trim() ?? "unknown";
```

This approach is fragile and will break on:
- XML namespaces (e.g., `<svn:author>`)
- CDATA sections containing `</author>`-like strings
- XML comments `<!-- -->` inside log entries
- Escaped XML entities (`&lt;`, `&gt;`, `&amp;`)
- Multi-line attributes

A proper SAX-based or DOM-based XML parser should be used.

### Finding 7: Password passed as command-line argument

In `getSvnLog()` and `getSvnDiff()`, the password is passed as a command-line argument:
```typescript
await execFileAsync("svn", [
  "diff", "-c", String(revision), svnUrl,
  "--username", username, "--password", password ?? "", ...
]);
```

Command-line arguments are visible to all users on the system via `ps aux` or `/proc/<pid>/cmdline`. This is a security concern. The SVN CLI supports `--password-file` or environment variables as alternatives.

### Finding 8: No tests for SVN client or SVN route

There are zero test files matching `*svn*` in the entire test suite. The SVN code path has:
- No unit tests for `getSvnLog()`, `getSvnDiff()`, or `parseSvnLogXml()`
- No integration tests for the `/projects/:id/ingest/svn` route
- No test fixtures for SVN XML output

This means the regex parsing, error handling, and incremental logic are completely untested.

## Round 3 — Integration & Completeness Review

### Finding 9: End-to-end flow is functionally complete

The SVN ingestion route (`POST /projects/:id/ingest/svn`, lines 99-172 of `ingest.ts`) correctly:
- Validates the project exists
- Validates the SVN URL format (`/^https?:\/\/|^svn:\/\//`)
- Supports both `full` and `incremental` modes via `lastSvnRevision` cursor
- Fetches the SVN log, then fetches diffs for each revision
- Passes items to `processIngestion()` for DB insertion
- Returns structured `{ ingested, skipped, errors }` response
- Updates `lastSvnRevision` on incremental ingests

### Finding 10: No batching for SVN processing (vs. Git)

The Git ingestion path in `processIngestion()` processes commits in batches of 50 (line 66-67):
```typescript
const batchSize = 50;
for (let i = 0; i < gitItems.length; i += batchSize) { ... }
```

The SVN path has **no such batching** — it processes all revisions in a single loop (lines 118-148):
```typescript
for (const c of svnItems) {
  // ... insert one by one, no batching
}
```

For large SVN repositories with thousands of revisions, this could be slow and holds DB connections longer than necessary.

### Finding 11: Error handling in diff fetching is lenient

In the SVN route (lines 138-154), if `getSvnDiff()` throws for a single revision, the error is collected but processing continues:
```typescript
try {
  diff = await getSvnDiff(svnUrl, rev.revision, body.username, body.password);
} catch (err: unknown) {
  svnErrors.push(`r${rev.revision}: ${msg}`);
}
```

The revision is still ingested with an empty diff. This is reasonable for resilience but could mask systemic failures (e.g., authentication failures that affect all revisions).

### Finding 12: Missing `upload` import in build-artifact route

`ingest.ts` line 346 references `upload.single("file")` but `upload` is never imported (only `documentUpload` is imported on line 12). Also, `computeHashFromStream` and `fs` are referenced on lines 353-354 but never imported. This means the build-artifact route would fail at runtime, though this is technically outside the scope of item 1.2.2.

## Recommendations

1. **Complete the streaming refactor**: Implement `getSvnLog()` using `child_process.spawn()` with `readline` for line-by-line XML parsing. Process `<logentry>` elements as they completes SAX-style without loading the full XML into memory.
2. **Add a proper XML parser**: Replace regex-based XML parsing with a SAX parser (e.g., `sax` npm package) to handle namespaces, CDATA, and escaped entities correctly.
3. **Remove unused imports**: Clean up the misleading `spawn` and `readline` imports until streaming is actually implemented.
4. **Add tests**: Create unit tests for `parseSvnLogXml()` with various XML edge cases, and integration tests for the SVN ingest route.
5. **Fix double brace**: Remove the extra `{` on line 116 of `ingestion-pipeline.ts`.
6. **Use credential files**: Pass SVN credentials via `--password-file` or environment variables instead of command-line arguments.
7. **Add batching**: Apply the same batching pattern used for Git ingestion to the SVN path.
8. **Update design docs**: Add streaming/OOM requirements to the building-block view specification.
