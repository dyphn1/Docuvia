## Round 1 — Architecture & Design Review

### Does the design document correctly describe the feature?

ADR-002 describes a "Local-First, Server-Augmented" architecture with two modes:
1. **Standalone Mode** — When `isServerConfigured()` returns false, the extension relies on local `.docuvia/` YAML files and git orphan branch reads.
2. **Server-Augmented Mode** — When a `server_url` is configured, the extension offloads heavy computation to the API server.

The implementation continues to match this design well. The `KnowledgeStore` class implements a clear three-tier loading strategy (lines 141-203 of `KnowledgeStore.ts`):
- **Tier 1 (Server API):** If `isServerConfigured()` is true AND `manifest.project_id` exists, it calls `pullSnapshot()` from the central server.
- **Tier 2 (Local `.docuvia/` directory):** If Tier 1 fails or returns empty, it reads `l1_tags.yaml`, `l2_modules.yaml`, `l3_router.yaml`, and `l3_decisions/*.md` directly from the workspace `.docuvia/` folder.
- **Tier 3 (Git orphan branch):** If Tier 2 also returns empty, it falls back to reading from the `docuvia-knowledge` orphan branch via `git cat-file --batch` (streaming, not `exec`).

### What changed since the last verification (2026-06-08)?

**Change 1 — `KnowledgeStore._loadFromGit` now uses `spawn` + `git cat-file --batch` instead of multiple `exec` calls.** The previous report noted that the git fallback used `child_process.exec` via promisify. This has been refactored: `runGit()` still uses `execFile` for `git ls-tree` (line 341), but the bulk blob reading now uses a single `spawn('git', ['cat-file', '--batch'])` with stdin piping (lines 364-424). This is a significant architectural improvement — it spawns one git process and pipes all blob requests through stdin, rather than spawning N separate `git show` processes. This addresses the performance concern raised in the previous report.

**Change 2 — `CentralServerClient` gained E2E mock interceptors.** The `query()`, `sync()`, and `pullSnapshot()` methods now check `process.env.DOCUVIA_MOCK_SERVER === '1'` and return mock data (lines 46-56, 100-102, 134-147). This enables E2E testing without a real server. The heartbeat mechanism (`startHeartbeat`, `_tickMetabolism`) is unchanged.

**Change 3 — `DocuviaCodeLensProvider` now uses LSP-based symbol anchors.** The previous regex-only approach has been enhanced with a two-tier strategy: (1) use cached LSP `DocumentSymbol` results when available (lines 150-151), (2) fall back to regex-only on initial load, then trigger async anchor updates via `vscode.executeDocumentSymbolProvider` (lines 106-138). The `documentAnchors` cache (line 89) maps document URIs to symbol line numbers. This is a significant improvement in accuracy and performance.

**Change 4 — `executeSearch` now routes to chat or webview based on config.** The previous report noted that `executeSearch` silently showed an empty results panel when no server was configured. The new implementation (lines 387-409) checks `docuvia.search.defaultView` config: if `'chat'`, it routes to `@docuvia /query` in Copilot Chat; if `'webview'`, it calls `centralClient.query()` and shows `SearchResultsPanel`. However, **the issue is only partially resolved** — when `defaultView` is `'webview'` and no server is configured, `centralClient.query()` still returns `[]` and the `SearchResultsPanel` shows empty results with no helpful message. The chat path is better since the chat participant handles the no-server case.

**Change 5 — `searchFromSelection` added with query length cap.** New command (lines 365-384) caps selected text at 2000 chars to prevent sending entire files to the server. This is a good security/performance measure.

**Change 6 — Bug fixes in `extension.ts`.** Multiple bug fixes: BUG A-1 (create `.docuvia/` directory before writing), BUG A-2 (ensure skeleton YAML files exist), BUG A-3 (pass explicit workspace root to `acceptL1Tags`), BUG N-2 (cap query length). These improve the reliability of the local-first init flow.

**Change 7 — `ChatParticipant` and `DashboardPanel` multi-root bias fix.** Commit `ffbea1b` fixed single-root bias in multi-root workspaces.

### Are there gaps between the design spec and the actual implementation?

**Gap 1 — `last_verified_at` decay not implemented.** ADR-002 explicitly mentions "Local garbage collection based on `last_verified_at` decay" but notes in parentheses: "(Note: `last_verified_at` is currently not implemented)." This remains unchanged. The `KnowledgeStore` has no decay/garbage collection logic. The `L3Decision` type in `types.ts` does not include a `last_verified_at` field. This is an acknowledged gap.

**Gap 2 — Git orphan branch fallback still requires `manifest.project_id`.** The Tier 3 git fallback (line 191) only activates if `manifest.project_id !== undefined`. For purely local projects without server connection, `project_id` will be absent, making the git fallback unreachable. This is unchanged from the previous report.

**Gap 3 — `executeSearch` webview mode still degrades poorly.** When `search.defaultView` is `'webview'` and no server is configured, the user sees an empty `SearchResultsPanel` with no indication that a server is needed. The chat route handles this better.

### Are there contradictions between different design documents?

No contradictions found. The ADR-002, the AGENTS.md, and the implementation are all aligned on the local-first principle.

### Is the feature complete per the design spec?

The core local-first feature is **complete**. The extension:
- Activates without a server (`onStartupFinished` and `workspaceContains:.docuvia` activation events in `package.json` lines 18-24).
- Loads knowledge from local `.docuvia/` YAML files when no server is configured.
- Provides full TreeView, CodeLens, Hover, Dashboard, and Chat Participant functionality using only local data.
- Gracefully degrades when server methods are called (e.g., `CentralServerClient.query()` returns `[]` when no `server_url` is configured, lines 58-61).
- New: E2E mock server support enables testing without a real server.
- New: LSP-based CodeLens anchoring improves accuracy.

## Round 2 — Code Quality & Security Review

### Is the implementation well-structured and following the project's coding rules?

**MVC Pattern:** The codebase maintains a clean separation:
- **Model:** `KnowledgeStore` (data layer), `types.ts` (domain types with Zod schemas)
- **View:** `KnowledgeGraphTreeProvider`, `TaskQueueTreeProvider`, `DashboardPanel`, `SearchResultsPanel` (UI presentation)
- **Controller:** `extension.ts` (command handlers), `ChatParticipant.ts` (chat request routing)

**Defensive Design:** Good use of early returns and guard clauses throughout:
- `KnowledgeStore.load()` guards against concurrent loading with `_loading` flag (lines 95-98).
- `CentralServerClient.query()` returns `[]` early when no `server_url` (lines 58-61).
- `DocuviaCodeLensProvider.provideCodeLens()` returns `[]` early when no snapshot is available (lines 144-146).
- `DashboardPanel._handleMessage` checks `msg.filePath.startsWith(workspaceRoot)` to reject paths outside the workspace (line 159).

**POP (Protocol-Oriented Programming):** The `IDocuviaClient` interface in `KnowledgeStore.ts` (lines 15-18) decouples the store from the concrete `CentralServerClient`, enabling testability and alternative implementations.

### Are there security vulnerabilities?

**1. `child_process.execFile` in `runGit()` (KnowledgeStore.ts line 341):** Uses `execFile` (not `exec`), which does NOT spawn a shell. The arguments are passed as an array. The `workspaceRoot` comes from VS Code's trusted `folder.uri.fsPath`. Risk: **LOW**. This is an improvement over the previous `exec`-based approach.

**2. `spawn('git', ['cat-file', '--batch'])` in `readGitBlobs()` (KnowledgeStore.ts line 365):** Uses `spawn` with array args (no shell). The `GIT_KNOWLEDGE_BRANCH` constant is hardcoded. The `projectId` is validated as a number by `ManifestSchema`. Risk: **LOW**.

**3. Path traversal in `DashboardPanel._handleMessage` (line 159):** The code checks `if (!msg.filePath.startsWith(workspaceRoot))` to reject paths outside the workspace. This is a good security measure. However, this is a simple string prefix check — it could be bypassed with paths like `/workspace-root-evil/path` if `workspaceRoot` is `/workspace`. A more robust check would use `path.resolve` and verify the normalized path starts with the workspace root. Risk: **LOW** (requires webview compromise).

**4. No input sanitization on YAML parsing:** The `parser.ts` functions use Zod schemas to validate parsed YAML, which provides structural validation. Content fields (e.g., `description`, `body`) are stored as plain strings without sanitization. Since this is a local-first VS Code extension, the risk is minimal.

**5. `searchFromSelection` query length cap (line 372):** The 2000-char cap prevents sending entire files to the server. This is a good defensive measure.

### Are there code smells, duplication, or anti-patterns?

**1. `KnowledgeStore.tryParse` is still dead code.** The previous report identified `tryParse` (lines 463-470 in the old version) as unused. In the current version, this method has been removed — the dead code was cleaned up. ✅

**2. `CentralServerClient._tickMetabolism` catches all errors silently (lines 203-205).** While intentional (heartbeat shouldn't crash), logging the error at debug level would aid troubleshooting. Unchanged from previous report.

**3. `ChatParticipant.ts` `handleQuery` still lowercases `d.body` at every iteration (line 316).** `d.body.toLowerCase().includes(query)` lowercases the body for each decision in the loop. For large decision bodies, this is slightly inefficient. Minor.

**4. `extension.ts` uses `require()` for `fs/promises`, `path`, and `js-yaml` in `initProject` and `detectEcosystem` (lines 419, 429, 492).** This is inconsistent with the ES module `import` style used everywhere else. The `require` calls are dynamic and only used in the init flow, so they don't affect startup performance, but they should be refactored to use ES module imports for consistency.

### Are error handling and edge cases properly addressed?

**Yes, generally well-handled:**
- `KnowledgeStore.load()` uses a try-catch with `_loading` guard and `_pendingReload` for concurrent reload requests.
- `CentralServerClient.query()` throws `CentralServerAuthError` on 401, which is caught in `ChatParticipant.handleBreadthQuery` and `executeSearch`.
- `TaskRunner.runExtractionAsync` catches per-chunk errors and continues processing remaining chunks (lines 285-290).
- `KnowledgeIndexer.buildTreeForFile` catches symbol provider failures gracefully (lines 84-86).
- New: `readGitBlobs` has proper error handling for the `git cat-file --batch` process, including stderr capture and non-zero exit code handling (lines 370-418).

## Round 3 — Integration & Completeness Review

### Does the feature integrate correctly with other parts of the system?

**Yes.** The local-first architecture continues to integrate well with all subsystems:

1. **TreeView (`KnowledgeGraphTreeProvider`):** Reads directly from `KnowledgeStore.snapshots`. No server dependency. ✅

2. **CodeLens (`DocuviaCodeLensProvider`):** Now uses LSP-based symbol anchors for improved accuracy. Both "online mode" (full decision data) and "offline fallback" (manifest path patterns) work without a server. ✅

3. **Hover (`DocuviaHoverProvider`):** Reads from `KnowledgeStore` snapshot and `KnowledgeIndexer`. No server dependency. ✅

4. **Chat Participant (`ChatParticipant.ts`):** The `/query` command performs local keyword search. The `/explore` command reads local files. The `/extract` command queues local tasks. The breadth query path requires a server and degrades gracefully. Multi-root bias fix improves workspace handling. ✅

5. **Dashboard (`DashboardPanel`):** Reads from `KnowledgeStore.getSnapshotFor()`. No server dependency. Multi-root bias fix. ✅

6. **TaskRunner:** Uses `vscode.lm.selectChatModels()` for local LLM access. No server dependency. ✅

7. **File Watcher:** `KnowledgeStore.startWatcher()` sets up `FileSystemWatcher` on `.docuvia/**` for all workspaces. ✅

8. **New: E2E mock server.** The `DOCUVIA_MOCK_SERVER` environment variable enables mock data for testing without a real server. ✅

### Are there missing tests?

The vscode-client has unit test infrastructure, but specific tests are still missing for:
- The three-tier loading strategy in `KnowledgeStore.load()`
- The `isServerConfigured()` branching logic
- The LSP-based CodeLens anchoring
- The `readGitBlobs` streaming git implementation
- The `executeSearch` chat/webview routing

This is unchanged from the previous report and is consistent with the project's overall test coverage pattern.

### Are there performance concerns?

**1. `KnowledgeStore.readGitBlobs` now uses a single `git cat-file --batch` process.** This is a significant improvement over the previous approach of spawning multiple `git show` processes. All blob requests are piped through stdin to a single git process. ✅

**2. `KnowledgeIndexer.buildTreeForFile` is debounced with 500ms delay (line 49-53).** Reasonable. ✅

**3. `KnowledgeStore._handleBatchedChanges` has incremental vs. full reload logic (lines 493-550).** Well-designed optimization with configurable thresholds. ✅

**4. `DocuviaCodeLensProvider` now uses LSP symbol anchors with async updates.** The initial load uses fast regex, then LSP results are cached asynchronously. This prevents Editor Host freezing. ✅

### Is the feature actually usable end-to-end without a server?

**Yes.** All core workflows remain functional without a server:
1. Open a workspace → extension activates automatically.
2. Run `Docuvia: Init Project` → creates `.docuvia/` with manifest.yaml.
3. Run `Docuvia: Analyze Project Architecture` (`/explore`) → generates L1 tags from local files.
4. Run `Docuvia: Add Decision` → creates L3 decision markdown files.
5. Run `Docuvia: Run L3 Extraction on Active File` → extracts decisions from code.
6. View Knowledge Graph tree with L1/L2/L3 hierarchy.
7. See CodeLens annotations (now with LSP-anchored accuracy).
8. Hover over symbols to see L3 decision previews.
9. Use `@docuvia /query` to search the local knowledge graph.
10. Use the Dashboard panel to see project statistics.
11. Use drag-and-drop in the TreeView to categorize decisions.

**All of the above work without any server configuration.**

## Findings

### Issues

1. **Minor — `executeSearch` webview mode still degrades without a helpful message** (`extension.ts` lines 397-398). When `search.defaultView` is `'webview'` and no server is configured, `centralClient.query()` returns `[]` and the `SearchResultsPanel` shows empty results with no indication that a server is needed. The chat route handles this better (the chat participant shows a tip about configuring `server_url`). **Recommendation:** Add a check in the webview branch: if `!centralClient.isServerConfigured()`, show an informational message instead of calling `query()`.

2. **Minor — `extension.ts` uses `require()` for dynamic imports** (`extension.ts` lines 419, 429, 492). The `fs/promises`, `path`, and `js-yaml` modules are loaded via `require()` inside function bodies, inconsistent with the ES module `import` style used everywhere else. **Recommendation:** Refactor to use ES module imports at the top of the file.

3. **Minor — Git orphan branch fallback requires `project_id`** (`KnowledgeStore.ts` line 191). For purely local projects, `project_id` will be `undefined`, making the git fallback unreachable. **Recommendation:** Consider using a workspace-path-based identifier for the git fallback when `project_id` is absent.

4. **Info — `last_verified_at` decay not implemented.** Acknowledged in ADR-002. No action needed.

### Risks

1. **Low — `DashboardPanel._handleMessage` path traversal check is a simple string prefix** (line 159). A more robust check would use `path.resolve` and verify the normalized path. Current risk is low since it requires webview compromise.

2. **Low — No git CLI availability check.** If git is not in PATH, the Tier 3 fallback will fail with an error caught and logged, but the user may not see the message. Unchanged from previous report.

### Recommendations

1. Improve the `executeSearch` webview mode UX for serverless mode (show a message instead of empty panel).
2. Refactor `require()` calls in `extension.ts` to ES module imports.
3. Consider making the git orphan branch path work without `project_id`.
4. Add unit tests for the three-tier loading strategy and the new `readGitBlobs` implementation.
5. Consider adding a git CLI availability check on activation.

## Overall Verdict: ✅ PASS

The local-first operation feature remains **well-implemented and functional**. Since the last verification (2026-06-08), several meaningful improvements have been made:

- **Git blob reading refactored** from multiple `exec` calls to a single `spawn` + `git cat-file --batch` streaming approach, addressing the performance concern from the previous report.
- **CodeLens anchoring improved** with LSP-based symbol caching for better accuracy.
- **E2E mock server support** added for testing without a real server.
- **Multiple bug fixes** for multi-root workspace bias, directory creation, and query length limits.
- **Dead code removed** (`tryParse` method).

The extension provides full standalone value without a central server, with a clear three-tier loading strategy. All core features work without server configuration. The issues found are minor UX gaps and code quality concerns, not architectural flaws or blockers.
