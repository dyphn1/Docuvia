## Round 1 — Architecture & Design Review

**What exists:**

The Markdown export endpoint is implemented at `export.ts:104-159` as `GET /projects/:id/export/md`. It:
1. Looks up the project by ID (returns 404 if not found)
2. Sets `Content-Type: text/markdown; charset=utf-8` and `Content-Disposition: attachment` with a sanitized filename
3. Streams Markdown content using `res.write()` to avoid buffering the entire output in memory
4. Iterates over L2 nodes in batches of 100 with offset pagination to prevent OOM
5. For each L2 node, writes headings, metadata, and then fetches and writes child L3 nodes
6. Calls `res.end()` to finalize the stream

The route is properly imported in `index.ts:14` and mounted at `index.ts:39` (`router.use(exportRouter)`). Since `export.ts` registers routes without a prefix (plain `router.get("/projects/:id/export/md")`) and `index.ts` mounts it with `router.use(exportRouter)`, the effective path depends on how the index router itself is mounted. Given that `index.ts` is imported as the root router in the server entrypoint, the route is accessible at `GET /projects/:id/export/md`.

**Gaps and issues:**

1. **Missing OpenAPI spec definition (critical).** The OpenAPI spec (`openapi.yaml`) only defines `/projects/{id}/export` (JSON) at line 483. There is no `/projects/{id}/export/md` path defined. This directly violates ADR-001 ("OpenAPI as Single Source of Truth"). Without a spec entry:
   - No Zod validator is generated for this endpoint
   - No React Query hook is generated for frontend consumption
   - No operationId exists for Orval codegen
   - API documentation is incomplete

2. **No frontend integration.** The `ProjectDetail` page (`artifacts/kg-engine/src/pages/projects/[id].tsx`) has no "Export Markdown" button or any UI to trigger the markdown export. The feature is therefore not usable end-to-end from the kg-engine frontend.

3. **Not listed in the AGENTS.md route inventory.** The AGENTS.md documentation at the top of the file lists `export` as one of the 21 route modules but doesn't specifically call out the markdown sub-route, and the comment from a prior verification (D-06) noted "Markdown export may be missing."

## Round 2 — Code Quality & Security Review

1. **No Zod validation.** The endpoint does not use any Zod validator for the `id` path parameter. It relies on raw `Number(req.params.id)` which produces `NaN` for non-numeric input. Passing `NaN` to the database query (`eq(projectsTable.id, NaN)`) will return no rows and correctly produce a 404 response, so this is not an exploitable bug, but it bypasses the project's standard validation pattern used by all other routes.

2. **No authentication or authorization.** The endpoint does not check whether the caller is authenticated or authorized to access the project. Any unauthenticated caller can export any project's knowledge base by providing a numeric project ID. This is consistent with other routes in the same codebase (which also appear to lack auth middleware), but it is still a security concern.

3. **Filename sanitization edge case.** Line 111: `project.name.replace(/[^a-zA-Z0-9]/g, "_")` replaces all non-alphanumeric characters. If a project name consists entirely of non-ASCII characters (e.g., a Chinese or Japanese project name), the resulting filename would be all underscores or empty, which could cause a confusing download experience.

4. **N+1 query pattern within the L3 loop.** For each L2 node in the batch, the code executes a separate query to fetch its L3 nodes (line 141-144). For a project with many L2 nodes, this produces N+1 queries (where N = L2 count per batch). This is noted in the existing JSON export endpoint's previous assessment (6.5.1 LGTM) but is more concerning in the streaming path where responses are already in progress.

5. **No error handling during stream.** If the database connection drops or an error occurs after `res.write()` has started but before `res.end()` is called, the client will receive a truncated Markdown file with no error indicator. There is no `try/catch` around the streaming loop and no `res.on('error')` handler.

6. **No test coverage.** There are no unit tests or integration tests for the markdown export endpoint. The existing test file list shows tests for MCP, generate, decay, embedding, and intent-router, but nothing for export.

## Round 3 — Integration & Completeness Review

**Usability gaps:**

1. **End-to-end incomplete.** While the backend endpoint exists and is functional (can be called directly via `curl` or HTTP client), there is no frontend UI to trigger it. A user cannot export a Markdown file from the kg-engine UI.

2. **API-first principle violated.** Because the endpoint is not in `openapi.yaml`, it cannot be consumed through the generated React Query hooks. Any developer wanting to integrate with the markdown export must manually construct an HTTP request, which contradicts the project's API-first architecture.

3. **No test for streaming behavior.** The chunked streaming approach (batching L2 nodes) is a reasonable design for large projects, but there is no test verifying that:
   - Batching actually prevents OOM for large datasets
   - The `Content-Type` header is set correctly
   - The response is valid Markdown
   - The endpoint returns 404 for non-existent projects

4. **L1 tags not included in markdown export.** The JSON export (`GET /projects/:id/export`) includes `l1Tags` in the response, but the Markdown export does not include any L1 tag information in the generated document. Architectural cross-cuttings (tags) are lost in the Markdown format.

5. **Commits not included in markdown export.** The JSON export includes `commits` but the Markdown export does not. This is a design choice, but it means the Markdown export is a partial data dump.

## Recommendations

1. **Add `/projects/{id}/export/md` to `openapi.yaml`** with proper operationId (`exportProjectMarkdown`), schema references, and response type. Run `pnpm --filter @workspace/api-spec run codegen` afterward.
2. **Add an "Export Markdown" button** to the `ProjectDetail` page or the project list actions.
3. **Add integration tests** for the Markdown export endpoint (200, 404, content-type, valid Markdown output).
4. **Add error handling** in the streaming loop — wrap in try/catch and call `res.status(500).end()` on failure.
5. **(Optional) Batch the L3 query** — fetch all L3 nodes for the batch of L2 IDs in a single `IN (...)` query instead of one per L2.

## Overall Verdict

**⚠️ WARN** — The Markdown export endpoint is implemented on the backend with a solid streaming/chunking design, but it is not defined in the OpenAPI spec (violating ADR-001), has no frontend integration, no Zod validation, no authentication, and no test coverage. The feature is partially complete and not usable end-to-end.
