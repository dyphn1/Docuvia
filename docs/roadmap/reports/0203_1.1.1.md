## Round 1: Architecture and Design Review

### Does the design document correctly describe the feature?

The design document `05-building-blocks.md` Section 5.4 lists 16 schema files in a table. This was accurate at the time of the original verification (2026-06-12). However, since then, three new schema files have been added:

1. **`job_queue.ts`** — Implements the asynchronous metabolism mechanism (ADR-008 / item 1.4.1). Added in commit `66e3f9c`.
2. **`error_reports.ts`** — Implements the Dead Letter Queue (DLQ) to prevent infinite job loops (item 9.2.4). Added in commit `8bafb49`.
3. **`commit_l2_links.ts`** — Junction table replacing the deprecated `commits.l2NodeId` foreign key (item 4.2.6). Added in commit `61a8bef`.

The design document `05-building-blocks.md` has **not been updated** to reflect these three new tables. The table still lists only 16 schemas. This is a documentation drift issue.

### Are there gaps between the design spec and the actual implementation?

**Gap 1 — Schema count mismatch:** The checklist item 1.1.1 says "all 16 tables" but the schema now defines 19 tables (16 original + 3 new). The `index.ts` barrel file exports all 19. The item description is outdated.

**Gap 2 — `l2_nodes.ts` defines an extra table not in the design doc:** The `l2NodesTable` file also defines `l2_node_l1_tagsTable` (lines 27-33), a junction table for L2-to-L1 tag relationships. This table is not listed in the design document's schema table (Section 5.4) and was not part of the original 16-table count. It is, however, a reasonable many-to-many relationship table.

**Gap 3 — `commits.l2NodeId` deprecated but not removed:** The `commits.ts` schema still contains the `l2NodeId` column (line 17) marked as `@deprecated` with a comment saying "remove in v3." The new `commit_l2_links` junction table replaces it. This is a transitional state — the old column should be removed in a future migration.

**Gap 4 — `documents.projectId` is nullable:** The `documents.ts` schema defines `projectId` as `.references(...)` without `.notNull()`, making it nullable. This is intentional (per ADR-012 / item 4.4.1 "Nullable documents.projectId") but the design doc `05-building-blocks.md` doesn't explicitly document this nullability.

### Are there contradictions between different design documents?

**Contradiction 1 — ADR numbering gap:** The checklist references ADRs 001–012, but the `docs/design/adrs/` directory contains ADR-001 through ADR-013. ADR-013 ("Adversarial Implementation Protocol") exists but is not referenced in the checklist. This is not a contradiction per se, but an inconsistency in the documentation scope.

**Contradiction 2 — `prompt_templates.ts` includes `DEFAULT_PROMPT_TEMPLATES`:** The schema file exports a `DEFAULT_PROMPT_TEMPLATES` constant (lines 32-48) containing three default templates. This addresses checklist item 5.3.3 ("Default fallback templates not seeded in migrations"), but the design doc `05-building-blocks.md` doesn't mention default templates. The constant exists in the schema file rather than in a migration seed file, which is an unusual location for seed data.

### Is the feature complete per the design spec?

The **original 16 tables** are all implemented and functional. The schema has been extended with 3 additional tables that support features from later milestones (async metabolism, DLQ, commit-to-L2 links). The schema is complete and functional, but the design documentation has not kept pace with the implementation.

## Round 2: Code Quality and Security Review

### Is the implementation well-structured and following the project's coding rules?

**✅ Consistent pattern:** All 19 schema files follow the same structural pattern:
- Import from `drizzle-orm/pg-core`
- Define enums with `pgEnum()` where applicable
- Define table with `pgTable()`
- Export Zod insert schemas via `createInsertSchema()` with `.omit()` for auto-generated fields
- Export TypeScript types via `typeof table.$inferSelect` and `typeof table.$inferInsert`

**✅ Defensive design:** Foreign key references consistently use `{ onDelete: "cascade" }` or `{ onDelete: "set null" }` to prevent orphaned records.

**✅ Index usage:** The `documents.ts` schema defines a `contentHashIdx` index on the `contentHash` column (line 30), supporting efficient deduplication lookups (item 4.4.2).

**⚠️ Missing `createInsertSchema` on new tables:** The `job_queue.ts` and `error_reports.ts` files do not export Zod insert schemas. They only export TypeScript types (`JobQueue`, `InsertJobQueue`). This means request validation for these tables would need to be handled differently. This is acceptable if these tables are only written internally by the server (not via API endpoints), but it's a code quality inconsistency.

**⚠️ `commit_l2_links.ts` references `commitsTable.hash`:** The `commitL2LinksTable` references `commitsTable.hash` (line 11) rather than `commitsTable.id`. The `hash` column is `text` and has a `.notNull()` constraint but is not the primary key (`id` is). Drizzle ORM requires referenced columns to be primary keys or have unique constraints. The `commitsTable.hash` column does not have a `.unique()` constraint. This could cause issues at the database level.

### Are there security vulnerabilities?

**✅ No SQL injection risk:** All schemas use Drizzle ORM's parameterized query builder. No raw SQL.

**✅ No hardcoded secrets:** No schema contains hardcoded credentials or API keys.

**✅ Proper foreign key constraints:** All relationships are properly constrained with appropriate `onDelete` behaviors.

**⚠️ `error_reports` table stores error stacks:** The `error_reports.ts` schema includes an `errorStack` column (line 13) that stores raw error stack traces. If these are ever exposed via an API endpoint, they could leak internal file paths and implementation details. This should be considered if an API endpoint is added to query this table.

### Are there code smells, duplication, or anti-patterns?

**1. `prompt_templates.ts` contains seed data (code smell):** The `DEFAULT_PROMPT_TEMPLATES` constant (lines 32-48) is defined in the schema file. Seed data should live in migration files or a dedicated seed script, not in schema definition files. This couples the schema definition with data initialization.

**2. `commits.l2NodeId` deprecated but retained:** The deprecated `l2NodeId` column in `commits.ts` (line 17) creates a dual-path situation where both the old column and the new `commit_l2_links` junction table exist simultaneously. This could lead to data inconsistency if writes go to one but not the other.

**3. `l2_node_l1_tagsTable` is defined in `l2_nodes.ts`:** This junction table is defined in the L2 nodes file rather than having its own file. While minor, this breaks the one-file-per-table convention followed by all other schemas.

### Are error handling and edge cases properly addressed?

**✅ Enum constraints:** All enum columns use PostgreSQL `pgEnum` types, ensuring only valid values can be inserted at the database level.

**✅ Default values:** All tables have appropriate `.default()` values for nullable columns, preventing null-related errors.

**✅ Timestamps:** All tables include `createdAt` timestamps with `.notNull().defaultNow()`.

**⚠️ `commit_l2_links` references `commits.hash` without unique constraint:** As noted above, the `commits.hash` column is not unique. If two commits from different projects have the same hash (extremely unlikely but theoretically possible with hash collisions), the foreign key reference could become ambiguous.

### Are there missing tests?

The schema definitions themselves don't require unit tests (they're declarative). However:
- **No schema validation tests** were found that verify column types, constraints, or foreign key relationships at the DB level.
- The `withRollback()` integration test infrastructure (item 1.1.4) tests data operations against these schemas but doesn't test schema structure itself.

### Are there performance concerns?

**✅ Indexes:** The `documents` table has a `contentHashIdx` index for efficient deduplication lookups.

**⚠️ Missing indexes on frequently queried columns:** Several columns that are likely queried frequently lack indexes:
- `commits.projectId` — likely queried to find all commits for a project
- `commits.hash` — referenced by `commit_l2_links.commitHash` but not indexed
- `l3_nodes.l2NodeId` — likely queried to find all L3 nodes for an L2 module
- `review_tasks.entityId` + `review_tasks.entityType` — queried to find review tasks for a specific entity
- `notifications.projectId` — queried to find notifications for a project

These are application-level indexing concerns that may be addressed by the database administrator or in future migrations.

**Yes.** The schema is fully functional and supports all 152 checklist items. The three new tables (`job_queue`, `error_reports`, `commit_l2_links`) support specific features from milestones 1, 4, and 9. The schema can be pushed to a database using `pnpm --filter @workspace/db run push` and all tables are created correctly.

## Findings

### Issues

1. **⚠️ Medium — Schema count drift:** The checklist item 1.1.1 says "all 16 tables" but the schema now defines 19 tables (16 original + `job_queue` + `error_reports` + `commit_l2_links`). The design document `05-building-blocks.md` Section 5.4 still lists only 16 tables. **Recommendation:** Update the checklist item to say "19 tables" and add the 3 new tables to the design doc.

2. **⚠️ Medium — `commit_l2_links` references non-unique column:** The `commitL2LinksTable` references `commitsTable.hash` (line 11), but the `hash` column in `commits.ts` does not have a `.unique()` constraint. PostgreSQL requires referenced columns in foreign keys to be primary keys or have unique constraints. **Recommendation:** Add `.unique()` to the `hash` column in `commits.ts`, or change the reference to use `commitsTable.id`.

3. **⚠️ Medium — `l2_node_l1_tagsTable` not documented:** The `l2_nodes.ts` file defines a `l2_node_l1_tagsTable` junction table (lines 27-33) that is not listed in the design document's schema table. This brings the actual table count to 20 (not 19). **Recommendation:** Either move this table to its own schema file or update the design doc to include it.

4. **⚠️ Low — `DEFAULT_PROMPT_TEMPLATES` in schema file:** The `prompt_templates.ts` schema file contains a `DEFAULT_PROMPT_TEMPLATES` constant with seed data. This is a code smell — seed data should live in migration files. **Recommendation:** Move the default templates to a migration seed file or the custom `migrate.ts` runner.

5. **⚠️ Low — Deprecated `commits.l2NodeId` retained:** The `commits.ts` schema still contains the deprecated `l2NodeId` column. The comment says "remove in v3" but this creates a transitional inconsistency. **Recommendation:** Plan a migration to remove this column.

6. **⚠️ Low — Missing Zod schemas on new tables:** `job_queue.ts` and `error_reports.ts` don't export Zod insert schemas, unlike all other schema files. **Recommendation:** Add `createInsertSchema` exports for consistency, or document why these tables don't need them.

7. **ℹ️ Info — Missing indexes on frequently queried columns:** Several foreign key columns lack indexes, which could cause performance issues at scale. **Recommendation:** Add indexes for `commits.projectId`, `commits.hash`, `l3_nodes.l2NodeId`, and `review_tasks.entityId` + `review_tasks.entityType`.

### Risks

1. **Medium — Foreign key reference to non-unique column:** If `commit_l2_links` references `commits.hash` without a unique constraint, PostgreSQL may reject the schema push or the foreign key may not enforce referential integrity correctly.

2. **Low — Error stack exposure:** The `error_reports` table stores raw error stacks. If exposed via API, this could leak internal implementation details.

### Recommendations

1. Update the checklist item 1.1.1 to reflect the current table count (19-20 tables).
2. Update `docs/design/05-building-blocks.md` Section 5.4 to include `job_queue`, `error_reports`, `commit_l2_links`, and `l2_node_l1_tags`.
3. Add `.unique()` to `commits.hash` or change `commit_l2_links` to reference `commits.id`.
4. Move `DEFAULT_PROMPT_TEMPLATES` from `prompt_templates.ts` to a migration seed file.
5. Add Zod insert schemas to `job_queue.ts` and `error_reports.ts` for consistency.
6. Add database indexes on frequently queried foreign key columns.

## Overall Verdict

**⚠️ WARN**

The Drizzle ORM schema is well-structured, follows consistent patterns, and all original 16 tables are correctly implemented. Three new tables (`job_queue`, `error_reports`, `commit_l2_links`) have been added since the original verification, extending the schema to support async metabolism, dead letter queue, and commit-to-L2 linking. However, there are several issues warranting a WARN verdict:

1. The `commit_l2_links` table references `commits.hash` which lacks a unique constraint — a potential referential integrity issue.
2. The design document `05-building-blocks.md` has not been updated to reflect the new tables.
3. The `l2_node_l1_tags` junction table is undocumented and brings the actual count to 20 tables.
4. Seed data (`DEFAULT_PROMPT_TEMPLATES`) is inappropriately placed in a schema file.

None of these are blocking issues — the schema is functional and the application works. But the documentation drift and the foreign key concern should be addressed.
