## Round 1 — Architecture & Design Review

### Does the design document correctly describe the feature?

**Yes, broadly.** The design documents describe a document upload and parsing system that:

1. Accepts PDF, DOCX, PPTX, Markdown, TXT, and build artifact files.
2. Uses `child_process.fork()` to isolate heavy parsing (PDF/DOCX/PPTX) from the main event loop.
3. Enforces memory limits (`--max-old-space-size=512`) and timeouts (60 seconds) on worker processes.
4. Validates file types via multer middleware with MIME type and extension whitelists.
5. Stores parsed content in the `documents` table.

The implementation in `document-parser.ts` and `parser-worker.js` matches this design. The `extractText()` function routes PDF/DOCX/PPTX to `parseInWorker()`, which forks a child process with `--max-old-space-size=512` and a 60-second timeout. Markdown, TXT, and build artifacts are handled inline (no fork needed).

### Are there gaps between the design spec and the actual implementation?

**Gap 1 — `documents.ts` has missing imports (CRITICAL).** The file `artifacts/api-server/src/routes/documents.ts` uses several variables/functions that are never imported:
- `upload` (line 85): `router.post("/documents", upload.single("file"), ...)` — `upload` is not imported. This will throw `ReferenceError: upload is not defined` at runtime.
- `fs` (lines 105, 112, 116, 121, 134): `fs.promises.readFile(...)`, `fs.promises.unlink(...)` — `fs` is not imported.
- `detectDocType` (line 110): Used but not imported (it's from `document-parser.js`).
- `computeHashFromStream` (line 120): Not imported or defined anywhere in the file.
- `logger` (line 137): Not imported.

This means the entire `POST /documents` endpoint (Misc Pool upload) is **non-functional** and will crash at runtime.

**Gap 2 — `documents.ts` duplicate `docType` variable.** Line 110 declares `const docType = detectDocType(...)` and line 122 declares `const docType = detectDocType(...)` again. In JavaScript/TypeScript, re-declaring a `const` in the same scope is a syntax error. However, these appear to be in different scope blocks (the second is inside the `try`), but the structure is confusing and error-prone.

**Gap 3 — `req.user` is not populated.** Line 89: `const uploadedBy = req.user?.id || 1` — There is no visible authentication middleware that sets `req.user`. This means `req.user` will always be `undefined`, and `uploadedBy` will always fall back to `1`. This is a hardcoded fake user, which is acceptable for development but should be flagged.

**Gap 4 — Build artifact parser in `ingest.ts` also has missing imports.** Line 353: `const contentHash = await computeHashFromStream(filePath)` — `computeHashFromStream` is not imported in `ingest.ts`. Also, `fs` is not imported. The build artifact upload endpoint at line 346 also uses `upload.single("file")` but `upload` is not imported (only `multer` is imported on line 14, not the configured `upload` instance).

### Are there contradictions between different design documents?

**No major contradictions.** The design documents are consistent about the isolation strategy and the file types supported. The archive design doc (`09-document-parser.md`) describes the same architecture.

### Is the feature complete per the design spec?

**Partially.** The core document parsing pipeline (`document-parser.ts` + `parser-worker.js`) is well-implemented and complete. The upload middleware (`upload.ts`) is correct. However, the route handlers that consume these modules (`documents.ts` and parts of `ingest.ts`) have critical missing imports that make them non-functional.

## Round 2 — Code Quality & Security Review

### Is the implementation well-structured and following the project's coding rules?

**`document-parser.ts` — Well-structured.** Uses defensive design (early returns, clear error handling). The `parseInWorker` function properly handles timeout, error, and exit events. The `extractText` function uses a clean switch statement. Function lengths are reasonable.

**`parser-worker.js` — Well-structured.** Clean separation of parse functions per doc type. Proper error handling with try/catch and cleanup of temp files.

**`documents.ts` — Poor.** Missing imports, duplicate variable declarations, and hardcoded user IDs violate basic code quality standards.

**`upload.ts` — Well-structured.** Clean multer configuration with proper file filtering.

### Are there security vulnerabilities?

**1. CRITICAL — Missing imports in `documents.ts` cause runtime crashes.** While not a traditional security vulnerability, a crashing endpoint can be a DoS vector and indicates the code was never tested.

**2. MEDIUM — Hardcoded fallback user ID.** `documents.ts` line 89: `const uploadedBy = req.user?.id || 1` — If auth middleware is ever added, the fallback to user ID `1` could allow unauthenticated uploads attributed to a real user. This should be `null` or rejected.

**3. LOW — Temp file in `document-parser.ts` uses `os.tmpdir()` with random name.** The temp file path is not predictable (uses `crypto.randomBytes(8)`), which is good. However, the temp file is written synchronously (`fs.writeFileSync`) and the worker reads it synchronously (`fs.readFileSync`). This is acceptable for the isolated worker pattern.

**4. LOW — Magic byte validation in `documents.ts` is incomplete.** The code checks PDF magic bytes (`25504446`) and ZIP magic bytes (`504B0304` for DOCX/PPTX), but only for PDF and DOCX/PPTX types. Build artifact files (`.log`, `.map`, `.fv`, `.fd`) have no magic byte validation. This is acceptable since build artifacts are text files.

**5. INFO — `parser-worker.js` uses `require()` dynamically.** The worker dynamically requires `pdf-parse`, `mammoth`, and `officeparser` at parse time. This is intentional (lazy loading to avoid loading heavy libraries in the main process), but it means missing dependencies won't be caught at startup.

### Are there code smells, duplication, or anti-patterns?

**1. `documents.ts` and `ingest.ts` both define document upload endpoints with overlapping functionality.** `documents.ts` has `POST /documents` (Misc Pool upload) while `ingest.ts` has `POST /projects/:id/ingest/document/upload` (project-associated upload). The `documents.ts` version duplicates logic (magic byte checking, hash computation) that should be in shared utility functions.

**2. `detectDocType` is defined in `document-parser.ts` but also partially re-implemented in `ingest.ts` lines 211-212 and 273-279.** The extension-to-type mapping is duplicated. `ingest.ts` should import `detectDocType` from `document-parser.ts`.

**3. `documents.ts` has dead code paths.** The `contentHash` variable is computed (line 120) but the `computeHashFromStream` function is not imported, so this line would throw. The entire try block is effectively dead code.

### Are error handling and edge cases properly addressed?

**`document-parser.ts` — Yes.** Handles worker timeout (SIGKILL after 60s), worker errors, worker abnormal exits, and temp file cleanup in all cases.

**`parser-worker.js` — Yes.** Catches parse errors, cleans up temp files, and sends structured error messages back to the parent.

**`documents.ts` — No.** The missing imports mean the error handling code paths are unreachable. The `catch` block on line 136-138 references `logger` which is not imported.

**`ingest.ts` document upload handler — Partially.** Lines 214-220 handle parse errors and empty content well. But the build artifact handler (lines 346-377) has the same missing import issues.

## Round 3 — Integration & Completeness Review

### Does the feature integrate correctly with other parts of the system?

**Core parsing pipeline — Yes.** The `document-parser.ts` module is correctly imported by `ingest.ts` (line 13) and used in the document upload handler (line 216). The `upload.ts` middleware is correctly imported and used.

**Route integration — BROKEN.** The `documents.ts` route has missing imports that prevent it from working. The `ingest.ts` build artifact endpoint also has missing imports.

**Database integration — Yes.** The `documents` table schema supports all required fields: `filename`, `docType`, `content`, `contentHash`, `affiliatedAt`, `validityStatus`, `uploadedBy`, `status`. The schema matches the insert operations in both route files.

### Are there missing tests?

**Yes.** No unit or integration tests were found for:
- `document-parser.ts` (the `extractText` and `parseInWorker` functions)
- `parser-worker.js` (the PDF/DOCX/PPTX parsing logic)
- `documents.ts` (the Misc Pool upload endpoint)
- Magic byte validation logic
- The `upload.ts` middleware file filter

The search for test files matching `document-parser|extractText|parseInWorker` returned no test files — only source files and documentation.

### Are there performance concerns?

**1. `parseInWorker` writes buffer to temp file.** The current implementation writes the buffer to a temp file and passes the file path to the worker, which reads it back. This involves unnecessary disk I/O. An alternative would be to send the buffer directly via IPC (`worker.send()` supports Buffer), but the current approach is acceptable for the security boundary it provides.

**2. Sequential processing.** The document upload handler processes one file at a time (multer `single("file")`). This is by design and acceptable for v1.

**3. Worker process overhead.** Forking a new process for each PDF/DOCX/PPTX parse operation has overhead (~50-100ms per fork). For bulk uploads, a worker pool would be more efficient. Acceptable for v1.

### Is the feature actually usable end-to-end?

**Partially.** The project-associated document upload endpoint (`POST /projects/:id/ingest/document/upload` in `ingest.ts`) is functional — it correctly imports `documentUpload`, `detectDocType`, and `extractText`. A user can upload a document to a project and have it parsed.

However, the Misc Pool upload endpoint (`POST /documents` in `documents.ts`) is **non-functional** due to missing imports. This means:
- Users cannot upload documents without a project association.
- The "Misc Pool" feature (ADR-012) is partially broken at the API level.

## Findings

### Issues

1. **CRITICAL — `documents.ts` missing imports.** The file uses `upload`, `fs`, `detectDocType`, `computeHashFromStream`, and `logger` without importing any of them. The `POST /documents` endpoint will throw `ReferenceError` at runtime. **Fix:** Add the missing imports:
   ```typescript
   import { documentUpload as upload } from "../middlewares/upload.js";
   import fs from "node:fs";
   import { detectDocType } from "../lib/document-parser.js";
   import { logger } from "../lib/logger.js";
   import { computeHashFromStream } from "../lib/hash.js"; // or wherever this is defined
   ```

2. **CRITICAL — `ingest.ts` build-artifact endpoint missing imports.** Lines 346-377 use `upload`, `computeHashFromStream`, and `fs` without importing them. **Fix:** Import `upload` from `../middlewares/upload.js`, `fs` from `node:fs`, and `computeHashFromStream` from the appropriate module.

3. **MEDIUM — Duplicate `docType` declaration in `documents.ts`.** Line 110 and line 122 both declare `const docType`. The second declaration will cause a syntax error if it's in the same scope, or shadow the first if in a different scope. **Fix:** Remove the duplicate declaration on line 122.

4. **MEDIUM — Hardcoded user ID fallback.** `documents.ts` line 89: `req.user?.id || 1` silently attributes uploads to user 1. **Fix:** Return 401 if `req.user` is not set, or use `null` for `uploadedBy`.

5. **LOW — `detectDocType` logic duplicated in `ingest.ts`.** The extension-to-type mapping is duplicated in `ingest.ts` lines 273-279. **Fix:** Import and use `detectDocType` from `document-parser.ts`.

6. **LOW — No tests for document parsing.** The entire document parsing pipeline lacks unit and integration tests. **Fix:** Add tests for `detectDocType`, `extractText` (mocking the worker), and the upload endpoints.

### Risks

1. **High — Runtime crashes in production.** The missing imports in `documents.ts` will cause immediate runtime failures if the `POST /documents` route is hit. This is a production-breaking bug.

2. **Medium — Untested code paths.** The document parsing code has never been executed in tests. Edge cases (corrupt PDFs, large files, timeout scenarios) are unverified.

3. **Low — Build artifact endpoint also affected.** The `ingest.ts` build-artifact handler has the same import issues, meaning build artifact upload via the API is also broken.

### Recommendations

1. **Immediate:** Fix all missing imports in `documents.ts` and `ingest.ts`.
2. **Immediate:** Add the `computeHashFromStream` function (or import it if it exists elsewhere).
3. **Short-term:** Add unit tests for `document-parser.ts` (mock the worker fork).
4. **Short-term:** Add integration tests for the document upload endpoints.
5. **Medium-term:** Consolidate duplicate `detectDocType` logic into a single shared function.
6. **Medium-term:** Replace the hardcoded user ID fallback with proper auth middleware.

---

## Overall Verdict: ⚠️ WARN

The core document parsing implementation (`document-parser.ts` + `parser-worker.js`) is **well-designed and correctly implements the isolation architecture** specified in the design docs. The `child_process.fork()` pattern with `--max-old-space-size=512` and 60-second timeout is properly implemented with correct error handling and temp file cleanup.

However, the **route handlers that consume the parser are broken** due to missing imports in `documents.ts` and `ingest.ts`. The `POST /documents` endpoint (Misc Pool upload) and the `POST /projects/:id/ingest/build-artifact` endpoint will crash at runtime with `ReferenceError`. This means the document upload feature is **not fully usable end-to-end** despite the core parser being correct.

The previous verification (2026-06-08, report 0007) only examined `document-parser.ts` in isolation and did not check the route files or the integration between components. The source files were subsequently modified (commit `93f9e8f` on 2026-06-12), and the route files were added/modified in later commits (`e4e8870`, `5e2ff18`) with these import issues introduced.
