## Round 1 — Architecture & Design Review

**What exists:**

The Markdown export feature is now fully implemented across all layers of the stack:

1. **OpenAPI spec** (`openapi.yaml:502-520`): Defines `GET /projects/{id}/export/md` with `operationId: exportProjectMarkdown`, proper integer `id` path parameter, and `text/markdown` response with `type: string, format: binary`. This resolves the previous critical finding where the endpoint was missing from the spec.

2. **Generated client** (`lib/api-client-react/src/generated/api.ts:1573-1630`): Orval codegen has produced:
   - `getExportProjectMarkdownUrl(id)` — URL builder returning `/api/projects/{id}/export/md`
   - `exportProjectMarkdown(id, options)` — async function returning `Promise<Blob>`
   - `useExportProjectMarkdown(id, options)` — React Query hook with proper typing
   - `getExportProjectMarkdownQueryKey(id)` — query key builder

3. **Backend route** (`export.ts:124-179`): `GET /projects/:id/export/md` with:
   - `checkProjectOwnership` middleware (IDOR prevention)
   - Streaming response via `res.write()` to avoid OOM
   - Batched L2 node fetching (batch size 100) for memory efficiency
   - Per-L2 L3 node queries with full content output
   - Proper `Content-Type: text/markdown; charset=utf-8` and `Content-Disposition: attachment` headers

4. **Frontend** (`projects/[id].tsx:262-277, 338-339`):
   - Imports `useExportProjectMarkdown` and `getExportProjectMarkdownQueryKey` from generated client
   - `handleExport` async function that calls `exportMarkdown()`, creates a Blob URL, and triggers download
   - "Export Markdown" button in the project detail page header area, with loading state ("Exporting...")

**Architecture assessment:**

- ✅ **ADR-001 compliance restored.** The endpoint is now defined in `openapi.yaml`, and the generated client, Zod validators, and React Query hooks are all produced by Orval codegen. The API-first principle is satisfied.
- ✅ **End-to-end completeness.** The feature is now usable from the kg-engine frontend: a user can navigate to a project and click "Export Markdown" to download the knowledge base.
- ✅ **Streaming design preserved.** The backend still uses chunked streaming with batched L2 queries to prevent OOM on large projects.
- ✅ **Route registration confirmed.** `index.ts:14` imports `exportRouter` and `index.ts:39` mounts it via `router.use(exportRouter)`.

**Remaining gaps:**

1. **No error handling during stream** (carried forward from previous verification). If the database connection drops after `res.write()` has started but before `res.end()`, the client receives a truncated Markdown file with no error indicator. There is no `try/catch` around the streaming loop.

2. **L1 tags not included in Markdown export** (carried forward). The JSON export includes `l1Tags` but the Markdown export does not include any L1 tag information. Architectural cross-cuttings are lost.

3. **Commits not included in Markdown export** (carried forward). The JSON export includes `commits` but the Markdown export does not.

## Round 2 — Code Quality & Security Review

**Positive findings:**

1. **IDOR prevention added.** The new `checkProjectOwnership` middleware (export.ts:15-32) verifies that the authenticated user owns the project before allowing export. This is a significant security improvement over the previous verification.

2. **Consistent middleware application.** Both the JSON export (`export.ts:34`) and Markdown export (`export.ts:124`) now use the same `checkProjectOwnership` middleware, ensuring uniform access control.

3. **Generated code is not hand-edited.** The `api-client-react/src/generated/api.ts` file is properly generated by Orval, satisfying ADR-001's prohibition on hand-writing API types.

4. **Frontend uses generated hooks.** The `projects/[id].tsx` page imports `useExportProjectMarkdown` from the generated client, not a custom fetch wrapper.

**Issues identified:**

1. **🔴 Hardcoded fallback userId.** `export.ts:18`: `const userId = (req as any).user?.id || 1;` — When no authenticated user is present (no auth middleware sets `req.user`), the middleware defaults to `userId = 1`. This means unauthenticated requests will be treated as user ID 1, potentially granting access to projects owned by user 1. This is a security vulnerability if auth middleware is not yet deployed. The comment on line 17 acknowledges this: "Fake userId extracted from bearer token (implementation pending auth middleware)".

2. **🟡 No Zod validation on path parameter.** The endpoint uses raw `Number(req.params.id)` without a Zod validator. While `NaN` produces a 404 (no project found with NaN ID), this bypasses the project's standard validation pattern. The OpenAPI spec defines the `id` parameter as `type: integer`, but no generated Zod validator is applied in the route handler.

3. **🟡 No error handling during stream.** The streaming loop (export.ts:143-175) has no `try/catch`. If a database error occurs mid-stream, the client receives a truncated file. The `res.on('error')` event is not handled.

4. **🟡 N+1 query pattern.** For each L2 node in the batch, a separate query fetches its L3 nodes (export.ts:160-163). For projects with many L2 nodes, this produces N+1 queries per batch.

5. **🟢 No test coverage.** There are no unit tests or integration tests for the Markdown export endpoint. No tests verify: 200 response with valid Markdown, 404 for non-existent projects, 403 for unauthorized access, Content-Type header, or streaming behavior.

6. **🟢 Filename sanitization edge case.** `export.ts:130`: `project.name.replace(/[^a-zA-Z0-9]/g, "_")` produces degenerate filenames for non-ASCII project names (e.g., all underscores for a Chinese name).

7. **🟢 `any` type cast.** `export.ts:18`: `(req as any).user?.id` uses an `any` cast, bypassing TypeScript's type checking. This is a code smell but acknowledged as temporary pending auth middleware.

## Round 3 — Integration & Completeness Review

**End-to-end flow:**

1. User navigates to a project detail page in kg-engine
2. The page loads project data, graph, and commits via generated React Query hooks
3. User sees an "Export Markdown" button in the project header area (line 338-339)
4. Clicking the button triggers `handleExport` which calls `useExportProjectMarkdown.refetch()`
5. The generated hook calls `GET /api/projects/{id}/export/md`
6. The `checkProjectOwnership` middleware verifies the user owns the project
7. The server streams Markdown content with batched L2/L3 queries
8. The frontend receives a Blob, creates an object URL, and triggers a file download

**Integration assessment:**

- ✅ OpenAPI spec → Orval codegen → React Query hook → Frontend button: fully wired
- ✅ Backend route properly registered in `index.ts`
- ✅ Both JSON and Markdown exports use the same ownership middleware
- ✅ Streaming design prevents OOM for large projects

**Performance considerations:**

- ✅ Batched L2 queries (100 per batch) prevent loading entire project into memory
- ✅ Streaming response via `res.write()` avoids buffering entire Markdown in memory
- ⚠️ N+1 L3 queries per L2 batch could be slow for projects with many L2 nodes
- ⚠️ No `LIMIT` on L3 queries per L2 — a single L2 with thousands of L3 nodes could still cause memory pressure

**Completeness:**

- ✅ Backend endpoint: implemented
- ✅ OpenAPI spec: defined
- ✅ Generated client: produced
- ✅ Frontend UI: "Export Markdown" button present
- ✅ Authentication/authorization: middleware present (with hardcoded fallback)
- ❌ Tests: none
- ❌ Error handling during stream: missing
- ❌ L1 tags in Markdown output: missing
- ❌ Commits in Markdown output: missing

## Recommendations

1. **Replace hardcoded `userId = 1` fallback** with proper authentication middleware that rejects unauthenticated requests with 401. The fallback should be removed entirely, not just documented.
2. **Add error handling in the streaming loop** — wrap the batch loop in try/catch and call `res.status(500).end()` on failure. Consider adding a `res.on('error')` handler for client disconnects.
3. **Add Zod validation** for the `id` path parameter using the generated validator from `@workspace/api-zod`.
4. **Add integration tests** for the Markdown export endpoint: 200 with valid Markdown, 404 for non-existent project, 403 for unauthorized access, Content-Type header verification.
5. **(Optional) Batch the L3 query** — fetch all L3 nodes for a batch of L2 IDs in a single `IN (...)` query instead of one per L2.
6. **(Optional) Include L1 tags** in the Markdown export for completeness (e.g., as a tag section at the top of the document).

## Overall Verdict

**⚠️ WARN** — The Markdown export feature has been significantly improved since the last verification. The critical OpenAPI spec gap has been resolved — the endpoint is now defined in `openapi.yaml`, the Orval codegen has produced proper React Query hooks, and the kg-engine frontend has an "Export Markdown" button. The feature is now usable end-to-end. A new `checkProjectOwnership` middleware adds IDOR prevention. However, the hardcoded `userId = 1` fallback is a security risk, there is no error handling during the streaming response, no Zod validation, and no test coverage. The feature is functionally complete but has security and reliability gaps that should be addressed.
