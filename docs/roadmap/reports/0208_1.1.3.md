## Round 1 — Architecture & Design Review

### Design Intent

The design spec (arc42 section 10.2.3) mandates that all DB-backed integration tests use `withRollback()` to ensure test isolation — no DB state leaks between tests. ADR-008 further requires that `withRollback()` be used to test DLQ routing and mutex lock proofs.

### Implementation Analysis

**`runInRollbackTransaction` (lib/db/src/index.ts, lines 42-60):**
The implementation uses a clever pattern:
1. Opens a real PostgreSQL transaction via `baseDb.transaction()`
2. Uses `AsyncLocalStorage.run()` to make the transaction the active DB client via a Proxy
3. Executes the callback within the transaction context
4. After the callback completes, throws a `RollbackSignal` (a custom `Error` subclass) to force a rollback
5. Catches the `RollbackSignal` and returns the callback's return value
6. If any other error occurs, it re-throws (which also triggers rollback via the transaction)

**`withRollback` alias (artifacts/api-server/test/support/db.ts, line 3):**
A simple re-export: `export const withRollback = runInRollbackTransaction;`

**AsyncLocalStorage + Proxy pattern (lib/db/src/index.ts, lines 26-34):**
The `db` export is a `Proxy` that checks `transactionStore.getStore()` first, falling back to the base `baseDb`. This means any code that imports `db` from `@workspace/db` automatically participates in the rollback transaction when inside a `withRollback` callback — no need to pass a transaction handle around.

### Gaps / Observations

1. **The `RollbackSignal` pattern is unconventional but correct.** It uses exception flow control to force a PostgreSQL transaction rollback. This is a known pattern (similar to `TransactionRollbackError` in Django tests). The implementation correctly distinguishes between `RollbackSignal` (expected) and real errors (re-thrown).

2. **The unreachable line 59** (`throw new Error("Rollback transaction completed unexpectedly")`) is dead code — the transaction callback always either throws `RollbackSignal` or a real error. This is fine as a safety net but could be confusing to readers.

3. **The Proxy-based `db` export** ensures that factories and route handlers automatically use the transaction without explicit passing. This is elegant and reduces boilerplate in tests.

4. **Factory support for transaction client:** The factories in `factories.ts` accept an optional `client` parameter and use `getDb(client)` to route queries. However, the integration tests examined (`mcp-list-projects.test.ts` and `generate.test.ts`) do NOT pass a client to factories — they rely on the `AsyncLocalStorage` Proxy pattern instead. Both approaches work, but the Proxy approach is the primary path.

### Verdict for Round 1

The design is correctly implemented. The `withRollback()` mechanism provides proper test isolation via PostgreSQL transactions with automatic rollback. The `AsyncLocalStorage` + Proxy pattern is a clean solution that makes the transaction transparent to all code that imports `db`.

## Round 2 — Code Quality & Security Review

### Code Quality

**Strengths:**
- **Clean separation of concerns:** The DB module (`lib/db/src/index.ts`) handles transaction management; the test support module (`db.ts`) provides a convenient alias; factories handle test data creation.
- **Defensive design:** The `RollbackSignal` class is a dedicated type for control flow, making the intent clear. The `instanceof` check on line 53 correctly distinguishes expected rollbacks from real errors.
- **Type safety:** The generic `<T>` on `runInRollbackTransaction<T>` preserves the return type through the rollback mechanism.
- **Minimal API surface:** `withRollback` is a single function with a single callback parameter — easy to use correctly.

**Issues / Code Smells:**

1. **Minor: Duplicate import in `handlers.ts`** (lines 1 and 7): Both `HttpResponse, http` from `"msw"` are imported twice. This is harmless but untidy.

2. **Minor: `any` types in `openai.ts` handler** (line 3: `async function openaiChatHandler({ request }: any)`): The `any` type bypasses TypeScript checking. While common in test code, it could mask issues if the MSW API changes.

3. **Informational: `RollbackSignal` extends `Error`** — This is a control-flow-by-exception pattern. While functional, it means stack traces for `RollbackSignal` will appear in debugging tools. The `name` property is not overridden, so `error.name` will be `"RollbackSignal"` by default (from the class name), which is acceptable.

### Security

No security concerns. This is test infrastructure code that does not handle user input, authentication, or external data. The `RollbackSignal` pattern is confined to test execution.

### Verdict for Round 2

The code is well-structured, follows the project's conventions, and has no significant quality or security issues. The minor issues noted are cosmetic and do not affect correctness.

## Round 3 — Integration & Completeness Review

### Integration with Test Infrastructure

**Vitest configuration (`vitest.config.ts`):**
- Test patterns correctly include `artifacts/*/test/**/*.test.ts` (integration tests) and `*.unit.test.ts` (colocated unit tests)
- Setup file `artifacts/api-server/test/setup/setup.ts` is loaded globally
- Coverage includes `artifacts/*/src/**/*.{ts,tsx}` and `lib/*/src/**/*.{ts,tsx}`

**MSW integration (`setup.ts`):**
- MSW server starts before all tests, resets handlers after each test, and closes after all tests
- Environment variables are set with sensible defaults for testing (`DATABASE_URL`, `AI_INTEGRATIONS_OPENAI_API_KEY`, etc.)
- The pool is properly closed in `afterAll`

**Integration test examples:**
- `mcp-list-projects.test.ts` — Uses `withRollback` to create projects, L2 nodes, and L3 nodes, then queries the MCP endpoint and asserts the response. This is a clean, well-structured integration test.
- `generate.test.ts` — Uses `withRollback` to test the full generate pipeline with LLM mocking via MSW. Verifies that L1/L2/L3 nodes are created and the project status is updated.

### Test Coverage Assessment

**What's covered:**
- ✅ `withRollback()` is used in both integration test files
- ✅ Factories support both standalone and transaction-scoped usage
- ✅ MSW provides deterministic LLM responses for generate tests
- ✅ The `AsyncLocalStorage` + Proxy pattern makes transactions transparent

**What's NOT covered (gaps):**
- ❌ **No dedicated unit test for `runInRollbackTransaction` itself.** There's no test that directly verifies the rollback behavior (e.g., inserting data inside `withRollback` and confirming it's not visible outside). The integration tests implicitly rely on this working, but a focused unit test would be valuable.
- ❌ **No test for the error re-throw path.** If the callback throws a real error (not `RollbackSignal`), the error should propagate. This path is untested.
- ❌ **No concurrent test isolation test.** ADR-008 mentions "Concurrent test runners MUST attempt to claim the same pending task simultaneously" — this is not yet implemented.
- ❌ **No DLQ routing proof test.** ADR-008 requires a test that injects a deterministic-failing task and asserts it transitions to DEAD_LETTER_QUEUE after 3 ticks.

### Performance

The `withRollback()` pattern uses a single PostgreSQL transaction per test. This is efficient — PostgreSQL handles rollback quickly. The `AsyncLocalStorage` lookup is O(1) and adds negligible overhead. No performance concerns.

### Verdict for Round 3

The integration test infrastructure is well-designed and functional. The `withRollback()` mechanism is properly integrated with Vitest, MSW, and the factory system. The two existing integration tests demonstrate correct usage. The main gaps are the absence of direct unit tests for `runInRollbackTransaction` itself and the DLQ/concurrency proof tests required by ADR-08 — but these are noted as known gaps in the quality requirements (Section 10.3).

## Recommendations

1. **Add a focused unit test** for `runInRollbackTransaction` that directly verifies data inserted inside the callback is not visible after the call returns.
2. **Add an error-path test** that confirms real errors (non-`RollbackSignal`) propagate correctly.
3. **Remove the duplicate import** in `handlers.ts`.
4. **Consider removing or documenting** the dead code on line 59 of `index.ts` (e.g., replace with a comment explaining it's unreachable).
5. **Implement the ADR-008 proof tests** (DLQ routing and mutex lock) when the metabolism worker and job queue are implemented.

## Overall Verdict

**✅ PASS** — The `withRollback()` integration test support is correctly implemented and properly integrated with the test infrastructure. The `runInRollbackTransaction` function uses a sound PostgreSQL transaction rollback pattern with `AsyncLocalStorage` for transparent transaction propagation. The existing integration tests demonstrate correct usage. The identified gaps are minor and relate to test coverage of the infrastructure itself, not to the implementation correctness.
