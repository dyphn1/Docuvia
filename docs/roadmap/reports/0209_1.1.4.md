## Round 1 — Architecture & Design Review

### Design Intent

The design spec (AGENTS.md, arc42 section 10.2.3) mandates that test factories in `factories.ts` provide a convenient way to create DB state for integration tests. The factories should:

1. Support both `build()` (create in-memory objects) and `create()` (insert into DB) patterns
2. Accept overrides for customizing generated data
3. Be compatible with `withRollback()` for test isolation
4. Be "friendly to randomized/fuzz inputs"
5. Cover all tables needed for testing

### Implementation Analysis

**Current state: 6 factories for 19 tables**

The existing `factories.ts` (133 lines) provides factories for:

1. **ProjectFactory** — `build()` + `create()`, standalone table, auto-generates name/repoUrl
2. **L2NodeFactory** — `build()` + `create()`, auto-creates project if no projectId
3. **L3NodeFactory** — `build()` + `create()`, auto-creates L2 node (and transitively a project) if no l2NodeId
4. **CommitFactory** — `build()` + `create()`, auto-creates project if no projectId
5. **DocumentFactory** — `build()` + `create()`, auto-creates project if no projectId
6. **ActivityLogFactory** — `build()` + `create()`, auto-creates project if no projectId

**Missing factories for 13 tables:**

- `L1TagFactory` — l1_tags (standalone table, no FK dependencies)
- `ReviewTaskFactory` — review_tasks (standalone table with enums)
- `CorrectionExampleFactory` — correction_examples (depends on projects)
- `PullRequestFactory` — pull_requests (depends on projects)
- `ProjectIntegrationFactory` — project_integrations (depends on projects)
- `NotificationFactory` — notifications (depends on projects)
- `SubscriptionFactory` — subscriptions (depends on projects, needs two projects)
- `LlmConfigFactory` — llm_configs (depends on projects)
- `PromptTemplateFactory` — prompt_templates (depends on projects)
- `NodeLinkFactory` — node_links (depends on l2_nodes, needs two L2 nodes)
- `JobQueueFactory` — job_queue (standalone table)
- `ErrorReportFactory` — error_reports (depends on projects and job_queue)
- `CommitL2LinkFactory` — commit_l2_links (depends on commits and l2_nodes)

### Gaps / Observations

1. **Factory coverage is only 31.6% (6/19 tables).** The majority of tables lack factories, which means tests for features involving these tables must manually construct INSERT statements or raw data objects. This increases test boilerplate and reduces consistency.

2. **Missing L1TagFactory is a significant gap.** L1 tags are a core part of the knowledge graph hierarchy (L1→L2→L3). The `generate.test.ts` integration test uses MSW to mock LLM responses that produce L1 tags, but there's no factory to directly create L1 tags in tests. This makes it harder to write tests that need pre-existing L1 tag state.

3. **Missing ReviewTaskFactory blocks review system testing.** The review system (Milestone 5) depends on `review_tasks` table. Without a factory, tests for review workflows must manually construct the enum values (`anchor`, `correct`, `validate`, `merge`) and status values (`pending`, `approved`, `rejected`, `deferred`).

4. **DocumentFactory doesn't support misc pool.** The `documents` schema has `projectId` as nullable (ADR-012 misc pool support), but `DocumentFactory.build()` requires `projectId` as a mandatory parameter. This means the factory cannot create unaffiliated misc pool documents.

5. **DocumentFactory doesn't handle `contentHash`.** The schema includes `contentHash` (SHA-256) and `affiliatedAt` columns, but the factory doesn't generate or allow overriding these fields.

6. **Faker seed is set globally** (`faker.seed(123)` at line 15). This ensures deterministic test execution, which is good. However, it means all factory calls across all tests share the same faker sequence, which could cause subtle ordering-dependent behavior if tests run in different orders.

### Verdict for Round 1

The factory pattern is well-designed and correctly implemented for the 6 tables that have factories. The `build()`/`create()` pattern with optional overrides is clean and follows the project's conventions. However, the coverage gap is significant — 13 of 19 tables lack factories, which creates a substantial barrier to writing comprehensive integration tests. The missing `L1TagFactory` and `ReviewTaskFactory` are particularly impactful since they are needed for testing core knowledge graph and review workflows.

## Round 2 — Code Quality & Security Review

### Code Quality

**Strengths:**

- **Consistent pattern:** All 6 factories follow the same `build()`/`create()` pattern with optional overrides, making the API predictable.
- **Auto-creation of dependencies:** Factories that depend on other entities (e.g., `L3NodeFactory` → L2Node → Project) auto-create their dependencies when not provided. This reduces boilerplate in tests.
- **Deterministic data:** `faker.seed(123)` ensures reproducible test data across runs.
- **Clean separation:** `build()` returns plain objects (good for unit tests), `create()` inserts into DB (good for integration tests).
- **Transaction support:** All `create()` methods accept an optional `client` parameter for use with `withRollback()`.

**Issues / Code Smells:**

1. **`any` types bypass TypeScript checking** (line 18, and all `create` method `client` parameters):

   ```typescript
   const getDb = (client?: any) => client ?? db;
   // ...
   create: async (overrides?: Partial<InsertProject>, client?: any) => {
   ```

   The `any` type for `client` means TypeScript won't catch if the wrong type is passed. This should be typed as `DbClient` (from `lib/db/src/index.ts`).

2. **Inconsistent parameter signatures across factories:**
   - `ProjectFactory.create(overrides?, client?)` — no required params
   - `L2NodeFactory.create(overrides?, client?)` — projectId in overrides
   - `L3NodeFactory.create(overrides?, client?)` — l2NodeId in overrides
   - `CommitFactory.create(overrides?, client?)` — projectId in overrides
   - `DocumentFactory.create(overrides?, client?)` — projectId in overrides
   - `ActivityLogFactory.create(overrides?, client?)` — projectId in overrides

   The `build()` methods have explicit required params (e.g., `build(projectId, overrides?)`) but `create()` methods put everything in `overrides`. This inconsistency could lead to confusion — a caller might expect `create(projectId, overrides?)` to match the `build()` signature.

3. **DocumentFactory.build requires projectId but schema allows null:**

   ```typescript
   build: (projectId: number, overrides?: Partial<InsertDocument>): InsertDocument => ({
   ```

   The `projectId` parameter is required (not optional), but the schema defines `projectId` as `.references(...)` without `.notNull()`. This means the factory cannot create misc pool documents (where `projectId` is null).

4. **No validation of enum values:** The factories don't expose or document the valid enum values for fields like `review_tasks.taskType`, `review_tasks.status`, `l2_nodes.type`, `l3_nodes.nodeType`, etc. Test authors must look up the schema files to find valid values.

5. **Missing `InsertJobQueue` type export:** The `job_queue.ts` schema uses `typeof jobQueueTable.$inferInsert` instead of the Zod-inferred type used by all other schemas. This inconsistency means the factory pattern (which relies on Zod schemas) would need special handling for this table.

### Security

No security concerns. This is test infrastructure code that generates fake data using `@faker-js/faker`. No user input, authentication, or external data handling is involved.

### Verdict for Round 2

The code quality is good for the existing 6 factories. The main issues are the use of `any` types (which reduces type safety), the inconsistent parameter signatures between `build()` and `create()`, and the DocumentFactory's inability to create misc pool documents. These are minor issues that don't affect correctness but reduce developer experience and type safety.

## Round 3 — Integration & Completeness Review

### Integration with Test Infrastructure

**Vitest configuration (`vitest.config.ts`):**

- Test patterns correctly include `artifacts/*/test/**/*.test.ts` (integration tests) and `*.unit.test.ts` (colocated unit tests)
- Setup file `artifacts/api-server/test/setup/setup.ts` is loaded globally
- Coverage includes `artifacts/*/src/**/*.{ts,tsx}` and `lib/*/src/**/*.{ts,tsx}`

**Integration test usage:**

- `mcp-list-projects.test.ts` — Uses `ProjectFactory`, `L2NodeFactory`, `L3NodeFactory` to set up project hierarchy, then queries MCP endpoint. Clean usage pattern.
- `generate.test.ts` — Uses `ProjectFactory`, `CommitFactory` to set up project with commits, then triggers generate pipeline with MSW-mocked LLM responses.

**withRollback integration:**

- Both integration tests wrap their test bodies in `withRollback(async () => { ... })`
- Factories work correctly inside the rollback transaction via the `AsyncLocalStorage` + Proxy pattern
- No data leaks between tests

### Test Coverage Assessment

**What's covered:**

- ✅ 6 factories with `build()` and `create()` methods
- ✅ Auto-creation of transitive dependencies (L3 → L2 → Project)
- ✅ Optional `client` parameter for transaction support
- ✅ Override support for customizing generated data
- ✅ Deterministic faker seed
- ✅ Integration tests demonstrate correct usage with `withRollback()`

**What's NOT covered (gaps):**

- ❌ **13 of 19 tables have no factory** — l1_tags, review_tasks, correction_examples, pull_requests, project_integrations, notifications, subscriptions, llm_configs, prompt_templates, node_links, job_queue, error_reports, commit_l2_links
- ❌ **No unit tests for factories themselves** — no `*.unit.test.ts` files exist in the entire project
- ❌ **DocumentFactory cannot create misc pool documents** (projectId is required but schema allows null)
- ❌ **DocumentFactory doesn't handle contentHash** — the SHA-256 content hash column is not populated by the factory
- ❌ **No factory for standalone tables** — l1_tags and job_queue are standalone (no FK dependencies) but have no factories
- ❌ **No factory for junction tables** — node_links and commit_l2_links are junction tables needed for graph traversal tests

### Performance

No performance concerns. Factory `create()` methods use standard Drizzle ORM inserts. The faker data generation is fast. The auto-creation of dependencies adds minimal overhead (at most 2 additional INSERTs for L3Node → L2Node → Project chain).

### Verdict for Round 3

The factories integrate well with the test infrastructure. The existing 6 factories are properly used in both integration tests and work correctly with `withRollback()`. The main gap is the sheer number of missing factories — 13 tables without factories means that any test involving these tables must manually construct test data, which is error-prone and inconsistent. The most critical missing factories are `L1TagFactory` (needed for knowledge graph tests), `ReviewTaskFactory` (needed for review system tests), and `NodeLinkFactory` (needed for graph traversal tests).

## Recommendations

1. **Add factories for all 13 missing tables.** Priority order based on testing needs:
   - **High priority:** `L1TagFactory`, `ReviewTaskFactory`, `NodeLinkFactory` — needed for core feature tests
   - **Medium priority:** `CorrectionExampleFactory`, `PullRequestFactory`, `ProjectIntegrationFactory`, `NotificationFactory`, `SubscriptionFactory`, `LlmConfigFactory`, `PromptTemplateFactory` — needed for Milestone 5/6 feature tests
   - **Low priority:** `JobQueueFactory`, `ErrorReportFactory`, `CommitL2LinkFactory` — needed for metabolism and DLQ tests

2. **Fix DocumentFactory to support misc pool documents.** Make `projectId` optional in `build()`:

   ```typescript
   build: (overrides?: Partial<InsertDocument>): InsertDocument => ({
     projectId: null,
     filename: faker.system.fileName(),
     ...
   })
   ```

3. **Add `contentHash` generation to DocumentFactory.** Use a hash of the content or a random hex string.

4. **Type the `client` parameter properly.** Replace `any` with the `DbClient` type from `lib/db/src/index.ts`.

5. **Consider aligning `create()` signatures with `build()`** — extract required FK params as explicit parameters rather than burying them in overrides.

6. **Add unit tests for factories** to verify that `build()` produces valid insert objects and `create()` correctly inserts into the database.

## Overall Verdict

**⚠️ WARN** — The existing 6 factories are well-designed and correctly implemented, following a clean `build()`/`create()` pattern with override support and transaction compatibility. They integrate properly with `withRollback()` and the Vitest test infrastructure. However, the coverage is significantly incomplete: only 6 of 19 tables (31.6%) have factories. The missing factories for `l1_tags`, `review_tasks`, `node_links`, and other core tables create a substantial barrier to writing comprehensive integration tests. The `DocumentFactory` also doesn't support the misc pool use case (nullable `projectId`) or the `contentHash` field. These gaps should be addressed to achieve the design spec's goal of convenient DB state creation for all test scenarios.
