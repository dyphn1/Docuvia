## Round 1 — Architecture & Design Review

### Design Intent

The design specifies stream-based Git ingestion using `child_process.spawn` (not `execFile`) to avoid buffering large git outputs into memory. The ingestion flow is: clone → stream git log output via readline → fetch diffs per commit → score/filter via `scoreCommit()` → batch insert into commits table. Both full and incremental modes are supported, with the latter using the `lastGitIngestedAt` cursor column on the projects table.

### Implementation Analysis

**`LocalGitClient.clone()` (git-client.ts, line 26-30):**
Uses `execFileAsync("git", ["clone", "--depth=500", ...])`. This is a single-shot operation — acceptable to use `execFile` here since clone output is minimal. Uses a temp directory with UUID for isolation. ✅

**`LocalGitClient.getCommits()` (git-client.ts, line 32-95):**
Uses `spawn("git", args, ...)` with `readline.createInterface({ input: child.stdout })`. This is the correct streaming approach per the design spec. Parses the custom `--format=COMMIT_SEP%n%H%n%s%n%an%n%aI%n%b` format line-by-line. ✅

**`LocalGitClient.getDiff()` (git-client.ts, line 141-170):**
Uses `spawn("git", ["show", "--format=", sha])` with `readline.createInterface`. The comment on line 150-151 explicitly states the reason: "avoiding V8's execFile limits." This matches the design intent. ✅

**Route handler `POST /projects/:id/ingest/git` (ingest.ts, line 35-99):**
Follows the correct flow: validate → clone → getCommits → getDiff per commit → processIngestion → cleanup. Supports both full and incremental mode. ✅

**OpenAPI spec alignment:**
The `GitIngestInput` schema defines `repoUrl`, `branch`, `limit`, `githubToken`, `mode` fields. The route handler's `GitIngestSchema` (ingest.ts lines 23-29) matches this exactly. The `GitIngestResult` schema defines `commitsIngested`, `commitsSkipped`, `totalFetched`. The response (ingest.ts lines 87-92) matches. ✅

### Gaps / Observations

1. **Memory concern — all diffs buffered ingest.ts lines 60-71:** The route handler iterates over all commits and calls `await client.getDiff(c.sha)` for each, accumulating all diffs in the `gitItems` array before passing to `processIngestion`. For the default limit of 100 commits (max 500), this could buffer substantial diff data in memory simultaneously. A streaming/chunked approach would be more memory-efficient.

2. **Redundant `lastGitIngestedAt` updates:** The `lastGitIngestedAt` cursor is updated in two places:
   - `ingest.ts` line 80-85: In the route handler after `processIngestion` returns
   - `ingestion-pipeline.ts` line 104-106: Inside `processIngestion()` for each batch
   
   The route handler's update (ingest.ts line 80-85) is conditional on `mode === "incremental"`, while the pipeline's update (line 104-106) runs unconditionally for every git ingestion. This means the pipeline always overwrites the cursor, making the route handler's update redundant in incremental mode. In full mode, the pipeline also updates `lastGitIngestedAt`, which may not be intended.

3. **No timeout on spawned processes:** Neither `getCommits` nor `getDiff` set a timeout. A hung `git log` or `git show` process (e.g., on a corrupted repo) would block the request indefinitely.

4. **No stderr capture for `getCommits`:** The `spawn` for `git log` (line 49) only reads stdout via readline. Stderr is not captured, so if git log produces error output (e.g., "fatal: bad object"), the error will go unnoticed. The `close` handler on line 89 only checks the exit code.

### Verdict for Round 1

The architecture is fundamentally sound and matches the design spec. The `spawn` + `readline` pattern is correctly used for streaming. The main gaps are: (a) memory concern from buffering all diffs, (b) redundant cursor updates, (c) no process timeout, and (d) missing stderr capture.

## Round 2 — Code Quality & Security Review

### Code Quality

**Strengths:**
- **Clean separation of concerns:** `LocalGitClient` handles Git CLI interactions; `ingest.ts` handles HTTP concerns; `ingestion-pipeline.ts` handles DB operations; `commit-scorer.ts` handles scoring.
- **Proper cleanup:** `client.cleanup()` is called in a `finally` block (ingest.ts line 97), ensuring temp directories are removed even on error.
- **Batch processing:** `processIngestion` processes commits in batches of 50 (ingestion-pipeline.ts line 66), preventing unbounded memory/CPU spikes.
- **Input validation:** The route uses Zod schema validation (`GitIngestSchema.parse`) on the request body.
- **Length limits:** Message text is sliced to 4000 chars (line 93), and the limit parameter is capped at 500 (ingest.ts line 44).

**Issues / Code Smells:**

1. **🟡 Medium — Noise commits are ingested, not filtered:** `scoreCommit()` returns `{ valid: false }` for noise patterns (merge commits, version bumps, etc.), but `processIngestion` at ingestion-pipeline.ts line 90 still inserts the commit with `valid: false`. The design (arc42 section 4.2) describes `scoreCommit` as a "signal/noise filter," suggesting noise commits should be skipped entirely rather than stored with a `valid=false` flag. Currently, noise commits consume DB space and will need to be filtered at query time.

2. **🟡 Medium — Silent diff failure:** `getDiff()` (git-client.ts lines 157-168) resolves with an empty string `""` on both non-zero exit codes and error events. While this prevents a single failed diff from aborting the entire ingestion, it means commits will be ingested with empty diffs without any warning logged at a visible level. The `logger.warn` calls are present but the ingestion pipeline has no way to know the diff was empty due to failure vs. genuinely empty.

3. **🟢 Low — `getCommits` mixes async iteration with Promise wrapping:** The method uses `for await (const line of rl)` (async iteration over readline) but then wraps the `close` handler in a `new Promise()` (git-client.ts lines 88-94). This "async iteration + Promise constructor" mixing works but is a known anti-pattern that can lead to subtle bugs if the async iteration throws.

4. **🟢 Low — `getDiff` uses readline for binary-safe data:** `git show` can contain binary diff content. Using `readline.createInterface` (git-client.ts line 146) splits on newlines, which could corrupt binary content. For commit ingestion this is likely acceptable (diffs are text), but it's a latent issue.

5. **🟢 Low — Dead code: error handler resolves instead of rejecting:** In `getDiff`, the `error` handler on line 165-168 calls `resolve("")` instead of `reject(e)`. This means spawn errors (e.g., git not found) are silently swallowed and the diff will be empty.

### Security

1. **🟡 Medium — `repoUrl` passed directly to `git clone`:** The `repoUrl` from the request body (or project record) is passed directly to `execFileAsync("git", ["clone", ..., repoUrl])` without URL validation. While the route handler checks if `repoUrl` is truthy, it doesn't validate the URL format. A malicious or malformed URL could potentially exploit shell injection if the underlying `execFile` implementation is not properly escaping arguments. However, since `execFile` (not `exec`) is used, arguments are passed directly to the process without shell interpretation, mitigating injection risk. The primary risk is cloning an unintended repository.

2. **🟢 Low — No authentication for the ingest endpoint:** The `POST /projects/:id/ingest/git` endpoint doesn't require authentication. Any client can trigger git ingestion for any project, potentially causing resource exhaustion (cloning large repos). This may be intentional for a local/dev setup but is a concern for production.

### Verdict for Round 2

The code is well-structured and follows the project's conventions. The main concerns are: noise commits being stored rather than skipped, silent diff failures, and the lack of URL validation for `repoUrl`. No critical security vulnerabilities given `execFile` (not `exec`) is used.

### Integration with System Components

**OpenAPI / Zod alignment:**
- The `GitIngestInput` schema in OpenAPI defines the same fields as the route's `GitIngestSchema` ✅
- The `GitIngestResult` schema matches the response format ✅
- The `IngestStatusResponse` schema includes `lastGitIngestedAt` and `pendingCommits` ✅

**Factory support:**
- `factories.ts` supports creating commit records for testing (though no git-specific ingestion tests exist)

### Test Coverage Assessment

**What's covered:**
- ✅ Core DB schema and migrations exist for all required tables
- ✅ `scoreCommit()` function is implemented and can be unit tested
- ✅ Integration test infrastructure (`withRollback`, MSW) is available

**What's NOT covered (gaps):**
- ❌ **No tests for `LocalGitClient`:** No unit or integration tests verify that git log parsing, diff fetching, or clone/cleanup work correctly
- ❌ **No tests for the `POST /projects/:id/ingest/git` endpoint:** No integration test creates a project, triggers git ingestion, and asserts the response
- ❌ **No tests for incremental ingestion:** The incremental mode (using `lastGitIngestedAt` cursor) is completely untested
- ❌ **No tests for `scoreCommit()` behavior in the pipeline:** While `scoreCommit` can be unit tested, there's no test verifying that noise commits receive `valid=false` or that the scoring affects ingestion behavior
- ❌ **No mock for `child_process.spawn`:** Unlike external HTTP APIs (mocked via MSW), there's no test fixture mocking git CLI output

### Performance

- The `spawn` + `readline` approach is efficient for streaming ✅
- Batch size of 50 in `processIngestion` prevents unbounded memory spikes ✅
- The `getDiff` calls are sequential (ingest.ts line 61: `for...of` with `await`), which is safe but slow for large commit counts. Parallel diff fetching with a concurrency limit could improve throughput.
- The quality requirement specifies "1000 commits < 30s" — the current sequential diff fetching likely won't meet this target for large repos, as each `git show` call involves process spawn overhead.

### Verdict for Round 3

The feature integrates correctly with the DB schema, OpenAPI spec, and pipeline architecture. The primary gap is the complete absence of tests for the git ingestion path. Performance may be a concern for large repos due to sequential diff fetching and multiple process spawns.

## Findings Summary

| # | Severity | Finding |
|---|----------|---------|
| 1 | 🟡 Medium | Noise commits (merge, bump, chore) are stored with `valid=false` instead of being skipped, contrary to the design's "signal/filter" intent. scoreCommit returns `valid: false` but processIngestion still inserts. (ingestion-pipeline.ts:89-97) |
| 2 | 🟡 Medium | `lastGitIngestedAt` cursor is updated redundantly in both `processIngestion` (unconditionally, ingestion-pipeline.ts:104-106) and the route handler (conditionally, ingest.ts:80-85). The unconditional update in the pipeline means full-mode ingestion also updates the cursor. |
| 3 | 🟡 Medium | No tests exist for the git ingestion path — no unit tests for `LocalGitClient`, no integration tests for the ingest endpoint, no tests for incremental mode. |
| 4 | 🟡 Medium | All diffs are buffered in memory before processing (ingest.ts:60-71). For 500 commits with large diffs, this could cause OOM. |
| 5 | 🟢 Low | `getDiff()` silently swallows errors by resolving with empty string instead of rejecting (git-client.ts:165-168). Spawn errors (e.g., git not found) are invisible. |
| 6 | 🟢 Low | `getCommits()` doesn't capture stderr — git log error messages are lost (git-client.ts:49). |
| 7 | 🟢 Low | No timeout on spawned git processes — a hung git process blocks indefinitely. |
| 8 | 🟢 Low | `getCommits()` mixes `for await` async iteration with Promise constructor wrapping (git-client.ts:57-94) — a known anti-pattern. |
| 9 | 🟢 Low | Diff fetching is sequential (for...of + await), which won't meet the 1000-commits-in-30s quality target for large repos. |

## Recommendations

1. **Skip noise commits entirely** during ingestion rather than storing them with `valid=false`. If storage is desired for audit purposes, add a separate `isNoise` boolean or filter at the DB query level. (Addresses finding #1)

2. **Remove the redundant `lastGitIngestedAt` update** from `processIngestion` (ingestion-pipeline.ts:104-106) and keep only the route handler's conditional update. Alternatively, make the pipeline's update conditional on an explicit parameter. (Addresses finding #2)

3. **Add integration tests for git ingestion:** Create a test that clones a small test repository (or mocks `child_process.spawn` output) and verifies the full ingestion flow including incremental mode. (Addresses finding #3)

4. **Stream diffs in batches** instead of buffering all diffs: process each batch of commits (with their diffs) through `processIngestion` immediately, then fetch the next batch. (Addresses finding #4)

5. **Add a timeout option** to spawned git processes and reject on timeout. (Addresses finding #7)

6. **Capture stderr** in `getCommits` and include it in error messages for better debuggability. (Addresses finding #6)

7. **Consider parallel diff fetching** with a concurrency limit (e.g., 5-10 concurrent `git show` processes) to improve throughput for large repos. (Addresses finding #9)

## Overall Verdict

**⚠️ WARN** — The Git ingestion feature is functionally implemented and correctly uses `child_process.spawn` with `readline` for streaming, matching the design specification. The OpenAPI contract is properly defined and aligned with the route handler. However, the feature has notable gaps: (1) noise commits are stored rather than filtered, (2) the `lastGitIngestedAt` cursor has a redundant update path, (3) there are zero tests for the entire git ingestion path, and (4) memory usage could be problematic for large ingestions due to full diff buffering. The issues are addressable and do not require architectural changes.
