## Round 1 — Architecture & Design Review

### Design ↔ Implementation Alignment

**✅ Correctly implemented:**

1. **`svn-client.ts` matches the design specification exactly.** The design says "SVN CLI wrapper (`svn log --xml`, `svn diff`)". The implementation provides:
   - `getSvnLog()` — uses `spawn("svn", ["log", "--xml", "-r", ...])` with streaming SAX XML parser (`sax` library), yielding `SvnRevisionInfo` objects one at a time via `AsyncGenerator`.
   - `getSvnDiff()` — uses `execFileAsync("svn", ["diff", "-c", revision, url, ...])` returning unified diff text.

2. **Streaming architecture is correct.** `getSvnLog` uses `spawn` (not `exec`) with stdout piped into a SAX parser, enabling constant-memory processing of arbitrarily large SVN logs — consistent with the ADR-008 streaming approach.

3. **Incremental ingestion cursor.** The `projects.lastSvnRevision` column (schema) is used in the route handler (line 124-126) to compute `startRevision = lastSvnRevision + 1` in incremental mode. The value is updated after ingestion (lines 181-186).

4. **Batch processing.** SVN log entries are batched in groups of 50 before calling `processIngestion()`, consistent with the design's batching strategy.

5. **DB schema alignment.** `projectsTable` has `svnUrl`, `lastSvnRevision` columns. `commitsTable` has `revision` (integer) and `vcsType` (text) to distinguish SVN from Git commits.

6. **OpenAPI contract.** The `POST /projects/{id}/ingest/svn` endpoint is fully implemented. Request body validated with `IngestSvnBody` (Zod, generated from OpenAPI). Response shape matches `SvnIngestResult`.

### Gaps / Deviations

1. **❌ Missing `VcsIngestAdapter` interface and `SvnIngestAdapter` class.** The design (08-cutting-concepts.md §8.3 POP) explicitly defines a `VcsIngestAdapter` interface:
   ```
   interface VcsIngestAdapter {
     ingest(input: IngestInput): Promise<IngestResult>;
   }
   ```
   Neither this interface nor a `SvnIngestAdapter` implementation exists anywhere in the codebase. The SVN ingestion logic is embedded directly in the `ingest.ts` route handler rather than being abstracted behind the adapter protocol. The Git ingestion suffers from the same issue — both bypass the intended POP pattern.

   **Impact:** Code duplication, harder unit testing (cannot mock the adapter), and a direct violation of the project's mandatory coding rules.

2. **⚠️ URL validation regex excludes `svn+ssh://`.** The route handler (line 117) validates:
   ```typescript
   if (!/^http?:\/\/|^svn:\/\//.test(svnUrl))
   ```
   This allows `http://`, `https://`, and `svn://` but **rejects `svn+ssh://`**, which is explicitly listed as a valid example in the OpenAPI schema description: "SVN repository URL (e.g. svn+ssh://... or https://...)". This is a spec-implementation mismatch.

3. **⚠️ `processIngestion` for SVN stores `diff` concatenated into `message`.** At line 136-141:
   ```typescript
   const fullMessage = c.diff ? `${c.message}\n\n${c.diff}` : c.message;
   // ...
   message: fullMessage.slice(0, 4000),
   ```
   Git ingestion stores only `c.message` in the message field (line 93). SVN conflates the commit message with the full diff, which means:
   - The actual commit message is lost after 4000 chars when diff is large.
   - Query results will show diffs instead of clean commit messages.
   - This is inconsistent with Git processing.

## Round 2 — Code Quality & Security Review

### Strengths

1. **No shell injection vulnerability.** Both `spawn` and `execFile` are used with argument arrays (not shell strings), preventing command injection even from malicious `svnUrl`, `username`, or `password` values.

2. **Proper streaming parser.** The SAX-based XML parser (`sax.createStream`) processes the SVN log incrementally without loading the entire XML into memory. The `AsyncGenerator` with a queue/promise pattern is well-implemented.

3. **ENOENT handling.** Both `getSvnLog` (line 131-136) and `getSvnDiff` (line 194-196) detect when the `svn` binary is not installed and return a clear, actionable error message.

4. **AbortController cleanup.** The `finally` block (line 165-168) calls `abortController.abort()` and `svnProcess.kill()` to prevent zombie processes.

5. **Input validation.** The route validates the request body with `IngestSvnBody` (Zod), checks project existence, and validates SVN URL format.

### Issues Found

1. **⚠️ No transactional safety for SVN commits (unlike Git).** The Git path in `processIngestion` (line 72) wraps its batch in `db.transaction()`. The SVN path (line 118) processes each revision individually without any transaction wrapper. If the process crashes mid-batch, some revisions will be inserted and others won't, with no rollback. The route-level `flushBatch` does batch commits into `processIngestion`, but `processIngestion` itself does not wrap the loop body for SVN type in a transaction.

   **Recommendation:** Wrap the SVN insert loop in `db.transaction()` or at minimum process each revision as an atomic unit so partial batches can be safely retried.

2. **⚠️ `password` visible in process arguments.** The password is passed as a command-line argument to `svn` via both `spawn` and `execFile`. While this avoids shell injection, on some systems command-line arguments are visible to all users via `ps` or `/proc`. Consider using SVN's `--password-file` option or environment variables if supported.

3. **⚠️ OpenAPI response codes incomplete.** The route can return:
   - `200` — documented ✅
   - `400` (validation error) — **not documented** in OpenAPI spec
   - `404` — documented ✅
   - `502` (SVN log failure) — **not documented** in OpenAPI spec
   - `500` (from `processIngestion` errors) — **not documented** in OpenAPI spec

4. **⚠️ Redundant Zod parsing.** Line 108 uses `IngestSvnBody.parse(req.body)` for the full body, but line 113 then parses `mode` again separately with `SvnModeSchema.parse(req.body)`. The `mode` is already part of `SvnIngestInput` and validated by `IngestSvnBody`. This is redundant.

5. **⚠️ No error response standardization for Zod failures.** Lines 109-111 return the raw Zod error object as `details` in the 400 response. This leaks internal validation details that could reveal schema structure.

6. **⚠️ `response` object is not typed.** The route handler parameter `res` is not typed as `express.Response`, losing type safety for response methods.

## Round 3 — Integration & Completeness Review

### Integration Correctness

1. **Endpoint wiring.** The ingest route is exported as default from `ingest.ts` and should be mounted by the express app. Integration with the projects table for `lastSvnRevision` cursor is correct.

2. **Score commit applies to SVN.** The `scoreCommit()` signal/noise filter is correctly called for SVN items (line 135), matching the design spec that requires filtering for all VCS sources.

3. **Activity logging and notifications.** The SVN path calls `logAndNotify()` (line 151), which writes to `activity_log`, updates `projects.updatedAt`, creates notification rows for subscribers, and dispatches to external integrations. This is consistent with the Git path.

4. **Hash generation for SVN.** SVN revisions use `hash: \`svn:R${c.revision}\`` (line 140), providing a unique identifier per project+revision. The duplicate check uses `projectId + vcsType + revision` (lines 119-128), which is correct.

5. **Ingest status endpoint.** The `GET /projects/:id/ingest/status` endpoint (lines 191-208) correctly exposes `lastSvnRevision` and `vcsType`, enabling clients to determine the next starting revision.

### Missing Coverage

1. **❌ No tests for SVN ingestion.** The search for `*.test.ts` files containing "svn" returned zero results. No unit tests for `getSvnLog`, `getSvnDiff`, or the SVN ingest route exist. The Git ingestion also lacks integration tests.

2. **❌ No mock SVN CLI fixture.** For integration testing, there are no MSW fixtures or mock SVN binary fixtures that would allow testing the SVN ingest path without requiring a real SVN installation.

3. **⚠️ `svn+ssh://` URLs blocked.** As noted in Round 1, the URL validation regex prevents `svn+ssh://` URLs, which are common in enterprise environments. This is a functional gap.

## Overall Verdict

**⚠️ WARN**

The SVN ingestion feature is functionally implemented and correctly follows the core design: streaming `svn log --xml` via spawn, `svn diff` via execFile, incremental cursor via `lastSvnRevision`, batch processing, and signal/noise filtering via `scoreCommit()`. Security is generally sound with no shell injection vulnerabilities.

However, the feature deviates from the project's mandatory POP architecture pattern (no adapter interface/implementation), has inconsistent transaction handling compared to Git, stores diffs inside the message field, blocks valid `svn+ssh://` URLs, and has zero test coverage. These issues collectively warrant a ⚠️ WARN rating rather than a clean pass.
