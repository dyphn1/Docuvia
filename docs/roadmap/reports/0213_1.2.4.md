## Round 1 — Architecture & Design Review

### Design Completeness

The design spec in `docs/archive_v1_design/phase-2-input-layer/10-build-artifact-parser.md` and the implementation plan in `docs/ai_plans/implement_build-artifact-parser.md` correctly describe the four artifact subtypes:
1. **Linker Map** (`.map`) — GCC ld / MSVC / EDK2 formats
2. **Firmware Volume** (`.fv`) — EDK2 DSC-style FV sections
3. **Flash Descriptor** (`.fd`) — EDK2 FDF-style flash regions
4. **Compile Log** (`.log`, `.txt`) — GCC/Clang/MSVC diagnostics

The implementation plan clearly defines the data flow: Upload → `detectDocType()` → `extractText()` → `build-artifact-parser.ts` → structured Markdown stored in `documentsTable.content`.

### Architecture Gaps

1. **Dedicated endpoint (`POST /projects/:id/ingest/build-artifact`) uses `req.file.path` instead of `req.file.buffer`** — The `documentUpload` middleware uses `multer.memoryStorage()` (line 16 of `upload.ts`), which means `req.file.path` is `undefined` and `req.file.buffer` holds the data. The dedicated endpoint at `ingest.ts:369` calls `computeHashFromStream(filePath)` with `req.file.path`, which would throw a runtime error. This endpoint is non-functional.

2. **Dedicated endpoint bypasses `extractBuildArtifactText()`** — Even if the path issue were fixed, the dedicated endpoint at `ingest.ts:369-393` reads the raw file content, strips ANSI codes, and passes `strippedContent` directly to `processIngestion`. It never calls `extractBuildArtifactText()` from `build-artifact-parser.ts`, so the structured Markdown parsing is completely bypassed. The raw content is stored in `documents.content` instead of the formatted Markdown.

3. **Dedicated endpoint uses `projectName: "Project ${projectId}"` (hardcoded)** — At `ingest.ts:378`, the project name is hardcoded instead of fetching it from the database, unlike the `/ingest/document/upload` handler which fetches the project first.

4. **No OpenAPI spec update** — The implementation plan listed the dedicated endpoint as "optional". The code in `ingest.ts` implements it, but there is no corresponding entry in the OpenAPI spec (`lib/api-spec/openapi.yaml` was not updated with `POST /projects/{id}/ingest/build-artifact`). This means no Zod validation schema was codegen'd for this endpoint.

### Checklist Body Status Consistency

The checklist marks item 1.2.4 as `- [x] 1.2.4  ✅  Build artifact parser`, indicating it is considered "Done" by the developer. However, the above gaps show the integration is incomplete/broken.

## Round 2 — Code Quality & Security Review

### Positive Findings

- **No external dependencies** — Parser uses only Node.js built-in regex, consistent with the design rationale.
- **Well-structured types** — All 5 exported interfaces (`BuildArtifactSubtype`, `MemorySection`, `FirmwareModule`, `BuildDiagnostic`, `ParsedBuildArtifact`) are clean and match the design spec exactly.
- **Summary-first Markdown output** — `formatAsBuildArtifactText()` correctly places the Summary section first, which is critical because `generate.ts:646` slices document content to 800 chars.
- **GCC + MSVC pattern coverage** — Both compiler diagnostic formats are handled in `parseCompileLog()`.
- **`detectDocType()` properly includes `.log`** — `document-parser.ts:28` correctly maps `.log` → `build_artifact`.
- **`.log` in ALLOWED_EXTENSIONS** — `upload.ts:13` includes `"log"` in the set.
- **`filename` parameter threaded through** — `extractText()` correctly accepts optional `filename` (line 87 of `document-parser.ts`) and passes it to `extractBuildArtifactText()`.
- **Deduplication in parseMapFile** — Uses `Set<string>` to deduplicate module names extracted from `.o` paths.

### Issues Found

1. **[BUG] Dedicated build-artifact endpoint will crash at runtime** — `ingest.ts:369-370`: `computeHashFromStream(filePath)` with `filePath = req.file.path` which is `undefined` when using `multer.memoryStorage()`. This will cause `fs.createReadStream(undefined)` to throw.

2. **[BUG] Dedicated endpoint bypasses structured parsing** — `ingest.ts:372`: The raw content (`strippedContent`) is stored directly, not processed through `extractBuildArtifactText()`. This defeats the purpose of having a dedicated build-artifact endpoint.

3. **[CODE SMELL] Duplicate `.log` handling in ingest.ts** — `ingest.ts:228-229` has an explicit `if (ext === "log") docType = "build_artifact"` after `detectDocType()` was already called. This is redundant since `detectDocType()` already handles `.log` at `document-parser.ts:28`. This comment (`// Fix extension matching logic to map .log to build_artifact`) suggests a workaround was added without updating the source.

4. **[MINOR] No input validation on `content` in build-artifact-parser** — Functions like `parseMapFile()`, `parseFvFile()`, etc. do not validate that `content` is a non-empty string. Empty or undefined content would produce empty sections/modules but no error.

5. **[MINOR] `parseMapFile` doesn't handle EDK2 format** — The implementation plan describes EDK2 map format with GUID columns (section 4.1.2 of the implementation plan), but `parseMapFile()` only handles GCC and MSVC formats.

6. **[MINOR] No unit tests** — There are zero test files for `build-artifact-parser.ts`. The parser contains complex regex logic for 4 different file formats and should have unit tests for each subtype.

## Round 3 — Integration & Completeness Review

### Integration Flow (Main Path — WORKING)

The primary integration path is correctly wired:
1. `upload.ts` accepts `.map`, `.fv`, `.fd`, `.log` extensions ✅
2. `detectDocType()` in `document-parser.ts` maps all four extensions → `"build_artifact"` ✅
3. `extractText()` calls `extractBuildArtifactText(buffer.toString("utf-8"), filename)` for `build_artifact` type ✅
4. `extractBuildArtifactText()` dispatches to the correct parser based on `detectSubtype()` ✅
5. `formatAsBuildArtifactText()` produces structured Markdown ✅
6. `processIngestion()` stores the structured Markdown in `documentsTable.content` ✅
7. `generate.ts:644-648` includes document content (sliced to 800 chars) as `documentContext` in LLM prompts ✅

### Integration Flow (Dedicated Endpoint — BROKEN)

The dedicated `POST /projects/:id/ingest/build-artifact` endpoint at `ingest.ts:363-394`:
- Accepts file upload via `documentUpload.single("file")` ✅
- **Fails** at `computeHashFromStream(req.file.path)` — `req.file.path` is `undefined` ❌
- **Does not call** `extractBuildArtifactText()` — stores raw content instead ❌
- Uses hardcoded `projectName` ❌
- Missing project existence check (no `SELECT FROM projectsTable`) ❌

### LLM Context Quality

The structured Markdown output is well-designed for the 800-character context window:
- Summary appears first (most valuable info within truncation limit)
- Markdown tables for memory sections are compact
- Module lists use `- name (path)` format which is human-readable

### Performance

- Regex parsing is synchronous and runs on the main thread. For very large build artifacts (e.g., multi-MB compile logs), this could block the event loop. However, this is acceptable for v1.
- The 50-diagnostic cap in `parseCompileLog()` (line 271) and 20-item caps in `parseMapFile()`/`parseFvFile()` bound the output size.

### Missing Tests

- No unit tests for `detectSubtype()` (5 format detection paths)
- No unit tests for `parseMapFile()` (GCC, MSVC patterns)
- No unit tests for `parseFvFile()` (INF extraction, metadata)
- No unit tests for `parseFdFile()` (flash region parsing)
- No unit tests for `parseCompileLog()` (GCC/MSVC diagnostic patterns)
- No integration test for the full upload → parse → store pipeline

## Recommendations

1. **Fix the dedicated endpoint** — Change `ingest.ts:369-370` to use `req.file.buffer` instead of `req.file.path`, and route content through `extractBuildArtifactText()`.
2. **Remove redundant `.log` workaround** — Remove lines 228-229 in `ingest.ts` since `detectDocType()` already handles `.log`.
3. **Add unit tests** — Create `build-artifact-parser.unit.test.ts` covering all 4 subtypes with sample data.
4. **Add project existence check** — The dedicated endpoint should verify the project exists (return 404) before processing.
5. **Implement EDK2 map format** — Add the GUID table parser described in the implementation plan.

## Overall Verdict

**⚠️ WARN** — The main integration path (document upload → `extractText()` → `build-artifact-parser` → structured Markdown) is correctly implemented and well-structured. However, the dedicated build-artifact endpoint is non-functional due to the `memoryStorage()` mismatch and bypasses structured parsing entirely. Additionally, there are zero tests for the parser, and minor gaps exist in format coverage and input validation.
