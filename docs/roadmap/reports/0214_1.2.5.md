## Round 1 — Architecture & Design Review

### Design Intent

The design spec defines `scoreCommit()` as a signal/noise filter applied during ingestion to filter out low-value commits (merge commits, `chore:` bumps, auto-generated changes, etc.). The glossary states: "Returns a numeric score; commits below the threshold are **skipped**." The runtime view describes it as: `scoreCommit() → filter low-signal commits`. The intent is clear: noise commits should **not** enter the database.

### Implementation Analysis

The implementation is extracted into `artifacts/api-server/src/lib/commit-scorer.ts` as a pure function:
- Returns `{ score: number, valid: boolean }`
- Defines `SCORER_CONSTANTS` with `BASE_SCORE: 0.3`, `VALID_THRESHOLD: 0.4`, `SIGNAL_BONUS: 0.15`
- Checks 10 noise patterns (merge, bump, chore, auto-generated, ci, wip, revert, initial commit, changelog, [skip ci], dependabot, chore(release):)
- Checks 9 signal patterns (fix, feat, add, refactor, implement, resolve, breaking change, decision, architecture, performance)
- Applies bonuses for detailed messages and diffs with TODO/FIXME or >100 lines
- Score is clamped to `MAX_SCORE: 1.0`

The implementation is consumed by:
1. **`ingestion-pipeline.ts`** (Git & SVN paths): Calls `scoreCommit()` and stores the result as `valid` on the commit row
2. **`github_webhooks.ts`** `ingestPrCommits()`: Calls `scoreCommit()` but **ignores the result entirely**

### Design-Implementation Gaps

1. **Noise commits are stored, not skipped**: The glossary says "commits below the threshold are skipped," but `ingestion-pipeline.ts` (lines 89-97 for Git, lines 135-147 for SVN) always INSERTS the commit row regardless of the `valid` flag — it merely marks noise commits as `valid: false`. This means:
   - Noise commits consume database rows and disk space
   - The `activity_log` and notification systems still fire for noise-ingested batches
   - The `commits` table becomes polluted with known-noise data

2. **GitHub webhook path ignores scoreCommit entirely**: In `github_webhooks.ts` lines 57-64:
   ```typescript
   const score = scoreCommit(c.commit.message);
   await db.insert(commitsTable).values({
     projectId,
     hash: c.sha,
     message: c.commit.message.split("\n")[0].trim(),
     author: c.commit.author?.name ?? "Unknown",
     valid: true,  // ← hardcoded, ignores `score`
   });
   ```
   The `score` variable is computed but never used. All PR commits get `valid: true` regardless of content.

### Positive Findings

- ✅ Duplication risk (R-05/D-01 from `11-risks-and-debt.md`) has been resolved: `scoreCommit()` is now a single shared utility in `commit-scorer.ts`, imported by both consumers.
- ✅ The function is a pure function — good testability, no side effects.
- ✅ The generate pipeline (`generate.ts` line 610-611) correctly filters with `eq(commitsTable.valid, true)`, so `valid: false` commits are excluded from knowledge generation. This partially mitigates the "not skipped" issue for Git/SVN paths.

## Round 2 — Code Quality & Security Review

### Structure & Readability

- `commit-scorer.ts` is clean, well-organized, and uses named constants instead of magic numbers.
- The noise/signal pattern arrays are clear and documented through naming.
- The scoring algorithm is simple and easy to understand.

### Code Issues

1. **🔴 Medium — `github_webhooks.ts` ignores scoreCommit result** (lines 56-64):
   The `score` return value from `scoreCommit()` is captured into a local variable and then completely discarded. The `valid` field is hardcoded to `true`. This means:
   - Merge commits from PRs, `dependabot` commits, and `chore:` commits enter the database as `valid: true`.
   - These commits will be processed by the generate pipeline, wasting LLM tokens and potentially polluting the knowledge graph.
   - The `score` variable assignment is dead code — a linter with dead-code detection would flag this.

2. **🟡 Medium — Noise commits inserted rather than skipped** (`ingestion-pipeline.ts` lines 84-100, 135-147):
   The `valid` result from `scoreCommit()` is only used to set the boolean flag, never to skip the INSERT. A simple `if (!valid) { skipped++; continue; }` guard would align the implementation with the design intent.

3. **🟡 Low — No unit tests for `scoreCommit()`**:
   A grep for `scoreCommit` or `commit-scorer` across all test files returns zero results. The scoring logic is sufficiently complex (10 noise patterns, 9 signal patterns, bonus arithmetic) to warrant dedicated unit tests covering:
   - Noise pattern matching (all 10+ patterns)
   - Signal pattern scoring accumulation
   - Edge cases: empty message, undefined message, long message
   - Diff bonus: TODO/FIXME detection, line counting
   - Score clamping at `MAX_SCORE`
   - Threshold boundary (`0.39` → invalid, `0.4` → valid)

4. **🟢 Low — Minor noise pattern gaps**:
   The current noise patterns don't cover some common noise commits:
   - `style:/format` commits
   - `test:` commits (often auto-generated snapshots)
   - `docs:` commits (README-only changes)
   - `refactor:` with no signal keywords
   - `[automated]` prefix
   - GitHub Actions bot (`github-actions[bot]`)

### Security

No security vulnerabilities identified in the `scoreCommit()` implementation or its consumers. The function is a pure string-matching utility with no auth, no network access, and no file I/O.

## Round 3 — Integration & Completeness Review

### Integration with Generate Pipeline

The generate pipeline (`generate.ts` lines 604-615) correctly filters commits using `eq(commitsTable.valid, true)`. This means:

- **Git/SVN path**: Noise commits stored with `valid: false` are effectively excluded from generation. The DB-space waste is the main concern.
- **Webhook path**: All PR commits are stored with `valid: true` (the bug above), so noise commits from GitHub PRs **will** be processed by the generate pipeline, consuming LLM tokens and potentially generating low-quality knowledge graph nodes.

### Integration with Notification System

`ingestion-pipeline.ts` increments `ingested` for all INSERTed commits (including those with `valid: false`), and calls `logAndNotify()` when `ingested > 0`. This means noise commits counted as "ingested" will trigger activity log entries and notifications, which is misleading.

### Deduplication via Hash

Both the Git/SVN ingestion paths and the webhook path use hash-based deduplication (`existingHashes` / `existing` checks before INSERT), so the `scoreCommit` filter is not relied upon for dedup. This is correct.

### Incremental Ingestion Compatibility

The `scoreCommit()` function is stateless and pure — it works correctly in both full and incremental modes. The cursor columns (`lastGitIngestedAt`, `lastSvnRevision`) are updated independently of the scoring, which is correct.

## Recommendations

1. **Fix `github_webhooks.ts` `ingestPrCommits()`** to respect the `scoreCommit()` result:
   ```typescript
   const { valid } = scoreCommit(c.commit.message);
   // ... then use: valid: valid  (instead of valid: true)
   ```

2. **Skip noise commits in `ingestion-pipeline.ts`** to match the design spec ("commits below the threshold are skipped"):
   ```typescript
   const { valid, score } = scoreCommit(c.message, c.diff);
   if (!valid) { skipped++; continue; }
   ```

3. **Add unit tests for `scoreCommit()`** covering all noise patterns, signal patterns, edge cases, boundary scores, and diff bonus logic.

4. **Consider extending noise patterns** for additional common noise prefixes (`style:`, `docs:`, `test:`, `[automated]`).

## Overall Verdict

**⚠️ WARN**

The `scoreCommit()` function itself is well-implemented — it correctly identifies noise vs. signal using regex patterns and a scoring algorithm. The architectural duplication issue from the original design debt has been resolved. However, there are two medium-severity issues that prevent the feature from fully meeting the design specification: (1) the GitHub webhook path ignores the scoring result entirely, allowing all PR commits through regardless of content, and (2) noise commits are stored with `valid: false` rather than being skipped as the design specifies. The generate pipeline's `valid: true` filter partially mitigates the impact for Git/SVN paths, but the webhook path issue means noisy PR commits will be processed by the LLM pipeline.
