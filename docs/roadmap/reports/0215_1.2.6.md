## Round 1 — Architecture & Design Review

### What the Design Spec Requires

The implementation plan (`implement_incremental-update.md`) defines these success criteria:

1. **Git incremental ingest** — `POST /projects/:id/ingest/git` with `{ "mode": "incremental" }` fetches only commits newer than `project.lastGitIngestedAt`
2. **SVN incremental ingest** — `POST /projects/:id/ingest/svn` with `{ "mode": "incremental" }` fetches only revisions > `project.lastSvnRevision`
3. **Incremental generate** — `POST /projects/:id/generate` in incremental mode processes only commits where `processedAt IS NULL`
4. **Status endpoint** — `GET /projects/:id/ingest/status` exposes cursor state
5. **Frontend UI** — "Last ingested" timestamp and "Sync (incremental)" button on project detail page

### Gaps Between Design and Implementation

1. **Cursor update dual-write inconsistency**: The `ingestion-pipeline.ts` `processIngestion()` function (lines 102-106) updates `lastGitIngestedAt` to `new Date()` on every batch. The route handler in `ingest.ts` (lines 80-85) then updates it again to `newestCommitDate`. This means the pipeline's cursor update is immediately overwritten by the route handler. While the end result is correct (the route handler's value wins), the redundant update in `processIngestion` is dead code that creates confusion.

2. **Generate ordering deviation**: The design spec explicitly recommends `ORDER BY createdAt ASC` for incremental mode (to process oldest unprocessed commits first for causal ordering). The implementation at `generate.ts` line 613 uses `desc` for both full and incremental modes.

3. **Missing response fields**: The design spec calls for `mode` and `unprocessedRemaining` in the generate response. The implementation at `generate.ts` lines 1158-1168 does not include these fields.

4. **OpenAPI `projectId` type mismatch**: The `IngestStatusResponse` schema at `openapi.yaml` line 2307 declares `projectId` as `type: "string"`, but the actual response from `ingest.ts` line 202 returns it as an integer.

## Round 2 — Code Quality & Security Review

### Strengths

- **Batch processing**: Both Git and SVN ingestion use batch sizes of 50 (`ingest.ts` line 170, `ingestion-pipeline.ts` line 66), preventing unbounded memory growth.
- **Streaming Git log**: `git-client.ts` uses `spawn` with `readline` interface (lines 49-78) instead of `execFile`, preventing OOM on large repositories.
- **Duplicate detection**: SHA-based dedup for Git (line 85), revision-based dedup for SVN (lines 119-128), content-hash dedup for documents (lines 156-166).
- **Transaction safety**: Git batch inserts in `ingestion-pipeline.ts` use `db.transaction()` (line 72).
- **SVN URL validation**: `ingest.ts` line 117 validates SVN URL format before processing.

### Issues Found

#### Issue 1: Redundant cursor update in `processIngestion()` (Medium)

**File:** `artifacts/api-server/src/lib/ingestion-pipeline.ts`, lines 102-106

```typescript
if (batchIngested > 0) {
  await tx
    .update(projectsTable)
    .set({ lastGitIngestedAt: new Date() })
    .where(eq(projectsTable.id, projectId));
  ingested += batchIngested;
}
```

This updates `lastGitIngestedAt` to `new Date()` on every batch, but the route handler in `ingest.ts` lines 80-85 immediately overwrites this with `newestCommitDate`. The `processIngestion` function should not be responsible for cursor management — it should focus on commit insertion. This separation of concerns violation makes the code harder to maintain and creates a subtle bug risk: if the route handler's update is ever removed, the cursor would advance to "now" instead of the actual latest commit date, potentially missing commits.

**Recommendation:** Remove the cursor update from `processIngestion()` and keep it only in the route handler.

#### Issue 2: Incremental generate uses `desc` instead of `asc` ordering (Medium)

**File:** `artifacts/api-server/src/routes/generate.ts`, line 613

```typescript
.orderBy(sql`${commitsTable.createdAt} desc`)
```

The design spec states: "Switched from `desc` to `asc` in incremental mode to process oldest unprocessed commits first, preserving causal dependency ordering." The current implementation uses `desc` for both modes, which means newer commits are processed first. This can cause L2/L3 nodes to be created with incomplete context if older commits haven't been processed yet.

**Recommendation:** Change to conditional ordering:

```typescript
.orderBy(mode === "incremental" ? sql`${commitsTable.createdAt} asc` : sql`${commitsTable.createdAt} desc`)
```

#### Issue 3: `processIngestion` cursor uses `new Date()` instead of commit timestamp (Low)

**File:** `artifacts/api-server/src/lib/ingestion-pipeline.ts`, line 105

Even if the dual-write issue is fixed, the `processIngestion` function sets `lastGitIngestedAt` to `new Date()` rather than the actual commit timestamp. This means if the ingestion pipeline is ever called without the route handler's override, the cursor would be set to the current wall-clock time, which could skip commits that fall between the last real commit timestamp and "now".

#### Issue 4: OpenAPI `projectId` type mismatch in `IngestStatusResponse` (Low)

**File:** `lib/api-spec/openapi.yaml`, line 2307

```yaml
projectId:
  type: "string"
```

The actual response returns `projectId` as an integer (`ingest.ts` line 202: `projectId: project.id` where `project.id` is a serial integer). This type mismatch will cause issues with strict OpenAPI validation and codegen.

**Recommendation:** Change to `type: integer`.

#### Issue 5: Missing `mode` and `unprocessedRemaining` in generate response (Low)

**File:** `artifacts/api-server/src/routes/generate.ts`, lines 1158-1168

The design spec calls for these fields in the response, but they are not included. The frontend cannot display the current mode or remaining unprocessed count without them.

## Round 3 — Integration & Completeness Review

### End-to-End Flow Verification

1. **Git incremental flow**: ✅ Complete
   - Frontend `IngestStatusCard` calls `useIngestGit` with `{ mode: "incremental" }` → Backend reads `project.lastGitIngestedAt` → Passes to `git log --since=<cursor>` → Inserts only new commits → Updates cursor → Returns counts → Frontend invalidates status query

2. **SVN incremental flow**: ✅ Complete
   - Frontend calls `useIngestSvn` with `{ mode: "incremental" }` → Backend computes `startRevision = lastSvnRevision + 1` → Fetches only new revisions → Processes in batches of 50 → Updates `lastSvnRevision` → Returns counts

3. **Generate incremental flow**: ✅ Complete (with ordering caveat)
   - Frontend calls `useGenerateKnowledge` with `{ mode: "incremental" }` → Backend queries `valid=true AND processedAt IS NULL` → Runs L1→L2→L3 pipeline → Marks commits as processed → Returns counts

4. **Status monitoring**: ✅ Complete
   - `GET /projects/:id/ingest/status` returns `lastGitIngestedAt`, `lastSvnRevision`, `pendingCommits`
   - Frontend `IngestStatusCard` displays VCS type, last sync time, pending count
   - "Sync (Incremental)" and "Generate (Delta)" buttons are functional

### Missing Tests

No dedicated tests for the incremental ingestion flow were found. The `artifacts/api-server/test/integration/` directory should include:

- Integration test: Git incremental ingest skips already-ingested commits
- Integration test: SVN incremental ingest starts from `lastSvnRevision + 1`
- Integration test: Generate incremental mode only processes `processedAt IS NULL` commits
- Integration test: Status endpoint returns correct cursor values

### Performance Considerations

- The `processIngestion` function queries ALL existing commit hashes for the project on every batch (line 74-79). For projects with thousands of commits, this could be slow. Consider using a `WHERE hash IN (...)` query instead.
- The `generate.ts` commit dedup check at line 74-79 fetches all existing hashes into memory. For large projects, this could be memory-intensive.

## Overall Verdict

**⚠️ WARN**

The incremental ingestion feature is substantially implemented and functional end-to-end. All major components (DB schema, Git/SVN routes, generate pipeline, status endpoint, OpenAPI spec, frontend UI) are in place. However, there are two medium-severity issues — the dual cursor update and the incorrect sort ordering in incremental generate — that could lead to subtle bugs in production. The remaining issues are low-severity and can be addressed in a follow-up cleanup pass.
