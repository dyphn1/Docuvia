## Round 1 — Architecture & Design Review

### What the Design Spec Requires

ADR-007 defines the intent routing funnel with these requirements:

1. **O(1) Fast-Path: Direct Filter** — If query contains `#attach` or file extensions (`.ts`, `.src/`), route to Direct RAG without LLM
2. **O(1) Fast-Path: Graph Filter** — If query hits L1/L2 names in the database, route to Graph RAG without LLM
3. **LLM Fallback** — For all other queries, use LLM to classify into one of 4 strategies: `vector_search`, `graph_traversal`, `direct_lookup`, `hybrid`
4. **4-Way Search Strategies**:
   - **Direct RAG**: O(1) lookup via commit hashes or full-text search on `l3_nodes.content`
   - **Graph RAG**: Traverse `node_linksTable` to find structural dependencies
   - **Vector RAG**: Cosine similarity over embeddings (PGVector via JSONB)
   - **Hybrid RAG**: Intersection of graph + vector with cross-validation boosting
5. **Temporal Decay**: Apply exponential decay (`Math.exp(-LAMBDA * daysSinceVerified)`) with 30-day half-life
6. **API Endpoints**: Both REST (`POST /search`) and MCP (`POST /mcp/query`, `GET /mcp/search_knowledge`) must expose the intent router

### Gaps Between Design and Implementation

1. **Validity status mismatch between direct_lookup and MCP search**: The `directLookupHandler` at `intent-router.ts:500,535` filters on `l3.validityStatus !== 'active'`, but the `vectorSearchHandler` at line 198-199 filters on `l3NodesTable.validityStatus` being `"valid"` or `"pending"`. The design spec (ADR-004, ADR-011) defines the status enum as `pending | valid | orphaned`, but the direct_lookup handler checks for `"active"` which is not a valid enum value. This means the direct lookup validity filter will never match any rows (since `validityStatus` stores `"valid"`, not `"active"`), so the filter is effectively a no-op — all L3 nodes pass through regardless of status.

2. **Hybrid search scoring boost design issue**: The hybrid search at `intent-router.ts:597` adds `r.score + 0.5` to the existing score for intersection nodes. This is a flat boost, not a "compounding score boost" as described in ADR-007 ("nodes found in both sets receive a compounding score boost"). A compounding boost would multiply scores; adding a flat 0.5 can cause intersection nodes to always outrank non-intersection nodes regardless of their actual relevance.

3. **Graph traversal uses only out-links**: The `graphTraversalHandler` (lines 425-449) only follows `outLinks` (source→target dependencies) but does not traverse in-links (dependents). For a complete graph traversal, both directions should be explored. The design spec says "traverses node_linksTable to find structural dependencies (Neighbor Infection)" which implies both directions.

4. **Graph fast-path fetches ALL L1/L2 names on every query**: The O(1) graph filter at `intent-router.ts:661-667` runs `SELECT name FROM l1_tags` and `SELECT name FROM l2_nodes` on every query. For systems with many projects/tags, this is O(N) in database size, not O(1). The ADR describes this as an "O(1) arbitration" but the implementation is a full table scan.

5. **`sanitizeLikeInput` and `escapeLike` are duplicates**: Two identical functions exist at `intent-router.ts:98-104`. `sanitizeLikeInput` and `escapeLike` have the same implementation (`str.replace(/[\\%_]/g, "\\$&")`). Only `sanitizeLikeInput` is actually used. `escapeLike` is dead code.

6. **`search.ts` missing `includePending` parameter**: The REST `POST /search` endpoint at `search.ts:22-31` does not read or pass `includePending` to `routeQuery()`, so the REST search always uses the default `includePending=false`. The MCP endpoints correctly support this parameter.

## Round 2 — Code Quality & Security Review

### Strengths

- **Well-structured types**: `IntentClassification`, `AgenticSearchResult`, `RouteQueryResult`, and `RoutingStrategy` are clean, exported types that make the API contract explicit.
- **Query sanitization**: `sanitizeQuery()` (lines 110-115) truncates to 2000 chars and strips control characters, mitigating prompt injection.
- **Strategy validation**: The LLM response is validated against `VALID_STRATEGIES` Set (line 155), preventing invalid strategy strings from reaching the switch statement.
- **Graceful fallback**: `classifyIntent()` returns a `vector_search` fallback on any LLM error (lines 131-181), ensuring the router never crashes due to LLM failures.
- **Embedding fallback**: `vectorSearchHandler` gracefully falls back to SQL LIKE search if embedding generation fails (lines 293-381).
- **Structured logging**: Uses pino with PII redaction in `logger.ts`.
- **Zod validation on MCP query**: `mcpQueryBodySchema` (line 204-208) validates `q`, `project_id`, and `limit` with proper bounds.

### Issues Found

#### Issue 1: validityStatus enum mismatch in direct_lookup (Medium)

**File:** `artifacts/api-server/src/lib/intent-router.ts`, lines 500, 535

```typescript
if (!includePending && l3.validityStatus !== 'active') continue;
```

The schema defines `validityStatus` as `"pending"` | `"valid"` | `"orphaned"`. The value `"active"` is never assigned anywhere in the codebase. This condition will always be `true` (since no row has `validityStatus === 'active'`), so the filter is effectively disabled — even `"orphaned"` nodes will be returned by direct lookup when `includePending` is false.

**Recommendation:** Change to:
```typescript
if (!includePending && l3.validityStatus !== 'valid') continue;
```

#### Issue 2: Duplicate `sanitizeLikeInput` / `escapeLike` functions (Low)

**File:** `artifacts/api-server/src/lib/intent-router.ts`, lines 98-104

Both functions have identical implementations. `escapeLike` is never called anywhere in the codebase. This is dead code.

**Recommendation:** Remove `escapeLike` and keep only `sanitizeLikeInput` (or vice versa).

#### Issue 3: `isSingleWord` check doesn't use the pre-filter (Low)

**File:** `artifacts/api-server/src/lib/intent-router.ts`, lines 625-645

The `isSingleWord` fast-path at line 625 (`!/\s/.test(trimmed) && trimmed.length > 3`) short-circuits to `direct_lookup` without checking the `#attach`/file-extension pre-filter first. This means a single-word query containing `#attach` (e.g., `"#auth"`) would go through direct_lookup instead of being recognized as a file-attachment query.

#### Issue 4: Project lookup N+1 in vector search (Medium)

**File:** `artifacts/api-server/src/lib/intent-router.ts`, lines 226-242

For every L2 node returned by vector search, a separate `SELECT name FROM projects` query is executed. With a limit of 10 results, this means up to 10 additional queries. The same pattern exists for L2 fallback results (lines 323-338).

**Recommendation:** Batch the project lookups using `WHERE id IN (...)` or join with projects table in the initial query.

#### Issue 5: `parseEmbedding` parses JSON on every comparison (Low)

**File:** `artifacts/api-server/src/lib/intent-router.ts`, lines 270-271

`parseEmbedding(node.embedding)` is called for every L3 node during scoring. For nodes with large embeddings (1536 dimensions), parsing the JSON string on every comparison is CPU-intensive. Consider pre-parsing or caching.

#### Issue 6: No input sanitization on graph traversal module name (Low)

**File:** `artifacts/api-server/src/lib/intent-router.ts`, line 402

```typescript
.where(like(l2NodesTable.name, `%${escapedModuleName}%`))
```

The `escapedModuleName` is sanitized with `sanitizeLikeInput`, but the LIKE pattern uses `%` wildcards on both sides. A module name of `"%test%"` (though unlikely) would match all nodes. The sanitization is correct, but this is worth noting.

#### Issue 7: `search.ts` has no error logging (Low)

**File:** `artifacts/api-server/src/routes/search.ts`, lines 22-32

The `POST /search` endpoint catches errors but does not log them:
```typescript
} catch (error) {
    res.status(500).json({ error: "Search failed" });
}
```

Compared to `mcp.ts` which logs with `logger.error({ err }, ...)`. This makes debugging search failures harder.

### Security Review

- ✅ **Prompt injection mitigation**: `sanitizeQuery()` strips control characters and truncates to 2000 chars.
- ✅ **MCP auth**: Bearer token auth via `MCP_PAT` env var (mcp.ts lines 19-35).
- ✅ **SQL LIKE injection prevention**: `sanitizeLikeInput` escapes `%`, `_`, and `\` characters.
- ✅ **Zod validation**: MCP query endpoint validates input with Zod schema.
- ⚠️ **No auth on REST search endpoint**: `POST /search` has no authentication middleware. Any caller can trigger LLM classification calls, potentially incurring costs.
- ⚠️ **LLM response parsed without schema validation**: `JSON.parse(raw)` at line 152 parses the LLM response but only loosely validates fields. A malformed LLM response could cause unexpected behavior, though the fallback mechanism mitigates crashes.

## Round 3 — Integration & Completeness Review

### End-to-End Flow Verification

1. **REST search flow**: ✅ Functional
   - `POST /search` with `{ query, projectId, limit }` → `routeQuery()` → O(1) fast-paths → LLM fallback → handler dispatch → results returned

2. **MCP query flow**: ✅ Functional
   - `POST /mcp/query` with Zod-validated body → `routeQuery()` → same routing logic → results returned

3. **MCP search flow**: ✅ Functional
   - `GET /mcp/search_knowledge?query=...&project_id=&limit=` → `routeQuery()` → results returned

4. **LLM fallback flow**: ✅ Functional
   - When fast-paths don't match, `classifyIntent()` calls OpenAI with structured JSON prompt
   - Response is validated, parsed, and dispatched to the correct handler

5. **Temporal decay integration**: ✅ Functional
   - Applied in both `vectorSearchHandler` (lines 219, 273) where `calculateTemporalDecay()` multiplies the raw cosine score

6. **Feedback loop**: ✅ Functional
   - `POST /search/feedback` updates `lastVerifiedAt` on L2/L3 nodes (search.ts lines 46-49), which feeds into temporal decay on subsequent queries

### Missing Tests

There are **zero test files** for the intent router or search functionality:

- No unit tests for `classifyIntent()` (LLM classification logic)
- No unit tests for `calculateTemporalDecay()` (exponential decay math)
- No unit tests for `sanitizeQuery()`, `sanitizeLikeInput()` (input sanitization)
- No unit tests for `vectorSearchHandler()`, `graphTraversalHandler()`, `directLookupHandler()`, `hybridSearch()`
- No integration tests for `POST /search` or `POST /mcp/query`
- No tests for the O(1) fast-path arbitration (the ADR-007 "Fast-Path Assertion" and "Fallback Assertion" are not implemented)
- No tests for the `embedding.ts` functions (`cosineSimilarity`, `generateEmbedding`, `parseEmbedding`)

The ADR-007 explicitly states:
> "Integration tests in `artifacts/api-server/test/integration/` MUST seed the database using factories, trigger an exact-match query, and use MSW to strictly assert that 0 external HTTP requests are made to the AI server."

This is not implemented.

### Performance Considerations

1. **Graph fast-path DB queries**: The O(1) graph filter (lines 661-667) fetches ALL L1 tags and L2 nodes on every query. For large knowledge graphs, this is expensive. Consider caching or using a materialized view.

2. **Embedding computation**: Each vector search generates a new embedding via OpenAI API call. For high-traffic systems, consider caching embeddings for common queries.

3. **N+1 project lookups**: As noted in Issue 4 above, each result triggers a separate project lookup query.

4. **Hybrid search parallelism**: The hybrid search correctly uses `Promise.all` (line 579) for parallel graph traversals, which is good.

5. **Synchronous regex parsing**: The `isSingleWord` check (line 625) and file extension check (line 650) use simple regex that won't cause ReDoS issues.

## Recommendations

1. **Fix validityStatus filter (Issue 1)**: Change `'active'` to `'valid'` in `directLookupHandler` at lines 500 and 535. This is a functional bug that causes orphaned nodes to be returned in search results.

2. **Add tests (Issue 11)**: This is the most critical gap. Create:
   - `intent-router.unit.test.ts`: Unit tests for `calculateTemporalDecay`, `sanitizeQuery`, `sanitizeLikeInput`, `classifyIntent` (mocked), `cosineSimilarity`
   - `search.integration.test.ts`: Integration tests with MSW for the fast-path assertion (0 LLM calls) and fallback assertion (1 LLM call) as required by ADR-007

3. **Add auth to REST search endpoint (Issue 3)**: Either add auth middleware or document that this endpoint is intentionally unauthenticated.

4. **Batch project lookups (Issue 2)**: Replace N+1 queries with a single `WHERE id IN (...)` query or a join.

5. **Remove dead code (Issue 4)**: Remove the unused `escapeLike` function.

6. **Fix pre-filter ordering (Issue 5)**: Move the `#attach`/file-ext check before the `isSingleWord` check, or integrate both checks.

7. **Add in-link traversal (Issue 6)**: Extend `graphTraversalHandler` to also follow in-links for complete dependency analysis.

## Overall Verdict

**⚠️ WARN**

The 4-way intent classification system is substantially implemented and architecturally sound. All four search strategies (vector, graph, direct, hybrid) are implemented, the O(1) fast-path arbitration pipeline is present, temporal decay is correctly applied, and both REST and MCP endpoints are wired up. The code is well-structured with good type definitions, input sanitization, and graceful fallbacks.

However, there is one functional bug (the `validityStatus !== 'active'` check that never matches), and the most significant gap is the complete absence of tests — the ADR-007 explicitly requires fast-path and fallback assertions that are not implemented. The N+1 query issue and missing auth on the REST search endpoint are additional concerns that should be addressed.
