## Round 1 — Architecture & Design Review

### What the Design Spec Requires

The design spec (arc42 §4.1) states:

- **Vector Search**: "Raw SQL cosine distance with Temporal Decay filter"
- **Storage**: "JSONB column type for embedding storage"
- **ADR-007**: "Vector RAG: Standard embedding similarity via PGVector (`embedding.ts`)"
- **Strategy**: "No external vector DB dependency in v1; embeddings stored as JSONB in PostgreSQL; sufficient for ≤100K nodes"

### Implementation Status

| Criterion                                  | Status             | Notes                                                                             |
| ------------------------------------------ | ------------------ | --------------------------------------------------------------------------------- |
| Embedding generation (`generateEmbedding`) | ✅ Implemented     | `embedding.ts:11-24` — uses OpenAI `text-embedding-3-small`, 1536 dimensions      |
| Cosine similarity computation              | ✅ Implemented     | `embedding.ts:30-42` — standard dot-product formula                               |
| Embedding storage                          | ✅ Implemented     | Stored via `generate.ts:931,1039` using `JSON.stringify(emb)`                     |
| Vector search handler                      | ✅ Implemented     | `intent-router.ts:188-385` — `vectorSearchHandler()`                              |
| Temporal decay on vector scores            | ✅ Implemented     | `intent-router.ts:218-220,272-274` — `calculateTemporalDecay()` applied           |
| Graceful fallback (LIKE search)            | ✅ Implemented     | `intent-router.ts:293-381` — falls back to SQL LIKE if embedding generation fails |
| JSONB column type                          | ❌ NOT implemented | Schema uses `text("embedding")` not `jsonb("embedding")`                          |
| Raw SQL cosine distance                    | ⚠️ Partial         | `vector-search.ts` exists but is incompatible with schema (see below)             |
| PGVector integration                       | ❌ NOT implemented | `vector-search.ts` references `<=>` operator but schema is `text` not `vector`    |

### Critical Gap: Two Conflicting Vector Search Implementations

There are **two separate vector search implementations** in the codebase:

1. **`intent-router.ts:188-385` (`vectorSearchHandler`)** — The ACTIVE implementation:
   - Fetches ALL rows with non-null embeddings from the database
   - Parses JSON embedding strings in JavaScript via `parseEmbedding()`
   - Computes cosine similarity in-app via `cosineSimilarity()`
   - Applies temporal decay in-app
   - Sorts and slices in JavaScript
   - This is called by `routeQuery()` and is the actual production code path

2. **`vector-search.ts:13-56` (`performVectorSearch`)** — DEAD CODE:
   - Uses raw SQL with pgvector `<=>` operator: `embedding::vector <=> ${vectorStr}::vector`
   - Computes cosine distance and temporal decay in SQL
   - **Never imported or called anywhere in the codebase**
   - **Incompatible with the schema**: casts `embedding` to `vector` type, but the column is `text`, not `vector`
   - Also has the `validityStatus = 'active'` bug (line 28) — schema uses `'valid'`/`'pending'`/`'orphaned'`

### Gap: JSONB vs text Column Type

The design spec explicitly states "JSONB column type for embedding storage" (arc42 §4.1). However:

- `l3_nodes.ts:31`: `embedding: text("embedding")` — uses `text`, not `jsonb`
- `l2_nodes.ts:19`: `embedding: text("embedding")` — uses `text`, not `jsonb`
- The `jsonb` import exists in both files but is only used for `path_patterns` in l2_nodes

The embeddings are stored as JSON-stringified text (`JSON.stringify(emb)` in `generate.ts:931,1039`), which works in a `text` column but loses JSONB indexing/querying capabilities. The design spec's intent was JSONB storage, but the implementation uses plain text.

### Gap: Duplicate Temporal Decay Implementations

There are **two implementations** of temporal decay:

1. `intent-router.ts:121-127` — `calculateTemporalDecay()` with 30-day half-life (`Math.LN2 / 30`)
2. `decay.ts:1-6` — `calculateTemporalDecay()` with configurable `decayRate` parameter (default 0.05)

These have different default decay rates (0.023 vs 0.05) and different interfaces. The `decay.ts` version is only used by its unit test, not by any production code.

## Round 2 — Code Quality & Security Review

### Strengths

- **Well-tested core math**: `embedding.unit.test.ts` covers `cosineSimilarity` with 6 test cases (identical, orthogonal, opposite, empty, different lengths, zero magnitude) and `parseEmbedding` with 5 test cases
- **Graceful degradation**: `vectorSearchHandler` falls back to SQL LIKE search if embedding generation fails (lines 293-381)
- **Input validation**: `generateEmbedding` checks for empty/null text; `parseEmbedding` handles null/undefined/invalid JSON
- **Cosine similarity correctness**: The implementation at `embedding.ts:30-42` is mathematically correct — handles zero magnitude, different length vectors, and returns values in [-1, 1]

### Issues Found

#### Issue 1: Schema uses `text` instead of `jsonb` for embeddings (Medium)

**Files:** `lib/db/src/schema/l3_nodes.ts:31`, `lib/db/src/schema/l2_nodes.ts:19`

```typescript
embedding: text("embedding"),
```

The design spec (arc42 §4.1) states "JSONB column type for embedding storage." Using `text` instead of `jsonb` means:

- No JSONB indexing capabilities
- No ability to query inside the embedding JSON at the database level
- The `vector-search.ts` raw SQL approach (`embedding::vector`) won't work with `text` type anyway

**Recommendation:** Change to `jsonb("embedding")` to match the design spec, or update the design spec to reflect the `text` type if there's a deliberate reason.

#### Issue 2: `vector-search.ts` is dead code with multiple bugs (Medium)

**File:** `artifacts/api-server/src/lib/vector-search.ts`

This file is never imported or called anywhere. It also contains:

- Line 28: `eq(l3NodesTable.validityStatus, 'active')` — should be `'valid'` (schema enum is `pending`/`valid`/`orphaned`)
- Line 41-42: Uses `embedding::vector` cast which requires pgvector and a `vector` column type, but the schema uses `text`
- The temporal decay SQL formula uses a hardcoded `0.05` decay rate, while `intent-router.ts` uses `Math.LN2 / 30 ≈ 0.0231`

**Recommendation:** Either remove `vector-search.ts` or fix it and integrate it. If keeping it, fix the validityStatus bug, change the column type to `vector` (requires pgvector), and align the decay rate.

#### Issue 3: In-app cosine similarity doesn't scale (Medium)

**File:** `artifacts/api-server/src/lib/intent-router.ts:203-224,268-278`

The `vectorSearchHandler` fetches ALL rows with non-null embeddings and computes cosine similarity in JavaScript:

```typescript
const l2Rows = await l2Query; // Fetches ALL L2 nodes with embeddings
const l2Scored = l2Rows
  .map((node) => {
    const emb = parseEmbedding(node.embedding);
    const rawScore = emb ? cosineSimilarity(queryEmbedding, emb) : 0;
    // ...
  })
  .sort((a, b) => b.score - a.score)
  .slice(0, limit);
```

For a knowledge graph with 100K nodes (the stated capacity), this means:

- Fetching 100K rows from the database
- Parsing 100K JSON strings
- Computing 1536-dimension dot products 100K times
- All in a single request handler

The design spec says "Raw SQL cosine distance" which would push this work to the database, but the implementation does it in-app.

**Recommendation:** Either use the `vector-search.ts` approach (with pgvector) or add a database-level similarity function. At minimum, add a pre-filter to reduce the candidate set before in-app computation.

#### Issue 4: Duplicate `calculateTemporalDecay` functions (Low)

**Files:** `intent-router.ts:121-127`, `decay.ts:1-6`

Two implementations with different interfaces and default decay rates:

- `intent-router.ts`: `calculateTemporalDecay(referenceDate: Date, now?: number)` — 30-day half-life
- `decay.ts`: `calculateTemporalDecay(updatedAt: Date, decayRate = 0.05)` — configurable rate

The `decay.ts` version is only used by its unit test. The `intent-router.ts` version is used in production.

**Recommendation:** Consolidate into a single implementation. Export from one canonical location.

#### Issue 5: `parseEmbedding` called on every comparison without caching (Low)

**File:** `artifacts/api-server/src/lib/intent-router.ts:216-217,270-271`

`parseEmbedding(node.embedding)` is called for every L2/L3 node during scoring. For 1536-dimension embeddings stored as JSON strings, parsing JSON on every comparison is CPU-intensive.

**Recommendation:** Pre-parse embeddings once before the scoring loop, or cache parsed embeddings.

#### Issue 6: `generateEmbedding` truncates to 8192 chars without warning (Low)

**File:** `artifacts/api-server/src/lib/embedding.ts:16`

```typescript
input: text.slice(0, 8192),
```

The text is silently truncated to 8192 characters. If a large document is embedded, the truncation happens without any log warning, which could lead to unexpected similarity results.

**Recommendation:** Add a debug log when truncation occurs.

### Security Review

- ✅ **No SQL injection in vector search**: The `vectorSearchHandler` uses Drizzle ORM parameterized queries
- ✅ **No SQL injection in `vector-search.ts`**: Uses parameterized queries with Drizzle `sql` template
- ⚠️ **`vector-search.ts` constructs vector string by joining numbers** (line 19): `const vectorStr = `[${embedding.join(",")}]``;` — while the embedding comes from the function parameter (not user input), this is a raw SQL string construction pattern that could be risky if the source changes
- ✅ **Embedding input truncated**: `text.slice(0, 8192)` prevents excessively large inputs to the embedding API

### Performance Considerations

1. **O(N) in-app similarity computation**: The `vectorSearchHandler` fetches ALL rows with embeddings and computes cosine similarity in JavaScript. For 100K nodes with 1536-dimension embeddings, this is ~153.6M floating-point operations per query. This will not scale to the stated 100K node capacity.

2. **No database-level indexing**: Since embeddings are stored as `text` (not `jsonb` or `vector`), there's no way to use database-level indexing for similarity search. A full table scan is required.

3. **N+1 project lookups**: Each vector search result triggers a separate `SELECT name FROM projects` query (lines 227-230, 324-327). With 10 results, this means 10 additional queries.

4. **JSON parsing overhead**: `parseEmbedding()` calls `JSON.parse()` on every row during scoring. For 100K rows, this is 100K JSON parse operations.

5. **The `vector-search.ts` approach would solve the scaling issue** if pgvector were available, as it pushes computation to the database with proper indexing. However, it's currently dead code.

## Recommendations

1. **Fix schema to use `jsonb` (Issue 1)**: Change `text("embedding")` to `jsonb("embedding")` in both `l3_nodes.ts` and `l2_nodes.ts` to match the design spec. This enables JSONB indexing and querying capabilities.

2. **Decide on vector search strategy (Issues 2, 3)**: Choose one approach:
   - **Option A**: Remove `vector-search.ts` and optimize the in-app approach (add pre-filtering, caching, batch project lookups)
   - **Option B**: Fix and integrate `vector-search.ts` — requires adding pgvector extension, changing column type to `vector`, fixing the validityStatus bug, and aligning decay rates

3. **Add integration tests (Issue 4)**: Create integration tests that:
   - Seed the database with factories containing embeddings
   - Test vector search with known similarity expectations
   - Test the fast-path assertion (0 LLM calls for exact matches)
   - Test the fallback assertion (1 LLM call for below-threshold queries)

4. **Consolidate decay functions (Issue 5)**: Remove the duplicate `decay.ts` or make it the canonical implementation used everywhere.

5. **Cache parsed embeddings (Issue 6)**: Pre-parse embeddings once before the scoring loop instead of parsing on every comparison.

6. **Add truncation warning (Issue 7)**: Log a debug message when `generateEmbedding` truncates input.

## Overall Verdict

**⚠️ WARN**

The vector search feature is functionally implemented and works correctly for small datasets. The core math (cosine similarity, temporal decay) is well-tested with unit tests, the embedding generation pipeline is complete, and the graceful fallback to LIKE search is a good resilience pattern.

However, there are significant gaps:

- The schema uses `text` instead of `jsonb` as specified in the design
- There are two conflicting vector search implementations (one active but unscalable, one potentially scalable but dead code with bugs)
- The in-app cosine similarity computation will not scale to the stated 100K node capacity
- Integration tests for vector search are completely absent, including the ADR-007 required fast-path and fallback assertions
