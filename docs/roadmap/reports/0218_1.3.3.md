## Round 1 — Architecture & Design Review

### Does the design document correctly describe the feature?

**Yes, partially.** ADR-007 describes Graph RAG as traversing `node_linksTable` to find structural dependencies, and the implementation in `graphTraversalHandler()` (lines 391–475 of `intent-router.ts`) does exactly this at a basic level:

1. **Seed node lookup** (lines 398–403): Finds an L2 node by name using `LIKE '%moduleName%'` with sanitized input.
2. **Out-link traversal** (lines 425–449): Queries `node_linksTable` for all rows where `sourceNodeId` matches the seed node, then fetches the corresponding target L2 nodes.
3. **L3 association** (lines 452–472): Fetches L3 nodes associated with the seed L2 node, ordered by `occurrenceCount DESC`.

### Gaps between design spec and implementation

1. **"Neighbor Infection" not implemented**: The ADR describes "Neighbor Infection" as a concept, implying multi-hop or recursive traversal of the graph. The current implementation only performs **1-hop out-link traversal** — it follows `node_links` from the seed node to immediate neighbors but never recurses. There is no depth parameter, no BFS/DFS, and no transitive closure.

2. **No link type filtering**: The `node_linksTable` schema includes a `linkType` column (default: `"depends_on"`), but `graphTraversalHandler` does not filter by link type. All out-links are treated equally regardless of relationship semantics.

3. **No inbound link traversal**: The handler only follows out-links (`sourceNodeId = node.id`). It does not traverse in-links (where the seed node is the `targetNodeId`), which would reveal dependents/upstream dependencies. (Note: The MCP endpoint `/mcp/get_dependencies` does query both in-links and out-links, but the core `graphTraversalHandler` does not.)

4. **No temporal decay on graph results**: Unlike `vectorSearchHandler` which applies exponential temporal decay to scores, `graphTraversalHandler` assigns static scores (1.0 for seed, 0.8 for dependencies, 0.9 for L3 nodes) with no decay factor.

### Contradictions between design documents

No contradictions found between ADR-007 and the implementation. The arc42 sections are high-level enough to be consistent.

### Is the feature complete per the design spec?

**No.** The core graph traversal (1-hop out-links + L3 fetch) is implemented, but the "Neighbor Infection" concept (multi-hop traversal) is missing. The feature is functional for direct dependency lookups but incomplete for broader graph analysis.

## Round 2 — Code Quality & Security Review

### Code structure and patterns

The implementation follows the project's conventions:
- Uses Drizzle ORM for database queries ✅
- Uses `sanitizeLikeInput()` to escape SQL LIKE wildcards ✅
- Follows the same handler pattern as `vectorSearchHandler` and `directLookupHandler` ✅
- Exported function with clear TypeScript return type ✅

### Security vulnerabilities

1. **Empty IN clause bug (Medium severity)**: At line 431–435 of `intent-router.ts`:
   ```typescript
   const targetIds = outLinks.map((l) => l.targetNodeId);
   const relatedL2s = await db
     .select()
     .from(l2NodesTable)
     .where(sql`${l2NodesTable.id} IN ${targetIds}`);
   ```
   If `outLinks` is empty (the seed node has no out-links), `targetIds` will be `[]`, producing `IN ()` which is **invalid SQL** and will throw a database error. The code checks `if (outLinks.length > 0)` before the query (line 430), so this is actually safe — the guard clause prevents the empty IN case. **No vulnerability here**, but the code structure is fragile; a future refactor could easily remove the guard.

2. **No input validation on moduleName**: The `graphTraversalHandler` does not validate that `moduleName` is non-empty. An empty string would produce `LIKE '%%'` which matches **all L2 nodes**. The handler then picks `nodes[0]` (or the one matching `projectId`), which could return an arbitrary node. This is a low-severity issue since the intent router typically provides moduleName from LLM extraction, but it's still a defensive gap.

3. **No validity status filtering on L3 results**: At line 453–458, the handler fetches L3 nodes without filtering by `validityStatus`:
   ```typescript
   const l3Decisions = await db
     .select()
     .from(l3NodesTable)
     .where(eq(l3NodesTable.l2NodeId, node.id))
   ```
   Compare with `vectorSearchHandler` which applies `l3ValidityCondition` (lines 197–199). This means graph traversal may return orphaned or pending L3 nodes that should be hidden by default.

### Code smells and anti-patterns

1. **N+1 query pattern**: Lines 437–448 iterate over `relatedL2s` but don't make additional queries per node (the project name lookup was already done). However, the MCP endpoints (`mcp.ts` lines 110–128) do have N+1 patterns for dependency resolution.

2. **Static scoring**: Graph results use hardcoded scores (1.0, 0.8, 0.9) with no normalization or contextual scoring. This makes hybrid merging less meaningful since graph scores don't reflect actual relevance.

3. **Missing test coverage**: The unit test file (`intent-router.unit.test.ts`) only tests `escapeLike`, `calculateTemporalDecay`, and `sanitizeQuery`. There are **no tests for `graphTraversalHandler`**, `vectorSearchHandler`, `directLookupHandler`, or `hybridSearch`. This is a significant gap for a core routing component.

### Error handling

- The handler has no try/catch — errors propagate to the caller (`routeQuery`), which also has no try/catch for the graph_traversal case. The `routeQuery` function relies on the route-level error handling (e.g., `search.ts` line 29 catches and returns 500). This is acceptable but means graph traversal errors produce generic 500 responses with no structured error information.

## Round 3 — Integration & Completeness Review

### Integration with other system components

1. **Intent Router → Graph Handler**: The `routeQuery` function correctly routes to `graphTraversalHandler` when the classification strategy is `"graph_traversal"` (lines 701–704). The moduleName is extracted from the classification entities or falls back to the raw query.

2. **O(1) Fast-Path**: The intent router includes a fast-path at lines 660–682 that checks if the query contains any known L1 tag names or L2 node names. If matched, it bypasses LLM classification and routes directly to graph traversal. This is a well-designed optimization.

3. **MCP Integration**: The MCP server exposes two graph-related endpoints:
   - `GET /mcp/get_dependencies` (lines 85–131): Queries both in-links and out-links for a module, returning dependency and dependent lists.
   - `GET /mcp/impact_analysis` (lines 133–174): Queries in-links to find impacted modules and counts L3 decisions.
   
   These endpoints **duplicate** some of the graph traversal logic already in `graphTraversalHandler` rather than reusing it. This is a code duplication concern.

4. **REST API**: The l2_nodes route provides `GET /l2-nodes/:id/links` and `POST /l2-nodes/:id/links` for managing node links, which is the CRUD complement to the graph traversal read path.

5. **Search Route**: The `POST /search` endpoint (search.ts) calls `routeQuery` which may route to graph traversal. The `POST /search/feedback` endpoint updates `lastVerifiedAt` for L2/L3 nodes, which feeds into temporal decay.

### Missing tests

- **No unit tests for `graphTraversalHandler`**: The handler is completely untested at the unit level.
- **No integration tests for graph traversal**: No integration tests verify the graph traversal with seeded database state.
- **No tests for the O(1) graph fast-path**: The fast-path at lines 660–682 is untested.

### Performance concerns

1. **No database index on `node_linksTable.sourceNodeId` or `targetNodeId`**: The schema does not define indexes on these foreign key columns. For large graphs, the `WHERE sourceNodeId = ?` and `WHERE targetNodeId = ?` queries will perform full table scans. This should be added as a database index.

2. **No caching**: The O(1) fast-path at lines 661–667 queries all L1 tags and all L2 nodes on every query to build the term list. This is O(n) in the number of tags/nodes, not O(1) as the ADR claims. For large knowledge graphs, this should be cached.

### End-to-end usability

The feature is **usable end-to-end** for the basic case: a user queries "what are the dependencies of module X?" and the system routes to graph traversal, finds the L2 node, follows out-links, and returns related nodes. However:

- Multi-hop queries ("what indirectly depends on X?") are not supported.
- The MCP `get_dependencies` endpoint provides a cleaner graph API than the intent router's graph handler, suggesting the intent router's graph handler may be underutilized.

## Findings Summary

### Issues

| # | Severity | Finding |
|---|----------|---------|
| 1 | Medium | No `validityStatus` filter on L3 nodes in `graphTraversalHandler` — may expose orphaned/pending nodes |
| 2 | Medium | No database indexes on `node_links.sourceNodeId` and `node_links.targetNodeId` — performance will degrade with graph size |
| 3 | Medium | No unit or integration tests for `graphTraversalHandler` — core routing logic is untested |
| 4 | Low | "Neighbor Infection" (multi-hop traversal) described in ADR-007 is not implemented — only 1-hop out-links |
| 5 | Low | No link type filtering in graph traversal — all `linkType` values are treated equally |
| 6 | Low | No inbound link traversal in `graphTraversalHandler` — only out-links are followed |
| 7 | Low | O(1) fast-path is actually O(n) — queries all L1/L2 names on every request with no caching |
| 8 | Low | Code duplication between `graphTraversalHandler` and MCP endpoints (`get_dependencies`, `impact_analysis`) |
| 9 | Low | No temporal decay applied to graph traversal results — static scores may misrepresent stale knowledge |
| 10 | Info | No input validation on `moduleName` parameter — empty string would match all L2 nodes |

### Recommendations

1. **Add `validityStatus` filter** to the L3 query in `graphTraversalHandler` (consistent with `vectorSearchHandler`).
2. **Add database indexes** on `node_linksTable.sourceNodeId` and `node_linksTable.targetNodeId`.
3. **Write unit tests** for `graphTraversalHandler` covering: seed node found/not found, with/without out-links, with/without L3 nodes, project-scoped queries.
4. **Consider implementing multi-hop traversal** with a configurable depth limit to fulfill the "Neighbor Infection" design.
5. **Extract shared graph logic** between `graphTraversalHandler` and MCP endpoints into a reusable function.
6. **Add temporal decay** to graph traversal scores for consistency with other search strategies.

---

## Overall Verdict

**⚠️ WARN** — The graph traversal feature is implemented and functional for the basic 1-hop case, and integrates correctly with the intent router and MCP. However, it lacks test coverage, doesn't filter L3 nodes by validity status, doesn't implement the multi-hop "Neighbor Infection" described in the design, and has no database indexes for the `node_links` table. The feature works for direct dependency lookups but is incomplete for broader graph analysis.
