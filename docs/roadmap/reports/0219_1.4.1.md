## Round 1 — Architecture & Design Review

### What the ADR Specifies

ADR-008 describes a **DB-backed asynchronous metabolism** system with these key components:

1. **PostgreSQL State Machine** — Heavy operations are written with `status: 'pending'` or `processedAt: null`; the API returns `200 OK` immediately.
2. **Client-Driven Heartbeat (Drip Feed)** — VS Code extension pings `GET /api/metabolism-tick` periodically, triggering micro-batch execution of N pending tasks.
3. **Admin Cron Endpoint** — `GET /admin/metabolism-tick` for idle periods, authenticated via `ADMIN_SECRET_TOKEN`, fail-closed.
4. **Distributed Postgres Job Queue** — Protected by `FOR UPDATE SKIP LOCKED` + `locked_at` timestamp for split-brain prevention and zombie-reaper recovery.
5. **Optimistic Locking for Generate Pipeline** — `UPDATE ... WHERE status = 'active'` with stale-indexing recovery after 30 minutes.
6. **Dead Letter Queue (DLQ)** — Tasks that fail 3 times transition to `DEAD_LETTER_QUEUE` status.

### Gaps Between Design and Implementation

1. **In-memory mutex vs. distributed Postgres lock**: The ADR explicitly calls for `FOR UPDATE SKIP LOCKED` with a `locked_at` timestamp to prevent split-brain race conditions when multiple API servers poll. The implementation uses a simple `let isMetabolismRunning = false` boolean, which only works for a single Node.js process. This is a **significant architectural deviation** — if the API server is scaled to multiple instances (e.g., PM2 cluster, Kubernetes), concurrent metabolism ticks will run simultaneously.

2. **Job queue table is dead code**: The `job_queue` table schema exists with all the right columns (`lockedAt`, `status`, `taskType`, `payload`) but is never used. The metabolism worker directly queries `correction_examples` and `l3_nodes` instead of pulling from a job queue. This means the state machine described in the ADR (PENDING → ACTIVE → COMPLETED/FAILED → DLQ) is not implemented.

3. **No dead letter queue**: The ADR mandates that tasks failing 3 times transition to `DEAD_LETTER_QUEUE`. The current implementation has no retry counting and no DLQ. If the LLM call for distillation fails, the error is logged but the correction is still marked as processed (`processedIds.push(correction.id)` happens regardless of individual failures — see `metabolism.ts:129-132`).

4. **No zombie-reaper**: The ADR describes automatic recovery for crashed processes via `locked_at` timestamp. Not implemented.

## Round 2 — Code Quality & Security Review

### Security Findings

1. **✅ Fail-closed admin endpoint**: The `/admin/metabolism-tick` route correctly returns 500 when `ADMIN_SECRET_TOKEN` is missing in non-development mode (`metabolism.ts:171-179`). The dev fallback to `"dev-secret-token"` is acceptable for local development.

2. **✅ Token validation**: Both `Authorization: Bearer` and `admin_token` query parameter are supported (`metabolism.ts:181-189`). The comparison uses strict equality (`token !== adminSecret`).

3. **⚠️ No authentication on client tick endpoint**: `GET /api/metabolism-tick` has no authentication at all. Any caller can trigger metabolism work. While this is a relatively low-risk endpoint (it only processes pending internal tasks), it could be abused for DoS by repeatedly triggering expensive LLM operations. Consider adding at least a lightweight shared-secret check.

4. **⚠️ `GITHUB_TOKEN` from env without validation**: `metabolism.ts:55` reads `process.env.GITHUB_TOKEN` but doesn't validate its presence before the merge gate loop. If the token is missing, the GitHub API calls will fail silently (caught by try/catch at line 69), and no L3 nodes will be promoted. This is acceptable fallback behavior but could lead to silent failures.

### Code Quality Findings

1. **⚠️ Distillation marks corrections as processed even on failure**: At `metabolism.ts:129`, `processedIds.push(correction.id)` is inside the `try` block but after the LLM call. If `openai.chat.completions.create` throws, the correction is NOT added to `processedIds` (correct). However, if the LLM returns a response but `guardrail` is falsy (empty string, null), the correction IS added to `processedIds` at line 129 but no prompt template is created. This means corrections can be silently marked as processed without producing any distillation output.

2. **⚠️ No batch size limit on merge gate**: The merge gate query at `metabolism.ts:21-36` has no `.limit()`. If thousands of L3 nodes are pending, all will be fetched and processed in a single tick. This could cause memory pressure and long-running requests.

3. **⚠️ Sequential LLM calls in distillation loop**: The distillation job at `metabolism.ts:102-133` calls the LLM sequentially for each correction. With a limit of 10, this could take a significant amount of time. No timeout or overall time budget is enforced.

4. **✅ Proper `finally` block for mutex release**: Both tick handlers use `finally { isMetabolismRunning = false }` (`metabolism.ts:163-165`, `metabolism.ts:204-206`), ensuring the mutex is released even on errors.

5. **✅ Error isolation in merge gate**: Each commit check is wrapped in its own try/catch (`metabolism.ts:62-72`), so one failed GitHub API call doesn't prevent processing of other nodes.

6. **⚠️ `any` type usage**: `metabolism.ts:99` uses `const promptsToInsert: any[]` — should use the proper Drizzle insert type.

   - **Mutex Lock Proof**: "Concurrent test runners MUST attempt to claim the same pending task simultaneously. DB assertions MUST prove exactly 1 worker transitions the task to ACTIVE."

   Neither test exists. The DLQ feature itself is not implemented, so the DLQ test cannot pass.

## Findings

### Issues

1. **[ARCH-1] In-memory mutex instead of distributed Postgres lock** — The ADR-008 explicitly requires `FOR UPDATE SKIP LOCKED` with `locked_at` for multi-instance safety. The current `let isMetabolismRunning = false` boolean only works for a single process. This is a design-deviation that will cause race conditions if the API server is ever scaled horizontally.

2. **[ARCH-2] `job_queue` table is dead code** — The schema exists with all required columns but is never used. The metabolism worker directly queries domain tables (`correction_examples`, `l3_nodes`) instead of pulling from a job queue. The ADR's state machine (PENDING → ACTIVE → COMPLETED/FAILED → DLQ) is not implemented.

3. **[ARCH-3] No dead letter queue** — Tasks that fail during distillation are not retried or moved to a DLQ. The ADR mandates 3 retries before DLQ transition. Currently, failed LLM calls are logged but the correction may still be marked as processed.

4. **[BUG-1] Corrections silently marked as processed** — If the LLM returns a falsy guardrail (empty/null), the correction is still added to `processedIds` and marked as processed, with no distillation output created. This data loss means the correction is wasted.

5. **[BUG-2] No limit on merge gate query** — The query for pending L3 nodes has no `.limit()`, risking memory pressure with large backlogs.

6. **[SEC-1] Client tick endpoint unauthenticated** — `GET /api/metabolism-tick` has no authentication, allowing any caller to trigger expensive LLM operations.

7. **[TEST-1] Zero test coverage** — No tests exist for the metabolism feature. The ADR's mandatory DLQ routing proof and mutex lock proof are both missing.

8. **[SPEC-1] Missing OpenAPI definitions** — The metabolism endpoints are not in `openapi.yaml`, violating the project's API-first convention.

### Recommendations

1. **Replace the in-memory mutex** with Postgres `FOR UPDATE SKIP LOCKED` on the `job_queue` table, as the ADR specifies. This enables multi-instance deployments and provides the zombie-reaper recovery via `locked_at`.

2. **Implement the job queue state machine** — Use `job_queue` table for the metabolism worker. Insert jobs when corrections are created or L3 nodes need merge-gate checking. The worker should pull from `job_queue` with proper locking.

3. **Add DLQ support** — Add a `retryCount` column to `job_queue` (or use the existing schema with a retry counter). After 3 failures, transition to a `dead_letter` status.

4. **Fix the distillation guardrail falsy-value bug** — Only add `correction.id` to `processedIds` if a non-empty guardrail was actually produced and inserted.

5. **Add `.limit()` to the merge gate query** — Process at most N nodes per tick (e.g., 50) to bound execution time.

6. **Add authentication to the client tick endpoint** — At minimum, require the same `x-docuvia-token` used for other API endpoints.

7. **Write the ADR-mandated tests** — DLQ routing proof and mutex lock proof as specified in ADR-008.

8. **Add metabolism endpoints to `openapi.yaml`** and run Orval codegen.

---

## Overall Verdict

⚠️ WARN — The core metabolism mechanism is implemented and functional: the client heartbeat tick, admin cron tick, merge gate fallback, and distillation job all exist and work. The generate pipeline has proper optimistic locking. However, there are significant architectural deviations from ADR-008 (in-memory mutex instead of distributed Postgres lock, dead-code job queue table, no DLQ, no zombie-reaper), one data-loss bug in the distillation logic, no test coverage, and missing OpenAPI definitions. The feature is operational for single-instance deployments but not ready for production multi-instance scaling.
