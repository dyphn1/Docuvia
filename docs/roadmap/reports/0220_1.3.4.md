## Round 1 — Architecture & Design Review

### What the Design Spec Requires

The design spec (ADR-007) defines Direct RAG as:

- **O(1) lookup via commit hashes** — when the query is a commit hash
- **Full-text search against `l3_nodes.content`** — when no hash is provided
- The runtime view (§6.3) shows: `API->>DB: Full-text search on l3_nodes.content`
- ADR-007 §6 Verifiability requires: "Integration tests MUST seed the database using factories, trigger an exact-match query, and use MSW to strictly assert that 0 external HTTP requests are made to the AI server"

### Implementation Status

| Criterion                          | Status             | Notes                                                                                                                                                                                |
| ---------------------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Commit hash lookup                 | ✅ Implemented     | `intent-router.ts:490-516` — regex `/^[0-9a-fA-F]{4,40}$/` detects hashes, queries `introducedInCommit`                                                                              |
| Content search                     | ⚠️ Partial         | Uses `ILIKE` pattern matching, not true PostgreSQL FTS (`to_tsvector`/`to_tsquery`)                                                                                                  |
| Title search                       | ✅ Implemented     | `ILIKE` on `l3_nodes.title` (line 528)                                                                                                                                               |
| Integration with `routeQuery()`    | ✅ Implemented     | Called at `intent-router.ts:706-709` for `direct_lookup` strategy                                                                                                                    |
| Fast-path (skip LLM)               | ✅ Implemented     | `intent-router.ts:627-644` — single-word queries skip LLM classification                                                                                                             |
| `includePending` filter            | ❌ Broken          | Checks `validityStatus !== 'active'` but schema uses `'valid'`/`'pending'`/`'orphaned'` — no node ever matches `'active'`, so ALL nodes are filtered out when `includePending=false` |
| True PostgreSQL FTS                | ❌ Not implemented | Code comment at line 521-522 explicitly says "sticking to ILIKE"                                                                                                                     |
| ADR-007 fast-path integration test | ❌ Missing         | No integration test asserting 0 LLM calls for exact-match queries                                                                                                                    |

### Critical Finding: `validityStatus` Bug in Direct Lookup

The `directLookupHandler` has a **data-loss bug** on lines 500 and 535:

```typescript
// Line 500 (commit hash path):
if (!includePending && l3.validityStatus !== "active") continue;

// Line 535 (content search path):
if (!includePending && l3.validityStatus !== "active") continue;
```

The schema defines `validityStatus` with values `'pending'`, `'valid'`, `'orphaned'` (see `l3_nodes.ts:37`). The value `'active'` **does not exist** in the schema. This means:

- When `includePending = false` (the default): ALL nodes are skipped because no node has `status === 'active'`. The direct search **always returns empty results** by default.
- When `includePending = true`: All nodes are returned regardless of status, including orphaned ones.

Compare this with the vector search handler (line 198-199) which correctly uses:

```typescript
eq(l3NodesTable.validityStatus, "valid");
```

This is a **critical bug** that makes the direct search feature non-functional in its default configuration.

### Gap: ILIKE vs. True Full-Text Search

The design spec says "full-text search" but the implementation uses `ILIKE` (case-insensitive pattern matching). The code itself acknowledges this gap:

```typescript
// Line 521-522:
// We would ideally use Postgres Full Text Search (to_tsvector/to_tsquery)
// but sticking to ILIKE for architectural continuity here.
```

ILIKE has several limitations compared to true FTS:

- No relevance ranking (no `ts_rank`)
- No stemming or language-aware tokenization
- No phrase search support
- Poor performance on large text columns (requires full table scan)
- No support for boolean operators (AND, OR, NOT)

However, for the v1 scope with ≤100K nodes, ILIKE is a reasonable pragmatic choice. The design spec's use of "full-text search" is aspirational.

### Gap: No Integration Tests for Direct Search

ADR-007 §6 requires integration tests that:

1. Seed the database using factories
2. Trigger an exact-match query
3. Assert 0 external HTTP requests (fast-path assertion)

No such integration test exists. The `intent-router.unit.test.ts` file tests utility functions (`escapeLike`, `sanitizeQuery`, `calculateTemporalDecay`) but does NOT test `directLookupHandler` or the fast-path logic.

## Round 2 — Code Quality & Security Review

### Strengths

- **Clean separation of concerns**: `directLookupHandler` is a standalone exported function with clear inputs/outputs
- **Input sanitization**: `sanitizeLikeInput()` escapes SQL LIKE wildcards (`%`, `_`, `\`) preventing LIKE injection
- **Fast-path optimization**: The single-word fast-path in `routeQuery()` (line 627-644) correctly avoids LLM classification for simple symbol lookups
- **Dual search paths**: Commit hash lookup and content search are cleanly separated with the `isHash` regex check
- **Proper integration**: The handler is correctly wired into the `routeQuery()` switch statement and accessible via both REST (`POST /search`) and MCP (`POST /mcp/query`, `GET /mcp/search_knowledge`) endpoints

### Issues Found

#### Issue 1: `validityStatus` bug — checks `'active'` instead of `'valid'` (CRITICAL)

**File:** `artifacts/api-server/src/lib/intent-router.ts:500,535`

```typescript
if (!includePending && l3.validityStatus !== "active") continue;
```

The schema defines `validityStatus` as `text("validity_status").notNull().default("pending")` with enum values `'pending'`, `'valid'`, `'orphaned'`. The value `'active'` does not exist.

**Impact:** When `includePending = false` (the default for all MCP and search queries), the direct lookup handler **always returns empty results** because no node ever has `validityStatus === 'active'`. This makes the entire direct search feature non-functional in production.

**Fix:** Change `'active'` to `'valid'` on both lines 500 and 535:

```typescript
if (!includePending && l3.validityStatus !== "valid") continue;
```

#### Issue 2: ILIKE instead of true full-text search (Low)

**File:** `artifacts/api-server/src/lib/intent-router.ts:523-532`

The implementation uses `ILIKE` for content search instead of PostgreSQL's `to_tsvector`/`to_tsquery`. While this is a deliberate pragmatic choice (acknowledged in the code comment), it means:

- No relevance ranking
- No stemming
- Full table scan required

**Recommendation:** Either update the design spec to reflect ILIKE-based search, or implement true FTS with `to_tsvector`/`to_tsquery` and a GIN index on `l3_nodes.content`.

#### Issue 3: N+1 project lookup queries in commit hash path (Low)

**File:** `artifacts/api-server/src/lib/intent-router.ts:502`

```typescript
const [l2] = await db
  .select({ projectId: l2NodesTable.projectId })
  .from(l2NodesTable)
  .where(eq(l2NodesTable.id, l3.l2NodeId));
```

This query runs once per L3 node in the result set. For a commit that affects 20 L3 nodes, this means 20 additional queries.

**Recommendation:** Batch the project lookups or use a JOIN like the vector search handler does (line 245-254).

#### Issue 4: No unit tests for `directLookupHandler` (Medium)

**File:** `artifacts/api-server/src/lib/intent-router.unit.test.ts`

The test file covers utility functions but does NOT test `directLookupHandler`. There are no tests for:

- Commit hash lookup path
- Content/title ILIKE search path
- `includePending` filtering behavior
- The single-word fast-path in `routeQuery()`

**Recommendation:** Add unit tests for `directLookupHandler` covering both code paths and the `includePending` filter.

#### Issue 5: `projectName` always null in direct lookup results (Low)

**File:** `artifacts/api-server/src/lib/intent-router.ts:512,546`

```typescript
projectName: null,
```

Unlike the vector search handler which resolves project names (line 227-230), the direct lookup handler always sets `projectName` to `null`. This means clients displaying direct search results won't show the project name.

**Recommendation:** Either resolve the project name via a JOIN (like vector search does) or via a separate query.

### Security Review

- ✅ **No SQL injection in LIKE search**: `sanitizeLikeInput()` properly escapes `%`, `_`, and `\` characters before constructing the LIKE pattern
- ✅ **No SQL injection in commit hash path**: Uses Drizzle ORM parameterized queries with `like(l3NodesTable.introducedInCommit, ...)`
- ✅ **Input length limit**: `sanitizeQuery()` truncates to 2000 characters; MCP endpoint validates `q` with Zod `.max(2000)`
- ✅ **MCP auth**: All `/mcp/*` routes require Bearer token via `MCP_PAT` environment variable
- ✅ **Search endpoint validation**: `POST /search` uses Zod schema validation (`SearchSchema`)

### Performance Considerations

1. **ILIKE performance**: `ILIKE '%query%'` cannot use standard B-tree indexes and requires a full table scan. For 100K L3 nodes, this could be slow. A `pg_trgm` GIN index would help.

2. **No index on `introducedInCommit`**: The commit hash lookup uses `LIKE` on `introducedInCommit` without an index. An index on this column would improve hash lookup performance.

3. **N+1 queries**: As noted in Issue 3, the commit hash path makes N+1 project lookup queries.

## Recommendations

1. **Fix the `validityStatus` bug immediately (Issue 1)**: Change `'active'` to `'valid'` on both lines 500 and 535 of `intent-router.ts`. This is a one-character fix that restores the direct search feature to working order.

2. **Add unit tests for `directLookupHandler` (Issue 2)**: Create tests covering:
   - Commit hash lookup with valid/invalid hashes
   - Content/title ILIKE search
   - `includePending = false` filtering (should only return `valid` nodes)
   - `includePending = true` filtering (should return `valid` + `pending` nodes)
   - Empty result handling

3. **Add integration tests (Issue 3)**: Create integration tests that:
   - Seed the database with factories containing L3 nodes with known content
   - Trigger exact-match queries and assert 0 LLM calls (fast-path assertion per ADR-007)
   - Verify the direct search returns expected results

4. **Decide on FTS strategy (Issue 4)**: Either:
   - Update the design spec to reflect ILIKE-based search (simpler)
   - Implement true FTS with `to_tsvector`/`to_tsquery` and a GIN index (more powerful)

5. **Batch project lookups (Issue 5)**: Use a JOIN or batch query instead of N+1 lookups in the commit hash path.

6. **Resolve project names (Issue 6)**: Either use a JOIN (like vector search) or a separate query to populate `projectName` in direct search results.

## Overall Verdict

**⚠️ WARN**

The direct search feature is architecturally well-designed with clean separation of concerns, proper input sanitization, and correct integration into the intent routing pipeline. The commit hash lookup and content search paths are logically sound, and the single-word fast-path optimization is a good token-saving measure.

However, there is a **critical data-loss bug** that makes the feature non-functional in production: the `validityStatus` filter checks for `'active'` instead of `'valid'`, causing the direct search to always return empty results when `includePending = false` (the default). This bug exists in both the commit hash path (line 500) and the content search path (line 535).

Additionally, there are no unit or integration tests for the direct search handler, which means this bug went undetected. The ADR-007 required fast-path integration test (asserting 0 LLM calls) is also missing.

The use of ILIKE instead of true PostgreSQL FTS is a known and acknowledged limitation that is acceptable for v1 but should be addressed in a future iteration.
