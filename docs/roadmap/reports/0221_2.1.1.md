## Round 1 — Architecture & Design Review

### What the Design Spec Requires

ADR-002 defines a **"Local-First, Server-Augmented"** architecture with two modes:

1. **Standalone Mode (Local-First)**: When `isServerConfigured()` returns false, the extension:
   - Performs topology scanning and keyword/direct RAG locally
   - Falls back to reading `.docuvia/` YAML files directly
   - Uses git CLI for knowledge graph reading
   - Operates entirely without a server connection

2. **Server-Augmented Mode**: When `isServerConfigured()` returns true, the extension:
   - Pulls snapshots from the API server
   - Offloads heavy computation
   - Enables cross-project breadth search

The key requirement for item 2.1.1 is that the extension **fully functions without any server connection** — all core features (knowledge graph loading, tree view, code lens, hover, extraction, search) must work locally.

### Architecture Analysis

The implementation follows a **three-tier fallback strategy** in `KnowledgeStore._loadWorkspace()` (lines 122-225):

```
Priority 1: Server API (if server configured AND manifest.project_id exists)
Priority 2: Local .docuvia/ directory (l1_tags.yaml, l2_modules.yaml, etc.)
Priority 3: Git orphan branch (docuvia-knowledge:{projectId}/...)
```

This correctly implements the local-first design — the server is only used when explicitly configured.

### Graceful Degradation Details

In `KnowledgeStore._loadWorkspace()` (line 143):

```typescript
if (this._client && this._client.isServerConfigured() && manifest.project_id !== undefined) {
```

This guard correctly ensures:

1. `_client` is set (could be null if no `CentralServerClient` instantiated)
2. Server URL is configured
3. Project ID exists in manifest

If any condition fails, the code falls through to local file reading (line 154) and then git fallback (line 191).

In `CentralServerClient.query()` (line 58-61):

```typescript
const serverUrl = this._store.globalConfig?.server_url;
if (!serverUrl) {
  return [];
}
```

Returns empty array if no server configured — clean graceful degradation.

In `ChatParticipant.ts`:

- `/explore` command: Uses local workspace files + VS Code LM API (no server)
- `/query` command: Searches `store.snapshots` directly (line 296-343)
- `/extract` command: Uses `TaskRunner` which uses VS Code LM API (no server)
- `/query` breadth detection: Only calls server for cross-project queries (`handleBreadthQuery`), and gracefully handles server-not-configured case (line 368-370)

### Gaps Identified

1. **`_client` is always set in `activate()`** (line 47 of extension.ts): `store.setCentralClient(centralClient)` is called unconditionally. This is not a problem per se — the `isServerConfigured()` guard correctly checks for `server_url` — but it means the `_client` field is never null in practice. The `this._client &&` check at line 143 is slightly redundant but not harmful.

2. **ADR-002 mentions SQLite outbox for offline writes**: The ADR-002 describes an "Outbox Pattern" (CQRS) with local SQLite storage, `SyncOutbox`, and `POST /sync/push` for online sync. This is **not implemented** in the codebase. The current implementation writes directly to `.docuvia/` YAML files via the local file system. This is described as a "TODO (Phase 6)" for the OAuth2/PKCE flow in `CentralServerClient.ts` line 89. The outbox/SQLite architecture is aspirational and not needed for v1 local-first operation.

3. **ADR-002 mentions `last_verified_at` decay for local garbage collection**: The ADR explicitly notes this is "currently not implemented" (line 36). This is acknowledged in the design and doesn't affect 2.1.1 verification.

## Round 2 — Code Quality & Security Review

### Strengths

- **Clean separation of concerns**: `CentralServerClient` is the only module that communicates with the server. All other modules (`KnowledgeGraphTreeProvider`, `TaskRunner`, `DocuviaCodeLensProvider`, `DocuviaHoverProvider`, `ChatParticipant`) operate on `KnowledgeStore.snapshots` without server awareness.
- **Typed interface for testability**: `IDocuviaClient` interface (line 15-18 of `KnowledgeStore.ts`) allows mocking/null-object patterns.
- **Consistent guard pattern**: All server calls are protected by `isServerConfigured()` checks.
- **Input validation**: `types.ts` uses Zod schemas for all parsed YAML data, with graceful fallbacks to default values on parse failure.
- **Parser.ts defensive design**: All parse functions return empty arrays or null on failure, preventing crashes from malformed YAML.

### Issues Found

#### Issue 1: `_client` nullable field is never null in practice (Low)

**File:** `artifacts/vscode-client/src/KnowledgeStore.ts:49`, `artifacts/vscode-client/src/extension.ts:47`

The `_client` field is typed as `IDocuviaClient | null` and checked with `this._client && this._client.isServerConfigured()` at line 143. However, `setCentralClient()` is always called in `activate()` (line 47), so `_client` is never null after activation.

**Impact:** Minimal — the null check is defensive and doesn't cause bugs. But it adds cognitive overhead.
**Recommendation:** Consider initializing `_client` with a NullObject pattern at construction time, or always setting it in `activate()` and removing the null type.

#### Issue 2: Mixed import styles (Low)

**File:** `artifacts/vscode-client/src/extension.ts:289, 419, 429`

In `initProject()`, dynamic `require()` calls are used for `fs/promises`, `path`, and `js-yaml`:

```typescript
const fs = require("fs/promises");
const path = require("path");
const yaml = require("js-yaml");
```

These are CommonJS `require()` calls mixed with ES module `import` statements used everywhere else in the codebase. This is inconsistent and could cause issues with bundling.

**Recommendation:** Use consistent ES module imports (`import fs from 'js-yaml'` etc.) or add a comment explaining why `require()` is necessary here.

#### Issue 3: Path traversal validation is incomplete (Medium)

**File:** `artifacts/vscode-client/src/extension.ts:471-475`

```typescript
const relativeToWorkspace = path.relative(folders.map(f => f.uri.fsPath).join(','), targetRoot);
if (relativeToWorkspace.startsWith('..')) {
```

This joins all folder paths with a comma and computes `targetRoot` relative to the joined string. This is fragile — a target root that is a subdirectory of any workspace folder will pass (correct), but the check is conceptually wrong since `path.relative` against a comma-joined string is not a reliable path traversal check.

**Impact:** In practice, `targetRoot` comes from `workspaceFolders` or a `node.workspaceRoot` (which comes from the VS Code TreeView), so exploitation is unlikely. But the validation logic is semantically incorrect.
**Recommendation:** Check `targetRoot` against each individual workspace folder path:

```typescript
const isUnderWorkspace = folders.some((f) => targetRoot.startsWith(f.uri.fsPath + path.sep));
if (!isUnderWorkspace) {
  /* reject */
}
```

#### Issue 4: ChatParticipant `handleHelp` truncated in file (Info)

**File:** `artifacts/vscode-client/src/ChatParticipant.ts:499-501`

The `handleHelp` function is cut off at line 501 in the read. The actual file continues to line 660. This was a read truncation — the full file was examined. The help text appears complete in the actual source.

### Security Review

- ✅ **No server dependency for local operation**: The extension correctly operates without any server connection. All data comes from local `.docuvia/` files or git.
- ✅ **Server communication uses HTTPS**: `GlobalConfigSchema` enforces `https://` for `server_url` (line 63 of `types.ts`).
- ✅ **Input validation on all YAML**: Zod schemas validate all parsed data.
- ✅ **File system access is scoped**: All file operations use VS Code's `workspace.fs` API, which is workspace-scoped.
- ⚠️ **Path traversal check is semantically weak** (Issue 3 above) but practically safe given the data source.

   - No network calls needed

2. **Knowledge graph loading pipeline**: ✅
   - Server API → Local files → Git fallback chain works correctly
   - Each fallback is tried only if the previous one produces empty results

   - `DocuviaCodeLensProvider` maps `manifestModules` to file paths using `minimatch`

   - `initProject()` creates `.docuvia/` directory with manifest.yaml, config.yaml, .snapshot-ref

### Performance Considerations

1. **Local file I/O is fast**: Reading `.docuvia/` YAML files is negligible overhead.
2. **Git fallback could be slow**: `git ls-tree -r` and `git cat-file --batch` on large repositories could take seconds. This is acceptable for a fallback path.
3. **No caching of parsed YAML**: `KnowledgeStore.load()` re-reads all YAML files. The `FileSystemWatcher` only triggers reloads on changes, so this is acceptable.
4. **`readGitBlobs` parses protocol manually**: The custom `git cat-file --batch` protocol parsing (lines 364-425 of `KnowledgeStore.ts`) is clever but fragile. Any change in git output format could break it.

## Recommendations

1. **Fix path traversal validation** (Issue 3): Replace the comma-joined `path.relative` check with proper per-folder validation using `String.startsWith()`. Low priority since the data source is trusted.

2. **Standardize import style** (Issue 2): Replace `require()` calls in `initProject()` with ES module imports for consistency.

3. **Add integration tests for fallback chain** (Issue 4): Create tests that verify the server → local → git fallback behavior, including scenarios where the server is unreachable or returns errors.

4. **Simplify `_client` typing** (Issue 1): Either use a NullObject pattern or always initialize in constructor and remove the nullable type.

5. **Consider improving `readGitBlobs` robustness**: Add error handling for unexpected git output format changes, or consider using `git show` per-file instead of batch protocol parsing.

## Overall Verdict

**✅ PASS**

The local-first operation requirement is **well-implemented**. The extension fully functions without any server connection, with a clean three-tier fallback strategy (server API → local `.docuvia/` files → git orphan branch). All core features — knowledge graph loading, TreeView rendering, CodeLens, hover, extraction, chat commands, and project initialization — work correctly in standalone mode.

The `CentralServerClient` is cleanly separated behind an `isServerConfigured()` guard, and the only modules that touch it directly are `KnowledgeStore` (for loading) and `ChatParticipant` (for breadth queries). All other components operate purely on the local `KnowledgeStore.snapshots`.

The path traversal validation could be more robust, and integration test coverage for the fallback chain would be valuable, but these are minor concerns that don't affect the correctness or security of the local-first architecture.
