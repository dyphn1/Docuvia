## Round 1 — Architecture & Design Review

**Design Spec (ADR-007) says:**

> **Hybrid RAG**: Intersection of graph constraints and vector similarities with cross-validation boosting (nodes found in both sets receive a compounding score boost). Implemented as `hybridSearch()` in `intent-router.ts`.

**Implementation (intent-router.ts, lines 560–608):**

The `hybridSearch()` function follows a 5-step pipeline:

1. **Vector search**: Calls `vectorSearchHandler()` to get semantically similar L2 and L3 nodes (line 570)
2. **Extract L2 seeds**: Takes the top-3 L2 node names from vector results (lines 573–576)
3. **Graph traversal**: Runs `graphTraversalHandler()` for each extracted L2 name to find structurally related nodes (lines 579–582)
4. **Merge with boost**: Builds a map keyed by `nodeLayer:id`. Nodes present in **both** vector and graph results receive a score boost of `r.score + 0.5` (lines 584–601)
5. **Re-rank**: Sorts merged results by score descending, returns top `limit` (lines 603–607)

**Findings:**

- ✅ The implementation matches the design spec: it performs both vector and graph retrieval, merges them, and applies a scoring boost to intersection nodes.
- ✅ The `routeQuery()` orchestrator (lines 711–713) correctly dispatches to `hybridSearch()` when the classification strategy is `"hybrid"`.
- ✅ Both the `/search` (line 27 in search.ts) and `/mcp/query` (line 221 in mcp.ts) endpoints invoke `routeQuery()`, so hybrid search is accessible from all entry points.
- ⚠️ **Design gap — limited graph seed selection**: The hybrid search only uses the top-3 L2 names from vector results to seed graph traversal (line 575: `.slice(0, 3)`). If the vector search returns fewer than 3 L2 nodes (or none), the graph portion will be sparse. This is a reasonable heuristic but is not documented in the design spec. The design says "intersection of graph constraints and vector similarities" which implies a broader intersection, but the implementation is constrained by the top-3 heuristic.
- ⚠️ **No temporal decay on graph results**: Vector search results have temporal decay applied (via `calculateTemporalDecay` in `vectorSearchHandler`, lines 218–220 and 272–274), but graph traversal results use fixed scores (1.0 for seed node, 0.8 for dependencies, 0.9 for L3 decisions). When merging, graph-only results are not decay-adjusted, which means old graph nodes can outrank newer, verified vector nodes.

## Round 2 — Code Quality & Security Review

**Code Quality:**

- ✅ The `hybridSearch()` function is clean, readable, and follows the project's defensive design patterns.
- ✅ The merge logic uses a `Map<string, AgenticSearchResult>` with a composite key (`nodeLayer:id`) to efficiently deduplicate and boost intersection nodes (lines 585–601).
- ✅ The scoring boost formula `existing.score += r.score + 0.5` (line 597) provides a meaningful advantage to nodes found by both strategies, consistent with the "compounding score boost" design.
- ✅ No SQL injection risks — `hybridSearch()` delegates to `vectorSearchHandler` and `graphTraversalHandler`, both of which use parameterized Drizzle ORM queries with `sanitizeLikeInput()` for LIKE patterns.

**Issues Found:**

- ⚠️ **`hybridSearch` is not exported**: It is a module-private function (`async function hybridSearch(...)`, not `export async function`). This means it cannot be directly unit-tested from `intent-router.unit.test.ts`. Only the public `routeQuery()` function can be tested end-to-end. This is a minor testability concern.
- ⚠️ **Inconsistent score ranges**: Vector search scores are in the range [0, 1] (cosine similarity × decay factor). Graph traversal scores are fixed at 1.0 (seed node), 0.8 (dependencies), or 0.9 (L3 decisions). The boost adds `r.score + 0.5` which means intersection nodes can reach scores up to ~2.3. This works for re-ranking but the score ranges are not normalized, making the `score` field in `AgenticSearchResult` difficult to interpret for API consumers.
- ⚠️ **No input validation in `hybridSearch`**: Unlike the route handlers, `hybridSearch` does not validate its inputs (e.g., checking that `query` is non-empty). It relies on the caller (`routeQuery`) to have already validated. This is acceptable given the private visibility but could be fragile if the function is ever refactored to be public.

## Round 3 — Integration & Completeness Review

**Integration:**

- ✅ The hybrid search is correctly integrated into the `routeQuery` switch statement (lines 711–713).
- ✅ Both `/search` (search.ts) and `/mcp/query` (mcp.ts) endpoints call `routeQuery()`, which handles all 4 strategies including hybrid.
- ✅ The `include_pending` parameter flows correctly from the MCP endpoint through `routeQuery` to `hybridSearch` to both `vectorSearchHandler` and `graphTraversalHandler`.
- ✅ The `vectorSearchHandler` has a graceful fallback: if `generateEmbedding()` returns null (e.g., OpenAI API failure), it falls back to SQL LIKE search (lines 293–381). This means the hybrid search degrades gracefully even without embeddings.

**Completeness:**

- ❌ **No dedicated tests for hybrid search**: The unit test file (`intent-router.unit.test.ts`) only tests `escapeLike`, `calculateTemporalDecay`, and `sanitizeQuery`. There are no tests for `hybridSearch`, `vectorSearchHandler`, `graphTraversalHandler`, or `directLookupHandler`. The ADR-007 specifies:

  > **Fast-Path Assertion:** Integration tests MUST seed the database using factories, trigger an exact-match query, and use MSW to strictly assert that 0 external HTTP requests are made to the AI server.
  > **Fallback Assertion:** Queries below the similarity threshold MUST assert that exactly 1 request is intercepted by MSW.

  These integration tests are not present.

- ⚠️ **No integration test for the hybrid merge logic**: The scoring boost behavior (intersection nodes getting `+ r.score + 0.5`) is untested. An integration test with seeded data should verify that nodes appearing in both vector and graph results receive higher scores than nodes appearing in only one set.
- ⚠️ **Performance concern**: The hybrid search makes 1 vector search call + up to 3 graph traversal calls. Each graph traversal makes 3–4 DB queries (find node, fetch out-links, fetch related L2s, fetch L3s). In the worst case, this is ~15 DB queries per hybrid search. For the expected scale (≤100K nodes), this is acceptable, but no query optimization (e.g., batching, indexing) has been verified.

| 5   | ℹ️ Info   | Top-3 L2 seed heuristic for graph traversal is not documented in the design spec but is a reasonable implementation choice.                   |
| 6   | ℹ️ Info   | Performance: up to ~15 DB queries per hybrid search in the worst case. Acceptable for current scale.                                          |

## Recommendations

1. **Add integration tests** for the hybrid search path that verify: (a) the merge produces results from both vector and graph sources, (b) intersection nodes receive a scoring boost, (c) temporal decay is applied consistently.
2. **Apply temporal decay** to graph traversal results before merging, or at minimum document the intentional asymmetry.
3. **Consider normalizing scores** to [0, 1] in the final merged output so API consumers can interpret confidence.
4. **Document the top-3 heuristic** in ADR-007 or as a code comment, explaining why 3 was chosen and what happens when fewer than 3 L2 nodes are returned.

---

## Overall Verdict

**⚠️ WARN**

The hybrid search implementation is functionally correct and matches the design spec's core requirement (vector + graph merge with scoring boost). The code is clean and well-integrated into the routing pipeline. However, the absence of any tests for the hybrid path (despite ADR-007 mandating them), the missing temporal decay on graph results, and the unnormalized score ranges warrant a WARN verdict. The feature works but needs test coverage and minor consistency fixes.
