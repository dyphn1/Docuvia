## Round 1 — Architecture & Design Review

### What the Design Specifies

ADR-001 ("VS Code Client Onboarding & Scope Discovery") defines the `/init` flow as:

1. **Deterministic Recon (Local)**: Reads `.gitignore` to filter hidden directories.
2. **Feature Sniffing**: Looks for ecosystem markers. "Does not transmit massive trees; uses shallow sampling" (ADR-001, line 41).
3. The detected ecosystem markers feed into a proposed "structured payload (low token)" sent to an LLM for L1 tag suggestions.

The `init-project.md` design doc specifies that `initProject` should:

- Create the `.docuvia/` directory.
- Generate skeleton files `l1_tags.yaml`, `l2_modules.yaml`, `l3_router.yaml` (with `project_name` key in `l1_tags.yaml`).

### What the Implementation Does

The `initProject` function in `extension.ts:444-516`:

1. Resolves workspace root (single folder, multi-folder QuickPick, or tree-node context).
2. Validates path traversal (lines 471-475).
3. Shows an overwrite confirmation dialog if `.docuvia/` already exists.
4. Writes `manifest.yaml` with project name, version, and detected ecosystems (line 493-498).
5. Writes `config.yaml` with hardcoded `similarity_threshold: 0.85` and `chunk_size: 1000`.
6. Writes `.snapshot-ref` with `"docuvia-knowledge\n"`.
7. Triggers `docuvia.refreshKnowledgeGraph` command.

The `detectEcosystem` function (lines 427-442) performs O(1) file-existence checks:

- `package.json` → `typescript/javascript`
- `pyproject.toml` or `requirements.txt` → `python`
- `go.mod` → `golang`
- `Cargo.toml` → `rust`
- `pom.xml` or `build.gradle` → `java`
- None found → `unknown`

### Gaps Identified

**Gap 1 — Ecosystem data is written to manifest.yaml but silently stripped on read.**

The `initProject` function writes `{ name, version, ecosystems }` to `manifest.yaml` (line 493-498). However, the `ManifestSchema` in `types.ts:116-119` only defines `project_id` (optional number) and `modules` (array of `{ name, path_patterns }`). The `ecosystems` field is not part of the schema. When `KnowledgeStore._loadWorkspace` calls `parseManifest` (line 134), the Zod parser silently drops unknown fields (via passthrough behavior) or returns a default object — the ecosystem data is permanently lost from the in-memory snapshot.

**Severity**: Medium — The ecosystem detection runs and writes correctly, but the result is never available at runtime, making it dead data.

**Gap 2 — Skeleton YAML files (l1_tags.yaml, l2_modules.yaml, l3_router.yaml) are NOT generated during init.**

The `init-project.md` design explicitly requires generating `l1_tags.yaml` (with `project_name` key), `l2_modules.yaml`, and `l3_router.yaml` as skeleton files. The current `initProject` function does NOT create any of these files. It only writes `manifest.yaml`, `config.yaml`, and `.snapshot-ref`. The `writeIfAbsent` helper (line 520-527) exists but is only called in the `acceptL1Tags` command path (line 310-317), never during `initProject`.

**Severity**: High — Without l1_tags.yaml, l2_modules.yaml, and l3_router.yaml, the Knowledge Graph TreeView has no data to display after init. A user who runs `docuvia.initProject` sees an initialized project but no L1/L2/L3 nodes in the tree.

**Gap 3 — .gitignore is not read during init.**

ADR-001 specifies "Reads .gitignore to filter hidden directories" as part of "Deterministic Recon." The `detectEcosystem` function does not read `.gitignore` at all.

**Severity**: Low — The ecosystem detection is shallow (just file existence), so `.gitignore` filtering is less critical for this specific function. However, it represents incomplete implementation of the design spec.

**Gap 4 — package.json content is not parsed; only existence is checked.**

The checklist item specifically says "Package.json ecosystem marker parsing." The current code only checks if `package.json` exists (line 433) and tags the project as `typescript/javascript`. It does not parse `package.json` for:

- `dependencies` / `devDependencies` (library/framework detection)
- `engines` field
- `type` field (`module` vs `commonjs`)

However, ADR-001's guidance ("shallow sampling," "does not transmit massive trees") suggests this may be intentional in v1. The function does cover 7 ecosystem marker files for 5 languages.

**Severity**: Low (by design, for v1).

## Round 2 — Code Quality & Security Review

### Issue 1 — Flawed path traversal check (extension.ts:471-475)

```typescript
const relativeToWorkspace = path.relative(folders.map(f => f.uri.fsPath).join(','), targetRoot);
if (relativeToWorkspace.startsWith('..')) {
```

`path.relative()` expects a single path as its second argument, but the code joins all folder paths with a comma. For example, with two workspace folders `/a` and `/b`, it computes `path.relative('/a,/b', targetRoot)`, which is meaningless. The check would only pass for `targetRoot` values that happen to be lexically "after" the comma-joined string. A correct approach would check `targetRoot` against each individual workspace folder.

**Severity**: Medium — In practice, the check rarely triggers because `targetRoot` is always set from a workspace folder URI. But the logic is incorrect and could either block valid paths or allow invalid ones in edge cases.

### Issue 2 — Inline `require()` calls inconsistent with project patterns

The `detectEcosystem` and `initProject` functions use `require('fs/promises')` and `require('path')` inline (lines 429, 430, 479, 492), while the rest of the codebase uses top-level ES module `import` statements. This is a code style inconsistency.

**Severity**: Low — Functional but inconsistent with the project's coding standards.

### Issue 3 — Inconsistent use of `vscode.workspace.fs` vs Node `fs`

`fileExists` (line 417-425) uses `require('fs/promises').stat()` while `writeIfAbsent` (line 520-527) uses `vscode.workspace.fs.stat()`. The `fileExists` helper is only called from `detectEcosystem`, which itself uses `fs/path` requires. Mixing filesystem APIs can cause subtle issues (e.g., `vscode.workspace.fs` handles virtual file systems; Node's `fs` does not).

**Severity**: Low — Works in practice for local files but architecturally inconsistent.

### Issue 4 — Hardcoded config.yaml values unused

The `config.yaml` written at lines 500-504 contains `similarity_threshold: 0.85` and `chunk_size: 1000`. These values are not referenced anywhere in the codebase — no code reads `config.yaml` during runtime. The `KnowledgeStore._loadWorkspace` only reads `manifest.yaml`, `l1_tags.yaml`, `l2_modules.yaml`, `l3_router.yaml`, and `l3_decisions/*.md`.

**Severity**: Low — Dead configuration, no runtime impact.

### Issue 5 — Commented-out snapshot initialization (line 509)

```typescript
// await store.initializeSnapshot(targetRoot);
```

The snapshot system appears incomplete. The `.snapshot-ref` file is written, but the actual initialization is commented out.

**Severity**: Medium — Incomplete feature: the orphan branch snapshot system is designed but not activated.

### Positive Observations

- The overwrite confirmation dialog (lines 482-486) is well-implemented, matching the design spec.
- Error handling with try/catch is present throughout.
- The `detectEcosystem` function correctly handles the case where no markers are found by returning `["unknown"]`.
- Debounced FileSystemWatcher in `KnowledgeStore` is well-structured.

## Round 3 — Integration & Completeness Review

### Integration Issues

**Issue 1 — Ecosystem data has no consumer.**

The ecosystem tags written to `manifest.yaml` are:

1. Written by `initProject` (line 496).
2. Silently stripped by `parseManifest` due to `ManifestSchema` not including the field.
3. Never displayed in any UI component (`KnowledgeGraphTreeProvider`, `DashboardPanel`, `SearchResultsPanel`).
4. Never sent to the central server.

The ecosystem detection is functionally dead code — it runs but the result is never used.

**Issue 2 — No tests for detectEcosystem or initProject.**

The test files (`src/tests/phase1.test.ts`, `tests/phase1-3.spec.ts`) don't appear to cover `detectEcosystem` or the `initProject` command flow. The `fileExists` function uses Node's `fs/promises` directly, making it difficult to test with VS Code's test infrastructure.

**Issue 3 — initProject does not call store.load() or produce KnowledgeStore data.**

After `initProject` writes `manifest.yaml`, `config.yaml`, and `.snapshot-ref`, it triggers `docuvia.refreshKnowledgeGraph` (line 509), which calls `store.load()`. But since `l1_tags.yaml`, `l2_modules.yaml`, and `l3_router.yaml` were never created, the store loads with zero tags, modules, and L3 entries. The Knowledge Graph tree will show an empty project node with a "No L1 tags found in l1_tags.yaml" placeholder.

**Issue 4 — Snapshot system incomplete.**

The `.snapshot-ref` file is written but the actual snapshot initialization (`store.initializeSnapshot`) is commented out. The `git cat-file --batch` fallback in `KnowledgeStore._loadFromGit` expects snapshot data from the orphan branch, but the snapshot is never created. This means the git fallback path will always fail for newly initialized projects.

### Positive Observations

- The `parseTags` function in `parser.ts:18-34` correctly handles both array format and `{ project_name, tags: [...] }` object format (lines 21-25), fixing the bug documented in earlier design docs.
- The multi-root workspace QuickPick flow (lines 458-466) is well-implemented.
- The inline `acceptL1Tags` command path properly uses `writeIfAbsent` for skeleton file creation (lines 310-317).

## Recommendations

1. **Add `.gitignore` filtering** to `detectEcosystem` to match ADR-001.
2. **Generate skeleton YAML files** (`l1_tags.yaml`, `l2_modules.yaml`, `l3_router.yaml`) during `initProject` using `writeIfAbsent`.
3. **Add `ecosystems` field** to `ManifestSchema` and display ecosystem info in the tree view or dashboard.
4. **Fix path traversal check** to validate against each workspace folder individually.
5. **Unify filesystem API usage** — prefer `vscode.workspace.fs` throughout.
6. **Add unit tests** for `detectEcosystem` covering all marker file combinations.
7. **Either implement or remove** `config.yaml` — dead configuration is confusing.

---

## Overall Verdict

**⚠️ WARN**

The ecosystem marker detection (`detectEcosystem`) is implemented and functional for the core use case — checking for the existence of 7 ecosystem marker files across 5 programming languages. However, the ecosystem data is silently lost during manifest parsing because the `ManifestSchema` doesn't include the field. More critically, the `initProject` flow does not generate the required skeleton YAML files (`l1_tags.yaml`, `l2_modules.yaml`, `l3_router.yaml`), leaving the Knowledge Graph empty after initialization. The path traversal check has a logic bug (comma-joined paths), and there are no tests for this feature. The item is partially implemented but has significant gaps.
