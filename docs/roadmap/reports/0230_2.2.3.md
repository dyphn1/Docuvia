## Round 1 — Architecture & Design Review

### What the Design Specifies

The design (ADR-001) describes the "Zero to One" onboarding flow:
1. VS Code TreeView detects absence of `.docuvia/` and provides an `[Initialize Docuvia Knowledge Base]` button.
2. On trigger (`docuvia.initProject`), the extension performs deterministic recon (reads `.gitignore`, `package.json`, ecosystem markers).
3. User confirms/modifies tags.
4. System writes `l1_tags.yaml` and generates `_project_profile.yaml` (Cognitive Snapshot).

### What the Implementation Does

The `initProject()` function in `extension.ts` (lines 444–515):
1. Determines target workspace root (single folder, QuickPick for multi-folder, or from tree node).
2. Validates path traversal.
3. Checks for existing `.docuvia/` — prompts for overwrite confirmation.
4. Creates `.docuvia/` directory via `fs.mkdir(docuviaDir, { recursive: true })`.
5. Writes `manifest.yaml` with `{ name, version, ecosystems }`.
6. Writes `config.yaml` with `{ similarity_threshold: 0.85, chunk_size: 1000 }`.
7. Writes `.snapshot-ref` with `"docuvia-knowledge\n"`.
8. Calls `docuvia.refreshKnowledgeGraph` to load the newly initialized state.

### Assessment

✅ **Three required files are created:** `manifest.yaml`, `config.yaml`, and `.snapshot-ref` — all present.

✅ **Overwrite protection:** The existing `.docuvia/` check and user prompt work correctly.

⚠️ **ADR-001 mentions `_project_profile.yaml`** (a "Cognitive Snapshot" capturing topology snapshot), but the implementation does NOT create this file. The `initProject` function creates `manifest.yaml` with `name/version/ecosystems` instead. This is a minor gap between ADR-001 description and implementation. The `_project_profile.yaml` concept from the ADR does not have a corresponding type definition or parser in the codebase.

✅ **ADR-003 orphan branch alignment:** The `.snapshot-ref` content `"docuvia-knowledge"` matches the `GIT_KNOWLEDGE_BRANCH` constant in `KnowledgeStore.ts` (line 12), ensuring consistency with the git-isomorphic sync protocol.

✅ **KnowledgeStore loader compatibility:** `KnowledgeStore._loadWorkspace()` (line 122) reads `manifest.yaml` first via `parseManifest()`, then falls back to reading `l1_tags.yaml`, `l2_modules.yaml`, and `l3_router.yaml`. The files written by `initProject` are sufficient for the loader to detect the `.docuvia/` directory exists and parse the manifest (though with empty `modules` since `initProject` doesn't create path patterns yet).

## Round 2 — Code Quality & Security Review

### Issues Found

**1. Dynamic `require()` calls inside an ESM module (Code Smell)**
- **File:** `extension.ts`, lines 479, 492
- The file uses ES module imports (`import * as path from 'path'`) at the top, but `initProject()` uses `require('fs/promises')` and `require('js-yaml')` inside the function body. This is inconsistent and can cause issues with bundlers and the VS Code extension host. Native `vscode.workspace.fs` is used for most operations, but Node `fs/promises` is used for `stat`/`mkdir`/`writeFile` in `initProject`. The `js-yaml` usage could be replaced with a static import.
- **Severity:** Low (works at runtime, but inconsistent with module system).

**2. Weak path traversal validation**
- **File:** `extension.ts`, lines 471–475
- The traversal check uses `path.relative(workspaceFolders.map(f => f.uri.fsPath).join(','), targetRoot)`, which joins all folder paths with commas into a single string. This is not a valid filesystem path — especially for multi-folder workspaces — and `path.relative()` behavior with such input is undefined. For a single-folder workspace it coincidentally works because the join produces just that path.
- **Recommendation:** Validate `targetRoot` against each individual workspace folder path instead.
- **Severity:** Medium (unlikely to be exploitable in practice since VS Code constrains the input, but semantically incorrect).

**3. Overwrite does not clean existing directory**
- **File:** `extension.ts`, lines 481–489
- When an existing `.docuvia/` directory is detected and the user confirms overwrite, only new files are written on top. Stale files from a previous initialization (e.g., an old `l1_tags.yaml` with different content) would remain. The directory is never deleted.
- **Recommendation:** Delete and recreate the directory on overwrite, or explicitly write/overwrite all expected files.
- **Severity:** Low (in practice, the fresh writes would overwrite same-named files, but orphaned files accumulate).

**4. `manifest.yaml` fields don't match `ManifestSchema`**
- **File:** `extension.ts` lines 493–497 vs `types.ts` lines 116–119
- `initProject` writes `{ name, version, ecosystems }` to `manifest.yaml`, but `ManifestSchema` only defines `project_id` (optional number) and `modules` (array of `{ name, path_patterns }`). The `name` and `ecosystems` fields are not in the schema. While YAML parsers are lenient about extra fields, the semantic mismatch suggests the schema and the writer are out of sync.
- **Severity:** Medium (the manifest produced by init cannot properly populate `manifestModules` in `KnowledgeGraphTreeProvider`, which relies on `modules` for CodeLens matching).

**5. Test does not verify the target files**
- **File:** `phase1.test.ts`, lines 54–57
- The test asserts existence of `l1_tags.yaml`, `l2_modules.yaml`, and `l3_router.yaml` but does NOT assert existence of `manifest.yaml`, `config.yaml`, or `.snapshot-ref`. This means item 2.2.3's specific deliverables are not covered by the test. The test was likely written for a different acceptance criterion.
- **Severity:** Medium (test coverage gap for the specific item).

**6. Test stub mismatch for overwrite flow**
- **File:** `phase1.test.ts`, line 14
- The `showWarningMessage` stub resolves `'Overwrite'` but the actual code checks `overwrite !== "Yes"` (line 486). The test's overwrite path would not behave correctly — the stub value `'Overwrite' !== 'Yes'`, so early in the flow (before initProject is called) the directory doesn't exist yet, and this stub isn't hit during the create path. But if the test were run against an already-initialized workspace, the overwrite check would silently skip.
- **Severity:** Low (test runs clean directory case, so it passes).

### Positive Findings

✅ **Singleton pattern:** `KnowledgeStore.getInstance()` ensures single instance across the extension.  
✅ **Graceful error handling:** Try/catch around the entire init flow with user-facing error messages (line 513).  
✅ **`writeIfAbsent` helper:** Used in `acceptL1Tags` (lines 310–317) to create skeleton files without overwriting — good defensive design.  
✅ **`vscode.workspace.fs` usage:** Primary file operations use the VS Code API (in `acceptL1Tags`), which is correct for extension sandboxing.

## Round 3 — Integration & Completeness Review

### Integration Assessment

**KnowledgeGraphTreeProvider detection**
- The tree provider correctly detects uninitialized workspaces at `KnowledgeGraphTreeProvider.ts` line 169: `this.store.snapshots.has(folder.uri.fsPath)`. After `initProject` runs and `refreshKnowledgeGraph` is called, `KnowledgeStore.load()` reads the `.docuvia/` directory and populates the snapshot. The tree view then shows the project as initialized. ✅

**acceptL1Tags secondary creation path**
- The `acceptL1Tags` command (lines 296–301) creates `.docuvia/` and `l3_decisions/` directories, then writes `l1_tags.yaml`, `l2_modules.yaml` (skeleton), and `l3_router.yaml` (skeleton). This is a separate code path from `initProject` and does NOT write `manifest.yaml`, `config.yaml`, or `.snapshot-ref`. If a user triggers `/explore` before `init initProject`, the workspace ends up with tag files but no manifest or snapshot-ref. The `KnowledgeStore` loader would find the directory but the manifest would parse as empty defaults. ⚠️

**KnowledgeStore.post-init reload flow**
- After `initProject` writes files, it calls `docuvia.refreshKnowledgeGraph` (line 510), which triggers `store.load()`. The loader reads `manifest.yaml` (gets empty modules), then reads `l1_tags.yaml` (doesn't exist yet — only created by `acceptL1Tags` or writing YAML in `initProject` — actually, looking more carefully, `initProject` does NOT write `l1_tags.yaml`). This means after `initProject`, the tree view would show the project as initialized but with "No L1 tags found in l1_tags.yaml" placeholder. The `l1_tags.yaml` is only written when the user runs `/explore` and confirms via `acceptL1Tags`. ✅ (This is by design — init creates the scaffolding, explore creates the tags.)

**Config consumption chain**
- `config.yaml` is written with `similarity_threshold: 0.85` and `chunk_size: 1000`, but no code in the VS Code extension reads these values from the project-level `config.yaml`. The `GlobalConfigSchema` defines `server_url` and `chunking_strategy`, not `similarity_threshold` or `chunk_size`. The written `config.yaml` fields don't match the schema for `GlobalConfig`. ❌

**Snapshot-ref usage chain**
- The `.snapshot-ref` file content (`docuvia-knowledge`) aligns with `GIT_KNOWLEDGE_BRANCH` in `KnowledgeStore.ts`. However, `_loadFromGit()` uses `GIT_KNOWLEDGE_BRANCH` directly as a constant, never reading `.snapshot-ref`. The `.snapshot-ref` file appears to be informational/developer-facing rather than consumed by code. ⚠️

## Overall Verdict

## ⚠️ WARN

The three required files (`manifest.yaml`, `config.yaml`, `.snapshot-ref`) are created by `initProject()` and the directory scaffolding works end-to-end. However, there are significant schema mismatches: the fields written to `manifest.yaml` and `config.yaml` don't align with the TypeScript `Zod` schemas defined in `types.ts`, and no code consumes the project-level `config.yaml`. The test coverage doesn't verify the specific deliverables of this item. The core functionality works, but the data contracts are inconsistent.
