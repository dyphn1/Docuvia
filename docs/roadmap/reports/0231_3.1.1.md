## Round 1 — Architecture & Design Review

### What the Design Specifies

ADR-006 describes a 4-stage swarm intelligence pipeline:

1. **Capture**: Human corrections via `POST /review_tasks` → stored in `correction_examples` table
2. **Distill**: Background job reads `processedAt IS NULL` rows, uses LLM to compress into architectural guardrails, inserts into `prompt_templates`, updates `processedAt`
3. **Inject**: Few-shot examples injected into the generate pipeline
4. **Evolve**: O(1) fast-path filters identify common patterns without LLM latency

### Implementation Status

| Stage | Status | Location |
|-------|--------|----------|
| Capture (L2 nodes) | ✅ Implemented | `review_tasks.ts:125-146` — inserts `correction_examples` on L2 review approval with `correctedValue` |
| Capture (L3 nodes) | ✅ Implemented | `review_tasks.ts:147-172` — inserts `correction_examples` on L3 review approval with `correctedValue` |
| Capture (L1 tags) | ❌ Missing | `review_tasks.ts:173-180` — updates tag description but does **NOT** create a `correction_examples` record |
| Distillation | ✅ Implemented | `metabolism.ts:89-145` — fetches up to 10 `processedAt IS NULL` rows, calls LLM, inserts guardrails into `prompt_templates`, sets `processedAt` |
| Few-shot injection | ⚠️ Partial | `generate.ts:88-117` — `getRecentCorrections()` and `buildFewShotSection()` exist, but only called for `l2_node` type (line 740). L3 corrections are never injected. |
| O(1) fast-path | ❌ Not implemented | No regex pre-filter or keyword mapping for guardrails from `prompt_templates` |

### Gaps Identified

1. **L1 tag corrections not captured**: When a user corrects an L1 tag via the review system (`review_tasks.ts:173-180`), the code updates `l1TagsTable.description` but does NOT insert a row into `correction_examples`. This breaks the feedback loop for L1 tags entirely — corrections are lost and never distilled into guardrails.

2. **L3 corrections not used for few-shot**: The `getRecentCorrections()` function accepts `"l2_node" | "l3_node"` as the `entityType` parameter, but it is only ever called with `"l2_node"` at `generate.ts:740`. L3 corrections stored in the database are never fetched or injected as few-shot examples. The `buildFewShotSection()` function is only called in `generateL2Nodes()` (line 245), never in the L3 generation path.

3. **Distillation processes corrections individually**: ADR-006 states the server should "detect patterns (e.g., multiple developers replacing `console.log` with `pino`) across the `correction_examples` table." The current implementation in `metabolism.ts:102-133` processes each correction independently with a separate LLM call, rather than batching them to detect cross-correction patterns. This is both less effective at pattern detection and more expensive (N LLM calls instead of 1 per batch).

## Round 2 — Code Quality & Security Review

### Code Quality Issues

1. **Missing `CorrectionExampleFactory`**: `factories.ts:5` imports `correctionExamplesTable` and `factories.ts:10` imports `InsertCorrectionExample` type, but no `CorrectionExampleFactory` is defined. The import on line 5 is unused (no factory object uses `correctionExamplesTable`). If any test tries to import `CorrectionExampleFactory`, it will get `undefined` at runtime. This blocks test coverage for the entire correction feedback loop.

2. **No input validation on `correctedValue`**: In `review_tasks.ts:124`, the code checks `if (body.correctedValue && task.status === "approved")` but does not validate the length or content of `correctedValue` before inserting into `correction_examples`. While the Zod schema for the review resolution endpoint may provide some validation, the `correctedValue` field in `ResolveReviewTaskBody` should have explicit max-length constraints to prevent abuse.

3. **Inconsistent null handling for L3 `projectId`**: In `review_tasks.ts:159`, when creating a correction example for an L3 node, the code uses `projectId: l2?.projectId ?? null`. If the L2 node is not found, `projectId` becomes `null`. This means the correction example won't be associated with any project, and `getRecentCorrections()` (which filters by `projectId`) will never retrieve it. This silently breaks the feedback loop for L3 corrections.

4. **No error handling for correction insertion**: The `db.insert(correctionExamplesTable)` calls at `review_tasks.ts:131` and `review_tasks.ts:158` are `await`ed but not wrapped in try/catch. If the insert fails (e.g., constraint violation), the error will propagate and potentially crash the request, even though the review task itself was already updated successfully. The correction example insertion is a side-effect that should be non-critical.

5. **Distillation job uses hardcoded model**: `metabolism.ts:105` uses `model: "gpt-4o-mini"` hardcoded, rather than respecting the project's LLM configuration. This means the distillation always uses the same model regardless of project settings.

### Security Review

- No significant security vulnerabilities found in the correction_examples flow.
- The `correctedValue` field is user-controlled but stored as `text` in the database and used only in LLM prompts (not executed as code). Prompt injection via corrected content is a theoretical concern but within acceptable bounds for this application.
- The `/admin/metabolism-tick` endpoint in `metabolism.ts:168-207` properly authenticates via `ADMIN_SECRET_TOKEN` and fails closed in production.

## Round 3 — Integration & Completeness Review

### Integration Points

1. **Review → Correction Examples**: ✅ Works for L2 and L3 nodes. ❌ Broken for L1 tags.
2. **Correction Examples → Few-shot**: ⚠️ Works for L2 corrections only. L3 corrections are stored but never retrieved for few-shot.
3. **Correction Examples → Distillation**: ✅ The metabolism job correctly queries `processedAt IS NULL` rows and processes them.
4. **Distillation → Prompt Templates**: ✅ Guardrails are inserted into `prompt_templates` table.
5. **Prompt Templates → Generate**: ✅ The `getPromptTemplate()` function in `generate.ts:30-69` fetches project-specific templates with fallback to global defaults and hardcoded defaults.

### Test Coverage

- **No tests exist** for the correction_examples creation flow (review resolution → correction_examples insertion).
- **No tests exist** for the `getRecentCorrections()` or `buildFewShotSection()` functions.
- **No tests exist** for the distillation job in `metabolism.ts`.
- **No tests exist** for the few-shot injection in the generate pipeline.
- The only existing test (`generate.test.ts`) tests the basic generate flow without any correction examples in the database.
- The missing `CorrectionExampleFactory` in `factories.ts` makes it impossible to write these tests without first fixing the factory.

### Performance Considerations

- The distillation job processes corrections one-by-one with individual LLM calls (`metabolism.ts:102-133`). For 10 corrections, this means 10 sequential LLM calls. Batching would be more efficient and cost-effective.
- The `getRecentCorrections()` function orders by `createdAt desc` with `limit 5` but has no index on `(projectId, entityType, createdAt)`. This could be slow with large numbers of correction examples.

### End-to-End Usability

The feature is partially usable:
- A developer can approve a review task with a correction, and it will be stored in `correction_examples`.
- The metabolism job will eventually distill it into a prompt template.
- The generate pipeline will use L2 corrections as few-shot examples.
- However, L1 tag corrections are lost, and L3 corrections are stored but never used for few-shot — reducing the effectiveness of the feedback loop.

## Recommendations

1. **Fix L1 tag correction capture**: Add `correction_examples` insertion in `review_tasks.ts:173-180` for L1 tags (similar to the L2/L3 paths).
2. **Use L3 corrections for few-shot**: Call `getRecentCorrections(projectId, "l3_node")` in the L3 generation path and pass them to the LLM prompt.
3. **Define `CorrectionExampleFactory`**: Add the missing factory in `factories.ts` to enable test coverage.
4. **Add error handling**: Wrap `correction_examples` insertion in try/catch to prevent insertion failures from crashing the review resolution.
5. **Batch distillation**: Process corrections in a single LLM call to detect patterns across corrections, as the design spec intends.
6. **Add database index**: Add an index on `correction_examples(projectId, entityType, createdAt)` for query performance.

---

## Overall Verdict

**⚠️ WARN**

The core correction_examples summary logic is implemented and functional for the L2 node path. The review → capture → distillation → prompt template pipeline works end-to-end for L2 corrections. However, there are significant gaps: L1 tag corrections are not captured at all, L3 corrections are stored but never used for few-shot, the `CorrectionExampleFactory` is missing (blocking tests), and the distillation job doesn't batch corrections for pattern detection as the design specifies. The feature is partially implemented with actionable gaps to address.
