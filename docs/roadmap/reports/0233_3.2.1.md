## Round 1 — Architecture & Design Review

**Design Spec (ADR-007, Section 3) says:**
> Knowledge nodes contain `created_at` and `lastVerifiedAt`.
> The router applies an Exponential Temporal Decay function to search scores (`Math.exp(-LAMBDA * daysSinceVerified)` in `intent-router.ts`). Knowledge untouched naturally sinks to the bottom.
> When old knowledge correctly answers a query, its `lastVerifiedAt` is updated via the `POST /search/feedback` endpoint (passing the `nodeLayer`), "refreshing" its lifespan.

**Implementation Review:**

1. **`calculateTemporalDecay()` function** (`intent-router.ts:121–127`):
   ```typescript
   export function calculateTemporalDecay(referenceDate: Date, now: number = Date.now()): number {
     const MS_PER_DAY = 1000 * 60 * 60 * 24;
     const HALF_LIFE_DAYS = 30;
     const LAMBDA = Math.LN2 / HALF_LIFE_DAYS;
     const daysSinceVerified = (now - referenceDate.getTime()) / MS_PER_DAY;
     return Math.exp(-LAMBDA * Math.max(0, daysSinceVerified));
   }
   ```
   - ✅ Correctly implements exponential decay with 30-day half-life.
   - ✅ Uses `Math.LN2 / HALF_LIFE_DAYS` for lambda — mathematically correct: after 30 days, `exp(-ln(2)/30 * 30) = exp(-ln(2)) = 0.5`.
   - ✅ Guards against future dates with `Math.max(0, daysSinceVerified)` — future-dated nodes get a decay factor of 1.0 (no penalty).
   - ✅ Pure function — no side effects, deterministic output for given inputs.
   - ✅ The `now` parameter defaults to `Date.now()` but is injectable, enabling reliable unit testing.

2. **Schema — `lastVerifiedAt` column presence:**
   - ✅ `l2_nodes.ts:21`: `lastVerifiedAt: timestamp("last_verified_at").defaultNow()` — exists, defaults to insertion time.
   - ✅ `l3_nodes.ts:33`: `lastVerifiedAt: timestamp("last_verified_at").defaultNow()` — exists, defaults to insertion time.
   - ✅ Both columns are nullable timestamps (no `.notNull()`), so they can be `null` for nodes that have never been explicitly verified.

3. **Application in vector search** (`intent-router.ts`):
   - ✅ L2 nodes (lines 218–220):
     ```typescript
     const referenceDate = node.lastVerifiedAt ?? node.createdAt;
     const decayFactor = calculateTemporalDecay(referenceDate);
     const score = rawScore * decayFactor;
     ```
   - ✅ L3 nodes (lines 271–273): Identical pattern — falls back to `createdAt` when `lastVerifiedAt` is null.
   - ✅ The decay factor (range 0.0–1.0) multiplies the raw cosine similarity, so older verified nodes get proportionally lower scores.
   - ✅ Fallback path correctness: when `lastVerifiedAt` is `null`, `createdAt` is used, meaning even without explicit verification, nodes still decay from their creation date.

4. **Integration with query pipeline:**
   - ✅ `routeQuery()` (line 614) dispatches to `vectorSearchHandler()` for `vector_search` and `hybrid` strategies.
   - ✅ Both `/search` (search.ts:27) and `/mcp/query` (mcp.ts:221) call `routeQuery()`.
   - ✅ The `includePending` parameter flows correctly through the entire pipeline.

5. **Feedback loop — refreshing `lastVerifiedAt`:**
   - ✅ `POST /search/feedback` (search.ts:34–56) updates `lastVerifiedAt` to `new Date()` for L2 (line 47) and L3 (line 49) nodes.
   - ✅ Uses Zod validation for the request body (`FeedbackSchema`).

**Findings:**
- ✅ The implementation matches the design spec precisely.
- ✅ The mathematical formula is correct and produces the expected half-life behavior.
- ✅ The null-safety fallback (`lastVerifiedAt ?? createdAt`) is a robust design choice.
- ⚠️ **Decay not applied in graph traversal or direct lookup**: `graphTraversalHandler()` (lines 391–475) and `directLookupHandler()` (lines 481–554) use fixed scores (1.0, 0.8, 0.9) without temporal decay. This is an intentional architectural asymmetry — graph/direct results are exact-match and not similarity-ranked, so decay is less meaningful there. However, it means the "knowledge naturally sinks" behavior from ADR-007 only applies to vector-ranked results.

## Round 2 — Code Quality & Security Review

**Code Quality:**
- ✅ `calculateTemporalDecay()` is a pure function — easy to test, no side effects, no external dependencies.
- ✅ Constants (`MS_PER_DAY`, `HALF_LIFE_DAYS`, `LAMBDA`) are clearly defined and named.
- ✅ The function is exported, enabling direct unit testing (and is tested).
- ✅ The formula `Math.exp(-LAMBDA * Math.max(0, daysSinceVerified))` is clean and idiomatic.
- ✅ `referenceDate` is resolved as `node.lastVerifiedAt ?? node.createdAt` — concise null-coalescing.
- ✅ The decay application (`rawScore * decayFactor`) is a simple multiplication — no unnecessary complexity.

**Unit Test Quality (`intent-router.unit.test.ts:19–43`):**
- ✅ Tests cover 4 boundary conditions:
  - `now` → 1.0 (no decay)
  - 30 days ago → 0.5 (half-life)
  - 60 days ago → 0.25 (two half-lives)
  - Future date → capped at 1.0
- ✅ Uses `toBeCloseTo()` for floating-point comparison — correct approach.
- ✅ Tests inject the `now` parameter for deterministic results.

**Security:**
- ✅ No SQL injection risks — all queries use parameterized Drizzle ORM.
- ✅ No injection risk in the decay function — pure math on dates.
- ⚠️ **Feedback endpoint lacks authentication**: `POST /search/feedback` (search.ts:34) does not require authentication. Any caller can refresh `lastVerifiedAt` for any node, potentially gaming search rankings. Severity: low (requires knowledge of node IDs, and the effect is bounded by the decay function).

**Issues Found:**
- ⚠️ **Low**: `POST /search/feedback` endpoint has no authentication. Consider adding auth middleware or rate-limiting.
- ℹ️ **Info**: The `interactionType` field in the feedback schema (`view`, `click`, `copy`, `citation`) is accepted but not used. All interaction types equally refresh `lastVerifiedAt`. Future work could weight different types.

## Round 3 — Integration & Completeness Review

**Integration:**
- ✅ Temporal decay math is correctly integrated into the vector search handler, which is the primary search strategy for the RAG pipeline.
- ✅ The `routeQuery()` orchestrator (lines 614–740) calls `vectorSearchHandler()` for `vector_search` and `hybrid` strategies — both apply decay.
- ✅ The hybrid search (item 1.3.5) inherits decay through `vectorSearchHandler()`.
- ✅ Both `/search` and `/mcp/query` endpoints invoke `routeQuery()`, ensuring decay is applied for all query entry points.
- ✅ The feedback loop (`POST /search/feedback`) correctly refreshes `lastVerifiedAt`, completing the decay lifecycle.

**Test Coverage:**
- ✅ **Unit tests**: Thorough coverage of `calculateTemporalDecay()` with 4 boundary-condition tests. This fully validates the mathematical correctness.
- ❌ **No integration tests for decay with DB**: No integration tests seed the database with nodes having different `lastVerifiedAt` values and verify that search result ordering respects decay. ADR-007 mentions integration tests with MSW for the RAG pipeline, but these are not present for the temporal decay specifically.
- ❌ **No test for the feedback endpoint**: `POST /search/feedback` has no test coverage.

**Mathematical Correctness Verification:**
- At `daysSinceVerified = 0`: `exp(-0) = 1.0` ✅
- At `daysSinceVerified = 30`: `exp(-ln(2)) = 0.5` ✅
- At `daysSinceVerified = 60`: `exp(-2*ln(2)) = 0.25` ✅
- At `daysSinceVerified = 90`: `exp(-3*ln(2)) = 0.125` ✅
- At `daysSinceVerified = -10` (future): `exp(-(-10)*LAMBDA)` would be > 1.0, but `Math.max(0, ...)` caps it to 0 → `exp(0) = 1.0` ✅

**Completeness:**
- ✅ The feature is complete per the design spec: the math is correct, the schema supports it, and the search applies it.
- ✅ The implementation handles edge cases: null `lastVerifiedAt`, future dates, and injectable `now` for testing.

## Recommendations

1. **Add integration tests** that seed nodes with different `lastVerifiedAt` values and verify search result ordering respects temporal decay.
2. **Add authentication** to `POST /search/feedback` to prevent arbitrary `lastVerifiedAt` refreshing.
3. **Consider documenting** the intentional asymmetry between vector search (decay-applied) and graph/direct lookup (fixed scores) in ADR-007 or a future ADR.

## Overall Verdict

**✅ PASS**

The `lastVerifiedAt` math in `intent-router.ts` is correctly implemented and matches the design spec. The `calculateTemporalDecay()` function is mathematically sound — it correctly implements exponential decay with a 30-day half-life, properly handles edge cases (null `lastVerifiedAt` falls back to `createdAt`, future dates are capped at 1.0), and is well-tested at the unit level with 4 boundary-condition tests. The function is pure, exported for testability, and correctly applied in the vector search pipeline. The identified issues (missing integration tests, unauthenticated feedback endpoint) are minor and do not prevent the mathematical logic from functioning as designed.
