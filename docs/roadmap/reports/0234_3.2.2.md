## Round 1 — Architecture & Design Review

**Design Spec (ADR-007, Section 3) says:**

> Knowledge nodes contain `created_at` and `lastVerifiedAt`.
> The router applies an Exponential Temporal Decay function to search scores (`Math.exp(-LAMBDA * daysSinceVerified)` in `intent-router.ts`). Knowledge untouched naturally sinks to the bottom.
> When old knowledge correctly answers a query, its `lastVerifiedAt` is updated via the `POST /search/feedback` endpoint (passing the `nodeLayer`), "refreshing" its lifespan.

**Item 3.2.2 specifically requires:** Decay must be applied to knowledge query results — i.e., the end-to-end flow from query entry points through to ranked results must incorporate temporal decay.

**Implementation Review — Path-by-path analysis:**

### Path A: Vector Search WITH embeddings (✅ Correct)

`vectorSearchHandler()` lines 214-224 (L2) and 268-278 (L3):

```typescript
const referenceDate = node.lastVerifiedAt ?? node.createdAt;
const decayFactor = calculateTemporalDecay(referenceDate);
const score = rawScore * decayFactor;
```

- ✅ Decay is correctly applied to cosine similarity scores.
- ✅ Null-safety fallback (`lastVerifiedAt ?? createdAt`) works correctly.

### Path B: Vector Search FALLBACK (SQL LIKE) (❌ Missing decay)

`vectorSearchHandler()` lines 293-381 — when `generateEmbedding()` returns null:

```typescript
// L2 fallback (line 336):
score: 0.9,
// L3 fallback (line 377):
score: 0.8,
```

- ❌ **No temporal decay applied.** Fixed scores are used regardless of node age.
- This means old unverified nodes rank equally with freshly verified ones when the embedding service is unavailable.

### Path C: Graph Traversal (❌ Missing decay)

`graphTraversalHandler()` lines 391-475:

```typescript
// Seed node (line 420):    score: 1.0
// Related L2 (line 446):   score: 0.8
// L3 decisions (line 469): score: 0.9
```

- ❌ **No temporal decay applied.** All scores are fixed constants.
- Graph traversal is the primary strategy for dependency/impact queries — these results are returned without any age-based ranking.

### Path D: Direct Lookup (❌ Missing decay)

`directLookupHandler()` lines 481-554:

```typescript
// Hash match (line 513):   score: 1.0
// ILIKE match (line 547):  score: 0.8
```

- ❌ **No temporal decay applied.** Exact-match and full-text results use fixed scores.

### Path E: Hybrid Search (⚠️ Partial decay)

`hybridSearch()` lines 560-608:

- ✅ Vector results inherit decay from `vectorSearchHandler()`.
- ❌ Graph results added during merge (lines 592-601) have **no decay** — they use fixed scores from `graphTraversalHandler()`.
- ❌ The merge scoring boost (`existing.score += r.score + 0.5` at line 597) can push non-decayed graph results above decayed vector results, producing counter-intuitive rankings where older nodes outrank newer ones.

### Path F: Single-word Fast-Circuit (❌ Missing decay)

`routeQuery()` lines 627-645:

```typescript
if (isSingleWord) {
  const results = await directLookupHandler(rawSearch, projectId, limit, includePending);
  if (results.length > 0) {
    return { routingStrategy: "direct_lookup", results, ... };
  }
}
```

- ❌ Short-circuits to `directLookupHandler()` which does not apply decay.
- This is the fastest path (no LLM call), but it returns results without any age-based ranking.

### Entry Points Integration:

- ✅ `POST /search` (search.ts:27) calls `routeQuery()` — flows through to handlers.
- ✅ `POST /mcp/query` (mcp.ts:221) calls `routeQuery()` — flows through to handlers.
- ✅ `GET /mcp/search_knowledge` (mcp.ts:77) calls `routeQuery()` — flows through to handlers.
- ✅ `includePending` parameter correctly flows through all paths.

### Feedback Loop:

- ✅ `POST /search/feedback` (search.ts:34-56) refreshes `lastVerifiedAt` for L2 and L3 nodes.
- ✅ This completes the decay lifecycle — verified nodes get their decay "reset."

**Findings:**

- ❌ **Critical gap**: Decay is only applied in 1 of 6 query paths (vector search with embeddings). The design spec says "the router applies decay to search scores" — this should be universal across all search strategies.
- ❌ The vector fallback path (SQL LIKE) uses fixed scores, creating an inconsistency where the system's behavior changes based on whether the embedding service is available.
- ❌ Hybrid search produces mixed-quality rankings because decayed vector results compete with non-decayed graph results.
- ✅ The feedback loop correctly refreshes `lastVerifiedAt`, but its impact is limited to the vector+embedding path.

## Round 2 — Code Quality & Security Review

**Code Quality:**

- ✅ The decay application pattern (`rawScore * decayFactor`) is clean and consistent where applied.
- ✅ The `calculateTemporalDecay()` function is pure, well-tested, and correctly implemented.
- ❌ **Inconsistent application**: The same concern (temporal decay) is handled differently across handlers. This violates the DRY principle — there's no shared "apply decay to results" utility that all handlers call.
- ❌ **Missing abstraction**: A function like `applyDecayToResults(results: AgenticSearchResult[]): AgenticSearchResult[]` could centralize the decay logic and ensure consistency.

**Refactoring Opportunity:**

```typescript
// Proposed shared utility (not currently present):
function applyDecay(results: AgenticSearchResult[]): AgenticSearchResult[] {
  return results.map((r) => ({
    ...r,
    score: r.score * calculateTemporalDecay(new Date(r.createdAt)),
  }));
}
```

This would need to be called in each handler before returning results.

**Security:**

- ✅ No new security issues beyond those identified in 3.2.1 (unauthenticated feedback endpoint).
- ✅ All queries use parameterized Drizzle ORM — no SQL injection risk.

**Issues Found:**

- ⚠️ **Medium**: Temporal decay is inconsistently applied across query handlers. Only `vectorSearchHandler()` (embedding path) applies decay; `graphTraversalHandler()`, `directLookupHandler()`, and the vector fallback path all use fixed scores.
- ⚠️ **Low**: Hybrid search merge logic can produce counter-intuitive rankings where non-decayed graph results outrank decayed vector results.
- ℹ️ **Info**: The single-word fast-circuit in `routeQuery()` bypasses decay entirely, which may be acceptable for exact-match queries but is undocumented.

## Round 3 — Integration & Completeness Review

**Integration:**

- ✅ The `routeQuery()` orchestrator correctly dispatches to all handlers based on classification.
- ✅ Both `/search` and `/mcp/query` entry points flow through `routeQuery()`.
- ✅ The `includePending` parameter correctly flows through all paths.
- ❌ The feedback loop (`POST /search/feedback`) only meaningfully affects the vector+embedding path. For graph/direct queries, refreshing `lastVerifiedAt` has no effect on future result rankings because those handlers don't read `lastVerifiedAt`.

**Test Coverage:**

- ✅ **Unit tests**: `calculateTemporalDecay()` is well-tested with 4 boundary conditions (3.2.1 report confirmed this).
- ❌ **No integration tests for decay in query results**: No tests verify that query results from any handler are ranked by decay.
- ❌ **No tests for decay in graph traversal**: No tests verify that graph results respect node age.
- ❌ **No tests for decay in hybrid search**: No tests verify correct ranking when merging decayed vector results with non-decayed graph results.
- ❌ **No tests for the vector fallback path**: No tests verify decay behavior when embeddings are unavailable.

**Completeness:**

- ⚠️ The feature is **partially complete**. The mathematical foundation (item 3.2.1) is correct, but the application of decay to query results (item 3.2.2) is incomplete — it only works for the vector+embedding path.
- ⚠️ The design spec's intent ("knowledge untouched naturally sinks to the bottom") is not fulfilled for graph traversal, direct lookup, or hybrid search results.

**Performance:**

- ✅ Decay computation is O(1) per node — no performance concern.
- ✅ No additional DB queries required — `lastVerifiedAt` is already fetched with the node data.

| 1   | ⚠️ Medium | Temporal decay is only applied in the vector+embedding path. Graph traversal, direct lookup, vector fallback, hybrid search graph portion, and the single-word fast-circuit all use fixed scores with no age-based ranking. |
| 2   | ⚠️ Medium | Hybrid search merge can produce counter-intuitive rankings — non-decayed graph results receive a +0.5 boost that can push them above decayed vector results.                                                                |
| 3   | ⚠️ Low    | The feedback loop (`POST /search/feedback`) refreshes `lastVerifiedAt`, but this has no effect on future rankings for graph/direct queries since those handlers don't read the field.                                       |
| 4   | ⚠️ Low    | No integration tests verify decay behavior in end-to-end query flows for any handler.                                                                                                                                       |
| 5   | ℹ️ Info   | No shared utility function for applying decay — the logic is duplicated (where present) rather than centralized.                                                                                                            |

## Recommendations

1. **Apply decay universally**: Add temporal decay to `graphTraversalHandler()` and `directLookupHandler()` by reading `lastVerifiedAt ?? createdAt` from each node and multiplying the fixed score by the decay factor. This fulfills the design spec's intent that "knowledge untouched naturally sinks to the bottom" across all query strategies.

2. **Fix the vector fallback path**: When `generateEmbedding()` returns null and the handler falls back to SQL LIKE, apply decay to the fixed scores (0.9, 0.8) based on each node's `lastVerifiedAt`.

3. **Fix hybrid search merge**: Either (a) apply decay to graph results before merging, or (b) normalize scores so decayed vector results and non-decayed graph results are comparable. The current +0.5 boost for intersection nodes is arbitrary and can produce misleading rankings.

4. **Add integration tests**: Seed the database with nodes having different `lastVerifiedAt` values and verify that query results from all handlers (vector, graph, direct, hybrid) are correctly ranked by decay.

5. **Consider a shared decay utility**: Create a function like `applyDecayToResults()` that all handlers call before returning, ensuring consistent behavior and reducing duplication.

---

## Overall Verdict

**⚠️ WARN**

The mathematical foundation of temporal decay (item 3.2.1) is correct and well-tested. However, the **application of decay to knowledge query results** (item 3.2.2) is incomplete. Decay is only applied in the vector search path when embeddings are available (1 of 6 query paths). The graph traversal handler, direct lookup handler, vector fallback path, hybrid search graph portion, and single-word fast-circuit all return results with fixed scores that ignore node age. This means the design spec's core promise — "knowledge untouched naturally sinks to the bottom" — is only fulfilled for a subset of queries. The feedback loop is correctly implemented but its impact is limited since most query paths don't consume `lastVerifiedAt`. The feature works as designed for the primary vector+embedding path but needs expansion to cover all query strategies.
