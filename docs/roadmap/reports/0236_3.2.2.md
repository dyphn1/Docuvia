## Round 1 — Architecture & Design Review

### Design Intent

ADR-007 Section 3 explicitly requires temporal decay to be applied to search scores across all query strategies so that "knowledge untouched naturally sinks to the bottom." The implementation should apply the exponential decay function `Math.exp(-LAMBDA * daysSinceVerified)` to raw search scores before returning results, ensuring older, unverified knowledge ranks lower than recently verified knowledge.

### Implementation Analysis

The `intent-router.ts` file contains six distinct query paths:

1. **Vector Search WITH embeddings** (lines 214-224 for L2, 268-278 for L3): Applies decay correctly
2. **Vector Search FALLBACK (SQL LIKE)** (lines 293-381): Uses fixed scores without decay
3. **Graph Traversal** (lines 391-475): Uses fixed scores without decay
4. **Direct Lookup** (lines 481-554): Uses fixed scores without decay
5. **Hybrid Search** (lines 560-608): Combines decayed vector results with non-decayed graph results
6. **Single-word Fast-Circuit** (lines 627-645 in `routeQuery`): Bypasses to direct lookup (no decay)

### Findings

1. **✅ Vector search with embeddings**: Correctly applies decay to both L2 and L3 nodes using `referenceDate = node.lastVerifiedAt ?? node.createdAt` and `score = rawScore * decayFactor`.
2. **❌ Vector search fallback**: L2 fallback (line 336) and L3 fallback (line 377) use fixed scores (0.9, 0.8) with no decay applied, violating the universal decay requirement.
3. **❌ Graph traversal**: All scoring uses fixed constants (seed: 1.0, related L2: 0.8, L3 decisions: 0.9) with no decay applied.
4. **❌ Direct lookup**: Hash match (line 513) and ILIKE match (line 547) use fixed scores (1.0, 0.8) with no decay applied.
5. **❌ Validity status bug**: Lines 500 and 535 still check for `validityStatus !== 'active'` instead of `'valid'`, breaking the direct lookup path when `includePending=false`.
6. **⚠️ Hybrid search**: Combines decayed vector results with non-decayed graph results; the merge scoring boost (`existing.score += r.score + 0.5`) can push older, non-decayed graph results above newer, decayed vector results.
7. **❌ Single-word fast-circuit**: Routes to `directLookupHandler` which applies no decay, meaning the fastest path returns results without age-based ranking.

**Design Gap**: The specification requires universal decay application so that "knowledge untouched naturally sinks to the bottom," but decay is only applied in 1 of 6 query paths (vector search with embeddings). This creates inconsistent behavior where the same query may return different rankings depending on which strategy is selected.

## Round 2 — Code Quality & Security Review

### Code Quality Issues

1. **❌ Inconsistent decay application**: Decay logic is duplicated where present (vector search) rather than centralized. No shared `applyDecayToResults()` utility exists.
2. **❌ Magic numbers**: Fixed scores (1.0, 0.9, 0.8) are hardcoded throughout handlers without decay adjustment.
3. **❌ Function length**: `vectorSearchHandler()` exceeds 180 lines, violating the 100-line recommended maximum.
4. **❌ Missing tests**: No unit tests for decay application in graph traversal, direct lookup, or fallback paths.

### Security Review

- **✅ Input validation**: All queries use parameterized Drizzle ORM — no SQL injection risk.
- **✅ Validity status**: Despite the 'active' vs 'valid' bug, the schema correctly defines the enum as `pending | valid | orphaned`.
- **✅ Error handling**: `classifyIntent()` has proper fallback to `vector_search` on failure.

### Critical Bug Re-Confirmation

The `validityStatus` check for `'active'` instead of `'valid'` (lines 500, 535) remains unfixed. This means when `includePending=false` (default), NO L3 nodes are returned by direct lookup because `validityStatus` never equals `'active'`. This breaks the entire direct lookup fast-path.

## Round 3 — Integration & Completeness Review

### Integration Coverage

- **✅ REST API**: `POST /search` correctly calls `routeQuery()`.
- **✅ MCP**: Both `POST /mcp/query` and `GET /mcp/search_knowledge` call `routeQuery()`.
- **✅ Feedback loop**: `POST /search/feedback` correctly updates `lastVerifiedAt` for L2/L3 nodes.
- **❌ Integration tests**: No tests verify decay behavior in end-to-end query flows for any handler.

### Completeness

- **⚠️ Partially complete**: Mathematical foundation (item 3.2.1) is correct and well-tested, but decay application to query results (item 3.2.2) is incomplete.
- **❌ Design intent unfulfilled**: The core promise "knowledge untouched naturally sinks to the bottom" only works for vector search with embeddings.
- **⚠️ Hybrid search inconsistency**: Mixed decay/application creates unpredictable rankings where boosting can override age-based ordering.

### Performance

- **✅ Decay computation**: O(1) per node — no performance concerns.
- **✅ Data availability**: `lastVerifiedAt` is already fetched with node data — no additional DB queries needed.

## Recommendations

1. **Fix critical validity status bug**: Change `'active'` to `'valid'` on lines 500 and 535 of `intent-router.ts`.
2. **Apply decay universally**: Add temporal decay to all query paths:
   - **Vector fallback**: Apply decay to fixed scores (0.9, 0.8) based on `lastVerifiedAt`
   - **Graph traversal**: Multiply fixed scores by decay factor for each node
   - **Direct lookup**: Multiply fixed scores by decay factor for each node
   - **Hybrid search**: Either apply decay to graph results before merging or normalize scores so decayed and non-decayed results are comparable
3. **Create shared decay utility**: Implement `applyDecayToResults(results: AgenticSearchResult[]): AgenticSearchResult[]` to centralize decay logic.
4. **Add integration tests**: Seed DB with nodes having different `lastVerifiedAt` values and verify all handlers return results ranked by decay.
5. **Refactor long functions**: Break `vectorSearchHandler()` into smaller, focused functions.
6. **Replace magic numbers**: Define constants for base scores (e.g., `BASE_SCORE_HASH_MATCH = 1.0`).

## Overall Verdict

### ⚠️ WARN

The mathematical foundation of temporal decay (item 3.2.1) is correct and well-tested. However, the **application of decay to knowledge query results** (item 3.2.2) remains **critically incomplete**. Decay is only applied in the vector search path when embeddings are available (approximately 1/6 of query paths). The graph traversal handler, direct lookup handler, vector fallback path, hybrid search graph portion, and single-word fast-circuit all return results with fixed scores that ignore node age.

This means the design spec's core promise — "knowledge untouched naturally sinks to the bottom" — is only fulfilled for a subset of queries. The feedback loop (`POST /search/feedback`) correctly updates `lastVerifiedAt`, but its impact is limited since most query paths don't consume this field for decay calculation. Additionally, the critical `validityStatus` bug ('active' vs 'valid') continues to break the direct lookup fast-path.

Until decay is applied universally across all query strategies and the validity status bug is fixed, the temporal decay feature cannot be considered complete per the design specification.
