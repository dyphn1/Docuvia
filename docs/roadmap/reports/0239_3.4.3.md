## Round 1 — Architecture & Design Review

### Design Intent

The `docuvia sync` CLI is a user-facing command-line tool triggered by a `post-push` git hook. Per the design spec (`implement_v2-core-architecture.md` §3.3), it should:

1. Read `.docuvia/config.yaml` and `.docuvia/.snapshot-ref` from the workspace.
2. Call `POST /sync` with the pushed branch name, commit hashes, and config content.
3. After the server responds, run `git fetch origin docuvia-knowledge` to update the local snapshot ref.

The server-side `POST /sync/push` endpoint (`sync.ts`) expects a CQRS outbox payload: `{ projectId, events: [{ type, payload }] }`. It acquires an advisory lock, applies DB operations in a transaction, and writes to the orphan branch.

### Implementation Analysis

**What exists:**

- `scripts/src/cli.ts` (lines 8-31) implements a `sync` subcommand that:
  - Reads `DOCUVIA_API_URL` and `MCP_PAT` from env vars.
  - Takes a `<project_id>` positional argument.
  - Calls `POST /api/projects/{projectId}/sync` (the ingestion trigger endpoint in `projects.ts`).
  - Does **not** read `.docuvia/config.yaml` or `.docuvia/.snapshot-ref`.
  - Does **not** send branch name, commit hashes, or config content.
  - Does **not** call `git fetch origin docuvia-knowledge` afterward.
- `artifacts/api-server/src/routes/projects.ts` (lines 239-259) has `POST /projects/:id/sync` which only logs an activity entry — it does **not** trigger the sync pipeline, does not process commits, and does not write to the orphan branch.
- `artifacts/api-server/src/lib/githook-template.sh` (line 6) invokes `docuvia sync --branch "$BRANCH" --commits "$COMMITS"` — but the CLI does **not** accept `--branch` or `--commits` flags.
- `artifacts/vscode-client/src/CentralServerClient.ts` (lines 99-128) has a `sync()` method that calls `POST /sync` with `{ projectId, pushedBranch, pushedCommits }` — but this endpoint (`POST /sync`) does **not exist** on the server. The server only has `POST /sync/push` which expects `{ projectId, events }`.

### Architecture Gaps

1. **CLI → Server payload mismatch:** The CLI calls `POST /projects/:id/sync` (ingestion trigger) instead of `POST /sync/push` (CQRS outbox). The githook template passes `--branch` and `--commits` flags that the CLI doesn't parse.
2. **Server endpoint is a stub:** `POST /projects/:id/sync` only inserts an activity log row. It does not process commits, update validity status, trigger generation, or write to the orphan branch.
3. **Missing `POST /sync` route:** The `CentralServerClient.sync()` calls `POST /sync` but the server only has `POST /sync/push`. These are different routes with different payload schemas.
4. **No `git fetch` step:** The CLI does not fetch the orphan branch after sync, breaking the "update local snapshot" step.
5. **No VS Code command:** There is no `docuvia.sync` command registered in `extension.ts` or declared in `package.json` contributions.

## Round 2 — Code Quality & Security Review

### Security Findings

1. **🟡 Medium — CLI uses `MCP_PAT` env var for auth:** The CLI passes the token as a `Bearer` header, which is correct. However, the githook template does not document how `MCP_PAT` should be set in the hook environment. Git hooks run in a limited environment and may not inherit `.env` files.
2. **🟡 Medium — No input validation on project ID:** `cli.ts` passes `process.argv[3]` directly to the URL template without validating it's a numeric ID. A malicious or malformed argument could cause unexpected URL construction.
3. **🟢 Low — `githook-template.sh` uses unquoted variables:** Line 6: `docuvia sync --branch "$BRANCH" --commits "$COMMITS"` — the variables are quoted, which is correct. However, `COMMITS` is constructed via `tr '\n' ','` which produces a trailing comma. This is cosmetic but could cause parsing issues if the server expects a clean list.

### Code Quality Findings

1. **🟡 Medium — `scripts/package.json` has no `bin` entry:** The CLI cannot be installed as a `docuvia` command via `npm install -g` or `pnpm link`. It can only be run via `tsx ./scripts/src/cli.ts`, which is not a distributable CLI.
2. **🟡 Medium — No build script for CLI:** The `scripts/package.json` has `"hello": "tsx ./src/hello.ts"` but no `"build"` or `"cli"` script. There is no compiled output.
3. **🟢 Low — `cli.ts` uses `process.exit()` directly:** While acceptable for a CLI, it makes the code untestable without mocking `process.exit`.
4. **🟢 Low — No tests for CLI:** There are no unit or integration tests for the `scripts/src/cli.ts` file.

### Completeness Summary

The `docuvia sync` CLI is **partially scaffolded but not functional**. The codebase has:

- A CLI file with the wrong interface and wrong server target.
- A server stub endpoint that doesn't perform sync.
- A correctly-designed `POST /sync/push` endpoint that nothing calls.
- A githook template that references flags the CLI doesn't support.
- A client `sync()` method that calls a non-existent server route.

The end-to-end sync flow (git hook → CLI → server → orphan branch → fetch) is **not operational**.

### Performance Considerations

- The CLI makes a single HTTP call, which is appropriate.
- The server's `POST /sync/push` correctly uses advisory locks and transactions for concurrent safety.
- No performance issues identified in the current (stub) implementation.

## Recommendations

1. **Fix CLI interface:** Update `scripts/src/cli.ts` to accept `--branch` and `--commits` flags matching the githook template.
2. **Fix CLI server target:** Change the CLI to call `POST /sync/push` with the correct CQRS outbox payload format: `{ projectId, events }`.
3. **Implement server sync logic:** Either replace the `POST /projects/:id/sync` stub with actual sync logic (process commits, update validity, trigger generation, write to orphan branch) or route it to the existing `POST /sync/push` handler.
4. **Add `POST /sync` route:** Either add a `POST /sync` endpoint that wraps `POST /sync/push`, or update `CentralServerClient.sync()` to call `POST /sync/push` directly.
5. **Add `git fetch` step:** After successful sync response, run `git fetch origin docuvia-knowledge` and update `.docuvia/.snapshot-ref`.
6. **Add `bin` entry to `scripts/package.json`:** Make the CLI installable as the `docuvia` command.
7. **Register `docuvia.sync` VS Code command:** Allow users to manually trigger sync from the command palette.
8. **Add tests:** Write integration tests for the CLI and the sync endpoint.

---

## Overall Verdict

**⚠️ WARN** — The `docuvia sync` CLI is scaffolded but has critical gaps preventing end-to-end operation. The CLI exists as a source file but is not installable, calls the wrong server endpoint with no payload, and the server's sync endpoint is a stub. The correctly-designed `POST /sync/push` CQRS endpoint exists on the server but is never called by anything. The githook template references CLI flags that don't exist. Core functionality (reading config, pushing deltas, fetching orphan branch) is missing. The item is partially implemented but not functional.
