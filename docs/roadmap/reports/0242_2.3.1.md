## Round 1 — Architecture & Design Review

### What the design spec says

The design docs establish that the VS Code client operates in a **multi-root workspace** environment:

1. **KnowledgeStore** maintains a `Map<string, KnowledgeGraphSnapshot>` keyed by workspace root path (`KnowledgeStore.ts:_snapshots` at line 43). The `load()` method (line 94) iterates `vscode.workspace.workspaceFolders` and calls `_loadWorkspace()` for each folder independently.

2. **KnowledgeGraphTreeProvider** produces one `project` node per workspace folder at the tree root (`getChildren()` at line 154–177), each scoped to its `workspaceRoot`. Every downstream node (l1tag, l2module, l3entry, unassigned-group) carries a `workspaceRoot` field that ties it to a specific root.

3. **TaskRunner** receives workspace-scoped operations. When `queueExtraction()` runs, it resolves the workspace root via `vscode.workspace.getWorkspaceFolder()` (line 294) and writes results to `.docuvia/` within that specific root. Similarly, `queueAutoCategorization()` takes an explicit `workspaceRoot` parameter.

4. **ChatParticipant** (`handleExplore` at line 153) resolves workspace root upfront — using the active editor's folder, falling back to a single folder, or prompting the user via `showWorkspaceFolderPick()` in multi-root scenarios — and passes it through to all downstream operations.

### What the implementation actually do

The implementation matches the design:

- **TaskRunner.runExtractionAsync()** (line 294): Uses `vscode.workspace.getWorkspaceFolder(vscode.Uri.file(params.sourceFilePath))` to dynamically resolve the correct workspace root at execution time. This means the root is determined per-file, not hardcoded at construction.

- **TaskRunner.writeExtractionResults()** (line 342–403): Accepts `workspaceRoot: string` and writes all output files (`l3_decisions/*.md`, `l3_router.yaml`) relative to that root. It also calls `this.store.load()` which reloads all workspace snapshots.

- **TaskRunner.queueAutoCategorization()** (line 59): Takes an explicit `workspaceRoot` parameter and uses `this.store.snapshots.get(workspaceRoot)` (line 95) to access the correct snapshot, and writes to `.docuvia/` within that root (line 170).

- **ChatParticipant.handleExtract()** (line 393–497): Resolves `workspaceRoot` per-file via `vscode.workspace.getWorkspaceFolder()` (line 427) and passes file paths to `taskRunner.queueExtraction()`, which re-resolves the root internally.

- **extension.ts activation** (line 70): Creates a single `TaskRunner` instance, but since TaskRunner receives `store` (which is multi-root aware) and resolves roots dynamically, a single instance correctly handles all workspace folders.

### Architecture verdict

The architecture is correct. TaskRunner does NOT cache or hardcode a single workspace root. All workspace-root-sensitive operations either receive an explicit `workspaceRoot` parameter or resolve it dynamically from the file path via `vscode.workspace.getWorkspaceFolder()`. The KnowledgeStore underneath is fully multi-root aware with per-root snapshots, per-root FileSystemWatchers, and per-root `.docuvia/` loading.

## Round 2 — Code Quality & Security Review

### Security findings

- **🟡 Medium — Path traversal check in `initProject()` is weak** (`extension.ts:471–475`): The check `path.relative(folders.map(f => f.uri.fsPath).join(','), targetRoot)` joins all folder paths into a single comma-separated string before computing relative path. This is not a valid path operation — `path.relative` expects a single path, not a comma-joined list. While the check still catches some traversal cases, it's semantically incorrect. Should iterate over folders and check that `targetRoot` starts with one of them.

- **🟢 Low — No input validation on `workspaceRoot` in TaskRunner**: `queueAutoCategorization()` accepts a `workspaceRoot` string blindly. If a caller passes an arbitrary path, the method will attempt to read/write `.docuvia/` there. In practice, all callers pass paths from `vscode.workspace.workspaceFolders` or tree nodes (which carry `workspaceRoot` from the store), so exploitation is limited.

### Code quality findings

- **🟢 Low — Unused parameter in `writeExtractionResults()`** (`TaskRunner.ts:342–349`): The method signature checks `if (!workspaceRoot) return;` at line 349, but the caller at line 296–297 already guards with `if (workspaceRoot)`. The redundant guard is harmless but inconsistent.

- **🟢 Low — AST chunking not implemented** (`TaskRunner.ts:408–411`): The `chunkContent()` method has a TODO for AST-based chunking that falls back to line chunking. This is documented tech debt, not a bug.

- **🟢 Low — Test coverage**: The Playwright E2E tests (`tests/phase1.spec.ts`) test single-workspace scenarios only. There are no multi-root workspace tests that verify TaskRunner correctly routes files to different workspace roots in a multi-folder setup.

### Code style compliance

Code follows project conventions: early returns, TypeScript strict typing, async/await patterns, and structured logging via `outputChannel`.

| KnowledgeStore ↔ `onDidChangeWorkspaceFolders` | ✅ Working | Re-initializes watchers when folders change (line 474–479)               |

### Completeness

All code paths for dynamic root scoping are implemented:

- Single workspace folder: ✅ Works (root resolved unambiguously)
- Multiple workspace folders: ✅ Works (root resolved per-file via `getWorkspaceFolder()`)
- No workspace folder: ✅ Handled (commands show warning messages)
- Workspace folder added/removed at runtime: ✅ Handled (`onDidChangeWorkspaceFolders` listener)

### Performance considerations

TaskRunner processes files sequentially (chunk by chunk, file by file). In a multi-root workspace with extractions queued from different roots concurrently, the single `TaskRunner` instance processes them one at a time. This is acceptable for the current scope but could become a bottleneck with many concurrent extractions.

| 4   | 🟢 Low    | AST chunking not implemented (TODO, documented)                                                                    |

## Recommendations

1. **Fix path traversal check** (`extension.ts:471`): Replace `path.relative(folders.map(f => f.uri.fsPath).join(','), targetRoot)` with a loop: `folders.some(f => targetRoot.startsWith(f.uri.fsPath + path.sep))`.
2. **Add multi-root E2E test**: Open a workspace with two folders, init both, trigger extraction on a file in each, and verify results land in the correct `.docuvia/` directory.
3. **Remove redundant guard** in `writeExtractionResults()` or add a comment explaining the defensive pattern.

## Overall Verdict

✅ **PASS** — TaskRunner correctly implements dynamic root scoping. All workspace-sensitive operations resolve the workspace root per-file at runtime via `vscode.workspace.getWorkspaceFolder()`, or receive an explicit `workspaceRoot` parameter. The underlying KnowledgeStore maintains per-root snapshots, per-root FileSystemWatchers, and per-root `.docuvia/` directories. The `onDidChangeWorkspaceFolders` listener handles runtime folder changes. The single non-critical finding is a weak path traversal check in `initProject()` that does not affect TaskRunner itself.
