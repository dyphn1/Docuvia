## Round 1 — Architecture & Design Review

### What the design spec says

The design requires that each workspace folder in a multi-root setup maintains its own isolated `.docuvia/` directory with independent:

1. **Knowledge snapshots** — `KnowledgeStore` maintains `Map<string, KnowledgeGraphSnapshot>` keyed by `workspaceRoot` (store.md line 9)
2. **FileSystemWatchers** — one watcher per workspace folder for `.docuvia/**` (store.md line 14)
3. **Tree nodes** — one Project node per workspace folder, all children carry `workspaceRoot` (nodes.md)
4. **Init/Explore/Extract operations** — all resolve the target workspace root before writing

### What the implementation actually does

**KnowledgeStore (`KnowledgeStore.ts`):**

- `_snapshots: Map<string, KnowledgeGraphSnapshot>` at line 43 — keyed by workspace root path ✅
- `load()` (line 94) iterates `vscode.workspace.workspaceFolders` and calls `_loadWorkspace()` for each ✅
- `_loadWorkspace(workspaceRoot)` (line 122) reads `.docuvia/` from that specific root ✅
- `getSnapshotFor(uri)` (line 69) resolves the correct snapshot via `vscode.workspace.getWorkspaceFolder()` ✅
- `startWatcher()` (line ~438) creates one `FileSystemWatcher` per workspace folder, stored in `_watchers: Map<string, vscode.FileSystemWatcher>` ✅
- `_handleBatchedChanges(workspaceRoot, changedPaths)` (line 493) performs per-workspace incremental vs. full reload ✅
- `onDidChangeWorkspaceFolders` listener (line 474) re-initializes watchers when folders change ✅
- `dispose()` (line 520) disposes all per-root watchers ✅

**KnowledgeGraphTreeProvider (`KnowledgeGraphTreeProvider.ts`):**

- `getChildren()` at root level (line 154–177) returns one `project` node per workspace folder, each with `workspaceRoot: folder.uri.fsPath` ✅
- All child node types (l1tag, l2module, l3entry, unassigned-group) carry `workspaceRoot` field ✅
- `getSnapshotFor()` lookups use `node.workspaceRoot` to scope queries ✅

**initProject (`extension.ts` line 444):**

- Resolves `targetRoot` from: (a) tree node's `workspaceRoot`, (b) single folder, or (c) QuickPick filtered to uninitialized folders ✅
- Writes `manifest.yaml`, `config.yaml`, `.snapshot-ref` to `path.join(targetRoot, '.docuvia')` ✅
- Overwrite guard: shows warning if `.docuvia/` already exists ✅
- Path traversal check at line 471–475 (weak — see Round 2) ⚠️

**acceptL1Tags (`extension.ts` line 287):**

- Now accepts `(yamlContent, explicitRoot)` — the `explicitRoot` parameter receives the workspace root from ChatParticipant ✅
- Writes to `path.join(workspaceRoot, '.docuvia', ...)` ✅
- BUG A-3 (hardcoded `workspaceFolders[0]`) is fixed ✅

**ChatParticipant (`ChatParticipant.ts`):**

- `handleExplore()` (line 153) resolves `workspaceRoot` upfront: active editor → single folder → `showWorkspaceFolderPick()` ✅
- Passes `workspaceRoot` to `acceptL1Tags` via button arguments at lines 198, 242, 256 ✅
- `handleExtract()` (line 395) resolves `workspaceRoot` via `vscode.workspace.getWorkspaceFolder()` at line 427 ✅

### Architecture verdict

The architecture is fundamentally correct. Each workspace folder gets its own `.docuvia/` directory, its own snapshot in the store, its own FileSystemWatcher, and its own project node in the tree. All major operations (init, explore, extract, acceptL1Tags, auto-categorize) resolve the workspace root before writing. The design intent of per-workspace isolation is met.

## Round 2 — Code Quality & Security Review

### Security findings

- **🟡 Medium — Path traversal check in `initProject()` is semantically broken** (`extension.ts:471–475`): `path.relative(folders.map(f => f.uri.fsPath).join(','), targetRoot)` joins all folder paths into a single comma-separated string. `path.relative` expects a single path, not a comma-joined list. This means the traversal check may produce false negatives (allowing paths that should be rejected) or false positives (rejecting valid paths). Should be: `folders.some(f => targetRoot === f.uri.fsPath || targetRoot.startsWith(f.uri.fsPath + path.sep))`.

- **🟢 Low — `acceptL1Tags` trusts `explicitRoot` without validation** (`extension.ts:290`): The command uses `explicitRoot` directly without verifying it matches a known workspace folder. If a malicious extension invokes this command with an arbitrary path, files could be written outside the workspace. In practice, only ChatParticipant invokes this command with roots from `vscode.workspace.workspaceFolders`, so the risk is limited.

### Code quality findings

- **🟡 Medium — `initProject` filters out initialized folders from QuickPick** (`extension.ts:458`): `const uninitialized = folders.filter(f => !store.snapshots.has(f.uri.fsPath))` means an already-initialized workspace can never be re-initialized from the palette. The overwrite guard at line 482 is only reachable via the tree node path (which passes `node.workspaceRoot` directly, bypassing the QuickPick). This is a UX inconsistency — the palette path prevents re-init, while the tree node path allows it.

- **🟢 Low — `acceptL1Tags` doesn't validate `workspaceRoot` against known folders** (see security finding above).

- **🟢 Low — No multi-root workspace tests**: `phase1.test.ts` only tests single-workspace scenarios. There are no tests that verify per-workspace isolation in a multi-root setup (e.g., init workspace A, init workspace B, verify each has its own `.docuvia/`).

- **🟢 Low — `writeExtractionResults` in TaskRunner always writes `l2_module_id: 'sys-uncategorized'`** (`TaskRunner.ts:386`): Extracted decisions are always assigned to a hardcoded `sys-uncategorized` module rather than being matched to existing L2 modules. This is a functional limitation but not an isolation issue.

### Code style compliance

Code follows project conventions: TypeScript strict typing, early returns, async/await, structured logging via `outputChannel`. The `KnowledgeStore` singleton pattern is consistent.

### Performance considerations

The `KnowledgeStore.load()` method clears and reloads all snapshots on every call (line 101: `this._snapshots.clear()`). In a multi-root workspace, this means adding a file to workspace A triggers a full reload of workspace B's snapshot too. The `_handleBatchedChanges()` method (line 493) mitigates this for watcher-triggered reloads by calling `_loadWorkspace(workspaceRoot)` for incremental updates, but `load()` itself (called by `refreshKnowledgeGraph` and `acceptL1Tags`) still does a full clear-and-reload. This is acceptable for the current scale.

## Recommendations

1. **Fix path traversal check** (`extension.ts:471`): Replace with `folders.some(f => targetRoot === f.uri.fsPath || targetRoot.startsWith(f.uri.fsPath + path.sep))`.
2. **Allow re-init from palette**: Add an "All folders" option to the QuickPick or remove the `uninitialized` filter, letting the overwrite guard handle already-initialized workspaces.
3. **Add workspace root validation to `acceptL1Tags`**: Check that `explicitRoot` matches a folder in `vscode.workspace.workspaceFolders` before writing.
4. **Add multi-root integration test**: Create a test that opens two workspace folders, initializes both, and verifies each `.docuvia/` is independent.
5. **Optimize `load()` for single-workspace changes**: Add an optional `workspaceRoot` parameter to `load()` so callers can reload a single root without clearing all snapshots.

## Overall Verdict

⚠️ **WARN** — Per-workspace `.docuvia/` isolation is architecturally sound and functionally working. The KnowledgeStore maintains per-root snapshots, per-root FileSystemWatchers, and per-root `.docuvia/` directories. All major operations (init, explore, extract, acceptL1Tags, auto-categorize) correctly resolve and use the workspace root. The critical BUG A-3 (acceptL1Tags writing to wrong workspace) has been fixed. However, there are notable gaps: a semantically broken path traversal check, no multi-root test coverage, and the `initProject` palette path blocking re-initialization of already-initialized workspaces. These are not blockers but represent real quality and security gaps that should be addressed.
