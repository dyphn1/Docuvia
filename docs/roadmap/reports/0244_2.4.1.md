## Round 1 — Architecture & Design Review

### Design Intent

The spec (`nodes.md`) defines a 6-level node hierarchy for the Knowledge Graph TreeView:

1. **Project** (Level 0) — workspace folder root
2. **L1 Tag** (Level 1) — architectural categories from `l1_tags.yaml`
3. **L2 Module** (Level 2) — functional subsystems from `l2_modules.yaml`
4. **L3 Entry** (Level 3) — individual decisions from `l3_decisions/*.md`
5. **Unassigned Decisions** (Virtual Level 1) — virtual container under Project for L3 entries with `l2_module_id === 'unassigned'` or unmapped IDs
6. **Placeholder** — informational nodes for empty/missing data

The `unassigned-group` node must:

- Appear as a child of the Project node (alongside L1 tags)
- Use icon `$(question)` and context value `unassigned-group`
- Be auto-created when any decision has `l2_module_id === 'unassigned'` or references a non-existent L2 module
- Expand to show unassigned L3 Entry nodes

### Implementation Analysis

**`KnowledgeGraphTreeProvider.ts`** (the core file):

- **`KGNodeKind` type** (line 8): Includes `'unassigned-group'` in the union — ✅
- **`getChildren()` for `project` nodes** (lines 180–215):
  - Builds `tagChildren` from L1 tags — ✅
  - Computes `validModuleIds` set from `snap.modules` — ✅
  - Checks `hasUnassigned` by scanning `snap.decisions` for `d.l2_module_id === 'unassigned'` or unmapped IDs — ✅
  - Appends `unassigned-group` node to `tagChildren` when `hasUnassigned` is true — ✅
- **`getChildren()` for `unassigned-group` nodes** (lines 231–245):
  - Filters decisions where `l2_module_id === 'unassigned'` or ID not in `validModuleIds` — ✅
  - Maps them to `l3entry` KGNode objects with `filePath` and `workspaceRoot` — ✅
- **`getTreeItem()` for `unassigned-group`** (lines 89–93):
  - Creates `TreeItem` with `Collapsed` state — ✅
  - Uses `ThemeIcon('question')` — ✅
  - Sets `contextValue = 'unassigned-group'` — ✅

**`extension.ts`** (wiring):

- TreeView created at line 56 with `treeDataProvider: kgProvider` and `dragAndDropController: kgProvider` — ✅
- `docuvia.autoCategorizeDecisions` command registered at line 132 — ✅

**`package.json`** (menus):

- Context menu item at line 188: `docuvia.autoCategorizeDecisions` with `when: view == docuvia.knowledgeGraph && viewItem == unassigned-group` — ✅

### Architecture Assessment

The implementation correctly follows the spec. The `unassigned-group` node is:

1. Conditionally created based on actual data state (not always present)
2. Positioned as a sibling of L1 tags under the Project node
3. Properly typed with dedicated `KGNodeKind` and `contextValue`
4. Wired to a context menu action for auto-categorization
5. Capable of expanding to show unassigned L3 entries

The design doc (`nodes.md` line 55) previously flagged this as "CONFLICT – Not Implemented", but the code has since been updated to include the full unassigned-group logic. The implementation now matches the spec.

**Finding:** The design doc `nodes.md` contains a stale ⚠️ CONFLICT note (line 55) claiming the `unassigned-group` is absent. This is outdated — the code fully implements it. 🟢 Low

## Round 2 — Code Quality & Security Review

### Code Quality Findings

1. **Defensive design in `getChildren` for `unassigned-group`** (lines 231–245): Properly guards against missing snapshot (`if (!snap) return []`), uses `Set` for O(1) module ID lookup, and handles both `'unassigned'` string and unmapped IDs. ✅

2. **Drag-and-drop integration** (lines 37–81): The `handleDrop` method correctly filters for `l2module` targets, validates `workspaceRoot` match, and updates `l3_router.yaml` with error handling. ✅

3. **Context value consistency**: The `contextValue` set in `getTreeItem` (`'unassigned-group'`) matches the `when` clause in `package.json` (`viewItem == unassigned-group`). ✅

4. **No input sanitization concerns**: The TreeProvider reads from the local `.docuvia/` directory and in-memory snapshot — no external user input is processed. ✅

5. **Bug in `autoCategorizeDecisions` command** (extension.ts lines 132–142): When invoked from the context menu on an `unassigned-group` node, the `node` parameter is the unassigned-group node itself. But the code calls `kgProvider.getChildren(node)` which correctly returns the unassigned L3 entries (since `getChildren` handles `unassigned-group` kind). This works correctly. ✅

### Test Coverage

This is consistent with the broader pattern in this codebase where VS Code extension UI logic lacks isolated unit tests (the checklist items 9.4.3–9.4.5 note E2E tests are "not done").

🟡 Medium: No unit tests for `KnowledgeGraphTreeProvider.getChildren()` logic, particularly the unassigned-group detection and filtering.
