## Round 1 — Architecture & Design Review

### Design Intent

Per ADR-004, when the system encounters an unknown branch, it should:

1. Execute `git merge-base HEAD origin/main` to find the nearest common ancestor
2. Ingest only commits between the merge-base and HEAD (the "delta"), avoiding re-scanning the entire repository
3. Anchor L3 knowledge to specific Git commits via Temporal Range Anchors (`introducedInCommit`, `verifiedUntilCommit`)
4. Store the branch name in `commits.branchName` for merge-gate tracking

This is the "Baseline Inheritance" mechanism: the server inherits the ancestor's knowledge state and only processes the delta.

### Implementation Analysis

**`getProjectedCommits()` exists but is dead code** (`git-client.ts` lines 97–115):
- Correctly executes `git merge-base HEAD origin/main` — ✅
- Constructs `revisionRange = "${mergeBase}..HEAD"` — ✅
- Falls back to full analysis on failure — ✅
- Calls `this.getCommits(limit, undefined, revisionRange)` — ✅
- **Never called by any route, service, or internal caller** — ❌ Dead code
- Confirmed: `search_files` for `getProjectedCommits` returns only the definition at line 97

**Ingest route bypasses merge-base** (`ingest.ts` line 55):
```typescript
const commits = await client.getCommits(limit, since);
```
- Uses `getCommits()` directly with optional `since` date filter — ❌ No merge-base projection
- The `since` date approach works for linear history but fails for feature branches, force-pushes, and squashed commits

**Temporal anchor columns exist but are never populated** (`l3_nodes.ts` lines 35–36):
- `introducedInCommit: text("introduced_in_commit")` — ✅ Schema exists
- `verifiedUntilCommit: text("verified_until_commit")` — ✅ Schema exists
- `processIngestion()` (`ingestion-pipeline.ts` lines 90–97) only inserts: `projectId`, `hash`, `message`, `author`, `valid`, `vcsType` — ❌ Temporal anchors never set

**Branch name column exists but is never populated** (`commits.ts` line 22):
- `branchName: text("branch_name")` — ✅ Schema exists
- `getCurrentBranchName()` (`git-client.ts` lines 117–128) exists — ✅
- **Never called during ingestion** — ❌ Dead code

### Architecture Assessment

The temporal delta projection architecture is partially implemented at the schema level (columns exist) and at the algorithm level (`getProjectedCommits` is correctly coded), but the critical integration wiring is missing. The ingest route calls `getCommits()` directly, completely bypassing the merge-base projection. The temporal anchor columns and branch name column are dead schema — they exist in the Drizzle schema but are never populated during ingestion.

## Round 2 — Code Quality & Security Review

### Code Quality Findings

1. **`getProjectedCommits` is well-implemented** (git-client.ts lines 97–115): Proper try/catch around `git merge-base`, correct fallback behavior, clean delegation to `getCommits()` with `revisionRange`. The algorithm is correct — it's just never called. ✅

2. **`execFileAsync` is used correctly** (line 102): No shell injection risk. The `baseRef` parameter is passed as an array argument, not interpolated into a shell command. ✅

3. **Incremental mode uses wrong strategy** (ingest.ts lines 54–55): The `mode: "incremental"` path uses `--since` date filter (`project.lastGitIngestedAt`), not merge-base. This doesn't handle:
   - Feature branches diverged from main
   - Force-pushes that rewrite history
   - Squashed commits where the original SHA no longer exists
   - Detached HEAD states
   🟡 Medium

4. **No tests for merge-base logic**: Zero test coverage for `getProjectedCommits()`, the fallback behavior, or the revision range construction. No test files reference `getProjectedCommits` or `merge-base`. 🟡 Medium

5. **No tests for temporal anchor population**: No tests verify that `introducedInCommit` or `verifiedUntilCommit` are populated during ingestion. 🟡 Medium

6. **Dead schema columns**: `l3_nodes.introducedInCommit`, `l3_nodes.verifiedUntilCommit`, `commits.branchName` exist in schema but are never written to. This is misleading — migrations will create the columns but they'll always be NULL. 🟡 Medium

### Security

- `git merge-base` uses `execFileAsync` (no shell) — safe from injection ✅
- `baseRef` parameter defaults to `"origin/main"` and is not user-controlled in the current (dead) code path ✅

### Edge Cases

| Scenario | Expected Behavior | Actual Behavior |
|----------|-------------------|-----------------|
| Feature branch with diverged history | merge-base finds common ancestor, only delta ingested | Full history ingested (no merge-base) |
| Force-pushed branch | merge-base handles rewritten history | `--since` date may miss commits |
| Squashed commits | merge-base finds pre-squash ancestor | `--since` date may miss commits |
| Detached HEAD | merge-base fails, fallback to full analysis | Works (fallback exists in dead code) but not reachable |
| No common ancestor | Fallback to full repository analysis | Works (fallback exists in dead code) but not reachable |

### Performance

- `git merge-base` is a fast O(1) git operation — negligible overhead
- The performance benefit of delta projection (only ingesting new commits) is significant for large repositories but is **unrealized** since `getProjectedCommits` is never called
- Current approach ingests up to `limit` (default 100) commits per request regardless of whether they've already been processed

## Findings Summary

| # | Severity | Finding |
|---|----------|---------|
| 1 | 🔴 High | `getProjectedCommits()` is dead code — never called by any route or service. The merge-base projection is completely disconnected from the ingestion pipeline. |
| 2 | 🟡 Medium | Temporal anchor columns (`introducedInCommit`, `verifiedUntilCommit`) exist in schema but are never populated during ingestion. |
| 3 | 🟡 Medium | `commits.branchName` column exists in schema but `getCurrentBranchName()` is never called during ingestion. |
| 4 | 🟡 Medium | Incremental mode uses `--since` date filter instead of merge-base; doesn't handle branch divergence, force-pushes, or squashed commits. |
| 5 | 🟡 Medium | Zero test coverage for merge-base logic, temporal anchor population, or branch name tracking. |

## Recommendations

1. **Wire `getProjectedCommits` into ingest route**: Change `ingest.ts:55` to call `client.getProjectedCommits(limit)` when mode is `"full"`, or add a new mode (e.g., `mode: "projected"`) that uses merge-base. This is the highest-priority fix.

2. **Populate temporal anchors during ingestion**: In `processIngestion()`, set `introducedInCommit` to the commit hash for each L3 node generated from that commit. Set `verifiedUntilCommit` when a node is invalidated by a later commit.

3. **Call `getCurrentBranchName()` during ingestion**: Store the branch name in `commits.branchName` to enable merge-gate tracking (item 4.3.8).

4. **Add tests**: Create unit tests for `getProjectedCommits` using a test git repository with known merge-base relationships. Create integration tests that verify temporal anchor population.

5. **Consider merge-base for incremental mode**: The `--since` date approach is fragile. Consider using merge-base as the primary incremental strategy, with `--since` as a fallback.

---

## Overall Verdict

**⚠️ WARN** — The temporal delta projection is partially implemented. The `getProjectedCommits()` algorithm in `git-client.ts` is correctly implemented with proper merge-base logic and fallback behavior, but it is **completely disconnected from the ingestion pipeline** — the ingest route calls `getCommits()` directly, bypassing merge-base projection entirely. Additionally, the temporal range anchor columns (`introducedInCommit`, `verifiedUntilCommit`) and `commits.branchName` column exist in the database schema but are never populated during ingestion. There are zero tests for any of this functionality. The feature exists as dead code and dead schema — the architecture is sound but the integration wiring is missing.
