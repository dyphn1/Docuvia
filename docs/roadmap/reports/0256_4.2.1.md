# Verification Report: Item 4.2.1 — Progressive Batch Mode (commits in groups of 20)

**Item ID:** 4.2.1
**Description:** Progressive batch mode (commits in groups of 20)
**Date:** 2026-06-19
**Verdict:** ⚠️ WARN

## Design Spec References

- `docs/design/09-architectural-decisions.md` — ADR-010: L2 Bootstrap — AI Discovery to Path Rules (lines 243–266)
- `docs/design/12-glossary.md` — "L2 Bootstrap" definition (line 35)

ADR-010 specifies: "The first generate run uses a progressive batch mode: commits are processed in groups of 20. Each batch's LLM prompt includes the L2 module list produced by previous batches, enabling the AI to self-correct module names and boundaries across batches."

## Round 1 — Architecture & Design Review

**Finding 1: Progressive batch loop is correctly implemented.**

In `generate.ts:864-887`, the bootstrap mode branch contains:

```typescript
// Bootstrap mode: batch 20 commits per LLM call, pass previous L2 list for self-correction
const BATCH_SIZE = 20;
const previousL2Names: string[] = [];

for (let batchStart = 0; batchStart < commitData.length; batchStart += BATCH_SIZE) {
  const batchCommits = commitData.slice(batchStart, batchStart + BATCH_SIZE);
  const batchResult = await generateL2Nodes(
    batchCommits,
    allL1Tags,
    documentContext,
    model,
    l2SystemPrompt,
    corrections,
    previousL2Names
  );
  for (const node of batchResult) {
    if (!previousL2Names.includes(node.name)) {
      previousL2Names.push(node.name);
    }
  }
  l2Input = [...l2Input, ...batchResult];
}
```

This matches the ADR-010 spec exactly: commits are processed in groups of 20, and `previousL2Names` is passed to each subsequent batch for self-correction.

**Finding 2: `generateL2Nodes()` correctly uses `previousL2Names` for self-correction.**

In `generate.ts:246-249`, the function builds a `previousBatchSection` that is included in the LLM prompt:

```typescript
const previousBatchSection =
  previousL2Names && previousL2Names.length > 0
    ? `\n\nL2 modules discovered in previous batches (maintain consistency with these names): ${previousL2Names.join(", ")}`
    : "";
```

This enables the AI to self-correct module names across batches, as required by ADR-010.

**Finding 3: Bootstrap vs. path-rule mode branching is correct.**

In `generate.ts:765-887`, the code checks `allBootstrapConfirmed` to decide between:

- **Path-rule mode** (lines 771–863): Uses `pathPatterns` from the DB to deterministically assign commits to L2 modules via glob matching.
- **Bootstrap mode** (lines 864–887): Uses the progressive batch LLM approach.

The `allBootstrapConfirmed` flag is computed at line 766–767: `existingL2.length > 0 && existingL2.every((n) => n.isBootstrapConfirmed)`. This means bootstrap mode is used when there are existing L2 nodes but not all are bootstrap-confirmed, or when there are no existing L2 nodes at all (since `every()` returns `true` for an empty array, but the `existingL2.length > 0` guard prevents false positives).

**Finding 4: Schema supports all required columns.**

The `l2_nodes` table schema (`lib/db/src/schema/l2_nodes.ts`) includes all columns required by ADR-010:

- `pathPatterns: jsonb("path_patterns")` (line 22)
- `reindexRequired: boolean("reindex_required").notNull().default(false)` (line 23)
- `isBootstrapConfirmed: boolean("is_bootstrap_confirmed").notNull().default(false)` (line 24)

**Finding 5: No dedicated "bootstrap" mode in the API schema.**

The `GenerateInputSchema` at `generate.ts:73-77` only accepts `mode: z.enum(["full", "incremental"])`. There is no `"bootstrap"` mode enum value. The bootstrap path is triggered implicitly (when L2 nodes exist but aren't all bootstrap-confirmed), not via an explicit API parameter. This is a design choice, not a bug — the ADR says "Bootstrap batch mode is a distinct pipeline mode" but doesn't require an explicit mode flag. However, it means the API cannot explicitly request bootstrap mode; it's inferred from project state.

## Round 2 — Code Quality & Security Review

**Finding 6: No input validation on batch size.**

The `BATCH_SIZE = 20` is hardcoded (line 866). This is correct per the ADR spec, but there's no guard against an empty `commitData` array before entering the batch loop. If `commitData` is empty, the loop simply won't execute (the condition `batchStart < commitData.length` is immediately false), so this is safe — but there's no early return for the empty case before the L2 generation logic. The empty case is handled earlier at lines 616–630 (returning zero counts), so this is fine.

**Finding 7: No deduplication across batches within the bootstrap loop.**

The bootstrap loop at lines 869–886 accumulates results into `l2Input` without deduplication. If the LLM returns the same module name in multiple batches, it will appear multiple times in `l2Input`. Deduplication happens later at lines 889–923 (the `existingL2Map` check), but only against _existing_ DB records — not against modules discovered earlier in the same bootstrap run. The `previousL2Names` array prevents the LLM from creating duplicates across batches (by instructing it to maintain consistency), but this is a soft LLM-level constraint, not a hard code-level deduplication. If the LLM ignores the instruction, duplicate L2 nodes could be created within a single generate run.

**Finding 8: No rate limiting between batches.**

Unlike the `condenseL3Node()` function which has a 500ms sleep between batches (line 166), the bootstrap batch loop has no delay between LLM calls. For projects with many commits (e.g., 200 commits = 10 batches), this could trigger OpenAI rate limits. The `condenseL3Node` comment says "Sleep to prevent rate limit" but the bootstrap loop lacks this protection.

**Finding 9: No test coverage for bootstrap batch mode.**

The integration test in `generate.test.ts` only tests the basic generate flow with 2 commits and `mode: "full"`. There is no test that:

- Verifies batching behavior with >20 commits
- Verifies `previousL2Names` is passed correctly across batches
- Verifies the bootstrap vs. path-rule mode branching
- Tests the `confirm-bootstrap` endpoint

The MSW mock in `openai.ts` handles the L2/L3 generation prompt, but the test only uses 2 commits (well below the batch size of 20), so the batch loop is never exercised.

## Round 3 — Integration & Completeness Review

**Finding 10: Confirm-bootstrap endpoint is implemented and wired.**

The `POST /projects/:id/l2-nodes/confirm-bootstrap` endpoint (`l2_nodes.ts:33-156`) correctly:

1. Updates approved modules with `isBootstrapConfirmed: true` and `pathPatterns` (lines 48–56)
2. Handles rejected modules by reassigning commits to `sys-uncategorized` and deleting rejected L2 nodes (lines 59–96)
3. Writes `.docuvia/config.yaml` with sorted module path patterns (lines 98–149)

This endpoint is defined in the OpenAPI spec at `openapi.yaml:251`.

**Finding 11: The `commit_l2_links` junction table is created and used.**

The schema (`commit_l2_links.ts`) correctly models the many-to-many relationship. In the bootstrap path, commits are assigned via `commitL2LinksTable` inserts (line 853–858). In the path-rule mode, the same table is used (line 852–858). The `commits.l2NodeId` column is still updated (line 847–850) for backward compatibility, though ADR-010 says it's deprecated.

**Finding 12: No `reindexRequired` flag usage in the bootstrap flow.**

ADR-010 states: "Historical `commit_l2_links` rows are flagged with `reindexRequired: true` and retroactively corrected on the next generate run." The schema has the column (line 23 of `l2_nodes.ts`), but the `generate.ts` code never sets `reindexRequired = true` on any L2 node or commit_l2_links row. This part of the ADR-010 consequence is not implemented.

## Gaps & Recommendations

1. **Add code-level cross-batch deduplication** in the bootstrap loop (`generate.ts:880-884`): before pushing to `l2Input`, check if a module name already exists in the accumulated results from previous batches. This provides a hard guarantee beyond the LLM-level soft constraint.

2. **Add rate limiting between batch LLM calls** in the bootstrap loop (`generate.ts:885`): add a configurable delay (e.g., 500ms) between batches to prevent 429 errors, matching the pattern already used in `condenseL3Node()`.

3. **Implement `reindexRequired` flag logic** (`generate.ts`): when bootstrap is confirmed and path patterns are saved, existing `commit_l2_links` rows should be flagged for reindexing so the next generate run can retroactively correct L2 assignments using the new path rules.

4. **Add integration tests for bootstrap batch mode**: create a test with >20 commits that verifies the batch loop executes multiple iterations, `previousL2Names` grows across batches, and the bootstrap vs. path-rule branching works correctly. Also add a test for the `confirm-bootstrap` endpoint.
