# Verification Report: Item 4.2.2 — AI Self-Correction Across Batches

**Item ID:** 4.2.2
**Description:** AI self-correction across batches
**Date:** 2026-06-19
**Verdict:** ⚠️ WARN

## Design Spec References

- `docs/design/09-architectural-decisions.md` — ADR-010: L2 Bootstrap — AI Discovery to Path Rules (lines 243–266)
- `docs/design/12-glossary.md` — "L2 Bootstrap" definition

ADR-010 specifies: "Each batch's LLM prompt includes the L2 module list produced by previous batches, enabling the AI to self-correct module names and boundaries across batches (automatic, no human review needed for cross-batch merges)."

The item 4.2.2 specifically covers the **self-correction** aspect — the mechanism by which the AI maintains consistency of module names and boundaries across the progressive batches.

## Round 1 — Architecture & Design Review

**Finding 1: `previousL2Names` mechanism is the core self-correction vehicle.**

In `generate.ts:246-249`, the `generateL2Nodes()` function builds a `previousBatchSection` that is injected into the LLM prompt:

```typescript
const previousBatchSection =
  previousL2Names && previousL2Names.length > 0
    ? `\n\nL2 modules discovered in previous batches (maintain consistency with these names): ${previousL2Names.join(", ")}`
    : "";
```

This is appended to the user message at line 261 alongside the commit list, L1 tags, document context, and few-shot correction examples. The instruction "maintain consistency with these names" is the self-correction directive.

**Finding 2: The bootstrap loop correctly accumulates and passes `previousL2Names`.**

In `generate.ts:864-887`, the bootstrap loop:
1. Initializes `previousL2Names` as an empty array (line 867)
2. For each batch, calls `generateL2Nodes()` with `previousL2Names` (line 878)
3. After each batch, appends newly discovered unique module names to `previousL2Names` (lines 880–883)

This means batch 1 gets no previous names, batch 2 gets batch 1's names, batch 3 gets batches 1+2's names, etc. — exactly as ADR-010 requires.

**Finding 3: Few-shot correction examples provide a second self-correction channel.**

The `getRecentCorrections()` function (lines 88–104) queries the `correction_examples` table for the 5 most recent human corrections for `entityType = "l2_node"`. These are formatted by `buildFewShotSection()` (lines 106–117) as:

```
Previous human corrections (use these as quality guidance):
Example 1:
  Original: "..."
  Corrected: "..."
```

This few-shot section is included in every batch's LLM prompt (line 245), providing human-correction-based self-correction across all batches, not just the cross-batch name consistency.

**Finding 4: The self-correction is LLM-level only — no code-level enforcement.**

The self-correction relies entirely on the LLM following the "maintain consistency" instruction. There is no code-level mechanism to:
- Detect if the LLM returned a renamed/duplicate module across batches
- Merge or rename L2 nodes that are semantically equivalent but named differently
- Validate that the LLM actually used the `previousL2Names` list

The `previousL2Names` array is used only for prompt construction and for deduplication against the DB (lines 880–883 check `!previousL2Names.includes(node.name)`), but this dedup is case-sensitive exact match only — it won't catch "AuthModule" vs "auth-module" vs "AuthenticationModule".

**Finding 5: The L2 system prompt does not explicitly mention self-correction.**

The default `l2_extractor` prompt in `templates.ts:16-40` describes the JSON schema and confidence scoring but does not include explicit instructions about maintaining consistency with previously discovered modules. The self-correction instruction is only in the dynamic `previousBatchSection` appended to the user message. This means:
- If a custom prompt template overrides the default, the self-correction behavior depends entirely on the `previousBatchSection` being present in the user message
- The system prompt itself doesn't reinforce the self-correction behavior

## Round 2 — Code Quality & Security Review

**Finding 6: Case-sensitive dedup is a gap.**

At line 881, the dedup check is `!previousL2Names.includes(node.name)` — a case-sensitive exact string match. If batch 1 produces "AuthModule" and batch 2 produces "authmodule" or "Auth-Module", both will be added to `previousL2Names` and both will be passed to subsequent batches, defeating the self-correction purpose. A case-insensitive comparison (or normalized comparison) would be more robust.

**Finding 7: No validation of LLM response structure for self-correction.**

The `generateL2Nodes()` function parses the LLM response with a regex JSON extraction (line 268: `content.match(/\[[\s\S]*\]/)`) and falls back to `[]` on parse failure. If the LLM returns malformed JSON or an unexpected structure, the function silently returns an empty array. There is no validation that the returned objects have a `name` field — if the LLM omits `name`, the `node.name` access at line 881 would be `undefined`, which would be added to `previousL2Names` as the string `"undefined"`.

**Finding 8: No rate limiting between batch LLM calls.**

As noted in the 4.2.1 verification report, the bootstrap batch loop has no delay between LLM calls. For projects with many commits, this could trigger OpenAI rate limits (HTTP 429), causing batch failures that would break the self-correction chain. If batch 3 fails, batches 4+ would lose the accumulated `previousL2Names` from batch 3.

**Finding 9: No retry logic for failed batches.**

If `generateL2Nodes()` throws (e.g., network error, OpenAI 429/500), the entire bootstrap loop fails and the generate request returns a 500. There is no retry with exponential backoff for individual batches, and no partial-success handling.

**Finding 10: Few-shot corrections are limited to 5 examples with no relevance ranking.**

`getRecentCorrections()` uses `.limit(5)` with `.orderBy(createdAt desc)` — it takes the 5 most recent corrections regardless of relevance to the current batch's commits. For self-correction quality, semantic relevance would be more effective than recency, but this is a minor concern.

## Round 3 — Integration & Completeness Review

**Finding 11: No test coverage for self-correction behavior.**

The integration test in `generate.test.ts` uses only 2 commits (well below the batch size of 20), so the bootstrap batch loop executes only a single iteration. There is no test that:
- Verifies `previousL2Names` is passed correctly to the second batch
- Verifies the `previousBatchSection` appears in the LLM prompt for batches after the first
- Verifies few-shot corrections are included in batch prompts
- Tests the self-correction behavior with >20 commits (triggering multiple batches)
- Tests that duplicate module names across batches are handled

The MSW mock in `openai.ts` always returns the same hardcoded response (`module1`), so even if >20 commits were used, the mock wouldn't exercise self-correction logic.

**Finding 12: The confirm-bootstrap endpoint does not validate self-correction quality.**

The `POST /projects/:id/l2-nodes/confirm-bootstrap` endpoint (`l2_nodes.ts:33-156`) accepts the human's approval/rejection of discovered modules but does not:
- Report any metrics about cross-batch consistency (e.g., "3 modules were renamed across batches")
- Flag potential duplicates for human review
- Provide a diff of what changed between batches

This means the human reviewer has no visibility into whether the self-correction worked well or poorly.

**Finding 13: The `previousBatchSection` prompt instruction is weak.**

The instruction "maintain consistency with these names" is a soft suggestion. A stronger instruction might be:
- "You MUST use these exact module names when the same component appears in new commits"
- "If you discover a new module that is similar to an existing one, use the existing name instead of creating a new one"
- "Do NOT create duplicate or renamed variants of already-discovered modules"

The current wording leaves room for the LLM to interpret "maintain consistency" loosely.

## Gaps & Recommendations

1. **Add case-insensitive deduplication** in the bootstrap loop (`generate.ts:881`): normalize module names to lowercase before comparing and storing in `previousL2Names`. Consider also normalizing hyphens/underscores.

2. **Validate LLM response structure** in `generateL2Nodes()` (`generate.ts:267-272`): after parsing, filter out any items missing a `name` field and log a warning. This prevents `undefined` from polluting `previousL2Names`.

3. **Add rate limiting and retry logic** to the bootstrap loop (`generate.ts:869-886`): add a configurable delay (e.g., 500ms) between batches and retry up to 3 times on transient failures (429, 500), matching the pattern already used in `condenseL3Node()`.

4. **Strengthen the self-correction prompt instruction** (`generate.ts:248`): change "maintain consistency with these names" to a more explicit directive like "You MUST use these exact module names when the same component appears. Do NOT create duplicate or renamed variants."

5. **Add integration tests for self-correction**: create a test with >20 commits that verifies:
   - `previousL2Names` grows across batches
   - The `previousBatchSection` appears in batch 2+'s prompt
   - Duplicate module names are deduplicated
   - Few-shot corrections are included in all batch prompts

6. **Add cross-batch consistency metrics** to the confirm-bootstrap response (`l2_nodes.ts`): report how many modules were discovered, how many were renamed/merged across batches, and flag potential duplicates for human review.
