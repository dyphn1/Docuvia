# Verification Report: Item 4.2.3 — L2 Module Map Confirmation UI

**Item ID:** 4.2.3  
**Description:** L2 module map confirmation UI  
**Date:** 2026-06-19  
**Verdict:** ⚠️ WARN

## Design Spec References

- `docs/design/09-architectural-decisions.md` — ADR-010: L2 Bootstrap — AI Discovery to Path Rules (lines 243–266)
- `docs/design/12-glossary.md` — "L2 Bootstrap" and "Path Pattern" definitions

ADR-010 specifies: "After all batches complete, the system presents the discovered L2 module map to the project manager for confirmation." Upon confirmation, L2 module boundaries are written as glob path patterns to `.docuvia/config.yaml`, and all future commits are assigned to L2 modules deterministically by path matching.

Item 4.2.3 specifically covers the **confirmation UI** — the interface through which the project manager reviews, approves, rejects, and edits the AI-discovered L2 module map.

## Round 1 — Architecture & Design Review

**Finding 1: The L2BootstrapReview component is a fully functional confirmation UI.**

The component at `L2BootstrapReview.tsx` provides:

- **Listing of unconfirmed modules** (line 72): Filters `l2Nodes` for `aiGenerated && !isBootstrapConfirmed`
- **Grouping by L1 tag** (lines 45–61): Groups discovered modules under their parent L1 tag using a `groupedNodes` memoized map, providing the "module map" view
- **Per-module approve/reject decisions** (lines 202–219): Each module card has Approve and Reject buttons with visual state (green border for approved, red for rejected, blue for pending)
- **Path pattern editing** (lines 222–230): Each module has an editable text input for glob path patterns, pre-populated with `node.pathPatterns`
- **Approve All shortcut** (lines 83–89): One-click action to approve all unconfirmed modules
- **Submit action** (lines 91–119): Calls `confirmBootstrap` mutation with `approvedModules` (id + pathPatterns) and `rejectedModuleIds`
- **Empty state** (lines 74–81): Shows "No new modules require confirmation" when no unconfirmed nodes exist

This matches ADR-010's requirement: "the system presents the discovered L2 module map to the project manager for confirmation."

**Finding 2: The confirmation UI is integrated into the project detail page as a tab.**

In `[id].tsx` (lines 569–575), the `L2BootstrapReview` component is rendered in a "Bootstrap Review" tab that:

- Only appears when `unconfirmedCount > 0` (line 379) — i.e., there are AI-generated L2 nodes awaiting confirmation
- Shows a badge with the count of unconfirmed modules (line 387)
- Uses an orange-themed visual style to draw attention (lines 381–382)

**Finding 3: The backend confirm-bootstrap endpoint correctly handles confirmation.**

The `POST /projects/:id/l2-nodes/confirm-bootstrap` endpoint (`l2_nodes.ts:33-156`):

1. Updates approved modules with `isBootstrapConfirmed: true` and new `pathPatterns` (lines 48–56)
2. Reassigns rejected modules' commits to a `sys-uncategorized` node, then deletes rejected L2 nodes (lines 58–96)
3. Writes confirmed module path patterns to `.docuvia/config.yaml` using glob specificity sorting (lines 99–149)

**Finding 4: The confirmation UI lacks module-level detail for informed decisions.**

The ADR-010 spec says the system should present "the discovered L2 module map" for confirmation. The current UI shows:

- Module name ✅
- L1 tag grouping ✅
- Description ✅ (line 200)
- Path patterns (editable) ✅
- Existing vs. new badge ✅

But it does **not** show:

- **Which commits contributed to this module** — The reviewer cannot see which files/commits the AI used to discover this module, making it impossible to verify correctness
- **Related L3 nodes count or preview** — No indication of how much L3 knowledge is scoped under this L2 node, which would help the reviewer understand the impact of rejection
- **Confidence score** — The `l2_nodes` table has no confidence column (unlike L3 nodes), so the AI's certainty is not communicated
- **Batch origin** — No indication of which batch discovered this module, which could help identify early-batch errors

**Finding 5: The confirmation UI does not handle the rejection workflow well.**

When a module is rejected:

- The UI sends the module ID in `rejectedModuleIds`
- The backend reassigns commits to a "sys-uncategorized" node and deletes the L2 node
- But the UI provides no explanation of what rejection means, no undo capability, and no confirmation dialog

A rejected module's commits are silently moved to "Uncategorized" — the reviewer may not realize the scope of this action. There is no warning like "Rejecting this module will move N commits to Uncategorized."

## Round 2 — Code Quality & Security Review

**Finding 6: The `groupedNodes` logic assumes single L1 tag per module.**

At line 52: `const tagId = node.l1TagIds?.[0]` — the code takes only the first L1 tag. For modules linked to multiple L1 tags, the module will only appear under the first tag's group. This is a simplification that could confuse reviewers if multi-tag modules exist.

**Finding 7: No client-side validation before submit.**

The `handleSubmit` function (lines 91–119) checks that at least one decision has been made (line 108), but does not validate:

- That path patterns are non-empty for approved modules (a module can be approved with empty path patterns)
- That path patterns are valid glob syntax
- That the user has reviewed all unconfirmed modules (they can approve/reject a subset)

**Finding 8: Path pattern input uses comma-separated values, not the storage format.**

At line 100: `customPath.split(",").map(s => s.trim()).filter(Boolean)` — the UI stores path patterns as a comma-separated string in the input field, while the backend stores them as a JSONB array. This split/join conversion is fragile: if a glob pattern itself contains a comma (e.g., `src/{a,b}/**`), it will be incorrectly split.

**Finding 9: The backend writes config.yaml to `project.repoUrl`.**

At line 143: `const configDir = path.join(project.repoUrl, ".docuvia")` — this uses `repoUrl` which is typically a remote URL (e.g., `https://github.com/...` or a local path). If `repoUrl` is a remote URL, `fs.writeFile` will fail. This is a pre-existing issue noted in other verification reports but affects the confirmation flow because a failed config write does not prevent the endpoint from returning `success: true` (it just logs the error at line 153).

**Finding 10: No activity log entry for bootstrap confirmation.**

The confirm-bootstrap endpoint does not insert into `activity_log` after successful confirmation. Compare with the L2 create endpoint (lines 183–187) which does log. This means there is no audit trail for bootstrap confirmation actions.

## Round 3 — Integration & Completeness Review

**Finding 11: No test coverage for the L2BootstrapReview component.**

There are no unit tests for `L2BootstrapReview.tsx`. The component:

- Has no `*.test.tsx` file
- Has no snapshot test
- Is not covered by any E2E test

**Finding 12: No integration test for the confirm-bootstrap endpoint.**

No test file in `artifacts/api-server/test/` covers the `POST /projects/:id/l2-nodes/confirm-bootstrap` endpoint. The endpoint's commit reassignment logic, config.yaml writing, and rejection flow are all untested.

**Finding 13: The confirmation UI is only in the web frontend, not in the VS Code extension.**

The ADR-010 says the module map is presented to the "project manager for confirmation." The current implementation only provides this UI in the kg-engine web frontend (`[id].tsx`). The VS Code extension has no equivalent confirmation interface. Given that the VS Code extension is the primary client (per the "Local-First Architecture" in Milestone 2), this is a significant gap — VS Code users would need to switch to the web UI to confirm L2 modules.

**Finding 14: The "Approve All" button does not populate path patterns for modules with empty patterns.**

When "Approve All" is clicked (lines 83–89), all modules are marked as "approve" but no path pattern editing occurs. If a module has empty `pathPatterns` (which is possible since `pathPatterns` is nullable in the schema), it will be submitted with an empty array. The backend will then write a config.yaml with empty path patterns, which defeats the purpose of deterministic commit-to-module assignment.

**Finding 15: The UI does not refresh after submission.**

The `onSuccess` callback (lines 32–34) invalidates the L2 nodes query, which triggers a re-fetch. However, the local `decisions` and `pathEdits` state is not reset after submission. If the re-fetch returns the same data (e.g., due to caching), the UI may still show the old decisions. The component should reset local state on successful submission.

## Gaps & Recommendations

1. **Add module detail to confirmation cards** (`L2BootstrapReview.tsx`): Show commit count and L3 node count for each module. Consider linking to a detail view or showing a preview of contributing commits. This gives the reviewer context to make informed decisions.

2. **Add rejection confirmation dialog** (`L2BootstrapReview.tsx`): Before submitting with rejections, show a confirmation dialog explaining that rejected modules' commits will be moved to "Uncategorized."

3. **Fix comma-containing glob handling** (`L2BootstrapReview.tsx:224-229`): Instead of comma-separated input, use one input per path pattern with an "Add Pattern" button, or usenewline-separated values. This prevents splitting globs that contain commas.

4. **Add client-side validation** (`L2BootstrapReview.tsx:91-119`):
   - Require non-empty path patterns for approved modules
   - Warn if not all modules have been decided
   - Validate glob syntax before submission

5. **Add activity log entry** (`l2_nodes.ts:151`): After successful confirmation, insert into `activity_log` with type `bootstrap_confirmed` describing how many modules were approved/rejected.

6. **Add tests**:
   - Unit tests for `L2BootstrapReview.tsx` covering approve, reject, approve-all, submit with mixed decisions
   - Integration test for `POST /projects/:id/l2-nodes/confirm-bootstrap` covering approval, rejection, commit reassignment, and config.yaml writing

7. **Add VS Code extension confirmation UI**: Implement a QuickPick or Webview panel in the VS Code extension that provides equivalent L2 module map confirmation, so VS Code-only users don't need to switch to the web frontend.

8. **Reset local state on success** (`L2BootstrapReview.tsx:32-34`): In the `onSuccess` callback, call `setDecisions({})` and `setPathEdits({})` to clear the form after successful submission.
