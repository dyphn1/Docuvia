# Verification Report: Item 4.2.4 — Path Pattern Storage in .docuvia/config.yaml

**Item ID:** 4.2.4
**Description:** Path pattern storage in .docuvia/config.yaml
**Date:** 2026-06-19
**Verdict:** ⚠️ WARN

## Design Spec References

- `docs/design/09-architectural-decisions.md` — ADR-010: L2 Bootstrap — AI Discovery to Path Rules (lines 243–266)
- `docs/design/10-quality-requirements.md` — Quality scenarios for knowledge persistence

ADR-010 specifies: "Upon human confirmation: L2 module boundaries are written as glob path patterns to `.docuvia/config.yaml` under `modules:`. All future commits are assigned to L2 modules deterministically by path matching — LLM is no longer used for L2 assignment."

Item 4.2.4 specifically covers the **persistence** aspect — whether path patterns are correctly stored in `.docuvia/config.yaml` after bootstrap confirmation.

## Round 1 — Architecture & Design Review

**Finding 1: Path pattern storage to config.yaml is implemented in the confirm-bootstrap endpoint.**

The `POST /projects/:id/l2-nodes/confirm-bootstrap` endpoint (`l2_nodes.ts:98-149`) writes path patterns to `.docuvia/config.yaml`:

1. Queries all bootstrap-confirmed L2 nodes for the project (lines 99–107)
2. Computes glob specificity depth for each module's path patterns (lines 111–123)
3. Sorts modules by depth descending (line 133) — more specific patterns first
4. Constructs a YAML structure with a `modules:` array containing `{id, name, pathPatterns}` (lines 135–141)
5. Writes to `<repoUrl>/.docuvia/config.yaml` using `js-yaml` dump (lines 143–148)

This matches ADR-010's requirement: "L2 module boundaries are written as glob path patterns to `.docuvia/config.yaml` under `modules:`."

**Finding 2: The generate pipeline reads path patterns for deterministic assignment.**

In `generate.ts` (lines 766–797), when all L2 nodes are bootstrap-confirmed (`allBootstrapConfirmed`), the pipeline:

1. Fetches existing L2 nodes with their `pathPatterns` from the database (line 756–759)
2. Sorts them by glob depth descending (lines 795–797) — matching the same specificity algorithm used in config.yaml writing
3. Converts glob patterns to RegExp for matching (line 799+)
4. Assigns commits to L2 modules based on file path matching against these patterns

This confirms the path patterns stored in the DB are used for deterministic commit-to-module assignment, as ADR-010 requires.

**Finding 3: The config.yaml write uses `project.repoUrl` as the base directory.**

At `l2_nodes.ts:143`: `const configDir = path.join(project.repoUrl, ".docuvia")`

This is a critical issue: `repoUrl` is typically a remote URL (e.g., `https://github.com/org/repo`) or a local filesystem path. If it's a remote URL, `fs.writeFile` will fail because `path.join("https://github.com/org/repo", ".docuvia")` produces an invalid filesystem path. The `fs.mkdir` with `{ recursive: true }` may silently succeed (creating a local directory with a mangled name), or the `fs.writeFile` will throw.

This is a **pre-existing issue** also noted in the 4.2.3 verification report, but it directly impacts 4.2.4 because the config.yaml write is the core of this item.

**Finding 4: The config.yaml write failure does not fail the confirmation request.**

The config.yaml writing code (lines 109–149) is not wrapped in a try-catch. If `fs.writeFile` throws (e.g., because `repoUrl` is a remote URL), the error propagates to the outer catch block (line 152), which returns a 500 error. However, by that point, the database has already been updated (approved modules marked as confirmed, rejected modules deleted). This means the DB state changes are persisted but the config.yaml is not written, and the user gets a generic "Internal server error" — even though the confirmation was partially applied.

There is no transaction wrapping both the DB updates and the file write, so a partial failure leaves the system in an inconsistent state.

**Finding 5: The config.yaml structure matches the ADR-010 specification.**

The YAML structure written (lines 135–141):

```yaml
modules:
  - id: 1
    name: "Authentication"
    pathPatterns:
      - "src/auth/**/*.ts"
      - "src/middleware/*.ts"
```

This is a clean, human-readable format that ADR-010 describes as "human-readable and editable without re-running AI." The `id` field links back to the database record, `name` is the module name, and `pathPatterns` is an array of glob patterns.

## Round 2 — Code Quality & Security Review

**Finding 6: Glob specificity sorting algorithm is duplicated.**

The `getStaticDepth` and `getMaxDepth` functions appear in both:

- `l2_nodes.ts:111-123` (config.yaml writing)
- `generate.ts:781-793` (path-rule mode assignment)

This duplication means if the sorting algorithm changes in one place, it may not be updated in the other, leading to inconsistent behavior between what's stored in config.yaml and how the generate pipeline assigns commits.

**Finding 7: No validation of path patterns before writing to config.yaml.**

The confirm-bootstrap endpoint writes whatever path patterns it receives from the frontend without validating:

- That patterns are valid glob syntax
- That patterns are non-empty strings
- That patterns don't contain path traversal sequences (e.g., `../../../etc/passwd`)

While glob patterns are generally harmless, writing unsanitized user input to a file on the server filesystem is a security concern. The patterns come from the `L2BootstrapReview` component's editable text input, which means a user could enter arbitrary strings.

**Finding 8: The config.yaml is written to the server's local filesystem, not to the git repo.**

The `repoUrl` field in the `projects` table is described as the repository URL. The config.yaml is written to `<repoUrl>/.docuvia/config.yaml` on the server's local filesystem. However, ADR-008 specifies that `.docuvia/` is a working tree directory that should be committed to the source repo. The current implementation writes to the server's view of the repo, which may not be the same as the developer's working tree.

If the server has a bare clone or a separate working copy, the config.yaml written there won't be visible to developers unless it's committed and pushed back. The orphan branch writer (`orphan-branch-writer.ts`) is the mechanism for writing to the git repo, but the confirm-bootstrap endpoint doesn't use it for config.yaml.

**Finding 9: No test coverage for config.yaml writing.**

There are no unit or integration tests that verify:

- The config.yaml file is created with correct content
- The glob specificity sorting produces the correct order
- The config.yaml write handles edge cases (empty patterns, special characters, unicode module names)
- The behavior when `repoUrl` is invalid or unreachable

## Round 3 — Integration & Completeness Review

**Finding 10: The config.yaml is written but never read back.**

The confirm-bootstrap endpoint writes `config.yaml` to disk, and the generate pipeline reads path patterns from the **database** (`l2NodesTable.pathPatterns`), not from the config.yaml file. This means:

1. The config.yaml file is written but serves no functional purpose in the current codebase
2. The ADR-010 statement that path patterns are "human-readable and editable without re-running AI" is only partially fulfilled — the file exists, but editing it would have no effect because the system reads from the DB
3. The config.yaml is essentially a one-way export, not a configuration source

This is a significant design gap: ADR-010 implies that `.docuvia/config.yaml` is the source of truth for path patterns after bootstrap, but the actual source of truth remains the database.

**Finding 11: The frontend sends path patterns from user input, not from the DB.**

In `L2BootstrapReview.tsx` (lines 98–101), when the user submits:

```typescript
const customPath = pathEdits[node.id];
const patterns = customPath
  ? customPath
      .split(",")
      .map((s) => s.trim())
      .filter(Boolean)
  : node.pathPatterns || [];
```

The path patterns sent to the backend come from:

1. User-edited text input (comma-separated), if the user modified them
2. The original `node.pathPatterns` from the database, if unedited

The comma-separated parsing is fragile (as noted in 4.2.3's report) — glob patterns containing commas will be incorrectly split. This means the config.yaml could contain malformed patterns even if the DB had correct ones.

**Finding 12: No integration between config.yaml writing and the orphan branch.**

ADR-008 establishes the `docuvia-knowledge` orphan branch as the canonical knowledge store. The `.docuvia/` directory (including `config.yaml`) is described as a "lightweight manifest" that points to the orphan branch HEAD. However, the confirm-bootstrap endpoint writes config.yaml directly to the filesystem without going through the orphan branch writer. This means:

1. The config.yaml is not versioned in git
2. Other developers cannot fetch it via `git fetch origin docuvia-knowledge`
3. The config.yaml is lost if the server's local filesystem is reset

**Finding 13: The config.yaml write does not create the `.docuvia/` directory if it doesn't exist.**

Actually, it does — `fs.mkdir(configDir, { recursive: true })` at line 144 handles this. However, if `repoUrl` is a remote URL, this creates a local directory with a mangled name like `https:/github.com/org/repo/.docuvia/` (note: `path.join` collapses `://`).

## Gaps & Recommendations

1. **Fix `repoUrl` handling for config.yaml writing** (`l2_nodes.ts:143`): Use a local working directory path instead of `repoUrl`. The server should maintain a working copy of each project repo, or the config.yaml should be written to the orphan branch via the orphan branch writer.

2. **Wrap DB + file write in a transaction** (`l2_nodes.ts:33-156`): Either make the file write part of a compensating transaction pattern, or write the config.yaml first and roll back on failure. At minimum, if the file write fails, revert the DB changes.

3. **Add path pattern validation** (`l2_nodes.ts:48-56`): Validate that path patterns are non-empty and contain valid glob syntax before writing to config.yaml. Consider using a glob validation library.

4. **Integrate config.yaml writing with the orphan branch** (`l2_nodes.ts:143-148`): Use the orphan branch writer to commit the config.yaml to the `docuvia-knowledge` branch, making it versioned and fetchable by other developers.

5. **Make config.yaml the source of truth** OR **remove the fiction that it is**: Either update the generate pipeline to read path patterns from config.yaml (making it a true config file), or document clearly that the DB is the source of truth and config.yaml is a read-only export.

6. **Extract glob sorting into a shared utility**: Create a shared module for `getStaticDepth` and `getMaxDepth` to avoid duplication between `l2_nodes.ts` and `generate.ts`.

7. **Fix comma-separated glob parsing** (`L2BootstrapReview.tsx:224-229`): Use one input per path pattern with an "Add Pattern" button, or use newline-separated values instead of comma-separated.

8. **Add tests**: Integration tests for the confirm-bootstrap endpoint that verify config.yaml content, sorting order, and error handling for invalid repo paths.
