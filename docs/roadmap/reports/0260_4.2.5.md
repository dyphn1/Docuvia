# Verification Report: Item 4.2.5 — Deterministic Commit-to-Module Assignment via Glob Matching

**Item ID:** 4.2.5
**Description:** Deterministic commit-to-module assignment via glob matching
**Date:** 2026-06-19
**Verdict:** ⚠️ WARN

## Design Spec References

- `docs/roadmap/completion_action_plan.md` — Item 4.2.5: Deterministic Glob Path Assignment (lines 44–48)
- `docs/design/09-architectural-decisions.md` — ADR-010: L2 Bootstrap — AI Discovery to Path Rules
- `docs/ai_plans/implement_v2-core-architecture.md` — Phase 3.2: `KnowledgeStore.ts` rewrite, Phase 4.4: Offline CodeLens

The completion_action_plan.md specifies:
> **The Trap:** Ambiguous or overlapping globs (`src/**/*.ts` vs `src/api/**/*.ts`) cause random commit assignments.
> **The Implementation:** Implement a **Glob Specificity Algorithm**: Score rules by the depth of static path segments (e.g., `src/api/` wins over `src/`). When saving to `.docuvia/config.yaml`, pre-sort the path array by this specificity score descending. During ingestion, the first matching pattern in the array wins, guaranteeing O(1) determinism.

ADR-010 states: "All future commits are assigned to L2 modules deterministically by path matching — LLM is no longer used for L2 assignment."

Item 4.2.5 specifically covers the **deterministic assignment** aspect — whether the glob matching algorithm correctly and deterministically assigns commits to L2 modules after bootstrap confirmation.

## Round 1 — Architecture & Design Review

**Finding 1: Path-rule mode with glob-to-RegExp matching is implemented in generate.ts.**

When all L2 nodes are bootstrap-confirmed (`allBootstrapConfirmed = true`), the generate pipeline enters "path-rule mode" (`generate.ts:771–863`):

1. Fetches existing L2 nodes with their `pathPatterns` from the database (lines 756–759).
2. Sorts them by glob specificity depth descending (lines 795–797) — more specific patterns first.
3. Converts glob patterns to RegExp using a custom `globToRegExp` function (lines 799–803):
   ```typescript
   const globToRegExp = (glob: string): RegExp => {
     const escaped = glob.replace(/[.+^${}()|[\]\\]/g, "\\$&");
     const regexStr = escaped.replace(/\\\*\*\*/g, ".*").replace(/\\\*/g, "[^/]*").replace(/\\\?/g, ".");
     return new RegExp(`^${regexStr}$`);
   };
   ```
4. Iterates over each commit's modified files, matching against sorted patterns (lines 827–841).
5. First match wins (due to specificity-sorted order), guaranteeing deterministic assignment.
6. Unmatched commits fall through to `sys-uncategorized` (line 844).

This design matches the completion_action_plan.md requirement: "the first matching pattern in the array wins, guaranteeing O(1) determinism."

**Finding 2: The glob specificity algorithm is correctly implemented.**

The specificity scoring (`generate.ts:781–793`):
```typescript
const getStaticDepth = (pattern: string): number => {
  let depth = 0;
  for (const part of pattern.split("/")) {
    if (/[*?{}[\]]/.test(part)) break;
    if (part) depth++;
  }
  return depth;
};
```
This counts static path segments before the first wildcard. For example:
- `src/api/controllers/` → depth 3
- `src/` → depth 1
- `**/*.ts` → depth 0

Sorting descending ensures `src/api/controllers/` matches before `src/`, which is correct.

**Finding 3: A SECOND, incompatible path-matching approach exists in the same file.**

At `generate.ts:470–474`, the L3 scoring logic uses a completely different approach:
```typescript
if (sourceFile && node.pathPatterns) {
  const patterns = node.pathPatterns as string[];
  if (patterns.some((p: string) => sourceFile.startsWith(p) || sourceFile === p)) {
    scoreW3 = 1;
  }
}
```
This uses `startsWith` — a simple prefix check that does NOT handle glob wildcards. A pattern like `src/**/*.ts` would only match files literally starting with the string `src/**/*.ts`, which is never a valid file path. This means:
- The W3 path score in L3 scoring mode is effectively useless for glob patterns.
- The same `pathPatterns` field is interpreted differently by two different code paths.

**Finding 4: The commit_l2_links junction table is correctly used for deterministic assignment.**

In path-rule mode, assignments are written to both:
- `commitsTable.l2NodeId` (legacy column, line 848)
- `commitL2LinksTable` (new junction table, lines 852–858) with `.onConflictDoNothing()`

This is correct: `commit_l2_links` is the proper many-to-many junction table.

**Finding 5: The orphan branch writer is NOT involved in path-rule assignment.**

The path-rule mode assignments are written directly to the PostgreSQL database (lines 846–859). The orphan branch writer is not called. This means:
- The commit-to-module assignment is only in the DB, not in the git-isomorphic knowledge graph.
- VS Code clients reading from the orphan branch won't see these assignments.

## Round 2 — Code Quality & Security Review

**Finding 6: The `globToRegExp` function has escaping bugs.**

At `generate.ts:799–803`:
```typescript
const globToRegExp = (glob: string): RegExp => {
  const escaped = glob.replace(/[.+^${}()|[\]\\]/g, "\\$&");
  const regexStr = escaped.replace(/\\\*\*\*/g, ".*").replace(/\\\*/g, "[^/]*").replace(/\\\?/g, ".");
  return new RegExp(`^${regexStr}$`);
};
```

Issues:
1. **Order of operations bug**: The function first escapes ALL special chars (`*` → `\*`), then tries to replace the already-escaped sequences (`\*\*` and `\*` — but the escaped form is `\\*` not `\*`). The regex `/\\\*\*\*/g` tries to match `\*\*\*` (backslash-star-star-star), but after escaping, `**` becomes `\*\*` (backslash-star twice). The escaping pass already converted `*` to `\*`, so `**` became `\*\*`, and the subsequent `.replace(/\\\*\*\*/g, ".*")` tries to match the literal string `\*\*\*` which doesn't exist.

   Let me trace through an example: `src/**/*.ts`
   - After escape: `src/\*\*/\*.ts` (each `*` becomes `\*`, `.` becomes `\.`)
   - Try `.replace(/\\\*\*\*/g, ".*")` → looking for literal `\*\*\*` — NOT FOUND (we have `\*\*` then `/\*`)
   - Try `.replace(/\\\*/g, "[^/]*")` → replaces `\*` with `[^/]*`: `src/[^/]*/[^/]*\.ts`
   - Final regex: `^src/[^/]*/[^/]*\.ts$`

   For `src/**/*.ts`, this actually works by accident because `**` becomes two consecutive `\*` tokens, each replaced by `[^/]*`. But `src/a/**/b/*.ts` would also work the same way — two levels of directory matching.

2. **The pattern `**` (matching zero or more directories) is NOT correctly handled.** Standard glob semantics for `**` means "zero or more directory levels." Two consecutive `[^/]*` segments requires at least one directory level between them. A file like `src/b.ts` (where `**` should match zero directories) would NOT match `^src/[^/]*/[^/]*\.ts$` because the `/[^/]*/` part requires a `/something/` segment.

3. **Character class patterns `[...]` are not handled.** A glob like `src/[a-b]/file.ts` would have the `[` and `]` escaped by the first replace, making it `src/\[a-b\]/file.ts`, which would never match a real file path.

4. **Brace expansion `{a,b}` is not handled.** A glob like `src/{api,lib}/file.ts` would have `{` and `}` escaped.

**Finding 7: Glob specificity algorithm cannot distinguish patterns of equal depth.**

When two patterns have the same static depth, the sort order is unstable (JavaScript's `.sort()` is not guaranteed to be stable in all environments, though V8's is stable since Node 12). For example:
- `src/api/*.ts` → depth 2
- `src/lib/*.ts` → depth 2

If a file `src/api/helper.ts` matches both patterns, the assignment depends on which L2 node was inserted first. This is not deterministic in a meaningful sense — it's arbitrary.

**Finding 8: No validation of glob patterns before use.**

Neither the confirmBootstrap endpoint nor the generate pipeline validates that path patterns are syntactically valid globs before:
- Storing them in the database (`l2NodesTable.pathPatterns`)
- Writing them to config.yaml
- Converting them to RegExp for matching

Invalid patterns silently produce regexes that never match, leading to all commits falling through to `sys-uncategorized`.

**Finding 9: The CodeLens provider uses minimatch (correct) while the server uses custom RegExp (incompatible).**

In `DocuviaCodeLensProvider.ts:64–66`:
```typescript
m.path_patterns.some(pattern => minimatch(relPath, pattern, { matchBase: true }))
```

This uses the `minimatch` library — a well-tested, standards-compliant glob matching library. But the server's path-rule mode uses the custom `globToRegExp` function. The same glob pattern could produce different match results on the server vs. the client:
- `**/*.ts` on the server: converts to `[^/]*` which requires at least one char per segment
- `**/*.ts` in minimatch: correctly handles `**` as zero or more directories

This inconsistency means a commit assigned to Module A on the server might show as Module B via CodeLens.

## Round 3 — Integration & Completeness Review

**Finding 10: No tests exist for deterministic glob assignment.**

There are zero unit or integration tests covering:
- The `globToRegExp` function
- The `getStaticDepth` / `getMaxDepth` specificity scoring
- The path-rule mode assignment loop
- Overlapping glob patterns and precedence
- Edge cases: empty patterns, unicode paths, deeply nested paths, patterns with no wildcards
- The fallback to `sys-uncategorized`
- Consistency between server glob matching and VS Code client minimatch

**Finding 11: The `sourceFile` variable used in L3 scoring mode is not the same as the `files` variable in path-rule mode.**

At line 470, the W3 scoring checks `sourceFile` (singular) against `node.pathPatterns`. But at line 823, the path-rule mode iterates over `files` (plural, from `gitClient.getModifiedFiles(commit.hash)`). This means:

- Path-rule mode (bootstrap-confirmed): correctly checks ALL modified files in a commit
- L3 scoring mode (bootstrap NOT confirmed): only checks one `sourceFile`, missing other files in the same commit

A commit that changes both `src/auth/login.ts` and `src/api/routes.ts` would only be scored against one of them in L3 mode, potentially assigning it to the wrong module.

**Finding 12: The `sys-uncategorized` node creation is not atomic with the commit assignment.**

At `generate.ts:805–819`, if no `sys-uncategorized` node exists, one is created and pushed to `existingL2`. But this happens inside the `try` block for `gitClient.clone()`. If the node creation fails (e.g., DB constraint violation from a concurrent generate run), the error is caught by the outer `catch`, and no assignments are made at all.

Additionally, the `sys-uncategorized` node is inserted with `isBootstrapConfirmed: true`, which means once it exists, the `allBootstrapConfirmed` check will consider it confirmed. If ALL real L2 nodes were rejected/deleted, the system would enter path-rule mode with only `sys-uncategorized` confirmed, and every commit would match the first pattern (which is none, since sys-uncategorized has no pathPatterns), so all would fall through to `sys-uncategorized` — correct but vacuous behavior.

**Finding 13: The glob specificity algorithm is duplicated across two files.**

The `getStaticDepth` and `getMaxDepth` functions appear in:
- `l2_nodes.ts:111–123` (config.yaml writing in confirm-bootstrap)
- `generate.ts:781–792` (path-rule mode assignment)

This is the same duplication noted in the 4.2.4 report. If the algorithm changes in one place, the other becomes inconsistent.

**Finding 14: Path-rule mode does not validate that patterns exist before matching.**

At `generate.ts:830`, `patterns` is cast from `node.pathPatterns as string[]`. If `pathPatterns` is `null` (which is the default for L2 nodes created before bootstrap), the empty array fallback `|| []` at line 791 only applies to the depth calculation, not to the pattern iteration. However, line 830 does `const patterns = (node.pathPatterns as string[]) || []`, so null patterns are handled. This is correct but fragile — it relies on a TypeScript cast that bypasses type safety.

**Finding 15: The generate pipeline mixes two generations of L2 assignment in one function.**

The `generateL2` inner function handles:
1. Path-rule mode (lines 771–863): deterministic glob matching
2. Bootstrap mode (lines 865–887): AI batch discovery
3. L3 scoring (lines 440–489): weighted scoring for L3 node creation

All three use the same `l2Nodes` array but interpret `pathPatterns` differently. The scoring approach (W3) is vestigial from the AI-discovery era and should be removed now that path-rule mode exists.

## Gaps & Recommendations

1. **Replace custom `globToRegExp` with `minimatch` or `picomatch`** (`generate.ts:799–803`): The custom glob-to-RegExp function has subtle bugs with `**` (zero directories), character classes, and brace expansion. Use the same `minimatch` library already used by the VS Code client for consistency. This also fixes the server/client inconsistency (Finding 9).

2. **Remove or fix the W3 `startsWith` path matching** (`generate.ts:470–474`): The `sourceFile.startsWith(p)` check is incompatible with glob patterns. Either remove the W3 path score entirely (since path-rule mode handles L2 assignment before L3 scoring), or convert it to use the same glob matching as path-rule mode.

3. **Add glob pattern validation** (`l2_nodes.ts:48–56`): Validate path patterns are syntactically valid globs before storing in the database. Reject or warn on invalid patterns at the API level.

4. **Add tiebreaker for equal-depth patterns** (`generate.ts:795–797`): When two patterns have the same static depth, add a secondary sort key (e.g., pattern length, module ID, or alphabetical) to ensure fully deterministic ordering.

5. **Extract glob sorting into a shared utility**: Create a shared module for `getStaticDepth`, `getMaxDepth`, and `globToRegExp` to eliminate duplication between `l2_nodes.ts` and `generate.ts`.

6. **Add comprehensive tests**: Unit tests for `globToRegExp` (or the replacement library), `getStaticDepth`, specificity sorting, and the full path-rule mode assignment loop with overlapping patterns, edge cases, and the sys-uncategorized fallback.

7. **Integrate path-rule assignments with the orphan branch**: After deterministic L2 assignment, write the results to the `docuvia-knowledge` orphan branch so VS Code clients can read them without a server connection.

8. **Document the two path-matching modes**: Clearly document that path-rule mode (bootstrap-confirmed) uses glob matching, while bootstrap mode uses AI discovery. The L3 scoring W3 path check should be documented as deprecated or removed.
