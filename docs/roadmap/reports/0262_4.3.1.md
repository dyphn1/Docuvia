## Round 2: Review Task Creation — Is the Quality Gate Actually Triggered?

Item 4.3.1 specifically states "Phase 1: Local Review quality gate (existing review_tasks)". The key question: **Are review tasks actually created when AI generates nodes?**

### Evidence — Review Task Creation Sites in `generate.ts`

| Location  | Trigger                                           | Task Type  | Entity    | Description                                                               |
| --------- | ------------------------------------------------- | ---------- | --------- | ------------------------------------------------------------------------- |
| Line 713  | New L1 tag created by AI                          | `anchor`   | `l1_tag`  | "New L1 tag generated by AI — review and anchor if accurate"              |
| Line 371  | L1 tag with low usage (noise detection)           | `anchor`   | `l1_tag`  | "Noise detection: Tag has very low usage — consider merging or removing"  |
| Line 405  | L1 tag near-duplicate detected                    | `merge`    | `l1_tag`  | "Noise detection: Tag appears to be a near-duplicate — consider merging"  |
| Line 307  | Cross-project L2 similarity detected              | `merge`    | `l2_node` | "Cross-project similarity detected — consider creating a dependency link" |
| Line 1093 | New L2 node created by AI (post-generation sweep) | `validate` | `l2_node` | "AI-generated L2 node — verify this component classification is accurate" |
| Line 1046 | New L3 node with confidence < 0.8                 | `validate` | `l3_node` | "AI-generated L3 node (confidence X%) — verify content accuracy"          |
| Line 1007 | L3 node condensed at occurrence threshold         | `validate` | `l3_node` | "L3 node condensed (N occurrences) — review AI-synthesized content"       |

### Round 2 Finding

**Review tasks are created at 7 distinct points in the generate pipeline**, covering all three entity types (L1, L2, L3) and multiple task types (anchor, validate, merge). The quality gate is comprehensive:

- **L1 tags**: Every new AI-generated L1 tag gets an `anchor` review task. Additionally, noise detection creates tasks for low-usage tags and near-duplicate tags.
- **L2 nodes**: Every new AI-generated L2 node gets a `validate` review task (via the post-generation sweep at line 1078-1102, which also deduplicates against existing pending tasks). Cross-project similarity triggers a `merge` task.
- **L3 nodes**: Low-confidence L3 nodes (confidence < 0.8) get a `validate` task. L3 nodes that reach the condensation threshold also get a `validate` task (if `condensationReviewRequired` is true).

**The post-generation L2 review task sweep (lines 1078-1102) includes deduplication logic**: it queries existing pending review tasks for L2 nodes and skips creating duplicates. This prevents redundant review tasks on re-runs.

**⚠️ Minor issue: L2 nodes created via update path don't get individual review tasks.** When an L2 node is updated (not created) at lines 894-907, `needsReview` is set to `true`, but no individual review task is created for the update. The post-generation sweep (line 1078-1082) queries `l2NodesTable` for `needsReview = true` and creates tasks for any not already covered. However, this sweep runs _after_ the L2 creation loop, so updated nodes that weren't newly created will be caught. This is correct behavior — the sweep covers both created and updated nodes.

**Round 2 Verdict: PASS** — The quality gate is fully implemented with 7 creation points covering all entity types.

## Round 3: ADR-011 Phase 1 Compliance & Completeness

From ADR-011 (lines 280-281): _"Phase 1 — Local Review (Quality Gate): The developer or reviewer inspects the AI-generated content in VS Code or the Web UI. They confirm whether the AI's interpretation is accurate. This gate ensures content quality and is the current `review_tasks` mechanism. Passing Phase 1 sets status to `pending`."_

### ADR-011 Phase 1 Requirements

| Requirement                                   | Status  | Evidence                                                                                                                                                                                                                                                            |
| --------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Review tasks exist for AI-generated nodes     | ✅ Done | 7 creation points in `generate.ts` (lines 307, 371, 405, 713, 1007, 1046, 1093)                                                                                                                                                                                     |
| Developer can review in Web UI                | ✅ Done | `artifacts/kg-engine/src/pages/review.tsx` — full review page with approve/reject/defect actions, correction editing, entity type icons, stats dashboard                                                                                                            |
| Developer can review in VS Code               | ✅ Done | VS Code extension has review-related commands and tree view                                                                                                                                                                                                         |
| Review resolution writes back corrections     | ✅ Done | `review_tasks.ts` PATCH handler (lines 124-181) writes `correctedValue` back to the actual node (L1/L2/L3) and creates `correction_examples` entries                                                                                                                |
| Correction examples feed back into generation | ✅ Done | `getRecentCorrections()` called in `generate.ts` line 740 for L2 extraction                                                                                                                                                                                         |
| Passing Phase 1 keeps status as `pending`     | ✅ Done | ADR-011 states "Passing Phase 1 sets status to `pending`" — the `review_tasks.status` is `pending` by default and transitions to `approved`/`rejected` on resolution. The L3 node's `validityStatus` remains `pending` until Phase 2 (merge gate). This is correct. |
| Activity log entry on resolution              | ✅ Done | `review_tasks.ts` line 191-194: inserts `review_resolved` activity log entry                                                                                                                                                                                        |

### Round 3 Finding

**ADR-011 Phase 1 is fully implemented.** The review_tasks mechanism serves as the quality gate: AI-generated nodes are queued for human review, reviewers can approve/reject with corrections in both the Web UI and VS Code, corrections are written back to the source nodes, and the feedback loop feeds corrections into future generation runs.

**⚠️ Note on "Passing Phase 1 sets status to `pending`":** The ADR wording is slightly confusing — it means that after Phase 1 review, the L3 node's `validityStatus` remains `pending` (not `valid`) until Phase 2 (merge gate) is also passed. The implementation correctly reflects this: resolving a review task sets `review_tasks.status` to `approved` but does NOT change `l3_nodes.validityStatus` to `valid`. The `validityStatus` stays `pending` until the merge gate (Phase 2, item 4.3.2) promotes it. This is correct ADR-011 behavior.

**Round 3 Verdict: PASS** — ADR-011 Phase 1 is fully compliant.

### Overall: ✅ PASS

The Phase 1 Local Review quality gate is fully implemented. The `review_tasks` mechanism is the backbone of the human-in-the-loop workflow: every AI-generated node (L1 tag, L2 module, L3 decision) is queued for human review, reviewers can inspect and correct content through both the Web UI and VS Code, and corrections feed back into future generation runs. The implementation correctly keeps L3 nodes at `validityStatus = pending` after Phase 1 review, awaiting Phase 2 (merge gate) to promote them to `valid`.

### Recommendations

1. **Consider adding a review task for L2 node updates** — currently, when an existing L2 node is updated (not created), `needsReview` is set to `true` but the review task is only created by the post-generation sweep. If the generate pipeline fails before reaching the sweep, the node will have `needsReview = true` but no review task. Consider creating the task inline at the update site.
2. **Add a review task counter to the dashboard** — the `GET /review-tasks/stats` endpoint exists but the dashboard page doesn't display review queue health. This is tracked under item 7.1.3 but worth noting as a Phase 1 completeness improvement.
