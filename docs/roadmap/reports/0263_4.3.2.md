## Round 1 — Architecture & Design Review

**What the spec says:** The Merge Gate (Phase 2) should check whether source commits have been merged into the default branch. Two mechanisms are envisioned: (1) GitHub webhook on PR merge, and (2) periodic polling as fallback. L3 nodes from merged commits → `valid`; from abandoned branches → `orphaned`.

**What exists:**

1. **Webhook path (primary):** `github_webhooks.ts:255-291` — When `action === "closed" && isMerged`, the handler fetches PR commits via `fetchPrCommits()` and updates matching L3 nodes from `pending` → `valid` using `inArray(l3NodesTable.commitHash, prCommitHashes)`. This is correctly implemented and handles the main case.

2. **Polling fallback (secondary):** `metabolism.ts:27-82` — The `runMetabolism()` function queries pending L3 nodes older than 24 hours, groups by project, and calls `checkCommitInDefaultBranch()` for each node's `commitHash` using the GitHub Compare API. Merged commits → `valid`. This is a reasonable fallback.

3. **`checkCommitInDefaultBranch()` implementation:** `github-client.ts:116-135` — Uses `GET /repos/{owner}/{repo}/compare/{default}...{sha}`. Returns `true` when status is `"identical"` or `"behind"` (meaning default is ahead of or equal to the commit, i.e., the commit is an ancestor). This is correct.

**Architecture gaps:**

- **No orphaned status transition:** When a PR is closed without merging (`github_webhooks.ts:341-350`), the handler only sets `pullRequestsTable.state = "closed"`. It does NOT update associated L3 nodes to `orphaned`. The `orphaned` value in the validity enum is never written anywhere in the codebase. The metabolism fallback also only promotes to `valid` — it never sets `orphaned` either. This means abandoned-branch L3 nodes remain `pending` forever, polluting the knowledge graph — exactly the scenario ADR-011 was designed to prevent.

- **Metabolism not auto-triggered:** `metabolism.ts` exposes `GET /metabolism-tick` and `GET /admin/metabolism-tick` but there is no internal scheduler (`setInterval`, node-cron, etc.) that calls it automatically. The route is mounted at `router.use(metabolismRouter)` (`routes/index.ts:48`) but without an external cron hitting the endpoint, the polling fallback never runs. The merge-gate fallback is effectively dead code.

- **`branchName` column never populated:** The `commits` table has `branchName text` (`commits.ts:22`), and `git-client.ts:18,122-123` defines the field and reads it from `git branch --show-current`. However, the ingestion pipeline (`routes/ingest.ts`) and webhook handler (`github_webhooks.ts`) never write `branchName` to the DB. The column exists in schema but is always NULL, making it impossible to query commits by branch or implement branch-level orphaned detection.

## Round 2 — Code Quality & Security Review

**Webhook handler quality:**

- The webhook responds with 202 immediately and processes asynchronously via `setImmediate()` (`github_webhooks.ts:207`). This is correct for avoiding GitHub retry timeouts.
- HMAC-SHA256 signature validation is present (`github_webhooks.ts:30-35`) with timing-safe comparison. Good.
- Error handling in the `setImmediate` callback catches errors and marks PR analysis as failed (`github_webhooks.ts:353-365`). Adequate.

**Metabolism endpoint security:**

- `GET /metabolism-tick` has NO authentication — anyone can trigger it (`metabolism.ts:150-166`). This is an unauthenticated endpoint that runs expensive GitHub API calls and DB updates. In production this could be abused for DoS.
- `GET /admin/metabolism-tick` has token-based auth via `ADMIN_SECRET_TOKEN` env var or query param (`metabolism.ts:168-200`). The dev fallback to `"dev-secret-token"` is acceptable for development but should be documented as a deployment risk.

**`checkCommitInDefaultBranch` correctness:**

- The GitHub Compare API endpoint `/compare/{base}...{sha}` with `base=defaultBranch` and `head=commitSha` returns `"behind"` when the default branch contains the commit. This is semantically correct.
- However, `defaultBranch` defaults to `"main"` (`github-client.ts:121`). Repos using `master`, `develop`, or other default branch names will get false negatives. No per-project configuration exists for this.

**No test coverage:** Zero tests exist for the merge gate logic. No tests in `artifacts/api-server/test/` reference `metabolism`, `checkCommitInDefaultBranch`, or the PR-merge webhook path. The webhook handler has no integration tests verifying L3 status transitions on PR merge events.

## Round 3 — Integration & Completeness Review

**End-to-end flow analysis:**

| Scenario                      | Webhook                                        | Metabolism                                 | Result            |
| ----------------------------- | ---------------------------------------------- | ------------------------------------------ | ----------------- |
| PR merged on GitHub           | ✅ Sets L3→valid                               | —                                          | Works             |
| PR closed without merge       | ❌ Only sets PR state=closed, L3 stays pending | ❌ Never sets orphaned                     | **Broken**        |
| Direct push to main (no PR)   | ❌ No webhook fires                            | ⚠️ Metabolism checks but only if triggered | **Dead code**     |
| Non-GitHub repos (SVN, local) | ❌ No webhook                                  | ❌ `parseGithubRepo` returns null, skipped | **Not supported** |

**Key integration gaps:**

1. **Orphaned status is unreachable code:** The `orphaned` value in the `validityStatus` enum is defined in the schema (`l3_nodes.ts:37`, `commits.ts:23`) and in the MCP query filter spec (4.3.3/4.3.4), but no code path ever writes it. The closed-without-merge webhook branch (`github_webhooks.ts:341-350`) should set L3 nodes to `orphaned` but doesn't.

2. **Metabolism requires external trigger:** Without a cron job or internal scheduler hitting `GET /metabolism-tick`, the polling fallback never executes. The `checkCommitInDefaultBranch` function and the entire merge-gate fallback in `metabolism.ts` are effectively dead code.

3. **Commit-to-L3 join relies on `commitHash`:** The webhook merge handler joins PR commits to L3 nodes via `l3NodesTable.commitHash` (`github_webhooks.ts:280-285`). This works for L3 nodes created from PR commits, but L3 nodes created via the generate pipeline may have `commitHash` set to a single hash while the PR has multiple commits. The `inArray` join handles this correctly for the PR commits, but L3 nodes from commits NOT in the PR (e.g., from a different branch that was merged) won't be caught.

4. **No branch-level orphaned detection:** Even if the orphaned status were implemented, the `branchName` column on commits is never populated, so there's no way to determine which branch a commit belonged to at the database level. The webhook handler has access to PR head branch info (`pr.head.ref`) but doesn't store it.

## Gaps & Recommendations

1. **Set L3 nodes to `orphaned` on PR close-without-merge.** In `github_webhooks.ts:341-350`, after setting PR state to `"closed"`, fetch the PR's commit hashes and update associated L3 nodes from `pending` → `orphaned`. This is the most critical gap — without it, abandoned branches pollute the knowledge graph.

2. **Auto-trigger the metabolism polling fallback.** Add an internal scheduler (e.g., `setInterval` in `app.ts` or a cron-triggered HTTP call) to hit `/metabolism-tick` periodically (e.g., every 6 hours). Without this, the polling path is dead code.

3. **Populate `branchName` during ingestion.** In `ingest.ts` and `github_webhooks.ts`, write the branch name to `commits.branchName`. The git-client already reads it (`git-client.ts:122-123`); it just needs to be included in the `insert()` call.

4. **Make default branch configurable per project.** Add a `defaultBranch` column to `projectsTable` or read it from the GitHub API (`repository.default_branch` in the webhook payload — it's already available at `payload.repository.default_branch`).

5. **Add tests for merge gate logic.** Create integration tests that: (a) fire a PR-merged webhook and verify L3→valid, (b) fire a PR-closed webhook and verify L3→orphaned, (c) call metabolism-tick and verify pending L3 nodes are correctly promoted.

6. **Secure the `/metabolism-tick` endpoint.** Add authentication or remove the unauthenticated route in production. The admin endpoint already has token auth — the public one should too.
