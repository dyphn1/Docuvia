# Verification Report: Item 4.3.3 — L3 Validity Status Enum: pending | valid | orphaned

**Item ID:** 4.3.3
**Description:** L3 validity status enum: pending | valid | orphaned
**Date:** 2026-06-20
**Verdict:** ⚠️ WARN

## Design Spec References

- `docs/design/adrs/ADR-009-ast-microkernel-architecture.md` (cross-references ADR-011)
- ADR-011 Two-Phase Knowledge Validity (from `docs/design/09-architectural-decisions.md` lines 275–300):
  - Validity status enum: `pending | valid | orphaned`
  - `pending` = default for newly AI-generated nodes
  - `valid` = promoted after merge gate (Phase 2)
  - `orphaned` = branch closed without merge, or commit abandoned

## Round 1 — Schema & Data Model Review

**What the spec says:** The validity status enum should have three values: `pending`, `valid`, and `orphaned`. This enum should be enforced at the database level.

**What exists:**

1. **`l3_nodes` table** (`l3_nodes.ts:37`): `validityStatus: text("validity_status").notNull().default("pending")` — plain `text` column, **no `pgEnum` constraint**.

2. **`commits` table** (`commits.ts:23`): `validityStatus: text("validity_status").notNull().default("pending")` — same plain `text` column, no enum constraint.

3. **No `pgEnum` is defined anywhere** in the schema. The `l3NodeTypeEnum` (`l3_nodes.ts:16`) is defined as `pgEnum("l3_node_type", ["change", "rule", "decision", "context"])` for the `nodeType` column, but no corresponding `pgEnum` exists for `validity_status`.

**Round 1 Findings:**

- ✅ Column exists on both `l3_nodes` and `commits` tables
- ✅ Default value is `"pending"` on both tables
- ❌ **No database-level enum constraint** — any string value can be inserted into `validity_status`. The enum is only enforced implicitly by application code, not by the DB schema. This means:
  - No protection against typos or invalid values at the DB level
  - No database-level documentation of the allowed values
  - Inconsistent with the pattern used for `l3_node_type` and `node_type` which DO use `pgEnum`

**Round 1 Verdict: WARN** — Column exists and defaults correctly, but lacks DB-level enum constraint.

## Round 2 — Code Path Review (Which Values Are Actually Written?)

**What the spec says:** Three values should be used: `pending` (default), `valid` (after merge), `orphaned` (after branch abandonment).

**Code paths that write `validityStatus`:**

| Location | Value Written | Context |
|----------|--------------|---------|
| `generate.ts:1030` | `"pending"` | New L3 node created by AI |
| `github_webhooks.ts:280` | `"valid"` | PR merged — L3 nodes from PR commits promoted |
| `metabolism.ts:83` | `"valid"` | Metabolism polling — commit found in default branch |
| **Nowhere** | `"orphaned"` | ❌ No code path ever writes `"orphaned"` |

**Code paths that read/filter by `validityStatus`:**

| Location | Filter | Values Checked |
|----------|--------|---------------|
| `intent-router.ts:198` | `includePending=true` | `"valid"` OR `"pending"` |
| `intent-router.ts:199` | `includePending=false` (default) | `"valid"` only |
| `intent-router.ts:500` | `!includePending` guard | `!== 'active'` ⚠️ |
| `intent-router.ts:535` | `!includePending` guard | `!== 'active'` ⚠️ |
| `vector-search.ts:28` | `!includePending` filter | `=== 'active'` ⚠️ |

**Critical inconsistency found:** `intent-router.ts:500,535` and `vector-search.ts:28` check for `'active'` as the validity status value, but the actual values used everywhere else are `"pending"`, `"valid"`, and `"orphaned"`. The value `'active'` is never written to the database. This means:
- The direct search path (`intent-router.ts:499-515`) will **skip ALL L3 nodes** when `includePending=false`, because no node ever has `validityStatus === 'active'`
- The vector search (`vector-search.ts:28`) will **return zero results** when `includePending=false`, because the filter `=== 'active'` matches nothing

This is a significant bug — the `'active'` value appears to be a leftover from an earlier naming convention that was changed to `"valid"` but never updated in these two filter locations.

**Round 2 Findings:**

- ✅ `"pending"` is correctly set as default on L3 creation
- ✅ `"valid"` is correctly set on PR merge and metabolism promotion
- ❌ **`"orphaned"` is never written** — no code path handles branch abandonment
- ❌ **`'active'` vs `"valid"` naming inconsistency** — two filter locations check for `'active'` which is never a valid value, causing silent query failures

**Round 2 Verdict: WARN** — Orphaned status unreachable; active/valid naming bug breaks query filtering.

## Round 3 — Integration & Completeness Review

**End-to-end flow analysis for each validity status value:**

| Value | Can be set? | Can be queried? | Used in filters? |
|-------|-------------|-----------------|------------------|
| `pending` | ✅ Yes (default on insert) | ✅ Yes (with `include_pending=true`) | ✅ Yes |
| `valid` | ✅ Yes (webhook merge, metabolism) | ✅ Yes (default filter) | ⚠️ Partially — `'active'` bug in 2 locations |
| `orphaned` | ❌ No code path sets it | N/A — never in DB | ❌ Not referenced in any filter |

**Integration gaps:**

1. **Orphaned status is unreachable code.** The `orphaned` value is defined in the spec and checklist, but no code path ever writes it. The closed-without-merge webhook handler (`github_webhooks.ts:341-350`) only sets `pullRequestsTable.state = "closed"` — it does NOT update associated L3 nodes to `orphaned`. The metabolism fallback also only promotes to `valid` and never sets `orphaned`. Abandoned-branch L3 nodes remain `pending` forever.

2. **The `'active'` vs `"valid"` bug silently breaks queries.** When `includePending=false` (the default for MCP queries per item 4.3.4), the intent-router's direct search path checks `l3.validityStatus !== 'active'` (line 500, 535) and the vector search checks `=== 'active'` (vector-search.ts:28). Since the actual value is `"valid"`, not `"active"`:
   - Direct search: ALL L3 nodes are skipped (none have status `'active'`), so zero results are returned
   - Vector search: The WHERE clause filters for `= 'active'`, matching nothing, so zero results are returned
   - This means **MCP queries with default settings (include_pending=false) return no results from direct or vector search paths**, defeating the purpose of the validity filter

3. **No DB-level enum constraint.** Unlike `l3_node_type` which uses `pgEnum`, the `validity_status` column is a plain text field. This is a data integrity risk.

4. **Export displays status correctly.** The Markdown export (`export.ts:168`) displays `l3.validityStatus` directly, which is correct — it will show "pending" or "valid" as expected.

## Gaps & Recommendations

1. **Fix the `'active'` → `"valid"` naming bug.** In `intent-router.ts:500,535` and `vector-search.ts:28`, change `'active'` to `"valid"`. This is a critical bug that silently breaks MCP queries and vector search when `includePending=false`.

2. **Add `"orphaned"` transition on PR close-without-merge.** In `github_webhooks.ts:341-350`, after setting PR state to `"closed"`, fetch the PR's commit hashes and update associated L3 nodes from `pending` → `orphaned`. This is the primary mechanism for marking abandoned knowledge.

3. **Add `"orphaned"` transition in metabolism fallback.** In `metabolism.ts`, after checking commits against the default branch, for nodes that are NOT merged AND are older than a threshold (e.g., 30 days), set `validityStatus` to `orphaned` instead of leaving them as `pending` forever.

4. **Add a `pgEnum` for `validity_status`.** Define `export const validityStatusEnum = pgEnum("validity_status", ["pending", "valid", "orphaned"])` and use it in both `l3_nodes.ts` and `commits.ts`. This ensures data integrity at the database level and is consistent with the pattern used for `l3_node_type`.

5. **Consider adding an orphaned cleanup mechanism.** For L3 nodes that have been `orphaned` for an extended period, consider automatic archival or deletion to prevent knowledge graph pollution.
