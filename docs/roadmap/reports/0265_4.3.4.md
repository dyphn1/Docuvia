# Verification Report: Item 4.3.4 — MCP Query Default Filter: status = valid only

**Item ID:** 4.3.4
**Description:** MCP query default filter should only return `status = valid` results
**Date:** 2026-06-20
**Verdict:** ⚠️ WARN

## Design Spec References

- ADR-011 Two-Phase Knowledge Validity (from `docs/design/09-architectural-decisions.md`):
  - MCP query default behavior: only return L3 nodes where `status = valid`
  - `pending` nodes are hidden by default — they are unreviewed AI-generated content
  - `orphaned` nodes are hidden by default — they come from abandoned branches
- Item 4.3.5: `include_pending=true` query parameter to also include pending

## Source Files Examined

| File | Purpose |
|------|---------|
| `artifacts/api-server/src/routes/mcp.ts` | MCP route handlers — `search_knowledge`, `query`, `get_decision_record`, etc. |
| `artifacts/api-server/src/lib/intent-router.ts` | `routeQuery()` orchestrator + `vectorSearchHandler` + `directLookupHandler` + `graphTraversalHandler` + `hybridSearch` |

## Round 1 — MCP Endpoint Parameter Review

**What the spec says:** MCP endpoints should default to `include_pending=false`, only returning `status = valid` results. Clients must explicitly pass `include_pending=true` to see pending nodes.

**What exists:**

1. **`GET /mcp/search_knowledge`** (`mcp.ts:93-109`):
   ```typescript
   const includePending = req.query.include_pending === "true" || false;
   ```
   - Defaults to `false` when `include_pending` is absent ✅
   - Correctly passes `includePending` to `routeQuery()` ✅

2. **`POST /mcp/query`** (`mcp.ts:236-253`):
   ```typescript
   const includePending = req.query.include_pending === "true" || false;
   ```
   - Same pattern, defaults to `false` ✅
   - Passes to `routeQuery()` ✅

3. **`GET /mcp/get_decision_record`** (`mcp.ts:202-224`):
   - Fetches L3 nodes by commit hash with NO `includePending` logic ❌
   - Returns ALL L3 nodes regardless of validityStatus ❌

4. **`GET /mcp/list_projects`** (`mcp.ts:39-66`):
   - Counts ALL L3 nodes per project without validityStatus filter ❌
   - Includes pending nodes in totals shown to MCP clients ❌

**Round 1 Findings:**
- ✅ The two primary query endpoints (`search_knowledge` and `query`) correctly default `includePending` to `false`
- ✅ The parameter naming convention (`include_pending`) is documented and consistent
- ✅ Both endpoints pass `includePending` through to the shared `routeQuery()` function
- ❌ Secondary endpoints (`get_decision_record`, `list_projects`) have no validityStatus filtering at all

**Round 1 Verdict: PASS (for primary endpoints)** — The two main query entry points correctly implement the default filter pattern. Secondary endpoints are out of scope for this item (they're separate checklist items' concern).

## Round 2 — Search Handler Filter Logic Review

**This is where the spec intent meets implementation reality.** When `includePending = false` flows through `routeQuery()` to the four search handlers:

### Vector Search (`intent-router.ts:197-199`)

```typescript
const l3ValidityCondition = includePending
  ? or(eq(l3NodesTable.validityStatus, "valid"), eq(l3NodesTable.validityStatus, "pending"))
  : eq(l3NodesTable.validityStatus, "valid");
```

- `includePending = false` → filters `validityStatus = "valid"` ✅
- `includePending = true` → filters `"valid" OR "pending"` ✅
- Applied consistently in all L3 sub-queries (lines 258, 262, 353)

### Direct Lookup (`intent-router.ts:500, 535`)

```typescript
if (!includePending && l3.validityStatus !== 'active') continue;
```

- ❌ **Critical bug: checks for `'active'` instead of `'valid'`**
- When `includePending = false`, this skips EVERY L3 node because none have `validityStatus === 'active'`
- The actual stored value is `"valid"`, not `"active"`
- Affects commit hash lookup (line 500) AND full-text content search (line 535)
- This is the same bug identified in the 4.3.3 report (item 4.3.3, round 2)

### Graph Traversal (`intent-router.ts:391-475`)

```typescript
export async function graphTraversalHandler(
  moduleName: string,
  projectId?: number,
  limit = 20
): Promise<AgenticSearchResult[]> {
```

- ❌ **No `includePending` parameter accepted**
- ❌ **No validityStatus filter applied** to any L3 node query
- Line 453-458: fetches L3 nodes by `l2NodeId` with no status filter
- All L3 nodes returned regardless of `validityStatus`
- Called directly by `routeQuery()` line 703 and by `hybridSearch()` line 580

### Hybrid Search (`intent-router.ts:560-608`)

```typescript
const vectorResults = await vectorSearchHandler(searchQuery, projectId, limit, includePending);
// ...
const graphResultArrays = await Promise.all(
  topL2Names.map((name) => graphTraversalHandler(name, projectId)) <-- no includePending!
);
```

- Vector results: correctly filtered ✅
- Graph results: NOT filtered (handler doesn't support the parameter) ❌
- Merged results include unfiltered graph traversal L3 nodes

### Standalone Vector Search (`vector-search.ts:27-28`)

```typescript
if (!includePending) {
  conditions.push(eq(l3NodesTable.validityStatus, 'active'));
}
```

- ❌ **Same `'active'` bug** — filters for `'active'` which matches zero rows
- When `includePending = false`, this function returns ZERO results
- This utility function appears to be an older/alternative code path

**Round 2 Findings:**
- ✅ Vector search handler (intent-router.ts) correctly implements validityStatus filtering
- ❌ **Direct lookup handler**: `'active'` bug silently returns empty results for queries and commit hash lookups
- ❌ **Graph traversal handler**: No filtering at all — returns all statuses including pending
- ❌ **Hybrid search**: Partially broken — graph results bypass the filter
- ❌ **vector-search.ts**: `'active'` bug in standalone utility

**Round 2 Verdict: WARN** — 1 of 4 code paths works correctly. The `'active'` bug is identical to the one found in verification 4.3.3.

## Round 3 — Integration & End-to-End Flow Analysis

**How `routeQuery()` orchestrator dispatches — and which paths enforce the filter:**

| Strategy | Handler | Filter Applied? | MCP Default Safe? |
|----------|---------|-----------------|-------------------|
| `vector_search` | `vectorSearchHandler()` | ✅ `= "valid"` | ✅ Yes |
| `direct_lookup` | `directLookupHandler()` | ⚠️ Uses `'active'` | ❌ Returns empty |
| `graph_traversal` | `graphTraversalHandler()` | ❌ No filter | ❌ Leaks pending |
| `hybrid` | Both vector + graph | ⚠️ Partial | ⚠️ Graph leaks |

**Fast-path routing impact (lines 649-682):**

The `routeQuery()` function has O(1) fast-path filters that bypass LLM classification:
- `#attach` or file extension match → `direct_lookup` → **broken filter** ❌
- Architectural term match → `graph_traversal` → **no filter** ❌
- No fast-path match → LLM classification → depends on strategy

This means the most common, fast MCP queries (which use `#attach` or reference known module names) are precisely the ones with broken or missing validity filters.

**Complete MCP endpoint coverage:**

| Endpoint | Has Validity Filter? | Notes |
|----------|---------------------|-------|
| `GET /mcp/search_knowledge` | ⚠️ Partial | Depends on routing strategy chosen |
| `POST /mcp/query` | ⚠️ Partial | Same as above |
| `GET /mcp/get_decision_record` | ❌ No | Returns all statuses |
| `GET /mcp/list_projects` | ❌ No | Counts include pending |
| `GET /mcp/get_dependencies` | ❌ No | L2-only, but no L3 filter if added |
| `GET /mcp/impact_analysis` | ❌ No | L3 count includes pending |

**Consistency with item 4.3.5 (`include_pending=true`):**

The `include_pending=true` parameter is correctly implemented in the two primary endpoints and correctly handled by `vectorSearchHandler`. However, it has no effect on `graphTraversalHandler` (which doesn't accept the parameter) and has no effect on `directLookupHandler` (where the `'active'` bug makes the filter meaningless).

## Gaps & Recommendations

1. **Fix `'active'` → `"valid"` naming bug (CRITICAL).** In `intent-router.ts:500,535` and `vector-search.ts:28`, change `'active'` to `"valid"`. This is the same critical bug found in 4.3.3. Without this fix, MCP direct lookup queries always return empty results.

2. **Add `includePending` parameter to `graphTraversalHandler`.** The function signature should accept an `includePending` boolean and apply a validityStatus filter to L3 node queries. This is required for both the graph traversal strategy and hybrid search to work correctly.

3. **Add validityStatus filter to `get_decision_record` MCP endpoint.** When looking up decisions by commit hash, pending L3 nodes should be excluded by default. Add an `include_pending` query parameter with the same default-false pattern.

4. **Fix `list_projects` L3 count accuracy.** Either filter to `validityStatus = "valid"` or provide separate counts for valid vs pending nodes so MCP clients get accurate project statistics.

5. **Consider adding `include_pending` support to all MCP endpoints.** For consistency, every endpoint that returns L3 nodes should support the `include_pending` parameter with a default of `false`.

6. **The `|| false` pattern is redundant.** `req.query.include_pending === "true" || false` can be simplified to `req.query.include_pending === "true"` which already evaluates to a boolean. The `|| false` adds no value and could mask type issues.
