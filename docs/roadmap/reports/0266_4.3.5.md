# Verification Report: Item 4.3.5 — `include_pending=true` query parameter

**Item ID:** 4.3.5
**Description:** MCP query endpoint should support `include_pending=true` query parameter to include pending-status results
**Date:** 2026-06-20
**Verdict:** ⚠️ WARN

## Design Spec References

- ADR-011 Two-Phase Knowledge Validity (from `docs/design/09-architectural-decisions.md`):
  - MCP query default behavior: only return L3 nodes where `status = valid`
  - `pending` nodes are hidden by default — they are unreviewed AI-generated content
  - `include_pending=true` parameter allows clients to explicitly request pending nodes
- Item 4.3.4: MCP query default filter — `status = valid` only

## Round 1 — Endpoint Parameter Existence & Default Behavior

**What the spec says:** MCP endpoints must support `include_pending=true` as a query parameter. Default should be `false` (hide pending nodes).

**What exists:**

1. **`GET /mcp/search_knowledge`** (`mcp.ts:98`):
   ```typescript
   const includePending = req.query.include_pending === "true" || false;
   ```
   - Parameter parsed from query string ✅
   - Defaults to `false` when absent ✅
   - Passed to `routeQuery()` ✅

2. **`POST /mcp/query`** (`mcp.ts:244`):
   ```typescript
   const includePending = req.query.include_pending === "true" || false;
   ```
   - Same pattern ✅
   - Passes to `routeQuery()` ✅

3. **`GET /mcp/get_decision_record`** (`mcp.ts:202-224`):
   - ❌ No `include_pending` parameter support
   - Returns ALL L3 nodes regardless of `validityStatus`

4. **`GET /mcp/list_projects`** (`mcp.ts:39-66`):
   - ❌ No validityStatus filtering at all
   - L3 counts include pending nodes

5. **`POST /search`** (`search.ts:22-32`):
   - ❌ Calls `routeQuery(query, projectId, limit)` without `includePending` — always defaults to `false`
   - Web UI search cannot request pending nodes

6. **`extensions-service.ts:9`** (`vscodeQuery()`):
   - ❌ Calls `routeQuery(q, projectId, limit)` without `includePending` — always defaults to `false`
   - VS Code extension cannot request pending nodes

**Round 1 Findings:**
- ✅ Both primary MCP query endpoints (`search_knowledge` and `query`) support the parameter
- ✅ Default is correctly `false` (hide pending)
- ✅ Parameter is consistently named `include_pending` (snake_case, matches convention)
- ❌ Secondary MCP endpoints (`get_decision_record`, `list_projects`) lack the parameter
- ❌ Non-MCP search paths (`/search`, `vscodeQuery`) don't expose the parameter

**Round 1 Verdict: PASS** — The two primary MCP endpoints correctly implement the parameter.

## Round 2 — Handler Propagation & Filter Logic

**Does `include_pending=true` actually include pending nodes when it reaches the search handlers?**

### Vector Search (`intent-router.ts:197-199`)

```typescript
const l3ValidityCondition = includePending
  ? or(eq(l3NodesTable.validityStatus, "valid"), eq(l3NodesTable.validityStatus, "pending"))
  : eq(l3NodesTable.validityStatus, "valid");
```

- `includePending = true` → returns both `"valid"` AND `"pending"` nodes ✅
- `includePending = false` → returns only `"valid"` ✅
- Applied consistently across all L3 sub-queries ✅

### Direct Lookup (`intent-router.ts:500, 535`)

```typescript
if (!includePending && l3.validityStatus !== 'active') continue;
```

- ❌ **Critical bug: checks `'active'` instead of `'valid'` or `'pending'`**
- When `includePending = false`: skips ALL nodes (none have `validityStatus === 'active'`) → returns empty
- When `includePending = true`: also skips ALL nodes → returns empty
- This handler is broken regardless of `includePending` value
- Same bug as identified in 4.3.3 and 4.3.4 reports

### Graph Traversal (`intent-router.ts:391-475`)

```typescript
export async function graphTraversalHandler(
  moduleName: string,
  projectId?: number,
  limit = 20
): Promise<AgenticSearchResult[]> {
```

- ❌ **Does not accept `includePending` parameter**
- ❌ **Never filters on `validityStatus`** for L3 nodes
- Returns ALL L3 nodes regardless of status
- Called by `routeQuery()` line 703 and `hybridSearch()` line 580

### Hybrid Search (`intent-router.ts:560-608`)

```typescript
const vectorResults = await vectorSearchHandler(searchQuery, projectId, limit, includePending);
// ...
const graphResultArrays = await Promise.all(
  topL2Names.map((name) => graphTraversalHandler(name, projectId))  // no includePending!
);
```

- Vector results: correctly filtered ✅
- Graph results: NOT filtered ❌
- Merged results include unfiltered graph traversal L3 nodes

### Standalone Vector Search (`vector-search.ts:27-28`)

```typescript
if (!includePending) {
  conditions.push(eq(l3NodesTable.validityStatus, 'active'));
}
```

- ❌ **Same `'active'` bug** — when `includePending = false`, filters for `'active'` which matches zero rows
- When `includePending = true`, no filter applied (correct behavior by accident)

**Round 2 Findings:**
- ✅ `vectorSearchHandler` correctly implements `includePending` logic
- ❌ `directLookupHandler` is completely broken (same `'active'` bug as 4.3.3/4.3.4)
- ❌ `graphTraversalHandler` doesn't accept `includePending` — always leaks pending nodes
- ❌ `hybridSearch` partially broken — graph portion leaks pending nodes
- ❌ `vector-search.ts` standalone utility has `'active'` bug

**Round 2 Verdict: WARN** — Only 1 of 4 code paths correctly implements `include_pending`. The same bugs from 4.3.3/4.3.4 persist.

**Fast-path routing bypass issue:**

The `routeQuery()` function has O(1) fast-path filters (lines 649-682):
- `#attach` or file extension → `direct_lookup` → **broken** ❌
- Architectural term match → `graph_traversal` → **over-inclusive** ⚠️

These fast-paths are the most common MCP query patterns, and they both fail to properly enforce the `include_pending` semantics.

**Consistency with item 4.3.4:**

Items 4.3.4 (default filter) and 4.3.5 (include_pending parameter) are two sides of the same coin. The bugs found in 4.3.4 directly apply here:
- The `'active'` bug in `directLookupHandler` makes both the default filter AND the include_pending parameter non-functional for that handler
- The missing filter in `graphTraversalHandler` means pending nodes are always included regardless of `include_pending` value

## Gaps & Recommendations

1. **Fix `'active'` → `'valid'` naming bug (CRITICAL).** In `intent-router.ts:500,535` and `vector-search.ts:28`, change `'active'` to `'valid'`. This is the same critical bug found in 4.3.3 and 4.3.4. Without this fix, `include_pending` has no effect on direct lookup queries — the handler always returns empty.

2. **Add `includePending` parameter to `graphTraversalHandler`.** The function signature must accept an `includePending` boolean and apply a `validityStatus` filter to L3 node queries. This is required for both graph traversal strategy and hybrid search to respect `include_pending`.

3. **Add `include_pending` support to `get_decision_record` MCP endpoint.** When looking up decisions by commit hash, pending L3 nodes should be excluded by default. Add the query parameter with the same default-false pattern.

4. **Add `include_pending` support to `list_projects` MCP endpoint.** Either filter to `validityStatus = "valid"` or provide separate counts for valid vs pending nodes.

5. **Expose `include_pending` on the Web UI search route.** The `/search` POST endpoint currently hardcodes the default behavior. Add an optional `include_pending` field to the request body schema.

6. **Expose `include_pending` on `vscodeQuery()`.** The VS Code extension bridge should forward `include_pending` to `routeQuery()` so extension users can also request pending nodes.

7. **The `|| false` pattern is redundant.** `req.query.include_pending === "true" || false` simplifies to `req.query.include_pending === "true"` which already evaluates to a boolean. While not a bug, it's noise that could be cleaned up during the fix pass.
