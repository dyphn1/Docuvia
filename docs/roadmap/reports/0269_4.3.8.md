## Round 1 — Webhook-Based Merge Detection (Primary Path)

**What ADR-011 requires:** The server must detect when a PR is merged and update L3 node validity accordingly.

### GitHub Webhook Handler (`github_webhooks.ts:255-340`)

The webhook handles three PR actions:

1. **`opened` / `synchronize`** (lines 200-254): Creates/updates PR record, ingests commits, notifies subscribers.
2. **`closed` + `merged`** (lines 255-340): Updates PR state to "merged", fetches PR commits, promotes associated L3 nodes from `pending` → `valid`, generates AI summary, posts PR comment, notifies subscribers.
3. **`closed` + not merged** (lines 341-352): Updates PR state to "closed" only.

**Findings:**

| Aspect                              | Status | Details                                                                                 |
| ----------------------------------- | ------ | --------------------------------------------------------------------------------------- |
| Webhook receives PR merge events    | ✅     | `action === "closed" && isMerged` correctly detects merge                               |
| PR record updated to "merged"       | ✅     | `state: "merged"`, `mergedAt` set                                                       |
| L3 nodes promoted on merge          | ✅     | Lines 278-286: `UPDATE l3_nodes SET validityStatus = 'valid' WHERE commitHash IN (...)` |
| PR commit fetch on merge            | ✅     | `fetchPrCommits()` retrieves all PR commits                                             |
| Join PR commits → L3 nodes          | ✅     | Uses `inArray(l3NodesTable.commitHash, prCommitHashes)`                                 |
| Only promotes from "pending"        | ✅     | Guard: `eq(l3NodesTable.validityStatus, "pending")` prevents overwriting "orphaned"     |
| Async processing after 202 response | ✅     | `setImmediate()` avoids blocking webhook acknowledgment                                 |
| Error handling                      | ✅     | Try/catch marks PR analysis as "failed" on exception                                    |

**Round 1 Verdict: PASS** — The webhook-based merge detection is correctly implemented for the happy path (PR merged → L3 promoted to valid).

## Round 2 — Polling/Fallback Path (Metabolism)

**What ADR-011 implies:** For cases where the webhook misses (e.g., server was down, webhook not configured), a fallback mechanism should periodically check pending nodes.

### Metabolism Merge Gate Fallback (`metabolism.ts:18-87`)

The metabolism job runs as a background task (triggered via `GET /metabolism-tick` or `GET /admin/metabolism-tick`):

1. **Query pending L3 nodes** (lines 21-36): Finds L3 nodes with `validityStatus = "pending"` created more than 24 hours ago.
2. **Check each commit** (lines 57-77): For each pending node, calls `checkCommitInDefaultBranch()` to verify if the commit is an ancestor of `main`.
3. **Promote merged** (lines 80-86): If confirmed merged, promotes to `valid`.

### `checkCommitInDefaultBranch()` (`github-client.ts:116-134`)

Uses the GitHub compare API: `GET /repos/{owner}/{repo}/compare/{defaultBranch}...{commitSha}`

- Returns `true` if status is `"identical"` or `"behind"` (meaning the commit is contained in the default branch).
- Returns `false` if the API errors (graceful degradation).

**Findings:**

| Aspect                                      | Status | Details                                                   |
| ------------------------------------------- | ------ | --------------------------------------------------------- |
| Fallback query for stale pending nodes      | ✅     | 24-hour threshold prevents checking freshly created nodes |
| GitHub compare API call                     | ✅     | Correctly uses `compare/main...{sha}`                     |
| Correct interpretation of comparison result | ✅     | `"identical"` or `"behind"` = merged                      |
| Promotion to "valid"                        | ✅     | Batch update via `inArray`                                |
| Error handling per node                     | ✅     | Individual try/catch, continues to next node              |
| Only processes pending nodes                | ✅     | `eq(l3NodesTable.validityStatus, "pending")`              |

**Gaps identified:**

| Gap                              | Severity  | Details                                                                                                                                                                                                                                                                                        |
| -------------------------------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Metabolism trigger mechanism** | ⚠️ Medium | The metabolism is only triggered via manual HTTP endpoints (`/metabolism-tick` or `/admin/metabolism-tick`). There is NO automatic cron/scheduled trigger in the codebase. The metabolism job relies on an external scheduler calling it, but no such scheduler is configured in the codebase. |
| **No "orphaned" transition**     | ⚠️ Medium | Neither the webhook nor the metabolism ever sets `validityStatus = "orphaned"`. When a PR is closed without merging (lines 341-352), only the PR state is set to "closed" — associated L3 nodes remain "pending" forever. This is a known gap from 4.3.2 and 4.3.6 reports.                    |
| **Hardcoded "main" branch**      | ⚠️ Low    | `checkCommitInDefaultBranch()` defaults to `"main"` but some repos use `"master"` or other default branches. No per-project configuration for default branch name.                                                                                                                             |

**Round 2 Verdict: WARN** — The fallback logic is correctly implemented but has no automatic trigger mechanism. The "orphaned" status is never written.

## Round 3 — Orphan Detection & Branch-Level Tracking

**What ADR-011 requires:** "Commits on branches that are later deleted without merging cause their L3 nodes to be set to `orphaned`."

### Orphan Detection on PR Close (Not Merged)

**`github_webhooks.ts:341-352`:**

```typescript
} else if (action === "closed") {
  // Closed but not merged
  await db
    .update(pullRequestsTable)
    .set({ state: "closed", updatedAt: new Date() })
    .where(...);
}
```

- ❌ **No L3 node update** — The handler only updates the PR record. It does NOT find or update L3 nodes associated with this PR's commits.
- ❌ **No "orphaned" status** — The `orphaned` value from ADR-011's enum is never written anywhere in the codebase.

### Branch Name Tracking

From the 4.3.7 report: The `commits.branchName` column exists but is never populated. This means:

- ❌ Cannot track which branch a commit belongs to at the database level
- ❌ Cannot detect orphaned commits without PR metadata
- The current merge tracking relies entirely on PR webhook data, not commit-level branch info

### Metabolism Fallback for Orphans

The metabolism merge gate only promotes to "valid" — it does NOT set "orphaned" for commits that are confirmed NOT in the default branch. The logic only checks `isMerged = true` and promotes; there's no `else` branch for `isMerged = false`.

**Findings:**

| Aspect                                          | Status     | Details                                                                                      |
| ----------------------------------------------- | ---------- | -------------------------------------------------------------------------------------------- |
| PR close-without-merge detection                | ✅         | Webhook correctly identifies `action === "closed" && !isMerged`                              |
| L3 nodes set to "orphaned" on PR close          | ❌ Missing | No code path writes "orphaned"                                                               |
| Metabolism detects non-merged commits           | ❌ Missing | Only promotes to "valid", never marks "orphaned"                                             |
| Branch name available for commit-level tracking | ❌ Missing | `commits.branchName` column exists but is never populated (see 4.3.7 report)                 |
| Orphan cleanup in MCP query filter              | ✅         | Default filter excludes non-valid nodes, so orphaned nodes (if they existed) would be hidden |

**Round 3 Verdict: FAIL** — The orphan detection flow is completely absent. This is a core ADR-011 requirement that is unimplemented.

## Gaps & Notes

1. **Metabolism scheduling gap:** The metabolism job is the only "polling" mechanism for merge status, but it has no cron trigger. In a production deployment, if nobody calls `/admin/metabolism-tick`, pending L3 nodes will never be promoted to "valid" via the fallback path (only webhook-triggered merges would work). A cron job or in-process scheduler (e.g., `setInterval`) should be configured.

2. **Orphan detection is a critical ADR-011 gap:** The `orphaned` status value exists in the schema enum but is never written. This means:
   - Abandoned feature branch commits' L3 nodes stay "pending" forever
   - They appear in queries when `include_pending=true`
   - The knowledge graph accumulates stale entries from discarded design attempts
   - This directly contradicts ADR-011's primary benefit: "Abandoned design attempts do not contaminate the canonical knowledge graph"

3. **Fixing orphan detection requires:**
   - In the webhook `closed` (not merged) handler: Find L3 nodes associated with PR commits and set `validityStatus = "orphaned"`
   - In the metabolism fallback: For commits confirmed NOT in default branch (after sufficient time), set `validityStatus = "orphaned"`
   - This depends on `commits.branchName` being populated (item 4.3.7) for proper branch-level tracking

4. **Hardcoded "main" branch in `checkCommitInDefaultBranch()`:** The function accepts a `defaultBranch` parameter (defaulting to `"main"`), but callers always use the default. The `projectsTable` does not have a `defaultBranch` column, so there's no way to configure per-project default branches. This could cause incorrect results for repos using `"master"` or other default branch names.

## Dependency Chain

```
4.3.7 (branchName populated) ──blocks──> 4.3.8 (orphan detection)
     │                                          │
     └── Schema exists but data flow broken     └── Orphan logic missing entirely
```

Even without 4.3.7 being fixed, orphan detection could be implemented at the PR level (when a PR is closed without merge, mark its L3 nodes as orphaned). The `branchName` column would be needed for more granular commit-level orphan detection (e.g., commits pushed directly to a branch without a PR).

## Final Verdict: WARN

The primary merge tracking path (GitHub webhook → PR merge → L3 "valid") is correctly implemented and functional. The fallback metabolism logic is sound but lacks an automatic trigger mechanism. The critical gap is the missing orphan detection: the "orphaned" status from ADR-011 is never written anywhere, meaning abandoned-branch knowledge nodes accumulate indefinitely. This is a medium-severity design conformance gap that undermines ADR-011's primary benefit. The fix is straightforward (add else branch in webhook handler and metabolism) but is currently entirely absent.
