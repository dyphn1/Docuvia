## Round 2 — Hash Computation & Storage (Upload Path)

**What ADR-012 requires:** At upload time, the server computes SHA-256 and stores it in `contentHash`.

### `computeHashFromStream()` (`artifacts/api-server/src/lib/utils/hash.ts:4-12`)

```typescript
export function computeHashFromStream(filePath: string): Promise<string> {
  return new Promise((resolve, reject) => {
    const hash = crypto.createHash("sha256");
    const stream = fs.createReadStream(filePath);
    stream.on("data", (chunk) => hash.update(chunk));
    stream.on("end", () => resolve(hash.digest("hex")));
    stream.on("error", reject);
  });
}
```

**Findings:**

| Aspect                       | Status | Details                                                                          |
| ---------------------------- | ------ | -------------------------------------------------------------------------------- |
| SHA-256 algorithm            | ✅     | `crypto.createHash("sha256")`                                                    |
| Hex encoding                 | ✅     | `hash.digest("hex")` produces 64-char hex string                                 |
| Streaming (memory-efficient) | ✅     | `fs.createReadStream` — handles large files without loading entirely into memory |
| Error propagation            | ✅     | `stream.on("error", reject)`                                                     |
| Return type                  | ✅     | `Promise<string>` — async/await compatible                                       |

## Gaps & Notes

1. **No gaps identified.** The implementation is complete and correct across all layers (schema, computation, storage, dedup, API contract).

2. **Minor observation:** The `contentHash` column is nullable, which is intentional for backward compatibility. Legacy rows (pre-ADR-012) may have NULL. The dedup logic handles this gracefully with the `??` fallback in `ingestion-pipeline.ts`.

3. **Hash computed from file, not content:** The upload handler computes the hash from the file on disk (`filePath`), while the ingestion pipeline fallback computes it from `doc.contentString`. Both produce the same SHA-256 result for identical content, so dedup works correctly in both paths.

## Final Verdict: PASS

The `contentHash` (SHA-256) implementation is fully functional across all required layers: the database column exists with an index, the hash is computed via streaming on every upload path, it is used for deduplication scoped to project ID, and the API contract correctly exposes it as a nullable string field. No gaps or issues found.
