
## Round 2 — Ingestion Pipeline: No Generation for Misc Pool Documents

**What ADR-012 requires:** The shared ingestion pipeline (`processIngestion`) must not create L1/L2/L3 nodes or review tasks for documents that are not associated with a project.

### `processIngestion()` — Document Path (`artifacts/api-server/src/lib/ingestion-pipeline.ts:153-189`)

```typescript
} else if (type === "document") {
  const docItems = items as DocumentItem[];
  for (const doc of docItems) {
    const hash = doc.contentHash ?? crypto.createHash("sha256").update(doc.content).digest("hex");

    const [existing] = await db
      .select({ id: documentsTable.id })
      .from(documentsTable)
      .where(and(
        eq(documentsTable.projectId, projectId),
        eq(documentsTable.contentHash, hash)
      ));

    if (existing) { skipped++; continue; }

    await db.insert(documentsTable).values({
      projectId, filename: doc.filename, docType: doc.docType,
      content: doc.content, contentHash: hash,
    });
    ingested++;
  }
}
```

**Key observation:** The `processIngestion()` function is only called when a `projectId` is present (the `DocumentItem` path requires `projectId`). The Misc Pool upload handler (`POST /documents`) does NOT call `processIngestion()` at all — it directly inserts into the database. This means:

| Aspect                                            | Status | Details                                                           |
| ------------------------------------------------- | ------ | ----------------------------------------------------------------- |
| `processIngestion()` not called for Misc Pool     | ✅     | Direct DB insert in upload handler                                |
| No L1 tag creation                                | ✅     | No L1 tag logic in document upload path                           |
| No L2 node creation                               | ✅     | No L2 node logic in document upload path                          |
| No L3 node creation                               | ✅     | No L3 node logic in document upload path                          |
| No review task creation                           | ✅     | No review_tasks insert anywhere in document upload path           |
| Dedicated `validityStatus: 'pending_affiliation'` | ✅     | Distinguishes unaffiliated documents from pipeline-processed ones |

**Round 2 Verdict: PASS** — The ingestion pipeline is not invoked for Misc Pool uploads. Documents are stored raw without any knowledge graph node generation.

## Round 3 — Background Workers & Query Filters Respect `pending_affiliation`

**What ADR-012 implies:** Background workers (metabolism, export, search) must not treat `pending_affiliation` documents as active knowledge nodes.

### Metabolism Route (`artifacts/api-server/src/routes/metabolism.ts:33`)

```typescript
eq(l3NodesTable.validityStatus, "pending"),
```

The metabolism worker only processes L3 nodes with `validityStatus = "pending"`. Documents with `validityStatus = "pending_affiliation"` are on the `documents` table, not the `l3_nodes` table, so they are inherently excluded.

### Intent Router (`artifacts/api-server/src/lib/intent-router.ts:198-199`)

```typescript
? or(eq(l3NodesTable.validityStatus, "valid"), eq(l3NodesTable.validityStatus, "pending"))
: eq(l3NodesTable.validityStatus, "valid");
```

The intent router queries `l3_nodes`, not `documents`. Misc Pool documents are not L3 nodes, so they are never returned in search results.

### Export Route (`artifacts/api-server/src/routes/export.ts:168`)

```typescript
res.write(`- **Status**: ${l3.validityStatus}\n`);
```

Export operates on L3 nodes, not raw documents. Misc Pool documents are excluded.

**Findings:**

| Aspect                                                  | Status | Details                                                |

**Round 3 Verdict: PASS** — Background workers and query paths operate on the `l3_nodes` table, which Misc Pool documents never enter. The `pending_affiliation` status is distinct from `pending`, preventing accidental processing.

## Gaps & Notes

1. **No gaps identified.** The implementation correctly separates Misc Pool document storage from the knowledge graph generation pipeline at every layer.

2. **Separation of concerns is architectural:** The Misc Pool upload path (`POST /documents`) and the project-scoped ingestion path (`POST /projects/:id/ingest/document`) are completely separate code paths. The former never calls `processIngestion()` or any generation function.

3. **`pending_affiliation` as a guard:** The explicit `validityStatus: 'pending_affiliation'` on Misc Pool documents provides a defense-in-depth measure. Even if a future worker were to query the `documents` table, it would need to explicitly filter for this status.

4. **No tests for Misc Pool upload path.** While the implementation is correct, there are no unit or integration tests specifically verifying that the Misc Pool upload handler does not trigger generation. This is a test coverage gap, not an implementation gap.

5. **Note on the `/api/documents/ingest` frontend path:** The frontend (`documents.tsx:118-120`) has a fallback URL `/api/documents/ingest` for Misc Pool uploads without a project, but the backend route is `POST /documents` (without `/ingest`). This may be a minor routing discrepancy in the frontend, but it does not affect the core requirement of no L1/L2/L3 generation.

## Final Verdict: PASS

The Misc Pool extraction is correctly implemented: documents uploaded without a project are stored with their content and SHA-256 hash, marked with `validityStatus: 'pending_affiliation'`, and never trigger L1/L2/L3 generation or review task creation. Background workers operate exclusively on the `l3_nodes` table, which Misc Pool documents never enter. The separation between the Misc Pool upload path and the project-scoped generation pipeline is architecturally clean and complete.
