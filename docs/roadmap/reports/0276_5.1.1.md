## Round 1 — Schema & Route Verification

### Review Tasks Schema (`review_tasks.ts`)

The `reviewTasksTable` defines the following structure:

```typescript
export const reviewTasksTable = pgTable("review_tasks", {
  id: serial("id").primaryKey(),
  entityType: reviewEntityTypeEnum("entity_type").notNull(),  // l1_tag | l2_node | l3_node
  entityId: integer("entity_id").notNull(),
  taskType: reviewTaskTypeEnum("task_type").notNull(),         // anchor | correct | validate | merge
  status: reviewStatusEnum("status").notNull().default("pending"), // pending | approved | rejected | deferred
  description: text("description"),
  correctedValue: text("corrected_value"),
  createdAt: timestamp("created_at").notNull().defaultNow(),
  resolvedAt: timestamp("resolved_at"),
});
```

The schema supports all three entity types (L1, L2, L3) and all four task types required by the design spec.

### Route Registration

- `GET /review-tasks` — list all tasks (enriched with entity names)
- `GET /review-tasks/stats` — pending/approved/rejected/deferred counts
- `PATCH /review-tasks/:id` — resolve a task (approve/reject with optional correction)

### OpenAPI Spec

The `review-tasks` tag is defined in `openapi.yaml` with the description "Human review and correction tasks". The routes are properly documented.

## Round 2 — Review Task Creation Coverage (The Core Check)

The design spec requires that **every** AI-generated node creates a review task. I traced all code paths in `generate.ts` where AI-generated nodes are produced.

### L1 Tag Creation (line 713)

When a new L1 tag is created by the AI, a review task is immediately inserted:

```typescript
// Line 713-719
await db.insert(reviewTasksTable).values({
  entityType: "l1_tag",
  entityId: created.id,
  taskType: "anchor",
  status: "pending",
  description: `New L1 tag "${tag.name}" generated by AI — review and anchor if accurate`,
});
reviewTasksCreated++;
```

✅ Every new AI-generated L1 tag gets an `anchor` review task.

### L2 Node Creation (lines 908-918, 1078-1102)

New L2 nodes are inserted with `needsReview: true` (line 917). After all L2 processing, a post-processing loop creates review tasks for every L2 node with `needsReview: true` that doesn't already have a pending review task:

```typescript
// Line 1078-1102
const postL2 = await db.select().from(l2NodesTable)
  .where(and(eq(l2NodesTable.projectId, projectId), eq(l2NodesTable.needsReview, true)));
// ... deduplication check ...
await db.insert(reviewTasksTable).values({
  entityType: "l2_node",
  entityId: node.id,
  taskType: "validate",
  status: "pending",
  description: `AI-generated L2 node: "${node.name}" — verify this component classification is accurate`,
});
```

✅ Every new AI-generated L2 node gets a `validate` review task. Deduplication prevents duplicate tasks.

### L2 Node Update (lines 894-907)

When an existing L2 node is updated by the AI, it sets `needsReview: true` (line 902). This means the post-processing loop at lines 1078-1102 will also catch updated nodes. However, the deduplication check (`coveredL2Ids`) prevents creating a new task if one already exists for that node.

✅ Updated L2 nodes are flagged for review. The post-processing loop handles them.

### L3 Node Creation — Low Confidence (lines 1044-1054)

New L3 nodes with confidence < 0.8 get a review task:

```typescript
// Line 1044-1054
if (confidence < 0.8) {
  await db.insert(reviewTasksTable).values({
    entityType: "l3_node",
    entityId: l3node.id,
    taskType: "validate",
    status: "pending",
    description: `AI-generated L3 node (confidence ${Math.round(confidence * 100)}%): "${l3data.title}" — verify content accuracy`,

```

⚠️ **Gap identified**: Only L3 nodes with confidence < 0.8 get a review task. High-confidence L3 nodes (≥ 0.8) do **not** get a review task. The design spec says "every AI-suggested L1 tag, L2 node, and L3 decision record creates a review_task row."

## Round 3 — Deduplication, Idempotency & Edge Cases

### Duplicate Prevention

The code implements deduplication at multiple levels:

1. **L1 noise detection** (lines 359-370, 393-404): Checks for existing pending tasks before inserting.
2. **L2 post-processing** (lines 1083-1092): Queries all pending L2 review tasks and skips nodes already covered.
3. **Cross-project links** (lines 293-306): Checks for existing pending merge tasks before inserting.

✅ Deduplication is properly implemented to prevent task accumulation on repeated pipeline runs.

### Idempotency

The generate endpoint uses incremental mode (tracking `processedAt` on commits) to avoid reprocessing the same commits. Combined with the deduplication checks, this means repeated runs won't create duplicate review tasks.

✅ Idempotency is maintained through cursor-based incremental processing and deduplication.

### High-Confidence L3 Gap Analysis

The confidence threshold of 0.8 is hardcoded at line 1045. While it's reasonable to skip review for high-confidence nodes as an optimization, this is a deviation from the strict "every AI-generated node" requirement in the design spec. The `reviewTasksCreated` counter (returned in the API response at line 1163) only counts tasks actually created, so the response accurately reflects what was done.

**Possible justification**: High-confidence L3 nodes may be considered "good enough" to auto-approve. However, the design spec (ADR-006) explicitly states "All AI-generated nodes are created with `status: "pending"` in `review_tasks`" with no confidence-based exemption.

### Edge Case: L3 Dedup Path (Existing Nodes)

When an L3 node is matched as a duplicate (line 988-1016), the occurrence count is incremented but no new node is created. If the condensation threshold is reached, a review task is created for the *existing* node. This is correct behavior — the existing node's content is being modified by AI, so it needs review.

✅ The dedup path correctly handles review task creation for condensed nodes.

## Final Verdict: ⚠️ WARN

Review task creation is implemented for the vast majority of AI-generated nodes:

- **L1 tags**: Every new AI-generated L1 tag gets an `anchor` review task.
- **L2 nodes**: Every new or updated AI-generated L2 node gets a `validate` review task (via post-processing loop with deduplication).
- **L3 nodes (low confidence)**: Nodes with confidence < 0.8 get a `validate` review task.
- **L3 nodes (condensed)**: Nodes that reach the condensation threshold get a `validate` review task.
- **Supplementary**: Noise detection and cross-project link detection create additional `anchor` and `merge` tasks.

**Gap**: High-confidence L3 nodes (confidence ≥ 0.8) do **not** receive a review task. This is a deviation from ADR-006 which states "All AI-generated nodes are created with `status: "pending"` in `review_tasks`." The confidence threshold at line 1045 of `generate.ts` should either be removed (to create tasks for all L3 nodes) or the design spec should be updated to document this intentional exemption.
