## Round 1 — Schema & Type Definition Verification

### Review Task Type Enum (`review_tasks.ts`)

The database schema defines the `review_task_type` enum with **four** values:

```typescript
export const reviewTaskTypeEnum = pgEnum("review_task_type", [
  "anchor",
  "correct",
  "validate",
  "merge",
]);
```

### Checklist Expectation vs. Schema

The checklist item 5.1.2 specifies three types: **anchor**, **merge**, **reject**.

| Expected by 5.1.2 | In Schema | Match? |
|--------------------|-----------|--------|
| anchor | anchor | ✅ |
| merge | merge | ✅ |
| reject | — | ❌ Not a task type |
| — | correct | ⚠️ Extra type |
| — | validate | ⚠️ Extra type |

**Analysis**: The checklist item description "anchor, merge, reject" is slightly misleading. "Reject" is not a task type — it is a **resolution action** (a value of the `review_status` enum: `pending | approved | rejected | deferred`). The actual task types in the schema are `anchor`, `correct`, `validate`, and `merge`. Of these:
- **`anchor`** — used for new AI-generated L1 tags (confirm the tag should exist)
- **`merge`** — used for cross-project similarity detection and near-duplicate L1 tags
- **`validate`** — used for AI-generated L2 and L3 nodes (verify accuracy)
- **`correct`** — defined but **never used** anywhere in the codebase

### OpenAPI Spec

The `ReviewTask` schema in `openapi.yaml` defines `taskType` as:
```yaml
taskType:
  type: string
  enum: [anchor, correct, validate, merge]
```

This matches the DB schema and generated Zod types.

| Aspect | Status | Details |
|--------|--------|---------|
| `anchor` type exists | ✅ | Used for L1 tag review tasks |
| `merge` type exists | ✅ | Used for cross-project and duplicate detection |
| `reject` as task type | ❌ | Not a task type — it's a resolution status |

**Round 1 Verdict: WARN** — The schema defines 4 task types while the checklist references 3. "Reject" is a resolution action, not a task type. The `correct` type is defined but never instantiated.

## Round 3 — Semantic Correctness & Design Alignment

### Design Intent (ADR-006)

ADR-006 states: "Humans review and either **anchor**, **merge**, or **reject**." This describes three **human actions**, not three task types. The implementation maps these actions to resolution statuses (`approved` ≈ anchor, `rejected` ≈ reject), while `merge` is both a task type and an implicit action (merging two nodes).

### Task Type Semantics

| Task Type | Semantic Meaning | Implementation |
|-----------|-----------------|----------------|
| `anchor` | "Should this node exist in the graph?" | ✅ Used for new L1 tags and noise-flagged tags |
| `merge` | "Should these two nodes be combined?" | ✅ Used for cross-project links and near-duplicate tags |
| `validate` | "Is this AI-generated content accurate?" | ✅ Used for L2/L3 nodes |
| `correct` | "Does this content need correction?" | ❌ **Never used** — no code path creates this |

### The `correct` Gap

The `correct` task type appears to have been intended for tasks where the reviewer provides a corrected value. However, the resolution endpoint already handles corrections for **all** task types — when a reviewer approves with a `correctedValue`, the system writes back to the node and creates a `correction_examples` row. This means the correction capability is built into the resolution flow generically, making a separate `correct` task type unnecessary.

### The Checklist Description Issue

The checklist item 5.1.2 says "Review task types: anchor, merge, reject" but:
1. There are **4** task types in the schema, not 3
2. "Reject" is a **resolution status**, not a task type
3. The actual types are: `anchor`, `correct`, `validate`, `merge`

The checklist description conflates task types (`anchor`, `merge`) with resolution actions (`reject`). The design spec (ADR-006) also uses "anchor, merge, reject" to describe human actions, not task types.

### Round 3 Findings

| Aspect | Status | Details |
|--------|--------|---------|
| `anchor` semantics match design | ✅ | Used for confirming new tags |
| `merge` semantics match design | ✅ | Used for combining similar/duplicate nodes |
| `validate` semantics are sound | ✅ | Used for verifying AI content accuracy |
| `correct` type is dead code | ⚠️ | Defined but never instantiated |
| Checklist description is imprecise | ⚠️ | Conflates task types with resolution actions |

**Round 3 Verdict: WARN** — The `correct` task type is dead code. The checklist description is imprecise but the implementation is functionally sound for the three active types.

## Final Verdict: ⚠️ WARN

The review task type system is **functionally implemented** for three of four defined types:

- **`anchor`**: Properly used for L1 tag review (new tags + noise detection).
- **`merge`**: Properly used for cross-project similarity and near-duplicate detection.
- **`validate`**: Properly used for L2/L3 node verification.

**Issues:**

1. **`correct` is dead code** — The `correct` task type is defined in the database schema, OpenAPI spec, and Zod types, but no code in the codebase ever creates a review task with `taskType: "correct"`. It should either be removed from the schema/spec or implemented. The correction capability is already built into the resolution flow generically (any task type can have a `correctedValue`), so a separate `correct` type may be unnecessary.

2. **Checklist description is imprecise** — Item 5.1.2 says "anchor, merge, reject" but "reject" is a resolution status, not a task type. The actual task types are `anchor`, `correct`, `validate`, and `merge`. The checklist description should be updated to match the actual schema, or the schema should be aligned with the intended design.
