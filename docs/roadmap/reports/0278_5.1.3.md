## Round 2 — Resolution Logic Verification

### What Happens When a Review Task Is Resolved

The resolution handler at lines 109-197 of `review_tasks.ts` performs the following:

1. **Parse + validate input** (lines 110-111):
   - `id` from path params → `ResolveReviewTaskParams.parse()` → coerced number
   - `body` from request → `ResolveReviewTaskBody.parse()` → `{ status, correctedValue? }`

2. **Update the task row** (lines 112-121):

   ```typescript
   db.update(reviewTasksTable)
     .set({
       status: body.status,
       correctedValue: body.correctedValue ?? null,
       resolvedAt: new Date(),
     })
     .where(eq(reviewTasksTable.id, id))
     .returning();
   ```

   - Returns 404 if task not found.

3. **Writeback correction to the actual node** (lines 123-181):
   - Only when `body.correctedValue` is truthy AND `task.status === "approved"`:
     - **`l2_node`**: Updates `l2NodesTable.description`, sets `needsReview: false`, `aiGenerated: false`; inserts into `correctionExamplesTable`.
     - **`l3_node`**: Updates `l3NodesTable.content`; inserts into `correctionExamplesTable` with projectId from parent L2.
     - **`l1_tag`**: Updates `l1TagsTable.description` (no correction example recorded).

4. **Mark L2 nodes as reviewed on approve/reject** (lines 183-189):
   - Sets `needsReview: false` for L2 entities regardless of whether a correctedValue was provided.

5. **Activity log entry** (lines 191-194):
   - Records `review_resolved` event with description including task ID, status, and whether correction was applied.

6. **Return enriched task** (lines 195-196):
   - Calls `enrichTask(task)` which fetches related entity name, project name, node content, and node type.

## Round 3 — HTTP Semantics, Idempotency & Design Alignment

### HTTP Method Justification

The design spec says `POST /review_tasks/:id/resolve`, while the implementation uses `PATCH /review-tasks/{id}`. The implementation's choice of `PATCH` is actually more semantically appropriate:

- `PATCH` signals a partial update to an existing resource (the review task's status).
- The `/resolve` suffix in the design spec is redundant — the `PATCH` method already conveys the intent.
- The OpenAPI spec (which is the SSOT per ADR-001) correctly defines it as `PATCH`.

The design spec sequence diagram is outdated/wrong about the HTTP method and body field names.

### Idempotency

The resolution endpoint is **not idempotent**: calling it twice on the same task will:

1. First call: Set status, resolvedAt, writeback → returns enriched task.
2. Second call: Set status again (overwriting previous), set resolvedAt to new timestamp → returns enriched task with updated resolvedAt.

There is no guard against re-resolving an already-resolved task. The frontend handles this by disabling buttons for non-pending tasks (`task.status === "pending"` check at line 185 in review.tsx), but the backend does not enforce this.

### Deferred Resolution

The `deferred` status is accepted by both the Zod schema and the OpenAPI enum, and correctly handled: a deferred task gets `status: "deferred"` and `resolvedAt` set, but no writeback occurs (since `body.correctedValue` is undefined and `task.status !== "approved"`). The task remains in the queue but marked as deferred rather than pending.

### Field Name Discrepancy: `action` vs `status`

The design spec sequence diagram shows `{ action: "anchor" }` but the implementation uses `{ status: "approved" }`. The mapping is:

- `action: "anchor"` → `status: "approved"` (accept the AI-generated node)
- `action: "reject"` → `status: "rejected"` (reject the node)
- `action: "merge"` → handled differently (merge is a task type, not a resolution action)

### Frontend Alignment

The Review UI (`review.tsx`) calls the endpoint correctly:

```typescript
resolveTask.mutate({ id, data: { status, correctedValue } });
```

This uses the generated `useResolveReviewTask` hook which calls `PATCH /api/review-tasks/{id}`. After success, it invalidates both the task list and stats queries. The UI provides three resolution actions: Approve, Reject, Defer — matching the three allowed status values.

## Final Verdict: ⚠️ WARN

The review resolution endpoint is **functionally implemented** and operational:

- **`PATCH /api/review-tasks/:id`** accepts `{ status: "approved" | "rejected" | "deferred", correctedValue? }` and correctly updates the task, writes back corrections to L2/L3 nodes, creates correction examples (for L2/L3), logs the event, and returns the enriched task.

**Issues:**

1. **Design spec sequence diagram is outdated** — `06-runtime-scenarios.md` line 120 documents `POST /review_tasks/:id/resolve { action: "anchor" }` which doesn't match the actual API (`PATCH /review-tasks/{id} { status: "approved" }`). The sequence diagram should be updated to reflect the OpenAPI spec.

2. **L1 tag corrections not recorded in `correction_examples`** — When an L1 tag is approved with a corrected description, the description is written back to `l1TagsTable` but no row is inserted into `correctionExamplesTable`. This breaks the continuous improvement loop for L1 tags.

3. **No backend guard against re-resolution** — The backend does not check if a task is already resolved before processing. While the frontend prevents this by hiding action buttons for non-pending tasks, the API itself is open to re-resolution via direct calls.
