## Round 1 — Correction Example Creation on L2/L3 Approval

### What the Design Spec Says

ADR-006 states: "Approved corrections are stored in `correction_examples` and injected as few-shot prompts in subsequent pipeline runs." The sequence diagram in `06-runtime-scenarios.md` line 120 shows the API inserting into `correction_examples` on review approval.

The requirement is: when a review task is resolved with `status: "approved"` and a `correctedValue` is provided, a row should be inserted into `correction_examples` capturing the original content and the human-corrected content.

### What the Implementation Provides

In `review_tasks.ts`, the resolution handler (lines 109-197) contains the following logic at lines 123-181:

```typescript
if (body.correctedValue && task.status === "approved") {
  if (task.entityType === "l2_node") {
    // lines 131-138: INSERT into correctionExamplesTable
    await db.insert(correctionExamplesTable).values({
      projectId: node.projectId,
      entityType: "l2_node",
      entityId: task.entityId,
      originalContent: node.description,
      correctedContent: body.correctedValue,
    });
    // lines 139-146: UPDATE l2NodesTable
  } else if (task.entityType === "l3_node") {
    // lines 157-164: INSERT into correctionExamplesTable
    await db.insert(correctionExamplesTable).values({
      projectId: l2?.projectId ?? null,
      entityType: "l3_node",
      entityId: task.entityId,
      originalContent: node.content,
      correctedContent: body.correctedValue,
    });
    // lines 167-172: UPDATE l3NodesTable
  } else if (task.entityType === "l1_tag") {
    // lines 173-179: UPDATE l1TagsTable ONLY — no correction_examples insert
    await db.update(l1TagsTable).set({
      description: body.correctedValue,
    }).where(eq(l1TagsTable.id, task.entityId));
  }
}
```

### Round 1 Findings

| Entity Type | Correction Example Created | Original Content Captured | Corrected Content Captured | Project ID |
|-------------|---------------------------|--------------------------|---------------------------|------------|
| `l2_node` | ✅ Yes | `node.description` | `body.correctedValue` | `node.projectId` |
| `l3_node` | ✅ Yes | `node.content` | `body.correctedValue` | `l2?.projectId ?? null` |
| `l1_tag` | ❌ **No** | — | — | — |

| Aspect | Status | Details |
|--------|--------|---------|
| L2 node correction example | ✅ | Inserted with correct fields |
| L3 node correction example | ✅ | Inserted with correct fields; projectId resolved via parent L2 |
| L1 tag correction example | ❌ | **Missing** — description is updated but no `correction_examples` row is created |
| Guard condition | ✅ | Only creates when `body.correctedValue && task.status === "approved"` |
| Null original content guard | ⚠️ | L2: `if (node && node.description)` — skips insert if description is null/empty. L3: `if (node.content)` — same. This means corrections where the original was empty are silently dropped. |

**Round 1 Verdict: WARN** — L2 and L3 nodes correctly create correction examples. L1 tags do not, breaking the continuous improvement loop for L1 tags. Additionally, the null-content guards mean that if the original node had no content/description, the correction example is silently skipped even though the human provided a meaningful correction.

## Round 2 — Consumption of Correction Examples (Few-Shot Injection)

### What the Design Spec Says

ADR-006: "Approved corrections are stored in `correction_examples` and **injected as few-shot prompts in subsequent pipeline runs**."

### What the Implementation Provides

In `generate.ts`, the `getRecentCorrections()` function (lines 88-104) fetches the 5 most recent correction examples for a given project and entity type:

```typescript
async function getRecentCorrections(
  projectId: number,
  entityType: "l2_node" | "l3_node"
): Promise<Array<{ original: string; corrected: string }>> {
  const examples = await db
    .select()
    .from(correctionExamplesTable)
    .where(and(
      eq(correctionExamplesTable.projectId, projectId),
      eq(correctionExamplesTable.entityType, entityType)
    ))
    .orderBy(sql`${correctionExamplesTable.createdAt} desc`)
    .limit(5);
  return examples.map((e) => ({ original: e.originalContent, corrected: e.correctedContent }));
}
```

The `buildFewShotSection()` function (lines 106-117) formats them into a prompt section:

```
Previous human corrections (use these as quality guidance):
Example 1:
  Original: "..."
  Corrected: "..."
```

This is injected into the L2 generation prompt at line 245:
```typescript
const fewShotSection = buildFewShotSection(corrections);
```

And included in the user message at line 261:
```
Available L1 tags...${fewShotSection}...Commits to analyze:...
```

### Round 2 Findings

| Aspect | Status | Details |
|--------|--------|---------|
| Fetch correction examples | ✅ | `getRecentCorrections()` queries by projectId + entityType, ordered by createdAt desc, limit 5 |
| Few-shot formatting | ✅ | `buildFewShotSection()` produces clear original→corrected examples |
| Injected into L2 generation | ✅ | Passed to `generateL2Nodes()` and included in the user prompt |
| Injected into L3 generation | ⚠️ | `generateL2Nodes()` produces L3 nodes as nested output, so the few-shot applies to the combined L2+L3 generation. There is no separate L3-specific few-shot injection. |
| Injected into L1 generation | ❌ | `generateL1Tags()` (line 180) does **not** accept or use corrections. No few-shot for L1. |
| Entity type filter | ✅ | Filtered by `entityType` so L2 corrections don't leak into L3 context and vice versa |
| Project scope | ✅ | Filtered by `projectId` — corrections are project-specific |
| Limit | ✅ | `.limit(5)` prevents context bloat |

**Round 2 Verdict: WARN** — The few-shot injection pipeline works correctly for L2/L3 generation. However: (1) L1 tag generation does not use correction examples at all, and (2) L3 nodes receive few-shot context only indirectly through the combined L2+L3 generation prompt (since `generateL2Nodes` produces both L2 and L3 output). This is a design choice rather than a bug, but it means L3-specific corrections may be less effective as few-shot signals.

## Round 3 — Distillation Loop & End-to-End Flow

### What the Design Spec Says

ADR-006 Self-Evolution Architecture describes the full closed loop:
1. Developer corrects AI output → stored in `correction_examples`
2. Background distillation job detects unprocessed rows (`processedAt IS NULL`)
3. LLM compresses raw corrections into architectural guardrails
4. Guardrails inserted into `prompt_templatesTable`
5. Future pipeline runs use updated prompts → fewer hallucinations

### What the Implementation Provides

In `metabolism.ts`, the `runMetabolism()` function (lines 15-148):

**Distillation Job (lines 89-145):**
```typescript
const pendingCorrections = await db
  .select()
  .from(correctionExamplesTable)
  .where(isNull(correctionExamplesTable.processedAt))
  .limit(10);
```

For each pending correction:
1. Calls LLM (`gpt-4o-mini`) with the original and corrected content
2. Asks the LLM to "extract a concise, single-sentence architectural guardrail/rule"
3. Inserts the guardrail as a new `promptTemplatesTable` row with `templateType: "l3_generator"`
4. Marks corrections as processed by setting `processedAt`

### End-to-End Flow Verification

| Step | Component | Status | Details |
|------|-----------|--------|---------|
| 1. Human approves with correction | `review_tasks.ts` | ✅ (L2/L3) / ❌ (L1) | Correction example created for L2/L3, not L1 |
| 2. Row has `processedAt = NULL` | `correction_examples` schema | ✅ | `processedAt` column exists and defaults to null |
| 3. Metabolism job picks up unprocessed rows | `metabolism.ts` | ✅ | `WHERE processedAt IS NULL` with `LIMIT 10` |
| 4. LLM distills into guardrail | `metabolism.ts` | ✅ | Uses `gpt-4o-mini`, extracts single-sentence rule |
| 5. Guardrail stored as prompt template | `metabolism.ts` | ✅ | Inserted into `promptTemplatesTable` with `isActive: true` |
| 6. Correction marked processed | `metabolism.ts` | ✅ | `processedAt` set to `new Date()` |
| 7. Generate pipeline uses new template | `generate.ts` | ✅ | `getPromptTemplate()` checks project-specific templates first, then global |
| 8. Template type alignment | — | ⚠️ | Distillation inserts as `templateType: "l3_generator"`, but the generate pipeline also uses `l1_tagger` and `l2_extractor` template types. L1 corrections are never distilled (since they're never captured). |

### Round 3 Findings

| Aspect | Status | Details |
|--------|--------|---------|
| Closed loop exists | ✅ | The full chain from correction → distillation → prompt update → next pipeline run is implemented |
| Distillation job trigger | ⚠️ | Triggered via `GET /metabolism-tick` or `GET /admin/metabolism-tick` — no automatic scheduler. Requires external cron or manual invocation. |
| Template type for distilled guardrails | ⚠️ | Always `l3_generator` — even if the correction was for an L2 node. This means distilled L2 corrections only affect the L3 generation prompt, not the L2 extraction prompt. |
| L1 gap propagates | ❌ | Since L1 corrections are never captured in `correction_examples`, they can never be distilled into prompt templates. The self-evolution loop is broken for L1 tags. |
| Idempotency of distillation | ✅ | `processedAt` guard prevents re-processing the same correction |
| Batch limit | ✅ | `LIMIT 10` per tick prevents runaway LLM costs |
| Error handling | ✅ | Individual correction failures are caught and logged; don't block the batch |

**Round 3 Verdict: WARN** — The distillation loop is architecturally complete and functional. The main issues are: (1) L1 corrections are never captured, so they can never enter the distillation pipeline; (2) distilled guardrails are always typed as `l3_generator` regardless of the source entity type; (3) the metabolism job requires external triggering (no built-in scheduler).

## Final Verdict: ⚠️ WARN

Correction examples creation on review approval is **partially implemented**:

**What works:**
- When a reviewer approves an L2 or L3 review task with a `correctedValue`, a row is correctly inserted into `correction_examples` with the original content, corrected content, project ID, entity type, and entity ID.
- The generate pipeline fetches recent correction examples and injects them as few-shot prompts into the L2/L3 generation LLM call.
- The background distillation job processes unprocessed correction examples into architectural guardrails stored as prompt templates, completing the self-evolution loop.

**Issues:**

1. **L1 tag corrections are never recorded in `correction_examples`** — When an L1 tag review task is approved with a corrected description, the description is written back to `l1TagsTable` but no row is inserted into `correctionExamplesTable`. This breaks the continuous improvement loop for L1 tags. The fix would be to add a `correctionExamplesTable.insert()` call in the `l1_tag` branch at line 173 of `review_tasks.ts`.

2. **L1 tag generation does not use few-shot corrections** — `generateL1Tags()` does not accept or inject correction examples. Even if L1 corrections were captured, they would not be used during L1 generation.

3. **Null original content silently drops corrections** — The guards `if (node && node.description)` (L2) and `if (node.content)` (L3) skip creating a correction example when the original content is null/empty. This means the first correction to a newly-created node (which may have empty content) is lost.

4. **Distillation always uses `templateType: "l3_generator"`** — Corrections distilled from L2 node corrections are still stored as `l3_generator` templates, which may not be the right template type for the correction's origin.
