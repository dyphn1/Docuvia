## Round 1 — Architecture & Design Review

**What the spec says:** The review queue should allow users to filter tasks by status and display them in a clear, actionable list. Users need to see what requires attention (pending), what was already handled (approved/rejected/deferred), and be able to navigate between these views efficiently.

**What the implementation does:** The review page implements a tabbed filter bar with four status tabs (pending, approved, rejected, deferred), each showing a count badge. Tasks are displayed as expandable `TaskCard` components showing entity type, node type, task type, description, and expandable node content. A right sidebar shows aggregate stats.

**Architecture assessment:**

- **Filter tabs:** Implemented at `review.tsx:286-305` — four buttons (pending/approved/rejected/deferred) with `filter` state driving `filteredTasks` at line 266. ✅
- **Tab counts:** Computed at `review.tsx:267-272` by filtering the full task array per status. Counts update after resolution via query invalidation. ✅
- **Task list rendering:** `review.tsx:326-330` maps `filteredTasks` to `TaskCard` components. ✅
- **Empty state:** `review.tsx:316-324` shows contextual empty messages per filter (e.g., "Run the AI pipeline..." for pending). ✅
- **Loading state:** `review.tsx:309-314` shows skeleton placeholders during loading. ✅
- **Stats sidebar:** `review.tsx:335-404` displays pending count (highlighted), approved/rejected/deferred counts, and "Reviewed Today" total. ✅
- **Auto-refresh:** Both list and stats queries use `refetchInterval: 10000` (10 seconds). ✅
- **Backend list endpoint:** `review_tasks.ts:68-75` returns all tasks ordered by `createdAt desc`, enriched with entity names and project names. ✅
- **Backend stats endpoint:** `review_tasks.ts:77-107` returns counts per status + today total. ✅

**Findings:**

1. **Client-side filtering only** (`review.tsx:266`): The filter is applied client-side on the full task list. The `GET /review-tasks` endpoint has no server-side status filter parameter. This works for small datasets but will degrade as task volume grows — the entire task table is fetched and transferred on every 10-second poll.
2. **No server-side pagination:** The list endpoint returns all tasks with no `limit`/`offset` support. Combined with auto-refresh, this means the browser accumulates the full task history indefinitely.
3. **Tab counts are O(n) per render:** `review.tsx:267-272` runs four `.filter()` passes on every render. For a list of hundreds of tasks this is negligible, but it could be a single `reduce()` pass.

## Round 2 — Code Quality & Security Review

**Filter implementation quality:**

- The filter state is a simple `useState<string>("pending")` at `review.tsx:236`. The default filter is "pending" — correct UX for a review queue. ✅
- Filter tabs use a clean `as const` array pattern at line 287: `(["pending", "approved", "rejected", "deferred"] as const)`. ✅
- Active tab styling uses conditional classes with `bg-primary text-primary-foreground` for the selected state. ✅
- Count badges adapt styling based on active state: `bg-primary-foreground/20` for active, `bg-muted` for inactive. ✅

**TaskCard display quality:**

- Entity type icons mapped via `entityIcons` object (`review.tsx:34-38`): l1_tag → Tag, l2_node → GitMerge, l3_node → Network, fallback → Layers. ✅
- Node type badge colors mapped for 7 types (`review.tsx:40-48`): module, package, pcd, change, rule, decision, context. ✅
- Expand/collapse with chevron toggle (`review.tsx:113-122`). ✅
- Inline edit mode with "Edit & Correct" button (`review.tsx:148-155`). ✅
- Correction display for resolved tasks (`review.tsx:172-181`): shows green-highlighted corrected value. ✅
- Date formatting via `date-fns` (`format(new Date(task.createdAt), "MMM d HH:mm")`). ✅

**Security:**

- No direct security concerns in the filter/display logic. Auth is handled at the API layer.
- The `PATCH /review-tasks/:id` endpoint uses Zod validation (`ResolveReviewTaskParams`, `ResolveReviewTaskBody`). ✅
- No XSS vectors: React escapes all rendered content. ✅

**Code quality issues:**

1. **`as any` cast** (`review.tsx:328`): `<TaskCard key={task.id} task={task as any} onResolve={handleResolve} />` — the `ReviewTask` type from the generated client should be used directly. The `TaskCardProps` interface is hand-written and mostly matches but isn't type-linked to the generated type.
2. **No error state for mutation** (`review.tsx:253-261`): `resolveTask.mutate` has `onSuccess` but no `onError` callback. If resolution fails, the user gets no feedback. The `Toaster` component is already available in the app.
3. **Stats endpoint makes 5 separate queries** (`review_tasks.ts:78-106`): One query per status count + one for today total. Could be a single `GROUP BY` query or a single query with conditional aggregation.

**Test coverage:**

- **Zero frontend tests** for the review page. `artifacts/kg-engine/` has zero `*.test.*` files. The filter tabs, tab counts, empty states, and task card display are all untested.
- **Zero backend tests** for review_tasks routes. `artifacts/api-server/test/` has no review-related test files. The stats aggregation, filtering, and enrichment logic are all untested.
- The `review_tasks.ts` route handler has non-trivial logic (enrichTask with 3 entity type branches, stats with 5 queries, correction writeback) that is entirely untested.

**Missing features / gaps:**

1. **No server-side status filter** — `GET /review-tasks` returns all tasks regardless of status. The filter is applied client-side. For large datasets, this is a performance concern.
2. **No pagination** — the list endpoint returns all tasks with no limit/offset. Combined with 10-second auto-refresh, this will cause unbounded memory growth in the browser.
3. **No project-level filtering** — tasks from all projects are shown in a flat list. The layout has a project selector in the header but it doesn't affect the review page.
4. **No error feedback on mutation failure** — `handleResolve` has no `onError` callback.
5. **No test coverage** — zero tests for frontend filter/display or backend list/stats endpoints.
6. **Stats endpoint inefficiency** — 5 separate DB queries where 1 conditional aggregation would suffice.

## Gaps & Recommendations

1. **Add server-side status filter** (`review_tasks.ts:68-75`): Add an optional `status` query parameter to `GET /review-tasks` and filter with `.where(eq(reviewTasksTable.status, status))` when provided. Update the frontend to pass the current filter value. This reduces data transfer and shifts filtering to the DB.

2. **Add pagination** (`review_tasks.ts:68-75`): Add `limit`/`offset` query parameters to the list endpoint. On the frontend, implement infinite scroll or pagination controls. This prevents unbounded memory growth.

3. **Add project filter to review queue**: Add a project dropdown to the review page (the layout already has a project selector in the header). Pass `projectId` to the backend and filter tasks by project. Requires joining through entity tables or adding `projectId` to the review_tasks table.

4. **Add error handling to resolve mutation** (`review.tsx:253-261`): Add `onError` callback to `resolveTask.mutate` to show a toast notification when resolution fails. The `Toaster` component is already imported in the app.

5. **Optimize stats endpoint** (`review_tasks.ts:77-106`): Replace 5 separate `count()` queries with a single `SELECT status, count(*) FROM review_tasks GROUP BY status` query plus one for today's count. Reduces DB round-trips from 5 to 2.

6. **Add tests**: Add integration tests for the review_tasks API (list with status filter, stats aggregation, resolve flow) and at minimum a snapshot test for the review page filter tabs and empty states.
