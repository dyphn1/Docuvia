## Round 1 — Architecture & Design Review

**What the spec says:** The review UI must provide Approve, Reject, and Defer action buttons on each task card. Clicking any button calls `PATCH /review-tasks/:id` with the corresponding status. An inline correction textarea should appear when the user clicks "Edit & Correct", and the corrected value is submitted alongside `approved` status. The stats badge should update after resolution.

**What the implementation does:** The `TaskCard` component renders three action buttons in its `CardFooter` (shown only when `task.status === "pending"`): Defer, Reject, and Approve. An "Edit & Correct" toggle switches the card into edit mode with a textarea. When in edit mode, the Approve button changes to "Save & Approve" and submits the corrected value.

**Action button mapping:**

| Button             | Location             | Behavior                                                                    |
| ------------------ | -------------------- | --------------------------------------------------------------------------- |
| **Defer**          | `review.tsx:194-201` | Calls `onResolve(task.id, "deferred")` — no correction                      |
| **Reject**         | `review.tsx:202-209` | Calls `onResolve(task.id, "rejected")` — no correction                      |
| **Approve**        | `review.tsx:218-226` | Calls `onResolve(task.id, "approved")` — no correction                      |
| **Save & Approve** | `review.tsx:210-217` | Calls `onResolve(task.id, "approved", correction)` — submits edited content |

**Findings:**

1. **All three action buttons exist and are wired correctly.** Defer, Reject, and Approve buttons are rendered for pending tasks (`review.tsx:185`). Each calls `onResolve` with the correct status string matching the OpenAPI enum. ✅
2. **Edit mode with correction textarea works.** The "Edit & Correct" button (`review.tsx:148-155`) toggles `editMode` state. When active, a `Textarea` replaces the read-only content pre block (`review.tsx:157-168`). The "Save & Approve" button submits the correction (`review.tsx:80-83`). ✅
3. **Correction writeback on approve is conditional.** `handleApproveWithCorrection` at `review.tsx:80-83` only passes `correctedValue` when `correction !== task.nodeContent`. This prevents unnecessary writebacks when content is unchanged. ✅
4. **No "merge" action button.** The checklist description says "Approve/merge/reject" but the actual UI has Defer/Reject/Approve. The "merge" task type in the schema (`review_tasks.ts:10`) is a review task _type_, not a resolution _action_. The UI correctly maps to the three resolution statuses defined in the OpenAPI spec (`approved`, `rejected`, `deferred`). The checklist description conflates task types with resolution actions. ✅ (no gap — the UI matches the spec)
5. **Stats badge updates after resolution.** `handleResolve` at `review.tsx:256-258` invalidates both the list and stats query keys, triggering a refetch. Combined with `refetchInterval: 10000`, the badge stays current. ✅
6. **Resolved tasks hide action buttons.** The `CardFooter` with all action buttons is conditionally rendered only when `task.status === "pending"` (`review.tsx:185`). Resolved tasks show their `correctedValue` if present (`review.tsx:172-181`). ✅

## Round 2 — Code Quality & Security Review

**Action button implementation quality:**

- Buttons use consistent styling: `variant="outline"` for Defer, `variant="destructive"` for Reject, default (primary) for Approve. Visual hierarchy is correct — Approve is the primary action on the right. ✅
- Icons from `lucide-react` provide clear visual cues: Clock (Defer), X (Reject), Check (Approve). ✅
- Button text uses sentence case consistently: "Defer", "Reject", "Approve", "Save & Approve". ✅

**Backend resolve handler quality (`review_tasks.ts:109-197`):**

- Zod validation on both params and body (`review_tasks.ts:110-111`). ✅
- Status is cast as `any` (`review_tasks.ts:115`) — minor type safety concern but functionally correct since the Zod schema already validates the enum. ⚠️
- Correction writeback to actual nodes: L2 (`review_tasks.ts:139-146`) and L3 (`review_tasks.ts:167-172`) nodes are updated with the corrected value. L1 tags get description updated (`review_tasks.ts:173-180`). ✅
- `needsReview: false` is set on L2 nodes for both approve and reject (`review_tasks.ts:184-189`). L3 nodes don't have `needsReview` — this is a minor inconsistency but not a functional gap since L3 validity is managed separately. ⚠️
- Activity log entry created for every resolution (`review_tasks.ts:191-194`). ✅
- 404 handling for non-existent task ID (`review_tasks.ts:121`). ✅

**Security:**

- No direct XSS vectors: React escapes all rendered content. ✅
- The `correctedValue` is stored as `text` in the DB — no sanitization needed for storage, and React handles safe rendering. ✅
- Auth is handled at the API layer (not in this route file). ✅

**Code quality issues:**

1. **No `onError` callback on resolve mutation** (`review.tsx:253-261`): If the PATCH request fails, the user gets no feedback. The `Toaster` component is available in the app but not used here.
2. **`as any` cast on task prop** (`review.tsx:328`): `task={task as any}` bypasses type checking. The `TaskCardProps` interface is hand-written and mostly matches the generated `ReviewTask` type but isn't type-linked.
3. **No re-resolve protection on the backend** (`review_tasks.ts:109-121`): The PATCH handler doesn't check if the task is already resolved. A task with `status !== "pending"` can be re-resolved, overwriting the previous resolution. The frontend hides buttons for non-pending tasks, but the API doesn't enforce this.

## Gaps & Recommendations

1. **Add re-resolve protection** (`review_tasks.ts:109-121`): At the start of the PATCH handler, query the existing task and return 409 Conflict if `status !== "pending"`. This prevents accidental overwrites and enforces the state machine invariant server-side.

2. **Add error handling to resolve mutation** (`review.tsx:253-261`): Add `onError` callback to `resolveTask.mutate` to show a toast notification when resolution fails. The `Toaster` component is already available in the app.

3. **Add tests**: Add integration tests for the resolve handler (approve/reject/defer, correction writeback, re-resolve rejection) and at minimum a snapshot test for the TaskCard action buttons.

4. **Fix type safety** (`review.tsx:328`): Replace `task as any` with proper typing by aligning `TaskCardProps` with the generated `ReviewTask` type or importing the generated type directly.

5. **Consider L3 needsReview consistency**: Either add `needsReview` to the L3 schema or document that L3 review status is tracked exclusively through the review_tasks table.
