## Round 1 — Architecture & Design Review

**What the spec says:** The `prompt_templates` table must store system prompt templates for L1, L2, and L3 generation. Projects inherit global default templates and can override them at the project level. The table should support CRUD operations scoped per project per type, with default fallback when no project-specific template exists.

**What the implementation does:**

### Schema (`prompt_templates.ts`)

The Drizzle schema defines:

- `id`: serial primary key
- `projectId`: integer FK → projects.id (nullable for global templates, ON DELETE CASCADE)
- `templateType`: pgEnum `prompt_template_type` with values `l1_tagger`, `l2_extractor`, `l3_generator` (NOT NULL)
- `systemPrompt`: text (NOT NULL)
- `isActive`: boolean (NOT NULL, default true)
- `createdAt`: timestamp (NOT NULL, default now())
- `updatedAt`: timestamp (NOT NULL, default now())

Zod schemas are generated via `drizzle-zod`: `insertPromptTemplateSchema` (omits id, createdAt, updatedAt) and `updatePromptTemplateSchema` (partial of insert).

### DDL Migration (`0000_short_ezekiel.sql`)

The SQL migration creates:

- `prompt_template_type` enum: `l1_tagger`, `l2_extractor`, `l3_generator`
- `prompt_templates` table with all columns matching the Drizzle schema
- FK constraint: `prompt_templates_project_id_projects_id_fk` (ON DELETE CASCADE)

### Findings

1. **Table exists with all required columns.** The `prompt_templates` table is defined in both Drizzle schema and SQL migration with matching columns: id, projectId, templateType, systemPrompt, isActive, createdAt, updatedAt. ✅
2. **Enum type covers all three template types.** `l1_tagger`, `l2_extractor`, `l3_generator` — matches the spec exactly. ✅
3. **projectId is nullable**, allowing global templates (projectId = NULL) as well as project-specific ones. This supports the inheritance model. ✅
4. **FK constraint with ON DELETE CASCADE** ensures templates are cleaned up when a project is deleted. ✅
5. **isActive column** allows soft-disabling templates without deletion. ✅
6. **Zod schemas are auto-generated from Drizzle** via `drizzle-zod`, ensuring type alignment between DB and validation layers. ✅
7. **Schema matches OpenAPI spec.** The `PromptTemplate` schema in `openapi.yaml` (lines 2321–2337) has properties: id, templateType, systemPrompt, isCustom, isActive, updatedAt — all derivable from the DB schema. The `isCustom` field is computed at the API layer (not stored in DB), which is correct. ✅

## Round 2 — Code Quality & Security Review

**Schema design quality:**

- The `promptTemplateTypeEnum` is defined using Drizzle's `pgEnum()`, which creates a proper PostgreSQL enum type. This is more type-safe than a text column with a check constraint. ✅
- `systemPrompt` is `text` (unbounded), appropriate for potentially long prompt strings. ✅
- `isActive` with default `true` is a good pattern for soft-delete/enable. ✅
- Timestamps use `defaultNow()` for automatic creation tracking. ✅

**Zod schema quality:**

- `insertPromptTemplateSchema` correctly omits auto-generated fields (id, createdAt, updatedAt). ✅
- `updatePromptTemplateSchema` is a partial of the insert schema, allowing flexible updates. ✅
- Type exports (`InsertPromptTemplate`, `PromptTemplate`) are properly inferred. ✅

**Security:**

- No direct SQL injection risk: Drizzle ORM uses parameterized queries. ✅
- The `systemPrompt` column stores arbitrary text — no sanitization needed at the DB level; prompt injection prevention is the caller's responsibility. ✅
- FK constraint prevents orphaned templates. ✅

**Code quality observations:**

1. **`updatedAt` has no auto-update trigger.** The schema sets `defaultNow()` but doesn't auto-update on row modification. The PUT handler in `templates.ts:107` manually sets `updatedAt: new Date()`, which is correct for the update path. However, the column definition itself lacks `.$onUpdate(() => new Date())` — this is a minor inconsistency but not a functional gap since the route handler manages it. ⚠️
2. **No unique constraint on (projectId, templateType).** The schema doesn't enforce uniqueness at the DB level. The GET handler uses `orderBy(desc(createdAt)).limit(1)` to pick the latest, and the PUT handler queries for existing rows before insert/update. This works but relies on application-level enforcement rather than a DB constraint. A `UNIQUE(projectId, templateType)` constraint would be stronger. ⚠️
3. **No index on (projectId, templateType).** The table lacks an index on the most common query pattern (lookup by project + type). For a small table this is fine, but it's worth noting. ⚠️

**Known debt (D-07):**

- The `prompt_templates` table exists but default fallback templates are **not seeded in migrations**. The hardcoded defaults in `templates.ts:9-46` (`DEFAULT_PROMPTS` constant) serve as the fallback at the application layer. The `getPromptTemplate()` function in `generate.ts:30-69` has a three-tier fallback: project-specific → global DB → hardcoded. The global DB tier (lines 49–64) queries for `isNull(projectId)` templates, but none are seeded. This means the global DB tier will always be empty, and the system always falls through to hardcoded defaults. This is a known, documented gap (D-07) — not a schema issue but an operational one.

## Gaps & Recommendations

1. **Add `.$onUpdate(() => new Date())`** to the `updatedAt` column in `prompt_templates.ts:19` to auto-update on any row modification, rather than relying solely on the route handler.

2. **Add a unique constraint** on `(projectId, templateType)` at the DB level to prevent duplicate templates. This can be done via Drizzle's `.unique()` or a raw SQL migration. The current application-level enforcement works but is not race-condition safe.

3. **Add an index** on `(projectId, templateType)` to optimize the most common query pattern (lookup by project + type).

4. **Address D-07**: Seed default global templates (with `projectId = NULL`) in a migration so the global DB tier in `getPromptTemplate()` is functional. This would allow operators to update global defaults without code changes.

5. **Add tests**: At minimum, integration tests for the GET (list with defaults), PUT (upsert), and DELETE (reset) endpoints, plus a factory for `promptTemplatesTable` in `factories.ts`.
