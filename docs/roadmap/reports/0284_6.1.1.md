## Round 1 — Architecture & Design Review

### What the Design Spec Says

ADR-001 establishes `lib/api-spec/openapi.yaml` as the **single source of truth** for all API contracts. The invariant is:

1. All API types are generated from `openapi.yaml` via Orval
2. Generated files (`lib/api-zod/src/generated/`, `lib/api-client-react/src/generated/`) are committed but never edited manually
3. Hand-writing API types, Zod schemas, or fetch wrappers that duplicate the spec is **prohibited**
4. Adding a new endpoint requires editing only `openapi.yaml` + implementing the route handler
5. Codegen must be run after every spec change

### What the Implementation Provides

**The positive — the codegen pipeline is fully operational:**

1. **OpenAPI spec exists and is comprehensive.** 2947 lines, 58 paths, 72 operationIds, 90+ schema definitions covering all major domains (projects, commits, L1/L2/L3 tags, review tasks, search, MCP, documents, integrations, sync, etc.). ✅

2. **Orval codegen is configured and working.** The `orval.config.cjs` has two outputs:
   - `api-client-react`: generates React Query hooks with custom fetch mutator
   - `zod`: generates Zod validators with coerce support for query params

   The config includes a sophisticated 3.1→3.0 downgrade pipeline (since Orval doesn't fully support 3.1), normalizing type arrays (`["string", "null"]` → `type: string, nullable: true`). ✅

3. **Generated files are committed and not hand-edited.** Both `lib/api-zod/src/generated/` and `lib/api-client-react/src/generated/` contain proper `/** Generated by orval v8.5.3 🍺 */` headers with "Do not edit manually" warnings. ✅

4. **Server routes import from generated Zod schemas.** `projects.ts` imports `CreateProjectBody`, `UpdateProjectParams`, `UpdateProjectBody`, `DeleteProjectParams`, `GetProjectParams`, etc. from `@workspace/api-zod`. `health.ts` imports `HealthCheckResponse`. ✅

5. **Frontend uses generated React Query hooks.** The kg-engine frontend imports from `@workspace/api-client-react` for all API calls. ✅

6. **API-first convention is documented and enforced in AGENTS.md.** The convention is clear: "Always edit `openapi.yaml` and run the codegen script." ✅

**The negative — routes exist in the server that are NOT in the OpenAPI spec:**

| `/projects/:id/sync`                  | POST        | `projects.ts:240`   | ❌       | No corresponding path in spec                            |
| `/projects/:id/ingest/build-artifact` | POST        | `ingest.ts:363`     | ❌       | No corresponding path in spec                            |

| ----------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------- |
| `POST /sync`                        | `POST /sync/push`                                      | Server adds `/push` suffix not in spec                        |

**Round 1 Verdict: WARN** — The codegen pipeline is fully operational and the API-first principle is well-established in documentation and tooling. However, **9 server-side routes/endpoints are not defined in the OpenAPI spec**, and there is a path mismatch for `/sync` vs `/sync/push`. This means the OpenAPI spec is NOT truly the single source of truth — it is the source of truth for the _generated types_ but not for the _actual API surface_.

## Round 2 — Code Quality & Security Review

**Positive findings:**

1. **Orval config is well-engineered.** The 3.1→3.0 downgrade with type-array normalization is a sophisticated solution to Orval's lack of 3.1 support. The `titleTransformer` ensures consistent naming. ✅

2. **Generated Zod schemas are used for validation.** Routes like `projects.ts` and `ingest.ts` import Zod schemas from `@workspace/api-zod` and use them to validate request bodies and params. This ensures runtime validation aligns with the spec. ✅

3. **Coerce override is properly configured.** The Orval config enables `zod.coerce` for query params, params, body (bigint/date), and response (bigint/date), which is correct for Express's string-based request handling. ✅

4. **Split mode with clean output.** Both Orval outputs use `mode: 'split'` and `clean: true`, ensuring generated files are organized and stale files are removed. ✅

5. **Custom fetch mutator.** The `api-client-react` output uses a custom fetch wrapper (`custom-fetch.ts`) with `setBaseUrl` and `setAuthTokenGetter`, which is a clean pattern for auth injection. ✅

**Issues identified:**

1. **🔴 Extensions VS Code routes use raw Zod, not generated schemas.** `extensions_vscode.ts` defines its own Zod schemas inline (`z.object({...})`) instead of importing from `@workspace/api-zod`. This means the VS Code extension endpoints bypass the API-first pipeline. While the OpenAPI spec defines `VscodeQueryInput` and `VscodeCreateDecisionInput`, the server doesn't use the generated validators.

2. **🔴 Metabolism routes have no spec and no generated types.** The `/metabolism-tick` and `/admin/metabolism-tick` endpoints are administrative/debug endpoints that are not in the spec. This is a minor concern (they're internal) but violates the "all routes in spec" principle.

3. **🟡 `/sync/path` path mismatch.** The spec defines `POST /sync` but the server implements `POST /sync/push`. This means the generated client will call `/sync` but the server expects `/sync/push`, causing a 404 at runtime. This is a **functional bug** — the sync endpoint is broken for any client using the generated hooks.

4. **🟡 `/projects/:id/sync` is a completely separate sync endpoint.** The `projects.ts:240` route handles project-specific sync, but the spec has no such path. This appears to be a different sync mechanism than the `/sync` endpoint.

5. **🟡 Build artifact ingestion not in spec.** The `POST /projects/:id/ingest/build-artifact` endpoint is implemented but not documented in the spec. This means no generated types or client hooks exist for it.

6. **🟢 MCP extra endpoints are internal-only.** `read_shared_memory` and `retrieve_original` are MCP-internal endpoints that may not need to be in the public API spec. However, they still violate the "all routes in spec" principle.

7. **🟢 `POST /documents` is a direct upload endpoint.** The `documents.ts:91` POST handler handles direct document uploads but is not in the spec. The spec only has project-scoped document ingestion.

**Round 2 Verdict: WARN** — The codegen quality is high, but there are significant gaps between the spec and the implementation. The `/sync` vs `/sync/push` mismatch is a functional bug. The extensions_vscode routes bypassing generated validators is a code quality concern.

## Round 3 — Integration & Completeness Review

**End-to-end flow for the API-first pipeline:**

1. Developer edits `lib/api-spec/openapi.yaml` to add/modify an endpoint
2. Runs `pnpm --filter @workspace/api-spec run codegen`
3. Orval generates:
   - Zod validators in `lib/api-zod/src/generated/` (imported by server routes)
   - React Query hooks in `lib/api-client-react/src/generated/` (imported by frontend)
4. Server route handler imports Zod schema from `@workspace/api-zod` for validation
5. Frontend component imports React Query hook from `@workspace/api-client-react`
6. `pnpm run typecheck` verifies type alignment across the stack

## Gaps & Recommendations

1. **🔴 Fix `/sync` path mismatch.** The spec defines `POST /sync` but the server implements `POST /sync/push`. Either update the spec to `/sync/push` or update the server to `/sync`. This is a functional bug — the generated client will get a 404.

2. **🔴 Add missing server routes to OpenAPI spec.** The following endpoints need to be added to `openapi.yaml`:
   - `POST /projects/{id}/sync` (project-specific sync)
   - `POST /projects/{id}/ingest/build-artifact` (build artifact ingestion)
   - `POST /admin/reindex-embeddings` (admin reindex)
   - `POST /documents` (direct document upload)
   - `GET /mcp/read_shared_memory` and `GET /mcp/retrieve_original` (MCP internal tools)
   - `GET /metabolism-tick` and `GET /admin/metabolism-tick` (or document them as intentionally internal)

3. **🟡 Use generated Zod schemas in extensions_vscode.ts.** Replace the inline `z.object({...})` definitions with imports from `@workspace/api-zod` to maintain API-first consistency.

4. **🟡 Add CI check for spec-to-server alignment.** Implement a CI step (or a script) that verifies all server routes are defined in the OpenAPI spec. This could be a simple comparison of `router.get/post/put/patch/delete` calls against spec paths.

5. **🟢 Consider adding a `$schema` or version tag** to the OpenAPI spec to make it easier to reference programmatically.

## Final Verdict: ⚠️ WARN

The `openapi.yaml` as single source of truth is **partially implemented**. The codegen pipeline is fully operational — Orval generates Zod validators and React Query hooks correctly, the server uses generated types for most routes, and the frontend uses generated hooks. The API-first convention is well-documented and followed in the main codebase.

However, the OpenAPI spec is **not truly the single source of truth** for the API surface. Nine server-side routes are not defined in the spec, and there is a path mismatch (`/sync` vs `/sync/push`) that causes a functional bug. The VS Code extensions routes bypass the generated Zod schemas entirely. There is no CI enforcement to prevent drift between the spec and the server.

The foundation is solid, but the discipline of "all routes in spec, all types from codegen" is not yet fully enforced.
