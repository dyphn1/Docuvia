## Round 1 — Architecture & Design Review

The codebase follows a **dual-pattern** approach to Zod validation:

**Pattern A — Generated Zod from OpenAPI spec (`@workspace/api-zod`):**
9 route files import validators from the Orval-generated `@workspace/api-zod` package. This is the intended "API-first" pattern per AGENTS.md. Examples: `projects.ts:68` (`CreateProjectBody.parse(req.body)`), `l1_tags.ts:23` (`CreateL1TagBody.parse(req.body)`), `review_tasks.ts:111` (`ResolveReviewTaskBody.parse(req.body)`).

**Pattern B — Inline `z.object()` schemas defined in route files:**
7 route files define their own Zod schemas inline. Examples: `generate.ts:73` (`GenerateInputSchema`), `search.ts:10` (`SearchSchema`), `mcp.ts:230` (`mcpQueryBodySchema`). These schemas are NOT generated from the OpenAPI spec and may drift from the spec.

**Gap 1 — `pull_requests.ts` POST `/analyze` (line 125-153):**
The handler reads `req.params.id` and `req.params.prNumber` with `isNaN()` checks but does NOT validate `req.body`. While this particular handler doesn't use `req.body` data (it only triggers async analysis), the route accepts arbitrary body content without validation. This is a minor gap since no body fields are consumed.

**Gap 2 — `projects.ts` POST `/projects/:id/sync` (line 240-259):**
This route handler reads `req.body` without any Zod validation. It only uses `req.params.id` (converted via `Number()`) and ignores the body entirely. The route is a stub that logs an activity entry. No body validation is needed functionally, but the route signature accepts a body that is silently discarded.

**Gap 3 — `github_webhooks.ts` POST handler (line 149+):**
The webhook handler uses `express.raw()` middleware (mounted in `app.ts:33`) and then `JSON.parse(rawBody.toString("utf8"))` at line 149. The parsed payload is cast to `Record<string, unknown>` without Zod validation. This is **architecturally intentional** — webhook payloads are validated via HMAC-SHA256 signature (line 24-33), not Zod. The dynamic nature of GitHub webhook events (many event types with different payload shapes) makes a single Zod schema impractical. This is an acceptable exception.

**Gap 4 — Inconsistent use of generated vs. inline Zod:**
The `ingest.ts` file uses BOTH patterns: `IngestSvnBody` from `@workspace/api-zod` (line 108) AND inline `GitIngestSchema` (line 23) / `SvnModeSchema` (line 31). The inline schemas duplicate validation that could be covered by the generated spec. This creates maintenance risk — if the OpenAPI spec changes, the inline schemas may not be updated.

## Round 2 — Code Quality & Security Review

**Consistent error handling pattern:**
All routes that use Zod validation follow the same pattern: `.parse(req.body)` which throws a ZodError on invalid input. However, there is **no global Zod error handler** middleware. The ZodErrors are caught by Express's default error handler, which returns a 500 with a stack trace in development. Only a few routes wrap in try/catch:

- `ingest.ts:107-111` — wraps `IngestSvnBody.parse()` in try/catch, returns 400
- `documents.ts:50-55` — uses `.safeParse()` with explicit 400 response
- `mcp.ts:237-240` — uses `.safeParse()` with explicit 400 response
- `search.ts:35-39` — uses `.safeParse()` with explicit 400 response

Most other routes rely on `.parse()` throwing, which Express catches as an unhandled error. This means **validation errors return 500 instead of 400** in production for most routes. This is a security concern: it leaks stack traces and misclassifies client errors as server errors.

**No global validation middleware:**
The Express app (`app.ts`) has no middleware like `express-zod` or a custom `validateRequest()` wrapper. Each route manually calls `.parse()` or `.safeParse()`. This is error-prone — a developer adding a new route handler might forget to add validation.

**`extensions_vscode.ts` bypasses generated Zod:**
The VS Code extension routes (`extensions_vscode.ts:7-26`) define inline schemas instead of importing from `@workspace/api-zod`. This means the OpenAPI spec may not cover these routes, and the generated React Query hooks won't include them. This is a spec drift risk.

## Round 3 — Integration & Completeness Review

**Coverage summary:**

- 22 route files total (including `github_webhooks.ts` and `metabolism.ts`)
- 16 route files with POST/PUT/PATCH handlers that accept request bodies
- 14 of 16 have Zod validation (either generated or inline)
- 2 of 16 have gaps: `pull_requests.ts` (POST /analyze — body unused), `projects.ts` (POST /sync — body unused)
- 1 special case: `github_webhooks.ts` — HMAC-validated, Zod not applicable

**Test coverage:**
No integration tests specifically verify Zod validation behavior (e.g., sending malformed payloads and asserting 400 responses). The test suite focuses on business logic, not validation edge cases.

**Orval codegen pipeline:**
The `pnpm --filter @workspace/api-spec run codegen` command regenerates validators from `openapi.yaml`. Routes using `@workspace/api-zod` automatically benefit from spec updates. Routes using inline schemas must be manually synchronized.

## Gaps & Recommendations

1. **Add global Zod error handler middleware** — Create a middleware that catches `ZodError` and returns 400 with structured error details. This eliminates the need for per-route try/catch and ensures consistent error responses. Estimated: ~15 lines in a new `middlewares/validation.ts`.

2. **Add Zod validation to `pull_requests.ts` POST `/analyze`** — Even though the body is unused, add a no-op schema or explicit body parser to prevent arbitrary payload acceptance. Estimated: ~5 lines.

3. **Add Zod validation to `projects.ts` POST `/sync`** — Same as above. Or remove the body parser if the route truly doesn't need a body. Estimated: ~5 lines.

4. **Migrate inline schemas to OpenAPI spec** — Add the routes from `extensions_vscode.ts`, `generate.ts`, `search.ts`, `mcp.ts`, `sync.ts`, `llm_config.ts`, and `integrations.ts` to `openapi.yaml` and run codegen. Then replace inline `z.object()` schemas with imports from `@workspace/api-zod`. This ensures the "API-first" principle is fully enforced.

5. **Add validation error tests** — For each POST/PUT/PATCH route, add at least one test case that sends an invalid payload and asserts a 400 response with structured error details.
