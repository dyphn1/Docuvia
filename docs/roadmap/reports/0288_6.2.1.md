## Round 1 — Architecture & Design Review

### What the Design Spec Says

The POST `/mcp/query` endpoint should serve as the Agentic RAG intent-routing entry point. It accepts a JSON body with `q` (query string), optional `project_id`, and optional `limit`. It should classify the query intent using an LLM (with O(1) fast-path filters), route to the appropriate search strategy (vector, graph, direct, hybrid), and return structured results with routing metadata.

### What the Implementation Provides

**Endpoint exists and is fully operational:**

1. **Route registration:** `routes/index.ts:12` imports `mcpRouter` from `./mcp` and mounts it at line 37 via `router.use(mcpRouter)`. The Express app mounts the combined router at `/api` (app.ts:40). The MCP router defines `POST /mcp/query` at line 236. Final path: `POST /api/mcp/query`. ✅

2. **Zod validation:** The handler uses an inline `mcpQueryBodySchema` (line 230-234) with `.safeParse()` (line 237), returning 400 with the first error message on failure. The schema validates:
   - `q`: string, min 1, max 2000
   - `project_id`: integer, positive, optional
   - `limit`: integer, min 1, max 50, default 10
   This is correct and secure. ✅

3. **Bearer token auth:** All `/mcp/*` routes are protected by middleware at lines 20-36 that checks `Authorization: Bearer <MCP_PAT>` header. Returns 401 on mismatch, 500 if `MCP_PAT` env var is not set. ✅

4. **Intent routing:** The handler calls `routeQuery()` (line 247) which implements:
   - **O(1) fast-path filters** (lines 649-682): `#attach`/file extension → direct_lookup; architectural term match → graph_traversal
   - **LLM classification fallback** (lines 684-687): `classifyIntent()` using gpt-4o-mini with JSON response format
   - **Strategy dispatch** (lines 700-721): switch on `classification.strategy` → vector_search, graph_traversal, direct_lookup, hybrid
   - **Single-word short-circuit** (lines 625-645): exact match via directLookupHandler before LLM call
   ✅

5. **Response shape:** Returns `{ query, routingStrategy, entities, results, metadata }` matching the `McpQueryResult` OpenAPI schema. ✅

6. **Error handling:** Try/catch around `routeQuery()` with `logger.error()` and 500 response. Zod validation errors return 400. ✅

### Gaps Identified

**Gap 1 — Inline Zod schema instead of generated:** The route defines `mcpQueryBodySchema` inline (line 230-234) instead of importing `McpQueryBody` from `@workspace/api-zod` (generated at `lib/api-zod/src/generated/api.ts:1034`). The generated schema exists and covers the same fields. The inline schema is slightly stricter (adds `.int().positive()`) but this is a spec drift risk — if the OpenAPI spec changes, the inline schema won't auto-update.

**Gap 2 — `include_pending` as query param, not body field:** The POST `/mcp/query` handler reads `include_pending` from `req.query` (line 244) rather than from the request body. The OpenAPI spec's `McpQueryInput` schema does not include `include_pending` as a property. This means:
   - Clients must send `include_pending` as a query string parameter (`?include_pending=true`) while the rest of the input is in the JSON body
   - The API contract in OpenAPI doesn't document this parameter for the POST endpoint
   - This is inconsistent with the GET `/mcp/search_knowledge` endpoint which also reads it from query params (line 98)

**Gap 3 — No dedicated integration test for POST /mcp/query:** The only MCP integration test is `mcp-list-projects.test.ts` (GET `/api/mcp/list_projects`). There is no test for POST `/api/mcp/query`. This means the endpoint's behavior with various input shapes, validation errors, and routing strategies is untested.

## Round 2 — Code Quality & Security Review

**Positive findings:**

1. **Input sanitization:** The `sanitizeQuery()` function (intent-router.ts:110-115) strips control characters and truncates to 2000 chars before sending to LLM. This mitigates prompt injection. ✅

2. **SQL LIKE sanitization:** Both `sanitizeLikeInput()` and `escapeLike()` (intent-router.ts:98-104) escape `%`, `_`, and `\` characters. Used in vectorSearchHandler fallback, graphTraversalHandler, and directLookupHandler. ✅

3. **Zod `.safeParse()` with explicit 400:** Unlike many other routes that use `.parse()` (which throws and results in 500), the POST `/mcp/query` handler correctly uses `.safeParse()` and returns 400 with a clear error message. ✅

4. **Structured logging:** Both the route handler and intent-router use `logger.info()`/`logger.error()` with structured context objects. ✅

5. **Bearer token middleware:** The MCP auth middleware (lines 20-36) is clean, uses early returns, and logs unauthorized attempts with IP. ✅

**Issues identified:**

1. **🟡 Redundant boolean expression on line 244:** `req.query.include_pending === "true" || false` — the `|| false` is redundant since the comparison already returns a boolean. Not a bug, but unnecessary. Same pattern on line 98.

2. **🟡 `project_id` type coercion inconsistency:** The Zod schema validates `project_id` as `z.number().int().positive()`, but the OpenAPI spec defines it as `zod.number().optional()` (no integer/positive constraint). The inline schema is stricter than the spec. This could cause the endpoint to reject values that the OpenAPI spec would accept (e.g., `1.5` or `-1`).

3. **🔴 No rate limiting on MCP endpoint:** The POST `/mcp/query` endpoint has no rate limiting. Since it calls the LLM (gpt-4o-mini) on every request (unless fast-path applies), an attacker with a valid token could exhaust LLM API credits. The GET-based MCP endpoints (list_projects, search_knowledge, etc.) also lack rate limiting.

## Gaps & Recommendations

1. **Migrate inline Zod schema to generated.** Replace the inline `mcpQueryBodySchema` (mcp.ts:230-234) with `McpQueryBody` from `@workspace/api-zod`. If the stricter `.int().positive()` constraints are desired, add them to the OpenAPI spec and regenerate. This ensures the "API-first" principle is enforced.

2. **Add `include_pending` to OpenAPI spec or body schema.** Either add `include_pending` as a query parameter in the OpenAPI path definition, or move it into the `McpQueryInput` body schema for consistency. Document the behavior either way.

3. **Add integration tests for POST `/mcp/query`.** Create `artifacts/api-server/test/integration/mcp-query.test.ts` with test cases for:
   - Valid query with results
   - Missing `q` parameter (400)
   - `q` exceeding 2000 chars (400)
   - Invalid `project_id` (400)
   - `include_pending=true` returning pending nodes
   - Bearer token missing (401)
   - Bearer token invalid (401)

4. **Add rate limiting to MCP endpoints.** Implement a rate limiter (e.g., `express-rate-limit`) on the MCP router to prevent LLM API credit exhaustion. Consider per-token rate limits since MCP uses PAT authentication.

5. **Fix redundant boolean expressions.** Remove `|| false` from lines 98 and 244 in mcp.ts. The comparison already returns a boolean.

## Final Verdict: ⚠️ WARN

The POST `/mcp/query` endpoint is **fully implemented and operational** with correct Zod validation, Bearer token auth, 4-way intent routing, O(1) fast-path filters, and proper error handling. The architecture is solid and matches the design spec. The gaps are: (1) inline Zod schema instead of generated (spec drift risk), (2) `include_pending` parameter inconsistency between implementation and OpenAPI spec, (3) no rate limiting, and (4) no integration test coverage for this endpoint. These are quality and completeness concerns, not functional defects.
