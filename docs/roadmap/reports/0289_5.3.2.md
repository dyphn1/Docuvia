## Round 1 — Architecture & Design Review

**What the spec says:** Projects must inherit global default templates and be able to override them at the project level. The system must support per-project customization of L1, L2, and L3 prompts. When a project has no custom template, the global default must be used as fallback.

**What the implementation does:**

### Schema Layer (`prompt_templates.ts`)

The `prompt_templates` table supports per-project overrides via:

- `projectId`: nullable FK → `projects.id` (ON DELETE CASCADE). When `NULL`, the template is a global default. When set, it's a project-specific override.
- `templateType`: pgEnum `prompt_template_type` with exactly the three required values: `l1_tagger`, `l2_extractor`, `l3_generator`.
- `systemPrompt`: the actual prompt text.
- `isActive`: allows soft-disabling without deletion.

This schema design correctly supports the inheritance model: global templates (projectId = NULL) and project-specific templates (projectId = N) coexist, and the API layer decides which to use.

### API Layer (`templates.ts`)

Three endpoints implement the full override lifecycle:

1. **GET `/projects/:id/templates`** (lines 52–78): Returns all 3 template types for a project. For each type, checks the DB for a project-specific row. If found, uses it; otherwise falls back to the `DEFAULT_PROMPTS` hardcoded constant. The response includes `isCustom: true/false` so the UI can distinguish overrides from defaults.

2. **PUT `/projects/:id/templates/:type`** (lines 80–134): Upserts a project-specific template. If a row already exists for (projectId, type), it updates `systemPrompt` and `updatedAt`. If not, it inserts a new row. This is the "override" mechanism — calling PUT creates a project-specific copy that shadows the global default.

3. **DELETE `/projects/:id/templates/:type`** (lines 136–150): Removes the project-specific template row, effectively resetting the project to use the global default. Returns 204 No Content.

### Generate Pipeline (`generate.ts`, lines 30–69)

The `getPromptTemplate()` function implements a 3-tier fallback chain:

1. **Project-specific active template** (lines 31–42): Queries `prompt_templates` where `projectId = ? AND templateType = ? AND isActive = true`, ordered by `createdAt DESC LIMIT 1`.
2. **Global DB template** (lines 49–64): Queries where `projectId IS NULL AND templateType = ? AND isActive = true`. This tier is currently non-functional because no global templates are seeded in migrations (D-07).
3. **Hardcoded defaults** (lines 67–68): Falls back to the `DEFAULT_PROMPTS` constant exported from `templates.ts`.

This correctly implements the per-project override with default fallback pattern.

### Frontend (`templates.tsx`)

The Templates page provides:

- Project selector sidebar listing all projects
- For each project, displays all 3 template types (L1 Tagger, L2 Extractor, L3 Generator)
- Each template shows a "Custom" or "Default" badge
- Edit button opens a textarea editor for the system prompt
- Save button calls `useUpsertProjectTemplate` (PUT endpoint)
- Reset button (shown only for custom templates) calls `useDeleteProjectTemplate` (DELETE endpoint)
- Toast notifications for success/failure feedback

### Findings

1. **Per-project override mechanism is fully implemented.** PUT creates project-specific rows, DELETE removes them, GET returns merged results. ✅
2. **All three template types (L1, L2, L3) are supported** at every layer: schema enum, API routes, generate pipeline, and frontend. ✅
3. **Default fallback works correctly.** The GET endpoint merges DB results with `DEFAULT_PROMPTS` constants. The generate pipeline has a 3-tier fallback. ✅
4. **Frontend provides complete CRUD UI** for managing per-project overrides. ✅
5. **The `isCustom` computed field** in the GET response correctly distinguishes project overrides from defaults. ✅
6. **DELETE correctly reverts to default** by removing the project-specific row, not by storing an empty override. ✅

## Round 2 — Code Quality & Security Review

**Override isolation:**

- Project A's custom prompts do not affect Project B. The `projectId` FK ensures complete isolation. ✅
- The `ON DELETE CASCADE` on `projectId` ensures templates are cleaned up when a project is deleted. ✅

**Input validation:**

- The PUT endpoint validates `systemPrompt` with `z.string().min(10)` (TemplateUpdateSchema, line 48–50). ✅
- The template type is validated against the enum values (`l1_tagger`, `l2_extractor`, `l3_generator`) at line 84–87. ✅
- The OpenAPI spec enforces the same enum constraint (line 559) and `minLength: 10` (line 2344). ✅

**Race condition analysis:**

- The PUT handler does a SELECT then either INSERT or UPDATE (lines 94–126). There is no unique constraint on `(projectId, templateType)`, so concurrent PUTs could create duplicate rows. The GET handler uses `orderBy(desc(createdAt)).limit(1)` to pick the latest, which mitigates read issues but doesn't prevent write duplication. ⚠️
- This is a minor concern for a low-concurrency admin operation (template editing), not a high-throughput API.

**Code quality observations:**

1. **No `.$onUpdate()` on `updatedAt`.** The schema sets `defaultNow()` but doesn't auto-update. The PUT handler manually sets `updatedAt: new Date()` at line 107, which is correct for the update path. Minor inconsistency — Drizzle's `.$onUpdate(() => new Date())` would be more robust. ⚠️

2. **No unique constraint on `(projectId, templateType)`.** Application-level enforcement works but isn't race-condition safe. A `UNIQUE(projectId, templateType)` constraint would be stronger. ⚠️

3. **No index on `(projectId, templateType)`.** The most common query pattern (lookup by project + type) would benefit from an index. Acceptable for a small table. ⚠️

4. **Global DB tier is non-functional (D-07).** The `getPromptTemplate()` function queries for `projectId IS NULL` global templates (lines 49–64), but none are seeded in migrations. The system always falls through to hardcoded defaults. This is a known, documented gap — the hardcoded defaults work correctly as fallback. ⚠️

5. **Hardcoded defaults are comprehensive.** The `DEFAULT_PROMPTS` constant (lines 9–46) contains detailed, well-structured prompts for all three types, with clear output format instructions. ✅

## Gaps & Recommendations

1. **Add a unique constraint** on `(projectId, templateType)` at the DB level to prevent duplicate rows from concurrent PUT requests. Can be done via Drizzle's `.unique()` or a raw SQL migration.

2. **Add an index** on `(projectId, templateType)` to optimize the most common query pattern.

3. **Add `.$onUpdate(() => new Date())`** to the `updatedAt` column in `prompt_templates.ts:19` for automatic timestamp management.

4. **Address D-07**: Seed default global templates (with `projectId = NULL`) in a migration so the global DB tier in `getPromptTemplate()` becomes functional. This would allow operators to update global defaults without code changes.

5. **Add tests**: Integration tests for GET (list with defaults), PUT (upsert creates override), DELETE (reset reverts to default), and a factory for `promptTemplatesTable` in `factories.ts`.
