## Round 1 — Architecture & Design Review

### What the Design Spec Says

The design docs (phase-5-query-mcp) describe MCP as a set of REST endpoints under `/mcp/*` that expose knowledge graph operations to AI agents. The individual tool endpoints are:

1. `GET /mcp/list_projects` — List all projects
2. `GET /mcp/search_knowledge` — Semantic search
3. `GET /mcp/get_dependencies` — Module dependency graph
4. `GET /mcp/impact_analysis` — Impact analysis
5. `GET /mcp/get_decision_record` — L3 decision record by commit hash
6. `POST /mcp/query` — Agentic RAG intent-routing entry point

The design docs do **not** describe a formal MCP `tools/list` discovery endpoint. The term "MCP tool discovery" in the checklist (6.2.2) refers to the ability for clients to discover available MCP tools.

### What the Implementation Provides

**No tool discovery endpoint exists.** There is:
- No `GET /mcp/tools/list` or equivalent REST endpoint that returns available tools
- No JSON-RPC `tools/list` method (the MCP spec's standard discovery mechanism)
- No endpoint that advertises tool names, descriptions, and input schemas
- No capability negotiation endpoint

**The kg-engine frontend hardcodes 5 of 8 endpoints** in `mcp.tsx` (lines 16-62), missing `read_shared_memory`, `retrieve_original`, and `query`. The badge on line 179 says "5 tools available" — which is incorrect (there are 8 endpoints in the route file, 6 in the OpenAPI spec).

### Gaps Identified

**Gap 1 — No tool discovery endpoint:** The MCP specification (Model Context Protocol) defines a standard `tools/list` method that allows clients to dynamically discover available tools. Docuvia's MCP implementation is REST-based and has no such discovery mechanism. Clients must be manually configured with endpoint URLs and schemas. This means:
- New endpoints added to `mcp.ts` are invisible to clients until manually documented
- The OpenAPI spec serves as the only machine-readable discovery mechanism, but it's not programmatically exposed via an MCP discovery call
- The `read_shared_memory` and `retrieve_original` endpoints aren't even in the OpenAPI spec

**Gap 2 — Inconsistency between route file, OpenAPI spec, and frontend:**
- 2 endpoints exist in code but not in OpenAPI spec (`read_shared_memory`, `retrieve_original`)
- 1 endpoint exists in OpenAPI but not in the kg-engine UI (`query`)
- The frontend hardcodes endpoint metadata instead of fetching it from a discovery source

## Round 2 — Code Quality & Security Review

**Positive findings:**

1. **All MCP endpoints are Bearer token protected.** The middleware at `mcp.ts:20-36` checks `Authorization: Bearer ${MCP_PAT}` for all `/mcp/*` routes. Returns 401 on mismatch, 500 if `MCP_PAT` is unset. ✅

2. **Input validation on all endpoints.** Each endpoint validates required parameters (query, module, commit_hash, id) and returns 400 with clear error messages. The POST `/mcp/query` endpoint uses Zod `.safeParse()`. ✅

3. **Error handling consistency.** All endpoints use try/catch with `logger.error()` and return 500 on unhandled errors. ✅

4. **The `read_shared_memory` and `retrieve_original` endpoints** (lines 68-91) are simple, focused, and follow the same error-handling pattern as the spec-defined endpoints. ✅

**Issues identified:**

1. **🟡 `read_shared_memory` and `retrieve_original` are undocumented.** These endpoints exist in the route file (mcp.ts:68-91) but are not in the OpenAPI spec. This violates the "API-first" principle stated in AGENTS.md. Any changes to these endpoints won't trigger codegen updates.

2. **🟡 kg-engine MCP page is manually maintained.** The `mcp.tsx` file hardcodes endpoint definitions (name, method, path, description, params). If a new endpoint is added to `mcp.ts`, the UI won't reflect it unless manually updated. This is a direct consequence of having no tool discovery mechanism.

3. **🟡 No test coverage for `read_shared_memory` or `retrieve_original`.** The only MCP integration test is `mcp-list-projects.test.ts`. The two undocumented endpoints have zero test coverage.

4. **🔴 No rate limiting on any MCP endpoint.** Same issue as identified in 6.2.1 report — no rate limiting on MCP routes, which could lead to LLM API credit exhaustion.

## Gaps & Recommendations

1. **Add a tool discovery endpoint.** Implement `GET /api/mcp/tools` (or `GET /api/mcp/tools/list`) that returns a JSON array of available tools with their names, descriptions, HTTP methods, paths, and parameter schemas. This would:
   - Enable dynamic client-side discovery
   - Keep the kg-engine UI in sync automatically
   - Follow the MCP specification's capability advertisement pattern

2. **Document all endpoints in OpenAPI spec.** Add `read_shared_memory` and `retrieve_original` to `lib/api-spec/openapi.yaml` and run codegen. This enforces the "API-first" principle.

3. **Make the kg-engine MCP page dynamic.** Instead of hardcoding endpoints in `mcp.tsx`, fetch the tool list from the discovery endpoint (once implemented) or generate it from the OpenAPI spec.

4. **Add integration tests for all MCP endpoints.** Create test files for the 7 untested endpoints, covering success cases, validation errors, and auth failures.

5. **Add rate limiting.** As noted in the 6.2.1 report, implement rate limiting on MCP routes to prevent LLM API credit exhaustion.

## Final Verdict: ⚠️ WARN

The individual MCP tool endpoints are **fully implemented and operational** — 8 endpoints exist with proper auth, validation, and error handling. However, **MCP tool discovery is missing**: there is no programmatic mechanism for clients to discover available tools. The OpenAPI spec partially serves this role but is incomplete (6 of 8 endpoints). The kg-engine UI hardcodes a subset of 5 endpoints. The lack of a discovery endpoint means clients must be manually configured, and new endpoints are invisible until separately documented. This is a completeness and maintainability gap, not a functional defect in the individual endpoints.
