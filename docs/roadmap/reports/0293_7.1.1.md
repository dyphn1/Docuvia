## Round 1 — Architecture & Design Review

**Frontend (`dashboard.tsx`):**

- The Dashboard component is the default route (`/`) in `App.tsx` (line 35), making it the landing page.
- Uses `useGetDashboard` generated hook (React Query) to fetch stats from `GET /api/dashboard`.
- Renders 5 stat cards: Projects, L1 Tags, L2 Nodes, L3 Nodes, Pending Reviews — each with an icon and formatted count.
- Renders a Recent Activity feed showing the 10 most recent activity log entries with timestamp and project name.
- Handles loading state (5 skeleton cards) and error state (destructive alert banner).
- Falls back to `emptyStats` (all zeros) when API returns no data — graceful degradation.

**Backend (`routes/dashboard.ts`):**

- `GET /dashboard` endpoint performs 5 independent `count()` queries across `projectsTable`, `l1TagsTable`, `l2NodesTable`, `l3NodesTable`, and `reviewTasksTable` (filtered to `status = 'pending'`).
- Fetches 10 most recent activity log entries ordered by `createdAt DESC`.
- For each activity row with a `projectId`, performs an additional query to fetch the project name — this is an N+1 query pattern (1 + N where N ≤ 10).
- Returns JSON matching the `DashboardStats` schema: `{ totalProjects, totalL1Tags, totalL2Nodes, totalL3Nodes, pendingReviews, recentActivity }`.

**Route Registration:**

- `dashboardRouter` is imported and mounted in `routes/index.ts` (line 28) — confirmed wired.

**OpenAPI Spec:**

- `/dashboard` GET endpoint defined at line 65 with `operationId: getDashboard`, tag `dashboard`, response schema `DashboardStats`.
- `DashboardStats` schema (line 1673) has 6 required integer/array fields matching the backend response.
- `ActivityItem` schema (line 1693) has `id`, `type` (enum), `description`, `projectName` (nullable), `createdAt`.

**Generated Client:**

- `useGetDashboard` hook exists at `api.ts:218` with proper query key management.
- `getGetDashboardUrl()` returns `/api/dashboard` (line 176).
- `DashboardStats` interface at `api.schemas.ts:31` matches the 6 fields.

**Architecture Assessment:** The dashboard is correctly architected end-to-end: OpenAPI spec → generated hooks → React component → Express route → DB queries. No structural gaps.

## Round 2 — Code Quality & Security Review

**Findings:**

1. **N+1 query in activity log enrichment** (`dashboard.ts:32-47`): For each of the 10 activity rows, a separate `SELECT` query fetches the project name. This could be a single `JOIN` or `GROUP BY` query. With only 10 rows this is low-impact, but it's a code quality concern.

2. **ActivityItem enum mismatch** (`openapi.yaml:1701` vs `activity_log.ts:5-12`): The OpenAPI spec defines the `type` enum as `[commit, l2_created, l3_created, review_resolved, tag_added]` (5 values), but the DB schema's `activityTypeEnum` includes `"document"` as a 6th value. The spec is missing `"document"` — this is spec drift.

3. **No authentication on `GET /dashboard`**: The dashboard endpoint has no auth middleware. This is consistent with the rest of the API (no routes have auth), but it means anyone with network access can read system-wide stats. This is a broader security concern tracked in 9.1.x items.

4. **No input validation needed**: The endpoint takes no parameters, so injection risk is minimal. The `count()` queries are safe.

5. **Error handling**: The endpoint has no `try/catch` — if any query fails, Express will return a 500 with the default error handler. The frontend handles this gracefully with the error alert and fallback to empty stats.

## Gaps & Recommendations

1. **Add test coverage** — Write an integration test for `GET /dashboard` that verifies the response shape and stat counts using `withRollback()` and test factories. Write a component test for `dashboard.tsx` that mocks the API response.

2. **Fix ActivityItem enum drift** — Add `"document"` to the `type` enum in `openapi.yaml:1701` to match the DB schema's `activityTypeEnum`.

3. **Optimize N+1 query** — Replace the per-row project name lookup with a single `JOIN` or `IN` query. Example: fetch all relevant projects in one query and map by ID in memory.

4. **Consider caching** — Dashboard stats don't need real-time accuracy. A 30-second cache or materialized view would reduce DB load.
