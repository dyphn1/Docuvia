## Round 1 — Architecture & Design Review

**What the dashboard currently shows:**
The dashboard (`dashboard.tsx`) renders 5 stat cards (Projects, L1 Tags, L2 Nodes, L3 Nodes, Pending Reviews) plus a Recent Activity feed. It fetches data from `GET /dashboard` which performs count queries across 5 tables.

**What is missing — Review Queue Health Indicator:**
The dashboard has a "Pending Reviews" stat card (showing a single aggregate count), but it has **no review queue health indicator**. Specifically:

1. **No review queue health breakdown** — The dashboard shows `pendingReviews` as a single number. It does not show the breakdown by status (pending, approved, rejected, deferred). A Project Manager cannot assess queue health from a single aggregate — they need to know if the queue is growing (many pending), being processed (many approved today), or stalled.

2. **No visual health indicator** — There is no color-coded health badge, progress bar, or status indicator showing the overall health of the review queue. The stakeholder requirement explicitly calls for "review task queue health" — a qualitative assessment, not just a count.

3. **No "reviewed today" metric** — The `GET /review-tasks/stats` endpoint returns `totalToday` (count of tasks created today), but this is not surfaced on the dashboard. A health indicator should show throughput — how many reviews were completed today.

4. **No trend or velocity data** — There is no indication of whether the review queue is improving (more approved than pending) or degrading (backlog growing). Even a simple ratio (e.g., "12 pending · 45 approved · 3 rejected") would provide health context.

5. **DashboardStats schema lacks review health fields** — The `DashboardStats` schema at `openapi.yaml:1673` defines 6 fields. It includes `pendingReviews` (a single count) but no breakdown fields for approved/rejected/deferred counts or today's throughput.

**What exists elsewhere:**
- The dedicated Review page (`/review`) has a full stats sidebar showing pending/approved/rejected/deferred counts, "Reviewed Today" metric, and a large pending count display with color coding.
- The `GET /review-tasks/stats` endpoint exists and returns `{ pending, approved, rejected, deferred, totalToday }`.
- The `ReviewStats` schema is defined in the OpenAPI spec.

**Architecture Assessment:** The review queue health data is fully available via the existing `GET /review-tasks/stats` endpoint, and the Review page already renders it beautifully. But the dashboard does not consume or display any of this data. The dashboard would need either: (a) a new API endpoint or extended `GET /dashboard` response, or (b) a separate frontend call to `GET /review-tasks/stats` from the dashboard component.

## Round 2 — Code Quality & Security Review

**Findings:**

1. **DashboardStats schema is incomplete for the stakeholder requirement** — The `DashboardStats` schema at `openapi.yaml:1673` defines `pendingReviews` as a single integer. For a proper health indicator, it should include:
   - `reviewQueueHealth`: an object or flattened fields with pending/approved/rejected/deferred counts
   - `reviewedToday`: count of tasks resolved today (or created today as a proxy)

2. **Backend dashboard route doesn't query review stats** — `routes/dashboard.ts` queries `reviewTasksTable` only for `WHERE status = 'pending'`. It does not query for approved/rejected/deferred counts. The review stats query pattern already exists in `routes/review_tasks.ts` (lines 77–107) but is not reused in the dashboard route.

3. **Frontend dashboard doesn't render any review health UI** — `dashboard.tsx` shows a single "Pending Reviews" card with a count. There is no health breakdown, no color coding for queue status, and no "reviewed today" metric.

4. **Review page already has the perfect component** — The Review page's stats sidebar (lines 335–404 of `review.tsx`) is a well-designed health indicator with:
   - Large pending count with primary color highlighting
   - Approved/Rejected/Deferred breakdown with color-coded icons
   - "Reviewed Today" metric
   - This could be adapted into a dashboard card component.

5. **Two possible implementation approaches:**
   - **Option A (Preferred):** Add review stats fields to the `GET /dashboard` response and `DashboardStats` schema. This keeps the dashboard self-contained with a single API call.
   - **Option B:** Have the dashboard frontend make a separate call to `GET /review-tasks/stats`. This avoids changing the dashboard API but adds a second request.

6. **No test coverage** — As noted in previous reports (7.1.1, 7.1.2), there are zero tests for the dashboard frontend or backend. Any changes should include tests.

## Gaps & Recommendations

1. **Extend `GET /dashboard` with review health data** — Add review queue health fields to the dashboard backend response. The query pattern already exists in `routes/review_tasks.ts` (lines 77–107). Either import and reuse that logic or inline the counts in the dashboard route.

2. **Update `DashboardStats` schema** — Add a `reviewHealth` object field (or flattened count fields) to the `DashboardStats` schema in `openapi.yaml`, then run `pnpm --filter @workspace/api-spec run codegen`.

3. **Add review health section to dashboard frontend** — Add a visually distinct card or section to `dashboard.tsx` showing:
   - A health badge (e.g., green "Healthy" if pending < 10, amber "Backlog" if pending ≥ 10, red "Stalled" if pending > 50)
   - Breakdown counts with color-coded icons (matching the Review page's design language)
   - "Reviewed Today" throughput metric
   - Link to `/review` for full queue management

4. **Reuse Review page design patterns** — The Review page's stats sidebar (lines 335–404 of `review.tsx`) uses a consistent design language with color-coded icons and counts. Extract a shared `ReviewHealthCard` component that can be used on both the dashboard and the Review page.

5. **Add test coverage** — Once implemented, add integration tests for the updated `GET /dashboard` endpoint and component tests for the new review health UI.
