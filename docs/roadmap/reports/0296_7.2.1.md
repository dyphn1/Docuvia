## Round 1 — Architecture & Design Review

**What the Pipeline page implements for ingest triggering:**

The Pipeline page (`/pipeline`) provides a complete ingest trigger UI as the left column of a two-column layout. It includes:

1. **Project selector** — A `<Select>` dropdown populated from `useListProjects()` that lists all projects by name and repo URL. On selection, it displays project metadata (commit count, L2/L3 node counts, status badge with color coding for active/indexing/error).

2. **Git ingest form** — A fully functional form with:
   - Repository URL input (optional override, falls back to project's stored repoUrl)
   - Branch input (defaults to "main")
   - Commit Limit input (number, defaults to 100)
   - GitHub Token input (password field, optional, for private repos)
   - Sync Mode selector (Full Sync / Incremental Sync)

3. **Trigger button** — "Ingest from GitHub" button that:
   - Is disabled when no project is selected or loading is in progress
   - Shows spinner + "Fetching commits..." during loading
   - Calls `POST /api/projects/{id}/ingest/git` via fetch with JSON body
   - Handles success and error responses

4. **Result display** — On success, shows a green card with 3-column layout: Ingested count, Skipped count, Total Fetched count.

5. **Error display** — On failure, shows a red error card with the error message.

## Round 2 — Code Quality & Security Review

**Findings:**

1. **Frontend uses raw fetch instead of generated hooks** — The pipeline.tsx `handleIngest` function uses `fetch()` directly rather than the generated `useIngestGit()` React Query hook. This means:
   - No automatic cache invalidation for ingest-related queries (though `queryClient.invalidateQueries({ queryKey: getListProjectsQueryKey() })` is called manually)
   - No built-in retry logic, request deduplication, or loading state management from React Query
   - Inconsistency with `IngestStatusCard.tsx` which correctly uses the generated `useIngestGit()` and `useIngestSvn()` hooks
   - This is a code quality concern but not a functional defect — the raw fetch works correctly

2. **Backend Zod validation is comprehensive** — The `GitIngestSchema` (lines 23–29 of ingest.ts) validates all inputs: optional repoUrl string, optional branch with default "main", optional limit number with default 100, optional githubToken, and mode enum with "full"/"incremental". The limit is capped at 500 (line 44). The backend correctly falls back to `project.repoUrl` when no override is provided (line 42).

3. **GitHub token is handled securely on the backend** — The token is sent in the request body (not URL), and the backend passes it to `LocalGitClient` for authentication. The frontend uses `type="password"` for the input field (line 224). The token is optional and only needed for private repos.

4. **Error handling is robust** — The backend wraps the entire ingest flow in try/catch/finally (lines 51–98), with `client.cleanup()` in the `finally` block ensuring temp directory cleanup. The frontend catches errors and displays them in a styled error card.

5. **Project status tracking** — When ingest starts, the backend clones the repo, fetches commits, processes them via `processIngestion()`, and updates `lastGitIngestedAt` for incremental mode. The project's status field can be checked via `GET /projects/:id/ingest/status`.

6. **Test coverage: none** — There are zero unit or integration tests for the pipeline frontend page or the ingest backend routes. This is consistent with the overall test gap noted in reports 7.1.1 through 7.1.3.

7. **OpenAPI spec alignment** — The `openapi.yaml` defines all 6 ingest-related paths. The `GitIngestInput` and `GitIngestResult` schemas match the backend implementation. However, the frontend does NOT use the generated React Query hooks from `@workspace/api-client-react` — it uses raw `fetch()`. This means the codegen pipeline is correct but the frontend开发者 chose raw fetch for the pipeline page specifically.

8. **Missing SVN ingest UI on the pipeline page** — The backend supports `POST /projects/:id/ingest/svn` and the API spec defines it, but the pipeline page only exposes a Git ingest form. The `IngestStatusCard` component (used on project detail pages) supports both Git and SVN. The pipeline page does not provide a way to trigger SVN ingest or document upload directly.

## Gaps & Recommendations

1. **Use generated React Query hooks** — Replace the raw `fetch()` in `pipeline.tsx` `handleIngest` with the generated `useIngestGit()` hook from `@workspace/api-client-react`. This would provide automatic cache management, consistent error handling, and alignment with the rest of the codebase (e.g., `IngestStatusCard.tsx`).

2. **Add ingest status to Pipeline page** — Integrate the `IngestStatusCard` component (or a summary version) into the Pipeline page so users can see the last sync time and pending commit count alongside the ingest trigger form. This would give context before triggering a new ingest.

3. **Consider adding SVN ingest to Pipeline page** — Currently only Git ingest is exposed on the Pipeline page. If SVN projects are common, consider adding a VCS type toggle or separate tab.

4. **Add test coverage** — Add integration tests for `POST /projects/:id/ingest/git` and component tests for the Pipeline page ingest form.
