## Round 1 — Architecture & Design Review

**What the Pipeline page implements for generate triggering:**

The Pipeline page (`/pipeline`) provides a complete generate trigger UI as the right column of a two-column layout (left column is ingest UI). It includes:

1. **Project selector** — A `<Select>` dropdown populated from `useListProjects()` that lists all projects by name and repo URL. On selection, it displays project metadata (commit count, L2/L3 node counts, status badge with color coding for active/indexing/error).

2. **Generate form** — A fully functional form with:
   - Model selector (dropdown with options: gpt-5.2 (recommended), gpt-5.4 (most capable), gpt-5-mini (fast), gpt-5-nano (cheapest))
   - Max Commits input (number field, defaults to 50)
   - Mode selector (Full Sync / Incremental Sync)

3. **Trigger button** — "Run AI Pipeline" button that:
   - Is disabled when no project is selected or loading is in progress
   - Shows spinner + "Running pipeline..." during loading
   - Calls `POST /api/projects/{id}/generate` via fetch with JSON body
   - Handles success and error responses

4. **Result display** — On success, shows a blue card with 2-column layout:
   - Column 1: L1 Tags created, L2 Nodes created (+ updates), L3 Nodes created
   - Column 2: Review Tasks created, Commits processed, Documents used as context

5. **Error display** — On failure, shows a red error card with the error message.

## Round 2 — Code Quality & Security Review

**Findings:**

1. **Frontend uses raw fetch instead of generated hooks** — The pipeline.tsx `handleGenerate` function uses `fetch()` directly rather than the generated `useGenerate()` React Query hook. This means:
   - No automatic cache invalidation for generate-related queries (though `queryClient.invalidateQueries({ queryKey: getListProjectsQueryKey() })` is called manually)
   - No built-in retry logic, request deduplication, or loading state management from React Query
   - Inconsistency with potential future hooks (though none exist for generate yet)
   - This is a code quality concern but not a functional defect — the raw fetch works correctly

2. **Backend Zod validation is comprehensive** — The `GenerateInputSchema` (lines 73–77 of generate.ts) validates all inputs: optional model string, optional maxCommits number with default 50, and mode enum with "full"/"incremental". The backend correctly applies project-specific LLM configuration when available.

3. **Project status transitions are handled safely** — The backend uses atomic updates with proper constraints to prevent race conditions:
   - Checks if project is in "active" or "error" state, or if "indexing" but stale (>30 mins)
   - Uses `updatedAt` timestamp to detect stale indexing states
   - Returns 409 Conflict if project is already indexing
   - Always resets status to "active" or "error" in finally/error blocks

4. **LLM configuration integration** — The backend properly fetches project-specific LLM config (similarityThreshold, condensationThreshold, condensationReviewRequired) and falls back to sensible defaults when not configured.

5. **Error handling is robust** — The backend wraps the entire generation flow in try/catch (lines 603–1175), with project status reset to "error" in the catch block. The frontend catches errors and displays them in a styled error card.

6. **Resource cleanup** — While not explicitly shown in the generate route (unlike ingest which has git client cleanup), the generation process doesn't appear to allocate external resources requiring cleanup beyond DB connections.

7. **OpenAPI spec alignment** — The `openapi.yaml` defines the generate path and schemas correctly. The frontend does NOT use the generated React Query hooks from `@workspace/api-client-react` (similar to the ingest UI), using raw `fetch()` instead.

8. **Missing detailed progress indicators** — The generate UI shows a simple "Running pipeline..." spinner but doesn't break down progress by phase (L1 tagging, L2 extraction, L3 generation). This is acceptable for the MVP but could be enhanced.

## Gaps & Recommendations

1. **Use generated React Query hooks** — Replace the raw `fetch()` in `pipeline.tsx` `handleGenerate` with the generated `useGenerate()` hook from `@workspace/api-client-react` when available. This would provide automatic cache management, consistent error handling, and alignment with codegen principles.

2. **Consider adding phase-based progress indicators** — Break down the "Running pipeline..." spinner into sub-steps (L1 Tagger → L2 Extractor → L3 Generator → Review queued) to give users better visibility into the multi-stage process.

3. **Add test coverage** — Add integration tests for `POST /projects/:id/generate` and component tests for the Pipeline page generate form.

4. **Validate GenerateResult schema completeness** — Ensure all fields defined in the OpenAPI spec (`crossProjectLinksDetected`, `noiseTasksCreated`) are actually returned by the backend and handled by the frontend (currently missing from UI display).
