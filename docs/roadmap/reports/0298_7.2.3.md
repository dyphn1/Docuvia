## Round 1 — Architecture & Design Review

**What 7.2.3 requires ("Pipeline result display"):**

The item calls for the Pipeline page to display the results of both ingest and generate operations. This means:

1. After triggering ingest, show a summary of what was ingested
2. After triggering generate, show a summary of what was generated
3. Display should be clear, structured, and informative
4. Error states should also be displayed

**Ingest result display (lines 265–297 of pipeline.tsx):**

After a successful ingest, the UI renders a green-themed card (`bg-emerald-500/10`) containing:

- A header with checkmark icon and "Ingest Complete" text
- A 3-column grid showing:
  - **Ingested** — `ingestResult.commitsIngested` (large bold number)
  - **Skipped** — `ingestResult.commitsSkipped` (large bold number)
  - **Total** — `ingestResult.totalFetched` (large bold number)

The frontend `IngestResult` interface (lines 29–33) defines:

```typescript
interface IngestResult {
  commitsIngested: number;
  commitsSkipped: number;
  totalFetched: number;
}
```

The backend ingest route (lines 87–92 of ingest.ts) returns:

```typescript
return res.json({
  commitsIngested: ingested,
  commitsSkipped: skipped,
  totalFetched: gitItems.length,
  errors: errors.length > 0 ? errors : undefined,
});
```

The OpenAPI `GitIngestResult` schema (lines 2214–2224) defines required: `[commitsIngested, commitsSkipped, totalFetched]` — all integers. The frontend interface matches the backend response and the OpenAPI schema. ✅

**Generate result display (lines 391–444 of pipeline.tsx):**

After a successful generate, the UI renders a blue-themed card (`bg-primary/10`) containing:

- A header with checkmark icon and "Pipeline Complete" text
- A 2×2 grid showing:
  - **L1 Tags** — `generateResult.l1TagsCreated`
  - **L2 Nodes** — `generateResult.l2NodesCreated` (+ optional update count in amber)
  - **L3 Nodes** — `generateResult.l3NodesCreated`
  - **Review Tasks** — `generateResult.reviewTasksCreated`
- A footer line: `X commits processed → go to Review Queue`
- Conditionally: `X docs used as context` (only shown when documentsUsed > 0)

The frontend `GenerateResult` interface (lines 35–43) defines:

```typescript
interface GenerateResult {
  l1TagsCreated: number;
  l2NodesCreated: number;
  l2NodesUpdated: number;
  l3NodesCreated: number;
  reviewTasksCreated: number;
  commitsProcessed: number;
  documentsUsed: number;
}
```

The backend generate route (lines 1158–1168 of generate.ts) returns:

```typescript
return res.json({
  l1TagsCreated,
  l2NodesCreated,
  l2NodesUpdated,
  l3NodesCreated,
  reviewTasksCreated,
  commitsProcessed: validCommits.length,
  documentsUsed: documents.length,
  crossProjectLinksDetected,
  noiseTasksCreated,
});
```

The OpenAPI `GenerateResult` schema (lines 2282–2301) defines required: `[l1TagsCreated, l2NodesCreated, l3NodesCreated, reviewTasksCreated, commitsProcessed]` with optional `l2NodesUpdated` and `documentsUsed`. The frontend interface matches the backend response and the OpenAPI schema. ✅

**Error display:**

Both ingest and generate have error display blocks:

- Ingest error (lines 292–297): Red card with AlertCircle icon and error message
- Generate error (lines 439–444): Red card with AlertCircle icon and error message

Both use the pattern: `catch (e) { setError(e instanceof Error ? e.message : "Unknown error"); }` — robust error handling that handles both Error objects and non-Error thrown values. ✅

## Round 2 — Code Quality & Security Review

**Findings:**

1. **Result display is well-structured and visually distinct** — Ingest results use emerald/green theme, generate results use primary/blue theme, errors use destructive/red theme. This gives users immediate visual feedback about the operation type and outcome.

2. **Frontend uses raw fetch (not generated hooks)** — Same pattern as noted in 7.2.1 and 7.2.2 reports. The pipeline.tsx uses `fetch()` directly rather than generated React Query hooks. This is a code quality concern but not a functional defect. The manual `queryClient.invalidateQueries()` call after success partially mitigates cache staleness.

3. **Backend response includes extra fields not displayed** — The backend returns `crossProjectLinksDetected` and `noiseTasksCreated` (lines 1166–1167 of generate.ts) but the frontend `GenerateResult` interface doesn't include these fields and the UI doesn't display them. This is a minor gap — the data is available but not surfaced. The OpenAPI spec also doesn't include these fields in the `GenerateResult` schema (lines 2282–2301), so this is a backend/OpenAPI drift issue.

4. **Ingest errors field not displayed** — The backend can return an `errors` array in the ingest result (line 91 of ingest.ts: `errors: errors.length > 0 ? errors : undefined`), but the frontend `IngestResult` interface doesn't include an `errors` field and the UI doesn't display individual error messages. Only the top-level error (from HTTP failure) is shown. This means per-commit ingest errors are silently swallowed in the UI.

5. **L2NodesUpdated display is conditional and subtle** — The update count is shown as a small amber `+N upd` suffix next to the L2 Nodes count (lines 406–410). This is easy to miss. A more prominent display (e.g., separate row or badge) would improve visibility.

6. **No result persistence** — Results are held in component state (`useState`) and are lost on page navigation or refresh. This is acceptable for an MVP but means users can't review historical pipeline runs from the UI.

7. **No accessibility concerns** — The result cards use semantic HTML (`div` with text), proper color contrast (theme-aware colors with dark mode variants), and icon+text combinations. The grid layout is readable.

8. **Input sanitization** — The result display values are all numbers rendered via `{ingestResult.commitsIngested}` etc. No user-controlled strings are rendered in the result cards, so XSS via result display is not a concern. Error messages come from the backend's `err.message` but are rendered in React's JSX (auto-escaped).

## Gaps & Recommendations

1. **Display `crossProjectLinksDetected` and `noiseTasksCreated`** — The generate result card should show these additional metrics. Consider adding a "Cross-project links detected" row and a "Noise flags raised" row to the generate result card. Also update the OpenAPI `GenerateResult` schema to include these fields.

2. **Surface ingest errors array** — When the backend returns per-commit errors in the ingest result, display them in the UI (e.g., a collapsible "X errors" section below the ingest result card). Update the frontend `IngestResult` interface to include `errors?: string[]`.

3. **Make L2NodesUpdated more prominent** — The current `+N upd` suffix in small amber text is easy to miss. Consider a separate "L2 Updated" cell or a badge.

4. **Add test coverage** — Add component tests for the Pipeline page that verify:
   - Ingest result card renders with correct values after mock ingest
   - Generate result card renders with correct values after mock generate
   - Error cards render on failed operations
   - Results are cleared when a new operation starts

5. **Consider result history** — For future enhancement, persist pipeline run results so users can review historical runs (could tie into the `activity_log` table).
