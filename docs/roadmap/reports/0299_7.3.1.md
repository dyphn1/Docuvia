## Round 1 — Architecture & Design Review

**What 7.3.1 requires ("Natural language query interface"):**

The item calls for a natural language query interface in the kg-engine frontend. This means:
1. A text input where users can type free-form natural language queries
2. The query is sent to the backend for processing
3. Results are displayed in a meaningful way
4. The interface should be accessible and intuitive

**Frontend implementation (query.tsx):**

The Query page provides:
- A centered layout with a BrainCircuit icon header and descriptive subtitle
- A project filter dropdown (Select) to scope queries to a specific project
- A search input with gradient glow effect and a "Search" button
- Form submission via `onSubmit` (Enter key or button click)
- Loading state with spinner in the button
- Error display in a red card with AlertCircle icon
- Results displayed as cards with layer badges (L1/L2/L3), project name, score, title, and content
- Empty state with helpful message suggesting pipeline runs
- Idle state showing available MCP tool endpoints

The frontend sends queries via `POST /api/mcp/query` with body:
```json
{
  "query": "user's natural language query",
  "projectId": 123,  // optional, omitted if "all"
  "limit": 20
}
```

**Backend implementation (mcp.ts + intent-router.ts):**

The `POST /mcp/query` endpoint:
1. Validates the request body with Zod (`McpQueryInput` schema: `q` required string 1–2000 chars, optional `project_id` positive int, optional `limit` 1–50 default 10)
2. Calls `routeQuery(q, project_id, limit, includePending)` from intent-router
3. Returns the full `RouteQueryResult` shape

The intent router (`routeQuery` function) implements:
1. **O(1) fast-path for single-word queries** (lines 625–645): Direct lookup without LLM call
2. **O(1) fast-path for `#attach` or file extension patterns** (lines 650–657): Direct lookup
3. **O(1) fast-path for known architectural terms** (lines 660–682): Graph traversal by matching against L1 tags and L2 node names
4. **LLM-based intent classification** (lines 685–687): Falls back to `classifyIntent()` using gpt-4o-mini
5. **Strategy dispatch** (lines 700–721): Routes to vector_search, graph_traversal, direct_lookup, or hybrid handlers

**Search strategies implemented:**
- **Vector search** (lines 188–385): Embedding-based cosine similarity over L2 and L3 nodes, with temporal decay applied. Falls back to SQL LIKE if embeddings unavailable.
- **Graph traversal** (lines 391–475): Finds L2 node by name, follows node_links for dependencies, fetches associated L3 decisions
- **Direct lookup** (lines 481–554): Commit hash matching or ILIKE full-text search on L3 title/content
- **Hybrid** (lines 560–608): Vector search + graph traversal merge with scoring boost for intersection

**Result filtering:**
- L3 nodes filtered by `validityStatus` (valid only by default, or valid+pending with `include_pending=true`)
- Project filter applied at DB query level for all strategies

## Round 2 — Code Quality & Security Review

**Findings:**

1. **Response shape mismatch between frontend and backend** — The frontend `SearchResponse` interface (lines 28–31) expects `{ results: [...], total: number }`. The backend `POST /mcp/query` returns `{ query, routingStrategy, entities, results, metadata }`. The backend does NOT return a `total` field. The frontend reads `data.total` (line 77) which will be `undefined`, causing the results counter to display "5 of undefined matches" (line 150). This is a **functional bug**.

2. **Frontend uses field name `query` in request body but OpenAPI uses `q`** — The frontend sends `{ query: "...", projectId: ..., limit: ... }` (lines 68–72) but the backend Zod schema expects `q` (line 231: `z.string().min(1, "q is required")`). The frontend's `query` field will fail Zod validation, causing a 400 error with message "q is required". This is a **critical bug** — the query interface is non-functional.

3. **Frontend uses `projectId` but backend expects `project_id`** — The frontend sends `projectId` (line 70) but the Zod schema expects `project_id` (line 232). This means project filtering will never work (the field will be ignored since it's not in the schema, and `project_id` will be `undefined`).

4. **Frontend ignores rich routing metadata** — The backend returns `routingStrategy`, `entities`, and `metadata` (with `classificationConfidence`, `reasoning`, `durationMs`) but the frontend discards all of this. The strategy indicator (required by 7.3.2) could be displayed but isn't.

5. **No input sanitization on the frontend** — The query string is sent as-is (only trimmed). While the backend has `sanitizeQuery()` that strips control characters, the frontend doesn't enforce the 2000-character limit. The Zod schema will reject queries > 2000 chars with a 400 error, but the user won't get a friendly inline validation message.

6. **No authentication on the frontend query** — The `POST /api/mcp/query` call (lines 65–73) sends no `Authorization` header. The backend MCP routes require `Bearer ${MCP_PAT}` (lines 20–36 of mcp.ts). This means the frontend query will always get a 401 Unauthorized response. This is a **critical bug** — the query interface is non-functional without auth.

7. **Error handling is basic** — The catch block (lines 78–79) handles errors with a generic message. A 401 will show "Search failed" with no indication that authentication is needed. A 400 from Zod validation will also show "Search failed" without the actual validation message.

8. **No test coverage for the Query page** — No `*.unit.test.ts` files exist for the query page component. The intent-router has unit tests for utility functions (`escapeLike`, `calculateTemporalDecay`, `sanitizeQuery`) but no integration tests for the full `routeQuery` pipeline or the MCP endpoint.

9. **Code quality is good otherwise** — The component is well-structured with clear state management, proper loading/error/result states, and good visual design with theme-aware colors and dark mode support.

10. **The idle state is helpful** — Lines 205–219 show available MCP tool endpoints when no search has been performed, which serves as good onboarding for new users.

## Gaps & Recommendations

1. **[CRITICAL] Fix request body field names** — Change the frontend request body from `{ query, projectId, limit }` to `{ q, project_id, limit }` to match the backend Zod schema. Without this fix, every query will return a 400 error.

2. **[CRITICAL] Add authentication to query requests** — The frontend must include an `Authorization: Bearer ${MCP_PAT}` header. This requires either: (a) storing the PAT in the frontend and sending it with each request, (b) creating a proxy endpoint that adds the server-side PAT, or (c) using a session-based auth mechanism. Option (b) is recommended to avoid exposing the PAT in client-side code.

3. **[BUG] Add `total` to backend response or remove from frontend** — Either add `total: results.length` to the `RouteQueryResult` return value, or change the frontend to use `results.length` instead of `data.total`.

4. **[ENHANCEMENT] Display routing strategy indicator** — The backend returns `routingStrategy` (vector_search, graph_traversal, direct_lookup, hybrid) and `metadata.reasoning`. Display these in the UI (e.g., a small badge below the results header showing "Strategy: vector_search — 0.95 confidence"). This would also satisfy item 7.3.2's strategy indicator requirement.

5. **[ENHANCEMENT] Improve error messages** — Parse the backend error response and show user-friendly messages. For 401, show "Authentication required — please configure your API key in Settings." For 400, show the Zod validation message.

6. **[ENHANCEMENT] Add frontend input validation** — Enforce the 2000-character limit on the frontend with a character counter and disable the Search button when the query is too long.

7. **[TESTING] Add test coverage** — Add component tests for the Query page that verify:
   - Search submission with correct request body shape
   - Result rendering with mock data
   - Error display on failed requests
   - Empty state display
   - Project filter integration
