## Round 1 — Architecture & Design Review

**What 7.4.1 requires ("Project CRUD"):**

The item calls for full Create, Read, Update, Delete operations for projects in the kg-engine frontend. This means:
1. **Create** — A form/dialog to create a new project (name, repo URL, description)
2. **Read** — A project list page showing all projects with stats; a project detail page
3. **Update** — Ability to edit project name, repo URL, description, status
4. **Delete** — Ability to delete a project with confirmation

**Backend implementation (projects.ts):**

The backend provides complete CRUD:
- `GET /projects` — List all projects with aggregated counts (L2, L3, commits)
- `POST /projects` — Create project with Zod-validated body; auto-creates default "System: Uncategorized" L2 node; logs activity
- `GET /projects/:id` — Get single project by ID with counts; 404 if not found
- `PATCH /projects/:id` — Update project fields with Zod-validated body; 404 if not found
- `DELETE /projects/:id` — Delete project; returns 204 No Content

**Frontend implementation:**

The frontend provides:
- **Create** ✅ — Dialog with name + repo URL inputs, validation, error handling, React Query cache invalidation
- **Read (list)** ✅ — Table with name, repo URL, status badge, L2/L3/commit counts, creation date; loading and empty states
- **Read (detail)** ✅ — Project header with stats, tabs for Graph View / Commits / L2 Directory / Bootstrap Review
- **Update** ❌ — No edit form or dialog anywhere in the frontend. The `useUpdateProject` hook exists in the generated API client but is never used in any page component.
- **Delete** ❌ — No delete button or confirmation dialog anywhere in the frontend. The `useDeleteProject` hook exists in the generated API client but is never used.

**API contract alignment:**

| Operation | OpenAPI | Backend | Frontend | Match? |
|-----------|---------|---------|----------|--------|
| Create | `POST /projects` with `ProjectInput` | `CreateProjectBody` (name, repoUrl, description?) | Sends `{ name, repoUrl }` | ✅ Yes |
| Read list | `GET /projects` → `Project[]` | Returns `Project[]` with counts | Uses `useListProjects` + `normalizeProjects` | ✅ Yes |
| Read detail | `GET /projects/:id` → `Project` | Returns `Project` with counts | Uses `useGetProject` | ✅ Yes |
| Update | `PATCH /projects/:id` with `ProjectUpdate` | `UpdateProjectBody` (name?, repoUrl?, description?, status?) | **Not implemented** | ❌ Missing |
| Delete | `DELETE /projects/:id` → 204 | Returns 204 | **Not implemented** | ❌ Missing |

## Round 2 — Code Quality & Security Review

**Findings:**

1. **Update operation completely missing from frontend** — There is no edit button, edit form, or edit dialog on either the project list page or the project detail page. The generated `useUpdateProject` hook (in `lib/api-client-react/src/generated/api.ts`, line 500) is available but never imported or used. This is a **functional gap** — users cannot modify a project after creation.

2. **Delete operation completely missing from frontend** — There is no delete button or confirmation dialog anywhere. The generated `useDeleteProject` hook (line 573) is available but never used. This is a **functional gap** — users cannot remove projects.

3. **No confirmation dialog for destructive actions** — Even if delete were added, there's no confirmation pattern established. The codebase has `Dialog` components available (used in the create project flow), but no delete-confirmation pattern exists.

4. **Backend PATCH returns zeroed counts** — The `PATCH /projects/:id` handler (lines 139–156) returns `l2Count: 0, l3Count: 0, commitCount: 0` instead of computing actual counts like the GET handlers do. This means after an update, the frontend would show zero counts until the next list refresh. This is a **minor bug**.

5. **Backend DELETE has no cascade handling** — The `DELETE /projects/:id` handler (lines 158–162) only deletes the row from `projectsTable`. It does not clean up related records in `l2_nodes`, `l3_nodes`, `commits`, `documents`, `activity_log`, `review_tasks`, `node_links`, `commit_l2_links`, `pull_requests`, `project_integrations`, `notifications`, `subscriptions`, `llm_configs`, or `prompt_templates`. This will cause **foreign key constraint violations** if any related records exist, or **orphaned data** if the DB doesn't enforce FK constraints. This is a **data integrity risk**.

6. **Backend DELETE has no 404 handling** — Unlike GET and PATCH, the DELETE handler does not check if the project exists before deleting. It will return 204 even if the project ID doesn't exist. This is a **minor API design issue**.

7. **Frontend create form doesn't match OpenAPI schema exactly** — The frontend sends `{ name, repoUrl }` but the OpenAPI `ProjectInput` schema requires `name` and `repoUrl` (both required) with optional `description`. The frontend doesn't include a description field in the create dialog. This is a **minor gap** — users cannot set a description at creation time.

8. **Frontend create form doesn't support vcsType or svnUrl** — The backend schema supports both Git and SVN projects (via `vcsType` and `svnUrl` columns), but the create form only has a "Repository URL" field with a placeholder mentioning GitHub. There's no VCS type selector or SVN URL field. SVN project creation through the UI is **not supported**.

9. **No test coverage for project CRUD** — No `*.unit.test.ts` files exist for the project pages or the projects route. The generated API client hooks are untested in the frontend.

10. **Code quality is good where implemented** — The project list page has clean table layout, status badges with color coding, loading/empty states, external link handling with `stopPropagation`, and proper React Query cache invalidation after creation. The project detail page has well-organized tabs, expandable L2 nodes, commit display, and export functionality.

11. **Project selector in layout header works well** — The header project dropdown (in `layout.tsx`) uses `useCurrentProject` hook with localStorage persistence, providing a global project context.

## Gaps & Recommendations

1. **[CRITICAL] Add Update project UI** — Add an "Edit" button to the project detail page (or a kebab menu on list rows) that opens a dialog with fields for name, repoUrl, description, and status. Wire it to `useUpdateProject` with cache invalidation. This is a core CRUD operation that is entirely missing.

2. **[CRITICAL] Add Delete project UI** — Add a "Delete" button with a confirmation dialog (using the existing `Dialog` component pattern) to the project detail page or list page. Wire it to `useDeleteProject` with cache invalidation and redirect to `/projects` after deletion.

3. **[HIGH] Add cascade cleanup to backend DELETE** — The `DELETE /projects/:id` handler must clean up all related records (l2_nodes, l3_nodes, commits, documents, activity_log, review_tasks, node_links, commit_l2_links, pull_requests, project_integrations, notifications, subscriptions, llm_configs, prompt_templates) either via DB-level `ON DELETE CASCADE` or explicit deletion in the handler. Without this, deleting a project with data will either fail with FK errors or leave orphaned records.

4. **[MEDIUM] Fix PATCH to return actual counts** — The update handler should compute and return real `l2Count`, `l3Count`, and `commitCount` values (like the GET handlers do) instead of hardcoding zeros.

5. **[MEDIUM] Add description field to create form** — The create project dialog should include an optional description textarea to match the `ProjectInput` schema.

6. **[MEDIUM] Add 404 check to DELETE handler** — The delete handler should return 404 if the project doesn't exist, consistent with GET and PATCH.

7. **[LOW] Add VCS type selector to create form** — For SVN support, add a VCS type dropdown (Git/SVN) and conditionally show an SVN URL field when SVN is selected.

8. **[LOW] Add test coverage** — Add unit/integration tests for:
   - Project list page rendering and empty/loading states
   - Create project dialog submission and error handling
   - Project detail page tab switching
   - Backend CRUD endpoints (especially cascade delete behavior)
