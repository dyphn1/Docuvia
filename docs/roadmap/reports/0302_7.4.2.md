## Round 1 — Architecture & Design Review

**What 7.4.2 requires ("LLM config management"):**

The item calls for a UI in the kg-engine frontend to view and edit per-project LLM configuration. This means:

1. **Read** — Display current LLM config (provider, model, thresholds, etc.) for a project
2. **Update** — Allow editing LLM config fields and saving changes
3. **Navigation** — A way to access the LLM config UI (dedicated page, settings page, or project detail tab)

**Backend implementation (llm_config.ts):**

The backend provides:

- `GET /projects/:id/llm-config` — Returns LLM config for a project; auto-creates a default config (provider: "openai", model: "gpt-5.2") if none exists. Returns 404 if project not found.
- `PATCH /projects/:id/llm-config` — Updates model and/or provider fields. Auto-creates config if none exists. Uses Zod validation (`LlmConfigInputSchema` with optional `model` and `provider` strings).

**Frontend implementation:**

The frontend provides:

- **Read** ❌ — No LLM config page, component, or tab exists anywhere in the frontend.
- **Update** ❌ — No edit form or dialog for LLM config exists.
- **Navigation** ❌ — No nav item for LLM config in the sidebar. No `/settings` or `/llm-config` route in App.tsx.

## Round 2 — Code Quality & Security Review

**Findings:**

1. **[CRITICAL] No LLM config UI exists in the frontend** — There is no page, component, tab, or dialog for managing LLM configuration. The `useGetLlmConfig` and `useUpdateLlmConfig` hooks are fully generated and available in the API client but are never imported or used anywhere in the frontend codebase. This is a **complete functional gap** — users cannot view or modify LLM settings through the web UI.

2. **[HIGH] Backend GET auto-creates config with hardcoded defaults** — The `GET /projects/:id/llm-config` handler (lines 19–33) auto-creates a config with `provider: "openai"` and `model: "gpt-5.2"` if none exists. This means every project silently gets an OpenAI-specific default, even if the user intends to use a different provider. The `isDefault: false` flag is set, but the hardcoded provider/model values are not appropriate for all deployments. This could cause confusion when the user hasn't explicitly configured anything yet.

3. **[HIGH] Backend PATCH only updates model and provider** — The `LlmConfigInputSchema` (lines 9–12) only accepts `model` and `provider` fields. The DB schema has 11 columns including `similarityThreshold`, `condensationThreshold`, `condensationReviewRequired`, `autoGenerate`, `maxCommitsPerRun`, and `cooldownMinutes`. None of these additional fields are exposed through the API. This means users cannot configure important operational parameters like similarity threshold (default 0.85), condensation threshold (default 30), auto-generation, or cooldown through the API.

4. **[MEDIUM] OpenAPI spec is more limited than DB schema** — The `LlmConfigInput` schema in openapi.yaml (lines 2364–2370) only defines `model` and `provider` properties. The `LlmConfig` response schema (lines 2347–2363) only exposes `id`, `projectId`, `provider`, `model`, `isDefault`, and `createdAt`. The remaining 6 DB columns (`similarityThreshold`, `condensationThreshold`, `condensationReviewRequired`, `autoGenerate`, `maxCommitsPerRun`, `cooldownMinutes`, `updatedAt`) are not in the OpenAPI spec, meaning they're completely hidden from the API contract.

5. **[MEDIUM] Backend PATCH doesn't validate provider values** — The `LlmConfigInputSchema` accepts any string for `provider` with no enum constraint. The OpenAPI spec also has no enum. This means invalid provider names like `"foo"` would be accepted and stored without error.

6. **[MEDIUM] Backend PATCH returns `createdAt` but not `updatedAt`** — Both GET and PATCH handlers return `createdAt: cfg.createdAt.toISOString()` but never include `updatedAt`. The Zod response schema also doesn't include `updatedAt`. This means clients have no way to know when the config was last modified.

7. **[LOW] Backend PATCH uses `updatedAt: new Date()` but it's not returned** — The PATCH handler sets `updatedAt: new Date()` on update (line 61), but the response serialization only includes `createdAt`. The `updatedAt` value is written to the DB but never sent back to the client.

8. **[LOW] No test coverage for llm_config route** — No `*.unit.test.ts` or integration test files exist for the llm_config route. The endpoint behavior (auto-create, update, 404 handling) is untested.

9. **[INFO] Route is properly registered** — The `llmConfigRouter` is correctly imported and mounted in `routes/index.ts` (lines 13, 38), so the backend endpoints are live.

10. **[INFO] Zod validation exists on backend** — The `LlmConfigInputSchema` provides runtime validation on the PATCH handler, preventing invalid types from reaching the DB.

## Gaps & Recommendations

1. **[CRITICAL] Create LLM config management UI** — Add a dedicated settings page or a new tab on the project detail page for LLM configuration. The UI should:
   - Display current config (provider, model, and all advanced settings)
   - Provide an edit form with fields for all 11 DB columns
   - Use `useGetLlmConfig` to fetch and `useUpdateLlmConfig` to save
   - Include cache invalidation after updates
   - Add a route in App.tsx (e.g., `/projects/:id/settings` or `/settings/llm`)
   - Add a nav item in layout.tsx sidebar (e.g., under "System" section)

2. **[HIGH] Expand API to cover all DB columns** — The `LlmConfigInputSchema` and OpenAPI `LlmConfigInput` schema should expose all configurable columns: `similarityThreshold`, `condensationThreshold`, `condensationReviewRequired`, `autoGenerate`, `maxCommitsPerRun`, `cooldownMinutes`. The response should also include `updatedAt`.

3. **[HIGH] Reconsider auto-create defaults on GET** — The `GET /projects/:id/llm-config` handler should return 404 (or a null/empty response) when no config exists, rather than silently creating a hardcoded OpenAI config. This prevents unintended provider/model defaults for deployments using other LLM providers.

4. **[MEDIUM] Add provider enum validation** — The `LlmConfigInputSchema` and OpenAPI spec should constrain `provider` to a known set of values (e.g., `openai`, `anthropic`, `google`, `ollama`, `custom`) to prevent invalid provider names.

5. **[MEDIUM] Return `updatedAt` in API responses** — Both GET and PATCH handlers should include `updatedAt` in the serialized response, and the OpenAPI `LlmConfig` schema and Zod `GetLlmConfigResponse`/`UpdateLlmConfigResponse` should include this field.

6. **[LOW] Add test coverage** — Add unit/integration tests for:
   - GET returning existing config
   - GET auto-creating defaults (or returning 404 after fix)
   - PATCH updating model/provider
   - PATCH with invalid provider/model
   - PATCH auto-creating config when none exists
   - 404 for non-existent project

7. **[LOW] Align OpenAPI spec with DB schema** — The OpenAPI `LlmConfig` response schema should include all 11 columns (or at least all user-configurable ones). The `LlmConfigInput` schema should include fields for all updatable columns.
