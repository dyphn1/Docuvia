## Round 1: Static Code Analysis

### What the code does

The `DocuviaCodeLensProvider` class (in `artifacts/vscode-client/src/DocuviaCodeLensProvider.ts`) implements `vscode.CodeLensProvider` and provides inline CodeLens annotations above function/class declarations showing the count of L3 decisions associated with the matched L2 module.

**CodeLens registration** (`extension.ts:72-86`):
```typescript
const codeLensProvider = new DocuviaCodeLensProvider(store, context);
context.subscriptions.push(
  vscode.languages.registerCodeLensProvider(
    [
      { language: 'typescript' },
      { language: 'javascript' },
      { language: 'typescriptreact' },
      { language: 'javascriptreact' },
      { language: 'python' },
    ],
    codeLensProvider
  )
);
```

The provider is registered for 5 language scopes: TypeScript, JavaScript, TSX, JSX, and Python.

**Declaration detection** — Two-tier approach:
1. **LSP semantic symbols** (preferred): `updateSymbolAnchors()` calls `vscode.executeDocumentSymbolProvider` to get AST-level Function/Class/Method line numbers. Cached in `documentAnchors` map. Updated asynchronously on document save.
2. **Regex fallback** (initial load): `findDeclarationLines()` uses language-specific regex patterns for function/class declarations. Covers all 5 registered languages.

**L3 decision count logic** (`provideCodeLenses()`, lines 159-182):
1. Gets the `KnowledgeSnapshot` for the document's workspace folder.
2. Matches the document's path against L2 module `source_paths` via `findMatchingModules()`.
3. For each matched module, filters `snapshot.routerIndex` to find L3 entries with matching `l2_module_id`.
4. Selects the module with the most decisions (`bestModule`).
5. Creates a CodeLens at **every declaration line** with title: `🧠 Docuvia: N Decision(s)`.
6. Each CodeLens carries a `CodeLensDecisionData` argument (moduleId, moduleName, decisionIds).

**Offline fallback** (lines 185-201): When no L2 module matches (or matched modules have no decisions), falls back to manifest path patterns via `findMatchingManifestModules()` using `minimatch`. Shows `🧠 Docuvia: <moduleName> — connect to server for decisions`.

### Code Quality Observations

- **Clean separation**: The provider is well-structured with clear helper functions (`findMatchingModules`, `findMatchingManifestModules`, `findDeclarationLines`, `normalizeSourcePath`).
- **Caching**: LSP symbol results are cached per-document URI and invalidated on save — good performance design.
- **Graceful degradation**: Returns `[]` for uninitialized workspaces, files outside folders, or unsupported languages. No crash paths found.
- **Dual-mode**: Online (server-backed L2 modules + L3 decisions) and offline (manifest-only) modes are cleanly separated.

## Round 2: Functional Verification

### What works

1. **CodeLens display with L3 count**: ✅ The `provideCodeLenses()` method correctly computes the L3 decision count from `snapshot.routerIndex` and formats the title string as `🧠 Docuvia: N Decision(s)` with correct pluralization.
2. **Declaration line detection**: ✅ Both regex and LSP-based detection are implemented. The regex patterns cover all 5 registered languages.
3. **Module-path matching**: ✅ `findMatchingModules()` correctly computes relative paths and matches against `source_paths`. `findMatchingManifestModules()` uses `minimatch` for glob matching.
4. **Command registration**: ✅ `docuvia.showDecisionsForLens` is registered in `package.json` (line 88) and in `extension.ts` (line 255-261).
5. **Anchor refresh**: ✅ `onDidChangeCodeLenses` event fires on knowledge store load and after async symbol resolution.

### What's broken or incomplete

1. **CRITICAL — `showDecisionsForLens` handler is a no-op** (`extension.ts:257-259`):
   ```typescript
   async (data: CodeLensDecisionData) => {
     // await showDecisionsForLens(store, data);
   }
   ```
   The handler body is **empty** (the actual implementation is commented out). Clicking a CodeLens does nothing. Per the design doc (`editor-integration.md:15-20`), clicking should show a `vscode.window.showQuickPick` with up to 2 decision items and a "View all in Chat" option. This is the most significant gap.

2. **No error handling for missing decision files**: If a decision's `.md` file is deleted after the knowledge graph loads, the `docuvia.openDecision` command (which would be called from the QuickPick) will throw `FileNotFound` with no user-friendly message. This is documented in `user-journeys.md:162`.

3. **Line-number anchoring drift**: The CodeLens uses line-number-based anchoring. When lines are inserted above a function, the lens drifts to the wrong line. This is a known issue documented in `user-journeys.md:148-153` (BUG D-1, D-2). AST-based or hash-based anchoring is planned but not implemented.

4. **Empty `source_paths` in skeleton**: The `initProject` skeleton creates `l2_modules.yaml` with `source_paths: []` by default. New users who don't manually populate `source_paths` will never see any CodeLens. No UI guidance prompts them (documented as BUG D-3 in `user-journeys.md:154`).

5. **Inconsistent path matching**: The CodeLens provider uses `minimatch` for manifest module matching, while the server uses custom RegExp. This can cause mismatches between server-assigned modules and client-side CodeLens display (noted in report `0260_4.2.5.md`).
