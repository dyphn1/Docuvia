## Round 1: Static Code Analysis

### What the code does

The `DocuviaHoverProvider` class (in `artifacts/vscode-client/src/DocuviaHoverProvider.ts`) implements `vscode.HoverProvider` and provides hover tooltips showing L3 decision context when the cursor is over a symbol that has associated L3 knowledge.

**Hover provider registration** (`extension.ts:95-109`):
```typescript
const hoverProvider = new DocuviaHoverProvider(store, indexer);
context.subscriptions.push(
  vscode.languages.registerHoverProvider(
    [
      { language: 'yaml', pattern: '**/.docuvia/*.yaml' },
      { language: 'markdown', pattern: '**/.docuvia/l3_decisions/*.md' },
    ],
    hoverProvider
  ),
  vscode.languages.registerHoverProvider({ language: 'typescript' }, hoverProvider),
  vscode.languages.registerHoverProvider({ language: 'javascript' }, hoverProvider),
  vscode.languages.registerHoverProvider({ language: 'typescriptreact' }, hoverProvider),
  vscode.languages.registerHoverProvider({ language: 'javascriptreact' }, hoverProvider),
  vscode.languages.registerHoverProvider({ language: 'python' }, hoverProvider)
);
```

The provider is registered for 7 language scopes: 5 source languages (TS/JS/TSX/JSX/Python) plus YAML and Markdown for `.docuvia/` data files.

**Hover resolution logic** (`provideHover()`, lines 14-41):
1. Gets the `KnowledgeSnapshot` for the document's workspace folder via `store.getSnapshotFor()`.
2. Calls `indexer.getMatchAt(document.uri, position.line)` to find an L3 decision ID at the cursor line.
3. If a match is found, looks up the full `L3Decision` from `snapshot.decisions`.
4. Builds a `MarkdownString` with:
   - Title: `**L3 Decision** — ${decision.title}`
   - Status badge: `**Status**: \`${decision.status}\``
   - Body preview: first 200 characters of `decision.body`
   - An `[Open Decision](command:docuvia.openDecision?...)` link if `decision.filePath` is set.
5. Returns a `vscode.Hover` wrapping the markdown and the current line's range.

**Indexing mechanism** (`KnowledgeIndexer.ts`):
- `KnowledgeIndexer` maintains a per-file `IntervalTree<string>` mapping line ranges to L3 decision IDs.
- On `indexSnapshot()` (triggered by `store.onDidLoad`), it iterates all router entries and queues `buildTreeForFile()` with a 500ms debounce.
- `buildTreeForFile()` calls `vscode.executeDocumentSymbolProvider` to get AST symbols, then uses `findBestSymbolMatch()` to match L3 decisions to symbols via word-overlap scoring on the decision title.
- If no symbol match is found, the decision is anchored to line 0,0 (effectively a file-level fallback).
- `getMatchAt()` performs an O(log n) interval tree search for the given line.
- `onDidChangeTextDocument` applies `shiftRanges()` to keep the interval tree in sync with live edits.
- `onDidSaveTextDocument` triggers a full rebuild of the tree for the saved file.

### Code Quality Observations

- **Clean, minimal implementation**: The hover provider is only 42 lines with a clear linear flow.
- **IntervalTree is well-implemented**: Proper BST-based interval tree with `insert`, `search`, and `shiftRanges` operations. Handles range shifting for live edits.
- **Graceful degradation**: Returns `undefined` for missing snapshot, no match, or missing decision — no crash paths.
- **Trusted markdown**: Correctly sets `md.isTrusted = { enabledCommands: ['docuvia.openDecision'] }` to enable command links (unlike the old design doc note suggested was broken).

### Design Doc Discrepancy

The design doc (`editor-integration.md:33`) specifies that the hover provider should use a **UUID regex** (`/[0-9a-f]{8}-.../i`) to detect UUIDs in `.docuvia` YAML/Markdown files and look them up in a **three-priority order** (L3 Decision → L2 Module → L1 Tag). The current implementation does **none of this**:

1. **No UUID regex**: The provider does not scan the hovered text for UUID patterns at all.
2. **No L2/L2 lookup**: Only L3 decisions are checked. There is no fallback to L2 module or L1 tag lookup.
3. **Line-based instead of symbol-based for source files**: The design doc describes UUID-based lookup for data files, but the implementation uses line-number-based interval tree matching for source files. This is actually a *different* (and arguably better) approach for source files, but it means the data file hover (Triggers B/C from `user-journeys.md:353-354`) is not implemented as designed.

## Round 2: Functional Verification

### What works

1. **L3 decision hover on source files**: ✅ When a user hovers over a line that falls within an L3 decision's matched symbol range, the hover correctly displays the decision title, status, body preview, and an "Open Decision" link.
2. **Interval tree indexing**: ✅ The `KnowledgeIndexer` correctly builds interval trees by matching L3 decisions to document symbols via title word overlap. The `findBestSymbolMatch()` scoring function is reasonable.
3. **Live edit tracking**: ✅ `onDidChangeTextDocument` applies `shiftRanges()` to keep interval trees in sync with insertions/deletions above the hovered line.
4. **Save-time rebuild**: ✅ `onDidSaveTextDocument` triggers a full tree rebuild, ensuring the index stays accurate after structural changes.
5. **Command link**: ✅ The `[Open Decision]` link uses `command:docuvia.openDecision?...` with `isTrusted` properly configured, and the `docuvia.openDecision` command is registered in `extension.ts:278-283`.
6. **Registration scope**: ✅ All 7 language scopes are registered (5 source + YAML + Markdown).

### What's broken or incomplete

1. **CRITICAL — Data file hover (Triggers B/C) not implemented**: The design specifies that hovering over UUIDs in `.docuvia/l2_modules.yaml` or `.docuvia/l3_decisions/*.md` should show contextual information about the referenced entity. The current implementation relies entirely on `indexer.getMatchAt()` which uses line-number-based interval trees. For YAML/Markdown data files, there is no UUID regex scanning, so hovering over a UUID in `l2_modules.yaml` (e.g., an `l1_tag_id` reference) shows nothing. This is a significant gap for Triggers B and C.

2. **CRITICAL — Three-priority lookup missing**: The design specifies a fallback chain: L3 Decision → L2 Module → L1 Tag. The current implementation only checks L3 decisions. If a UUID in a YAML file references an L2 module or L1 tag, the hover returns nothing.

3. **Symbol matching can produce false positives**: `findBestSymbolMatch()` uses simple word overlap scoring. If a decision title shares words with an unrelated symbol (e.g., a decision titled "Auth Module" matching any function containing "auth"), the hover will show the wrong decision. There is no validation that the matched symbol is semantically related to the decision.

4. **Line 0,0 fallback is too broad**: When no symbol match is found, the decision is inserted at `tree.insert(0, 0, decision.id)`. This means the decision will match line 0 of the file, which could show an unrelated hover at the top of the file. A better approach would be to not insert at all or use a file-level hover.

5. **No `source_paths` filtering for hover**: Unlike the CodeLens provider which matches files against L2 module `source_paths`, the hover provider does not filter by `source_paths`. It shows any L3 decision whose matched symbol range includes the hovered line, regardless of whether the file belongs to the decision's L2 module. This could show irrelevant decisions.

6. **No handling for empty `source_paths`**: Per `user-journeys.md:378`, when `source_paths` is empty for all modules, the expected behavior is to show a one-time info hover guiding the user to configure paths. The current implementation silently shows nothing.

7. **No file existence check for `filePath`**: Per `user-journeys.md:380`, if a decision's `.md` file has been deleted, the "Open Decision" link will lead to an error. No existence check is performed before rendering the link.

**Overall: WARN** — The hover provider's core functionality for source files is well-implemented. Hovering over a symbol that has been matched to an L3 decision correctly shows a rich preview with title, status, body excerpt, and a working "Open Decision" link. The interval tree indexing with live edit tracking and save-time rebuild is solid. However, the data file hover feature (UUID regex scanning in `.docuvia` YAML/Markdown files) and the three-priority lookup chain (L3→L2→L1) specified in the design doc are completely absent. Additionally, there is no `source_paths` filtering, no guidance for empty configurations, no file existence checks, and no automated tests for any of the hover or indexer functionality.
