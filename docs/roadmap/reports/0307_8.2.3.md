## Round 1: Static Code Analysis

### What the code does

Item 8.2.3 tracks the known technical debt item D-05: "CodeLens uses line-number anchoring — drifts as file is edited." This is documented in `docs/design/11-risks-and-debt.md:27` and `docs/design/vscode-client/ui-ux/user-journeys.md:148-164` (BUG D-1, D-2).

Two providers are affected by line-number anchoring:

**1. CodeLens provider** (`DocuviaCodeLensProvider.ts`):

The `provideCodeLenses()` method (line 140) determines declaration lines via two mechanisms:

- **LSP semantic symbols** (preferred): `updateSymbolAnchors()` (line 106) calls `vscode.executeDocumentSymbolProvider` and caches the resulting line numbers in `documentAnchors` (a `Map<string, number[]>`). Updated asynchronously on document save.
- **Regex fallback** (initial load): `findDeclarationLines()` (line 69) scans every line of the document against language-specific regex patterns for function/class declarations.

Both approaches produce **raw line numbers** — integers that are inherently position-dependent. The CodeLens objects are created with `new vscode.Range(lineIndex, 0, lineIndex, 0)` at line 175/195, anchoring them to absolute line positions.

**2. Hover provider** (`DocuviaHoverProvider.ts`):

The `KnowledgeIndexer` (`indexer/KnowledgeIndexer.ts`) maintains per-file `IntervalTree<string>` instances mapping line ranges to L3 decision IDs. The tree is built by `buildTreeForFile()` (line 55) which:

1. Calls `vscode.executeDocumentSymbolProvider` to get AST symbols
2. Matches L3 decisions to symbols via `findBestSymbolMatch()` (word-overlap scoring on decision title vs. symbol name)
3. Inserts the symbol's `range.start.line` and `range.end.line` into the interval tree

Live edits are tracked by `onDidChangeTextDocument()` (line 150) which calls `tree.shiftRanges()` to adjust stored line numbers when lines are inserted/deleted above.

### Anchoring drift mechanism

The drift bug manifests as follows:

1. A CodeLens is placed at line 42 (a function declaration).
2. The user inserts 5 lines above line 42 (e.g., adding imports).
3. The function is now at line 47, but the CodeLens remains at line 42 until the next `provideCodeLenses()` call.
4. On the next call, `findDeclarationLines()` or `updateSymbolAnchors()` re-scans the document and finds the function at line 47 — so the CodeLens is corrected.

**Key insight**: For the CodeLens provider, the drift is **self-healing on re-render** because the declaration detection re-scans the document each time. The drift only persists between the edit event and the next `provideCodeLenses()` invocation. VS Code re-invokes `provideCodeLenses()` on every document change, so the window of drift is very small (one render cycle).

For the **KnowledgeIndexer** (hover), the situation is different:

- `shiftRanges()` attempts to keep the interval tree in sync with edits, but it operates on the **old** tree structure. If a change occurs within an interval (e.g., lines added inside a function), `shiftRanges` only adjusts `end`, not the semantic association.
- The tree is only fully rebuilt on save (`onDidSaveTextDocument` → `buildTreeForFile()`), meaning hover associations can be stale between saves.
- The `findBestSymbolMatch()` function uses word-overlap scoring, which can match the wrong symbol if the document structure changes significantly.

### Code Quality Observations

- **IntervalTree.shiftRanges()** has a subtle bug: when `delta` is negative (lines deleted), the `fromPoint` comparison `node.start >= fromPoint` uses the original `fromPoint` from the edit event. But if multiple content changes are processed in the same event, the second shift operates on already-shifted ranges, potentially corrupting the tree. The code sorts changes by `rangeOffset` descending (line 156) to process from bottom-to-top, which mitigates this for non-overlapping changes but not for overlapping ones.
- **No hash-based or content-based anchoring**: Neither the CodeLens provider nor the KnowledgeIndexer uses content-based anchoring (e.g., hashing the function signature or body snippet). The design doc (`user-journeys.md:164`) mentions "AST or snippet-hash anchoring (tracked in roadmap Phase 4)" as the planned fix.
- **No symbol identity tracking**: The CodeLens provider does not track symbol identity across edits. It re-scans from scratch each time, which is correct but doesn't prevent the one-render-cycle drift.

## Round 2: Functional Verification

### What works

1. **CodeLens re-renders on edit**: ✅ VS Code re-invokes `provideCodeLenses()` on document changes. The regex-based `findDeclarationLines()` re-scans the entire document, so CodeLens positions are corrected within one render cycle of any edit.

2. **KnowledgeIndexer.shiftRanges() for simple insertions**: ✅ When lines are inserted above all indexed ranges, `shiftRanges()` correctly adjusts both `start` and `end` of all intervals. The bottom-to-top processing order of content changes minimizes corruption for non-overlapping edits.

3. **KnowledgeIndexer full rebuild on save**: ✅ `onDidSaveTextDocument` triggers `buildTreeForFile()` which re-queries the LSP for symbols and rebuilds the interval tree from scratch, correcting any accumulated drift.

4. **Hover provider graceful degradation**: ✅ If the interval tree is stale or empty, `getMatchAt()` returns `undefined` and the hover provider returns `undefined` — no crash, no incorrect hover.

### What's broken or incomplete

1. **CONFIRMED — CodeLens drift between render cycles**: When a user inserts lines above a function, the CodeLens visually drifts to the wrong line for one render cycle. This is a brief but noticeable flicker. The `documentAnchors` cache (LSP-based) is only updated on save, so between saves, the CodeLens provider falls back to regex detection which re-scans correctly — but there's still a one-cycle flicker as VS Code re-renders.

2. **CONFIRMED — KnowledgeIndexer drift between saves**: The interval tree is only fully rebuilt on save. Between saves, `shiftRanges()` keeps the tree in sync for simple insertions/deletions above ranges, but:
   - Edits **within** a function's range (e.g., adding lines inside the function) cause `shiftRanges` to extend the `end` of the interval, making it cover more lines than the actual symbol.
   - If the function itself is moved (cut-paste), `shiftRanges` cannot track this — the interval stays at the old position until save-time rebuild.
   - If a new function is inserted that matches the same L3 decision's title better than the original, the interval tree still points to the old range until rebuild.

3. **IntervalTree.shiftRanges() edge case bug**: When multiple overlapping content changes occur in the same event (e.g., a multi-cursor edit or a large paste that replaces existing content), the sequential `shiftRanges` calls can corrupt the tree. The second shift operates on ranges already modified by the first shift. This is a latent bug that could cause hover to show incorrect results or miss valid matches.

4. **No AST-based anchoring**: The design doc (`user-journeys.md:148`) explicitly states: "Line-number anchoring is used exclusively. There is NO AST-based or hash-based anchoring. 'Drift Protection' is a planned feature, not yet implemented." This is the core of D-05.

5. **No symbol identity persistence**: Neither provider tracks symbol identity (e.g., by symbol name + signature hash) across edits. A content-based approach would allow stable anchoring even when lines are inserted/deleted.

6. **findBestSymbolMatch() fragility**: The word-overlap scoring in `findBestSymbolMatch()` can produce incorrect matches when document structure changes. If a new symbol is added that shares more words with a decision title than the original matched symbol, the decision will be incorrectly associated with the new symbol after the next rebuild.

**Overall: WARN** — Item 8.2.3 (D-05) is a **known, documented, and acknowledged** technical debt item. The codebase uses line-number anchoring exclusively for both CodeLens and hover providers. AST-based or hash-based anchoring ("Drift Protection") is explicitly planned for Phase 4 and not yet implemented. In practice, the impact is mitigated by two factors: (1) the CodeLens provider re-scans the document on every render cycle, so drift lasts at most one render cycle, and (2) the KnowledgeIndexer fully rebuilds its interval tree on every document save. However, between saves, complex edits (especially within function ranges or cut-paste operations) can cause the hover provider to show stale associations. The `IntervalTree.shiftRanges()` method also has a latent edge-case bug with overlapping content changes. This item should remain open as WARN until Phase 4 anchoring improvements are implemented.
