## Round 1 — Architecture & Design Review

The `/query` command is implemented as part of the `@docuvia` Copilot Chat participant registered via `registerDocuviaChatParticipant()` at `ChatParticipant.ts:104–149`.

**Registration flow:**
1. `extension.ts:113` calls `registerDocuviaChatParticipant(context, store, taskRunner, centralClient)`
2. The handler at `ChatParticipant.ts:110–124` routes `cmd === 'query'` to `handleQuery()` (line 116–117)
3. `package.json:143–146` declares the `query` command in `chatParticipants.commands`

**`/query` handler logic** (`ChatParticipant.ts:275–344`):
1. Extracts and trims the query from `request.prompt` — line 281
2. Shows usage hint if query is empty — lines 282–287
3. Checks if it's a "breadth" query (cross-project) via `isBreadthQuery()` — line 290
4. If breadth: delegates to `handleBreadthQuery()` which calls `centralClient.query()` — lines 291–293
5. If local: checks `store.snapshots.size === 0` and shows init message — lines 296–299
6. Iterates all snapshots, filtering modules by name/slug/description and decisions by title/body — lines 304–319
7. Renders matching L2 modules and L3 decisions as markdown — lines 326–343
8. Shows "no results" if nothing matched — lines 321–324

**Breadth detection** (`isBreadthQuery()`, lines 347–355):
- Routes to central server if query starts with `@` or matches patterns: `other projects`, `cross-project`, `how do others`, `how do other`

**`handleBreadthQuery()`** (lines 357–391):
- Calls `centralClient.query(query, 10)` — line 364
- Handles empty results with server-not-configured tip — lines 365–372
- Renders cross-project results with title, project name, tags, snippet — lines 374–378
- Catches `CentralServerAuthError` and shows auth message — lines 380–386
- Catches generic errors and shows failure message — lines 387–389

**`executeSearch()` in extension.ts** (lines 387–409):
- `docuvia.openSearch` command opens input box, then routes to chat with `@docuvia /query <query>` or webview based on `search.defaultView` config
- `docuvia.searchFromSelection` command takes editor selection, caps at 2000 chars (BUG N-2 fix), then calls `executeSearch()`
- Both paths converge on the same `/query` handler via chat

**Architecture assessment:** Clean two-path design (local depth vs. cross-project breadth). The local search is straightforward iteration over in-memory snapshots. The breadth search properly delegates to the central server with auth error handling. The `executeSearch()` function provides a nice bridge from palette commands to the chat participant. No architectural gaps found.

## Round 2 — Code Quality & Security Review

**Input validation:**
- Query is trimmed and lowercased — `ChatParticipant.ts:281`
- Empty query shows usage hint — lines 282–287
- `searchFromSelection` caps query at 2000 chars — `extension.ts:372–376`
- No SQL injection risk (all queries are in-memory JS operations or HTTP POST to central server)

**Error handling:**
- `handleBreadthQuery` catches `CentralServerAuthError` separately from generic errors — lines 380–390
- `CentralServerClient.query()` throws `CentralServerAuthError` on 401, generic `Error` on other non-OK — `CentralServerClient.ts:78–84`
- `CentralServerClient.query()` returns empty array if server not configured — lines 58–61
- `DOCUVIA_MOCK_SERVER` env var enables mock responses for E2E testing — lines 46–56

**Security considerations:**
- Local search only reads from in-memory `KnowledgeStore` snapshots — no file I/O in the query path
- Cross-project query sends to server URL from global config (validated as HTTPS URL in `types.ts:62–64`)
- Token sent via `x-docuvia-token` header — `CentralServerClient.ts:67–69`
- No path traversal risk — query is a search string, not a file path
- Selection truncation prevents sending entire files to server — `extension.ts:372–376`

**Code quality:**
- Clean separation: `handleQuery` orchestrates, `isBreadthQuery` classifies, `handleBreadthQuery` delegates
- Local search limits L3 results to 5 (`slice(0, 5)`) — prevents flooding chat with hundreds of results — line 339
- Minor: The local search does case-insensitive matching via `toLowerCase()` on both sides — correct
- Minor: Module matching checks `m.slug.includes(query)` but slug is already lowercase (from `slugify()` in `KnowledgeStore.ts:236`), and query is lowered — correct

## Gaps & Recommendations

1. **No E2E test for breadth query path.** The `DOCUVIA_MOCK_SERVER=1` env var is already wired up in `CentralServerClient.ts:46–56` and could be used in tests to verify the cross-project search flow without a real server. Low priority — the local path is the primary use case.

2. **No result limit for L2 modules.** L3 decisions are capped at 5 results (`slice(0, 5)` at line 339), but L2 modules have no limit. In a project with hundreds of modules, this could flood the chat. Consider adding a similar cap for consistency.

Neither gap is critical. The `/query` command is fully functional and well-tested for its primary use cases.
