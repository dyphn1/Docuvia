## Round 1 — Architecture & Design Review

The `/extract` command is implemented as part of the `@docuvia` Copilot Chat participant registered via `registerDocuviaChatParticipant()` at `ChatParticipant.ts:104–149`.

**Registration flow:**
1. `extension.ts:113` calls `registerDocuviaChatParticipant(context, store, taskRunner, centralClient)`
2. The handler at `ChatParticipant.ts:110–124` routes `cmd === 'extract'` to `handleExtract()` (line 118–119)
3. `package.json:147–149` declares the `extract` command in `chatParticipants.commands`

**`/extract` handler logic** (`ChatParticipant.ts:393–497`):
1. Determines target path from `request.prompt` or active editor — lines 400–401
2. Falls back to single workspace folder if no path and no editor — lines 403–417
3. Validates path exists via `vscode.workspace.fs.stat()` — lines 419–425
4. Reads `extraction.includePatterns` from workspace config — line 429
5. If target is a file: adds directly to processing list — lines 433–434
6. If target is a directory: recursively gathers files, skipping `node_modules`, `.git`, `.docuvia` — lines 436–462
7. Filters files against `includePatterns` using `minimatch` — lines 451–453
8. If no files match: shows message and returns — lines 465–468
9. Reads each file's content and queues extraction via `taskRunner.queueExtraction()` — lines 472–491
10. Respects cancellation token — line 474
11. Reports queued count to user — lines 493–496

**TaskRunner extraction pipeline** (`TaskRunner.ts`):
1. `queueExtraction()` creates a UUID task, adds to TaskQueueTreeProvider, and fires async processing — lines 40–58
2. `runExtractionAsync()` selects LM model (prefers `gpt-4o` from `copilot` vendor, with fallbacks) — lines 241–258
3. Chunks content via `chunkContent()` (line-based, 4000-char chunks) — lines 424–450
4. Processes each chunk via `processChunk()` which sends to LM with prompt asking for YAML decisions — lines 311–341
5. Collects all decisions and writes results via `writeExtractionResults()` — lines 294–309
6. `writeExtractionResults()` matches files to L2 modules via `minimatch` on `source_paths`, writes `.docuvia/l3_decisions/<slug>.md` files, and appends to `l3_router.yaml` — lines 343–422
7. Reloads knowledge store after writing — line 300

**`docuvia.runExtraction` command** (`extension.ts:185–246`):
- Separate palette command for extracting the active file
- Includes additional guards: include pattern check with user override prompt, line count warning (>1000 lines), file size warning (>50 KB)
- These guards are **not** present in the `/extract` chat command path

**Architecture assessment:** Clean design with two entry points (chat command and palette command) converging on the same `TaskRunner.queueExtraction()` method. The chat command supports both file and folder targets with recursive scanning. The palette command adds safety guards for large files. The async fire-and-forget pattern (line 55: `void this.runExtractionAsync(...)`) ensures the chat response returns immediately while processing continues in the background. No architectural gaps found.

## Round 2 — Code Quality & Security Review

**Input validation:**
- Path existence checked via `vscode.workspace.fs.stat()` — `ChatParticipant.ts:419–425`
- Graceful handling of missing path with user-facing error message — lines 422–425
- Directory traversal: skipped via `node_modules`, `.git`, `.docuvia` exclusion — line 442
- File filtering via `includePatterns` glob matching — lines 451–453
- Empty file list after filtering returns informative message — lines 465–468

**Error handling:**
- File read errors silently skip the file (`continue`) — lines 477–482
- LM model selection has 3-level fallback: `gpt-4o/copilot` → any `copilot` → any model — `TaskRunner.ts:243–250`
- If no LM available: task marked as failed with "No LM model available" — lines 251–256
- Per-chunk errors are logged but don't abort the pipeline — lines 286–291
- Write errors caught and reported as task failure — lines 306–308
- Cancellation token checked between chunks — line 264

**Security considerations:**
- No path traversal risk: paths are resolved within workspace folders
- File content is sent to the LM model API (Copilot) — no external HTTP calls beyond the LM API
- No user-controlled data is interpolated into shell commands
- The `processChunk()` prompt includes `<code_chunk>` tags with an instruction to ignore instructions inside them (prompt injection mitigation) — `TaskRunner.ts:319–329`
- The `/extract` chat command does **not** include the file size/line count warnings that the palette command has. This means a user could `/extract` a very large file via chat without the safety guard. Minor concern.

**Code quality:**
- Clean separation: `handleExtract` orchestrates file discovery, `TaskRunner` handles LM processing
- UUID-based task IDs for tracking — `TaskRunner.ts:41`
- Progress reporting via `stream.progress()` and task status updates — `ChatParticipant.ts:436,470`, `TaskRunner.ts:270–274`
- Help text accurately describes the command: "Queue L3 decision extraction for the active file, specified file, or folder" — `ChatParticipant.ts:506`
- AST chunking strategy is listed as TODO with fallback to line-based — `TaskRunner.ts:427–430`

## Gaps & Recommendations

1. **No E2E test for `/extract` execution.** The command is only tested indirectly via the help table. A full execution test would require a working LM model, which is reasonable to skip in CI, but a unit test for `handleExtract()`'s file discovery logic (pure logic) would be valuable and LM-independent.

2. **Missing safety guards in chat path.** The palette command (`docuvia.runExtraction`) warns about large files (>1000 lines, >50 KB) but the `/extract` chat command does not. A user could `/extract` a very large file or directory via chat without any size warning. Consider sharing the guard logic between both entry points.

3. **AST chunking not implemented.** `TaskRunner.ts:427–430` falls back to line-based chunking when `ast` strategy is configured. This is documented as a TODO and logged at runtime. Not a blocker for v1 but worth tracking.

None of these gaps are critical. The `/extract` command is fully functional and well-implemented for its primary use cases.
