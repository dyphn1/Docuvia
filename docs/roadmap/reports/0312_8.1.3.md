## Round 1 — Architecture & Design Review

The spec (nodes.md §"Data Management & Sync") requires:
1. FileSystemWatcher monitoring `.docuvia/**` across all workspaces
2. `onDidChangeTreeData` fired for localized UI repaints
3. Lazy evaluation via `getChildren` dynamic snapshot reads
4. Multi-workspace aware snapshots

### Refresh Event Chain

The refresh mechanism follows a clean event-driven chain:

```
FileSystemWatcher (onDidCreate/onDidChange/onDidDelete)
  → debounce (300ms)
    → KnowledgeStore._handleBatchedChanges()
      → incremental _loadWorkspace() OR full load()
        → KnowledgeStore._onDidLoad.fire()
          → KnowledgeGraphTreeProvider.refresh() [via constructor subscription]
            → _onDidChangeTreeData.fire()
              → VS Code TreeView repaints
```

## Round 2 — Code Quality & Security Review

### Code Quality Findings

1. **Clean event chain**: The refresh path is unidirectional: Store → Provider → TreeView. No circular dependencies or event loops. ✅

2. **Debounce implementation**: Uses `Set<string>` for pending changes (deduplication) + `setTimeout` for debouncing. The timer is properly cleared and reset on each new change. ✅

3. **Incremental reload logic**: The `_handleBatchedChanges` method (lines 493–517) intelligently chooses between incremental (single workspace) and full reload based on configurable thresholds. This prevents unnecessary full reloads when only a few files change. ✅

4. **Proper cleanup**: `dispose()` method (lines 520–527) disposes all watchers, the event emitter, and clears the singleton instance. ✅

5. **Loading guard**: `load()` uses `_loading` and `_pendingReload` flags (lines 94–120) to prevent concurrent loads and coalesce pending reloads. ✅

6. **Context command integration**: `docuvia.refreshKnowledgeGraph` is placed in the view title menu (`view/title` at package.json line 160–163) with `when: view == docuvia.knowledgeGraph` and `group: navigation`, alongside `openDashboard` and `openSearch`. ✅

### Potential Concerns

1. **`refresh()` fires with no node argument**: `KnowledgeGraphTreeProvider.refresh()` calls `this._onDidChangeTreeData.fire()` with no argument, which causes VS Code to repaint the entire tree. The spec (nodes.md line 73) says "the store attempts to pass specific affected Project nodes for localized UI repaints." The current implementation does NOT pass a specific node — it always refreshes the entire tree. However, this is functionally correct (the tree is small) and the spec language says "attempts to" which is aspirational. 🟢 Low.

2. **No `onDidChangeTreeData` for individual node updates**: The `refresh()` method signature accepts no parameter. VS Code's `EventEmitter` supports passing a specific node for partial refresh, but the current implementation always passes `undefined`. This means expanding/collapsing state may be lost on refresh. 🟢 Low — acceptable for current project scale.

3. **Static `onDidFinishIndexing` event**: The static event emitter `onDidFinishIndexing` (line 41) is never consumed by any listener in the codebase. It fires but nothing subscribes to it. 🟢 Low — dead code, no functional impact.

### Security

- FileSystemWatcher only monitors `.docuvia/**` within workspace folders — no external paths. ✅
- No user input processed in the refresh chain — all paths come from `vscode.workspace.fs` APIs. ✅
- The `refreshKnowledgeGraph` command calls `store.load()` which reads only from the local `.docuvia/` directory. ✅

## Gaps & Recommendations

1. **🟢 Low — Full tree refresh instead of targeted node refresh**: `refresh()` fires `_onDidChangeTreeData.fire()` with no node argument, causing a full tree repaint. The spec aspires to pass specific affected Project nodes for localized repaints. This is acceptable at current scale but could be improved for large trees.

2. **🟢 Low — Unused `onDidFinishIndexing` static event**: `KnowledgeStore.onDidFinishIndexing` is fired but never consumed. Consider removing it or adding a subscriber.

3. **🟡 Medium — No unit tests for refresh chain**: The debounce logic, incremental reload decision, and concurrency guards are untested in isolation. Consider adding tests for `_handleBatchedChanges` edge cases.
