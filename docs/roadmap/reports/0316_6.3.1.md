## Round 1 — Architecture & Design Review

**Route mounting:** The webhook router is correctly mounted in `app.ts:33` with `express.raw({ type: "application/json" })` BEFORE `express.json()`, which is required for HMAC-SHA256 signature validation to work on the raw body. The route is intentionally not in `routes/index.ts` since it needs raw body parsing.

**HMAC-SHA256 validation:** The `validateGitHubSignature()` function (lines 24–33) correctly uses `crypto.timingSafeEqual()` with buffer padding to prevent timing attacks. The implementation is sound.

**Event handling:** The handler processes:

- `action === "opened"` — upserts PR record, ingests commits, notifies subscribers (lines 200–254)
- `action === "synchronize"` — same as opened, updates headSha (lines 200–254)
- `action === "closed" && isMerged` — updates PR state, sets L3→valid, generates AI summary, posts PR comment (lines 255–340)
- `action === "closed"` (without merge) — updates PR state to "closed" only (lines 341–352)
- Non-`pull_request` events — returns 200 "Event ignored" (lines 158–160)

**Architecture gap — `closed` without merge does NOT set L3→orphaned:** When a PR is closed without merging (line 341), only the `pullRequestsTable.state` is updated to `"closed"`. The L3 nodes associated with the PR's commits are left in `"pending"` status forever. Per ADR-011, these should be set to `"orphaned"`. This is a ~10 line fix: add a DB update similar to the merge path's L3 update but setting `validityStatus: "orphaned"`.

**Architecture gap — `ping` and `reopened` events:** The handler only checks `eventType !== "pull_request"` and returns 200 for everything else. GitHub sends a `ping` event on webhook creation — this is silently ignored (acceptable but could return a more informative response). The `reopened` action on pull requests falls through to the final `catch` without any handling — the PR record is not updated and no processing occurs.

**Async processing:** The handler correctly responds with 202 immediately (line 195) and processes asynchronously via `setImmediate` (line 198), preventing GitHub timeout retries.

## Round 2 — Code Quality & Security Review

**Security gap — No fail-closed when `GITHUB_WEBHOOK_SECRET` is unset (lines 136–145):** If the environment variable is not configured, both `if` conditions are false and the code falls through without any authentication. This means the endpoint accepts arbitrary POST payloads from anyone. In production, this could allow attackers to trigger PR analysis, L3 validity changes, or send malicious payloads. The correct behavior should be: if `GITHUB_WEBHOOK_SECRET` is not set, log a warning and either reject all requests or refuse to start.

**Error handling:** The `setImmediate` callback has a try/catch (lines 199–367) that logs errors and marks PR analysis as "failed" if it was "in_progress". However, the error handler at line 356 uses `.catch(() => {})` to swallow errors from the failure-marking query itself — this is acceptable defensive design.

**Input validation:** The handler validates `projectId` is a number (line 128), validates JSON parsing (line 148), checks for `pull_request` payload (line 162), and verifies the project exists (line 167). These are appropriate guards.

**No `securitySchemes` in OpenAPI spec:** The webhook path at line 1377 has no authentication documented. Since webhooks use HMAC signatures rather than Bearer tokens, this is partially justified, but the spec should document the `X-Hub-Signature-256` header requirement.

## Round 3 — Integration & Completeness Review

**Zero test coverage:** No test files exist for the webhook endpoint. The MSW fixtures (`github-pr.json`, `github-commits.json`) are used for mocking GitHub API responses in other tests, not for testing the webhook handler itself. There are no tests for:

- HMAC validation (valid/invalid/missing signature)
- PR opened/synchronize/closed/merged event handling
- L3 validity status transitions
- Error paths (invalid project, missing payload, etc.)

**OpenAPI spec alignment:** The spec at lines 1377–1401 documents the path correctly with 202/400/404 responses. However, it's missing:

- `X-Hub-Signature-256` header parameter
- `X-GitHub-Event` header parameter
- `ping` event handling documentation

**Route path mismatch between spec and code:** The spec says `/webhooks/github/{projectId}` and the code mounts at `/api/webhooks/github` with the router handling `/:projectId`. This means the actual path is `/api/webhooks/github/{projectId}` — the `/api` prefix is added by `app.ts:40`. The spec server is defined at `/api` (line 7), so the spec path `/webhooks/github/{projectId}` correctly resolves to `/api/webhooks/github/{projectId}`. ✓

**Notification integration:** The handler correctly queries `subscriptionsTable` and creates notifications for both `new_pr_opened` and `pr_merged` events (lines 241–252, 327–338). This is properly integrated.

## Gaps & Recommendations

1. **[HIGH] Add L3→orphaned on PR close-without-merge:** In the `action === "closed"` branch (line 341), add a DB update to set `l3NodesTable.validityStatus = "orphaned"` for commits associated with the closed PR, mirroring the merge path's L3 update logic.

2. **[HIGH] Fail-closed when `GITHUB_WEBHOOK_SECRET` is unset:** Add an `else` clause after line 145 that returns 500 or 401 when `webhookSecret` is not configured. Alternatively, validate at startup and refuse to start the server without the secret.

3. **[HIGH] Add test coverage:** Create integration tests for the webhook endpoint covering: valid HMAC signature, invalid signature, missing signature, PR opened event, PR merged event (L3→valid), PR closed-without-merge event (L3→orphaned), and invalid project ID.

4. **[MEDIUM] Handle `reopened` action:** Add handling for `action === "reopened"` to reset PR state to "open" and re-ingest commits.

5. **[LOW] Improve `ping` response:** Return a more informative response for `ping` events (e.g., `{ message: "pong" }`) to aid webhook setup debugging.

6. **[LOW] Document headers in OpenAPI spec:** Add `X-Hub-Signature-256` and `X-GitHub-Event` as header parameters to the webhook path in `openapi.yaml`.
