## Round 1 — Architecture & Design Review

**Core HMAC-SHA256 implementation:** The `validateGitHubSignature()` function (`github_webhooks.ts:24–33`) is compact and correct:

```typescript
function validateGitHubSignature(rawBody: Buffer, signature: string, secret: string): boolean {
  const expected = `sha256=${crypto.createHmac("sha256", secret).update(rawBody).digest("hex")}`;
  const sigBuf = Buffer.from(signature.padEnd(expected.length, "\0"));
  const expBuf = Buffer.from(expected.padEnd(sigBuf.length, "\0"));
  return crypto.timingSafeEqual(expBuf, sigBuf);
}
```

The implementation: (1) computes `sha256=<hex>` using `crypto.createHmac`, (2) pads both buffers to equal length with null bytes, (3) uses `crypto.timingSafeEqual` for constant-time comparison. This correctly prevents timing attacks. ✅

**Raw body middleware ordering:** In `app.ts:33`, the webhook route is mounted with `express.raw({ type: "application/json" })` BEFORE `express.json()` (line 37). This is critical — HMAC validation requires the raw unmodified body bytes. ✅

**Signature header extraction:** Line 133 reads `req.headers["x-hub-signature-256"]` — the correct GitHub header name. ✅

**Conditional validation flow (lines 136–145):**

```
if (webhookSecret && signature) → validate or reject
else if (webhookSecret && !signature) → reject with 400
else → no validation (falls through)
```

The missing `else` branch means when `GITHUB_WEBHOOK_SECRET` is unset, all requests pass without any authentication. This is a **critical fail-closed gap** — the endpoint accepts arbitrary POST payloads, allowing attackers to trigger PR state changes, L3 validity transitions, and LLM API calls.

**Key difference from 6.3.1:** Item 6.3.1 verified the webhook listener *exists and is routed*. Item 6.3.2 specifically validates the HMAC-SHA256 *signature verification logic*. The crypto implementation itself is sound — the gap is in the conditional enforcement.

## Round 2 — Code Quality & Security Review

**Timing-safe comparison:** ✅ Uses `crypto.timingSafeEqual()` with buffer padding — correct.

**Buffer padding approach:** The padding with `"\0"` (null bytes) to equalize lengths before `timingSafeEqual` is a valid technique. This prevents leaking length information through timing. An alternative would be to compare `expected.length === signature.length` first and return false immediately, but the padding approach is equally secure.

**HMAC algorithm choice:** Uses SHA-256 as required by GitHub's `X-Hub-Signature-256` header. GitHub deprecated SHA-1 (`X-Hub-Signature`) — this implementation correctly uses SHA-256. ✅

**Fail-closed gap (CRITICAL):** When `process.env.GITHUB_WEBHOOK_SECRET` is undefined:
- Line 136: `webhookSecret` = `undefined`
- Line 137: `undefined && signature` = `false` — skips validation
- Line 142: `undefined && !signature` = `false` — skips rejection
- Code falls through to process the webhook with zero authentication

This means any unauthenticated caller can: (1) trigger commit ingestion, (2) change PR state in the DB, (3) set L3 nodes to `valid` or `pending`, (4) trigger LLM API calls via `generatePrAiSummary()`, (5) post PR comments via the GitHub token. This is effectively an unauthenticated write API.

**No runtime validation of secret format:** The code doesn't check if the secret is a reasonable length or format. An empty string `GITHUB_WEBHOOK_SECRET=""` would technically pass the `if (webhookSecret)` truthiness check (empty string is falsy, so it would actually skip validation). This is fine — the real fix is fail-closed behavior.

## Round 3 — Integration & Completeness Review

**Zero test coverage for signature validation:** No test files exist for the webhook endpoint anywhere in `artifacts/api-server/test/`. There are no tests verifying:
- Valid signature acceptance
- Invalid signature rejection
- Missing signature rejection
- Missing `GITHUB_WEBHOOK_SECRET` behavior

The MSW fixtures (`github-pr.json`, `github-commits.json`) mock GitHub API responses (outbound calls) but don't test the webhook handler itself.

**OpenAPI spec gap:** The webhook path in `openapi.yaml` (lines 1377–1401) does **not** document:
- `X-Hub-Signature-256` header parameter
- `X-GitHub-Event` header parameter
- The `400 "Invalid signature"` response reason (only says "Invalid signature or bad payload")
- No `securitySchemes` — the endpoint's authentication mechanism is undocumented

**Deployment documentation:** `docs/design/07-deployment.md` (line 44) correctly documents `GITHUB_WEBHOOK_SECRET` as "Required when GitHub PR integration is active." However, the code doesn't enforce this — the server starts without the secret and silently accepts unsigned webhooks.

## Gaps & Recommendations

1. **[CRITICAL] Add fail-closed behavior when `GITHUB_WEBHOOK_SECRET` is unset:** Add an `else` clause after line 145 that returns `401` or `500` when the secret is not configured. Better yet, fail at startup: check `GITHUB_WEBHOOK_SECRET` at app initialization and refuse to start if it's missing when the webhook route is mounted.

2. **[HIGH] Add HMAC validation test coverage:** Create integration tests covering: (a) valid signature → 202 accepted, (b) invalid signature → 400 rejected, (c) missing `X-Hub-Signature-256` header → 400 rejected, (d) missing `GITHUB_WEBHOOK_SECRET` env var → request rejected.

3. **[MEDIUM] Document webhook headers in OpenAPI spec:** Add `X-Hub-Signature-256` and `X-GitHub-Event` header parameters to the `/webhooks/github/{projectId}` path in `openapi.yaml`. Consider adding a `securitySchemes` section or at minimum documenting the auth mechanism.
