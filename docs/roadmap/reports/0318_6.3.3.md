## Round 1 — Architecture & Design Review

**Three-endpoint PR analysis surface:**

1. **`GET /projects/:id/pull-requests`** (lines 16–37): Lists all PRs for a project, ordered by `createdAt DESC`. Returns serialized PR objects. Validates project existence first. ✅

2. **`GET /projects/:id/pull-requests/:prNumber`** (lines 40–122): Returns PR detail with knowledge graph impact: commit count, linked L2 nodes, linked L3 nodes. L3 nodes are joined through L2 to scope by `projectId`, then filtered by matching `commitHash` against commits ingested after the PR's `createdAt`. ✅ (with caveat — see Round 2)

3. **`POST /projects/:id/pull-requests/:prNumber/analyze`** (lines 125–240): Manually triggers async AI impact analysis. Guards against re-running completed analyses (returns 202 "already_completed"). Gathers L2/L3 nodes created after the PR's `createdAt`, sends them to GPT-4o for summary, stores result in `aiSummary` column.

**Webhook-triggered analysis (github_webhooks.ts, lines 255–340):** On PR merge (`action === "closed" && isMerged`), the webhook handler: (a) sets PR state to "merged", (b) fetches PR commits and sets associated L3 nodes to `valid`, (c) generates AI summary via `generatePrAiSummary()`, (d) posts the summary as a PR comment via `postPrComment()`, (e) notifies subscribers. This satisfies the "fetch commits, diff, post comment" requirement. ✅

**GitHub client library (`github-client.ts`):**

- `fetchPrCommits()` — Paginated fetch (max 250 commits across 3 pages), returns sha/message/author. ✅
- `fetchPrDiff()` — Fetches unified diff using `application/vnd.github.v3.diff` Accept header. ⚠️ Defined but never called in the analysis flow.
- `postPrComment()` — Posts to `/issues/{prNumber}/comments` endpoint. Silently logs errors (no throw). ✅
- `parseGithubRepo()` — Extracts owner/repo from URL via regex. ✅
- `checkCommitInDefaultBranch()` — Uses GitHub compare API. ⚠️ Defined but never called in the analysis flow.

## Round 2 — Code Quality & Security Review

**Async analysis pattern:** The `POST /analyze` endpoint responds with 202 immediately and processes via `setImmediate` (line 156). This is correct — PR analysis involves LLM calls that can take seconds. ✅

**Status tracking:** The `analysisStatus` column (`pending` → `in_progress` → `completed`/`failed`) provides a clean state machine. The `already_completed` guard (line 146) prevents accidental re-runs. The catch block (lines 227–237) sets status to `failed`. ✅

**PR comment posting:** `postPrComment()` (github-client.ts:80–100) fires on merge but errors are only logged (line 98), not propagated. This is acceptable — a failed comment shouldn't fail the webhook processing. ✅

**GET detail endpoint — imprecise commit scoping (MEDIUM):** The detail endpoint (lines 61–71) fetches commits where `gte(commitsTable.createdAt, pr.createdAt)`. This time-range approach can include commits from _other_ PRs that were ingested after this PR was created. A more precise approach would filter by a direct PR-to-commit link table. For a single-PR workflow this is unlikely to cause issues, but in multi-PR environments it could return inflated commit counts and unrelated L3 nodes.

**Missing unique constraint on `githubPrNumber` per project (LOW):** The `pull_requests` table has no unique constraint on `(projectId, githubPrNumber)`. The upsert logic in the webhook handler (github_webhooks.ts:212–234) handles this with a SELECT-then-INSERT/UPDATE pattern, which is correct but vulnerable to race conditions under concurrent webhook deliveries.

**Unused functions — `fetchPrDiff` and `checkCommitInDefaultBranch`:** Both are implemented in `github-client.ts` but never called anywhere in the codebase. `fetchPrDiff` was likely intended to be part of the PR analysis context but the current `generatePrAiSummary()` and webhook analysis only use L2/L3 nodes, not the raw diff. This is dead code — not a bug, but it indicates the analysis could be richer with diff context.

**No input validation on `POST /analyze` body:** The endpoint accepts any request body (unused). Since all parameters come from the path, this is fine — but the OpenAPI spec doesn't document a request body, which is correct since none is needed.

## Gaps & Recommendations

1. **[HIGH] Add test coverage for PR analysis routes:** Create integration tests covering: (a) `GET /projects/:id/pull-requests` returns correct list, (b) `POST /analyze` triggers async analysis and stores `aiSummary`, (c) `POST /analyze` returns `already_completed` on re-run, (d) webhook merge path generates summary and posts comment, (e) analysis status transitions through the full state machine.

2. **[HIGH] Include diff context in AI summary generation:** The `fetchPrDiff()` function exists but is never called. The AI summary should include the PR's unified diff alongside L2/L3 changes for a richer impact analysis. This is a ~5 line change in `generatePrAiSummary()` (github-webhooks.ts) and in the `POST /analyze` handler.

3. **[MEDIUM] Improve commit scoping in GET detail endpoint:** Instead of time-range filtering (`gte(commitsTable.createdAt, pr.createdat)`), create a `pr_commits` junction table or filter by commits actually fetched from the GitHub PR commits API. This prevents false positives when multiple PRs are active.

4. **[LOW] Add unique constraint `UNIQUE(projectId, githubPrNumber)`:** Add a database-level unique constraint on `(projectId, githubPrNumber)` to prevent duplicate PR records under race conditions. The application-level SELECT-then-UPSERT in the webhook handler handles the happy path but isn't atomic.

5. **[LOW] Remove or use dead code:** Either integrate `fetchPrDiff` and `checkCommitInDefaultBranch` into the analysis flow, or remove them to reduce the maintenance surface.
