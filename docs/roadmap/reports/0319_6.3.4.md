## Round 1 — Architecture & Design Review

**Schema completeness:** The `pull_requests` table is fully defined across all three schema sources (Drizzle ORM, migration SQL, snapshot) with 14 columns: `id`, `projectId`, `githubPrNumber`, `title`, `body`, `headSha`, `baseSha`, `author`, `state` (pr_state enum), `url`, `analysisStatus` (pr_analysis_status enum), `aiSummary`, `mergedAt`, `createdAt`, `updatedAt`. Two pgEnums are defined: `pr_state` (open/closed/merged) and `pr_analysis_status` (pending/in_progress/completed/failed). All three sources are in sync — no schema drift.

**REST API routes:** Three endpoints are implemented in `pull_requests.ts`:
- `GET /projects/:id/pull-requests` — Lists all PRs for a project, ordered by `createdAt desc` (lines 16–37)
- `GET /projects/:id/pull-requests/:prNumber` — Returns PR detail with L2/L3 impact nodes and AI summary (lines 40–122)
- `POST /projects/:id/pull-requests/:prNumber/analyze` — Triggers async AI analysis (lines 125–240)

**Webhook integration:** The webhook handler (`github_webhooks.ts`) upserts PR records on `opened`/`synchronize` actions (lines 200–235) and updates state to `merged` + triggers AI summary generation on `closed`+merged (lines 255–324). The webhook creates the `pull_requests` record before ingesting commits, ensuring the PR exists for analysis.

**OpenAPI spec:** All three endpoints are documented in `openapi.yaml` (lines 1304–1376) with `PullRequest`, `PullRequestDetail`, and `PrAnalyzeResult` schemas. Generated hooks (`useListPullRequests`, `useGetPullRequestDetail`, `useAnalyzePullRequest`) exist in `api.ts`.

**Frontend:** The `pull-requests.tsx` page (416 lines) provides a full PR management UI with project selector, webhook setup card, PR list with state/analysis badges, detail panel with L2/L3 impact, and manual analyze trigger. Uses generated hooks correctly.

**Findings:**
1. ⚠️ **No unique constraint on `(projectId, githubPrNumber)`:** Neither the Drizzle schema, migration SQL, nor snapshot defines a unique index on `(project_id, github_pr_number)`. The webhook handler does an application-level upsert (SELECT then INSERT/UPDATE), which is correct but vulnerable to race conditions under concurrent webhook deliveries. A `UNIQUE` constraint would provide a safety net.
2. ⚠️ **No test coverage:** There are zero integration tests for the pull_requests routes. The factory imports `pullRequestsTable` but no test file exercises the PR endpoints. The `github-pr.json` MSW fixture exists but is not used in any PR-specific test.
3. ⚠️ **GET detail uses time-range commit scoping:** The detail endpoint (lines 61–69) fetches commits where `commits.createdAt >= pr.createdAt`. This is imprecise in multi-PR environments where commits from different PRs may overlap in time. A more robust approach would use the PR's commit list from GitHub's API.

## Round 2 — Code Quality & Security Review

**Input validation:** All three endpoints validate `projectId` and `prNumber` with `isNaN()` checks and return 400 for invalid input. The list endpoint validates project existence (404 if missing).

**Error handling:** The async analysis endpoint (lines 156–238) has a try/catch that sets `analysisStatus: "failed"` on error. The `.catch(() => {})` on the failure update (line 236) prevents cascading errors.

**Serialization:** The `serializePr()` function (lines 242–249) correctly converts timestamps to ISO strings and handles nullable `mergedAt`.

**Security gaps:**
- No authentication on any of the three PR endpoints (consistent with the rest of the API — no auth middleware exists on non-MCP routes)
- The `POST /analyze` endpoint triggers expensive LLM calls without auth — an attacker could exhaust API credits
- No rate limiting on the analyze endpoint

**Code quality:** The `analysisStatus === "completed"` check at line 146 returns 202 with a message but still proceeds to re-run analysis (the response is sent at line 154, but the check at line 146 doesn't actually prevent re-analysis — it just returns an informational 202 while the async work continues). This is a minor logic issue: the guard should either block re-analysis or be removed.

## Round 3 — Integration & Completeness Review

**End-to-end flow:** The full chain works: GitHub webhook → upsert PR record → ingest commits → manual/auto analysis → AI summary stored in `pull_requests.aiSummary` → frontend displays impact. The webhook creates the PR record, and the merge handler generates the AI summary and posts a GitHub comment.

**Route mounting:** The router is correctly imported at `routes/index.ts:18` and mounted at line 43 via `router.use(pullRequestsRouter)`.

**Generated hooks:** All three endpoints have generated React Query hooks in `api.ts` (lines 4437–4470+), and the frontend page uses them correctly.

**Webhook ↔ route consistency:** The webhook handler uses the same `pullRequestsTable` schema and field names as the REST routes. No drift between write path (webhook) and read path (REST).

**Missing features:**
- No `PATCH /projects/:id/pull-requests/:prNumber` endpoint for manual state updates
- No pagination on the list endpoint
- No server-side filtering by state or analysisStatus
- No `reopened` action handler in the webhook (only `opened`, `synchronize`, `closed`)

## Gaps & Recommendations

1. **Add unique constraint:** Create a migration adding `UNIQUE (project_id, github_pr_number)` to prevent duplicate PR records under concurrent webhook deliveries.
2. **Add integration tests:** Test the full webhook → REST → frontend chain, including PR creation via webhook, analysis triggering, and detail retrieval.
3. **Add `reopened` handler:** Handle `action === "opened"` already covers reopens (GitHub sends `opened` for both new and reopened PRs), so this is actually fine — but add a comment in the code to clarify this for future maintainers.
4. **Consider auth on analyze endpoint:** At minimum, add rate limiting to prevent abuse of the LLM-triggering endpoint.
