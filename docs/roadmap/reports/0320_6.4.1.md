## Round 1 — Architecture & Design Review

**Core dispatcher implementation:** The `notifyExternalIntegrations()` function in `slack-teams-client.ts` (lines 137–162) is the central dispatcher. It:
1. Queries `projectIntegrationsTable` for enabled integrations matching the project ID
2. Filters by `notificationTypes` array if configured (line 150–151)
3. Routes to `postSlackMessage()` or `postTeamsMessage()` based on `integrationType`
4. Wraps everything in try/catch with graceful degradation (line 159–161)

**Slack payload builder:** `buildSlackPayload()` (lines 11–49) produces Slack Block Kit messages with:
- Emoji mapping for 3 event types: `new_commit`, `new_l3_node`, `cross_link_detected` (lines 16–25)
- Title mapping for the same 3 event types
- Optional fields for `l3Count`, `commitCount`, and `similarity` from the payload object
- Fallback to `:bell:` emoji and raw event type string for unknown event types

**Teams payload builder:** `buildTeamsPayload()` (lines 75–111) produces Teams MessageCard payloads with the same 3 event types and color coding.

**Invocation call sites:** `notifyExternalIntegrations` is called from 3 places:
1. **`ingestion-pipeline.ts:231`** — On commit/document ingestion completion, dispatches `new_commit` or `new_document` events
2. **`generate.ts:1125`** — After L3 node generation, dispatches `new_l3_node` events
3. **`generate.ts:339`** — After cross-project link detection, dispatches `cross_link_detected` events

**All calls use `void` fire-and-forget pattern** — the async dispatcher is not awaited, which is correct for non-blocking notifications.

**REST API for integration management:** The `integrations.ts` router exposes 5 endpoints:
- `GET /projects/:id/integrations` — List all integrations for a project
- `POST /projects/:id/integrations` — Create a new Slack/Teams integration
- `PATCH /integrations/:integrationId` — Update webhook URL, enabled state, notification types
- `DELETE /integrations/:integrationId` — Remove an integration
- `POST /integrations/:integrationId/test` — Send a test notification

**Schema:** The `project_integrations` table has 7 columns: `id`, `projectId`, `integrationType` (pgEnum: `slack`/`teams`), `webhookUrl`, `enabled`, `notificationTypes` (JSONB string array), `createdAt`, `updatedAt`. All 3 schema sources (Drizzle ORM, migration SQL, snapshot) are in sync.

**OpenAPI spec:** All 5 endpoints are documented under the `integrations` tag with schemas: `ProjectIntegration`, `ProjectIntegrationInput`, `ProjectIntegrationUpdate`. The `notificationTypes` field supports filtering which events trigger webhooks.

**Frontend:** The `integrations.tsx` page (456 lines) provides a full integration management UI with project selector, add form (type + webhook URL + enabled toggle), integration list with enable/disable toggle, test button, and delete with confirmation dialog.

**Findings:**
1. ⚠️ **`new_document` event type missing from Slack/Teams payload builders:** The ingestion pipeline dispatches `new_document` events (line 234 of `ingestion-pipeline.ts`), but neither `buildSlackPayload()` nor `buildTeamsPayload()` has an emoji/title mapping for `new_document`. The fallback (`:bell:` + raw event type string) will be used, which works but produces a poor user experience in Slack/Teams.
2. ⚠️ **No notification event types for PR events:** The github_webhooks.ts dispatches in-app notifications for `new_pr_opened` and `pr_merged` events (to subscribers), but does NOT call `notifyExternalIntegrations()` for these events. Users who configure a Slack webhook will not receive PR-related notifications externally.
3. ⚠️ **No test coverage:** Zero test files reference Slack, Teams, or integration dispatch logic.
4. ⚠️ **Webhook URL stored in plaintext:** The `webhook_url` column stores the full URL including the secret token (e.g., `https://hooks.slack.com/services/T00/B00/secret`). There is no encryption at rest. This is a security concern for production deployments.
5. ✅ **Notification type filtering works correctly:** The `notificationTypes` JSONB column allows per-integration event type filtering, and the dispatcher correctly checks `allowedTypes.includes(eventType)` before dispatching.

## Round 2 — Code Quality & Security Review

**Input validation:** The `integrations.ts` routes validate `projectId` and `integrationId` with `isNaN()` checks (400 for invalid). The create endpoint validates the project exists (404 if missing). The `IntegrationInputSchema` validates `webhookUrl` with `z.string().url()`, though this does not enforce HTTPS.

**Error handling:** Both `postSlackMessage()` and `postTeamsMessage()` catch fetch errors and non-OK responses, logging warnings and returning `false`. The `notifyExternalIntegrations()` outer try/catch prevents notification failures from crashing the calling pipeline. However, there is no retry mechanism — a transient fetch failure silently drops the notification.

**Webhook URL validation gap:** The `z.string().url()` validator accepts `http://` URLs. Slack and Teams webhooks should always use `https://`. The frontend `validateUrl()` helper in `integrations.tsx` does check for `https://` prefix (line 252), but the backend API does not enforce this — a direct API call with `http://` would be accepted.

**Serialization:** The `serializeIntegration()` function (lines 24–30) correctly converts timestamps to ISO strings. The `notificationTypes` JSONB field is passed through directly.

**Security considerations:**
- No authentication on any integration endpoints (consistent with the rest of the API)
- The test endpoint (`POST /integrations/:integrationId/test`) triggers an actual webhook call without auth — an attacker could use this to flood a Slack channel
- Webhook URLs with secret tokens are logged in error paths (line 65: `webhookUrl` is included in the log metadata at warn level)

## Round 3 — Integration & Completeness Review

**End-to-end flow:** The full chain works: Configure integration via REST API/Frontend → Ingestion or generation triggers `notifyExternalIntegrations()` → Dispatcher queries DB for enabled integrations → Sends formatted payload to Slack webhook URL → Slack renders Block Kit message.

**Route mounting:** The integrations router is correctly imported at `routes/index.ts:20` and mounted at line 45 via `router.use(integrationsRouter)`.

**Generated hooks:** The Orval codegen produces `useListProjectIntegrations`, `useCreateProjectIntegration`, `useUpdateProjectIntegration`, `useDeleteProjectIntegration`, and `useTestProjectIntegration` hooks, all of which are used correctly in the frontend page.

**Schema ↔ code alignment:** The `integrationType` pgEnum (`slack`, `teams`) matches the switch in `notifyExternalIntegrations()` and the `z.enum()` validation in the route. No drift.

**Notification types enum alignment:** The OpenAPI spec declares notification type enum: `[new_commit, new_l3_node, cross_link_detected]` (line 2641). The ingestion pipeline also emits `new_document`, which is NOT in the OpenAPI enum — a schema inconsistency.

**Frontend ↔ backend alignment:** The frontend help text mentions "new commits ingested, new L3 decision nodes, and cross-project links detected" (line 299), matching the 3 event types with emoji mappings. The `new_document` type is not mentioned in the UI.

## Gaps & Recommendations

1. **Add `new_document` mapping:** Add `new_document` to `emojiMap`, `titleMap`, `colorMap`, and `titleMap` in both `buildSlackPayload()` and `buildTeamsPayload()` for consistent UX. Update the OpenAPI enum and frontend help text accordingly.
2. **Add PR event external notifications:** Call `notifyExternalIntegrations()` from `github_webhooks.ts` for `new_pr_opened` and `pr_merged` events, and add corresponding emoji/title/color mappings.
3. **Enforce HTTPS on backend:** Add `.refine(url => url.startsWith("https://"))` to the `webhookUrl` field in `IntegrationInputSchema` to prevent plaintext webhook token exposure over HTTP.
4. **Add webhook URL redaction in logs:** Remove `webhookUrl` from the log metadata at line 65 (and equivalent Teams line 127) to prevent secret token leakage in log aggregation systems.
5. **Add testing:** Unit test the payload builders for all event types. Integration test the full dispatch chain with a mock webhook server (e.g., MSW or a local echo endpoint).
6. **Consider retry with backoff:** Add at least one retry with exponential backoff for transient webhook delivery failures.
