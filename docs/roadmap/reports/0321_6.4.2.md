## Round 1 — Architecture & Design Review

**Teams payload builder:** `buildTeamsPayload()` (lines 75–111 of `slack-teams-client.ts`) produces Microsoft Teams MessageCard payloads with:

- Color mapping for 3 event types: `new_commit` (blue `#0078D7`), `new_l3_node` (green `#107C10`), `cross_link_detected` (orange `#D83B01`) — lines 80–84
- Title mapping for the same 3 event types — lines 85–89
- Optional facts for `l3Count`, `commitCount`, and `similarity` — lines 91–95
- Fallback to purple `#6264A7` and raw event type string for unknown event types
- Correct MessageCard structure: `@type: "MessageCard"`, `@context: "https://schema.org/extensions"`, `themeColor`, `summary`, `sections` with `activityTitle`, `activitySubtitle`, `facts`, and `markdown: true`

**Teams HTTP dispatcher:** `postTeamsMessage()` (lines 113–135) sends the payload via `fetch()` with:

- `POST` method, `Content-Type: application/json` header
- Non-OK response handling with `logger.warn()` including status and URL (line 127)
- Try/catch around the fetch call with error logging (line 132)
- Returns `true` on success, `false` on failure

**Central routing:** The `notifyExternalIntegrations()` function (lines 137–162) routes to `postTeamsMessage()` when `integration.integrationType === "teams"` (line 155). The routing is a simple if/else chain that checks `"slack"` first, then `"teams"`.

**Invocation call sites (same 3 as Slack):**

1. **`ingestion-pipeline.ts:231`** — On commit/document ingestion, dispatches `new_commit` or `new_document` events
2. **`generate.ts:1125`** — After L3 node generation, dispatches `new_l3_node` events
3. **`generate.ts:339`** — After cross-project link detection, dispatches `cross_link_detected` events

All calls use `void` fire-and-forget pattern — correct for non-blocking notifications.

**Test notification:** `sendTestNotification()` (lines 164–173) correctly routes to `postTeamsMessage()` for non-slack integration types (line 172), using a test payload of `{ l3Count: 3, commitCount: 5 }`.

**Findings:**

1. ⚠️ **`new_document` event type missing from Teams payload builder:** The ingestion pipeline dispatches `new_document` events, but `buildTeamsPayload()` has no color/title mapping for it. The fallback (purple `#6264A7` + raw `new_document` string) will be used, producing a poor UX in Teams channels.
2. ⚠️ **No notification event types for PR events:** The `github_webhooks.ts` dispatches in-app notifications for `new_pr_opened` and `pr_merged` but does NOT call `notifyExternalIntegrations()`. Teams webhook users will not receive PR-related notifications.
3. ⚠️ **No test coverage:** Zero test files reference Teams or integration dispatch logic.
4. ⚠️ **Webhook URL stored in plaintext:** The `webhook_url` column stores the full URL including the secret token (e.g., `https://outlook.office.com/webhook/.../IncomingWebhook/.../...`). No encryption at rest.
5. ✅ **Teams MessageCard format is correct:** The payload structure follows the Microsoft Teams Incoming Webhook MessageCard schema with proper `@type`, `@context`, `themeColor`, and `sections` fields.
6. ✅ **Color coding is distinct from Slack emoji:** The Teams implementation uses a different, platform-appropriate format (color-coded MessageCards vs. Block Kit), showing proper platform adaptation rather than a copy-paste of the Slack payload.

## Round 2 — Code Quality & Security Review

**Input validation:** The `integrations.ts` routes validate `projectId` and `integrationId` with `isNaN()` checks (400 for invalid). The create endpoint validates the project exists (404 if missing). The `IntegrationInputSchema` validates `webhookUrl` with `z.string().url()`, though this does not enforce HTTPS.

**Error handling:** `postTeamsMessage()` catches fetch errors and non-OK responses, logging warnings and returning `false`. The `notifyExternalIntegrations()` outer try/catch prevents notification failures from crashing the calling pipeline. However, there is no retry mechanism — a transient fetch failure silently drops the notification.

**Webhook URL validation gap:** The `z.string().url()` validator accepts `http://` URLs. Teams webhooks should always use `https://`. The frontend `validateUrl()` helper in `integrations.tsx` does check for `https://` prefix, but the backend API does not enforce this.

**Security considerations:**

- No authentication on any integration endpoints (consistent with the rest of the API)
- The test endpoint (`POST /integrations/:integrationId/test`) triggers an actual webhook call without auth
- Webhook URLs with secret tokens are logged in error paths (line 127: `webhookUrl` is included in the log metadata at warn level)

**Code parity with Slack:** The Teams dispatcher (`postTeamsMessage`) is structurally identical to `postSlackMessage` — same error handling pattern, same return type, same logging approach. This consistency is good for maintainability.

## Round 3 — Integration & Completeness Review

**End-to-end flow:** The full chain works: Configure Teams integration via REST API/Frontend → Ingestion or generation triggers `notifyExternalIntegrations()` → Dispatcher queries DB for enabled integrations with `integrationType === "teams"` → Sends MessageCard payload to Teams webhook URL → Teams renders the adaptive card.

**Route mounting:** The integrations router is correctly imported at `routes/index.ts:20` and mounted at line 45 via `router.use(integrationsRouter)`.

**Schema ↔ code alignment:** The `integrationType` pgEnum (`slack`, `teams`) matches the if/else in `notifyExternalIntegrations()` and the `z.enum()` validation in the route. No drift.

**OpenAPI spec coverage:** The `ProjectIntegration` schema (line 2859) declares `integrationType` enum `[slack, teams]`. The `ProjectIntegrationInput` schema (line 2886) matches. The test endpoint (`POST /integrations/:integrationId/test`) is documented at line 1566.

**Frontend ↔ backend alignment:** The frontend integration form allows selecting "teams" as the integration type (via the `z.enum(["slack", "teams"])` schema). The test button calls `useTestProjectIntegration` which hits the test endpoint, which correctly routes to `postTeamsMessage()` for Teams integrations.

**Notification types enum alignment:** The OpenAPI spec declares notification type enum: `[new_commit, new_l3_node, cross_link_detected]`. The ingestion pipeline also emits `new_document`, which is NOT in the OpenAPI enum — a schema inconsistency (same issue as Slack).

**Comparison with 6.4.1 (Slack):** The Teams dispatcher is a peer implementation to the Slack dispatcher, living in the same file. All findings from the Slack verification (6.4.1) apply equally to Teams, with the additional note that the Teams MessageCard format is correctly implemented with platform-appropriate structure.

## Gaps & Recommendations

1. **Add `new_document` mapping:** Add `new_document` to `colorMap` and `titleMap` in `buildTeamsPayload()` for consistent UX. Suggested: color `#7B68EE` (medium slate blue), title "New Documents Ingested". Update the OpenAPI enum and frontend help text accordingly.
2. **Add PR event external notifications:** Call `notifyExternalIntegrations()` from `github_webhooks.ts` for `new_pr_opened` and `pr_merged` events, and add corresponding color/title mappings in `buildTeamsPayload()`.
3. **Enforce HTTPS on backend:** Add `.refine(url => url.startsWith("https://"))` to the `webhookUrl` field in `IntegrationInputSchema` to prevent plaintext webhook token exposure over HTTP.
4. **Add webhook URL redaction in logs:** Remove `webhookUrl` from the log metadata at line 127 to prevent secret token leakage in log aggregation systems.
5. **Add testing:** Unit test `buildTeamsPayload()` for all event types. Integration test the full Teams dispatch chain with a mock webhook server (MSW or local echo endpoint).
6. **Consider retry with backoff:** Add at least one retry with exponential backoff for transient webhook delivery failures.
