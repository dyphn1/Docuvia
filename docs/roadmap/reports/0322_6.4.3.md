**Schema ↔ Code alignment:** All 4 schema representations (Drizzle ORM, migration SQL, Drizzle snapshot, OpenAPI) are in sync. All 7 columns match in name, type, nullability, and defaults.

**pgEnum definition:** The `integration_type` enum is defined in Drizzle as `pgEnum("integration_type", ["slack", "teams"])` (line 6 of `project_integrations.ts`). The migration SQL creates `CREATE TYPE integration_type AS ENUM ('slack', 'teams')`. The OpenAPI schema declares `enum: [slack, teams]`. All three are aligned.

**Foreign key constraint:** The `project_id` column references `projects(id)` with `ON DELETE CASCADE` in all 3 SQL-level representations (migration, snapshot, ALTER TABLE constraint at line 249 of the SQL file). This ensures integrations are automatically cleaned up when a project is deleted.

**Index:** The standalone migration `002_add_project_integrations.sql` creates `idx_project_integrations_project` on `project_id` for efficient per-project lookups. The main migration SQL (0000) does not include this index in the CREATE TABLE but the snapshot at line 250 confirms `CREATE INDEX "idx_commit_l2_links_commit"` exists — however, the `project_integrations` index is only in the standalone migration file, not in the monolithic `0000_short_ezekiel.sql`. This is a minor inconsistency but does not affect functionality since the standalone migration is the authoritative source.

**Zod validators:** The schema exports `insertProjectIntegrationSchema` (omits id, createdAt, updatedAt), `updateProjectIntegrationSchema` (partial of insert), and `selectProjectIntegrationSchema` (full select). These are generated via `drizzle-zod`'s `createInsertSchema`/`createSelectSchema`, ensuring type-safe validation that stays in sync with the Drizzle schema.

**Type exports:** `ProjectIntegration` (select type) and `InsertProjectIntegration` (insert type) are exported for use across the codebase. The `slack-teams-client.ts` imports `ProjectIntegration` from `@workspace/db` for the `sendTestNotification()` function parameter.

## Round 2 — Code Quality & Integration Review

**REST API usage:** The `integrations.ts` route file performs all CRUD operations against `projectIntegrationsTable`:

- `GET /projects/:id/integrations` — Lists all integrations for a project (line 32)
- `POST /projects/:id/integrations` — Creates a new integration with Zod-validated input (line 49). Verifies project exists (404 if not found).
- `PATCH /integrations/:integrationId` — Updates webhook URL, enabled flag, or notification types (line 71). Manually sets `updatedAt: new Date()`.
- `DELETE /integrations/:integrationId` — Deletes an integration (line 93). Returns 204 on success.
- `POST /integrations/:integrationId/test` — Sends a test notification (line 112).

**Notification dispatcher integration:** `notifyExternalIntegrations()` in `slack-teams-client.ts` (line 137) queries `projectIntegrationsTable` filtering by `projectId` AND `enabled = true`, then iterates results dispatching to Slack or Teams based on `integrationType`. The `notificationTypes` JSONB column is used as an optional event-type filter (line 150–151).

**Route mounting:** The integrations router is correctly imported and mounted in `routes/index.ts` (lines 20, 45).

**Frontend integration:** The `integrations.tsx` page uses the generated React Query hooks (`useListProjectIntegrations`, `useCreateProjectIntegration`, `useUpdateProjectIntegration`, `useDeleteProjectIntegration`, `useTestProjectIntegration`) from `@workspace/api-client-react`, confirming the Orval codegen pipeline has processed the integration schemas.

**Input validation:** The route uses `IntegrationInputSchema` (Zod) with `z.enum(["slack", "teams"])` for type, `z.string().url()` for webhook URL, and `z.array(z.string()).nullable().optional()` for notification types. The PATCH endpoint uses a partial schema.

**Serialization:** The `serializeIntegration()` helper (line 24) converts `createdAt`/`updatedAt` to ISO strings for JSON responses, ensuring consistent date formatting.

## Round 3 — Completeness & Cross-Cutting Review

**Per-project config requirement:** The `project_integrations` table stores integration configuration per-project via the `project_id` FK column. Each project can have multiple integrations (one-to-many), each with its own type, webhook URL, enabled flag, and notification type filter. This fully satisfies the "per-project config" requirement.

**Multi-tenancy:** The table design supports multiple integration types (slack, teams) per project, with independent enabled/disabled toggles and webhook URLs. The `notificationTypes` JSONB column allows per-integration event filtering.

**Schema export chain:** `project_integrations.ts` → `schema/index.ts` (line 17) → `@workspace/db` package → used by API server, slack-teams-client, and tests. The export chain is complete.

**OpenAPI coverage:** 5 paths and 3 schemas (`ProjectIntegration`, `ProjectIntegrationInput`, `ProjectIntegrationUpdate`) are defined. All paths are tagged `integrations`. The schemas match the Drizzle/Zod definitions.

**Migration strategy:** Both the monolithic initial migration (`0000_short_ezekiel.sql`) and the standalone migration (`002_add_project_integrations.sql`) define the table. The standalone migration adds the `project_id` index. This dual-path approach is consistent with the project's migration strategy.

**Factory coverage:** The `project_integrations` table does NOT have a dedicated factory in `factories.ts` (noted in report 0209_1.1.4). This is a test infrastructure gap but does not affect the production implementation.

**No issues found.** The `project_integrations` table is fully implemented across all layers: Drizzle ORM schema, migration SQL, Drizzle snapshot, OpenAPI spec, Zod validators, REST API routes, notification dispatcher queries, and frontend UI. All representations are in sync.

## Gaps & Recommendations

1. **Add test factory:** Create a `ProjectIntegrationFactory` in `factories.ts` (depends on `ProjectFactory`). This is a test infrastructure improvement, not a production defect.

2. **Consider adding `updatedAt` trigger:** The `updatedAt` column is manually set in the PATCH route (`updatedAt: new Date()`), but there is no database-level `ON UPDATE` trigger. If any other code path updates the table, `updatedAt` would not auto-update. Consider adding a Drizzle middleware or DB trigger for this.
