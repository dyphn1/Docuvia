## Round 1: Implementation Analysis

### JSON Export Endpoint — `GET /api/projects/:id/export`

The export route at `artifacts/api-server/src/routes/export.ts:34-120` implements a comprehensive JSON export:

1. **Route registration**: `router.get("/projects/:id/export", checkProjectOwnership, async (req, res) => {...})` — mounted via `routes/index.ts` and `app.ts` at `/api`, making the full path `/api/projects/:id/export`. ✅

2. **Authorization middleware**: `checkProjectOwnership` (lines 15-32) verifies the project exists and the authenticated user owns it, returning 404/403 as appropriate. The userId is extracted from `(req as any).user?.id || 1` — the fallback to `1` is a placeholder pending auth middleware. ✅ (with caveat)

3. **Data aggregation**: The handler fetches:
   - Project record from `projectsTable` ✅
   - L2 node count and IDs from `l2NodesTable` ✅
   - L3 node count (iterating per L2 node) from `l3NodesTable` ✅
   - Commit count from `commitsTable` ✅
   - Full L2 nodes with L1 tag links and L3 counts ✅
   - Full L3 nodes via SQL `IN` clause ✅
   - All commits ordered by `createdAt desc` ✅
   - All L1 tags ordered by `usageCount desc` ✅

4. **Response shape**: Returns a well-structured JSON object:

   ```json
   {
     "project": { ...project, l2Count, l3Count, commitCount, createdAt, updatedAt },
     "l1Tags": [ ... ],
     "l2Nodes": [ ...nodes with l3Count and l1TagIds ],
     "l3Nodes": [ ...nodes with ISO dates ],
     "commits": [ ...commits with ISO dates ],
     "exportedAt": "2026-06-22T..."
   }
   ```

   This matches the `ProjectExport` schema in the OpenAPI spec (lines 1787-1811). ✅

5. **Date serialization**: All `createdAt`/`updatedAt` fields are converted to ISO strings via `.toISOString()`, which is correct for JSON serialization of Date objects. ✅

### Markdown Export Endpoint — `GET /api/projects/:id/export/md`

The file also implements a streaming Markdown export (lines 124-179) as a bonus — this covers item 6.5.2 as well, but we focus on 6.5.1 here.

### Caveats Noted

- **N+1 query pattern for L3 count** (lines 48-54): The L3 count is computed by iterating over each L2 node and issuing a separate `count(*)` query. For projects with many L2 nodes, this is O(n) round-trips. A single `GROUP BY` query would be more efficient. This is a performance concern, not a correctness bug.
- **Placeholder auth**: The `checkProjectOwnership` middleware uses `userId = 1` as a fallback. In production, this should enforce real authentication. However, the ownership check logic itself is correctly implemented.

## Round 3: Edge Cases & Production Readiness

### Edge Case Analysis

| Edge Case                        | Handling                                                                                                | Status |
| -------------------------------- | ------------------------------------------------------------------------------------------------------- | ------ |
| Non-existent project             | `checkProjectOwnership` returns 404 before handler runs                                                 | ✅     |
| Unauthorized access              | `checkProjectOwnership` returns 403 if `ownerId !== userId`                                             | ✅     |
| Project with no L2 nodes         | `l2Ids.length` check at line 80 returns empty `l3Nodes` array                                           | ✅     |
| Project with no commits          | Returns empty `commits` array                                                                           | ✅     |
| Large project (many L2/L3 nodes) | No pagination on commit fetch (line 92-96) — could be slow for very large projects                      | ⚠️     |
| Concurrent export requests       | No rate limiting or mutex — but exports are read-only, so this is acceptable                            | ✅     |
| Invalid project ID               | `Number(req.params.id)` returns `NaN` for non-numeric input; the DB query would return no results → 404 | ✅     |

### Performance Observations

1. **N+1 L3 count** (lines 48-54): For a project with 100 L2 nodes, this issues 100 separate `count(*)` queries. Should be replaced with a single `GROUP BY l2NodeId` query.
2. **No pagination on commits** (line 92-96): For repositories with thousands of commits, this fetches all rows. Consider adding `limit`/`offset` parameters.
3. **No streaming for JSON export**: The entire response is buffered in memory before `res.json()`. For very large projects, this could cause memory pressure. The Markdown export correctly uses streaming (`res.write` + `res.end()`).

### Security Observations

1. **IDOR prevention**: The `checkProjectOwnership` middleware correctly prevents users from exporting other users' projects. ✅
2. **No auth middleware in practice**: The `userId` fallback to `1` means if no auth middleware sets `req.user`, all requests are treated as user 1. This is a known gap but not specific to export.
3. **No input validation on `id`**: `Number("abc")` → `NaN`, which results in no DB match → 404. Acceptable behavior but could return 400 for clarity.
