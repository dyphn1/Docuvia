## Round 2 — Code Quality & Security Review

**Security:**
- No authentication on the integrations API routes — any caller can create/read/update/delete integrations for any project. This is consistent with the broader API (most routes lack auth), but for a management UI that controls webhook destinations, this is a security gap.
- Webhook URL is validated as a URL and must start with `https://` (frontend validation at line 252) — good, prevents plaintext webhook dispatch.
- No rate limiting on the test endpoint — an attacker could spam webhook test requests to arbitrary URLs.

**Code quality:**
- Frontend code is clean, well-structured, with proper TypeScript types from generated hooks.
- Backend uses Zod validation on both create and update — good.
- `serializeIntegration()` helper avoids repetition — good.
- Error handling with try/catch and structured logging via `logger.error()` — good.
- `notificationTypes` field is accepted by the API but the frontend provides no UI to configure it. Users cannot filter which event types trigger notifications. This is a functional gap — the field exists in schema, API, and spec but is not exposed in the management UI.

**Test coverage:**
- Zero test coverage for integration routes (no integration test file found).
- Zero test coverage for the integrations frontend page.
- The `sendTestNotification()` function exists in `slack-teams-client.ts` and is wired to the frontend, but has no unit tests.

**Code style:** Consistent with codebase patterns. Frontend uses generated hooks correctly. Backend follows the same error handling and logging patterns as other routes.

## Gaps & Recommendations

1. **No authentication on integration management routes** — Any caller can manage integrations for any project. Recommend adding at minimum a shared secret or bearer token check, consistent with the approach used for MCP routes (6.2.3).

2. **`notificationTypes` not exposed in frontend** — The schema and API support per-integration event type filtering, but the frontend has no UI for it. Users cannot choose to receive only `new_commit` notifications but not `new_l3_node`, for example. Recommend adding a multi-select or checkbox group in the add/edit form.

3. **Zero test coverage** — No integration tests for the 5 API endpoints, no unit tests for `sendTestNotification()`, no frontend component tests. Recommend adding at minimum: (a) integration tests for CRUD operations with `withRollback()`, (b) unit tests for `sendTestNotification()` with mocked fetch.

4. **PR events not forwarded to external integrations** — `github_webhooks.ts` dispatches in-app notifications for PR events but never calls `notifyExternalIntegrations()`. Users with Slack/Teams webhooks won't receive PR notifications. This is tracked under 6.4.1/6.4.2 but affects the completeness of this integration management feature.

5. **No rate limiting on test endpoint** — `POST /integrations/{id}/test` sends HTTP requests to arbitrary URLs with no rate limiting. Recommend adding rate limiting middleware.
