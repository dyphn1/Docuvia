## Round 1 — Architecture & Design Review

**Command Registration (`extension.ts` lines 371–400):**
- `docuvia.openSearch` (line 371): Registers command, shows `showInputBox` with prompt "Search cross-project knowledge", placeholder "e.g. how do other projects handle auth". On empty/whitespace-only input, returns early (line 376). Calls `executeSearch(context, centralClient, query.trim())`.
- `docuvia.searchFromSelection` (line 382): Checks for active editor and non-empty selection (line 384). Shows warning if no selection. Caps query at 2000 chars (BUG N-2 fix, line 389–397) with user-facing warning. Calls `executeSearch()`.

**`executeSearch()` function (lines 403–429):**
- Reads `docuvia.search.defaultView` config (default: `"chat"`)
- If `"chat"`: executes `workbench.action.chat.open` with `@docuvia /query ${query}` — this routes through the Copilot Chat participant
- If `"webview"` (any value other than `"chat"`): calls `centralClient.query(query, 20)` and opens `SearchResultsPanel`
- Error handling: catches `CentralServerAuthError` with specific message, generic errors with "Search failed" message

**Package.json declarations:**
- Commands declared at lines 105–112 with correct titles and icons
- `openSearch` appears in `view/title` menu (line 171) with `when: view == docuvia.knowledgeGraph` and `group: navigation` — correct
- `searchFromSelection` appears in `editor/context` menu (line 205) with `when: editorHasSelection` and `group: "docuvia"` — correct
- `searchFromSelection` does NOT have a keybinding — it's context-menu only, which is appropriate

**Configuration:**
- `docuvia.search.defaultView` (package.json lines 215–224): enum `["chat", "webview"]`, default `"chat"`. Labels: "Copilot Chat" / "Dedicated Webview Tab". Correct.

**SearchResultsPanel:**
- Full webview panel implementation with CSP, nonce, XSS-safe HTML escaping
- Results grouped by projectName with keyword highlighting
- Click-to-open-result sends message back to extension which opens chat with `@docuvia /query <title>`
- Keyboard accessible (Enter/Space on cards)
- Empty state message when no results

**Architecture verdict:** The two commands are well-designed with clean separation. The `executeSearch` function is a proper shared entry point. The dual-mode (chat/webview) design is sound.

## Round 2 — Code Quality & Security Review

**Route mismatch (CRITICAL):**
- `CentralServerClient.query()` sends `POST ${serverUrl}/query` (CentralServerClient.ts line 72)
- Server route is `POST /api/extensions/vscode/query` (extensions_vscode.ts line 28, mounted under `/api` prefix in app.ts line 40)
- The client URL `/query` does NOT match the server endpoint `/api/extensions/vscode/query`
- This means the webview mode (`defaultView != "chat"`) will **always fail** with a 404 or connection error
- The chat mode (`defaultView == "chat"`) works because it doesn't make a direct HTTP call — it delegates to the Copilot Chat participant which has its own routing

**XSS protection:**
- `SearchResultsPanel._buildHtml()` uses `escapeHtml()` for all user-controlled content (title, snippet, projectName, tags) — correct
- Uses CSP with nonce for style and script — correct
- `highlightKeywords()` operates on already-escaped HTML — correct
- `JSON.stringify(r.title)` for onclick handler — correct, prevents injection

**Input validation:**
- `openSearch`: empty/whitespace-only check (line 376) — correct
- `searchFromSelection`: empty selection check (line 384), length cap at 2000 chars (line 389–397) — correct
- Backend `VscodeQuerySchema`: `z.string().min(1)` — correct, rejects empty strings

**Error handling:**
- `executeSearch` try/catch with specific `CentralServerAuthError` handling — correct
- `SearchResultsPanel` doesn't handle the case where `centralClient.query()` returns `[]` with no server configured — the panel shows "No cross-project results found" with no guidance about configuring a server (known issue from user-journeys.md BUG N-1)

**Code quality:**
- Clean, readable code with proper TypeScript types
- `SearchResultsPanel` uses singleton pattern (`_current`) correctly — reuses existing panel
- `SearchResultsPanel._handleMessage()` only handles `openResult` type — correct
- No test coverage found for `executeSearch`, `SearchResultsPanel`, or the two commands

1. User runs `docuvia.openSearch` or `searchFromSelection` → `executeSearch()` → ✅

**Response shape mismatch:**

- The `SearchResultsPanel` renders `CentralSearchResult[]` — the data shape from the server won't match

## Gaps & Recommendations

1. **CRITICAL: Route mismatch in `CentralServerClient.query()`** — The client sends `POST ${serverUrl}/query` but the server endpoint is `POST /api/extensions/vscode/query`. The webview search mode is completely broken. Recommend either: (a) change the client to send to `${serverUrl}/api/extensions/vscode/query`, or (b) add a dedicated `/query` shortcut route on the server that delegates to the same handler.

2. **Response shape mismatch** — Even after fixing the route, `vscodeQuery()` → `routeQuery()` returns results in the intent-router format, not `CentralSearchResult[]`. The `SearchResultsPanel` expects `{ title, projectName, l1Tags, snippet, score }` but will receive L1/L2/L3 node objects. Recommend creating a proper DTO mapping in `vscodeQuery()` or changing the client to use the existing `/api/search` route which already returns `{ results: [...] }`.

3. **No server-not-configured UX in webview mode** — When `server_url` is not configured, `centralClient.query()` returns `[]` immediately. The panel shows "No cross-project results found" with no indication that the server isn't configured. Recommend adding a check in `executeSearch()` that calls `centralClient.isServerConfigured()` before making the API call, and shows an informative message with setup instructions.

4. **Zero test coverage** — No unit or integration tests for either command, `executeSearch()`, or `SearchResultsPanel`. Recommend adding: (a) unit tests for `executeSearch()` with mocked centralClient and config, (b) unit tests for the 2000-char truncation logic, (c) snapshot tests for `SearchResultsPanel._buildHtml()`.

5. **User journey doc stale reference** — `user-journeys.md` line 492 references `defaultView = "panel"` but the actual config value is `"webview"`. Recommend updating the doc to match the implementation.
