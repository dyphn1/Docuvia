## Round 1 — Architecture & Design Review

### Design Intent

Per `10-quality-requirements.md` and `03-context-and-scope.md`, the API key used by the VS Code extension to authenticate with the Docuvia server must be stored using VS Code's `SecretStorage` API, which delegates to the OS keychain (macOS Keychain, Windows Credential Manager, Linux Secret Service). The key requirement is: **credentials must never be stored in plaintext** — not in workspace settings, global settings, `.docuvia/` config files, or any other file on disk.

### Implementation Analysis

**`CredentialManager` class** (`CredentialManager.ts`):

```typescript
const SECRET_KEY = "docuvia.serverToken";

export class CredentialManager {
  constructor(private readonly _secrets: vscode.SecretStorage) {}

  async getToken(): Promise<string | undefined> {
    return this._secrets.get(SECRET_KEY);
  }

  async setToken(token: string): Promise<void> {
    await this._secrets.store(SECRET_KEY, token);
  }

  async clearToken(): Promise<void> {
    await this._secrets.delete(SECRET_KEY);
  }
}
```

- Uses `vscode.SecretStorage` exclusively — ✅ No plaintext storage paths
- Single secret key `"docuvia.serverToken"` — ✅ Well-defined key namespace
- Three operations: `get`, `store`, `delete` — ✅ Complete lifecycle
- Injected via constructor from `context.secrets` in `extension.ts:44` — ✅ Proper VS Code extension lifecycle integration

**Token input flow** (`extension.ts:349-361`):

```typescript
vscode.commands.registerCommand("docuvia.setServerToken", async () => {
  const token = await vscode.window.showInputBox({
    prompt: "Enter your Docuvia server API token",
    password: true,              // ✅ Masked input
    placeHolder: "docuvia_token_...",
    validateInput: (v) => (v.trim().length === 0 ? "Token cannot be empty" : null),
  });
  if (token && token.trim().length > 0) {
    await credentialManager.setToken(token.trim());
  }
});
```

- `password: true` — ✅ Token is masked during input
- Empty string validation — ✅ Prevents storing empty tokens
- Trim before store — ✅ Prevents whitespace-related auth failures

**Token transport** (`CentralServerClient.ts`):

All five server-facing methods (`query`, `sync`, `pullSnapshot`, `_tickMetabolism`, `sendFeedback`) follow the same pattern:

```typescript
const token = await this._creds.getToken();
const headers: Record<string, string> = { "Content-Type": "application/json" };
if (token) {
  headers["x-docuvia-token"] = token;
}
```

- Token sent as custom `x-docuvia-token` header — ✅ Not in URL/query string
- Conditional header inclusion — ✅ Graceful when no token configured
- Consistent across all server-facing methods — ✅ No method遗漏

### Architecture Assessment

The credential storage architecture is **clean and correct**. The token exists in exactly three states:
1. **In memory** — during the `showInputBox` prompt (ephemeral)
2. **In OS keychain** — via `vscode.SecretStorage` (persistent, encrypted at rest by the OS)
3. **In HTTP header** — `x-docuvia-token` on outgoing requests (transient, HTTPS transport assumed)

There are **zero plaintext storage paths**. The token is never written to:
- `~/.docuvia/config.yaml` (global config — only `server_url`, `chunking_strategy`, `telemetry`)
- `.docuvia/` workspace files
- VS Code `settings.json` (workspace or global)
- Any `.env` file
- Any log output

## Round 2 — Code Quality & Security Review

### Security Findings

1. **✅ Correct use of `vscode.SecretStorage`**: The API is the standard VS Code mechanism for secret persistence. On macOS it uses Keychain, on Windows Credential Manager, on Linux Secret Service/libsecret. The OS handles encryption at rest.

2. **✅ No plaintext fallback paths**: Searched all `.ts` files in the vscode-client for alternative token storage (`globalState`, `workspaceState`, `config.get`, `.env`, plaintext). None exist. The `CredentialManager` is the sole credential access point.

3. **✅ Token not logged**: The token value is never passed to `outputChannel.appendLine()` or any logging function. The `server_url` is logged (line 40) but not the token.

4. **✅ Token not in VS Code settings**: The `package.json` `contributes.configuration` section contains no token-related settings. Users cannot accidentally expose the token through settings sync or workspace settings files.

5. **🟡 MEDIUM — Token sent as custom header over HTTPS assumed**: The `x-docuvia-token` header is a custom authentication scheme. The `server_url` in `~/.docuvia/config.yaml` is documented as requiring `https://` (per `settings.md` line 60: "Must use `https://`"). However, there is no runtime validation that the URL uses HTTPS. If a user configures `http://` instead of `https://`, the token would be transmitted in cleartext.
   - **Mitigation**: The design doc mandates HTTPS. The risk is low since this is a developer tool connecting to a known server.
   - **Recommendation**: Consider adding a runtime check in `CentralServerClient` that warns or rejects non-HTTPS URLs when a token is configured.

6. **🟢 LOW — No token rotation mechanism**: Once set, the token persists indefinitely until manually cleared. There is no automatic rotation or expiry handling.
   - **Status**: Acceptable for v1. Token rotation can be added when RBAC is implemented (noted as TODO in `CentralServerClient.ts:89`).

7. **🟢 LOW — `checkAuthorizationScope` is a stub**: `CentralServerClient.ts:90-93` has `checkAuthorizationScope(_scope: string)` returning `true` unconditionally. This is noted as a Phase 6 TODO for OAuth2/PKCE.
   - **Status**: Not relevant to SecretStorage verification — this is a future RBAC feature.

### Code Quality Findings

8. **✅ Minimal and focused**: `CredentialManager.ts` is 19 lines with a single responsibility. No unnecessary complexity.

9. **✅ Clean dependency injection**: `CredentialManager` receives `vscode.SecretStorage` via constructor, making it testable with a mock SecretStorage implementation.

10. **✅ Consistent error handling**: `CentralServerClient` throws `CentralServerAuthError` on 401 responses, which is caught upstream to prompt the user to reconfigure their token.

### Test Coverage

No unit or integration tests exist for `CredentialManager`. The vscode-client test suite (`src/tests/`) does not cover credential management.

🟡 **Low**: No tests for `CredentialManager` — while the class is simple, tests would verify that `getToken`/`setToken`/`clearToken` correctly delegate to the `SecretStorage` mock. However, the class is a thin wrapper with no branching logic, so the risk of bugs is minimal.

## Recommendations

1. **[MEDIUM] Add HTTPS enforcement for server URL**: In `CentralServerClient`, add a check that warns the user (or rejects the connection) when `server_url` uses `http://` and a token is configured. This prevents accidental token exposure over unencrypted connections.

2. **[LOW] Add unit tests for `CredentialManager`**: Create a mock `vscode.SecretStorage` and verify `getToken`/`setToken`/`clearToken` delegation. While the class is simple, tests would prevent regression if the implementation grows.

3. **[LOW] Document token lifecycle**: Add a brief note in the user-facing docs about token expiry and rotation, so users know they need to manually re-run `docuvia.setServerToken` if the server-side token is rotated.

## Overall Verdict

✅ **PASS** — The API key is stored exclusively via VS Code's `SecretStorage` API, which delegates to the OS keychain (macOS Keychain, Windows Credential Manager, Linux Secret Service). The token is never written to disk in plaintext — not in settings files, config files, `.docuvia/` workspace files, or logs. The implementation is minimal (19 lines), focused, and correctly integrated into the extension lifecycle via `context.secrets`. The token is collected through a password-masked input box and transported as a custom `x-docuvia-token` HTTP header. There are no plaintext fallback paths. Two minor observations (no HTTPS enforcement at runtime, no unit tests) are acceptable for v1.
