## Round 1 — Architecture & Design Review

### Design Intent

Per `08-crosscutting-concepts.md` line 464, the API server must:

1. Use `CORS_ORIGIN` environment variable to control which origins are allowed
2. Never use wildcard (`*`) origins in production
3. Prevent CSRF by restricting cross-origin requests to known, trusted origins

### Implementation Analysis

**CORS middleware** (`app.ts:30`):

```typescript
import cors from "cors";
// ...
app.use(cors());
```

- `cors()` with **no configuration** — ❌ This defaults to `origin: *`, allowing ALL origins
- No `CORS_ORIGIN` environment variable is read or used anywhere in the codebase
- No conditional logic based on `NODE_ENV` (development vs production)
- No origin allowlist or regex pattern

**Environment variable audit:**

| Env Var | Used in Code | Documented in `07-deployment.md` |
|---------|-------------|----------------------------------|
| `PORT` | ✅ `index.ts:4` | ✅ Required |
| `DATABASE_URL` | ✅ | ✅ Required |
| `OPENAI_API_KEY` | ✅ | ✅ Required |
| `GITHUB_WEBHOOK_SECRET` | ✅ | ✅ Conditional |
| `NODE_ENV` | ✅ Used in `logger.ts`, `metabolism.ts` | ✅ Documented |
| `CORS_ORIGIN` | ❌ **Not used anywhere** | ❌ **Not documented** |

**Frontend dev server proxy** (`vite.config.ts:37-42`):

```typescript
proxy: {
  "/api": {
    target: apiTarget,
    changeOrigin: true,
  },
},
```

- The Vite dev server proxies `/api` to the API server with `changeOrigin: true`
- This means in **development**, the browser talks to the same origin (Vite dev server), so CORS is not relevant
- In **production**, if the frontend is served from a different origin than the API server, CORS becomes critical

### Architecture Assessment

The CORS configuration is **incomplete and contradicts the design spec**. The design explicitly states that CORS must be "strictly governed by `CORS_ORIGIN` with no wildcards in production," but the implementation uses `cors()` with no options, which is the equivalent of `cors({ origin: "*", credentials: true })` — the most permissive possible configuration.

**Key observations:**

1. **The `cors` package is installed and imported** — the dependency exists but is misconfigured
2. **No `CORS_ORIGIN` env var exists** — the design-specified configuration variable was never implemented
3. **No production-specific CORS logic** — there is no `NODE_ENV` check to apply stricter CORS in production
4. **The Vite dev proxy masks the issue in development** — since the browser sees same-origin requests, CORS is never triggered during local development

## Round 2 — Code Quality & Security Review

### Security Findings

1. **🔴 HIGH — Wildcard CORS allows all origins** (`app.ts:30`):
   - `app.use(cors())` with no configuration sets `Access-Control-Allow-Origin: *`
   - Any website can make cross-origin requests to the API, including authenticated requests with cookies/credentials
   - **Impact**: Enables CSRF attacks — a malicious website could trigger API actions (ingest, generate, review resolution) if a user has an active session
   - **Note**: The API uses token-based auth (`x-docuvia-token` header) rather than cookies, which limits the CSRF attack surface. However, the `cors()` default also enables `credentials: true`, and browsers may still send cookies if they exist.

2. **🟡 MEDIUM — `CORS_ORIGIN` env var documented in design but never implemented**:
   - The crosscutting concepts document specifies `CORS_ORIGIN` as the configuration mechanism
   - No code reads this variable; no `.env.example` or deployment documentation mentions it
   - **Impact**: Operators have no way to configure CORS without modifying source code

3. **🟡 MEDIUM — No OPTIONS preflight handler**:
   - The `cors()` middleware handles OPTIONS automatically, but there is no explicit OPTIONS route or middleware
   - This is acceptable behavior for the `cors` package, but means there's no control over preflight response headers or caching
   - **Impact**: Low — the `cors` package handles preflight correctly by default

4. **🟢 LOW — Vite dev server has `allowedHosts: true`** (`vite.config.ts:36`):
   - The dev server accepts requests from any host, which is appropriate for local development
   - This does not affect production since Vite is not used as a production server
   - **Impact**: None for production

### Code Quality Findings

5. **✅ `cors` package is a standard, well-maintained dependency**: `cors@2.8.6` is the latest v2, widely used with Express

6. **✅ Correct middleware ordering**: `cors()` is applied at `app.ts:30` before route mounting at `app.ts:40`, ensuring CORS headers are set on all responses

7. **🟡 MEDIUM — No environment-based configuration pattern**: Unlike other env vars (`PORT`, `DATABASE_URL`, `GITHUB_WEBHOOK_SECRET`), `CORS_ORIGIN` has no implementation pattern to follow. The codebase has no precedent for environment-based feature flags.

8. **🟢 LOW — Single CORS configuration point**: The CORS middleware is applied once in `app.ts`, not scattered across routes. This is good — fixing it requires changing only one line.

### Test Coverage

No tests exist for CORS configuration. The test suite does not verify:
- `Access-Control-Allow-Origin` header values
- Behavior with different `CORS_ORIGIN` values
- Preflight OPTIONS request handling
- Rejection of requests from disallowed origins

🟡 **Medium**: No CORS tests — the wildcard configuration cannot be caught without integration tests that verify response headers.

## Recommendations

1. **[HIGH] Implement `CORS_ORIGIN` configuration**: Replace `app.use(cors())` with environment-variable-driven configuration:
   ```typescript
   const corsOrigin = process.env.CORS_ORIGIN;
   app.use(cors(corsOrigin ? { origin: corsOrigin } : { origin: true }));
   ```
   - In development (no `CORS_ORIGIN` set): allow all origins via `origin: true` (reflects request origin)
   - In production (`CORS_ORIGIN=https://app.example.com`): restrict to specific origin(s)
   - Support multiple origins via comma-separated values if needed

2. **[MEDIUM] Add `CORS_ORIGIN` to deployment documentation**: Add to the env var table in `07-deployment.md` with description "Comma-separated list of allowed CORS origins (required in production)".

3. **[MEDIUM] Add CORS integration tests**: Create tests that:
   - Verify `Access-Control-Allow-Origin` header matches `CORS_ORIGIN` when set
   - Verify wildcard behavior when `CORS_ORIGIN` is not set (development mode)
   - Verify OPTIONS preflight returns correct headers

4. **[LOW] Add startup log for CORS config**: Log the CORS configuration at server startup so operators can verify it's correct:
   ```typescript
   logger.info({ corsOrigin: corsOrigin || "wildcard (development)" }, "CORS configuration");
   ```

## Overall Verdict

⚠️ **WARN** — The `cors` package is installed and correctly applied as Express middleware, but it is configured with the default wildcard (`origin: *`) setting, which directly contradicts the design specification in `08-crosscutting-concepts.md` that requires CORS to be "strictly governed by `CORS_ORIGIN` with no wildcards in production."

The `CORS_ORIGIN` environment variable specified by the design does not exist anywhere in the codebase — not in the code, not in the deployment documentation, not in any `.env` file or configuration. This means:
- In development: CORS is effectively a non-issue because the Vite dev server proxies API requests (same-origin)
- In production: The API server allows cross-origin requests from any domain, which weakens CSRF protections

**Re-verification note:** This is a re-verification of the same CORS configuration previously examined in report `0333_9.1.3.md` (2026-06-24). No code changes have been made since that report. All findings remain unchanged.

The fix is straightforward: read `CORS_ORIGIN` from the environment and pass it to the `cors()` middleware. The low severity of this finding in the current development context (single-host, developer tool) is offset by the high severity in any production deployment scenario.
