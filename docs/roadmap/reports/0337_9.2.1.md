## Round 1 — Architecture & Design Review

### Design Intent

Per `08-crosscutting-concepts.md` §8.7, the structured logging system must:

1. Use a **centralized** pino logger instance shared across all components
2. Enforce **PII and auth token redaction** in all environments (not just production)
3. Support **LOG_LEVEL** configuration via environment variable
4. Use **pino-pretty** for human-readable output in development
5. Output **structured JSON** in production for log aggregators
6. Integrate with Express via **pino-http** for automatic request/response logging

### Implementation Analysis

**Logger Core** (`logger.ts`):

```typescript
import { pino } from "pino";

const isProduction = process.env.NODE_ENV === "production";

export const logger = pino({
  level: process.env.LOG_LEVEL || "info",
  redact: {
    paths: ["req.headers.authorization", "password", "token", "authorization", "apiKey"],
    censor: "[REDACTED]",
  },
  transport:
    process.env.NODE_ENV !== "production"
      ? {
          target: "pino-pretty",
          options: { colorize: true },
        }
      : undefined,
});
```

**HTTP Middleware** (`app.ts`):

```typescript
app.use(
  pinoHttp({
    logger,
    serializers: {
      req(req) {
        return { id: req.id, method: req.method, url: req.url?.split("?")[0] };
      },
      res(res) {
        return { statusCode: res.statusCode };
      },
    },
  })
);
```

**Build Integration** (`build.mjs`):

```typescript
plugins: [
  esbuildPluginPino({ transports: ["pino-pretty"] }),
],
```

### Architecture Assessment

The structured logging system has a **solid, well-designed architecture** that meets the design requirements:

**Strengths:**
1. ✅ **Centralized logger** — Single `logger.ts` module exports one pino instance, imported by 24 source files across routes, lib, and memory modules
2. ✅ **PII redaction** — Environment-agnostic redaction pipeline strips `authorization`, `password`, `token`, `apiKey` keys with `[REDACTED]` censor. This is always active, not just in production
3. ✅ **LOG_LEVEL configuration** — `process.env.LOG_LEVEL || "info"` allows runtime log level control
4. ✅ **Environment-aware transport** — pino-pretty with colorize in non-production, raw JSON in production
5. ✅ **pino-http integration** — Custom serializers strip query strings from URLs and limit request/response logging to essential fields (id, method, url, statusCode)
6. ✅ **Build integration** — `esbuild-plugin-pino` correctly bundles the pino-pretty transport for the esbuild-based build
7. ✅ **Consistent usage pattern** — Nearly all route files import and use the logger with structured context objects (e.g., `logger.error({ err, projectId }, "message")`)
8. ✅ **Request context propagation** — pino-http automatically attaches request IDs, enabling correlation of log entries per-request

**Weaknesses:**
1. 🟡 **One route uses `console.error` instead of logger** — `l2_nodes.ts:146` uses `console.error(error)` in the bootstrap confirmation catch block, bypassing pino entirely. This means the error won't have structured context, won't be redacted, and won't respect LOG_LEVEL
2. 🟡 **LOG_LEVEL not documented in deployment docs** — The environment variables table in `07-deployment.md` does not list `LOG_LEVEL` as an optional variable
3. 🟡 **No PII redaction test** — The design doc explicitly requires a test that verifies PII is replaced with `[REDACTED]` in log output. No such test exists
4. 🟡 **No logger unit tests at all** — The logger module has no test coverage for level configuration, redaction behavior, or transport selection
5. 🟢 **Minor: `isProduction` variable unused** — The `isProduction` constant on line 3 of `logger.ts` is defined but never referenced (the transport config uses `process.env.NODE_ENV !== "production"` inline)

## Round 2 — Code Quality & Security Review

### Security Findings

1. **✅ PII redaction is correctly configured** — The `redact.paths` array covers the key sensitive fields: `req.headers.authorization`, `password`, `token`, `authorization`, `apiKey`. The redaction is environment-agnostic (always active), which is the correct approach since debug logs in any environment could contain sensitive data.

2. **✅ pino-http serializers limit data exposure** — The custom `req` serializer strips query parameters (`req.url?.split("?")[0]`) which could contain tokens or PII. The `res` serializer only logs `statusCode`, not headers or body.

3. **🟡 MEDIUM — `console.error` bypasses redaction in `l2_nodes.ts:146`** — The bootstrap confirmation error handler uses `console.error(error)` directly. If the error object contains sensitive data (e.g., database connection strings with passwords), it will be logged in plaintext without redaction. This is the only instance of `console.error` in the API server source (excluding examples and scripts).

4. **🟢 LOW — `pino-pretty` transport in build** — The `esbuild-plugin-pino` bundles `pino-pretty` as a transport. In production, the transport is `undefined` (raw JSON), but the pino-pretty dependency is still bundled. This is a minor bundle size concern, not a security issue.

### Code Quality Findings

5. **✅ Consistent structured logging pattern** — 23 of 24 API server source files use the logger with structured context objects. The pattern `logger.error({ err, projectId }, "message")` provides excellent traceability.

6. **✅ Logger is a singleton** — The logger is instantiated once in `logger.ts` and imported everywhere. No risk of multiple pino instances or conflicting configurations.

7. **✅ Build correctly handles pino worker threads** — The `esbuild-plugin-pino` plugin with `transports: ["pino-pretty"]` ensures the pino-pretty transport worker is correctly bundled. The entry points include both `index.ts` and `ast-worker.ts`, ensuring pino works in both main and worker threads.

8. **🟡 MEDIUM — Dead code: `isProduction` variable** (`logger.ts:3`):
   ```typescript
   const isProduction = process.env.NODE_ENV === "production";
   ```
   This variable is never used. The transport config inline-checks `process.env.NODE_ENV !== "production"`. This is dead code that should be removed or used.

9. **🟡 MEDIUM — `l2_nodes.ts` doesn't import logger** — The file has no `import { logger }` statement and uses `console.error` instead. This is inconsistent with every other route file.

10. **🟢 LOW — Example files use `console.log`** — `ast-demo.ts`, `ast-demo-c-cpp.ts`, `ast-demo-php.ts`, and `verify-proxy.ts` use `console.log`/`console.error` extensively. These are example/verification scripts, not production code, so this is acceptable but worth noting.

### Test Coverage

11. **🔴 No logger tests exist** — Zero test files reference `logger`, `pino`, or `redact`. The design doc's verifiability requirement explicitly states:
    > "The test suite MUST instantiate the Pino logger, simulate an error containing mock PII (e.g., email addresses, bearer tokens, or auth headers), and capture the output stream. The assertion MUST explicitly verify that the sensitive strings are replaced with `[REDACTED]` in the final log output."

    This test does not exist. The `console.error` bypass in `l2_nodes.ts` would be caught by such a test.

12. **🔴 No pino-http integration tests** — No tests verify that HTTP requests produce structured log output with the expected serializers.

### Missing Features / Gaps

1. **`console.error` bypass in `l2_nodes.ts:146`** — The bootstrap confirmation endpoint uses `console.error(error)` instead of `logger.error({ err }, msg)`. This bypasses structured logging, PII redaction, and LOG_LEVEL filtering. Fix: import the logger and replace `console.error(error)` with `logger.error({ error }, "[POST /l2_nodes/:id/confirm-bootstrap] Unhandled error")`.

2. **No PII redaction test** — The design doc's mandatory verifiability requirement is not met. A test should instantiate the logger, log an object containing `{ authorization: "Bearer secret123", password: "hunter2" }`, capture the output stream, and assert that `"secret123"` and `"hunter2"` do not appear in the output while `"[REDACTED]"` does.

3. **LOG_LEVEL not documented** — The environment variables table in `07-deployment.md` should list `LOG_LEVEL` as an optional variable with default `info` and allowed values (`trace`, `debug`, `info`, `warn`, `error`, `fatal`).

4. **Dead code: `isProduction` variable** — The unused constant in `logger.ts:3` should be removed.

5. **No logger level tests** — No tests verify that `LOG_LEVEL=warn` suppresses `logger.info()` calls, or that the default level is `info`.

## Overall Verdict

⚠️ **WARN** — The structured logging system is **well-architectured and comprehensively deployed** across the codebase. The centralized pino logger with environment-aware transport, PII redaction, and pino-http integration demonstrates strong observability design. The redaction pipeline is correctly always-on (not gated on debug mode), and the pino-http serializers appropriately limit sensitive data exposure.

However, there is one **code quality inconsistency** (`console.error` bypass in `l2_nodes.ts`), **no test coverage** for the logger (including the design doc's mandatory PII redaction verification test), and the `LOG_LEVEL` environment variable is **undocumented** in the deployment guide. The core logging infrastructure is solid, but the gaps in testing and documentation prevent a PASS rating.
