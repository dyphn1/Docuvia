## Round 1 — Architecture & Design Review

### Design Intent

Per §8.3.2 (MVC), all UI code must enforce three-layer separation:

| Layer | Responsibility | Forbidden |
|-------|---------------|-----------|
| **View** (`*.tsx` / component file) | Renders JSX from props and state only | Business logic, API calls, direct state mutations outside setter props |
| **Controller** (event handler / hook callsite) | Handles user events; orchestrates service calls; updates local state | Direct DOM manipulation, database access, rendering |
| **Model** (`*.model.ts` / query hook / KnowledgeStore) | Manages data persistence; syncs to DB/file/cache | Rendering, UI event handling |

**Flow:** User interaction → Controller → Model → View (re-render)

### Implementation Analysis

#### React Frontend (kg-engine) — Strong MVC Separation

The React frontend demonstrates **excellent** MVC separation in most pages. The architecture is clean:

**View Layer — Pure rendering components:**
- `dashboard.tsx` — Renders dashboard from `useGetDashboard` hook data. No business logic, no API calls. Pure conditional rendering (loading skeleton, error alert, stat cards). ✅
- `review.tsx` — Renders review queue from `useListReviewTasks` / `useGetReviewStats`. Delegates all mutations to `useResolveReviewTask` hook. ✅
- `query.tsx` — Renders search results from local state. ✅
- `pull-requests.tsx` — Renders PR list from `useListPullRequests`. Contains `PrDetailPanel` sub-component that uses `useGetPullRequestDetail`. ✅

**Controller Layer — Event handlers and hook callsites:**
- `pipeline.tsx` — `handleIngest` and `handleGenerate` are classic Controller: they manage local loading/error state, call `fetch()`, and invalidate queries on success. The handlers orchestrate Model (fetch) and View (state updates). ✅
- `integrations.tsx` — `handleToggle`, `handleDelete`, `handleTest` are clean Controller methods that call `useUpdateProjectIntegration`, `useDeleteProjectIntegration`, `useTestProjectIntegration` mutations. ✅
- `L2BootstrapReview.tsx` — `handleSubmit` orchestrates `useConfirmBootstrap` mutation with local state management. ✅

**Model Layer — Generated hooks + React Query cache:**
- All data fetching uses `@workspace/api-client-react` generated hooks (`useGetDashboard`, `useListReviewTasks`, `useListProjects`, etc.) — these are the Model layer. ✅
- React Query cache acts as the Model store with `invalidateQueries` for cache invalidation. ✅

#### VS Code Extension — Good MVC Separation

**View Layer:**
- `KnowledgeGraphTreeProvider` — Implements `vscode.TreeDataProvider<KGNode>`. Renders tree nodes from `KnowledgeStore` snapshots. No business logic beyond node filtering for drag-and-drop. ✅
- `DashboardPanel` — Implements a VS Code WebviewPanel. Renders dashboard HTML from `KnowledgeStore` snapshot data. Delegates all data access to `store.getSnapshotFor()`. ✅
- `SearchResultsPanel` — Implements a VS Code WebviewPanel for search results. Pure rendering from input results. ✅

**Controller Layer:**
- `extension.ts` command handlers — `docuvia.startExplore`, `docuvia.initProject`, `docuvia.autoCategorizeDecisions`, `docuvia.refreshKnowledgeGraph` are all Controllers that orchestrate between user actions and Model. ✅
- `ChatParticipant.ts` — `registerDocuviaChatParticipant` is a Controller that routes chat commands to Model operations. ✅

**Model Layer:**
- `KnowledgeStore` — Singleton that manages in-memory knowledge graph state. Handles YAML parsing, file watching, and snapshot management. No rendering or UI event handling. ✅

### Architecture Assessment

The MVC pattern is **well-implemented** across both the React frontend and VS Code extension. The React frontend has the cleanest separation: View components are purely functional (render from props/state), Controllers are event handlers that call Model hooks, and Model is the generated React Query hooks + cache.

**Strengths:**
1. ✅ **React frontend has consistent MVC** — All 8 page components follow the same pattern: View (JSX rendering) + Controller (event handlers calling hooks) + Model (generated React Query hooks).
2. ✅ **VS Code extension correctly separates TreeViews (View) from KnowledgeStore (Model)** — The `KnowledgeGraphTreeProvider` never directly reads from disk; it always goes through `KnowledgeStore`.
3. ✅ **Generated hooks enforce Model boundary** — The API-First approach (`openapi.yaml` → Orval codegen) ensures all data access goes through typed hooks, preventing ad-hoc API calls in Views.
4. ✅ **Sub-components follow MVC** — `TaskCard` in `review.tsx`, `PrDetailPanel` in `pull-requests.tsx`, `IntegrationCard` in `integrations.tsx` are pure View components that receive data via props and delegate actions via callback props.

**Weaknesses:**
1. 🟡 **`pipeline.tsx` and `query.tsx` use raw `fetch()` instead of generated hooks** — These pages bypass the Model layer by making direct `fetch()` calls in their Controller handlers. While the Controller/View separation is maintained, the Model layer is circumvented — there's no generated hook for the ingest/generate/mcp-query endpoints being called from the frontend.
2. 🟡 **`documents.tsx` uses raw `fetch()` for document loading** — The `loadDocuments` function (line 94-101) uses `fetch()` directly instead of using a generated hook, bypassing the Model layer.
3. 🟡 **`mcp.tsx` is entirely self-contained** — The MCP API explorer page defines endpoints locally and uses `fetch()` directly. While it's a utility page (not a core data page), it doesn't use the generated Model layer.
4. 🟡 **`DashboardPanel.ts` contains `buildDashboardPayload` helper** — The `DashboardPanel` View class contains a pure function `buildDashboardPayload` (lines 39-89) that transforms Model data into View data. While this is a data transformation function (not business logic), it's embedded in the View class rather than being extracted to a separate utility or Model layer function.

## Round 2 — Code Quality & Security Review

### MVC Violations Found

1. **🟡 MEDIUM — `pipeline.tsx:77,108` — Raw `fetch()` bypasses Model layer:**
   ```typescript
   // pipeline.tsx line 77
   const res = await fetch(`/api/projects/${selectedProject}/ingest/git`, {
     method: "POST",
     headers: { "Content-Type": "application/json" },
     body: JSON.stringify({ ... }),
   });
   ```
   The ingest and generate endpoints are defined in `openapi.yaml` but the frontend doesn't use the generated hooks for these operations. Instead, it constructs raw fetch requests. This bypasses the Model layer (generated hooks with Zod validation), meaning:
   - No Zod validation on request bodies from the frontend
   - No type safety on request/response shapes
   - No React Query caching for these operations
   - If the API contract changes, the frontend won't get compile-time errors

2. **🟡 MEDIUM — `query.tsx:65` — Raw `fetch()` for MCP query:**
   ```typescript
   const res = await fetch("/api/mcp/query", {
     method: "POST",
     headers: { "Content-Type": "application/json" },
     body: JSON.stringify({ query: query.trim(), projectId: ..., limit: 20 }),
   });
   ```
   The MCP query endpoint is defined in `openapi.yaml` but the frontend uses raw fetch. Same issues as above — no validation, no caching, no type safety.

3. **🟡 MEDIUM — `documents.tsx:97` — Raw `fetch()` for document loading:**
   ```typescript
   const res = await fetch(`/api/projects/${projectId}/documents`);
   ```
   Bypasses the generated `useListProjectDocuments` hook (if it exists in the generated API client).

4. **🟢 LOW — `mcp.tsx:81` — Self-contained API explorer with local endpoint definitions:**
   The MCP page defines endpoint schemas locally and uses `fetch()` directly. This is acceptable for a developer tool/explorer page, but it means changes to the API spec won't be reflected here automatically.

5. **🟢 LOW — `DashboardPanel.ts:39-89` — `buildDashboardPayload` in View class:**
   The `buildDashboardPayload` function is a pure data transformation (maps `KnowledgeGraphSnapshot` to `DashboardPayload`). While it's technically in the View class, it doesn't perform business logic or API calls — it's a view-model transformation. However, extracting it to a separate utility would improve testability and separation.

### Positive Findings

6. ✅ **Consistent hook usage across core pages** — `dashboard.tsx`, `review.tsx`, `integrations.tsx`, `pull-requests.tsx`, `subscriptions.tsx`, `l1-tags.tsx`, `templates.tsx` all use generated React Query hooks consistently. This is the strongest evidence of MVC compliance.

7. ✅ **Mutation pattern is clean** — All pages that perform write operations use `useMutation` hooks with `onSuccess` callbacks for cache invalidation. The pattern is: `const mutate = useXxxMutation()` → `mutate.mutate({ data })` → `onSuccess: () => queryClient.invalidateQueries()`. This is textbook Controller → Model → View flow.

8. ✅ **VS Code extension Model is singleton and reactive** — `KnowledgeStore` uses `EventEmitter` for change notification, and Views subscribe via `store.onDidLoad()`. This is a proper reactive Model pattern.

9. ✅ **Sub-components use props for data and callbacks for actions** — `TaskCard`, `IntegrationCard`, `PrDetailPanel` all receive data via props and communicate user actions via callback props (`onResolve`, `onDeleted`, `onUpdated`). This is correct View → Controller communication.

### Test Coverage

10. **🟡 No MVC-specific tests** — There are no tests that specifically verify layer separation (e.g., testing that a View component doesn't make direct API calls). The integration tests for routes test the API boundary but don't test frontend layer compliance.

11. **✅ Component structure supports testing** — The MVC separation means View components can be tested with mock data without needing API mocks. The Controller logic (event handlers) can be tested with mock hooks.

### Missing Features / Gaps

1. **Raw `fetch()` in pipeline.tsx** — The ingest and generate endpoints are called via raw `fetch()` instead of generated hooks. This is the most significant MVC gap because:
   - The endpoints exist in `openapi.yaml` (confirmed by the API server routes)
   - Generated hooks should exist in `@workspace/api-client-react`
   - Using raw fetch bypasses the Model layer entirely

2. **Raw `fetch()` in query.tsx and documents.tsx** — Same issue for MCP query and document list endpoints.

3. **No lint rule enforcing MVC** — There's no ESLint rule that prevents Views from importing `fetch` or direct API utilities. The rule is documented in the design doc but not enforced programmatically.

4. **`buildDashboardPayload` in DashboardPanel** — The view-model transformation function is embedded in the View class. It could be extracted to a `dashboard-viewmodel.ts` utility for better testability.

## Overall Verdict

⚠️ **WARN** — The MVC pattern is **well-implemented across the majority of the codebase**. The React frontend demonstrates excellent layer separation in 5 out of 8 page components — View components are pure (render from props/state), Controllers are clean event handlers that orchestrate Model calls, and the Model layer is the generated React Query hooks + cache. The VS Code extension also follows MVC correctly: TreeProviders are pure Views, `KnowledgeStore` is the Model, and `extension.ts` command handlers are Controllers.

However, there are **notable violations** in `pipeline.tsx`, `query.tsx`, and `documents.tsx` where raw `fetch()` calls bypass the Model layer entirely. These are not just stylistic issues — they circumvent the API-First contract (Zod validation, type safety, caching) that is a core project convention per AGENTS.md. The fact that `IngestStatusCard.tsx` already uses generated `useIngestGit`/`useIngestSvn` hooks proves the hooks exist, making the raw fetch in `pipeline.tsx` a layer violation rather than a missing codegen gap. These violations are localized to 3 files but represent a meaningful gap from a PASS rating, especially given the project's strict API-First mandate.
