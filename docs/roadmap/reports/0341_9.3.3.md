# Verification Report: Item 9.3.3 — POP (Protocol-Oriented Programming) for Services

**Item ID:** 9.3.3
**Description:** POP (Protocol-Oriented Programming) for services — All services and data-access layers must be defined behind a TypeScript interface (protocol) before implementation
**Date:** 2026-06-25
**Verdict:** ⚠️ WARN

---

## Design Spec References

- `docs/design/08-crosscutting-concepts.md` §8.3.4 — "All services and data-access layers must be defined behind a TypeScript interface (protocol) before implementation"
- Checklist item 9.3.3: `POP (Protocol-Oriented Programming) for services`

### Design Rules (from §8.3.4)

1. Every service that calls the database must implement an interface defined in the same file or a `types.ts` sibling.
2. Every service that calls the LLM must depend on the `LLMClient` interface from `lib/integrations-openai-ai-server/`.
3. Never instantiate a concrete class from a consumer — depend on the interface (inversion of control).

### Design Examples (from §8.3.4)

The design doc prescribes two patterns:
1. **Repository pattern** — `interface CommitRepository` → `class DrizzleCommitRepository implements CommitRepository` → consumers depend on `CommitRepository`
2. **VCS Adapter pattern** — `interface VcsIngestAdapter` → `class GitIngestAdapter implements VcsIngestAdapter` + `class SvnIngestAdapter implements VcsIngestAdapter`

## Round 1 — Architecture & Design Review

### Design Intent

Per §8.3.4, the POP pattern requires three layers:

```
┌──────────────────────────────────────────────────┐
│  Consumer (route handler / another service)       │
│    ↓ depends on interface (never concrete class)  │
├──────────────────────────────────────────────────┤
│  Interface (protocol contract)                    │
│    ↓ implemented by                              │
├──────────────────────────────────────────────────┤
│  Concrete Implementation                         │
└──────────────────────────────────────────────────┘
```

### Implementation Analysis

#### ✅ Correctly Following POP (2 files)

**1. `artifacts/ast-core/src/sink.ts` + `disk-jsonl-sink.ts` / `ipc-sqlite-sink.ts`**
- Interface `AstSink` defined in `ast-core/src/sink.ts` with `emit()` and `flush()` methods
- `DiskJsonlSink` and `IpcSqliteSink` both `implements AstSink`
- This is the **only** proper POP implementation in the production codebase

**2. `artifacts/ast-core/src/language-provider.ts`**
- Interface `LanguageProvider` defined with `wasm_file`, `extractClasses()`, `extractFunctions()`, `extractImports()`, `extractCalls()`
- `DefaultProvider implements LanguageProvider`
- Correct POP pattern

**3. VS Code Providers (implementing VS Code SDK interfaces)**
- `DocuviaHoverProvider implements vscode.HoverProvider`
- `DocuviaCodeLensProvider implements vscode.CodeLensProvider`
- `KnowledgeGraphTreeProvider implements vscode.TreeDataProvider<KGNode>, vscode.TreeDragAndDropController<KGNode>`
- `TaskQueueTreeProvider implements vscode.TreeDataProvider<TQNode>`
- These correctly depend on VS Code's own interfaces (external protocol)

#### ❌ Not Following POP (core server services)

**Critical Gap: No VCS Adapter Interface**

The design doc explicitly prescribes the VCS Adapter pattern:
```typescript
// Design doc example:
interface VcsIngestAdapter {
  ingest(input: IngestInput): Promise<IngestResult>;
}
class GitIngestAdapter implements VcsIngestAdapter { ... }
class SvnIngestAdapter implements VcsIngestAdapter { ... }
```

**Reality:** `LocalGitClient` and `svn-client.ts` are standalone classes with no shared interface:
- `git-client.ts` exports `class LocalGitClient` with methods `clone()`, `getCommits()`, `getDiff()`, `getModifiedFiles()`, `getCurrentBranchName()`, `getProjectedCommits()`
- `svn-client.ts` exports standalone async generator function `getSvnLog()` and `getSvnDiff()` — no class, no interface
- There is **no** `VcsIngestAdapter` interface anywhere in the codebase

**Critical Gap: No Repository Interface**

The design doc prescribes:
```typescript
// Design doc example:
interface CommitRepository {
  findUnprocessed(projectId: number): Promise<Commit[]>;
  markProcessed(commitId: number): Promise<void>;
}
class DrizzleCommitRepository implements CommitRepository { ... }
```

**Reality:** All database access is done directly via Drizzle ORM queries in route handlers and service functions. There is no `CommitRepository` interface, no `DrizzleCommitRepository` class, no repository abstraction layer at all.

**Critical Gap: No LLMClient Interface**

The design doc rule: "Every service that calls the LLM must depend on the `LLMClient` interface from `lib/integrations-openai-ai-server/`."

**Reality:** `lib/integrations-openai-ai-server/src/client.ts` exports a **singleton** `openai` instance directly:
```typescript
export const openai = new OpenAI({
  apiKey: process.env.AI_INTEGRATIONS_OPENAI_API_KEY,
  baseURL: process.env.AI_INTEGRATIONS_OPENAI_BASE_URL,
});
```
There is no `LLMClient` interface. Consumers import the concrete `openai` singleton directly. The `intent-router.ts` and `embedding.ts` both `import { openai } from "@workspace/integrations-openai-ai-server"` — directly depending on the concrete implementation.

**Critical Gap: No Service Interfaces for Core Functions**

The following service modules export functions directly with no interface:
- `intent-router.ts` — exports `routeQuery()` function (no `IntentRouter` interface)
- `vector-search.ts` — exports `performVectorSearch()` function (no `VectorSearch` interface)
- `embedding.ts` — exports `generateEmbedding()`, `cosineSimilarity()`, `parseEmbedding()` (no `EmbeddingService` interface)
- `ingestion-pipeline.ts` — exports `processIngestion()` function (no `IngestionService` interface)
- `document-parser.ts` — exports `detectDocType()`, `extractText()` (no `DocumentParser` interface)
- `build-artifact-parser.ts` — exports `detectSubtype()`, `parseMapFile()`, etc. (no `BuildParser` interface)
- `commit-scorer.ts` — exports `scoreCommit()` function (no `CommitScorer` interface)
- `extensions-service.ts` — exports `vscodeQuery()`, `createL3Decision()`, `getFileContext()` (no `ExtensionService` interface)

### Architecture Assessment

The POP pattern is **not implemented** in the core API server. The architecture is overwhelmingly concrete-dependency based:

1. **Only 1 production interface** exists (`AstSink` in `ast-core`) — this is the sole POP-compliant module
2. **The `LanguageProvider` interface** in `ast-core` is POP-compliant but is part of a subsystem (AST core) rather than the main server services
3. **VS Code providers** correctly implement VS Code SDK interfaces, but this is standard VS Code extension architecture (not project-specific POP)
4. **All core services** (`git-client`, `intent-router`, `vector-search`, `embedding`, `ingestion-pipeline`, `document-parser`, `build-artifact-parser`, `commit-scorer`, `extensions-service`) are concrete classes/functions with no interfaces
5. **The `integrations-openai-ai-server`** exports a singleton instead of an interface, violating the "depend on interface, not implementation" rule

**Strengths:**
1. ✅ `AstSink` interface is correctly defined and implemented by multiple sinks
2. ✅ `LanguageProvider` interface is correctly defined and implemented
3. ✅ VS Code providers correctly implement VS Code SDK interfaces
4. ✅ Type system provides some contract safety via TypeScript types (even without interfaces)

**Weaknesses:**
1. ❌ **No VCS adapter interface** — `LocalGitClient` and SVN client have no shared protocol
2. ❌ **No repository interface** — DB access is inline Drizzle queries in routes
3. ❌ **No LLMClient interface** — `openai` singleton is imported directly everywhere
4. ❌ **No service interfaces** — All core service modules are concrete implementations
5. ❌ **Direct instantiation in routes** — `new LocalGitClient()` in `ingest.ts:51` and `generate.ts:792`
6. ❌ **No dependency injection** — No DI container, no constructor injection of interfaces

## Recommendations

1. **[HIGH] Define `VcsIngestAdapter` interface** (per design doc §8.3.4):
   ```typescript
   // artifacts/api-server/src/lib/types/vcs-adapter.ts
   export interface VcsIngestAdapter {
     clone(url: string, branch?: string): Promise<void>;
     getCommits(limit: number, since?: Date): Promise<VcsCommitItem[]>;
     getDiff(ref: string): Promise<string>;
     getModifiedFiles(ref: string): Promise<string[]>;
     cleanup(): Promise<void>;
   }
   // Then: class GitIngestAdapter implements VcsIngestAdapter
   // Then: class SvnIngestAdapter implements VcsIngestAdapter
   ```

3. **[HIGH] Remove direct instantiation from routes** — Replace `new LocalGitClient()` with a factory function or DI container that returns `VcsIngestAdapter`.

4. **[MEDIUM] Define repository interfaces** for DB access:

5. **[MEDIUM] Define service interfaces** for the 8+ service modules in `api-server/src/lib/` — at minimum for `intent-router`, `ingestion-pipeline`, and `embedding` since these are the most critical and most likely to need alternative implementations.

## Overall Verdict

⚠️ **WARN** — The POP (Protocol-Oriented Programming) pattern is **not implemented** in the core API server. The design doc §8.3.4 prescribes three specific rules (DB services must implement interfaces, LLM services must depend on `LLMClient` interface, never instantiate concrete classes from consumers), and **all three are violated** throughout the codebase.

The **only** POP-compliant code in the production codebase is:
- `AstSink` interface in `ast-core/src/sink.ts` (implemented by `DiskJsonlSink` and `IpcSqliteSink`)
- `LanguageProvider` interface in `ast-core/src/language-provider.ts` (implemented by `DefaultProvider`)

The `integrations-openai-ai-server` is the most critical violation — it exports a concrete `OpenAI` singleton instead of an `LLMClient` interface, which means every service that uses LLM capabilities (`intent-router.ts`, `embedding.ts`) is tightly coupled to the OpenAI implementation. This directly violates the design doc requirement.

The VCS adapter pattern (the example given in the design doc) is completely absent — there is no `VcsIngestAdapter` interface, and `LocalGitClient` is instantiated directly in two route files (`ingest.ts:51` and `generate.ts:792`).

However, the lack of interfaces does not cause runtime failures — the code compiles and functions correctly. The impact is on **testability** (cannot mock external dependencies), **flexibility** (cannot swap implementations without modifying consumers), and **design contract enforcement** (no compile-time guarantee that implementations satisfy the protocol). This is a WARN rather than FAIL because the code works as written, but it does not follow the documented architecture.
