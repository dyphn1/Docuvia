## Design Spec References

- `docs/design/08-crosscutting-concepts.md` §8.3.5 — "UI structures (VS Code providers) must follow OOP patterns: encapsulation, inheritance where appropriate, composition over inheritance"
- Checklist item 9.3.4: `OOP for UI structures (VS Code providers)`

### Design Rules (from §8.3.5)

1. All VS Code providers must be implemented as classes (not plain functions or anonymous objects)
2. Providers must implement their corresponding VS Code SDK interface explicitly
3. State must be encapsulated (private fields, public methods only as needed)
4. Composition over inheritance — prefer injecting dependencies via constructor
5. Lifecycle management (dispose pattern) for subscriptions and watchers

## Round 1 — Architecture & Design Review

### Design Intent

Per §8.3.5, the VS Code extension's UI layer must follow OOP principles:

```
┌─────────────────────────────────────────────────────────┐
│  extension.ts (Composition Root)                         │
│    ↓ constructs and wires                                │
├─────────────────────────────────────────────────────────┤
│  Provider Classes (encapsulated state + behavior)       │
│    ↓ implement VS Code SDK interfaces                   │
├─────────────────────────────────────────────────────────┤
│  VS Code SDK Interfaces (TreeDataProvider, etc.)        │
└─────────────────────────────────────────────────────────┘
```

### Implementation Analysis

#### ✅ Excellent OOP — Full Encapsulation Pattern (4 files)

**1. `KnowledgeGraphTreeProvider` (292 lines)**
- Proper class with encapsulated state: `private readonly _onDidChangeTreeData`, `private readonly store`
- Implements two VS Code interfaces: `vscode.TreeDataProvider<KGNode>`, `vscode.TreeDragAndDropController<KGNode>`
- Constructor injection: `constructor(private readonly store: KnowledgeStore)`
- Private helper logic, public interface methods only
- Event-driven pattern via `EventEmitter` (proper OOP event encapsulation)

**2. `DocuviaCodeLensProvider` (215 lines)**
- Proper class with encapsulated state: `private readonly _store`, `private readonly _onDidChangeCodeLenses`, `private documentAnchors`
- Implements `vscode.CodeLensProvider` interface
- Constructor injection of both `KnowledgeStore` and `vscode.ExtensionContext`
- Private method `updateSymbolAnchors()` encapsulated — internal caching mechanism hidden
- Defensive pattern: LSP-based semantic parsing with regex fallback

**3. `TaskQueueTreeProvider` (170 lines)**
- Proper class with encapsulated state: `private _tasks`, `private readonly _onDidChangeTreeData`
- Implements `vscode.TreeDataProvider<TQNode>`
- Clean public API: `addTask()`, `updateTaskStatus()`, `clearCompleted()`, `getPendingCount()`, `getInProgressCount()`
- Internal state management hidden — tasks modified through methods only

**4. `DashboardPanel` (424 lines)**
- Proper class with full lifecycle management: `private readonly _panel`, `private readonly _context`, etc.
- Static factory pattern: `static createOrShow()` — controls instantiation
- Implements VS Code `WebviewPanel` lifecycle (dispose handling, message passing)
- Private methods for `_pushData()`, `_handleMessage()`, `_buildHtml()` — all encapsulated
- Static registry: `private static _panels = new Map<string, DashboardPanel>()` — prevents duplicate panels

#### ✅ Good OOP — Proper Class Design (4 files)

**5. `SearchResultsPanel` (228 lines)**
- Same patterns as `DashboardPanel`: static factory, private constructor, encapsulated state
- CSP-aware HTML generation with nonce (security + OOP)
- Message handling via `_handleMessage()` — encapsulated

**6. `DocuviaHoverProvider` (41 lines)**
- Concise but proper class: 2 private fields, constructor injection
- Implements `vscode.HoverProvider` interface
- Delegates to `KnowledgeIndexer` for matching logic (composition)

**7. `CredentialManager` (19 lines)**
- Minimal but correct OOP: encapsulates `SecretStorage` dependency
- Clean public API: `getToken()`, `setToken()`, `clearToken()`
- Constructor injection of `vscode.SecretStorage`

**8. `KnowledgeStore` (607 lines)**
- Singleton pattern with `private static _instance` — proper OOP singleton
- Implements `IDocuviaClient` interface (structural typing for circular import avoidance)
- Encapsulated state: `_snapshots`, `_globalConfig`, `_watchers` all private
- Event via `onDidFinishIndexing` — encapsulated event emitter

#### ✅ Acceptable — Factory Function + Class (2 files)

**9. `ChatParticipant.ts` (724 lines)**
- Uses factory function pattern: `registerDocuviaChatParticipant()` returns `vscode.ChatParticipant`
- VS Code's `createChatParticipant()` is the OOP wrapper — handler is a closure
- This is the standard VS Code pattern for chat participants (not a class per se, but OOP-compliant via VS Code SDK)
- All handlers are pure functions with clear separation of concerns

**10. `KnowledgeIndexer.ts` (179 lines)**
- Proper class with `Disposable` pattern (subscriptions tracked in `_disposables`)
- Implements cleanup via `dispose()` — proper lifecycle management
- Constructor injection of `KnowledgeStore`
- Encapsulated interval trees: `private _trees`, `private _indexingQueue`

### Architecture Assessment

The VS Code extension's UI layer demonstrates **strong OOP implementation**:

1. ✅ **All providers are classes** — No plain-function providers exist
2. ✅ **All implement VS Code SDK interfaces** — `TreeDataProvider`, `CodeLensProvider`, `HoverProvider`, `ChatParticipant`
3. ✅ **Encapsulation is consistent** — All fields are `private readonly` or `private`, state modified through methods
4. ✅ **Constructor injection is universal** — Every class receives dependencies via constructor
5. ✅ **Composition over inheritance** — No deep inheritance hierarchies; composition via injected dependencies
6. ✅ **Lifecycle management** — `Disposable` pattern in `KnowledgeIndexer`, panel dispose handling in `DashboardPanel` and `SearchResultsPanel`
7. ✅ **Static factory patterns** — `DashboardPanel.createOrShow()` and `SearchResultsPanel.createOrShow()` prevent duplicate instances

**Strengths:**
1. ✅ Consistent OOP patterns across all 12 source files
2. ✅ Proper interface implementation (VS Code SDK contracts)
3. ✅ Encapsulation is thorough — no public mutable state exposed
4. ✅ Composition root in `extension.ts` — all wiring is centralized
5. ✅ Singleton pattern for `KnowledgeStore` with proper lazy initialization
6. ✅ Event-driven patterns via `EventEmitter` (not callback hell)

**Weaknesses:**
1. 🟡 `ChatParticipant.ts` uses closure-based handlers instead of class methods — this is VS Code's prescribed pattern but is less testable than class-based providers
2. 🟡 `CentralServerClient` has no interface (relevant to POP but not strictly OOP)

## Recommendations

1. **[INFO] Consider extracting shared panel logic** — `DashboardPanel` and `SearchResultsPanel` share static factory and message-handling patterns. A lightweight `BasePanel` utility class could reduce ~30 lines of shared boilerplate, but the current duplication is minimal and acceptable.

2. **[INFO] `ChatParticipant` testability** — The closure-based handler pattern makes unit testing individual commands harder. If testability becomes a concern, consider extracting handler logic into a separate `ChatCommandHandler` class that can be tested independently.

3. **[INFO] Future: Abstract base for providers** — If more TreeViews are added in the future, a base `SingletonTreeProvider` with common refresh/event patterns could reduce boilerplate.
