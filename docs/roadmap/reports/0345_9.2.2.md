## Round 1 — Architecture & Design Review

### Design Intent

Per the building blocks doc and cross-cutting concepts, the activity log system must:

1. **Persist all AI-generated events** — L1 tag creation, L2 node creation, L3 node creation, review resolutions, document uploads, and commit ingestions
2. **Support project attribution** — Optional `projectId` column to link events to specific projects
3. **Provide audit trail** — Immutable record with type, description, and timestamp for compliance and debugging
4. **Feed the dashboard** — Recent activity panel showing the last 10 events with project context
5. **Feed metabolism pipeline** — Source data for distillation into prompt templates and guardrails
6. **Use a typed enum** — Activity types constrained to a predefined set

### Implementation Analysis

**Schema** (`lib/db/src/schema/activity_log.ts`):

```typescript
export const activityTypeEnum = pgEnum("activity_type", [
  "commit",
  "l2_created",
  "l3_created",
  "review_resolved",
  "tag_added",
  "document",
]);

export const activityLogTable = pgTable("activity_log", {
  id: serial("id").primaryKey(),
  type: activityTypeEnum("type").notNull(),
  description: text("description").notNull(),
  projectId: integer("project_id"),
  createdAt: timestamp("created_at").notNull().defaultNow(),
});
```

**Migration SQL** (`0000_short_ezekiel.sql`):

```sql
CREATE TYPE "public"."activity_type" AS ENUM('commit', 'l2_created', 'l3_created', 'review_resolved', 'tag_added', 'document');
CREATE TABLE "activity_log" (
  "id" serial PRIMARY KEY NOT NULL,
  "type" "activity_type" NOT NULL,
  "description" text NOT NULL,
  "project_id" integer,
  "created_at" timestamp DEFAULT now() NOT NULL
);
```

**Dashboard Query** (`dashboard.ts:26-47`):

```typescript
const activityRows = await db
  .select()
  .from(activityLogTable)
  .orderBy(sql`${activityLogTable.createdAt} desc`)
  .limit(10);
```

Performs a descending-order query with limit 10, then joins `projectsTable` to attach `projectName` to each activity item.

**Activity Logging Callers** — The `logAndNotify()` helper in `ingestion-pipeline.ts:211-245` is the central dispatcher for "commit", "tag_added", and "document" types. Individual route handlers (l1_tags, l2_nodes, l3_nodes, review_tasks, projects, extensions-service, generate) also insert activity records directly.

### Architecture Assessment

**Strengths:**
1. ✅ **Schema design** — Proper use of PostgreSQL enum for type safety, serial primary key, `defaultNow()` for automatic timestamping, nullable `projectId` for events not tied to a specific project
2. ✅ **Typed enum** — `activity_type` enum constrains values to exactly the 6 types specified in the design
3. ✅ **Zod insert schema** — `createInsertSchema` with `omit({ id: true, createdAt: true })` correctly auto-generates validation for inserts
4. ✅ **Dashboard integration** — Dashboard endpoint performs a descending-order query with limit 10 and joins project names, exactly as the design requires
5. ✅ **Comprehensive event coverage** — All 6 activity types are actually used in production code. The `document` type is triggered via `ingestion-pipeline.ts:logAndNotify()` when documents are ingested through the ingest route
6. ✅ **Frontend rendering** — `dashboard.tsx` correctly consumes `recentActivity` from the API response and renders it with timestamps and project names
7. ✅ **Centralized helper** — `logAndNotify()` in `ingestion-pipeline.ts` provides a consistent pattern for activity logging with notification dispatch

**Weaknesses:**
1. 🟡 **Missing index** — No index on `created_at` or `project_id`. The dashboard query `ORDER BY created_at DESC LIMIT 10` will perform a full table scan on large datasets
2. 🟡 **Missing `document` in OpenAPI enum** — The DB enum includes `document` but the OpenAPI `ActivityItem.type` enum omits it (line 1701 of `openapi.yaml`)
3. 🟡 **No foreign key on `project_id`** — The column is a plain integer with no FK constraint to `projects.id`; referential integrity relies on application logic
4. 🟡 **No metabolism/consumption pipeline** — The design says activity_log "feeds the metabolism pipeline's distillation input" — no code reads activity_log for distillation purposes
5. 🟢 **No dedicated activity_log route** — No `GET /activity` endpoint for browsing/paginating activity history beyond the dashboard's top-10

## Round 2 — Code Quality & Security Review

### Security Findings

1. ✅ **No sensitive data exposure** — Activity log descriptions are human-readable messages (e.g., "L3 node \"Auth Module\" created", "Ingested 3 documents") containing no tokens, passwords, or PII
2. ✅ **No SQL injection risk** — All queries use Drizzle ORM parameterized queries
3. ✅ **No write protection needed** — Activity logs are append-only by design; no update/delete endpoints exist (appropriate for audit trail)
4. 🟡 **LOW — No access control on activity data** — The dashboard endpoint returns all activity records regardless of project ownership. In a multi-tenant scenario, this could leak cross-project activity information. Current single-user architecture makes this acceptable.

### Code Quality Findings

1. ✅ **Consistent logging pattern** — All activity log inserts follow the same pattern: `db.insert(activityLogTable).values({ type, description, projectId })`
2. ✅ **Type safety** — The `activityTypeEnum` ensures only valid types can be inserted
3. ✅ **Zod validation** — Insert schema validates type enum and description at the API boundary
4. ✅ **`document` activity type is used** — The `document` enum value is actively triggered in `ingestion-pipeline.ts:logAndNotify()` when documents are ingested via the POST `/projects/:id/ingest` (content-ingest) and POST `/projects/:id/ingest/build-artifact` routes
5. 🟡 **No error handling around activity inserts in some paths** — In `extensions-service.ts:71`, the activity insert is wrapped in try/catch (good). In `generate.ts` (lines 746, 1125, 1155) and `ingestion-pipeline.ts` (line 218), activity inserts are not wrapped — a DB failure would propagate and potentially fail the parent operation
6. 🟡 **No pagination API** — Only the dashboard's top-10 query exists. There's no way for users to browse historical activity beyond the 10 most recent items
7. 🟢 **No test coverage** — No unit or integration tests verify activity log insertion, type constraints, or dashboard query behavior

### Test Coverage

8. 🔴 **No activity_log tests** — Zero test files reference `activityLogTable`, `activity_type`, or activity-related operations. The design's audit trail requirement should have at least:
   - Insert query returns created record with auto-generated id and timestamp
   - Enum constraint rejects invalid types
   - Dashboard query returns correct ordering (most recent first)

### Missing Features / Gaps

1. **No index on `created_at`** — The dashboard's `ORDER BY created_at DESC LIMIT 10` query will degrade as the table grows. A `CREATE INDEX idx_activity_log_created_at ON activity_log(created_at DESC)` should be added.
2. **No metabolism/consumption pipeline** — The design states activity_log feeds the metabolism pipeline's distillation input. No code reads from activity_log for this purpose.
3. **No dedicated activity browsing API** — Only accessible via the dashboard's top-10. No `GET /activity` with pagination, filtering by type/project, or search.
4. **Missing `document` in OpenAPI enum** — `ActivityItem.type` in `openapi.yaml:1701` lists 5 enum values; the DB has 6.
5. **No referential integrity** — `project_id` has no FK constraint to `projects.id`; orphaned activity records can exist if a project is deleted.
6. **No test coverage** — Zero tests for activity log behavior.
7. **Activity inserts unguarded in some paths** — `generate.ts` and `ingestion-pipeline.ts` don't wrap activity inserts in try/catch, risking parent operation failure on DB errors.

## Overall Verdict

⚠️ **WARN** — The activity log table is **well-designed and broadly implemented** across the codebase. The schema uses proper typing (PG enum with all 6 values actively used), the dashboard integration works end-to-end (API query with project join → frontend rendering), and all 6 activity types are consistently recorded throughout the ingestion, generation, review, extension, and project pipelines. The `document` type is correctly triggered via `logAndNotify()` in the ingestion pipeline.

However, there are notable gaps: no database index for the dashboard's sort query, the metabolism pipeline doesn't consume activity data as designed, there's no dedicated API for browsing activity history, the OpenAPI enum is out of sync with the DB schema, and there's zero test coverage. The core audit trail infrastructure is solid, but completeness and performance gaps prevent a PASS rating.
