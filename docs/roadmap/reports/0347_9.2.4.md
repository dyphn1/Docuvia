## Round 1 — Architecture & Design Review

### Design Intent

Per the quality requirements and building blocks docs, the error reporting / alerting mechanism must:

1. **Implement a Dead Letter Queue (DLQ) pattern** — Jobs that fail repeatedly (3 times) are isolated into the `error_reports` table
2. **Provide `error_reports` table** — Schema with fields for project ID, job ID, task type, error message, error stack, and payload snapshot
3. **Integrate with `job_queue`** — Background jobs track status (`pending` → `processing` → `failed`/`completed`), with retry counting
4. **Prevent infinite crash loops** — After 3 failures, the job is moved to the DLQ and stops retrying
5. **Surface errors for operators** — Either via the `error_reports` table, notifications, or external alerting

### Implementation Analysis

**`error_reports` Table Schema** (`lib/db/src/schema/error_reports.ts`):

```typescript
export const errorReportsTable = pgTable("error_reports", {
  id: serial("id").primaryKey(),
  projectId: integer("project_id").references(() => projectsTable.id, { onDelete: "cascade" }),
  jobId: integer("job_id").references(() => jobQueueTable.id, { onDelete: "set null" }),
  taskType: text("task_type").notNull(),
  errorMessage: text("error_message").notNull(),
  errorStack: text("error_stack"),
  payloadSnapshot: jsonb("payload_snapshot"),
  createdAt: timestamp("created_at").notNull().defaultNow(),
});
```

**`job_queue` Table Schema** (`lib/db/src/schema/job_queue.ts`):

```typescript
export const jobStatusEnum = pgEnum("job_status", ["pending", "processing", "failed", "completed"]);

export const jobQueueTable = pgTable("job_queue", {
  id: serial("id").primaryKey(),
  taskType: text("task_type").notNull(),
  payload: jsonb("payload").notNull().default({}),
  status: jobStatusEnum("status").notNull().default("pending"),
  lockedAt: timestamp("locked_at"),
  createdAt: timestamp("created_at").notNull().defaultNow(),
  updatedAt: timestamp("updated_at").notNull().defaultNow(),
});
```

**Key Observations:**

1. ✅ **Schema definition exists** — `error_reports` table is properly defined with all required fields (project ID, job ID, task type, error message, stack trace, payload snapshot, timestamp)
2. ✅ **Schema exported** — `error_reports.ts` is re-exported from `lib/db/src/schema/index.ts:19`
3. ✅ **Zod insert schema exists** — `insertErrorReportSchema` is generated via `createInsertSchema`
4. ✅ **`job_queue` status enum includes `failed`** — The status lifecycle supports failure tracking
5. ❌ **No DLQ processing logic** — There is **zero application code** that inserts into `error_reports`. No service, no function, no route writes to this table. The schema is defined but completely unused.
6. ❌ **No retry counting** — The `job_queue` table has no `attempts` or `retryCount` column. There is no way to track how many times a job has failed, making the "3 failures → DLQ" rule impossible to implement.
7. ❌ **No background job processor** — There is no worker/service that reads from `job_queue` and processes jobs. The `projects.ts:245` explicitly acknowledges this: `// In a real implementation this would trigger an async job via job_queue.ts`
8. ❌ **No error notification** — Even when jobs fail, there is no mechanism to notify operators. The `notifyExternalIntegrations` function is only called for successful events (new commits, new L3 nodes, cross-links), never for failures.
9. ❌ **No `error_reports` route** — There is no REST endpoint to query or manage error reports. The route registry (`routes/index.ts`) has no error-reports router.
10. ❌ **No migration** — The `error_reports` table has no Drizzle migration file applied to the database.

### Architecture Assessment

**Strengths:**
1. ✅ **Schema design is well-structured** — The `error_reports` table has all the necessary fields for a DLQ: project context, job reference, error details, payload snapshot for replay debugging.
2. ✅ **Foreign key relationships correct** — `projectId` cascades on delete, `jobId` sets null on delete (preserving the error report if the job record is cleaned up).
3. ✅ **`job_queue` status enum includes `failed`** — The lifecycle is modeled correctly at the schema level.

**Weaknesses:**
1. 🔴 **No runtime implementation** — The entire DLQ mechanism is a dead schema. No code inserts, reads, or processes error reports.
2. 🔴 **No retry tracking** — `job_queue` lacks an `attempts` column, making the "3 failures → DLQ" rule unimplementable without schema changes.
3. 🔴 **No job processor** — There is no background worker that reads from `job_queue` and executes tasks. The queue is defined but never consumed.
4. 🔴 **No alerting integration** — Even the existing notification system (`notifyExternalIntegrations`) is never invoked for error/failure events.
5. 🔴 **No API surface** — No REST routes for querying, listing, or resolving error reports.

## Round 2 — Code Quality & Security Review

### Security Findings

1. ✅ **Schema-level security is sound** — The `error_reports` table doesn't store credentials or tokens. The `payloadSnapshot` is a JSONB column that could theoretically contain sensitive data, but since no code writes to it, there's no current risk.
2. 🔴 **No access control on error reports** — Since there's no route to read `error_reports`, there's no access control to evaluate. When implemented, error reports should be scoped to the project owner.
3. 🟡 **Payload snapshot could leak secrets** — The `payloadSnapshot` JSONB field is designed to store the full job payload. If that payload contains API keys, tokens, or file contents, they would be stored in plaintext in the DLQ. Encryption or redaction should be considered.

### Code Quality Findings

1. ✅ **Schema definition is clean** — The `error_reports.ts` file is well-structured, uses Drizzle ORM conventions, and includes a Zod insert schema.
2. ✅ **Comment documents intent** — `// Max's Rule: Dead Letter Queue (DLQ) to prevent infinite crash loops` clearly documents the purpose.
3. 🔴 **Dead schema — zero usage** — The `error_reports` table and `insertErrorReportSchema` are exported but never imported by any service, route, or middleware. This is dead code.
4. 🔴 **`job_queue` also unused** — The `job_queue` table is similarly defined but never used. Only one comment in `projects.ts:245` references it, explicitly noting it's not yet implemented.
5. 🟡 **No test coverage** — Zero test files reference `error_reports`, `job_queue`, or DLQ patterns. No tests exist for error handling in background jobs.
6. 🟡 **Inconsistent with working patterns** — Other tables (notifications, activity_log, subscriptions) follow the pattern: schema → routes → service → tests. `error_reports` and `job_queue` stop at the schema step.

### Test Coverage

7. 🔴 **No tests at all** — Zero test files cover error reporting, job queuing, or DLQ behavior. The quality requirements' DLQ pattern is completely untested.

## Recommendations

1. **[CRITICAL] Add `attempts` column to `job_queue`** — Add an `attempts: integer("attempts").notNull().default(0)` column to track retry count. This is prerequisite to implementing the 3-failure DLQ threshold.

2. **[CRITICAL] Implement DLQ processing service** — Create a service that:
   - Reads pending jobs from `job_queue`
   - Increments `attempts` on each retry
   - When `attempts >= 3`, inserts into `error_reports` with the error details and sets job status to `failed`
   - Logs the DLQ insertion via `logger.error()`

3. **[CRITICAL] Create database migration** — Run `pnpm --filter @workspace/db run push` to apply the `error_reports` and `job_queue` schemas to the dev database.

4. **[HIGH] Add error notification** — When a job is moved to the DLQ, notify project subscribers and external integrations (Slack/Teams) about the failure:
   ```typescript
   void notifyExternalIntegrations(projectId, projectName, "job_failed", {
     jobId: job.id,
     taskType: job.taskType,
     attempts: job.attempts,
   });
   ```

5. **[HIGH] Add `GET /error_reports` route** — Create a router to list error reports, scoped by project, with filtering by date range and task type.

6. **[MEDIUM] Add DLQ tests** — Write integration tests that:
   - Simulate 3 consecutive job failures
   - Verify the job is moved to `error_reports`
   - Verify the job status is set to `failed`
   - Verify notification is triggered

7. **[MEDIUM] Add payload redaction** — Before storing in `payloadSnapshot`, redact sensitive fields (API keys, tokens) to prevent secret leakage in the DLQ.

---

## Overall Verdict

❌ **FAIL** — The error reporting / alerting mechanism is **architecturally defined but completely unimplemented**. The `error_reports` table schema exists in code and is properly structured with all necessary fields (project ID, job ID, task type, error message, stack trace, payload snapshot). The `job_queue` table also has a correct status enum with a `failed` state.

However, **no runtime logic exists**:
- No service inserts into `error_reports`
- No job processor reads from `job_queue`
- No retry counting (missing `attempts` column)
- No DLQ threshold logic
- No error notification to operators
- No REST API to query error reports
- No database migration applied
- No test coverage

The entire mechanism is a **dead schema** — it represents good design intent but provides zero operational error reporting or alerting capability. The quality requirements' DLQ pattern ("Any job failing 3 times is isolated into the `error_reports` table") cannot be fulfilled without significant implementation work across schema, service, routing, and notification layers.
