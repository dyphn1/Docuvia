## Round 1 — Architecture & Design Review

### Design Intent

The spec mandates a closed-loop self-evolution system where:
1. A reviewer approves an AI-generated node (L1 tag, L2 node, or L3 node) with a correction (`correctedValue`).
2. The system stores the original vs. corrected content in the `correction_examples` table.
3. Future generation runs inject these corrections as few-shot examples.
4. A background distillation job compresses accumulated corrections into architectural guardrails stored as prompt templates.

The key design requirement: **ALL entity types** (L1, L2, L3) must have their corrections captured in `correction_examples`.

### Implementation Analysis

In `review_tasks.ts` (lines 124-171), the resolution handler implements the following conditional logic:

```typescript
if (body.correctedValue && task.status === "approved") {
    if (task.entityType === "l2_node") {
        // Lines 126-143: Fetch node → guard on node.description → INSERT correction_examples → UPDATE l2NodesTable
    } else if (task.entityType === "l3_node") {
        // Lines 144-163: Fetch node + parent L2 → guard on node.content → INSERT correction_examples → UPDATE l3NodesTable
    } else if (task.entityType === "l1_tag") {
        // Lines 164-170: UPDATE l1TagsTable ONLY — NO correction_examples insert
    }
}
```

**Entity-type breakdown:**

| Entity Type | correction_examples Insert | Original Content | Corrected Content | Project ID | Update Target |
|-------------|--------------------------|------------------|--------------------|------------|---------------|
| `l2_node`   | ✅ Yes                   | `node.description` | `body.correctedValue` | `node.projectId` | `l2NodesTable` |
| `l3_node`   | ✅ Yes                   | `node.content`   | `body.correctedValue` | `l2?.projectId ?? null` | `l3NodesTable` |
| `l1_tag`    | ❌ **No**                | —                | —                  | —          | `l1TagsTable` only |

**Guard conditions:**
- L2: `if (node && node.description)` — skips insert if description is falsy (null, undefined, empty string)
- L3: `if (node.content)` — skips insert if content is falsy
- L1: No insert at all

### Architecture Assessment

**Strengths:**
- The L2 and L3 paths correctly implement the spec: they capture original content, corrected content, project ID, entity type, and entity ID.
- The `correction_examples` schema is well-designed with `processedAt` for idempotent distillation.
- The guard conditions prevent storing corrections where the original content was empty (which could lead to meaningless few-shot examples).

**Weaknesses:**
- **Critical gap**: L1 tag corrections are never stored in `correction_examples`. The `l1_tag` branch (lines 164-170) only updates `l1TagsTable.description` — the correction is applied but the feedback loop is broken.
- The null-content guards, while preventing empty originals, may silently drop legitimate corrections where a reviewer is establishing content for a newly-created node that had a placeholder.

## Round 2 — Code Quality & Security Review

### Violations Found

1. **🟠 High — `review_tasks.ts:164-170` — L1 tag corrections never stored in `correction_examples`**
   - The `l1_tag` branch only updates `l1TagsTable.description` with the corrected value. No row is inserted into `correctionExamplesTable`. This breaks the continuous improvement loop for L1 tags as specified in ADR-006 and section 09.
   - **Impact**: L1 tag corrections are lost to the self-evolution system. The distillation job can never learn from L1 corrections, and future L1 generation runs never benefit from past human corrections.

2. **🟡 Medium — `review_tasks.ts:127,148` — Null original content silently drops corrections**
   - The guards `if (node && node.description)` (L2) and `if (node.content)` (L3) skip creating a correction example when the original content is falsy. This means if a reviewer corrects a node that was created with empty/null content (e.g., a newly extracted module with no description yet), the correction is silently discarded.
   - **Impact**: Edge-case data loss; the guard is overly protective.

3. **🟡 Medium — `generate.ts:88-104` — `getRecentCorrections()` only supports `l2_node` and `l3_node` entity types**
   - The function signature is `entityType: "l2_node" | "l3_node"` — no `"l1_tag"` option exists. Even if L1 corrections were stored in `correction_examples`, they could not be fetched for few-shot injection.
   - **Impact**: Compound issue — even after fixing the L1 insert gap, L1 generation would still not use corrections.

4. **🟢 Low — `generate.ts:175-208` — `generateL1Tags()` does not accept corrections parameter**
   - Unlike `generateL2Nodes()` which accepts `corrections: Array<{ original: string; corrected: string }>`, the L1 generation function has no such parameter and does not build a few-shot section.
   - **Impact**: Structural gap preventing L1 correction usage.

### Positive Findings

1. ✅ **L2/L3 correction capture is correct** — Fields match schema, project ID resolution works correctly for L3 via parent L2 lookup.
2. ✅ **Guard condition on `body.correctedValue && task.status === "approved"`** — Only creates correction examples when there's actually a correction (not on plain approve without correctedValue, or on reject).
3. ✅ **Schema design supports the full pipeline** — `processedAt` column enables idempotent distillation; `entityType` enables scoped few-shot retrieval.
4. ✅ **Distillation job is functional** — `metabolism.ts` correctly queries `WHERE processedAt IS NULL`, calls LLM, inserts into `promptTemplatesTable`, and marks rows as processed.

### Test Coverage

- No unit tests specifically for the correction example creation logic in `review_tasks.ts`.
- No integration tests verifying the full review-approval → correction-example → few-shot-injection pipeline.
- The `withRollback()` test infrastructure exists but is not exercised for this flow.

### Missing Features / Gaps

1. **L1 correction capture** — The `l1_tag` branch needs a `correctionExamplesTable.insert()` call similar to the L2/L3 paths.
2. **L1 few-shot consumption** — `generateL1Tags()` needs a corrections parameter and a `buildFewShotSection()` call in its prompt.
3. **`getRecentCorrections()` type union expansion** — Needs to include `"l1_tag"` in the entityType parameter.
4. **Distillation template type routing** — L2 corrections distilled as `l3_generator` may not be optimal; consider routing based on `correctionExamplesTable.entityType`.

## Recommendations

1. **[HIGH] Add `correction_examples` insert in the `l1_tag` branch** — Mirror the L2/L3 pattern: fetch the existing tag, guard on its existence, insert into `correctionExamplesTable` with `entityType: "l1_tag"`, `originalContent: tag.description`, `correctedContent: body.correctedValue`, `projectId` (L1 tags are global, so use `null` or the project from the review task context).

2. **[HIGH] Expand `getRecentCorrections()` type union** — Add `"l1_tag"` to the `entityType` parameter type and verify the SQL query works with global (null projectId) L1 corrections.

3. **[MEDIUM] Add corrections parameter to `generateL1Tags()`** — Accept `Array<{ original: string; corrected: string }>` and include `buildFewShotSection(corrections)` in the user prompt.

4. **[MEDIUM] Relax null-content guard for L2/L3** — Consider allowing correction examples even when original content is empty, since the correction itself is valuable signal. Alternatively, only guard against `undefined`/`null` but allow empty strings.

5. **[LOW] Route distillation template type by entity type** — Use `correctionExamplesTable.entityType` to determine the appropriate `templateType` (`l1_tagger`, `l2_extractor`, or `l3_generator`) when inserting distilled guardrails.

6. **[LOW] Add integration tests** — Create a test that exercises the full flow: create review task → approve with correction → verify `correction_examples` row exists → trigger generate → verify few-shot is injected.

---

## Overall Verdict

⚠️ **WARN** — Correction examples creation on review approval is **partially implemented**. The L2 and L3 paths correctly capture corrections in the `correction_examples` table, and the downstream pipeline (few-shot injection → distillation → prompt template update) works for these entity types. However, **L1 tag corrections are never captured** in `correction_examples`, breaking the continuous improvement loop for L1 tags. Additionally, `generateL1Tags()` does not consume corrections even if they were stored, and the `getRecentCorrections()` function excludes the `"l1_tag"` entity type. These issues are persistent from the previous verification (2026-06-20) with no code changes detected.
