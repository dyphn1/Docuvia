## Round 1 — Architecture & Design Review

### Design Intent

The design spec (arc42 section 7.1) defines a single-host deployment topology where all three processes — `api-server` (Node.js 24, port 8080), `kg-engine` (Vite dev server, port 18774), and PostgreSQL (port 5432) — run on the same machine. The VS Code extension connects locally. Section 7.5 adds deployment considerations: no Docker in v1, static serving not wired, no .vsix build script.

The topology diagram shows:
- Browser → kg-engine (port 18774) → api-server (port 8080) → PostgreSQL
- VS Code Extension → api-server (port 8080)
- api-server → OpenAI-compatible LLM API (HTTPS)
- GitHub → api-server (webhook HTTPS)

### Implementation Analysis

**Server Entry (`artifacts/api-server/src/index.ts`):**
- ✅ PORT env var validated with explicit error message on missing/invalid
- ✅ Server listens on the configured port
- ✅ Structured logging on startup

**Express App (`artifacts/api-server/src/app.ts`):**
- ✅ CORS middleware applied (wildcard — `app.use(cors())`)
- ✅ pino-http request logging
- ✅ GitHub webhook raw body parser mounted before JSON middleware
- ✅ LLM proxy route mounted at `/proxy/v1`
- ✅ API routes mounted at `/api`
- ❌ No static file serving (`express.static()` not configured) — kg-engine assets are not served by api-server

**Database (`lib/db/src/index.ts`):**
- ✅ DATABASE_URL env var validated with explicit error
- ✅ Connection pooling via `pg` Pool

**GitHub Webhooks (`github_webhooks.ts`):**
- ✅ GITHUB_WEBHOOK_SECRET env var read from process.env
- ✅ HMAC-SHA256 signature validation
- ✅ GITHUB_TOKEN env var used for API calls (not documented in env var table)
- ⚠️ Signature validation is conditional — only runs when `webhookSecret` is set; server starts without it silently

**CI Workflow (`.github/workflows/ci.yml`):**
- ✅ Uses `ubuntu-latest` runner
- ✅ Node.js 24, pnpm 9
- ✅ PostgreSQL 16 service container for test job
- ✅ Environment variables provided: DATABASE_URL, PORT, AI_INTEGRATIONS_OPENAI_API_KEY, AI_INTEGRATIONS_OPENAI_BASE_URL

### Architecture Assessment

The single-host deployment topology is **well-documented** in the design spec. The code structure supports it correctly:
- All three processes can run on one machine
- Environment variables are properly validated
- The VS Code extension connects via configurable `server_url`

However, there are gaps between the design doc and the actual codebase:
1. **OPENAI_API_KEY vs AI_INTEGRATIONS_OPENAI_API_KEY** — The design doc's env var table lists `OPENAI_API_KEY`, but the codebase uses `AI_INTEGRATIONS_OPENAI_API_KEY`. This is a naming discrepancy that would confuse operators following the deployment guide.
2. **GITHUB_TOKEN not documented** — The webhook handler reads `process.env.GITHUB_TOKEN` for API calls, but this variable is not listed in the env var table.
3. **Static serving not wired** — The design doc acknowledges this (D-03), but it's a real gap for production single-host deployment where you'd want the frontend served from the same port.
4. **CORS is wildcard** — `app.use(cors())` with no configuration allows all origins. Acceptable for development/single-host, but the design doc doesn't explicitly specify this.

## Round 2 — Code Quality & Security Review

### Violations Found

1. **🟡 MEDIUM — `OPENAI_API_KEY` naming discrepancy** — The design doc (`07-deployment.md` line 43) specifies `OPENAI_API_KEY` as the required env var. The codebase (`integrations-openai-ai-server/src/client.ts:9`) reads `AI_INTEGRATIONS_OPENAI_API_KEY`. An operator following the deployment guide would set the wrong variable name and the server would fail to initialize the LLM client.

2. **🟡 MEDIUM — `GITHUB_TOKEN` undocumented** — `github_webhooks.ts:175` reads `process.env.GITHUB_TOKEN` for fetching PR commits and posting comments. This required variable is not listed in the env var table in `07-deployment.md`. Without it, PR analysis features would fail silently.

3. **🟡 MEDIUM — Webhook secret not enforced at startup** — `github_webhooks.ts:131-140` only validates HMAC signatures when `webhookSecret` is set AND signature is present. If the secret is not configured, the server starts and accepts unsigned webhooks. The design doc says "Required when GitHub PR integration is active" but the code doesn't enforce this conditional requirement.

4. **🟢 LOW — CORS wildcard acceptable for single-host** — `app.use(cors())` allows all origins. For a single-host deployment where the frontend and API are on the same machine (different ports), this is functionally acceptable. However, if the frontend is served from a different origin (e.g., Vite dev proxy), CORS is needed. The design doc doesn't specify CORS policy.

5. **🟢 LOW — `LOG_LEVEL` env var functional but undocumented** — `logger.ts:7` reads `process.env.LOG_LEVEL` with fallback to `"info"`. This works correctly but is not listed in the deployment env var table. (Cross-reference: report 0346_9.2.3 already flagged this.)

6. **🟢 LOW — `NODE_ENV` used but not documented as deployment var** — `logger.ts:3` and `logger.ts:13` use `NODE_ENV` to toggle pretty logging. The env var table lists it as optional with default `development`, which is correct, but the operational significance (pretty vs JSON logging) is not explained.

### Positive Findings

1. ✅ **PORT validation is explicit** — Clear error message naming the variable, plus validation for invalid values
2. ✅ **DATABASE_URL validation** — Clear error with guidance ("Did you forget to provision a database?")
3. ✅ **HMAC validation is correct** — Uses `crypto.timingSafeEqual` to prevent timing attacks, pads buffers
4. ✅ **Webhook processing is async** — Responds 202 immediately, processes via `setImmediate` to avoid GitHub retry timeouts
5. ✅ **CI test job provides all required env vars** — DATABASE_URL, PORT, AI_INTEGRATIONS_OPENAI_API_KEY are all configured
6. ✅ **Logger has redaction pipeline** — `req.headers.authorization`, `password`, `token` etc. are redacted

### Test Coverage

No tests are relevant for this item — deployment topology documentation is a design/operations concern, not a runtime code concern. The CI workflow itself is the "test" for whether the deployment process works.

## Recommendations

1. **[MEDIUM] Align env var naming** — Either update the design doc to reflect `AI_INTEGRATIONS_OPENAI_API_KEY`, or add a note explaining the naming convention. Alternatively, support both names with a fallback.

2. **[MEDIUM] Add `GITHUB_TOKEN` to env var table** — Document it as "Required for GitHub PR analysis. GitHub personal access token with `repo` scope."

3. **[MEDIUM] Enforce webhook secret when GitHub integration is active** — If a project has GitHub integration configured, the server should refuse to start (or at least warn prominently) if `GITHUB_WEBHOOK_SECRET` is not set.

4. **[LOW] Add `.env.example`** — Create an `.env.example` file at the repo root listing all required/optional variables with example values. This is the single most impactful operator experience improvement.

5. **[LOW] Document CORS policy** — Add a brief note to the deployment docs explaining that CORS is wildcard by design for single-host deployment, and that production multi-host deployments need to configure `CORS_ORIGIN` (future work per D-03).

## Overall Verdict

⚠️ **WARN** — The single-host deployment topology is comprehensively documented in `docs/design/07-deployment.md` with a clear Mermaid diagram, explicit environment variable table, and honest acknowledgment of known gaps (no Docker, no static serving, no .vsix). The code correctly implements the topology: PORT and DATABASE_URL are validated at startup, the Express app is properly structured, and the VS Code extension connects via a configurable `server_url`. However, there are three documentation-code discrepancies: (1) `OPENAI_API_KEY` in the design doc vs `AI_INTEGRATIONS_OPENAI_API_KEY` in code, (2) `GITHUB_TOKEN` is required for PR analysis but undocumented, and (3) webhook secret validation is not enforced at startup. These gaps would cause confusion for operators following the deployment guide but do not prevent the system from functioning. The core topology documentation is accurate and complete.
