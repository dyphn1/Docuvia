## Round 1 — Architecture & Design Review

### Design Intent

The design docs explicitly acknowledge that the VS Code extension is fully implemented (source code, package.json, esbuild bundling) but the compiled `.vsix` package is not produced by CI. The extension can be built and packaged manually via `pnpm --filter @workspace/vscode-client run package`, but this step is not automated in the CI pipeline.

The intended flow is:
1. Developer runs `pnpm run package` in the vscode-client package
2. `vsce package --no-dependencies` produces a `.vsix` file
3. `.vsix` can be sideloaded (`code --install-extension`) or published to VS Code Marketplace

### Implementation Analysis

**Extension Manifest (`artifacts/vscode-client/package.json`):**
- ✅ `engines.vscode: "^1.90.0"` — properly declared
- ✅ `publisher: "docuvia"` — publisher identity set
- ✅ `scripts.package: "pnpm run esbuild && vsce package --no-dependencies"` — build+package script exists
- ✅ `@vscode/vsce: "^3.9.2"` in devDependencies — packaging tool installed
- ✅ `scripts.build` uses `tsc --noEmit && tsc -p tsconfig.json --outDir out` — type-check + emit
- ✅ `scripts.esbuild` bundles `src/extension.ts` into `out/main.js` for production

**Extension Entry Point (`artifacts/vscode-client/src/extension.ts`):**
- ✅ 654 lines of well-structured TypeScript
- ✅ Registers all views, commands, tree providers, CodeLens, hover, chat participant
- ✅ Proper activation/deactivation lifecycle
- ✅ Imports from 14+ supporting modules

**CI Workflow (`.github/workflows/ci.yml`):**
- ✅ `lint` job — formatting checks
- ✅ `typecheck-and-build` job — `pnpm run typecheck` + `pnpm -r --if-present run build`
- ✅ `test` job — Vitest with PostgreSQL
- ❌ **No `.vsix` packaging step** — CI never invokes `pnpm run package` in vscode-client
- ❌ **No artifact upload of `.vsix`** — even if built, there's no artifact declaration

**Workspace Configuration (`pnpm-workspace.yaml`):**
- ✅ `artifacts/*` is included in the workspace
- ✅ vscode-client is discoverable by pnpm

### Architecture Assessment

The extension source code is **fully implemented and buildable**. The `package.json` correctly defines a `package` script that bundles via esbuild and packages via vsce. The compiled output (`out/extension.js`) exists in the repo, confirming the build works.

The gap is purely in **CI automation**: the `typecheck-and-build` job runs `pnpm -r --if-present run build`, which invokes the `build` script (tsc typecheck + emit), but does NOT invoke the `package` script (esbuild + vsce package). This means:
- The extension is type-checked in CI
- But the final distributable `.vsix` artifact is never produced in CI

## Round 2 — Code Quality & Security Review

### Violations Found

1. **🟡 MEDIUM — CI does not produce `.vsix` artifact** — The `typecheck-and-build` job in `.github/workflows/ci.yml` runs `pnpm -r --if-present run build` but never invokes `pnpm --filter @workspace/vscode-client run package`. The `.vsix` file is not generated, not uploaded as an artifact, and not available for distribution. This is the core D-02 debt.

2. **🟡 MEDIUM — No CI step to validate `vsce package` succeeds** — Even if the `package` script were added to CI, there's no guarantee it would pass in the CI environment (vsce requires a valid `README.md`, `CHANGELOG.md`, and `LICENSE` in the extension package). The vscode-client directory lacks these files:
   - No `README.md` in `artifacts/vscode-client/`
   - No `CHANGELOG.md` in `artifacts/vscode-client/`
   - No `LICENSE` in `artifacts/vscode-client/`
   - `vsce package` will warn or fail without these.

3. **🟢 LOW — Compiled `out/` directory committed to repo** — `artifacts/vscode-client/out/extension.js` and `artifacts/vscode-client/out/extension.d.ts.map` exist in the repo. This suggests the build was run manually at some point, but these artifacts are not reproducible via CI. This could cause confusion about whether the committed output is up-to-date with source.

4. **🟢 LOW — `package.json` `private: true`** — The extension package is marked `"private": true`, which prevents accidental publishing via `vsce publish`. This is intentional for pre-1.0 development but should be noted.

### Positive Findings

1. ✅ **Extension source is complete** — All 14+ modules are implemented (ChatParticipant, KnowledgeGraphTreeProvider, CodeLensProvider, HoverProvider, TaskRunner, KnowledgeIndexer, etc.)
2. ✅ **Build script is correct** — `pnpm run esbuild && vsce package --no-dependencies` is the standard VS Code extension packaging pattern
3. ✅ **vsce is installed** — `@vscode/vsce@^3.9.2` is in devDependencies and present in lockfile
4. ✅ **esbuild bundling configured** — Properly bundles extension.ts into a single `out/main.js` with minification
5. ✅ **Activation events well-defined** — `onStartupFinished`, `workspaceContains:.docuvia`, specific commands
6. ✅ **Known debt is documented** — D-02 and R-07 explicitly acknowledge this gap

### Test Coverage

No tests are directly relevant for this item — the `.vsix` build script is a CI/infrastructure concern, not a runtime feature. The extension has E2E tests (Playwright) but those test the extension functionality in a VS Code test instance, not the packaging pipeline.

## Recommendations

1. **[MEDIUM] Add CI packaging step** — Add a new job (or step) in `.github/workflows/ci.yml` that runs `pnpm --filter @workspace/vscode-client run package` on the `main` branch only, and uploads the `.vsix` as an artifact:
   ```yaml
   package-vsix:
     name: Package VS Code Extension
     runs-on: ubuntu-latest
     needs: [typecheck-and-build]
     if: github.ref == 'refs/heads/main'
     steps:
       - uses: actions/checkout@v4
       - uses: pnpm/action-setup@v4
       - uses: actions/setup-node@v4
         with: { node-version: "24", cache: "pnpm" }
       - run: pnpm install --frozen-lockfile
       - run: pnpm --filter @workspace/vscode-client run package
       - uses: actions/upload-artifact@v4
         with:
           name: docuvia-vsix
           path: artifacts/vscode-client/*.vsix
   ```

2. **[MEDIUM] Add extension metadata files** — Create `artifacts/vscode-client/README.md` (extension description for Marketplace) and `artifacts/vscode-client/CHANGELOG.md`. These are required for clean `vsce package` execution.

3. **[LOW] Add `out/` to `.gitignore` or remove committed output** — The compiled output should be a CI artifact, not a committed file. Add `artifacts/vscode-client/out/` to `.gitignore` and remove the committed files.

4. **[LOW] Document manual packaging workflow** — Add a section to `docs/design/07-deployment.md` explaining how developers can package the extension locally: `pnpm --filter @workspace/vscode-client run package`

## Overall Verdict

⚠️ **WARN** — The VS Code extension source code is fully implemented (654-line entry point, 14+ supporting modules, proper package.json with `engines.vscode`, esbuild bundling, and vsce packaging script). The `package` script in `artifacts/vscode-client/package.json` correctly defines `pnpm run esbuild && vsce package --no-dependencies`, and `@vscode/vsce` is installed as a devDependency. However, the CI pipeline (`.github/workflows/ci.yml`) never invokes this script — it only runs typecheck and build, skipping the final packaging step. The `.vsix` distributable artifact is never produced, uploaded, or available for sideloading. Additionally, the extension package is missing metadata files (README.md, CHANGELOG.md) that `vsice package` expects. This is a known debt item (D-02, R-07) explicitly documented in `11-risks-and-debt.md`. The extension cannot be distributed via VS Code Marketplace or easily sideloaded without manual developer intervention.
