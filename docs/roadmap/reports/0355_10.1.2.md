## Round 2: Implementation Reality Check

**Question:** Does `.github/workflows/ci.yml` contain a `typecheck-and-build` job that actually runs typecheck and build?

### Evidence Found

**1. `.github/workflows/ci.yml` — `typecheck-and-build` job (lines 48-79)**
- Job name: `Typecheck & Build`
- Runs on: `ubuntu-latest`
- Node.js: `24` (via `actions/setup-node@v4`)
- pnpm: `9` (via `pnpm/action-setup@v4`)
- Steps:
  1. `actions/checkout@v4`
  2. `pnpm/action-setup@v4` (version 9)
  3. `actions/setup-node@v4` (node-version "24", cache "pnpm")
  4. `pnpm install --frozen-lockfile`
  5. `pnpm --filter @workspace/api-spec run codegen` — regenerates Orval types
  6. `pnpm run typecheck` — runs TypeScript type checking across all packages
  7. `pnpm -r --if-present run build` — builds all packages recursively with `NODE_ENV=production`

**2. Root `package.json` scripts (lines 8-10)**
- `"build": "pnpm run typecheck && pnpm -r --if-present run build"` — build includes typecheck
- `"typecheck": "pnpm run typecheck:libs && pnpm -r --filter \"./artifacts/**\" --filter \"./scripts\" --if-present run typecheck"` — covers libs + artifacts + scripts
- `"typecheck:libs": "tsc --build"` — uses TypeScript project references for lib packages

**3. TypeScript project references (`tsconfig.json`)**
- Root `tsconfig.json` extends `./tsconfig.base.json`
- References: `lib/db`, `lib/api-client-react`, `lib/api-zod`, `lib/integrations-openai-ai-server`
- `tsconfig.base.json` sets `"isolatedModules": true`, `"module": "esnext"`, `"moduleResolution": "bundler"`, `"target": "es2022"`

**4. Per-package typecheck scripts**
- `artifacts/api-server/package.json`: `"typecheck": "tsc -p tsconfig.json --noEmit"`
- `artifacts/kg-engine/package.json`: `"typecheck": "tsc -p tsconfig.json --noEmit"`

- `artifacts/ast-core/package.json`: `"typecheck": "tsc --b"`
- `artifacts/mockup-sandbox/package.json`: `"typecheck": "tsc -p tsconfig.json --noEmit"`
- `scripts/package.json`: `"typecheck": "tsc -p tsconfig.json --noEmit"`

## Round 3: Impact & Risk Assessment

### Workflow Completeness

| Criterion | Assessment |
|-----------|-----------|
| Triggers (push + PR to main/dev) | ✅ Correct |
| Concurrency management | ✅ `cancel-in-progress: true` prevents redundant runs |
| Dependency installation | ✅ `--frozen-lockfile` ensures reproducible installs |
| Codegen before typecheck | ✅ Prevents stale generated code from causing type errors |
| Typecheck coverage (libs + artifacts + scripts) | ✅ All package categories covered |
| Build verification (all packages) | ✅ Recursive build with production env |
| Node.js version alignment (prod = CI = 24) | ✅ Matches `02-constraints.md` |
| pnpm version (9.x) | ✅ Aligned with `packageManager: pnpm@9.15.9` |

### Risks

1. **No CI status badge in README (LOW):** The workflow is functional but there's no visual badge showing pass/fail status. This is cosmetic but helpful for contributors.

2. **No caching of build artifacts between jobs (LOW):** The `lint` and `typecheck-and-build` jobs each do their own `pnpm install`. A shared cache or artifact upload would reduce CI time.

3. **No explicit `needs` dependency between jobs (INFO):** The `test` and `typecheck-and-build` jobs run independently. A failing build doesn't block tests from running, which is actually desirable for diagnostic purposes.

4. **Missing `pnpm install` caching within job (LOW):** `actions/setup-node` with `cache: "pnpm"` handles this — ✅ actually fine.
