## Item Description

> Database migrations: push vs migrate strategy

The design doc (`07-deployment.md` §7.5) states under "Deployment Considerations": "Database migrations: Run via compiled JS (`node dist/migrate.js`) in production. (Dev may use `push`)." This checklist item verifies that both the `push` (development) and `migrate` (production) paths are fully implemented, documented, and operationally sound.

## Round 2: Implementation Reality Check

**Question:** Are both the `push` and `migrate` paths fully implemented, and do they produce consistent results?

"push-force": "drizzle-kit push --force --config ./drizzle.config.cjs",

**2. `lib/db/src/migrate.ts` — Production migration runner (83 lines):**

- Acquires PostgreSQL Advisory Lock (ID: `7274813`) before running migrations

**3. `lib/db/drizzle/0000_short_ezekiel.sql` — Initial monolithic migration (250 lines):**
- Creates all 19 tables, enums, indexes, and foreign keys in a single migration file
- This is the "baseline" migration that `migrate.ts` applies

**4. `lib/db/src/migrations/002_add_project_integrations.sql` — Incremental migration:**
- Adds `project_integrations` table and `integration_type` enum
- Demonstrates the migration path handles incremental changes

**5. `lib/db/src/migrations/001_add_l3_node_source_refs.sql` — Suggested migration (not yet converted):**
- Contains a suggested `CREATE TABLE l3_node_source_refs` DDL

- This is a **pending** migration — SQL exists but hasn't been integrated into the migration journal

**6. `lib/db/drizzle/meta/_journal.json` — Migration journal:**
- Only one entry: `0000_short_ezekiel` (the initial migration)
- The `002_add_project_integrations.sql` file exists in `src/migrations/` but is **not registered** in the journal

**7. `lib/db/drizzle.config.cjs` — Drizzle Kit configuration:**

### Gap Analysis

**Gap 1 — `002_add_project_integrations.sql` not registered in journal.**
The file exists at `lib/db/src/migrations/002_add_project_integrations.sql` but is not listed in `drizzle/meta/_journal.json`. This means:
- `migrate.ts` (which reads from `../drizzle` folder) will **not** pick it up — the drizzle migrator only runs SQL files that are in its own `drizzle/` directory AND registered in the journal
- The `002` file is in `src/migrations/` not `drizzle/` — this appears to be a misplacement
- The initial migration (`0000_short_ezekiel.sql`) already includes `project_integrations` table, so the `002` file is redundant — it re-creates the same table

**Gap 2 — `001_add_l3_node_source_refs.sql` is a suggestion, not a real migration.**
The file contains a "suggested" DDL with instructions to "Coordinate with Database Schema Expert to convert into a Drizzle migration." This is an untracked work-in-progress, not a gap in the push/migrate strategy itself.

**Gap 3 — Seed logic location (known issue, D-07).**
The seed of default prompt templates lives in `migrate.ts` (the runner) rather than in a Drizzle migration SQL file. This was flagged in prior reports (5.3.3, non_success_problems_analysis). It works correctly when the `migrate` path is used, but if someone uses `push` + manual seed, templates won't be seeded. This is a known debt item (D-07), not a gap in the push/migrate strategy per se.

## Round 3: Impact & Risk Assessment

### Functional Completeness of the Push/Migrate Strategy

| Criterion | Assessment |
|-----------|-----------|
| Dev can apply schema via `push` | ✅ `pnpm --filter @workspace/db run push` |
| Dev can force-reset schema via `push-force` | ✅ `pnpm --filter @workspace/db run push-force` |
| Prod can apply migrations via `migrate` | ✅ `pnpm --filter @workspace/db run migrate` |
| Migrations are idempotent | ✅ Drizzle migrator tracks applied migrations |
| Concurrent migration safety | ✅ Advisory lock (ID 7274813) |
| Crash safety | ✅ Lock released in `finally` block |
| Seed data on fresh deploy | ✅ `migrate.ts` seeds prompt templates |
| Incremental migrations work | ⚠️ Only initial migration in journal; `002` file misplaced |
| Schema ↔ migration consistency | ✅ `0000_short_ezekiel.sql` matches current schema |

### Risks

1. **Misplaced migration file (LOW):** `002_add_project_integrations.sql` is in `src/migrations/` instead of `drizzle/` and isn't in the journal. Since the initial migration already includes this table, it's a no-op. But the file creates confusion about which migrations are "real."

2. **Seed only runs on `migrate` path (MEDIUM, known D-07):** If a production deploy uses `push` instead of `migrate`, default prompt templates won't be seeded. The generate pipeline has hardcoded fallbacks, so this is not a blocker — but it's an inconsistency.

3. **No `migrate` script for compiled JS (LOW):** The design doc says "Run via compiled JS (`node dist/migrate.js`)" but the actual script runs via `tsx src/migrate.ts` (TypeScript execution without compile step). This is functionally equivalent and arguably better (no build step needed for migrations), but doesn't match the literal design doc wording.

### What Changed Since Design Doc Was Written

The design doc describes `node dist/migrate.js` (compiled output) but the implementation uses `tsx src/migrate.ts` (direct TypeScript execution). This is a minor deviation — the behavior is identical, and the `tsx` approach is more developer-friendly.

## Verdict

### Overall: **PASS** — Both push and migrate paths are fully implemented

The dual-path migration strategy is correctly implemented:
- **Development:** `pnpm --filter @workspace/db run push` (drizzle-kit push) applies schema changes from `src/schema/index.ts`
- **Production:** `pnpm --filter @workspace/db run migrate` runs `migrate.ts` which applies SQL migrations from `drizzle/` folder with advisory lock protection

Both paths are documented in `07-deployment.md` §7.3 and `AGENTS.md`. The advisory lock mechanism in `migrate.ts` demonstrates production-grade operational hygiene.

The gaps identified (misplaced `002` file, seed location) are housekeeping items, not strategy gaps. The core push vs migrate design is sound and correctly implemented.

### Recommended Actions

1. **Remove or relocate `002_add_project_integrations.sql`** — It's redundant (table already in `0000_short_ezekiel.sql`) and misplaced. Either delete it or move it to `drizzle/` and add it to the journal if it represents a real incremental migration.

2. **Update design doc wording** — Change `node dist/migrate.js` to `tsx src/migrate.ts` in `07-deployment.md` §7.5 to reflect the actual implementation.

3. **Address D-07** — Move seed logic from `migrate.ts` into a proper Drizzle migration SQL file so it runs on both push and migrate paths (tracked separately under item 5.3.3).

### Status for Tracking Table

**PASS** — The push vs migrate strategy is fully implemented, documented, and operationally sound.
