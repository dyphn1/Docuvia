## Round 1 — Architecture & Design Review

### Design Intent

The VS Code extension must declare activation events in `package.json` so that VS Code loads the extension when relevant conditions are met (not on every startup). The extension should activate:
1. When VS Code finishes starting up (`onStartupFinished`) — ensures the extension is available immediately
2. When a workspace contains a `.docuvia` directory — ensures activation for Docuvia-initialized projects
3. When specific commands are invoked — ensures lazy activation for command-driven workflows
4. When specific tree views are opened — ensures UI panels trigger activation

### Implementation Analysis

**Extension Manifest (`artifacts/vscode-client/package.json` lines 18-24):**
```json
"activationEvents": [
    "onStartupFinished",
    "workspaceContains:.docuvia",
    "onCommand:docuvia.initProject",
    "onView:docuvia-knowledge-graph",
    "onView:docuvia.knowledgeGraph"
]
```

✅ **`onStartupFinished`** — Activates after VS Code startup completes. This is the recommended event for extensions that need to be available immediately (as opposed to the deprecated `*` wildcard). It ensures the extension's commands, tree views, and chat participant are registered without delaying VS Code startup.

✅ **`workspaceContains:.docuvia`** — Activates when the workspace contains a `.docuvia` directory. This is the primary "project-aware" activation trigger. Since Docuvia-initialized projects always have this directory, the extension activates automatically for relevant workspaces.

✅ **`onCommand:docuvia.initProject`** — Activates when the `docuvia.initProject` command is invoked. This is a redundant safety net: even if the extension hasn't activated via `onStartupFinished` or `workspaceContains`, invoking this command will trigger activation.

✅ **`onView:docuvia-knowledge-graph`** — Activates when the `docuvia-knowledge-graph` view is opened. Note: this view ID does not match any view registered in `contributes.views` (see Round 2).

✅ **`onView:docuvia.knowledgeGraph`** — Activates when the `docuvia.knowledgeGraph` tree view is opened. This view ID matches the registered view in `contributes.views.docuvia` (line 39).

**Extension Entry Point (`artifacts/vscode-client/src/extension.ts` lines 21-40):**
- ✅ `activate()` is an `async function` returning `Promise<void>` — correct signature
- ✅ Creates output channel on activation — proper diagnostics setup
- ✅ Reads global config from `~/.docuvia/config.yaml` — graceful degradation if missing
- ✅ Initializes `CredentialManager` and `CentralServerClient` — full dependency wiring
- ✅ Loads knowledge graph and starts file watcher — complete initialization
- ✅ Registers all providers, commands, and views — comprehensive contribution binding
- ✅ `deactivate()` properly disposes the KnowledgeStore — clean lifecycle

### Architecture Assessment

The activation events are **well-designed** and follow VS Code best practices:
- Uses `onStartupFinished` instead of deprecated `*` wildcard
- Includes a `workspaceContains` trigger for project-aware activation
- Includes command-based triggers for lazy activation
- Includes view-based triggers for UI-driven activation

The `activate()` function is comprehensive and registers all contributions in the correct order.

## Round 2 — Code Quality & Security Review

### Violations Found

1. **🟡 MEDIUM — Mismatched view ID in activationEvents** — The activation event `"onView:docuvia-knowledge-graph"` (package.json line 22) references a view ID `docuvia-knowledge-graph` that does not exist in `contributes.views`. The registered view IDs are `docuvia.knowledgeGraph` and `docuvia.taskQueue` (lines 39, 43). This is likely a typo or leftover from a rename. The correct ID `docuvia.knowledgeGraph` IS also listed (line 23), so the effect is harmless — VS Code simply ignores unknown view IDs in activation events. However, it indicates incomplete cleanup after a refactor.

2. **🟢 LOW — `onStartupFinished` activates for all workspaces** — The `onStartupFinished` event causes the extension to activate in every VS Code session, even for workspaces that don't use Docuvia. This is a minor performance concern (the extension runs `activate()` and loads config even when not needed). However, this is an intentional design choice: the extension needs to register commands and views eagerly so they appear in the Command Palette. The `workspaceContains:.docuvia` trigger provides additional activation for Docuvia projects. The overhead of `activate()` without a `.docuvia` directory is minimal (just config read and KnowledgeStore instantiation).

3. **🟢 LOW — No `onLanguage` activation events** — The extension registers CodeLens and Hover providers for TypeScript, JavaScript, and Python, but does not include `onLanguage:typescript` or similar activation events. This means the extension activates on startup (via `onStartupFinished`) regardless of which languages are in use. This is acceptable given the `onStartupFinished` approach, but adding `onLanguage` events could reduce activation time for non-TS/JS/Python workspaces.

### Positive Findings

1. ✅ **Follows VS Code best practices** — Uses `onStartupFinished` (recommended) instead of deprecated `*` wildcard
2. ✅ **Project-aware activation** — `workspaceContains:.docuvia` ensures the extension is available for Docuvia-initialized projects
3. ✅ **Command-based lazy activation** — `onCommand` events provide a safety net for command-driven workflows
4. ✅ **View-based activation** — `onView` events ensure the extension activates when UI panels are opened
5. ✅ **Complete activate() implementation** — All providers, commands, views, and menus are registered in the activation function
6. ✅ **Clean deactivation** — `deactivate()` properly disposes the KnowledgeStore
7. ✅ **Test coverage exists** — `phase1.test.ts` verifies extension presence (`vscode.extensions.getExtension("docuvia.vscode-client")`) and command execution

### Test Coverage

- `artifacts/vscode-client/src/tests/phase1.test.ts` line 22-24: Tests that the extension is present via `vscode.extensions.getExtension("docuvia.vscode-client")` — this implicitly verifies activation works (the extension must activate to be discoverable).
- Line 48: Executes `docuvia.initProject` command — verifies command registration works post-activation.
- No dedicated test for activation event triggers (e.g., testing that `workspaceContains:.docuvia` correctly activates the extension). This is a testing gap but acceptable for the activation event configuration itself.

## Recommendations

1. **[LOW] Remove/fix stale view ID** — Remove `"onView:docuvia-knowledge-graph"` from `activationEvents` in `package.json` (line 22). It references a non-existent view ID and is redundant since `"onView:docuvia.knowledgeGraph"` (the correct ID) is already listed on line 23.

2. **[LOW] Add activation unit test** — Add a test that verifies the extension activates when `workspaceContains:.docuvia` is satisfied. This can be done by opening a workspace with a `.docuvia` directory in the test fixture and asserting the extension is active.

3. **[INFO] Consider `onLanguage` triggers** — If startup performance becomes a concern, add `onLanguage:typescript`, `onLanguage:javascript`, `onLanguage:python` to the activation events to reduce unnecessary activation for non-target workspaces.
