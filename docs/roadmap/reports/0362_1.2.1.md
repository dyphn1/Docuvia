## Round 1 — Architecture & Design Review

### Design Intent

The design specifies stream-based Git ingestion using `child_process.spawn` (not `execFile`) to avoid buffering large git outputs into memory. The ingestion flow is: clone → stream git log output via readline → fetch diffs per commit → score/filter via `scoreCommit()` → batch insert into commits table. Both full and incremental modes are supported, with the latter using the `lastGitIngestedAt` cursor column on the projects table.

### Implementation Analysis

**`LocalGitClient.clone()` (git-client.ts, line 26-37):**
Uses `execFileAsync("git", ["clone", "--depth=500", ...])`. This is a single-shot operation — acceptable to use `execFile` here since clone output is minimal. Uses a temp directory with UUID for isolation. ✅

**`LocalGitClient.getCommits()` (git-client.ts, line 39-100):**
Uses `spawn("git", args, ...)` with `readline.createInterface({ input: child.stdout })`. This is the correct streaming approach per the design spec. Parses the custom `--format=COMMIT_SEP%n%H%n%s%n%an%n%aI%n%b` format line-by-line. ✅

**`LocalGitClient.getDiff()` (git-client.ts, line 152-181):**
Uses `spawn("git", ["show", "--format=", sha])` with `readline.createInterface`. The comment on line 161-162 explicitly states the reason: "avoiding V8's execFile limits." This matches the design intent. ✅

**`LocalGitClient.getProjectedCommits()` (git-client.ts, line 102-122):**
A new addition since the last verification. Uses `git merge-base HEAD <baseRef>` to find the ancestor of un-indexed commits and scopes `getCommits()` to the revision range `${mergeBase}..HEAD`. This implements the "Diff Projection & Ancestor Anchoring" design pattern from arc42 section 5.3. ✅ **Improvement since last verification.**

**Route handler `POST /projects/:id/ingest/git` (ingest.ts, line 37-102):**
Follows the correct flow: validate → clone → getCommits → getDiff per commit → processIngestion → cleanup. Supports both full and incremental mode. ✅

**OpenAPI spec alignment:**
The `GitIngestInput` schema (openapi.yaml lines 2197-2212) defines `repoUrl`, `branch`, `limit`, `githubToken`, `mode` fields. The route handler's `GitIngestSchema` (ingest.ts lines 25-31) matches this exactly. The `GitIngestResult` schema (openapi.yaml lines 2214-2223) defines `commitsIngested`, `commitsSkipped`, `totalFetched`. The response (ingest.ts lines 90-95) matches. ✅

### Gaps / Observations

1. **Memory concern — all diffs buffered (ingest.ts lines 63-74):** The route handler iterates over all commits and calls `await client.getDiff(c.sha)` for each, accumulating all diffs in the `gitItems` array before passing to `processIngestion`. For the default limit of 100 commits (max 500), this could buffer substantial diff data in memory simultaneously. A streaming/chunked approach would be more memory-efficient.

2. **Redundant `lastGitIngestedAt` updates:** The `lastGitIngestedAt` cursor is updated in two places:
   - `ingest.ts` lines 83-88: In the route handler after `processIngestion` returns (conditional on `mode === "incremental"`)
   - `ingestion-pipeline.ts` lines 104-109: Inside `processIngestion()` for every batch (unconditional — uses `new Date()` not the commit date)

   The pipeline's update (line 104-109) runs unconditionally for every git ingestion, meaning full-mode ingestion also updates the cursor. Additionally, the pipeline uses `new Date()` rather than the actual commit date, which is incorrect — it should use the newest commit's date.

3. **No timeout on spawned processes:** Neither `getCommits` nor `getDiff` set a timeout. A hung `git log` or `git show` process (e.g., on a corrupted repo) would block the request indefinitely.

4. **No stderr capture for `getCommits`:** The `spawn` for `git log` (line 52) only reads stdout via readline. Stderr is not captured, so if git log produces error output (e.g., "fatal: bad object"), the error will go unnoticed until the close handler checks the exit code.

### Verdict for Round 1

The architecture is fundamentally sound and matches the design spec. The `spawn` + `readline` pattern is correctly used for streaming. A new `getProjectedCommits()` method has been added since the last verification, improving the ancestor-anchoring capability. The main gaps remain: (a) memory concern from buffering all diffs, (b) redundant/incorrect cursor updates, (c) no process timeout, and (d) missing stderr capture.

## Round 2 — Code Quality & Security Review

### Code Quality

**Strengths:**

- **Clean separation of concerns:** `LocalGitClient` handles Git CLI interactions; `ingest.ts` handles HTTP concerns; `ingestion-pipeline.ts` handles DB operations; `commit-scorer.ts` handles scoring.
- **Proper cleanup:** `client.cleanup()` is called in a `finally` block (ingest.ts line 100), ensuring temp directories are removed even on error.
- **Batch processing:** `processIngestion` processes commits in batches of 50 (ingestion-pipeline.ts line 66), preventing unbounded memory/CPU spikes.
- **Input validation:** The route uses Zod schema validation (`GitIngestSchema.parse`) on the request body.
- **Length limits:** Message text is sliced to 4000 chars (ingestion-pipeline.ts line 95), and the limit parameter is capped at 500 (ingest.ts line 46).
- **New `getProjectedCommits()` method:** Clean implementation of the merge-base lookup pattern with proper error handling and fallback.

**Issues / Code Smells:**

1. **🟡 Medium — Noise commits are ingested, not filtered:** `scoreCommit()` returns `{ valid: false, score: 0.1 }` for noise patterns (merge commits, version bumps, etc.), but `processIngestion` at ingestion-pipeline.ts line 92 still inserts the commit with `valid: false`. The design (arc42 section 4.2) describes `scoreCommit` as a "signal/noise filter," suggesting noise commits should be skipped entirely rather than stored with a `valid=false` flag. Currently, noise commits consume DB space and require filtering at query time.

2. **🟡 Medium — Silent diff failure:** `getDiff()` (git-client.ts lines 168-179) resolves with an empty string `""` on both non-zero exit codes and error events. While this prevents a single failed diff from aborting the entire ingestion, it means commits will be ingested with empty diffs without any warning logged at a visible level. The `logger.warn` calls are present but the ingestion pipeline has no way to distinguish an empty diff due to failure vs. genuinely empty.

3. **🟡 Medium — `lastGitIngestedAt` uses `new Date()` instead of commit date:** In `processIngestion` (ingestion-pipeline.ts line 108), the cursor is set to `new Date()` rather than the newest commit's actual date. This means the incremental cursor wall-clock time may not match the commit timeline, potentially causing missed or re-ingested commits if the system clock and git commit dates diverge.

4. **🟢 Low — `getCommits` mixes async iteration with Promise wrapping:** The method uses `for await (const line of rl)` (async iteration over readline) but then wraps the `close` handler in a `new Promise()` (git-client.ts lines 93-99). This "async iteration + Promise constructor" mixing works but is a known anti-pattern.

5. **🟢 Low — `getDiff` uses readline for binary-safe data:** `git show` can contain binary diff content. Using `readline.createInterface` (git-client.ts line 157) splits on newlines, which could corrupt binary content. For commit ingestion this is likely acceptable (diffs are text), but it's a latent issue.

6. **🟢 Low — Dead code: error handler resolves instead of rejecting:** In `getDiff`, the `error` handler on lines 176-179 calls `resolve("")` instead of `reject(e)`. This means spawn errors (e.g., git not found) are silently swallowed and the diff will be empty.

7. **🟢 Low — `getCurrentBranchName()` and `getModifiedFiles()` are unused exports:** `LocalGitClient.getCurrentBranchName()` and `getModifiedFiles()` exist as public methods but are not called from any route handler or pipeline. They may be intended for future use or testing but currently represent dead code.

### Security

1. **🟡 Medium — `repoUrl` passed directly to `git clone`:** The `repoUrl` from the request body (or project record) is passed directly to `execFileAsync("git", ["clone", ..., repoUrl])` without URL validation. While `execFile` (not `exec`) mitigates shell injection by passing arguments directly without shell interpretation, a malformed URL could still cause unintended behavior (e.g., cloning an unintended repository, or passing arbitrary git flags via a crafted URL). The route handler only checks `repoUrl` is truthy (ingest.ts line 48).

2. **🟢 Low — No authentication for the ingest endpoint:** The `POST /projects/:id/ingest/git` endpoint doesn't require authentication. Any client can trigger git ingestion for any project, potentially causing resource exhaustion (cloning large repos). This may be intentional for a local/dev setup but is a concern for production.

3. **🟢 Low — `githubToken` accepted but never used:** The `GitIngestSchema` accepts a `githubToken` field (ingest.ts line 29), and the OpenAPI spec documents it, but the token is never passed to `LocalGitClient.clone()` or used for authentication. This is either dead functionality or an incomplete feature.

### Verdict for Round 2

The code is well-structured and follows the project's conventions. The main concerns are: noise commits being stored rather than skipped, silent diff failures, the `lastGitIngestedAt` cursor using `new Date()` instead of actual commit dates, and the unused `githubToken` parameter. No critical security vulnerabilities given `execFile` (not `exec`) is used. Two new minor unused methods (`getCurrentBranchName`, `getModifiedFiles`) have been added since last verification.

- The `projects` table has `lastGitIngestedAt` cursor column ✅

**OpenAPI / Zod alignment:**

- The `GitIngestResult` schema matches the response format ✅
- The `IngestStatusResponse` schema includes `lastGitIngestedAt` and `pendingCommits` ✅

**Factory support:**

- `factories.ts` supports creating commit records for testing (though no git-specific ingestion tests exist)

### Test Coverage Assessment

**What's covered:**

- ✅ Core DB schema and migrations exist for all required tables
- ✅ `scoreCommit()` function is implemented and can be unit tested (pure function, no side effects)
- ✅ Integration test infrastructure (`withRollback`, MSW) is available

**What's NOT covered (gaps):**

- ❌ **No tests for `LocalGitClient`:** No unit or integration tests verify that git log parsing, diff fetching, or clone/cleanup work correctly
- ❌ **No tests for the `POST /projects/:id/ingest/git` endpoint:** No integration test creates a project, triggers git ingestion, and asserts the response
- ❌ **No tests for incremental ingestion:** The incremental mode (using `lastGitIngestedAt` cursor) is completely untested
- ❌ **No tests for `scoreCommit()` behavior in the pipeline:** While `scoreCommit` can be unit tested, there's no test verifying that noise commits receive `valid=false` or that the scoring affects ingestion behavior
- ❌ **No mock for `child_process.spawn`:** Unlike external HTTP APIs (mocked via MSW), there's no test fixture mocking git CLI output
- ❌ **No tests for `getProjectedCommits()`:** The new merge-base lookup logic is untested

### Performance

- The `spawn` + `readline` approach is efficient for streaming ✅
- Batch size of 50 in `processIngestion` prevents unbounded memory spikes ✅
- The `getDiff` calls are sequential (ingest.ts line 63: `for...of` with `await`), which is safe but slow for large commit counts. Parallel diff fetching with a concurrency limit could improve throughput.
- The quality requirement specifies "1000 commits < 30s" — the current sequential diff fetching likely won't meet this target for large repos, as each `git show` call involves process spawn overhead (~10-50ms per spawn).

### Verdict for Round 3

The feature integrates correctly with the DB schema, OpenAPI spec, and pipeline architecture. A new `getProjectedCommits()` method improves ancestor-anchoring support. The primary gap is the complete absence of tests for the git ingestion path. Performance may be a concern for large repos due to sequential diff fetching and multiple process spawns.

## Recommendations

1. **Skip noise commits entirely** during ingestion rather than storing them with `valid=false`. If storage is desired for audit purposes, add a separate `isNoise` boolean or filter at the DB query level. (Addresses finding #1)

2. **Fix `lastGitIngestedAt` update:** Remove the unconditional update from `processIngestion` (ingestion-pipeline.ts:104-109) and pass the actual commit date from the route handler. The cursor should use the newest commit's authored date, not `new Date()`. (Addresses finding #2)

3. **Add integration tests for git ingestion:** Create a test that clones a small test repository (or mocks `child_process.spawn` output) and verifies the full ingestion flow including incremental mode and `getProjectedCommits()`. (Addresses finding #3)

4. **Stream diffs in batches** instead of buffering all diffs: process each batch of commits (with their diffs) through `processIngestion` immediately, then fetch the next batch. (Addresses finding #4)

5. **Implement or remove `githubToken`:** Either wire up the token for authenticated clone operations (especially for private repos) or remove it from the schema to avoid confusion. (Addresses finding #5)

6. **Add a timeout option** to spawned git processes and reject on timeout. (Addresses finding #8)

7. **Capture stderr** in `getCommits` and include it in error messages for better debuggability. (Addresses finding #7)

8. **Consider parallel diff fetching** with a concurrency limit (e.g., 5-10 concurrent `git show` processes) to improve throughput for large repos. (Addresses finding #10)

## Overall Verdict

**⚠️ WARN** — The Git ingestion feature is functionally implemented and correctly uses `child_process.spawn` with `readline` for streaming, matching the design specification. The OpenAPI contract is properly defined and aligned with the route handler. Since the last verification (2026-06-16), a new `getProjectedCommits()` method has been added that correctly implements the merge-base ancestor anchoring pattern. However, the core issues from the previous verification persist: (1) noise commits are stored rather than filtered, (2) the `lastGitIngestedAt` cursor has a redundant and incorrect update path (uses `new Date()` instead of commit date), (3) there are zero tests for the entire git ingestion path, (4) memory usage could be problematic for large ingestions due to full diff buffering, and (5) the `githubToken` parameter is accepted but never used. The issues are addressable and do not require architectural changes.
