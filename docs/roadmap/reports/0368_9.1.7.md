## Round 1 — Architecture & Design Review

### Design Intent

Per `08-crosscutting-concepts.md` and `10-quality-requirements.md`, the API server must:

1. Enforce rate limits on all public API endpoints to prevent abuse
2. Apply stricter limits to LLM-heavy endpoints (MCP, search) to prevent cost overruns
3. Return standard `RateLimit-*` headers so clients can self-regulate
4. Use IP-based tracking as the rate limit key

### Implementation Analysis

**Rate Limiter Module** (`rate-limit.ts`):

```typescript
import rateLimit from "express-rate-limit";

export const standardLimiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15 minutes
  max: 500, // Limit each IP to 500 requests per windowMs
  message: { error: "Too many requests from this IP, please try again later." },
  standardHeaders: true,
  legacyHeaders: false,
});

export const mcpLimiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15 minutes
  max: 100, // Limit each IP to 100 requests per windowMs
  message: { error: "Too many MCP or Search requests. Rate limit exceeded." },
  standardHeaders: true,
  legacyHeaders: false,
});
```

**Route Application** (`routes/index.ts`):

```typescript
// Apply standard rate limiter to all routes by default
router.use(standardLimiter);

// Specific limiters can be applied by the individual routers or overriding below
router.use("/mcp", mcpLimiter);
router.use("/search", mcpLimiter);
```

**App Middleware Chain** (`app.ts`):

```
pinoHttp → cors → github webhooks (raw body) → proxy → express.json → express.urlencoded → /api router
```

### Architecture Assessment

The rate limiting architecture is **functional and well-structured** but has notable gaps:

**Strengths:**
1. ✅ **Two-tier rate limiting** — Standard (500 req/15min) and MCP (100 req/15min) tiers correctly differentiate between lightweight reads and expensive LLM operations
2. ✅ **Standard headers enabled** — `RateLimit-*` headers are returned, enabling client-side rate limit awareness
3. ✅ **Legacy headers disabled** — `X-RateLimit-*` headers are turned off, correctly migrating to the modern standard
4. ✅ **Applied at the correct middleware layer** — Rate limiters are applied at the router level (`routes/index.ts`), after CORS and body parsing but before route handlers
5. ✅ **MCP and search share the stricter limiter** — Both `/mcp` and `/search` routes use the cost-prevention tier, which is appropriate since both trigger LLM calls
6. ✅ **Client-side retry logic exists** — `batch/utils.ts` has `isRateLimitError()` detection with automatic retry, providing end-to-end rate limit handling

**Weaknesses:**
1. 🟡 **No `trust proxy` configuration** — The Express app does not set `app.set('trust proxy', ...)`. When deployed behind a reverse proxy (nginx, AWS ALB, etc.), `req.ip` will always be the proxy's IP (typically `127.0.0.1`), causing all clients to share the same rate limit bucket. This effectively disables rate limiting in any production deployment behind a proxy.
2. 🟡 **No custom keyGenerator** — The default IP-based key is used. For multi-tenant deployments, there's no way to differentiate rate limits per API key or per project.
3. 🟡 **No rate limit bypass for authenticated admin routes** — Routes like `/admin/metabolism-tick` are rate-limited by IP, which could block legitimate admin operations if they originate from the same IP as normal traffic.
4. 🟢 **No `skip` condition** — There's no mechanism to exempt health checks or internal calls from rate limiting.
5. 🟢 **No `handler` override** — The default express-rate-limit handler is used. No custom logging or alerting when rate limits are hit.

## Round 2 — Code Quality & Security Review

### Security Findings

1. **🟡 MEDIUM — No `trust proxy` configuration** (`app.ts`):
   - Express's `req.ip` reads from `X-Forwarded-For` only when `trust proxy` is configured
   - Without it, all traffic behind a reverse proxy appears to come from the same IP
   - **Impact**: Rate limiting is ineffective in production deployments behind a load balancer or reverse proxy
   - **Severity**: Medium — only affects proxied deployments; direct connections work correctly
   - **Fix**: Add `app.set('trust proxy', 1)` after the `const app` declaration, or configure based on environment

2. **🟡 MEDIUM — No rate limit event logging** (`rate-limit.ts`):
   - When a client exceeds the rate limit, the default handler returns 429 with the message but does not log the event
   - **Impact**: No observability into rate limit violations; cannot detect abuse patterns or identify misbehaving clients
   - **Severity**: Medium — operational blind spot, not a direct security vulnerability
   - **Fix**: Add a custom `handler` that logs the IP, path, and timestamp:
     ```typescript
     handler: (req, res) => {
       logger.warn({ ip: req.ip, path: req.path }, "Rate limit exceeded");
       res.status(429).json({ error: "Too many requests" });
     }
     ```

3. **🟢 LOW — Rate limit values may need tuning** (`rate-limit.ts`):
   - Standard: 500 requests per 15 minutes = ~33 req/min
   - MCP: 100 requests per 15 minutes = ~6.7 req/min
   - For a developer tool with bursty usage patterns (e.g., triggering a generate pipeline), the MCP limit may be too aggressive
   - **Impact**: Legitimate power users may hit the MCP limit during normal usage
   - **Severity**: Low — this is a tuning concern, not a security issue

4. **🟢 LOW — No CORS interaction with rate limiting**:
   - Rate limiting is applied before CORS headers are set (CORS middleware is in `app.ts`, rate limiting in `routes/index.ts`)
   - This means a cross-origin attacker and a same-origin user share the same rate limit bucket
   - **Impact**: Minimal — the rate limit is per-IP regardless of origin

### Code Quality Findings

5. **✅ Clean module structure**: The `rate-limit.ts` module is concise and well-organized. Two clearly named exports with descriptive comments.

6. **✅ Correct middleware ordering**: The standard limiter is applied globally at the router level, then overridden with the stricter limiter for specific paths. This follows the express-rate-limit best practice.

7. **✅ Client retry logic**: The `batch/utils.ts` module correctly detects rate limit errors and retries with backoff, providing resilience on the client side.

8. **🟡 MEDIUM — Generate route has hardcoded sleep** (`generate.ts:157`):
   - A 500ms sleep is added after each LLM call to "prevent rate limit"
   - This is a crude throttle, not a rate limit — it slows down legitimate usage without preventing abuse from clients that don't respect it
   - **Impact**: Adds unnecessary latency to the generate pipeline; does not replace proper rate limiting

### Test Coverage

No tests exist for rate limiting. The test suite does not verify:
- Rate limit enforcement (429 status after exceeding max)
- Rate limit headers (`RateLimit-*` presence and correctness)
- Different behavior between standard and MCP tiers
- Rate limit behavior behind a reverse proxy (`X-Forwarded-For` handling)

🟡 **Medium**: Rate limiting is a security control with no test coverage. While the implementation delegates to a well-tested library (`express-rate-limit`), the integration (correct tier application, proxy handling) is untested.

### Missing Features / Gaps

1. **No `trust proxy` configuration**: In production deployments behind nginx, AWS ALB, Cloudflare, or any reverse proxy, `req.ip` will always be the proxy's IP address. All clients share the same rate limit bucket, effectively disabling rate limiting.

2. **No rate limit event logging**: When a client is rate-limited, no log entry is created. This prevents security monitoring, abuse detection, and incident response.

3. **No per-API-key rate limiting**: The system uses IP-based keys only. For deployments with multiple users behind a corporate NAT, all users share one rate limit. Conversely, a single attacker using multiple IPs can bypass the limit.

4. **No rate limit response headers on CORS preflight**: The CORS middleware in `app.ts` does not explicitly handle OPTIONS preflight requests. Some browsers may not include rate limit headers in preflight responses.

5. **Hardcoded sleep in generate pipeline**: The 500ms sleep in `generate.ts:157` is a workaround, not a solution. It adds latency without providing actual rate limit protection.

## Recommendations

1. **[MEDIUM] Configure `trust proxy`**: Add `app.set('trust proxy', 1)` to `app.ts` after the `const app` declaration. For multi-proxy deployments, use `app.set('trust proxy', 'loopback')` or specify the number of proxy hops. This ensures `req.ip` correctly reads `X-Forwarded-For`.

2. **[MEDIUM] Add rate limit event logging**: Override the default handler in both limiters to log rate limit violations:
   ```typescript
   handler: (req, res) => {
     logger.warn({ ip: req.ip, path: req.path, method: req.method }, "Rate limit exceeded");
     res.status(429).json({ error: "Too many requests from this IP, please try again later." });
   }
   ```

3. **[MEDIUM] Add integration tests for rate limiting**:
   - Test that the 4th consecutive request to an MCP endpoint within the window returns 429
   - Test that `RateLimit-*` headers are present in responses
   - Test that standard and MCP tiers have different limits
   - Test with `X-Forwarded-For` header to verify proxy-aware IP detection

4. **[LOW] Replace hardcoded sleep with proper backoff**: The 500ms sleep in `generate.ts:157` should be replaced with exponential backoff based on the `Retry-After` header from 429 responses, or removed entirely if rate limiting is properly enforced at the middleware layer.

5. **[LOW] Consider per-API-key rate limiting**: For future iterations, consider adding an optional API key header and using it as a secondary rate limit key for authenticated users.

## Overall Verdict

⚠️ **WARN** — The rate limiting implementation is architecturally sound with a well-designed two-tier strategy (standard 500 req/15min, MCP 100 req/15min) using the industry-standard `express-rate-limit` library. The code is clean, correctly structured, and properly applied at the middleware layer. Client-side retry logic with rate limit detection provides additional resilience.

However, there is a **critical deployment gap**: the absence of `trust proxy` configuration means rate limiting is effectively non-functional in any production deployment behind a reverse proxy (which is the documented deployment topology in `07-deployment.md`). Without this configuration, all clients appear to come from the same IP and share a single rate limit bucket, completely defeating the purpose of per-IP rate limiting.

Additionally, the lack of rate limit event logging creates a security observability gap — there is no way to detect or respond to abuse patterns. The absence of test coverage for this security control means regressions would go unnoticed.

The implementation is correct for development and direct-connection scenarios but requires `trust proxy` configuration before it can protect a production deployment.
