## Round 1 — Architecture & Design Review

### Design ↔ Implementation Alignment

**✅ Correctly implemented:**

1. **Isomorphic WASM Parsing** — `web-tree-sitter` is used across both API server (`ast-worker.ts`) and VS Code client (`ast.worker.ts`). The `generateAst()` function in `parser-core.ts` provides a unified async generator interface.

2. **Language Provider Interface** — `LanguageProvider` interface in `language-provider.ts` defines `extractClasses`, `extractFunctions`, `extractImports`, `extractCalls`. `DefaultProvider` implements it with tree-sitter Query API support. Architecture supports custom plugins.

3. **Config-Driven Grammars** — `LanguageRegistry.loadFromString()` accepts TOML config and merges with defaults. 12 languages built-in (TS, JS, Python, Rust, Go, Java, C, C++, Ruby, PHP, C#).

4. **Scope-Resolved Ingestion (FQN)** — `buildScopeMap()` in both `parser-core.ts` and `ast-worker.ts` resolves import statements to Fully Qualified Names (e.g., `moduleA::init`). Handles named imports, wildcards, default imports, and language-specific patterns.

5. **Call Classification** — `classifyCall()` distinguishes method calls vs function calls across 10+ languages, enabling proper FQN resolution for inter-module dependency edges.

6. **Worker Pool (Piscina)** — `AstWorkerPool` uses Piscina for parallel parsing with configurable thread count (`maxThreads = cpus - 1`).

7. **Quarantine Mechanism** — Files that cause worker crashes/timeouts are quarantined in SQLite (`quarantine-db.ts`), preventing endless retries.

8. **Ingestion Pipeline** — `ast-ingestion-pipeline.ts` maps AST events to L2 nodes (modules), L3 nodes (classes/functions), and node_links (depends_on edges) with deduplication.

9. **IPC Sink for VS Code** — `IpcSqliteSink` batches events and posts them to the host extension via `postMessage`.

10. **Resource Cleanup** — `generateAst()` uses `try/finally` to ensure `tree.delete()`, `parser.delete()`, and `provider.deleteQueries()` are called.

### Gaps / Deviations

1. **❌ No `git diff-tree -M` fast-path (ADR-022 §2)** — The design specifies O(1) incremental computation using `git diff-tree -M` as the primary fast-path delta calculator. No implementation exists. The current pipeline processes all files in a batch without delta detection.

2. **❌ No `fast-glob` + `xxhash` graceful degradation (ADR-022 §2)** — For workspaces without `.git`, the design specifies fallback to `fast-glob` + `xxhash` content fingerprints. Not implemented.

3. **⚠️ No Strict ACK Protocol / Bounded Job Dispatch (ADR-022 §3)** — The design specifies "Strict ACK Protocol / Bounded Job Dispatch (max 100 in-flight jobs)." The implementation uses `p-limit` with `maxInFlight = 100` in `ast-worker-pool.ts`, which bounds concurrency but does not implement the ACK protocol or coordinate with the worker's completion signal. The Piscina queue handles job dispatch, but backpressure from the database writer is not wired.

4. **⚠️ .jsonl Spool Files Partially Implemented (ADR-022 §3)** — Workers do write AST skeletons to temporary `.jsonl` files (`ast-worker.ts` line 557-560), but the ingestion pipeline reads these files sequentially. There is no streaming bulk-insert — each event is processed individually with DB round-trips.

5. **⚠️ No Size Limits (ADR-022 §3 — Fault Tolerance)** — The design specifies "Size Limits (e.g., skip >1MB or *.min.js)" as a fault tolerance layer. The `ParsingFunnel` only checks for binary NUL bytes. No file size limit or minified file filter exists.

6. **⚠️ Poison Pill Quarantine Timing (ADR-022 §3)** — Design specifies "Kill worker at 500ms." The implementation uses a 500ms timeout (`ast-worker-pool.ts` line 37), which is correct. However, the quarantine is in-memory SQLite (`DatabaseSync`), meaning it resets on server restart. The design implies "permanent SQLite blacklist."

7. **⚠️ No `languages.toml` in repo** — The code supports loading a `languages.toml` for custom grammar configuration, but no template or default file exists in the repository. Users must discover the format from source code.

8. **⚠️ Cross-Language / Polyglot Edges (ADR-022 §SRE)** — The design specifies API Contracts (OpenAPI/Swagger) as Bridge Nodes and framework-specific AST tracking (tRPC, Next.js Server Actions). No implementation exists for cross-language edge detection.

9. **⚠️ Node Identity & UUID Stability (ADR-022 §SRE)** — Design specifies FQN (`src/auth.ts::login`) and rename tracking via `git diff-tree -M`. FQN resolution is implemented locally per-file, but rename tracking across commits is not wired.

## Round 2 — Code Quality & Security Review

### Strengths

1. **Clean separation of concerns** — `ast-core` is a pure library with no DB or I/O dependencies (except `web-tree-sitter` and `smol-toml`). The API server and VS Code client both depend on it, ensuring true isomorphic execution.

2. **Comprehensive multi-language support** — 12 languages with tree-sitter Query API queries, fallback to `descendantsOfType` for resilience if queries fail.

3. **Robust error handling in workers** — Quarantine on crash/timeout, graceful WASM load failure with `console.warn` and fallback.

4. **Memory-conscious design** — `.jsonl` spool files prevent IPC OOM. `IpcSqliteSink` batches events (batchSize=100) to reduce IPC overhead.

5. **Type safety** — Full TypeScript with strict interfaces (`AstEvent`, `AstSink`, `LanguageProvider`, `ParseResult`).

6. **Resource cleanup** — `try/finally` blocks ensure tree/parser/query resources are released.

### Issues Found

1. **⚠️ `any` types in ast-worker.ts** — `buildScopeMap(importStatements: any[])` and `classifyCall(callNode: any)` use `any` instead of typed `Node`. This bypasses TypeScript's safety net for tree-sitter node access.

2. **⚠️ `node:sqlite` dependency (quarantine-db.ts)** — Uses `node:sqlite` which is a Node.js 22.5+ experimental API. Requires `--experimental-sqlite` flag in Node.js <24. Node.js 24 (per AGENTS.md) supports it natively, but this is a hard dependency on a specific Node version feature.

3. **⚠️ `DatabaseSync` blocks the event loop** — The quarantine DB uses synchronous SQLite (`DatabaseSync`). In a high-throughput ingestion scenario, this could block the event loop during quarantine checks.

4. **⚠️ No input validation on file paths** — `ast-worker.ts` reads `filePath` directly from dispatch. A path traversal in `filePath` (from untrusted input) could read arbitrary files. In practice, file paths come from the project's own file walker, so risk is low.

5. **⚠️ `LanguageRegistry.load()` is a stub** — The async `load()` method just returns `new LanguageRegistry(DEFAULT_REGISTRY)` without reading any TOML file from disk. The `loadFromString()` method exists but is never called by the API server. The `languages.toml` loading path is effectively dead code in production.

6. **⚠️ Duplicate `buildScopeMap` and `classifyCall`** — These functions are fully duplicated between `parser-core.ts` (ast-core) and `ast-worker.ts` (api-server). This creates a maintenance burden and risks divergence.

7. **⚠️ Missing `tree-sitter-wasms` dependency** — The `ast-worker.ts` tries to resolve WASM from `tree-sitter-wasms` package, but this is not listed in `ast-core`'s `package.json` dependencies. Only `web-tree-sitter` is listed. The fallback to individual language packages works, but the primary path may fail.

## Round 3 — Integration & Completeness Review

### Integration Correctness

1. **End-to-end flow (API server):** File batch → `AstWorkerPool.dispatch()` → `ast-worker.ts:parseAst()` → `.jsonl` temp file → `ast-ingestion-pipeline.ts:ingestAstBatch()` → L2/L3 nodes + links in PostgreSQL. The pipeline is wired correctly with proper event sequencing.

2. **End-to-end flow (VS Code):** Extension → `ast.worker.ts` (worker thread) → `generateAst()` → `IpcSqliteSink` → IPC → extension host. The worker correctly uses `postMessage` for events and completion signals.

3. **Database integration:** The ingestion pipeline uses Drizzle ORM with proper insert/returning patterns and `onConflictDoNothing()` for link deduplication.

4. **Activity logging:** The pipeline logs AST ingestion results to `activityLogTable`.

### Missing Coverage

1. **🔴 Incremental/delta ingestion** — The most significant gap. Without `git diff-tree`, the system must re-parse all files on every ingestion run. For large repos, this is prohibitively expensive and contradicts the "Sub-second Incremental Updates" design goal.

2. **🔴 Cross-language dependency edges** — The design's polyglot edge detection (API contracts, framework-specific tracking) is entirely missing. Currently only intra-file call resolution exists (via scope map), and inter-file resolution is limited to matching callee names against L2 node basenames.

3. **🟡 No streaming bulk-insert** — Each L2/L3 node and link is inserted individually. For large codebases (10K+ files), this will be extremely slow. The design explicitly mentions "bulk-insert operations."

4. **🟡 Worker thread isolation** — The VS Code worker (`ast.worker.ts`) uses `addEventListener("message")` on `globalThis`, which is the standard worker pattern. However, there is no message type validation beyond `type === "parse"`, and no authentication on the IPC channel.

5. **🟡 No progress reporting** — For large ingestions, there is no mechanism to report progress to the user. The `AstWorkerPool.dispatch()` fires-and-forgets with `Promise.all`.

## Overall Verdict

**⚠️ WARN**

The AST Microkernel has a solid architectural foundation: the core parsing engine (`ast-core`) is well-designed, truly isomorphic across API server and VS Code client, and implements the key design goals of scope-resolved FQN extraction, multi-language support via tree-sitter queries, and proper resource cleanup. The ingestion pipeline correctly maps AST events to the knowledge graph (L2/L3 nodes + links).

However, the implementation is incomplete relative to ADR-022's specification. The most critical gaps are the **incremental ingestion fast-path** (`git diff-tree`) and **cross-language polyglot edges**, both of which are core design pillars. Without delta ingestion, the system cannot scale to large repositories. Additionally, the `LanguageRegistry.load()` stub means the config-driven grammar system (`.toml` customization) is non-production-ready, and the missing size limits create OOM risk on generated/minified files.

The codebase is functional for first-pass full ingestion of small-to-medium projects but requires the incremental path and bulk-insert optimization before it can be considered production-ready for the Phase 4 milestones (4.2–4.7) that depend on it.
