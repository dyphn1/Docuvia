## Round 1 — Architecture & Design Review

### Design ↔ Implementation Alignment

**✅ Correctly implemented:**

1. **DB-backed queue pattern** — Pending tasks are queried from PostgreSQL (`l3NodesTable`, `correction_examplesTable`) with status flags, not stored in memory
2. **Micro-batching** — Distillation job uses `.limit(10)` for chunked processing (line 104)
3. **Admin endpoint auth** — `/admin/metabolism-tick` correctly validates against `ADMIN_SECRET_TOKEN` with fail-closed behavior in production
4. **Error handling** — Both endpoints wrap `runMetabolism()` in try/catch with proper logging
5. **Conditional L3 promotion** — Merge gate fallback correctly checks `checkCommitInDefaultBranch` before promoting L3 nodes

### Gaps / Deviations

1. **❌ Fake in-memory mutex** — Line 17: `let isMetabolismRunning = false` is a single-process boolean. ADR-008 §2 line 36 explicitly requires "distributed Postgres job queue using `FOR UPDATE SKIP LOCKED` combined with a `locked_at` timestamp." The implementation provides zero distributed coordination.

2. **❌ No `FOR UPDATE SKIP LOCKED`** — The pending L3 node query (lines 28-43) has no row-level locking. Multiple concurrent metabolism ticks can select and process the same rows, causing duplicate L3 promotions and wasted GitHub API calls.

3. **❌ No `locked_at` timestamp** — ADR-008 specifies a `locked_at` field for zombie-reaper recovery. No such field exists. If a metabolism tick crashes mid-flight, stale locks persist indefinitely with no recovery mechanism.

4. **❌ No optimistic locking for pipeline state** — ADR-008 §4 specifies "conditional `UPDATE` statements (`WHERE status = 'active'`)" with `0 rows affected` detection. No such pattern exists in the codebase.

5. **❌ Unauthenticated `/metabolism-tick` endpoint** — Line 164: The primary tick endpoint has NO authentication. Anyone can trigger background work (LLM calls, GitHub API calls). The ADR implies the tick should be triggered only by the VS Code client heartbeat or admin cron. The admin endpoint has auth but the operational endpoint does not.

6. **❌ No Dead Letter Queue** — ADR-008 §Verifiability requires DLQ routing with 3 retries → `DEAD_LETER_FILE`. No DLQ logic exists in the current implementation. The `runMetabolism()` function has no retry counting or failure escalation.

7. **❌ Source code TODO acknowledges the gap** — Line 15: `// TODO: [CRITICAL BUG FIX] - Mutex is fake. Replace this single-instance in-memory Mutex with Postgres FOR UPDATE SKIP LOCKED.` This has been known and unaddressed.

## Round 2 — Code Quality & Security Review

### Strengths

1. **Fail-closed admin auth** — The admin endpoint correctly falls back to dev-only mode only when `NODE_ENV === 'development'`, and fails closed (500) otherwise
2. **Structured logging** — All operations use `logger.info/error` with contextual metadata (counts, IDs, errors)
3. **Graceful error handling per item** — The merge gate loop catches errors per-commit (line 79-81) and per-correction (line 144-146), preventing one failure from aborting the entire batch
4. **Token source flexibility** — Admin endpoint accepts both `Authorization: Bearer` header and `admin_token` query param

### Issues Found

1. **❌ CRITICAL: Unauthenticated background work endpoint** — `/metabolism-tick` triggers LLM API calls and GitHub API calls without any auth. An attacker can:
   - Exhaust LLM API budget by repeated calls
   - Trigger GitHub API rate limiting by scanning commits
   - Cause duplicate processing of pending nodes

2. **❌ CRITICAL: Race condition on `isMetabolismRunning`** — The check-then-set pattern (lines 165-170) is not atomic. Two concurrent requests can both read `isMetabolismRunning = false` and both proceed to execute `runMetabolism()`, causing:
   - Duplicate L3 node promotions
   - Duplicate LLM distillation calls
   - Wasted GitHub API quota

3. **⚠️ Type safety issue** — Line 112: `const promptsToInsert: any[] = []` bypasses TypeScript type safety. Should use `typeof promptTemplatesTable.$inferInsert` or the proper Drizzle type.

4. **⚠️ Hardcoded model name** — Line 118: `model: "gpt-4o-mini"` is hardcoded. Should reference `llm_configsTable` for per-project model switching (which the checklist marks as ✅ Done).

5. **⚠️ No request timeout** — The metabolism tick can run indefinitely if there are many pending tasks. No timeout or circuit breaker exists.

6. **⚠️ `GITHUB_TOKEN` from env without fallback** — Line 65: `process.env.GITHUB_TOKEN` can be undefined. The `checkCommitInDefaultBranch` function receives `undefined` as the token, which may cause runtime errors for projects using private repos.

## Round 3 — Integration & Completeness Review

### Integration Correctness

1. **DB-as-IPC pattern is correct** — Pending tasks are stored in PostgreSQL, and the metabolism worker queries them. The pattern is sound; the execution lacks distributed coordination.
2. **Merge gate fallback works** — The L3 promotion logic correctly groups nodes by project, extracts repo URL, and checks merge status via GitHub API.
3. **Distillation pipeline is functional** — Correction examples are fetched, sent to LLM for guardrail extraction, and inserted into `promptTemplatesTable`.

### Missing Coverage

1. **No concurrent execution test** — ADR-008 §Verifiability requires "Concurrent test runners MUST attempt to claim the same pending task simultaneously. DB assertions MUST prove exactly 1 worker transitions the task to ACTIVE." No such test exists.
2. **No DLQ test** — ADR-008 requires "inject a mocked deterministic-failing task... assert the task transitions to DEAD_LETER_FILE." No such test exists.
3. **No zombie recovery** — If a metabolism tick crashes, there's no mechanism to detect and reclaim stuck locks.
4. **No metrics/observability** — No tracking of metabolism tick duration, success rate, or failure rate.

## Overall Verdict

**❌ FAIL**

The metabolism worker implements the DB-backed queue pattern correctly at a high level, but critically fails to implement the distributed mutex specified in ADR-008. The fake in-memory boolean is the exact anti-pattern the master roadmap Phase 6 (Hardening) was designed to eliminate. Combined with the unauthenticated tick endpoint (a security vulnerability that can be exploited to exhaust API budgets), this item requires immediate remediation before production deployment.

**Required fixes:**
1. Replace `let isMetabolismRunning` with a PostgreSQL advisory lock or `FOR UPDATE SKIP LOCKED` row claim pattern
2. Add `locked_at` timestamp column to pending task queries for zombie recovery
3. Add authentication to `/metabolism-tick` (API key or internal-only)
4. Implement DLQ routing for failed tasks
5. Add concurrent execution tests per ADR-008 §Verifiability
