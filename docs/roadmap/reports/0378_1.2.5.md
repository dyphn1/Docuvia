## Round 1 — Architecture & Design Review

### Design ↔ Implementation Alignment

**✅ Correctly implemented:**

1. **Streaming log parser** — `getSvnLog()` uses `AsyncGenerator` with SAX streaming parsing of `svn log --xml` output. This is well-designed: memory-efficient, backpressure-aware, and properly cleans up the subprocess via `AbortController` in the `finally` block.

2. **Shell injection prevention** — All subprocess invocations use `spawn()`/`execFile()` with argument arrays (not shell string interpolation). The `revRange` is constructed from typed `number` parameters. URL validation enforces `https?://` or `svn://` scheme.

3. **Incremental ingestion** — The `lastSvnRevision` field on `projectsTable` correctly tracks the last ingested revision. The route reads this on `mode: "incremental"` and starts from `lastSvnRevision + 1`, preventing re-ingestion.

4. **Revision-based deduplication** — `processIngestion()` checks for existing commits with `eq(commitsTable.revision, c.revision)` + `vcsType: "svn"`, preventing duplicate ingestion of the same SVN revision.

5. **Batching** — The ingestion route buffers up to 50 items before flushing via `processIngestion()`, preventing unbounded memory growth for large SVN histories.

6. **Error resilience** — Individual diff fetch failures are caught and logged (`svnErrors.push(...)`) without aborting the entire ingestion. The route returns both `svnErrors` and `ingestErrors` separately, aiding debugging.

### Gaps / Deviations

1. **⚠️ Diff concatenation into message field (architecture drift)** — The primary checklist finding. `ingestion-pipeline.ts` line 145 constructs `fullMessage = c.diff ? \`${c.message}\n\n${c.diff}\` : c.message`, then stores this combined blob in `commitsTable.message` (truncated to 4000 chars). This violates ADR-014 (Database-as-IPC): diffs are structural data that should be separately indexed for graph queries, not blob-concatenated into a text field. Consequences:
   - The diff content is lost if it exceeds 4000 - len(message) characters
   - No structured access to diff data for L3 node generation (the diff is the primary source for change analysis)
   - Git commits store `diff` separately in their pipeline path; SVN's concatenation is inconsistent

2. **⚠️ Missing diff storage column** — The `commitsTable` has no `diff` column. Git commits store the diff as part of `message` too (line 95: `message: c.message.slice(0, 4000)`), but Git commits have their full content hashed in `hash` (SHA). SVN commits use synthetic `svn:R${revision}` hashes which provide no content integrity.

3. **⚠️ No commit hash for SVN commits** — SVN uses `hash: \`svn:R${c.revision}\`` which is a synthetic identifier, not a content hash. This means:
   - No integrity verification (same revision could have different content if re-ingested after SVN history modification)
   - The `commitsTable.hash` column's uniqueness guarantee is weakened for SVN entries

## Round 2 — Code Quality & Security Review

### Strengths

1. **Command injection protection** — `spawn()` with array args, `execFile()` with array args, regex-validated URL. No shell interpolation risk.

2. **Resource cleanup** — `getSvnLog()` uses `AbortController` + `finally { abortController.abort(); svnProcess.kill(); }`. This is correct and prevents zombie SVN processes on client disconnect.

3. **Authentication handling** — `--no-auth-cache` and `--non-interactive` flags prevent credential persistence on the server filesystem. Password is passed per-invocation only.

4. **Error categorization** — SVN CLI not-found errors (`ENOENT`) are handled with a user-friendly message clearly stating the prerequisite.

### Issues Found

1. **⚠️ No authentication/authorization on SVN ingestion route** — `POST /projects/:id/ingest/svn` has no auth middleware. Any client can trigger SVN ingestion for any project by ID. While this is a systemic issue (no auth middleware exists on any route — consistent with reports 0376, 0377), the SVN route is particularly sensitive because it accepts `username`/`password` in the request body which are forwarded to the SVN server. An attacker could use this endpoint to probe internal SVN servers via the API server as a proxy.

2. **⚠️ Credential exposure in request body** — `username` and `password` are sent in plaintext in the request body. The body is logged via pino-http (though URL query strings are stripped, body content is not). This risks SVN credentials appearing in server logs.

3. **🟡 No rate limiting on diff fetching** — For large SVN histories, the ingestion performs one `svn diff -c REVISION` subprocess per revision sequentially. This can create a thundering herd against the SVN server, especially for full-mode ingestion of large repositories. A delay or concurrency limit would be protective.

4. **🟡 XML parser error handling** — The SAX parser's `error` event calls `reportError()`, but the `parser.on("error", ...)` handler does not reset the parser state. After a SAX error, the parser may be in an inconsistent state and subsequent entries could be silently lost.

## Round 3 — Integration & Completeness Review

### Integration Correctness

1. **SVN log → ingestion pipeline flow** works end-to-end: `getSvnLog()` streams revisions → route fetches diffs per revision → `processIngestion()` creates commit records with scoring → `lastSvnRevision` is updated for incremental mode.

2. **Commit scoring** correctly uses `scoreCommit(c.message, c.diff)` for SVN, same as Git. The diff content informs the `DIFF_TODO_BONUS` and `DIFF_LENGTH_BONUS` heuristics.

3. **Activity log and notification** — `processIngestion()` calls `logAndNotify()` for SVN ingested commits, consistent with Git pathway.

### Missing Coverage

1. **⚠️ No dedicated SVN test coverage** — Integration or unit tests for the SVN ingestion path are not colocated with the source files. The `getSvnLog()` generator and `getSvnDiff()` are untestable without an SVN server mock.

2. **⚠️ Git vs SVN pipeline divergence** — Git ingestion uses batched DB transactions (`db.transaction()` with `batchSize = 50`) for efficiency, while SVN processes items one-by-one in a simple for loop (`for (const c of svnItems)`). For large SVN histories, this creates N individual INSERT statements without transaction grouping — a performance regression vs Git.

3. **🟡 No SVN URL deduplication** — Multiple ingestion requests for the same SVN URL / project pair can run concurrently. No mutex or lock prevents parallel ingestion from creating duplicates (though the revision-based dedup check mitigates this at the row level).

## Overall Verdict

**⚠️ WARN**

The SVN integration is functional for basic use cases — log streaming, diff fetching, incremental mode, deduplication, and error handling are all implemented correctly. The architecture drift flagged in the checklist is real: diffs are concatenated into the `message` field rather than being stored as structured data, losing content beyond 4000 chars and preventing diff-based graph queries (per ADR-014). This is not a breaking defect (SVN ingestion works), but it prevents proper L3 node generation from SVN diff content and creates an inconsistency with the Git-isomorphic graph design. The absence of authentication on the SVN route (systemic issue) and credential handling concerns add to the risk profile.
