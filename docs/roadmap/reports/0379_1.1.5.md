## Round 1 — Architecture & Design Review

### Design ↔ Implementation Alignment

**✅ Correctly implemented:**

1. **OpenAI-compatible client wrapper** — `integrations-openai-ai-server` is a self-contained package that wraps the official `openai` SDK with environment validation (`AI_INTEGRATIONS_OPENAI_BASE_URL`, `AI_INTEGRATIONS_OPENAI_API_KEY`). This provides a single injection point for swapping providers later.
2. **Per-project model switching** — `llm_config.ts` exposes CRUD for `llm_configsTable` with `provider` and `model` columns. `generate.ts` reads the model via `getModel(projectId, override)` and passes it to every `openai.chat.completions.create()` call. This correctly supports per-project model selection.
3. **Multi-modal coverage** — The package covers chat completions, image generation/editing, audio (voice chat, TTS, STT), and batch processing — all from a single abstraction.
4. **Graceful degradation** — `embedding.ts` returns `null` on failure with a warn-level log, allowing fallback to SQL LIKE search. `intent-router.ts` falls back to `vector_search` on classification failure.

### Gaps / Deviations

1. **⚠️ No true abstraction layer — direct OpenAI coupling** — Despite being called an "LLM abstraction layer," the package is an OpenAI-specific wrapper, not a generic LLM interface. All imports across the codebase reference `@workspace/integrations-openai-ai-server` directly. There is no generic `LlmClient` interface that could be implemented for Anthropic, Ollama, or other providers. The `provider` column in `llmConfigsTable` exists but is never read or used — `generate.ts`'s `getModel()` only returns the model string, and the OpenAI client is hardcoded.
2. **⚠️ Stale ADR reference** — The checklist references "ADR-004-openai-compatible-llm-interface-only.md" but ADR-004 is "Git-Isomorphic Graph." There is no ADR documenting the OpenAI-only constraint. The actual constraint appears to be an architectural decision (ADR-003 mentions OpenAI usage) but is not formally specified.
3. **⚠️ Provider column unused** — `llmConfigsTable` has a `provider` field (default "openai"), but no code reads or acts on it. The `LlmConfigInputSchema` allows `provider` in PATCH but it's stored and returned without any provider-specific routing logic.
4. **⚠️ Hardcoded model names in multiple places** — `embedding.ts` hardcodes `text-embedding-3-small`, `intent-router.ts` hardcodes `gpt-4o-mini`, `image/client.ts` hardcodes `gpt-image-1`, `audio/client.ts` hardcodes `gpt-audio` and `gpt-4o-mini-transcribe`. Only the generate pipeline respects the per-project model config. This means "per-project model switching" only applies to chat completions, not embeddings, intent routing, image generation, or audio.

## Round 2 — Code Quality & Security Review

### Strengths

1. **Environment validation at module load** — `client.ts` throws immediately if env vars are missing, failing fast rather than at first API call.
2. **Error handling in embedding** — `generateEmbedding()` catches errors and returns `null` with logging, enabling graceful fallback.
3. **Input sanitization** — `intent-router.ts` sanitizes queries before sending to LLM.
4. **Rate limiting in batch** — `batch/utils.ts` uses `p-limit` and `p-retry` for concurrency control and automatic retry with backoff.
5. **Temp file cleanup** — `audio/client.ts` uses `try/finally` with `unlink().catch()` for temp files.

### Issues Found

1. **⚠️ No auth on llm_config routes** — `llm_config.ts` exposes GET and PATCH `/projects/:id/llm-config` without any authentication middleware. Any caller can read or modify LLM config for any project. This is an internal-only concern if the API is not exposed publicly, but it's a gap for multi-tenant deployments.
2. **⚠️ `as any` cast in audio client** — `voiceChat()` and `voiceChatStream()` use `message as any` to access `message.audio?.transcript` and `message.audio?.data`. This bypasses TypeScript's type system for OpenAI's audio response shape. A proper type definition would be safer.
3. **⚠️ Hardcoded default model `gpt-5.2`** — The default model in `llm_config.ts` and `generate.ts` is `gpt-5.2`, which may not exist or may be deprecated. This should be validated or at least documented as a placeholder.
4. **⚠️ Missing error handling in image client** — `generateImageBuffer()` and `editImages()` don't have try/catch. If the OpenAI API returns an error or `response.data` is empty, the function will throw an unhandled error rather than degrading gracefully.
5. **⚠️ `editImages()` has unused `outputPath` parameter** — The parameter is typed but the function always returns the buffer regardless. If `outputPath` is provided, it writes to disk AND returns the buffer — this dual behavior is undocumented and could cause confusion.

## Round 3 — Integration & Completeness Review

### Integration Correctness

1. **Generate pipeline** — Correctly reads per-project LLM config via `getModel()` and passes the model to all `openai.chat.completions.create()` calls. The pipeline orchestrates LLM calls for L1/L2/L3 generation, content synthesis, and noise detection.
2. **Metabolism** — Uses `openai.chat.completions.create()` for content synthesis with the project's configured model. Correctly integrated.
3. **Intent router** — Uses `openai.chat.completions.create()` for query classification with `gpt-4o-mini`. Has fallback logic.
4. **Embedding** — Uses `openai.embeddings.create()` with `text-embedding-3-small`. Has graceful null fallback.
5. **GitHub webhooks** — Uses `openai.chat.completions.create()` for PR analysis.

### Missing Coverage

1. **❌ No generic LLM interface** — The architecture cannot swap LLM providers without modifying every import. A `LlmClient` interface with `chat()`, `embed()`, `generateImage()`, etc. methods would be required for true provider abstraction.
2. **❌ Per-project model switching is incomplete** — Only `generate.ts` and `metabolism.ts` use the per-project model. Embedding, intent routing, image generation, and audio all use hardcoded models.
3. **❌ No provider routing** — The `provider` field in the config is stored but never acted upon. There is no factory or strategy pattern to select an LLM client based on provider.
4. **⚠️ No retry logic in core chat calls** — Only `batch/utils.ts` has retry logic. Direct `openai.chat.completions.create()` calls in `generate.ts`, `intent-router.ts`, `metabolism.ts` have no retry on transient failures (rate limits, 5xx errors).

## Overall Verdict

**⚠️ WARN**

The `integrations-openai-ai-server` package is a functional OpenAI-specific wrapper with good environment validation, multi-modal coverage, and graceful degradation in key paths. However, it is **not a true abstraction layer** — it is a thin wrapper around the OpenAI SDK with no interface abstraction, no provider routing, and hardcoded model names in most modules. The per-project model switching (via `llm_configsTable`) only applies to the chat completion pipeline; embeddings, intent routing, image generation, and audio all use hardcoded models regardless of project config. The `provider` field is stored but never acted upon, making the "OpenAI-compatible only" constraint implicit rather than enforced by architecture. This is a known and accepted state per the checklist legend (⚠️ WARN = uses a fallback or has architectural drift), but it should be documented that the "abstraction layer" is aspirational, not structural.
