## Round 1 — Architecture & Design Review

### Design ↔ Implementation Alignment

**✅ Correctly implemented:**

1. **LLM-based intent classification** (line 129–176) — 4-way routing via `classifyIntent()` matches ADR-007 specification
2. **Vector search handler exists** (`vectorSearchHandler`, line 182–378) — generates embeddings and searches both L2 and L3 nodes
3. **Temporal decay integration** — `calculateTemporalDecay()` applied to vector scores with 30-day half-life, matching ADR-007
4. **Fallback mechanism** — SQL LIKE fallback when embedding generation fails (line 289–373) with `sanitizeLikeInput()` for injection prevention
5. **Hybrid search** — `hybridSearch()` (line 562–610) correctly combines vector + graph traversal with intersection boosting
6. **Fast-path short-circuit** (line 626–647) — exact match bypass for single-word queries (Max's Rule)

### Gaps / Deviations

1. **❌ pgvector NOT implemented** — ADR-019 (Accepted 2026-06-25) mandates `vector(1536)` column type with IVFFlat/HNSW indexes. Actual implementation:
   - `l2_nodes.embedding` is `text("embedding")` (JSONB text), NOT `vector(1536)`
   - `l3_nodes.embedding` is `text("embedding")`, NOT `vector(1536)`
   - No `CREATE EXTENSION IF NOT EXISTS vector;` found anywhere in migrations or schema files
   - No IVFFlat/HNSW index definitions

2. **❌ In-memory cosine similarity** — `intent-router.ts` loads ALL embeddings into Node.js heap:
   - Lines 207–218: fetches all L2 nodes with non-null embeddings, then computes cosine similarity in JS
   - Lines 264–274: same for L3 nodes via INNER JOIN
   - This is exactly the OOM risk ADR-019 was designed to prevent
   - Code comment at line 209 explicitly acknowledges: `// TODO: [CRITICAL BUG FIX] - pgvector migration missing. In-memory cosine similarity will OOM on large graphs.`

3. **⚠️ Dual implementation paths exist but disconnected:**
   - `vector-search.ts` (`performVectorSearch`) uses `embedding::vector <=> ${vectorStr}::vector` SQL syntax — the CORRECT pgvector approach
   - BUT: it references `embedding::vector` cast which requires pgvector extension (will fail on current schema where embedding is `text`)
   - `performVectorSearch` is NOT called from `intent-router.ts` — it's an orphaned module, unused

4. **❌ No database migration** — No SQL migration files found for adding pgvector extension or altering column types

## Round 2 — Code Quality & Security Review

### Strengths

1. **Input sanitization** — `sanitizeQuery()` (line 106–111) truncates to 2000 chars and strips control characters; `sanitizeLikeInput()` escapes LIKE wildcards
2. **Defensive embedding parsing** — `parseEmbedding()` handles null/invalid JSON gracefully
3. **Structured logging** — `logger.warn/error/info` used appropriately throughout
4. **Confidence clamping** — `Math.max(0, Math.min(1, parsed.confidence))` prevents out-of-range values
5. **Strategy validation** — `VALID_STRATEGIES` Set validates LLM output before use

### Issues Found

1. **⚠️ SQL injection risk in vector-search.ts (line 43–44):**
   ```typescript
   rawScore: sql<number>`1 - (embedding::vector <=> ${vectorStr}::vector)`
   ```
   `vectorStr` is built from `embedding.join(",")` — if the embedding array contained string-controlled values (unlikely from OpenAI, but possible from cached/computed embeddings), this could be exploited. The cast to `::vector` provides some protection but is not parameterized.

2. **❌ Schema mismatch — TEXT vs VECTOR:**
   Casting `text::vector` in raw SQL only works if the pgvector extension is installed AND the column actually stores vector-compatible text format. The current `text` column stores JSON arrays like `[0.0123, -0.0456, ...]` which IS compatible with pgvector text input format — so `::vector` cast would work IF extension is enabled. But without the extension, it throws an error.

3. **⚠️ Performance — N+1 project lookups:**
   Lines 221–224: for each L2 result, a separate query fetches project name. Should be batched or JOINed.

4. **⚠️ Double sort (line 376–377):**
   ```typescript
   results.sort((a, b) => b.score - a.score);
   results.sort((a, b) => b.score - a.score);
   ```
   Duplicate sort — no functional impact but indicates incomplete refactoring.

## Round 3 — Integration & Completeness Review

### Integration Correctness

1. **Route integration** — `routeQuery()` correctly dispatches to `vectorSearchHandler` for `vector_search` and `hybrid` strategies
2. **End-to-end flow works** for small datasets: query → embedding generation → in-memory cosine similarity → temporal decay → ranked results
3. **Search route** (`search.ts`) does NOT import `performVectorSearch` from `vector-search.ts` — the pgvector-ready implementation is completely disconnected from the live API

### Missing Coverage

1. **pgvector extension setup** — No migration, no Docker compose config, no deployment documentation
2. **IVFFlat/HNSW index creation** — Required per ADR-019 for sub-millisecond retrieval at scale
3. **Data migration script** — Existing JSONB embeddings need to be verified/transitioned to vector columns
4. **Connection pool sizing** — Vector search with pgvector may require different pool configuration
5. **Monitoring/metrics** — No tracking of vector search latency, index hit rates, or fallback frequency

## Overall Verdict

**⚠️ WARN**

The vector search functionality is **architecturally incomplete** per ADR-019 (pgvector migration accepted 2026-06-25). The current implementation works for small-scale development but will fail at production scale due to OOM risks. A correct pgvector implementation already exists in `vector-search.ts` but is completely disconnected from the live system. The checklist correctly marks this as ⚠️ WARN ("Temporarily mocked, uses a fallback, or has architectural drift") — the in-memory approach is a known architectural drift from the accepted ADR.

**Recommended priority:** HIGH — This is a Phase 6 (Architecture Hardening) item per the master roadmap. The `vector-search.ts` module provides a ready-made migration path that just needs to be wired into `intent-router.ts` and the schema needs the `vector(1536)` column type + indexes.
