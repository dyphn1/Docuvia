## Round 1 — Architecture & Design Review

### Design ↔ Implementation Alignment

**✅ Correctly implemented:**

1. **OpenAI-compatible client** — `integrations-openai-ai-server` provides a clean singleton `openai` client initialized from environment variables (`AI_INTEGRATIONS_OPENAI_BASE_URL`, `AI_INTEGRATIONS_OPENAI_API_KEY`). This allows any OpenAI-compatible endpoint (e.g., local LLM via `OPENAI_BASE_URL` override).
2. **Per-project model switching** — `llm_configs.ts` stores per-project `model` and `provider` in the DB. `generate.ts` reads `cfg?.model` and passes it to the OpenAI API call, allowing different projects to use different models.
3. **Graceful degradation** — `embedding.ts` returns `null` on failure with a warn log, allowing fallback to SQL LIKE search.
4. **Input validation** — `llm_config.ts` uses Zod schema (`LlmConfigInputSchema`) for PATCH body validation.
5. **Environment-based secrets** — API keys are read from env vars, not hardcoded.

### Gaps / Deviations

1. **⚠️ Provider abstraction is cosmetic** — The `provider` column in `llm_configs` is stored but never read by `generate.ts`. The system is hardcoded to use the OpenAI client regardless of the `provider` value stored in the database. Changing `provider` to "anthropic" in the DB would have zero effect.
2. **⚠️ No abstraction interface** — All LLM consumers (`generate.ts`, `embedding.ts`, `intent-router.ts`, `metabolism.ts`, `pull_requests.ts`, `github_webhooks.ts`) import directly from `@workspace/integrations-openai-ai-server`. There is no `LlmProvider` interface or factory pattern.
3. **⚠️ LLM proxy is a mock** — `llm-proxy.ts` is wired at `/proxy/v1` but returns mock responses (`"This is a mock proxy response"`). It compresses prompts correctly but never forwards to a real LLM endpoint.
4. **⚠️ Stale ADR reference** — Checklist references "ADR-004-openai-compatible-llm-interface-only.md" which doesn't exist. ADR-004 is "git-isomorphic-graph.md".

## Round 2 — Code Quality & Security Review

### Strengths

1. **Clean error handling** — `embedding.ts` uses try/catch with structured logging and graceful null fallback.
2. **Zod validation** — `llm_config.ts` validates PATCH input before database writes.
3. **Environment variable guard** — `client.ts` throws descriptive errors if required env vars are missing at module load time.
4. **Text truncation** — `embedding.ts` slices input to 8192 chars to avoid token limit errors.
5. **No secrets in code** — All credentials from environment.

### Issues Found

1. **⚠️ Dead code path** — `llm-proxy.ts` is mounted in `app.ts` but never called by any route. The generate pipeline calls OpenAI directly, bypassing the proxy entirely. The proxy returns mock responses, making it non-functional for production use.
2. **⚠️ Unused DB column** — `provider` in `llm_configs` is write-only (set by `llm_config.ts`, never read by any consumer). This is technical debt — future developers may assume it works.

---

## Round 3 — Integration & Completeness Review

### Integration Correctness

1. **OpenAI direct path works** — `generate.ts` → `openai.chat.completions.create()` is the live path and functions correctly with any OpenAI-compatible endpoint.
2. **Embedding pipeline works** — `embedding.ts` → `openai.embeddings.create()` with `text-embedding-3-small` is wired into the ingestion pipeline.
3. **Per-project config works** — `llm_config.ts` CRUD → `generate.ts` reads model config → passes model name to OpenAI API.

### Missing Coverage

1. **No multi-provider support** — Despite the DB schema suggesting it, there is no code path that uses the `provider` field to select a different LLM client.
2. **No provider interface/factory** — Adding a new provider (e.g., Anthropic, Ollama-compatible) requires touching every file that imports `openai`.
3. **LLM proxy not production-ready** — The `/proxy/v1/chat/completions` endpoint is a mock that echoes back compressed prompts without calling a real LLM.

## Overall Verdict

**⚠️ WARN**

The LLM abstraction layer is **functional for OpenAI-compatible endpoints** but the "abstraction" is limited to:
1. Environment-variable-based endpoint switching (any OpenAI-compatible server works)
2. Per-project model name configuration in the DB

True multi-provider support (Anthropic, Ollama, etc.) is not implemented — the `provider` column in the schema is dead, and all consumers hardcode the OpenAI import. This matches the checklist's existing ⚠️ WARN status and the AGENTS.md design decision to default strictly to OpenAI-compatible endpoints. The system works correctly within its stated scope.
